## HIGH — pattern drift / dead branches

### H1-v2. Dep validation drift across the 6 factories
The 6 `createX(deps) → fn` modules use the same shape but inconsistent
strictness. Canonical pattern reads as: **strict TypeError throws for
required deps; `logger=console` defaulted; non-fatal helpers (processEnv,
fetchImpl) defaulted.** Drift:

| File | Required validated | Notable gap |
|---|---|---|
| `lib/sdk/build-options.js:68-71` | 4 of 4 | clean |
| `lib/sdk/callbacks.js:40-52` | 13 of 13 | clean — most thorough |
| `lib/handlers/voice.js:32-39` | 8 of 8 | clean |
| `lib/handlers/download.js:44-48` | 5 of 5 | `bot` is **passed at call time** to `downloadAttachments(bot, ...)` not validated at factory time — by design, since one factory serves many bots. Distinct pattern; document. |
| `lib/handlers/config-callback.js:35-42` | 8 of 8 | clean — `bot` is implicit via `ctx`. |
| `lib/handlers/abort.js:38-45` | 8 of 9 | **`bot` is used at line 85 (`tg(bot, …)`) but NOT validated** at the factory entry. Inconsistent vs `config-callback.js` which gets `bot` from ctx. If `bot` is null at boot, the abort handler will fail at first invocation, not at factory creation. |

Fix: pick canonical and apply. Recommendation:
- Required-at-factory deps → strict TypeError throw at the top.
- `logger=console` and other safe defaults → keep.
- For `lib/handlers/abort.js`, add `if (!bot) throw new TypeError('bot required');` to match the other 5.

## MEDIUM — naming clarity

### M1-v2. `lib/handlers/voice.js` vs `lib/telegram/voice.js`: ambiguous
- `lib/telegram/voice.js` — Whisper transcription engine + voice attachment
  detection (`transcribe`, `isVoiceAttachment`). Header at line 2-9
  describes openai/whisper.cpp backends — **transport-agnostic**, NOT
  Telegram-specific. Naming under `telegram/` is misleading.
- `lib/handlers/voice.js` — orchestration: download → transcribe →
  persist transcription → emit ack reaction. Telegram-specific
  (`setMessageReaction`, etc).

The `telegram/voice.js` placement is the inverse of intent — it's the
non-Telegram primitive being misclassified as Telegram-coupled. Suggest:
- `lib/voice.js` for the transcription engine (move out of `telegram/`).
- `lib/handlers/voice.js` stays — it's the Telegram-coupled orchestrator.

This pattern recurs once: `lib/error/net.js:redactBotToken` is also
Telegram-coupled (token redaction for `bot${TOKEN}`-shaped URLs) but
sits under `error/`. Naming suggests "error networking" but it's
actually "Telegram bot token redaction." Less critical (one helper).

### M2-v2. `lib/sdk/router.js` description-vs-implementation mismatch
File at `:7` describes itself as a "thin single-pm wrapper" — actual
implementation at `:35-38` is `({ pm }) => pm`. Three-line wrapper, 22
lines of comment. Not strictly drift but the comment-to-code ratio
suggests the seam isn't earning its keep. v1's H2 flagged this; the
header was compressed but not deleted.

### M3-v2. `lib/handlers/download.js` factory does not validate `bot`
v1's H1-style drift recurs in Phase B: `download.js` accepts `bot` as
a per-call argument but does not document or validate it at factory
time. Compare:
- `download.js:159` — `async function downloadAttachments(bot, token, chatId, msg, rows)`
- `abort.js:65` — `await pm.interrupt(sessionKey)` uses `bot` from
  factory closure (line 28).

Two valid patterns: factory-bound bot vs per-call bot. Pick one.
Factory-bound is simpler when the factory already binds `botName`
(both abort and download bind `botName`); the bot itself is the
runtime instance and passing it per-call adds nothing.
