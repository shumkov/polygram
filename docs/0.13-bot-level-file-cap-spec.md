# Spec v2 — Configurable file-size caps (default + bot + chat + topic), send & receive

Status: **DRAFT v2 — revised after 5-persona review (adversarial / feasibility / scope / security / correctness)**
Target: polygram 0.13.x · prod fleet (shumabit + umi-assistant on UMI VPS, local Bot API server → 2 GB capable)

## 0. Operator decisions (signed off)
1. **Default (no override anywhere) = 20 MB** both inbound and outbound — a new `config.defaults.maxFileBytes` tier (today there is no default; it falls to the 2 GB backend ceiling).
2. **`shumabit` bot-level = 100 MB.** `umi-assistant` = no bot override → inherits the **20 MB default**.
3. **Over-cap outbound = throw loudly** (no silent file drops).
4. **Scope = cap ALL outbound paths.** On prod (SDK) the real agent file-send path is **IPC/cron** (SDK replies are text-only); also covered: CLI `reply(files)`. file_id/URL sends are uncapped by design (not locally sizable).
5. **Keep the 2 GB backend ceiling** — capability preserved; any tier clamps to it.

**Precedence (both directions):** `topic ?? chat ?? bot ?? default ?? backend-ceiling`, then `resolveFileCaps` clamps to the backend ceiling.

## 1. Current state (code-verified)
- `maxFileBytes` exists at **topic** + **chat** tiers only (`polygram.js:798`: `_inTopicCfg.maxFileBytes ?? chatConfig.maxFileBytes ?? null`). No bot tier, no default tier.
- Backend ceilings (`lib/attachments.js` `resolveFileCaps`): cloud 20 MB in / 50 MB out; **local Bot API server = 2 GB both ways**. Overrides clamp down, never exceed.
- **Inbound filter** (`polygram.js:796-803`, `filterAttachments`) is backend-agnostic and uses the override. ✅ But **the inbound DOWNLOAD** (`lib/handlers/download.js:67`) calls `resolveFileCaps({ localApi })` **without the override** → streams at the 2 GB ceiling. Gap (see §3.3b).
- **Outbound** is enforced only in CLI mode (`channels-tool-dispatcher.js:291` via `CliProcess.maxOutboundFileBytes`, resolved `topic ?? chat` only — no bot tier). **Prod runs SdkProcess** → no outbound check today. **IPC/cron path** (`ipc-send.js` → `tg`) has no size check.
- **Single send chokepoint confirmed:** `tg = createSender(db, console)` (`polygram.js:2177`) → `send()` (`lib/telegram/api.js:112`). The dispatcher gets it as `send: tg`, ipc-send gets `tg`, `deliver.js` calls the same closure. `config` (module-level, post-`filterConfigToBot` so `config.bot`/`config.chats`/`config.defaults` are populated) is in scope at 2177 and is **mutated in place** at runtime (never reassigned) → a captured reference stays live.
- **No config schema validation** (`loadConfig` is bare `JSON.parse`; `filterConfigToBot` checks only `bots`/`chats` presence) → adding `defaults.maxFileBytes` / `bots.<n>.maxFileBytes` is accepted and round-trips through `saveConfig`.
- SDK replies are **text-only** (`lib/prompt.js`: "Do NOT use Telegram MCP tools"; `build-options.js` wires no reply-files MCP tool). There is **no SDK `reply(files)`** path to cap.

## 2. Design

### 2.1 New tiers in config
- **Default:** `config.defaults.maxFileBytes` (bytes). `config.defaults` already exists (timeout/maxTurn) and survives `filterConfigToBot` (spread). Global, both bots.
- **Bot:** `config.bots.<name>.maxFileBytes` → readable as `config.bot.maxFileBytes` after `config.bot = config.bots[BOT_NAME]` (`polygram.js:2141`). Mirrors the existing `config.bot.pm` tier (`factory.js`).

### 2.2 Single source of truth — `resolveMaxFileOverride(config, chatId, threadId)`
One resolver, used by **every** site (inbound filter, inbound download, outbound `send()`, CLI pre-check) so precedence can't drift (the existing CLI-vs-inbound drift is *why* this is centralized):
```js
// precedence: topic ?? chat ?? bot ?? default ?? null  (resolveFileCaps then clamps to ceiling)
function resolveMaxFileOverride(config, chatId, threadId = null) {
  if (!config) return null;
  const chat = config.chats?.[String(chatId)] || null;
  const topicCfg = (chat && threadId != null) ? getTopicConfig(chat, String(threadId)) : null;
  return topicCfg?.maxFileBytes
    ?? chat?.maxFileBytes
    ?? config.bot?.maxFileBytes
    ?? config.defaults?.maxFileBytes
    ?? null;
}
```
- **Reuse `getTopicConfig`** (`lib/session-key.js:99`) for topic resolution — do NOT hand-roll `chat.topics[t]` (review: avoids divergence with the normalization every other site uses). Placement: verify `lib/session-key.js` has no `require` of `lib/attachments.js` before importing it there; if circular, host `resolveMaxFileOverride` in `session-key.js` (which already owns `getTopicConfig`) and re-export, or in a tiny new `lib/file-cap.js`. **Decision at impl time; no hand-rolled topic lookup.**
- **`maxFileBytes` semantics:** must be a positive byte count. `resolveFileCaps` (`attachments.js:62`) treats `<= 0`/non-number as "no override" → falls through to the next tier / backend default. Document: `0` is **not** "block all"; it's "no override." (Parity with today.)

### 2.3 Receive — inbound filter (`polygram.js:~798`)
Replace the inline chain with `override: resolveMaxFileOverride(config, chatId, threadIdStr)`. Feeds `filterAttachments` as today. Backend-agnostic → works on SDK prod.
Note the existing `maxTotalBytes: Math.max(_fileCaps.inBytes, MAX_TOTAL_BYTES)` coupling: a per-file cap above 50 MB also raises the album total budget. With a 20 MB default this *lowers* nothing below 50 MB (Math.max keeps 50 MB total) — acceptable; out of scope to change total-budget separately.

### 2.3b Receive — close the download gap (`lib/handlers/download.js:~67`) [from review B4]
`downloadOneAttachment` must use the override too, or a file with falsified/zero `file_size` (which `filterAttachments` budgets as worst-case but does **not** reject, since `0 > cap` is false) gets streamed up to 2 GB. `createDownloadAttachments` already receives `config`; `chatId` is in scope and `threadId` = `msg.message_thread_id`. Change line 67 to:
```js
const cap = resolveFileCaps({
  localApi: !!config.bot?.apiRoot,
  override: resolveMaxFileOverride(config, chatId, msg?.message_thread_id?.toString() || null),
}).inBytes;
```
This makes the streaming/local-link cap match the filter cap. (Cloud is already hard-bounded at 20 MB by getFile; this matters on the local-API path.)

### 2.4 Send — enforce at the `send()` chokepoint (`lib/telegram/api.js`)
The universal outbound enforcement (covers CLI dispatcher, IPC/cron, and any media polygram itself emits). Concrete, fully-specified:

**Imports (top of api.js):**
```js
const fs = require('fs');
const { coerceFileParams, FILE_FIELD_BY_METHOD } = require('./input-file');
const { resolveFileCaps, resolveMaxFileOverride } = require('../attachments'); // or wherever resolver is hosted
```
**New helper (exported from `input-file.js`, which owns the `{source}` shape — keeps the bare-string=file_id rule co-located):**
```js
// Bytes for a LOCALLY statable file param, else null (skip — file_id / URL / stream / InputFile).
// Bare strings are file_ids/URLs by coerceFileValue's contract → never statSync them.
function localFileBytes(v) {
  if (Buffer.isBuffer(v)) return v.length;
  if (v && typeof v === 'object' && typeof v.source === 'string'
      && v.source.startsWith('/') && !/^https?:\/\//i.test(v.source)) {
    try { return fs.statSync(v.source).size; } catch { return null; }  // missing/unreadable → skip, don't crash the send
  }
  return null;
}
```
**Cap check in `send()` — placed BEFORE `coerceFileParams` (api.js:122), while the param is still raw; chatId/threadId already derived at api.js:113-114:**
```js
const mb = (n) => (n / (1024 * 1024)).toFixed(1);
const fileField = FILE_FIELD_BY_METHOD[method];
if (config && fileField && params[fileField] != null) {
  const bytes = localFileBytes(params[fileField]);
  if (bytes != null) {
    const cap = resolveFileCaps({
      localApi: !!config.bot?.apiRoot,
      override: resolveMaxFileOverride(config, chatId, threadId),
    }).outBytes;
    if (bytes > cap) {
      throw new Error(`telegram ${method}: file ${mb(bytes)}MB exceeds the ${mb(cap)}MB send limit`);
    }
  }
}
```
**Wiring:** `createSender(db, logger = console, config = null)` → `(bot, method, params, meta) => send({ bot, method, params, db, meta, logger, config })`; `send({ …, config = null })`; `polygram.js:2177` → `tg = createSender(db, console, config)`. `config = null` default makes the guard a clean no-op (back-compat for the ~30 `send()` test calls + `createSender(db, logger)` in tests).
**Placement is load-bearing:** the throw is at function top, *before* `insertOutboundPending` (api.js:183) and before the markdown/HTML retry layers → no orphan `pending`/`failed` row, no double-send, no fallback interaction. (Verified by review; pin with a test.)
**Covered methods** = the 7 keys of `FILE_FIELD_BY_METHOD` (photo/document/audio/video/animation/voice/videoNote). `sendSticker` is excluded (file_id-based, not a local upload) — intentional.

### 2.5 CLI consistency (fold into the shared resolver — no parallel precedence) [review B2 + scope §3.5]
On prod this path is inactive (SDK), but to prevent the drift the panel flagged, the CLI pre-check + system-prompt line must use the **same** resolver, not a second inline chain:
- `buildSpawnContext` (`polygram.js:~481`) passes `outboundCapOverride: resolveMaxFileOverride(config, chatId, threadId)`.
- `cli-process.js:616` → `const _capOverride = topicConfig?.maxFileBytes ?? opts.outboundCapOverride ?? null;` — wait: that double-counts topic. Cleaner: pass the resolver's result and use it directly: `_capOverride = opts.outboundCapOverride ?? null` (the resolver already applied topic→chat→bot→default). The system-prompt "Max file size" line (`cli-process.js:828`) then matches `send()`.
- ctx→opts plumbing for `outboundCapOverride` rides the same path as `opts.localApi` (verified: `start(spawnContext)` → `_spawnTmuxClaude` reads `opts.*`).
- If we prefer to keep the diff minimal: **defer** this section and document that on CLI mode the dispatcher pre-check/system-prompt may understate the cap (send() still enforces correctly). Decision: **include it** (low cost, removes drift) unless impl reveals plumbing friction.

### 2.6 Out of scope / documented limitations
- **file_id / public-HTTPS sends are uncapped** (can't size locally). Trust boundary: the cap is resource-control for honest use, **not** an exfiltration barrier — a compromised/prompt-injected agent could `sendDocument` a large file_id/URL. Stated explicitly (review security F2).
- Lowering the local Bot API server's own 2 GB ceiling.
- A separate inbound **total**-bytes bot/default tier (only per-file is configured; total stays `Math.max(perFile, 50MB)`).
- Multi-file CLI `reply(files)` partial-delivery: an over-cap file mid-batch is rejected by the dispatcher pre-check before send (friendly message); earlier files already delivered. CLI-only; documented.

## 3. Edge cases to test
1. Default-only (no bot/chat/topic) → 20 MB both ways (umi-assistant).
2. Bot tier present → 100 MB (shumabit); chat override beats bot; topic beats chat.
3. Override > ceiling → clamped (no escape past 2 GB / cloud 20-50).
4. `config.bot.maxFileBytes` & `config.defaults` unset, `config = null` → behaves as today (no cap); guard no-op.
5. Over-cap `sendDocument({source})` → throws with MB figures; under-cap → sends; **no `messages` row left pending/failed**.
6. `localFileBytes`: `{source:/abs}` over→throw; `{source:'https://…'}`→null (no statSync, no ENOENT); bare-string file_id→null; missing `{source}` path→null (no crash); Buffer over→throw; InputFile/stream→null.
7. Inbound: zero/absent `file_size` file on local-API → download cap now = override (not 2 GB) [B4].
8. `maxFileBytes: 0` → treated as "no override" → next tier/backend default (documented).
9. Clamp math: `resolveFileCaps({localApi:true, override:100MB}).outBytes === 100MB`; cloud `override:100MB` → out clamps to 50 MB, in to 20 MB.
