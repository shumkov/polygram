# 0.10.0 followup: pinning the claude binary (not just the version string)

> **RESOLVED in 0.10.0-rc.19.** Polygram now spawns the absolute
> versioned binary `~/.local/share/claude/versions/<version>` via
> `lib/claude-bin.js`, never the bare `claude` on `$PATH`.
>
> The investigation found the claude CLI's real install model:
> each version is a standalone immutable binary under
> `~/.local/share/claude/versions/`, and `~/.local/bin/claude` is a
> symlink the auto-updater re-points. Spawning the absolute
> versioned path is a true pin — the updater only adds new files,
> never overwrites — so none of the heavier options (A bundle /
> B npm-dep / C cache) were needed. `POLYGRAM_CLAUDE_BIN` overrides
> the path for non-standard installs / CI / tests.
>
> See `AGENTS.md` "How the pin is enforced". The rest of this doc
> is kept for the research context.

## Why this matters

rc.15 added `CLAUDE_CLI_PINNED_VERSION = '2.1.142'` and a boot-time
`claude --version` check that WARNs on mismatch. That's better than
nothing but it's not actually a pin:

- `claude install` / `npm i -g @anthropic-ai/claude-code` can update
  the binary on PATH between polygram runs — even between turns.
- Claude Code's auto-update mechanism may bump the binary without
  user action.
- The boot check only fires ONCE; mid-session updates aren't caught.
- A WARN is easy to miss in logs; production deployments may run
  for days on a drifted CLI before anything visibly breaks.

The tmux backend reads internal CLI artefacts (JSONL format, queue
semantics, banner ASCII, READY hints, paste behaviour). Any of these
can change across CLI versions. We need polygram to spawn a SPECIFIC
binary that won't drift, period.

## Research questions

### Q1 — How does the claude CLI ship + update?

- npm package `@anthropic-ai/claude-code`? Confirm version semantics
  (does `npm i -g <pkg>` give a stable version, or does it have
  internal auto-updates?).
- `claude install` subcommand — what does it install, where, and
  how is it invoked? Native binary? Bundled Node?
- Is there a `--no-auto-update` flag or env var
  (`CLAUDE_CODE_NO_AUTO_UPDATE`?) that disables the in-process
  updater for the spawned session?
- Where does claude store its installed-version binary by default?
  `~/.claude/binaries/<version>/`? `/usr/local/bin/claude` symlink?
  npm global prefix?

### Q2 — What are the pinning options?

Three candidate approaches, listed in order of robustness:

#### A) Bundle a specific claude binary in polygram's repo

Pros:
- Hermetic. No matter what's installed system-wide, polygram uses
  ITS bundled binary.
- Trivially reproducible across hosts.

Cons:
- Binary size in repo (10-50 MB?). Inflates git history.
- Per-platform builds — Mac arm64, Mac x64, Linux, etc. Need
  multiple binaries OR a build step.
- Anthropic licensing — can polygram legally redistribute the
  claude binary? Read the LICENSE.

#### B) npm-install a specific version into polygram's node_modules

In polygram's `package.json`:
```json
{
  "dependencies": {
    "@anthropic-ai/claude-code": "2.1.142"
  }
}
```

Then spawn from `node_modules/.bin/claude` (or wherever the
package's bin entry points). The version is locked by polygram's
own `package.json` + `package-lock.json`.

Pros:
- npm handles the install/distribution.
- Version is part of polygram's source tree (package.json).
- Survives system-wide claude updates.
- Reproducible via `npm ci`.

Cons:
- npm-installed claude may have a different auto-update path than
  the standalone binary. NEEDS VERIFYING — does `node_modules`-
  installed claude run an in-process updater?
- The package may not be on the public npm registry (TBD — Q1).
- Bin entry point + invocation may differ from the global binary.

#### C) Symlink-managed per-polygram binary cache

Polygram maintains `~/.polygram/claude-cache/<version>/claude` and
spawns from that absolute path. On first boot at a new pinned
version, polygram downloads or builds the binary. The path it
spawns is unaffected by system PATH or system-wide updates.

Pros:
- Decouples polygram entirely from system claude state.
- Can support multiple polygram instances on different versions.

Cons:
- Needs a download/install mechanism — what's the source of
  truth for a specific binary? (Q1.)
- Cache lifecycle / cleanup logic.

### Q3 — Disabling claude's in-process auto-update

Even if we spawn the right binary, claude itself may auto-update on
startup. Need to know:

- Is there a `CLAUDE_CODE_NO_AUTO_UPDATE=1` env var? Check the
  CLI's `--help` for related flags.
- Is `--bare` mode enough to disable auto-update? (rc.4 release
  notes mention `--bare` skips hooks/LSP/plugin-sync — does it
  skip self-update too?)
- If no flag exists, polygram could spawn claude with a writable
  install dir that's deliberately empty/locked, so any update
  attempt fails harmlessly.

### Q4 — Runtime fingerprint, not just version string

Even if claude reports v2.1.142 on `--version`, the binary on disk
might have been swapped. Defense-in-depth options:

- Hash the binary (`shasum`) at boot; compare against a pin.
- Include the binary hash in the rc commit when the pin is bumped.
- Polygram's daemon refuses to spawn TmuxProcess if hash mismatch.

This is harder to maintain (every CLI release means recomputing
the hash) but eliminates the "version string lies" risk entirely.

### Q5 — What does Anthropic publish?

- Is there a public release notes / changelog for each claude
  CLI version? Where?
- Does Anthropic distinguish "breaking" releases from minor /
  patch?
- What's the auto-update cadence (daily? per-session?
  on-demand?).

## Investigation steps (when you tackle this)

1. Read the `claude` CLI source (or behaviour) for:
   - How `--version` is computed.
   - The auto-update mechanism (look for `update`, `upgrade`,
     `fetch latest` patterns).
   - `claude install` semantics.
   - Env vars / flags that disable auto-update.
2. Check the npm registry: does `@anthropic-ai/claude-code` exist
   publicly? Versions list?
3. Test option B (npm-install): add to polygram's `package.json`,
   spawn from `node_modules/.bin/claude`. Verify the spike still
   passes against this binary.
4. If B works: write the runner change to use the local path,
   delete the boot-time version-check warning (replace with a
   hash check), document in AGENTS.md.
5. If B doesn't work (no public package, auto-update on
   `node_modules` path): fall back to option C and design the
   cache layout.

## Acceptance criteria

- Polygram cannot accidentally run against an unpinned claude
  version. Either it spawns the correct binary or refuses to
  start.
- Bumping the pinned version is one PR with: package.json
  / pin constant / hash / spike pass evidence.
- A `claude update` invocation outside polygram does NOT affect
  the running daemon.
