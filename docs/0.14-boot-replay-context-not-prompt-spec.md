# Spec v3 — Boot-replay: skip stale re-answers on a deliberate restart, with visibility

Status: **DRAFT v3.1 — hardened after a second review pass + prod-data validation** (v1 context-injection killed by review; v2 "skip-dispatched/recover-replay-pending" killed by prod data; v3 direction validated, integration hardened in §9)
Target: polygram 0.14.x
Origin: 2026-06-16 — a deploy restart re-answered a stale screenshot + prompt. Operator: *"if you resume the session you're not supposed to load old shit."*

## 0. Design history (why we're on v3)

- **v1 — "inject downtime messages as a context note the agent judges."** Killed by review: there is no non-turn injection path on a resumed Claude session (every channel is a `role:'user'` turn; the SessionStart hook is verified-dead). "Context" collapses to "one bundled prompt."
- **v2 — "on clean shutdown skip `dispatched` chatter, recover `replay-pending` in-flight; the 30 s drain separates quick interactive from long autonomous."** Killed by **prod data** (§2): the drain does NOT separate them.
- **v3 (this) — don't try to auto-classify. On a deliberate restart, SKIP re-dispatch and make it VISIBLE. On crash, recover all (unchanged).**

## 1. Current behavior (code-verified)

- Boot-replay (`polygram.js` ~2751-2826): `getReplayCandidates({chatIds, olderThanMs: replayWindowMs})` → inbound rows in `handler_status IN ('dispatched','processing','replay-pending')` within `1.2 × max(maxTurn)` (~72 min), deduped, **re-dispatched as fresh turns** (👀 ack, `preMark:'replay-attempted'`).
- **Dedup = `hasCompletedTurnFor`** (turn_metrics, `error IS NULL`), NOT `hasOutboundReplyTo` (rc.51 turned that off; ack-bubbles caused false "replied" drops — the rc.50 incident). v3 keeps `hasCompletedTurnFor`.
- Shutdown (`polygram.js` ~2612-2697; SIGTERM/SIGINT/SIGHUP): drains ≤ `SHUTDOWN_DRAIN_MS` (30 s), then `markReplayPending` flips still-in-flight rows → `'replay-pending'`. On the VPS this **completes** (`shutdown-drain {in_flight, elapsed_ms}` + `polygram-stop` fire every restart; `systemctl` gives `TimeoutStopSec=90s`, `ExecStop=tmux kill-server`→SIGHUP). The "pkill 1 s" footgun is the legacy Mac/tmux path, not `systemctl`.
- `polling_state` (migration 005): `(bot_name, last_update_id, ts)` — the home for a marker column.

## 2. Prod data that drove v3 (shumabit.db, n=3430 turns)

| turn duration | share |
|---|---|
| <10 s | 14% |
| 10–30 s | 33% |
| 30–60 s | 20% |
| 1–5 m | 29% |
| 5–30 m | 4% |
| >30 m | **0% (2 ever)** |

- **53% of turns run ≥30 s** → outlive the 30 s drain → become `replay-pending` on restart. So `replay-pending` is the *common* state for ordinary interactive turns, not a marker of "long autonomous work." v2's split is invalid.
- The **4 real `replay-pending` rows are 3/4 conversational**, incl. the rc.57 case `msg151 "how it goes? resume?"` — **a user message**. So neither `handler_status` nor trigger-source separates skip-vs-recover.
- `>30 m` turns ≈ 0: the "7-hour Xero task" was many *normal-length* turns; its interrupted turn is indistinguishable from a chat reply. **No automatic skip-vs-recover classifier exists.**
- Restarts re-dispatch only **0–1** turns each (`replay-on-boot` events) — small blast radius; the pain is re-firing even one.

**Conclusion:** stop trying to classify. Decide by *intent of the restart* (deliberate vs crash), and make the deliberate-skip visible.

## 3. Design

### 3.1 Clean-shutdown marker (DB, not a file)
Chosen DB over a sentinel file (operator's call, and correct): the marker is written **in the same transaction** as `markReplayPending` (no torn state where the marker says "clean" but rows weren't marked), cleared transactionally on read, queryable, and free of stray-file/perms/cleanup hazards. Cost is a trivial nullable column.

- New column `polling_state.clean_shutdown_at INTEGER` (migration; nullable, back-compat). Per-bot (PK is `bot_name`).
- **Write**: in the shutdown handler, in the **same transaction** as `markReplayPending`, set `clean_shutdown_at = <now>`. (After the drain; co-committed with the in-flight→`replay-pending` marking.) If the process dies before this commits → no marker → crash branch.
- **Read+clear at boot-start** (before the replay loop), transactionally: read `clean_shutdown_at`, then set it to NULL in the same statement/txn. "Clean" iff non-null and within a recency bound (≤ a few × `replayWindowMs`). Any other state → crash. Clear-on-read is what stops a stale marker from a prior boot reading as clean after a later crash.
- Fail toward recovery: missing/stale/unreadable → crash (recover).

### 3.2 Boot disposition
After the existing `hasCompletedTurnFor` dedup, for the candidate set:
- **Crash** (no fresh marker): re-dispatch ALL — *current behavior, untouched*. rc.57 cannot regress here.
- **Clean** (fresh marker): **skip ALL candidates** — mark each terminal (`'replay-skipped'`, one-shot like `'replay-attempted'` so they don't re-fire now or re-surface next boot). No re-dispatch, no 👀 storm. Then **emit ONE visibility notice** (§3.3) if any were skipped.

We do NOT split by `handler_status` (§2 proves it meaningless). A deliberate restart skips everything pending; the resumed session still has full conversation context, so the agent continues naturally on the next real interaction.

### 3.3 Visibility notice (the rc.57 mitigation)
rc.57's harm was *silent* abandonment. On a clean restart that skipped ≥1 candidate, emit **one** concise message per affected chat/topic:

> `↺ Restarted. I didn't auto-resume N message(s) you sent before the restart: "<short>"… If any still need a reply, send it again.`

- One message, informational — NOT N re-answers. Gated on `skippedCount > 0`.
- Per `(chat_id, thread_id)` group (isolateTopics-safe).
- Delivered via the normal send path (`tg`), logged.
- This is the operator's "I'm here, I'll re-ask if needed" loop — visible, not silent, and bounded (0–1 per restart per the data).

### 3.4 Keep
`resolveReplayWindowMs` (still bounds candidates), `markReplayPending` on shutdown, `hasCompletedTurnFor` dedup, attachment re-fetch (now working post-0.13.2 — only relevant on the crash/recover path).

## 4. Observability
- `replay-on-boot` event + `[replay]` log report **classification (clean/crash)** and **recovered vs skipped** counts; per skipped row log `msg_id`/`thread_id`.
- Add `replay-on-boot` to `keepForeverKinds` (`lib/db/events-retention.js`) — currently pruned at 90 d.

## 5. Spikes (de-risk before integration)
1. **Marker round-trip + atomicity** (`spikes/` or a test): with a `freshDb`, write `clean_shutdown_at` in the same txn as a `markReplayPending`-style update; assert read-and-clear returns clean once then crash (null) after; assert a stale value (older than the recency bound) reads as crash; assert it's per-bot.
2. **Disposition purity**: a pure `classifyReplay({candidates, cleanShutdown, hasCompletedTurn})` → `{recover, skip}`; assert clean→all-skip, crash→all-recover(after dedup), dedup excludes completed.
3. **Marker-on-real-restart** (read-only confirmation, not a deploy): we already see `markReplayPending` + `polygram-stop` (DB writes in the handler) fire on every VPS restart — evidence the same-txn marker write will land. Confirm by adding the write behind a flag in a dev run, or accept the existing-evidence and cover with the unit spike.

## 6. Test plan (red→green; assert behavior, not tautology)
Extract the disposition + marker into pure-ish modules (like `replay-window.js`) so they're unit-testable without booting the daemon.
- **Clean → all candidates SKIPPED**: 0 `redeliverAsFreshTurn`; rows → `'replay-skipped'`; exactly one notice emitted with the skipped list; **outbound re-answer count to those msg_ids = 0**.
- **Clean, 0 candidates → no notice.**
- **Crash (no marker) → all RECOVERED** (rc.57 pin) — re-dispatch fired.
- **Stale marker** (write clean → simulate crash without clear) → next boot = crash → recovers. (Highest-severity silent-skip path.)
- **Clear-on-read**: marker present → read once → gone → second boot with no new marker = crash.
- **Dedup**: ack-bubble row (outbound, no completed turn) is still a candidate via `hasCompletedTurnFor` (not `hasOutboundReplyTo`).
- **One-shot skip**: skipped on clean boot N → not re-surfaced on boot N+1.
- **isolateTopics**: notices grouped per `(chat_id, thread_id)`; no cross-topic leakage.
- Integration (real-claude): a deliberate restart mid-conversation produces a single notice and **no re-answer**; a simulated crash still recovers.

## 7. Rollout
1. Migration (add `clean_shutdown_at`) + marker module + disposition module + notice; extract for tests.
2. Spikes + tests green; targeted re-review (reliability + correctness — crash-recovery is touched only on the unchanged crash path; the new surface is the clean-skip + marker).
3. Release 0.14.0 → deploy (better-sqlite3 rebuild, sequential). First deploy: no marker yet → crash branch → recovers (safe); subsequent deliberate restarts skip + notice.
4. Verify: a deliberate redeploy mid-conversation → one notice, no re-answer; a simulated crash → recovers.

## 9. Hardening from the second review pass (v3.1) — implementation requirements

The v3 *direction* (decide by restart intent; crash path untouched; visible skip) was validated; the pure disposition module + the marker spike pass. These are the integration requirements the re-review made mandatory — the spike now proves the marker ones against the real `polling_state`:

**H1 — Marker written UNCONDITIONALLY on every clean shutdown.** Real `markReplayPending` (`lib/db.js:629`) only runs in the shutdown handler's `if (remaining>0)` branch (`polygram.js:2655`); the common clean-drain-with-nothing-in-flight case never calls it. The marker must be a standalone write that fires on *every* clean shutdown (in the same txn as `markReplayPending` when it runs, else its own txn) — else a stale `replay-pending` row from a prior life is crash-recovered on a deliberate restart (rc.57 re-fire). Add a combined `db.recordCleanShutdown({botName, now})` (markReplayPending's UPDATE + the marker UPSERT in one `db.raw.transaction`); `markReplayPending` is a bare `.run()` today and is NOT a joinable txn.

**H2 — Marker UPSERT must satisfy `polling_state` NOT NULL (`last_update_id`, `ts`, migration 005).** A fresh/quiet bot has no `polling_state` row (created only on a non-empty getUpdates batch). The upsert must `COALESCE` existing values or seed defaults (`0`, `now`) — proven in the hardened spike — or the first shutdown throws.

**H3 — Migration 013 + bump `SCHEMA_VERSION` 12→13.** `runMigrations` early-returns when `user_version >= SCHEMA_VERSION` (`lib/db.js:46`); adding `clean_shutdown_at` without the bump silently skips on every deployed (v12) DB → "no such column". (The repo has a documented prior occurrence of exactly this.) Test: a v12 DB upgrades to v13 with the column.

**H4 — Marker read has its OWN try/catch → default crash.** The boot-replay block has a single swallowing try/catch; a thrown marker read (missing column, DB error) would skip ALL recovery (silent total loss). Wrap the read so any error ⇒ `clean=false` (recover). Reject future-dated markers (clock skew) and markers older than `2 × resolveReplayWindowMs(config)` (derived, not a magic constant).

**H5 — Gate the skip/notice set through the SAME gate the crash path uses.** The crash path routes candidates through `redeliverAsFreshTurn → gateInbound(tier:'redelivery')` (`polygram.js:2810`), which drops `/new`, `/compact`, `/model`, pair-claims, and abort-shaped rows (`gate-inbound.js:129-132,109-113`). `classifyReplay` has no gate → v3 would post *"I didn't auto-resume your /new."* Filter the skip+notice set through the same predicate; admin/abort rows are skipped silently (never re-answered ⇒ never announced).

**H6 — Boot disposition ordering (idempotent, fail-toward-recovery).** The crash-seam risk lives in the unwritten caller. Required order: read marker (do **not** clear) → gate+classify → for each `(chat,thread)` group: send the notice in its own try/catch; **only on confirmed send** mark that group's rows terminal `'replay-skipped'`; on send failure leave the rows non-terminal (recoverable) + emit `replay-notice-failed` → after all groups, clear the marker last. A boot interrupted mid-loop re-runs the clean branch next boot; already-`replay-skipped` rows are excluded by `getReplayCandidates`' status IN-list (one-shot), so notices don't double-send. `'replay-skipped'` must be added to NO live-candidate IN-list.

**H7 — Observability.** Per skipped row emit detail `{msg_id, thread_id, text_snippet, age_ms, handler_status}`; emit `replay-notice-sent {chat_id, thread_id, notice_msg_id}` / `replay-notice-failed {chat_id, thread_id, error}`. Add `replay-on-boot` + these to `keepForeverKinds` (`lib/db/events-retention.js`). This is what proves in production whether a real task was skipped-and-announced vs silently lost.

**H8 — Grouping separator.** Use a NUL (`\x00`) separator in the per-`(chat,thread)` key (defensive; no real collision today since ids are numeric strings).

## 8. Risks
- **A genuine long task interrupted by a deliberate restart is not auto-resumed** — now VISIBLE (the notice); on a deliberate restart the operator is in the loop and can re-trigger. The trade vs rc.57's *silent* loss; the notice is the safety net. (Data: ≤1 such item per restart.)
- **Open: the unattended-autonomous case** (review premise gap). The "operator is present, can re-ask" assumption holds for interactive deploys; for an AUTOMATED deploy (CI→ansible→systemctl) interrupting an *autonomous* task (e.g. a scheduled job), "skip + notice" leaves a tombstone the chat may not surface to anyone in time. Prod data: the 4 historical `replay-pending` rows were all *user* messages (incl. the rc.57 Xero case, a user "resume?"), and turn-runtime can't classify (Xero ran as normal-length turns) — so we cannot auto-detect "autonomous." Decision needed (see §11).
- **Considered + rejected — "suppress only already-acked re-answers" (smaller).** Targets the operator's exact complaint without skip-all. Rejected because "already acked but not completed" is precisely the rc.50 ack-bubble ambiguity (`hasOutboundReplyTo` was turned OFF in rc.51 for causing false "answered" drops); detecting it reliably is the unsolved problem, and `hasCompletedTurnFor` already removes *completed* turns. Skip-all-on-clean + gate (H5) + notice is simpler and doesn't reintroduce that ambiguity.

## 11. Open decision — the unattended-autonomous trade

For a deliberate restart that interrupts an **autonomous** (non-user-triggered) turn:
- **(A) Skip + notice (recommended).** Uniform skip-all-on-clean; the notice is the awareness mechanism. Simplest; matches the data (≤1 candidate/restart; historically all user-triggered). A truly unattended autonomous job is a rare residual; if it bites, escalate to (B) as a follow-up.
- **(B) Recover autonomous-wakeup-triggered candidates, skip user-triggered.** Auto-resume scheduled/cron tasks (no human) while skipping interactive chatter. Handles the unattended case better, but adds trigger-source detection and doesn't help the rc.57 "resume?" case (user-triggered → still skipped+notice, but the operator was present there anyway). More surface.
- **Marker reliability**: same-txn write + clear-on-read + fail-to-crash; pinned by the stale-marker test. Crash path is unchanged, so rc.57 can't regress through it.
- **Notice noise**: bounded to ≥1-skipped clean restarts (rare); one message, not N.
- **Automated/unattended clean deploys**: the notice still fires to the chat, so awareness isn't tied to someone watching the deploy.
