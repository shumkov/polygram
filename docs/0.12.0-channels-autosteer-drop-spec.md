**Parent:** autosteer (`lib/handlers/autosteer.js`, `lib/autosteered-refs.js`, channels

**Prod evidence (Shumabit@UMI "hire" topic, 2026-06-09):**

| msg | time | what |
|---|---|---|
| 2384 in | 23:14:33 | "1. I fixed it" → starts a turn |
| **2385 in** | **23:15:00** | **"let's update it once tomorrow morning"** → `inject-user-message` + `autosteer` (✍, priority next) |
| 2386 out | 23:15:01 | reply to 2384 only ("Cleaned up. ✅ Aoff…") |

The 2384 turn was **tool-less** (`num_tool_uses=0`) and cleared at 23:15:01 — one second after 2385
was injected. 2385 was never folded into 2386 and never ran as its own turn. **Dropped.** From the
user's seat: "claude missed my message."

---

## Problem

On channels, autosteer dispatches a mid-turn follow-up via `pm.injectUserMessage`, which writes it
to the bridge as a fresh `user_msg` (F#24) — **best-effort**: "claude usually folds it into the
current response cycle but MAY treat it as a distinct next turn… the bridge protocol doesn't
expose a true mid-stream merge" (cli-process.js F#24 comment). When the in-flight turn ends
**before** claude folds the injected message — most reliably when the turn is **tool-less** (it
finishes in one quick response cycle with no tool round-trips to absorb the late input) — the
message is neither folded nor promoted to a new turn. **It is silently lost.**

The SDK used to catch exactly this: `drainStaleAutosteerBuffer` re-dispatched buffered follow-ups
as a synthetic new turn "where a turn ended with zero tool calls (no hook fire, followups would
otherwise be lost)" (`polygram.js:387-389`). That safety net was deleted when the SDK moved to
native priority push. Channels never had a native push to make it obsolete — so channels is now
running **without** the safety net **and** without the guarantee. This spec restores the safety
net for the channels backend only.

## Mechanism (verified)

- `autosteer.tryAutosteer` → `pm.injectUserMessage({content, priority:'next', msgId})` →
  `CliProcess.injectUserMessage` writes a `user_msg` to the bridge with a fresh `turn_id`
  (cli-process.js ~2396). The msg gets a ✍ reaction and is tracked in `autosteeredRefs`
  (`lib/autosteered-refs.js`) so the trigger turn's success can clear it.
- The proc emits `'idle'` at turn-end (cli-process.js 1441/1542); polygram's success path calls
  `clearAutosteeredReactions(sessionKey)` (`polygram.js:404`) to drop the ✍ refs.
- **Gap:** that clear is unconditional — it removes the ✍ whether or not the injected message was
  actually folded/answered. Nothing checks "did this follow-up get addressed?" before discarding it.

## Design

**Restore a channels stale-drain at the turn-end hook.** When the trigger turn ends, before
clearing the autosteered refs, decide whether each autosteered follow-up was addressed; if not,
**re-dispatch it as a fresh turn** through the normal path so claude answers it.

### 1. Detection — was the autosteer folded? (Decision A)

Options, cheapest→most precise:

- **(A1) Tool-less-turn heuristic** (mirrors the old SDK stale-drain). If the trigger turn ended
  with `num_tool_uses === 0`, assume the late-arriving injected msg was NOT folded (a tool-less
  turn is one fast response cycle; a msg injected at its tail can't be absorbed). Re-dispatch any
  autosteered refs for that turn. Simple, matches the historical rule, and the prod case is exactly
  this. False-positive risk: a tool-less turn that DID fold the follow-up → a duplicate re-dispatch
  (claude sees it twice). Mitigated by (B).
- **(A2) turn_id correlation** (precise). Track each injected msg's `turn_id`; if no reply/turn
  ever resolves it by the time the trigger turn ends, it wasn't processed → re-dispatch. Requires
  the bridge/cli-process to surface "this injected turn_id never produced output," which it does
  not cleanly today (injected msgs aren't first-class pendingTurns). More implementation, fewer
  false positives.
- **(A3) Reply-coverage check.** Inspect whether the trigger turn's reply text plausibly addressed
  the follow-up — rejected: unreliable, model-dependent, not worth it.

**Recommendation: A1 (tool-less heuristic) for v1**, guarded by the de-dupe in B. It fixes the
observed case with minimal surface; A2 is the precise follow-up if A1's false-positive rate is
non-trivial in practice.

### 2. Re-dispatch + loop-safety (Decision B)

Re-dispatch the original follow-up message as a fresh turn via `dispatchHandleMessage` (the same
entry the autonomous-wakeup + edit-redelivery paths reuse), reconstructing the message from its
stored row. **Loop-safety is mandatory:** the re-dispatched turn must NOT itself be eligible for
re-drain (mark it so a second tool-less turn doesn't re-drain it again), and a message must be
drained **at most once** (clear it from the autosteer tracker the moment it's re-dispatched).

### 3. Where it hooks

At the turn-end success path that already calls `clearAutosteeredReactions(sessionKey)`
(`polygram.js`). Before/within that clear: if the just-ended turn qualifies (A1) and has
autosteered refs, re-dispatch them, then clear. A failed re-dispatch still clears the ✍ but logs
`autosteer-stale-drain-failed` so it's visible (never silently swallow twice).

## Scope

**In:** channels/cli backend only (where `injectUserMessage` is a best-effort bridge write).
**Out:** SDK backend — native priority push genuinely folds/queues; no drop. **Out:** the
multi-tool-turn case — if the turn made tool calls, claude had absorption points and the fold is
reliable; A1 deliberately only fires on tool-less turns. **Out:** changing the autosteer decision
itself (when to ✍ vs queue) — this only adds the post-hoc safety net.

## Edge cases

- **Multiple follow-ups autosteered into one turn** → re-dispatch all, in arrival order, as
  sequential turns (or one combined turn — Decision C).
- **Follow-up that WAS folded into a tool-less turn** (A1 false positive) → claude sees it twice.
  Acceptable v1 (claude reconciles "you already told me this"); A2 removes it.
- **Trigger turn errored / was killed** → don't re-dispatch into a dead session; the next user
  message naturally re-establishes context. Guard on a live session.
- **Re-dispatch races a brand-new user message** → ordering: drain BEFORE accepting the next
  message, or let the next message naturally supersede (Decision D).
- **`/stop` during the trigger turn** → treat as intentional; do NOT re-drain.

## Test plan

Unit (`tests/handlers-autosteer.test.js` / a turn-end-drain test, deterministic with fakes):
1. Tool-less trigger turn ends with an autosteered ref → re-dispatches that follow-up via
   `dispatchHandleMessage` exactly once, then clears the ref.
2. Trigger turn WITH tool calls ends with an autosteered ref → does NOT re-dispatch (A1 scope).
3. A re-dispatched follow-up is marked so a subsequent tool-less turn does NOT re-drain it (no loop).
4. Errored/killed trigger turn → no re-dispatch into the dead session.
5. Multiple autosteered refs → all re-dispatched once, in order.
6. Re-dispatch failure → ref still cleared + `autosteer-stale-drain-failed` logged (no silent loss
   on the failure path either).

Plus a forensic regression mirror of the prod trace: a tool-less turn with an autosteer that
produced no reply → emits an `autosteer-stale-drain` event for the dropped msg_id.

## Decisions (for sign-off)

- **A. Detection = A1 tool-less heuristic (v1), A2 as precise follow-up.** *Confirm, or go straight
  to A2.*
- **B. Re-dispatch via `dispatchHandleMessage`, at-most-once, loop-guarded.** *Confirm.*
- **C. Multiple follow-ups: sequential turns vs one combined turn.** Recommended: **combined** (one
  re-dispatch carrying all un-folded follow-ups, in order) — fewer turns, matches "fold" intent.
  *Confirm.*
- **D. Ordering vs a new inbound message during drain.** Recommended: drain on the `'idle'` before
  the next dispatch; if a newer message already arrived, let normal dispatch handle it and drain
  rides as context. *Confirm.*
