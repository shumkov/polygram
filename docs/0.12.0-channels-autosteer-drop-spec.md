## The bug

On the **channels/cli backend**, autosteer dispatches a mid-turn follow-up via
`pm.injectUserMessage` → `CliProcess.injectUserMessage` writes it to the bridge as a fresh
`user_msg` (F#24). This is **best-effort**: claude "usually folds it into the current response
cycle but MAY treat it as a distinct next turn — the bridge protocol doesn't expose a true
mid-stream merge" (cli-process.js F#24 comment). When the in-flight turn ends **before** claude
folds the injected message — most reliably when the turn is **tool-less** (one fast response cycle,
no tool round-trips to absorb the late input) — the message is **neither folded nor promoted to a
new turn. Silently lost.**

The SDK once caught this (`drainStaleAutosteerBuffer`, re-dispatched buffered follow-ups when a
turn "ended with zero tool calls"); it was deleted as "obsolete with native priority push"
(`polygram.js:380-390`). Channels has no native push, so the deletion **regressed channels** — it
runs without the safety net AND without the guarantee.

### Prod evidence (Shumabit@UMI "hire" topic, 2026-06-09)

| msg | time | what |
|---|---|---|
| 2384 in | 23:14:33 | "1. I fixed it" → starts a turn |
| **2385 in** | **23:15:00** | **"let's update it once tomorrow morning"** → autosteered (✍, priority next) |
| 2386 out | 23:15:01 | reply to 2384 only ("Cleaned up. ✅ Aoff…") |

The 2384 turn was **tool-less** (`num_tool_uses=0` in turn_metrics) and cleared 1s after 2385 was
injected. 2385 was never folded into 2386 and never ran as its own turn. From the user's seat:
"claude missed my message." This is the canonical instance — **but it is the only confirmed one;
frequency is unmeasured (see Q3).**

## Why the obvious fix (A1 tool-less heuristic) is DEAD — review findings

The original design re-dispatched a follow-up when the trigger turn ended with
`num_tool_uses === 0`. Five personas killed it:

1. **P0 (feasibility + adversarial, conf 100): the signal doesn't exist on channels.** `CliProcess`
   hardcodes `numToolUses: null` in every turn result (`cli-process.js:1434` success, `:1637`
   interrupt) — never `0`. So `=== 0` never fires (no-op), and a falsy check (`!num_tool_uses`)
   fires on EVERY turn (mass double-dispatch). claude's tool calls happen behind the bridge TUI;
   polygram does not count them. A1 is unimplementable as written.
2. **P1 (adversarial): base-rate inversion.** Folds are the NORM (the F#24 quote), drops the
   exception. Among tool-less autosteered turns the common case is *folded* — so even a working A1
   would re-dispatch already-answered follow-ups and **double-answer on the majority of fires**.
3. **P1 (adversarial + feasibility): the error path still drops.** `clearAutosteeredReactions` also
   fires in the unconditional `finally` (`polygram.js:1678`) on errored/timed-out turns → refs
   cleared with no drain → the prod incident recurs on errored turns. (And the hook reference
   "~404" is the function *definition*; there are 7 clear sites — the channels success path is the
   `result.alreadyDelivered` early-return `~1382-1397`.)
4. **P1 (scope + coherence + security): duplicate machinery + a gate gap.** Re-dispatch +
   `_isReplay` + `dispatchHandleMessage` is exactly what `lib/handlers/edit-redelivery.js` now
   ships — it should be *reused*, not re-implemented. That path also re-gates via `shouldHandle`,
   which the drain omitted → a stale re-dispatch would bypass pairing/mention (security).
5. **P1 (feasibility/adversarial/security): loop-guard has no mechanism.** `_isReplay` does NOT gate
   autosteer (`autosteer.js` checks only `inFlight`). Counterpoint (feasibility, conf 75): a
   re-dispatched turn hits an *idle* session, so `tryAutosteer` returns `{autosteered:false}` and
   the msg is never re-added to `autosteeredRefs` — the loop is mostly closed *structurally*, but a
   re-dispatch landing while a NEW turn is in flight could re-autosteer (needs a real marker).
6. **P2: `autosteeredRefs` stores only `{chatId,msgId}`** (not the message) → re-dispatch must
   `db.getMessage` + rebuild via the boot-replay pattern; **and** the follow-up's row is already
   `status='replied'` (its autosteer turn called `markReplied`), so it lacks boot-replay's one-shot
   guard.

## Investigation questions for the fresh session (answer before designing)

- **Q1 — Right layer?** Is a *post-hoc drain* (re-dispatch the dropped follow-up after the turn) the
  right fix, or should channels autosteer be made *reliable upstream* so it doesn't drop? Prior art:
  the native-queue / U7 spike (`scripts/spikes/native-queue.mjs`, superseded for SDK) and the
  `{continue:false}` PostToolBatch force-end-turn primitive. Is there a channels-bridge equivalent
  that would let an injected follow-up reliably become a next turn instead of being best-effort?
- **Q2 — Detection signal (if post-hoc):** the precise approach is **A2 — turn_id correlation**:
  fire ONLY on actual drops (no base-rate problem, no tool-count needed). The injected `user_msg`
  carries a fresh `turn_id` (`cli-process.js ~2396`); `CliProcess` already correlates reply
  `turn_id`s → pending turns (`~1201`). Can an injected `turn_id`'s resolution be observed (did it
  ever produce a reply by trigger-turn-end)? What instrumentation is needed to make injected msgs
  first-class enough to track?
- **Q3 — Measure first.** Pull the fold-vs-drop ratio from prod telemetry before building anything:
  `inject-user-message` / `autosteer` events vs turns that produced a matching reply. If drops are
  rare (likely), weigh the machinery against the frequency — dropping the feature may be correct.
- **Q4 — Reuse.** Extract a shared `redeliverAsFreshTurn(sessionKey, chatId, msg, bot)` from the
  edit-redelivery logic (reconstruct from db row, `_isReplay` tag, re-gate via `shouldHandle`,
  immediate-ack reaction). The drain (if built) becomes a thin caller. Avoid a parallel impl.
- **Q5 — Error/`/stop` path.** The prod incident was a tool-less *success*, but errored/timed-out
  turns ALSO drop the follow-up (the `finally` clear). Should the drain cover those (with a
  live-session guard), or are errored-turn follow-ups knowingly dropped?

  ~2701-2742`.
- **Tests precedent:** `tests/handlers-edit-redelivery.test.js`.

## Candidate approaches (for the fresh session to weigh)

- **(A) A2 post-hoc drain** — track injected `turn_id` resolution; on a real drop, `redeliverAsFreshTurn`. Precise, but needs injected-msg tracking instrumentation.
- **(B) Upstream reliability** — make channels autosteer deterministically become a next-turn when not folded (bridge-level), eliminating the drop. Bigger, but removes the class.
- **(C) Drop the feature** — accept the rare drop; the prod watcher flags recurrence. Cheapest if Q3 shows drops are vanishingly rare.

## Original design (REJECTED — A1 is dead; preserved for context)

> Everything below is the pre-review design. Do NOT build it. It is kept so the investigation can
> see what was tried and why each piece failed (the review findings above map onto it).

**Restore a channels stale-drain at the turn-end hook.** When the trigger turn ends, before
clearing the autosteered refs, decide whether each autosteered follow-up was addressed; if not,
re-dispatch it as a fresh turn through the normal path.

- **(A1) Tool-less-turn heuristic** — if the trigger turn ended with `num_tool_uses === 0`, assume
  the injected msg was NOT folded → re-dispatch. ← **dead: `num_tool_uses` is `null` on channels;
  and folds are the norm so this double-answers.**
- **(A2) turn_id correlation** — track each injected msg's `turn_id`; if no reply ever resolves it
  by turn-end, re-dispatch. ← **the surviving direction (Q2).**
- **(A3) Reply-coverage check** — inspect whether the reply addressed the follow-up. Rejected:
  unreliable/model-dependent.

Re-dispatch via `dispatchHandleMessage`, at-most-once, loop-guarded; hook at the success path that
calls `clearAutosteeredReactions`. Edge cases: multiple follow-ups, A1 false positive (double
send), errored/killed turn, ordering vs a new message, `/stop`. (All re-examined in the review
above.)
