# 0.12.0 — Known issues / deferred

## OPEN — Dev-channels intermittent inbound-message drop (channel-bind race)

**Status:** open · trying a claude-version bump first · monitoring.

**Symptom:** A Music-topic turn occasionally gets no reply and hangs — claude
sits at a fresh empty prompt, polygram's turn never resolves, and the
`cli-mid-turn-unknown-prompt` watchdog spins. Recurs intermittently (e.g.
msg 1311, 2026-06-02 — dropped, while the album turn 5 min earlier with the
identical config delivered fine).

**Root cause (proven with a live repro):** a race inside claude's
`--dangerously-load-development-channels`. The bridge pushes the `user_msg`
notification right after `mcp-ready` (~38ms — the first ListToolsRequest), but
claude's *channel subscription* (`server:polygram-bridge`) activates slightly
later than its MCP-tool registration. When the push lands before the channel is
listening, the message is **silently dropped** → no turn → no hooks → polygram
hangs. Evidence: bridge log shows `user_msg-notify-ok` + `mcp-ready`, but the
pane shows the empty-state placeholder and the new `cli-hook-stream-live` probe
never fires (zero hooks for the session; ndjson 0 bytes). The
"server:polygram-bridge  no MCP server configured with that name" banner is
present in BOTH working and dropped turns, so it is NOT the discriminator — the
discriminator is whether any hook fires (`cli-hook-stream-live`).

**Why polygram can't directly fix it:** the race is inside claude's
research-preview channels feature; polygram only sends the `user_msg` and tails
hooks. It can recover/avoid, not fix the upstream race.

**Observability in place (rc.16):** `cli-hook-stream-live` (fires on a
session's first hook — its absence after a dispatched turn = the message was
dropped), `cli-turn-resolved-by-stop`, `cli-stop-unattributed`.

**Current mitigation (rc.18):** pinned claude bumped 2.1.142 → 2.1.158 (16
versions newer) to see if the channels reliability improved upstream. E2E
(`tests/e2e-channels-real-claude.test.js`) confirms the channel flow + Stop
hook work on 2.1.158. **Verdict (2026-06-04): the bump did NOT resolve it** —
36h of telemetry showed 4 `startup-gate` deaths + 2 `cli-mid-turn-unknown-prompt`
drops, including one this morning (msg 1372, 09:25). The two failure surfaces
are now treated separately (below).

**Startup-gate death (TMUX_SESSION_GONE) — silently auto-retried (rc.25, option a):**
when claude exits *inside* the startup gate (before the channel goes live), the
message was never delivered, so re-sending is idempotent by construction. The
dispatcher already poison-cleared the session_id (rc.20) on this code; rc.25
adds a silent **one-shot re-dispatch** (`startup-auto-retry` event,
`lib/handlers/dispatcher.js`) that spawns a fresh session and delivers the same
message — so a transient startup flake never reaches the user. Only on a SECOND
consecutive startup death does the friendly "🔄 reset it, resend" reply surface
(`_startupRetried` one-shot guard → never a loop). This closes the
startup-death half of the gap (the failure mode that fired this morning + was
behind the "/stop said stopped but it kept going" report). **Still open: the
mid-turn drop** (`cli-mid-turn-unknown-prompt`) — claude is up and the channel
subscribed late, dropping a `user_msg` *after* dispatch — needs the hook-based
delivery watchdog below, a distinct mechanism.

**Status update (2026-06-10, rc.36):** step 1 below **SHIPPED** as the 0.13 D2
delivery watchdog (`docs/0.13-channels-lifecycle-design.md` §3 D2, two-regime
spec; `lib/process/cli-process.js _deliveryWatchdogFire`). Exactly the design
this step sketched: UPS pickup (`cli-ups-seen`) is the delivery confirmation;
a dispatched primary with no pickup and ZERO session activity gets one
idempotent re-write of the same envelope (`cli-delivery-rewrite`); still
nothing → bridge teardown onto the existing recovery path
(`cli-delivery-watchdog-escalate`). Activity since dispatch (claude busy on a
foreign cycle) extends instead — the don't-double-process caveat implemented.
The recovery is also now observable end-to-end (the 19:37 startup-retry on
deploy night closed with a `cli-ups-seen` 5s later — first observed proof).

**Remaining TODO (the race itself is upstream — claude's dev-channels preview):**

1. **Targeted race fix (the only true fix).** Investigate the channels MCP
   protocol for a "channel subscribed" signal the bridge can wait for before
   sending the first `user_msg` (instead of firing ~38ms after
   `mcp-ready`/first ListToolsRequest). If such a signal exists, gating the
   first `user_msg` on it eliminates the race at the source. Contingent on the
   protocol exposing it — **re-check on every pinned-binary bump** (fold a
   probe into `scripts/cli-driver-spike/preflight.sh`) and watch claude
   release notes for channels graduating from research preview.

2. **Tripwires (monitor, don't act below them):**
   - `startup-auto-retry` rate climbing above the ~1/day baseline, or any
     SECOND-consecutive startup death surfacing the user-visible "resend" copy
     more than rarely;
   - any `cli-delivery-watchdog-escalate` event (the watchdog's re-write
     failed too — the drop class is biting harder than the recovery);
   - `cli-delivery-rewrite` firing on sessions with a LIVE hook stream
     (would suggest the watchdog's activity gate needs tightening, not that
     delivery is failing).

(Option — moving cli topics to the SDK backend — avoids dev-channels entirely
and is reliable, but bills per-token instead of the Max subscription; held in
reserve, not the chosen path.)

## OPEN — User-facing error messaging for CLI-backend failures (humanize, don't leak internals)

**Status:** open · todo · UX/messaging.

**Symptom (live, 2026-06-03):** the general chat showed a user this raw string:

> Hit a snag: [Shumabit@HOME:startup-gate] tmux session disappeared for
> polygram-shumorobot-channels-b9e9ec24 after 31362ms (matched: dev-channels,
> session-age). claude likely exited; last pane content: … ▰▰▰▰▰▱ 27% …

That's scary, opaque, full of internals (tmux session names, ms timings, gate
match reasons, pane ASCII), and gives no clear "what do I do / what should I wait
for." A human just sees "something broke."

**Root cause:** `lib/error/classify.js` maps *known* error kinds to friendly
copy in `USER_MESSAGES` (emoji + plain language + action hint — e.g. timeout →
"⏳ I went quiet too long without finishing. Try resending or simplifying.").
But the new CLI/channels-backend failure modes are NOT in `PATTERNS`/`CODES`, so
they fall through to the `unknown` default (~classify.js:280):
`Hit a snag: ${reason}. Try resending.` — which echoes the raw error verbatim.
The SDK backend didn't have this problem because its error surfaces were already
classified to friendly copy; the CLI backend regressed on parity.

**What good looks like (parity with the SDK backend):** every user-visible
message should be (1) **not scary**, (2) **understandable by a non-engineer**,
(3) **clear on the next step or what it's waiting for**. No tmux names, no
millisecond timings, no pane dumps, no internal gate vocabulary. Technical detail
stays in the `events`/log (it already does — `handler-error.detail_json` has the
full string for forensics); the user gets the human version.

**Next steps:**

1. **Classify the CLI-backend failure modes** in `lib/error/classify.js` — add
   `PATTERNS`/`CODES` + `USER_MESSAGES` entries (and `isTransient`/`autoRecover`
   where apt) for at least:
   - **startup-gate / "tmux session disappeared" / "claude likely exited"** →
     transient; e.g. "⏳ I took too long to wake up. Try sending that again." (+
     consider auto-retry once before surfacing anything).
   - **bridge-disconnected (socket-close)** mid-turn → e.g. "🔌 Lost my
     connection for a second. Resend and I'll pick it up."
   - **cli-mid-turn-unknown-prompt** (if it ever surfaces to the user) → friendly
     equivalent.
2. **Harden the `unknown` fallthrough** — stop echoing raw `reason` to users.
   Replace with a generic, calm, actionable line ("⚠️ Something went wrong on my
   end — try resending. If it keeps happening, /new.") and keep the raw `reason`
   only in the logged event.
3. **Audit every user-facing string across cases** (startup, mid-turn, turn-end,
   resume-fail, bridge drop, compaction, queue overflow) for the three criteria
   above — esp. "what should the user do / wait for next." Use the SDK backend's
   `USER_MESSAGES` as the tone/clarity reference.
4. **Prefer silent auto-recovery over a scary message** where the failure is
   transient (startup flake under host load, one-off socket close): retry/respawn
   once and only message the user if recovery fails.

**Acceptance:** trigger each CLI-backend failure mode (kill the tmux session
mid-startup, close the bridge socket mid-turn, etc.) and confirm the user sees a
calm, actionable line with zero internal identifiers, while the raw detail still
lands in `events`.

## RESOLVED (2026-06-09) — LRU eviction can kill a session's live background job

**Status:** ✅ FIXED. `_evictLRU` now skips a session reporting
`hasActiveBackgroundWork()` (cli: `_bgWorkSince !== null`) the same way it skips
`inFlight`; when every free slot is so pinned, `getOrSpawn` soft-overflows the
budget + warns (`lru-overflow-pinned`) rather than killing a job or parking on a
~hour-long blocker. Spec + design: `docs/0.12.0-lru-eviction-pin-spec.md`. The
original write-up is kept below for the evidence trail.

**Status (original):** open · latent · cannot bite shumorobot today, matters at scale / on
the multi-chat production fleet.

**The gap:** `ProcessManager._evictLRU` (lib/process-manager.js:271) skips
`inFlight` sessions, but `inFlight` means "a TURN is being processed," NOT "a
background job is running." A session whose turn has resolved but left a
long-running backgrounded shell/agent (e.g. the shumorobot Music topic's
SoundCloud `listen-sync download` — a 50+ min `claude -p` job that runs after the
dispatch turn already resolved) is marked idle → **evictable**. Eviction calls
`oldest.kill('evict')` → `killSession(tmux)` → the background process dies, and
the job's "report back" autonomous-wakeup has no session to land on. polygram
can't see the curator's background shells (they live inside the claude process),
so it has no signal to protect them.

**Why it can't bite shumorobot today:** eviction only fires on **cost-budget
pressure**, and there's **no idle reaper**. shumorobot has at most 3 cli sessions
(Shumabit@HOME + Music + Orchestra), cli cost = 3 each → max total cost 9 <
budget 10 — the budget is never exceeded, so `_evictLRU` never runs. The Music
download is safe. (It becomes real if shumorobot grows past 3 sessions, or on the
production fleet where the budget IS pressured.)

**Separate, larger exposure:** a daemon **restart** kills all background jobs
regardless of eviction — `shutdown-drain` drains in-flight *turns*, not background
*jobs*, and the report-back wakeup is lost. Unavoidable without job-survival
work; operators should avoid restarting while a long background job runs.

**Fix sketch (when it's worth it):** pin a session from eviction while it has
live background work. Detect a `run_in_background` Bash (or sub-agent) that hasn't
completed — via the hook stream (PreToolUse with a background marker, cleared on
the matching completion / autonomous-wakeup) — and treat that session like
`inFlight` in `_evictLRU` (skip it). Clear the pin when the job's completion
wakeup fires. Non-trivial: requires tracking background-job lifecycle, which
polygram doesn't do today. Until then, the cost-budget headroom (shumorobot) is
the only thing protecting these jobs.

**Full design + the real fix:** see
`docs/0.12.0-background-work-lifecycle-plan.md` — eviction-pin is deferred there
(can't bite shumorobot); the incident-driven core is a background-work *detection
primitive* + a *stall-watchdog*, with the detection mechanism (pane-scrape vs
agent-declares-via-protocol) decided empirically in P0.

## OPEN — Channels backend: occasional VERBATIM re-delivery of a prior assistant message (claude re-emits)

**Status:** open · documented · NOT fixed (every candidate fix rejected — below) ·
rare / not reproducible on demand.

**Symptom (live, shumorobot general 2026-06-04):** the channels backend
occasionally delivers an OLD assistant message AGAIN — byte-identical — plus a
duplicate sticker, while the user is sending follow-ups. Incident transcript:
after "All done. **76 snippets** imported…" (msg 1397, 14:50:24) + `[sticker:pumped]`
(1398), the user asked two NEW questions ("Are you redownloading?" 1399, "Does
shúmee writable now?" 1400); polygram then re-delivered the **byte-identical**
"All done…" (msg 1401), a reworded variant (1402), and the sticker **twice**
(1403/1404) BEFORE the real answer (1405 "Not redownloading").

**Root cause (established, multi-agent + JSONL-verified):**

- **claude itself re-emits** the prior `reply` tool call. Proven via the session
  JSONL: three "All done" reply tool calls (07:50:23 / 07:50:57 / 07:51:31 UTC).
  polygram has **no replay buffer** — the bridge/daemon is a stateless line
  pass-through (`channels-bridge-server.js`), faithfully delivering whatever
  reply-tool calls claude makes. The duplication is upstream of polygram.
- **Channels-specific → SDK never has it.** SDK autosteer is a true mid-stream
  input merge (`inputController.enqueue`) with no new "notification". The channels
  backend instead has (a) the reply-**tool** delivery surface, (b)
  `injectUserMessage` (F#24, rc.15 / commit `c97b682`) which folds a mid-turn
  follow-up by writing a **standalone `user_msg` with a FRESH `turn_id`** — the
  divergence doc (`docs/0.11.0-channels-backend-divergence.md:95`) explicitly
  warned this needed a new bridge message kind and was *deferred*, and (c) the
  autonomous-wakeup path (ScheduleWakeup / background-shell-completion). Any of
  these re-prompts claude while its just-delivered message is still in context, and
  claude can re-emit it (verbatim or reworded).
- The existing **content-dedup** (`cli-process.js:994-1017`, `recentContentHashes`,
  `contentDedupWindowMs=60_000`) catches re-emits WITHIN 60s — the incident's +34s
  re-emit WAS suppressed (no msg row) — but misses later ones (the +68s re-emit →
  delivered as 1401).

**Why it's hard / why no fix shipped:** a real-claude repro harness
(`scripts/spikes/channels-reannounce-repro.mjs`, 4 runs across 2 triggers) did
**NOT** reproduce the verbatim replay. Mid-turn inject and background-shell
completion each produce a *reasonable, differently-worded* message (claude
answering a status question / reporting a bg job done) — not a byte-identical
replay. The verbatim replay is **rare/conditional** (likely needs `ScheduleWakeup`
+ overlapping probes stacked, which the spike couldn't force). Candidate fixes, all
rejected:

1. **Queue mid-turn follow-ups instead of injecting** (kill the trigger) —
   REJECTED: loses the autosteer "fold into the running turn" UX (F#24).
2. **Bind the injected `user_msg` to the active `turn_id`** — NOT VALIDATED:
   `turn_id` is just polygram's reply-routing tag (claude echoes it back), unlikely
   to change claude's continuation behavior; and the inject isn't even the *proven*
   trigger (the spike folds cleanly).
3. **Per-session "never deliver the identical message/sticker twice" dedup** —
   REJECTED: duplicate stickers and short repeats ("Ok", "👍") are **legitimate**;
   a blanket identical-dedup would wrongly suppress real messages.

**Net:** the duplication is claude re-emitting under rare conditions; it's
low-frequency, the visible artifact (a repeated sticker / short line) is usually
harmless, and every targeted fix either breaks a legitimate behavior or chases an
unproven trigger. Deferred deliberately.

**Forensics (how to spot it):** `messages` OUT rows with byte-identical `text` (or
the same sticker) close in time, `source=channels-tool-dispatcher`, coincident with
`autosteer` / `inject-user-message` / `autonomous-wakeup-message` events. The
session JSONL (`~/.claude/projects/<cwd>/<session>.jsonl`) confirms claude itself
re-emitted. Repro harness: `scripts/spikes/channels-reannounce-repro.mjs`
(`INJECT_VARIANT=baseline|bind|frame`).
