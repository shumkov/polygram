## L1 — Drop polygram's `stdinLock`  **[DEFERRED]**

Solution doc §7: *"Turn-ordering has exactly one FIFO authority (the
ledger inside TmuxProcess) — drop polygram's separate `stdinLock`."*

**Why deferred.** `sendToProcess` (`polygram.js`) holds `stdinLock`
across the whole turn. It is now **redundant for the tmux backend** —
`TmuxProcess.pendingQueue` + `_runTurn`/`_finishTurn` already
serialise primary turns. But `sendToProcess` is **backend-agnostic**,
and `stdinLock` is **load-bearing for the SDK backend**: there is a
documented in-code test (3 rapid stream-json writes →
`result#1="A"`, `result#2="B\nC"`, pending#3 stuck). Dropping it
globally risks an SDK regression for zero user-facing benefit — the
doc's "one FIFO authority" is an elegance goal, not a correctness
one.

**The safe partial.** A `if (entry.backend !== 'tmux')` guard around
the `stdinLock.acquire` in `sendToProcess` would remove the redundant
double-serialisation for tmux while leaving SDK untouched. Low-risk,
small. Not done only because it has ~zero user-facing effect.

**Resolution.** Do the tmux-scoped skip if/when wanted; drop
`stdinLock` entirely when the SDK backend is retired (the migration
is heading there anyway).

## L2 — Per-msgId reaction-write lock  **[DEFERRED]**

Solution doc §7: *"all reaction writes for a msgId serialise on a
per-msgId lock; `autosteeredRefs` becomes the sole authority for an
autosteered msg's reaction state."*

**Why deferred.** The problem doc attributes stuck reactions to a
single cause — *"the turn-completion signal never reaches the
reactor."* Phases 1–2 fixed exactly that signal (empty turns now
resolve; `extra-turn-reply` fires reliably; the Phase 4 stale-sweep
guarantees every turn yields a terminal signal). rc.17 already paced
reaction *clearing*.

A per-msgId reaction-write lock is **defense-in-depth against a
reaction-write *ordering* race** — but there is no trace and no
reproduction showing such a race still occurs after Phases 1–3.
Writing the lock now means guessing at a bug's shape and touching the
reactor + `autosteeredRefs` + `polygram.js` for a hypothetical.
Adding speculative hardening on un-soaked rc's is precisely the
rc.7→rc.19 anti-pattern this effort exists to end.

**Resolution.** Soak rc.20, then query shumorobot telemetry for
stuck-reaction events (`events` table; reactor states never clearing).
If they still occur → fix the *real* race from a concrete trace. If
they do not → the lock was never needed.

## N1 — Test B2 ("result before its user-message") not written  **[NOTE]**

The solution doc's test plan listed B2: *"`result` arriving before
its `user-message` → assert the turn still delivers non-empty text."*

It was **deliberately not written.** B2 guards against JSONL event
reorder. The `LogTail` reads the session JSONL in strict append
(byte) order, and claude writes a turn's `user`/`queue-operation`
line *before* that turn's `assistant` lines (verified in the Phase 0
and Phase 1 JSONL captures). The reorder B2 hypothesises does not
occur with file-order tailing — writing a contrived test for it would
assert behaviour the real CLI never produces.

The empty-turn *class* B2 was grouped under is covered by Phase 1's
coalescing (a `thinking` line no longer resolves a turn empty) and
the Phase 1 red→green integration test.

# Review findings — 4-agent audit (2026-05-17)

After Phase 4, four independent review agents (concurrency/race audit,
correctness, silent-failure, test-coverage) audited `git diff
47a8f42..HEAD`. Each agent finding was then traced to ground against
the actual code. **Net: of the agents' flagged items, only R1 and R2
were real bugs.** R3–R6 were agent over-flags that do not survive
tracing — kept here with the disproof so the analysis is auditable.

**All six were addressed in the rc.20 batch** — R1/R2 fixed, R4/R5/R6
applied as cheap hardening, R3 verified as needing no change.

## R1 — Primary-turn timeout strands its folded autosteers  **[FIXED — rc.20 batch]**

When a primary turn failed/timed out, `_finishTurn` called
`_dropFromActiveGroup(turn)` for the **primary only**. Autosteer
turns folded into that `_activeGroup` (via `_foldAutosteer` on a
`queue-operation remove`) were left `state:'streaming'` — never
flushed (no terminal `result` arrived, which is *why* the primary
timed out), never swept (`_sweepStaleTurns` targets `'pasted'`).
They leaked in `_ledger`, and `_activeGroup` stayed non-empty so the
next autonomous assistant message was accumulated into the dead
group and silently swallowed. **Fixed:** `_finishTurn` now retires
any leftover `_activeGroup` turns and resets the group when a turn
ends unflushed. Test: `R1 — a primary turn timeout retires its
folded autosteers` (red→green).

## R2 — A primary paste routed through the TUI queue desynced the enqueue FIFO  **[FIXED — rc.20 batch]**

`_enqueuedTurns` (was `_enqueuedAutosteers`) mirrors the TUI's input
queue; `queue-operation remove`/`dequeue` are bare (no token) so they
resolve positionally. The `enqueue` handler filtered
`kind==='autosteer'` — so a primary turn's paste that the TUI queued
(`enqueue`→`dequeue`) was never tracked, and the positional `dequeue`
shift then popped an *autosteer* instead, desyncing the FIFO (a
later `remove` folded the wrong turn, or nothing). **Fixed:** the
`enqueue` handler tracks EVERY queued turn — primary or autosteer;
`remove` still only folds autosteers. Test: `R2 — a primary paste
routed through the TUI queue does not desync the enqueue FIFO`
(red→green). Uncommon trigger (a primary paste is queued only when
the TUI is momentarily busy at turn handover).

## R3 — "Stale sweep does not clear the reactor"  **[NOT A BUG — verified]**

The silent-failure agent flagged `_sweepStaleTurns` as leaking the ✍
reaction because `onAutosteerMatchMiss` only logs. **Traced to ground
— it does not leak.** `handleMessage` (`polygram.js:1486-1500`) has a
`finally` that calls `clearAutosteeredReactions(sessionKey)` on EVERY
exit path (success, error, timeout, throw) of the *primary* turn's
handler — its own comment says "covers ALL exit paths". A folded or
swept autosteer's ✍ is cleared when the primary turn's `handleMessage`
unwinds, regardless of how the turn ended. The sweep emitting a
diagnostic-only event is correct. The agent did not trace the
`finally`. No fix needed.

## R4 — "Double-resolve guard for a folded turn"  **[NOT A BUG — verified]**

The concurrency agent flagged a folded turn (`via='fold'`,
`state='streaming'`) being re-resolved by a late `user-message`.
**Traced — unreachable.** `_routeUserMessage` matches turns with
`state !== 'done' && state !== 'failed'`, then skips any already in
`this._activeGroup.turns`. `_foldAutosteer` always pushes the turn
into `_activeGroup` and the only ways out are `_flushActiveGroup`
(which sets `state='done'` → then excluded by the state filter) or
`_dropFromActiveGroup` (called only for the *primary*). So a
`streaming` folded turn is ALWAYS in the current `_activeGroup` →
always skipped. No double-resolve path exists. No fix needed.

## R5 — "`_pasteConfirms` not cleared on `kill()`"  **[NOT A BUG]**

Pending paste-confirm timers are `unref`'d and the Map is per-instance.
A killed `TmuxProcess` is never reused (resume creates a fresh
instance), so the instance + its Map + timers are simply GC'd. Zero
observable effect. Optional tidiness at most.

## R6 — "`_extractTokens` regex is unanchored"  **[NOT A BUG]**

`/pgm-corr-[0-9a-f]+/g` over-matching would need a token followed
immediately by more hex with no delimiter. `_embedToken` ALWAYS emits
the token as `corr-id="<token>"` — the closing `"` (and the ` / `
separators in a concatenated user-message) is a non-hex delimiter
that terminates the match at exactly 24 hex chars. Over-match cannot
occur in any embedding context. Anchoring to `{24}` is harmless
hygiene but fixes nothing.

## R7 — A wedged `captureWide` hangs the turn  **[PRE-EXISTING]**

`_awaitTurnComplete`'s poll loop re-checks its deadline only *between*
`captureWide` calls. If a single `tmux capture-pane` subprocess
wedges, the turn neither completes nor times out → `send()` hangs,
the queue starves. Pre-dates this work (the loop structure is
unchanged) but real. **Fix (separate):** an absolute `setTimeout`
reject around the `_runTurn` race.

## R8 — `inject-fail` event has no consumer  **[PRE-EXISTING]**

`injectUserMessage` emits `inject-fail` on a failed autosteer paste;
no `onInjectFail` callback exists, so the failure is silent until the
stale sweep catches it `turnTimeoutMs` later. Pre-dates this work.
**Fix (separate):** wire `onInjectFail` to log + clear the reaction,
or fail the ledger turn immediately.

## R9 — §4 committed-intent latch has no automated test  **[TEST GAP]**

The `intentLock` rework in `polygram.js` `handleMessage` is verified
only by reasoning + the real-TUI spike — no CI test exercises the
burst autosteer-vs-primary path. `handleMessage` is hard to unit-test;
the latch logic could be extracted or driven through a fake `pm`.

## R10 — A genuinely empty JSONL `result` resolves as success  **[EDGE]**

§6 fail-loud covers only the capture-won/no-JSONL branch. A JSONL
`result` carrying genuinely empty text (a thinking-only terminal
message) resolves `error:null, text:''` → polygram delivers "No
response generated." Rare; note for the soak.

## R11 — `_finishTurn` retires a fresh NEW-TURN autosteer's group  **[FIXED — commit 98171cf]**

Surfaced by the `autosteer-tui-real.mjs` full run (2026-05-17): the
`reasoning-primary-with-autosteer` scenario fails INV-2/INV-6a/INV-6b
**consistently in isolation** (re-run twice). A NEW-TURN autosteer's
reply is emitted as an `autonomous-assistant-message` instead of
`extra-turn-reply`, so it never threads back to the autosteered
Telegram msgId.

**Pre-existing — confirmed against baseline.** The three backend
files (`tmux-process.js`, `process-manager.js`, `callbacks.js`) were
checked out at commit `a2d39d0` (the pre-R7/R8/R9/R10 HEAD) and the
scenario re-run — it fails identically there. The R7/R8/R9/R10 batch
did not cause it. The defect was introduced by the R1 fix in commit
`57b8e83`.

**Root cause.** `_finishTurn` (`lib/process/tmux-process.js:690`) has
the R1 block:

```
if (this._activeGroup.turns.length > 0) {
  for (const t of this._activeGroup.turns) {
    if (t.state !== 'done' && t.state !== 'failed') t.state = 'failed';
  }
  this._activeGroup = { turns: [], text: '', pendingSteerCausesNewBubble: false };
}
```

Its comment claims "On a successful turn `_flushActiveGroup` already
reset the group, so `turns` is empty here and this is a no-op." That
assumption is **false** for a NEW-TURN autosteer: between the primary
`result` (which `_flushActiveGroup` uses to reset the group) and the
primary's `_runTurn` reaching `_finishTurn`, the JSONL tail can
deliver the dequeued autosteer's `user-message` → `_routeUserMessage`
pushes that fresh autosteer turn into `_activeGroup`. The R1 block
then marks it `failed` and resets the group; the autosteer's
subsequent `assistant-chunk`s arrive with an empty `_activeGroup` and
leak via the `autonomous-assistant-message` branch in
`_handleSessionEvent`. (`autosteer-2s-after-primary` passes because
the autosteer arrives long after the primary fully completes — no
race.)

**Fixed (commit `98171cf`).** `_activeGroup` now carries a
`primaryTurnId` — the turnId of the primary turn that owns the group.
`_routeUserMessage` stamps it when a primary turn joins the group; a
NEW-TURN autosteer group never sets it and keeps `primaryTurnId:
null`. `_finishTurn`'s R1 block retires the group ONLY when
`this._activeGroup.primaryTurnId === turn.turnId` — the group the
finishing primary actually owns. A fresh NEW-TURN autosteer group
(`primaryTurnId: null`) therefore survives an unrelated primary's
`_finishTurn`, accumulates its chunks, and delivers `extra-turn-reply`
normally. The R1 case (a primary timeout retiring ITS folded
autosteers) is preserved — that group's primary did route in and set
`primaryTurnId`, so the guard still fires; verified by the unchanged
R1 regression test still passing.

Deterministic regression test: `R11 — a NEW-TURN autosteer routed
during the _finishTurn window is NOT retired by the primary` in
`tests/tmux-process-jsonl.test.js`. It writes the primary's terminal
assistant line and the autosteer's dequeued `user-message` in ONE
`appendFileSync`, so a single tail read processes both synchronously
and `_finishTurn` runs with the fresh NEW-TURN autosteer sitting in
`_activeGroup` — the exact race. Red before the fix (autosteer reply
leaks as `autonomous-assistant-message`), green after (exactly one
`extra-turn-reply` with the autosteered msgId). The real-TUI
`reasoning-primary-with-autosteer` scenario now passes on the
`via:new-turn` path (INV-2/INV-6a/INV-6b green).

## Downgraded — NOT a bug

One agent flagged `willHavePrimary` in `_routeUserMessage` as
misclassifying a fold when the autosteer's `user-message` precedes the
primary's. **It cannot:** the primary is always pasted before any
autosteer (`send` commits before `injectUserMessage`, enforced by the
Phase 3 committed-intent latch), so claude always writes the primary's
`user-message` first. The dequeue-driven new-turn case and the
concatenated multi-token fold case are both classified correctly.

# Spawn-lifecycle findings (independent of the turn-ledger rewrite)

The two findings below are **not** part of the turn-ledger
concurrency work. They are `TmuxProcess.start()` lifecycle bugs —
they would exist with or without the Phase 1–4 batch. They are
recorded here only because they surfaced during the same 0.10.0
spike. Caught together on shumorobot 2026-05-17 22:03, topic `:3`
(the Music topic): one user sent 3 messages, all 3 got error
replies — msg 1 `TUI did not signal ready`, msg 2+3 `tmux spawn
failed: duplicate session polygram-shumorobot--1003807211164-3`.

## S1 — `start()` leaked the tmux session it created on a post-spawn failure  **[FIXED — commit 72582da]**

**Symptom.** A transient first-spawn failure wedged a chat/topic
*permanently*. shumorobot 2026-05-17 22:03: msg 1's spawn failed at
`_waitForReady` (`TMUX_READY_TIMEOUT`); msgs 2 and 3 then failed with
`tmux spawn failed: ... duplicate session`. The orphan tmux session
was confirmed still alive afterward and had to be killed by hand.

**Root cause.** `TmuxProcess.start()`
(`lib/process/tmux-process.js`, the `_spawning` IIFE) called
`runner.spawn()` — which on success means the tmux session NAME now
exists — then ran `_armSessionLogTail()`, `_waitForReady()` and the
`init` emit with **no cleanup path**. When `_waitForReady()` threw
`TMUX_READY_TIMEOUT` (`tmux-process.js` `_waitForReady`, the
`throw … 'TUI did not signal ready'`), the error propagated straight
out of `start()` and the tmux session was left running. Every later
`getOrSpawn` retry reuses the same deterministic `tmuxName`
(`sessionName(botName, chatId, threadId)` in
`lib/tmux/tmux-runner.js`), so `runner.spawn()`'s `tmux new-session
-d -s <same-name>` rejected with `TMUX_SPAWN_FAILED` /
`duplicate session` (`tmux-runner.js` `spawn`, the `catch` that
wraps the `runFn` error). One transient failure → permanent wedge.

**Fix (commit 72582da).** After `runner.spawn()` resolves,
everything that follows runs inside a `try/catch` in `start()`. On
any throw the catch tears the session down — `killSession(tmuxName)`
plus closing the just-armed JSONL `_sessionLogTail` — before
re-throwing, so a retry gets a clean name. A `sessionCreated` flag
distinguishes "`spawn()` itself failed (no session — nothing to
kill)" from "session created, a later step failed (must kill)", so
no spurious `kill-session` is issued when `tmux new-session` itself
fails. Tests (`tests/tmux-process.test.js`, the `R-spawn-leak`
group): readiness-failure-kills-orphan and any-post-spawn-throw-kills
were ✖ before the fix, ✔ after; no-spurious-kill guards the
`spawn()`-itself-failed branch; a clean-retry test pins the
end-to-end contract.

## S2 — Topic `:3` TUI never signalled ready: stale cross-backend `--resume`  **[FIXED — commit 2230da6]**

**This is the trigger S1 turned permanent.** S1 stops a recurrence
from *wedging* (the retry gets a clean spawn); S2 stops the first
spawn from *failing* in the first place.

**What the evidence shows.**

- The polygram `sessions` row for `-1003807211164:3`
  (`~/.polygram/shumorobot.db`) is **stale and cross-backend**:
  `claude_session_id = ec13e620-4975-4bff-a5d3-451f9d2dd390`,
  `agent = shumabit`, `cwd = /Users/ivanshumkov`,
  `pm_backend = sdk`. It predates the per-topic config.
- The current per-topic config (`~/.polygram/config.json`, topic
  `"3"`) is `agent: music-curation:music-curator`,
  `cwd: /Users/ivanshumkov/Music/rekordbox`,
  `permissionMode: default`. **Both the cwd and the agent exist on
  disk** (`/Users/ivanshumkov/Music/rekordbox` is a dir;
  `music-curation@local` is in `~/.claude/plugins/installed_plugins.json`)
  — so a bad cwd / missing agent is **not** the cause.
- At 22:03 polygram spawned the tmux backend and passed
  `existingSessionId = ec13e620` → `start()` built `--resume
  ec13e620`. The `--debug-file`
  (`~/.polygram/shumorobot/logs/tmux-claude--1003807211164-3.log`)
  shows claude **forked** that historic session: `FileHistory:
  Copied backup … from session ec13e620-… to
  71ef3dc7-c8c0-47bd-85f0-17c7ce0032d2` at 22:03:27.4. The resumed
  source `ec13e620-…jsonl` is a 958-line / 1.5 MB historical session
  dated 2026-05-13.
- All five MCP servers connected fine within ~6 s
  (`plugin:serena:serena` in 4865 ms, `peekaboo` in 2501 ms, etc.) —
  slow-MCP-startup is **not** the cause; the 120 s `readyTimeoutMs`
  was nowhere near exhausted by MCP.
- The debug log shows the TUI rendered (`screen=577x200`) and the
  session lived ~9 min until the manual kill at 22:12:16. The TUI
  was *up* — yet polygram's `_waitForReady` capture-pane poll never
  matched `READY_HINTS_RE` across the full 120 s
  (`handler-error: TUI did not signal ready` fired at exactly
  22:05:25, 120 s after the 22:03:25 spawn).

**Root cause.** Resuming a large, *cross-backend* historic
session (an SDK-era `ec13e620`) under the tmux backend, while also
applying a different `--agent` and a different project `cwd` (whose
`.claude/settings.json` differs), left the TUI in a state that never
rendered the plain `? for shortcuts` ready hint within 120 s — most
plausibly a resume-replay / project-trust / settings prompt the
capture-pane regex does not recognise. The stale `sessions` row is
the concrete defect: polygram resumed a session that belongs to a
different backend + agent + cwd than the topic is now configured for.

**The fix (commit 2230da6).** A session is valid only for the config
it was created under. `resolveSessionForSpawn`
(`lib/db/sessions.js`) compares the stored `sessions` row's
spawn-identity fields against the freshly-resolved chat+topic config;
on drift it **deletes the stale row** and returns
`existingSessionId: null`, so the next spawn starts **fresh** under
the correct config (and the `onInit` callback re-upserts the row
with the new `claude_session_id`). `buildSpawnContext`
(`polygram.js`) wires this at **cold spawn only** — a warm process
already runs under its spawn-time config, so its row is left alone
until the next cold spawn — and logs a `session-config-drift`
telemetry event with the before/after field values so the soak can
see it firing.

**Field-set decision — only `agent` / `cwd` / `pm_backend`
invalidate** (`SPAWN_IDENTITY_FIELDS` in `lib/db/sessions.js`):

- `agent`, `cwd`, `pm_backend` are **spawn-identity**: baked into the
  process at spawn time (`--agent`, the tmux/SDK working dir, the
  `SdkProcess` vs `TmuxProcess` class) and cannot be changed on a
  live session.
- `model` and `effort` are **excluded**. A live `/model` or
  `/effort` change is pushed into the running session by
  `pm.setModel` / `pm.applyFlagSettings` with **no respawn**
  (`lib/handlers/slash-commands.js` `applyConfigChange`,
  `lib/handlers/config-callback.js`). Including them in the
  invalidating set would double-handle that path AND destructively
  drop the whole session — discarding all conversation context — on
  every model switch. The stored `model`/`effort` columns are
  informational, not identity.

**Self-heal — no manual SQL.** The stale `-1003807211164:3` row
(`agent=shumabit`, `cwd=/Users/ivanshumkov`, `pm_backend=sdk`) drifts
on all three fields versus the Music topic's resolved config
(`music-curation:music-curator`, `/Users/ivanshumkov/Music/rekordbox`,
`tmux`). The next message to thread 3 detects the drift, drops the
row, and spawns fresh with the correct agent/cwd. Every other
pre-per-topic-config stale row across all chats self-heals the same
way. Regression test: `the actual stale shumorobot :3 row self-heals`
in `tests/sessions.test.js` reproduces the exact production row and
asserts `drift.fields = [agent, cwd, pm_backend]` and the row is
dropped — ✖ before the fix (`resolveSessionForSpawn is not a
function`), ✔ after.

**rc.20 is NOT implicated.** `git log -L` over `_waitForReady` and a
`-S` search on `READY_HINTS_RE` across the rc.20 batch
(`5808191..a2d39d0`) show the readiness path was untouched by
Phase 1–4. The last change to it was the L1 banner fix (`e431986`)
and the rc.14 bypass-mode matcher (`c5db495`).
