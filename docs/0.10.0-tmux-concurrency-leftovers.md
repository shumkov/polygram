## L1 — Drop polygram's `stdinLock`  **[DEFERRED]**

Solution doc §7: *"Turn-ordering has exactly one FIFO authority (the
ledger inside TmuxProcess) — drop polygram's separate `stdinLock`."*

**Why deferred.** `sendToProcess` (`polygram.js`) holds `stdinLock`
across the whole turn. It is now **redundant for the tmux backend** —
`TmuxProcess.pendingQueue` + `_runTurn`/`_finishTurn` already
serialise primary turns. But `sendToProcess` is **backend-agnostic**,
and `stdinLock` is **load-bearing for the SDK backend**: there is a
documented in-code test (3 rapid stream-json writes →
`result#1="A"`, `result#2="B\nC"`, pending#3 stuck). Dropping it
globally risks an SDK regression for zero user-facing benefit — the
doc's "one FIFO authority" is an elegance goal, not a correctness
one.

**The safe partial.** A `if (entry.backend !== 'tmux')` guard around
the `stdinLock.acquire` in `sendToProcess` would remove the redundant
double-serialisation for tmux while leaving SDK untouched. Low-risk,
small. Not done only because it has ~zero user-facing effect.

**Resolution.** Do the tmux-scoped skip if/when wanted; drop
`stdinLock` entirely when the SDK backend is retired (the migration
is heading there anyway).

## L2 — Per-msgId reaction-write lock  **[DEFERRED]**

Solution doc §7: *"all reaction writes for a msgId serialise on a
per-msgId lock; `autosteeredRefs` becomes the sole authority for an
autosteered msg's reaction state."*

**Why deferred.** The problem doc attributes stuck reactions to a
single cause — *"the turn-completion signal never reaches the
reactor."* Phases 1–2 fixed exactly that signal (empty turns now
resolve; `extra-turn-reply` fires reliably; the Phase 4 stale-sweep
guarantees every turn yields a terminal signal). rc.17 already paced
reaction *clearing*.

A per-msgId reaction-write lock is **defense-in-depth against a
reaction-write *ordering* race** — but there is no trace and no
reproduction showing such a race still occurs after Phases 1–3.
Writing the lock now means guessing at a bug's shape and touching the
reactor + `autosteeredRefs` + `polygram.js` for a hypothetical.
Adding speculative hardening on un-soaked rc's is precisely the
rc.7→rc.19 anti-pattern this effort exists to end.

**Resolution.** Soak rc.20, then query shumorobot telemetry for
stuck-reaction events (`events` table; reactor states never clearing).
If they still occur → fix the *real* race from a concrete trace. If
they do not → the lock was never needed.

## N1 — Test B2 ("result before its user-message") not written  **[NOTE]**

The solution doc's test plan listed B2: *"`result` arriving before
its `user-message` → assert the turn still delivers non-empty text."*

It was **deliberately not written.** B2 guards against JSONL event
reorder. The `LogTail` reads the session JSONL in strict append
(byte) order, and claude writes a turn's `user`/`queue-operation`
line *before* that turn's `assistant` lines (verified in the Phase 0
and Phase 1 JSONL captures). The reorder B2 hypothesises does not
occur with file-order tailing — writing a contrived test for it would
assert behaviour the real CLI never produces.

The empty-turn *class* B2 was grouped under is covered by Phase 1's
coalescing (a `thinking` line no longer resolves a turn empty) and
the Phase 1 red→green integration test.

# Review findings — 4-agent audit (2026-05-17)

After Phase 4, four independent review agents (concurrency/race audit,
correctness, silent-failure, test-coverage) audited `git diff
47a8f42..HEAD`. Each agent finding was then traced to ground against
the actual code. **Net: of the agents' flagged items, only R1 and R2
were real bugs.** R3–R6 were agent over-flags that do not survive
tracing — kept here with the disproof so the analysis is auditable.

**All six were addressed in the rc.20 batch** — R1/R2 fixed, R4/R5/R6
applied as cheap hardening, R3 verified as needing no change.

## R1 — Primary-turn timeout strands its folded autosteers  **[FIXED — rc.20 batch]**

When a primary turn failed/timed out, `_finishTurn` called
`_dropFromActiveGroup(turn)` for the **primary only**. Autosteer
turns folded into that `_activeGroup` (via `_foldAutosteer` on a
`queue-operation remove`) were left `state:'streaming'` — never
flushed (no terminal `result` arrived, which is *why* the primary
timed out), never swept (`_sweepStaleTurns` targets `'pasted'`).
They leaked in `_ledger`, and `_activeGroup` stayed non-empty so the
next autonomous assistant message was accumulated into the dead
group and silently swallowed. **Fixed:** `_finishTurn` now retires
any leftover `_activeGroup` turns and resets the group when a turn
ends unflushed. Test: `R1 — a primary turn timeout retires its
folded autosteers` (red→green).

## R2 — A primary paste routed through the TUI queue desynced the enqueue FIFO  **[FIXED — rc.20 batch]**

`_enqueuedTurns` (was `_enqueuedAutosteers`) mirrors the TUI's input
queue; `queue-operation remove`/`dequeue` are bare (no token) so they
resolve positionally. The `enqueue` handler filtered
`kind==='autosteer'` — so a primary turn's paste that the TUI queued
(`enqueue`→`dequeue`) was never tracked, and the positional `dequeue`
shift then popped an *autosteer* instead, desyncing the FIFO (a
later `remove` folded the wrong turn, or nothing). **Fixed:** the
`enqueue` handler tracks EVERY queued turn — primary or autosteer;
`remove` still only folds autosteers. Test: `R2 — a primary paste
routed through the TUI queue does not desync the enqueue FIFO`
(red→green). Uncommon trigger (a primary paste is queued only when
the TUI is momentarily busy at turn handover).

## R3 — "Stale sweep does not clear the reactor"  **[NOT A BUG — verified]**

The silent-failure agent flagged `_sweepStaleTurns` as leaking the ✍
reaction because `onAutosteerMatchMiss` only logs. **Traced to ground
— it does not leak.** `handleMessage` (`polygram.js:1486-1500`) has a
`finally` that calls `clearAutosteeredReactions(sessionKey)` on EVERY
exit path (success, error, timeout, throw) of the *primary* turn's
handler — its own comment says "covers ALL exit paths". A folded or
swept autosteer's ✍ is cleared when the primary turn's `handleMessage`
unwinds, regardless of how the turn ended. The sweep emitting a
diagnostic-only event is correct. The agent did not trace the
`finally`. No fix needed.

## R4 — "Double-resolve guard for a folded turn"  **[NOT A BUG — verified]**

The concurrency agent flagged a folded turn (`via='fold'`,
`state='streaming'`) being re-resolved by a late `user-message`.
**Traced — unreachable.** `_routeUserMessage` matches turns with
`state !== 'done' && state !== 'failed'`, then skips any already in
`this._activeGroup.turns`. `_foldAutosteer` always pushes the turn
into `_activeGroup` and the only ways out are `_flushActiveGroup`
(which sets `state='done'` → then excluded by the state filter) or
`_dropFromActiveGroup` (called only for the *primary*). So a
`streaming` folded turn is ALWAYS in the current `_activeGroup` →
always skipped. No double-resolve path exists. No fix needed.

## R5 — "`_pasteConfirms` not cleared on `kill()`"  **[NOT A BUG]**

Pending paste-confirm timers are `unref`'d and the Map is per-instance.
A killed `TmuxProcess` is never reused (resume creates a fresh
instance), so the instance + its Map + timers are simply GC'd. Zero
observable effect. Optional tidiness at most.

## R6 — "`_extractTokens` regex is unanchored"  **[NOT A BUG]**

`/pgm-corr-[0-9a-f]+/g` over-matching would need a token followed
immediately by more hex with no delimiter. `_embedToken` ALWAYS emits
the token as `corr-id="<token>"` — the closing `"` (and the ` / `
separators in a concatenated user-message) is a non-hex delimiter
that terminates the match at exactly 24 hex chars. Over-match cannot
occur in any embedding context. Anchoring to `{24}` is harmless
hygiene but fixes nothing.

## R7 — A wedged `captureWide` hangs the turn  **[PRE-EXISTING]**

`_awaitTurnComplete`'s poll loop re-checks its deadline only *between*
`captureWide` calls. If a single `tmux capture-pane` subprocess
wedges, the turn neither completes nor times out → `send()` hangs,
the queue starves. Pre-dates this work (the loop structure is
unchanged) but real. **Fix (separate):** an absolute `setTimeout`
reject around the `_runTurn` race.

## R8 — `inject-fail` event has no consumer  **[PRE-EXISTING]**

`injectUserMessage` emits `inject-fail` on a failed autosteer paste;
no `onInjectFail` callback exists, so the failure is silent until the
stale sweep catches it `turnTimeoutMs` later. Pre-dates this work.
**Fix (separate):** wire `onInjectFail` to log + clear the reaction,
or fail the ledger turn immediately.

## R9 — §4 committed-intent latch has no automated test  **[TEST GAP]**

The `intentLock` rework in `polygram.js` `handleMessage` is verified
only by reasoning + the real-TUI spike — no CI test exercises the
burst autosteer-vs-primary path. `handleMessage` is hard to unit-test;
the latch logic could be extracted or driven through a fake `pm`.

## R10 — A genuinely empty JSONL `result` resolves as success  **[EDGE]**

§6 fail-loud covers only the capture-won/no-JSONL branch. A JSONL
`result` carrying genuinely empty text (a thinking-only terminal
message) resolves `error:null, text:''` → polygram delivers "No
response generated." Rare; note for the soak.

## R11 — `_finishTurn` retires a fresh NEW-TURN autosteer's group  **[FIXED — commit 98171cf]**

Surfaced by the `autosteer-tui-real.mjs` full run (2026-05-17): the
`reasoning-primary-with-autosteer` scenario fails INV-2/INV-6a/INV-6b
**consistently in isolation** (re-run twice). A NEW-TURN autosteer's
reply is emitted as an `autonomous-assistant-message` instead of
`extra-turn-reply`, so it never threads back to the autosteered
Telegram msgId.

**Pre-existing — confirmed against baseline.** The three backend
files (`tmux-process.js`, `process-manager.js`, `callbacks.js`) were
checked out at commit `a2d39d0` (the pre-R7/R8/R9/R10 HEAD) and the
scenario re-run — it fails identically there. The R7/R8/R9/R10 batch
did not cause it. The defect was introduced by the R1 fix in commit
`57b8e83`.

**Root cause.** `_finishTurn` (`lib/process/tmux-process.js:690`) has
the R1 block:

```
if (this._activeGroup.turns.length > 0) {
  for (const t of this._activeGroup.turns) {
    if (t.state !== 'done' && t.state !== 'failed') t.state = 'failed';
  }
  this._activeGroup = { turns: [], text: '', pendingSteerCausesNewBubble: false };
}
```

Its comment claims "On a successful turn `_flushActiveGroup` already
reset the group, so `turns` is empty here and this is a no-op." That
assumption is **false** for a NEW-TURN autosteer: between the primary
`result` (which `_flushActiveGroup` uses to reset the group) and the
primary's `_runTurn` reaching `_finishTurn`, the JSONL tail can
deliver the dequeued autosteer's `user-message` → `_routeUserMessage`
pushes that fresh autosteer turn into `_activeGroup`. The R1 block
then marks it `failed` and resets the group; the autosteer's
subsequent `assistant-chunk`s arrive with an empty `_activeGroup` and
leak via the `autonomous-assistant-message` branch in
`_handleSessionEvent`. (`autosteer-2s-after-primary` passes because
the autosteer arrives long after the primary fully completes — no
race.)

**Fixed (commit `98171cf`).** `_activeGroup` now carries a
`primaryTurnId` — the turnId of the primary turn that owns the group.
`_routeUserMessage` stamps it when a primary turn joins the group; a
NEW-TURN autosteer group never sets it and keeps `primaryTurnId:
null`. `_finishTurn`'s R1 block retires the group ONLY when
`this._activeGroup.primaryTurnId === turn.turnId` — the group the
finishing primary actually owns. A fresh NEW-TURN autosteer group
(`primaryTurnId: null`) therefore survives an unrelated primary's
`_finishTurn`, accumulates its chunks, and delivers `extra-turn-reply`
normally. The R1 case (a primary timeout retiring ITS folded
autosteers) is preserved — that group's primary did route in and set
`primaryTurnId`, so the guard still fires; verified by the unchanged
R1 regression test still passing.

Deterministic regression test: `R11 — a NEW-TURN autosteer routed
during the _finishTurn window is NOT retired by the primary` in
`tests/tmux-process-jsonl.test.js`. It writes the primary's terminal
assistant line and the autosteer's dequeued `user-message` in ONE
`appendFileSync`, so a single tail read processes both synchronously
and `_finishTurn` runs with the fresh NEW-TURN autosteer sitting in
`_activeGroup` — the exact race. Red before the fix (autosteer reply
leaks as `autonomous-assistant-message`), green after (exactly one
`extra-turn-reply` with the autosteered msgId). The real-TUI
`reasoning-primary-with-autosteer` scenario now passes on the
`via:new-turn` path (INV-2/INV-6a/INV-6b green).

## Downgraded — NOT a bug

One agent flagged `willHavePrimary` in `_routeUserMessage` as
misclassifying a fold when the autosteer's `user-message` precedes the
primary's. **It cannot:** the primary is always pasted before any
autosteer (`send` commits before `injectUserMessage`, enforced by the
Phase 3 committed-intent latch), so claude always writes the primary's
`user-message` first. The dequeue-driven new-turn case and the
concatenated multi-token fold case are both classified correctly.

# Spawn-lifecycle findings (independent of the turn-ledger rewrite)

The two findings below are **not** part of the turn-ledger
concurrency work. They are `TmuxProcess.start()` lifecycle bugs —
they would exist with or without the Phase 1–4 batch. They are
recorded here only because they surfaced during the same 0.10.0
spike. Caught together on shumorobot 2026-05-17 22:03, topic `:3`
(the Music topic): one user sent 3 messages, all 3 got error
replies — msg 1 `TUI did not signal ready`, msg 2+3 `tmux spawn
failed: duplicate session polygram-shumorobot--1003807211164-3`.

## S1 — `start()` leaked the tmux session it created on a post-spawn failure  **[FIXED — commit 72582da]**

**Symptom.** A transient first-spawn failure wedged a chat/topic
*permanently*. shumorobot 2026-05-17 22:03: msg 1's spawn failed at
`_waitForReady` (`TMUX_READY_TIMEOUT`); msgs 2 and 3 then failed with
`tmux spawn failed: ... duplicate session`. The orphan tmux session
was confirmed still alive afterward and had to be killed by hand.

**Root cause.** `TmuxProcess.start()`
(`lib/process/tmux-process.js`, the `_spawning` IIFE) called
`runner.spawn()` — which on success means the tmux session NAME now
exists — then ran `_armSessionLogTail()`, `_waitForReady()` and the
`init` emit with **no cleanup path**. When `_waitForReady()` threw
`TMUX_READY_TIMEOUT` (`tmux-process.js` `_waitForReady`, the
`throw … 'TUI did not signal ready'`), the error propagated straight
out of `start()` and the tmux session was left running. Every later
`getOrSpawn` retry reuses the same deterministic `tmuxName`
(`sessionName(botName, chatId, threadId)` in
`lib/tmux/tmux-runner.js`), so `runner.spawn()`'s `tmux new-session
-d -s <same-name>` rejected with `TMUX_SPAWN_FAILED` /
`duplicate session` (`tmux-runner.js` `spawn`, the `catch` that
wraps the `runFn` error). One transient failure → permanent wedge.

**Fix (commit 72582da).** After `runner.spawn()` resolves,
everything that follows runs inside a `try/catch` in `start()`. On
any throw the catch tears the session down — `killSession(tmuxName)`
plus closing the just-armed JSONL `_sessionLogTail` — before
re-throwing, so a retry gets a clean name. A `sessionCreated` flag
distinguishes "`spawn()` itself failed (no session — nothing to
kill)" from "session created, a later step failed (must kill)", so
no spurious `kill-session` is issued when `tmux new-session` itself
fails. Tests (`tests/tmux-process.test.js`, the `R-spawn-leak`
group): readiness-failure-kills-orphan and any-post-spawn-throw-kills
were ✖ before the fix, ✔ after; no-spurious-kill guards the
`spawn()`-itself-failed branch; a clean-retry test pins the
end-to-end contract.

## S2 — Topic `:3` TUI never signalled ready: stale cross-backend `--resume`  **[FIXED — commit 2230da6]**

**This is the trigger S1 turned permanent.** S1 stops a recurrence
from *wedging* (the retry gets a clean spawn); S2 stops the first
spawn from *failing* in the first place.

**What the evidence shows.**

- The polygram `sessions` row for `-1003807211164:3`
  (`~/.polygram/shumorobot.db`) is **stale and cross-backend**:
  `claude_session_id = ec13e620-4975-4bff-a5d3-451f9d2dd390`,
  `agent = shumabit`, `cwd = /Users/ivanshumkov`,
  `pm_backend = sdk`. It predates the per-topic config.
- The current per-topic config (`~/.polygram/config.json`, topic
  `"3"`) is `agent: music-curation:music-curator`,
  `cwd: /Users/ivanshumkov/Music/rekordbox`,
  `permissionMode: default`. **Both the cwd and the agent exist on
  disk** (`/Users/ivanshumkov/Music/rekordbox` is a dir;
  `music-curation@local` is in `~/.claude/plugins/installed_plugins.json`)
  — so a bad cwd / missing agent is **not** the cause.
- At 22:03 polygram spawned the tmux backend and passed
  `existingSessionId = ec13e620` → `start()` built `--resume
  ec13e620`. The `--debug-file`
  (`~/.polygram/shumorobot/logs/tmux-claude--1003807211164-3.log`)
  shows claude **forked** that historic session: `FileHistory:
  Copied backup … from session ec13e620-… to
  71ef3dc7-c8c0-47bd-85f0-17c7ce0032d2` at 22:03:27.4. The resumed
  source `ec13e620-…jsonl` is a 958-line / 1.5 MB historical session
  dated 2026-05-13.
- All five MCP servers connected fine within ~6 s
  (`plugin:serena:serena` in 4865 ms, `peekaboo` in 2501 ms, etc.) —
  slow-MCP-startup is **not** the cause; the 120 s `readyTimeoutMs`
  was nowhere near exhausted by MCP.
- The debug log shows the TUI rendered (`screen=577x200`) and the
  session lived ~9 min until the manual kill at 22:12:16. The TUI
  was *up* — yet polygram's `_waitForReady` capture-pane poll never
  matched `READY_HINTS_RE` across the full 120 s
  (`handler-error: TUI did not signal ready` fired at exactly
  22:05:25, 120 s after the 22:03:25 spawn).

**Root cause.** Resuming a large, *cross-backend* historic
session (an SDK-era `ec13e620`) under the tmux backend, while also
applying a different `--agent` and a different project `cwd` (whose
`.claude/settings.json` differs), left the TUI in a state that never
rendered the plain `? for shortcuts` ready hint within 120 s — most
plausibly a resume-replay / project-trust / settings prompt the
capture-pane regex does not recognise. The stale `sessions` row is
the concrete defect: polygram resumed a session that belongs to a
different backend + agent + cwd than the topic is now configured for.

**The fix (commit 2230da6).** A session is valid only for the config
it was created under. `resolveSessionForSpawn`
(`lib/db/sessions.js`) compares the stored `sessions` row's
spawn-identity fields against the freshly-resolved chat+topic config;
on drift it **deletes the stale row** and returns
`existingSessionId: null`, so the next spawn starts **fresh** under
the correct config (and the `onInit` callback re-upserts the row
with the new `claude_session_id`). `buildSpawnContext`
(`polygram.js`) wires this at **cold spawn only** — a warm process
already runs under its spawn-time config, so its row is left alone
until the next cold spawn — and logs a `session-config-drift`
telemetry event with the before/after field values so the soak can
see it firing.

**Field-set decision — only `agent` / `cwd` / `pm_backend`
invalidate** (`SPAWN_IDENTITY_FIELDS` in `lib/db/sessions.js`):

- `agent`, `cwd`, `pm_backend` are **spawn-identity**: baked into the
  process at spawn time (`--agent`, the tmux/SDK working dir, the
  `SdkProcess` vs `TmuxProcess` class) and cannot be changed on a
  live session.
- `model` and `effort` are **excluded**. A live `/model` or
  `/effort` change is pushed into the running session by
  `pm.setModel` / `pm.applyFlagSettings` with **no respawn**
  (`lib/handlers/slash-commands.js` `applyConfigChange`,
  `lib/handlers/config-callback.js`). Including them in the
  invalidating set would double-handle that path AND destructively
  drop the whole session — discarding all conversation context — on
  every model switch. The stored `model`/`effort` columns are
  informational, not identity.

**Self-heal — no manual SQL.** The stale `-1003807211164:3` row
(`agent=shumabit`, `cwd=/Users/ivanshumkov`, `pm_backend=sdk`) drifts
on all three fields versus the Music topic's resolved config
(`music-curation:music-curator`, `/Users/ivanshumkov/Music/rekordbox`,
`tmux`). The next message to thread 3 detects the drift, drops the
row, and spawns fresh with the correct agent/cwd. Every other
pre-per-topic-config stale row across all chats self-heals the same
way. Regression test: `the actual stale shumorobot :3 row self-heals`
in `tests/sessions.test.js` reproduces the exact production row and
asserts `drift.fields = [agent, cwd, pm_backend]` and the row is
dropped — ✖ before the fix (`resolveSessionForSpawn is not a
function`), ✔ after.

**rc.20 is NOT implicated.** `git log -L` over `_waitForReady` and a
`-S` search on `READY_HINTS_RE` across the rc.20 batch
(`5808191..a2d39d0`) show the readiness path was untouched by
Phase 1–4. The last change to it was the L1 banner fix (`e431986`)
and the rc.14 bypass-mode matcher (`c5db495`).

## B3 — mid-turn interrupt did not settle the turn  **[FIXED — commit 1b3fdc1]**

Investigated FIRST (it determines the abort architecture). Finding:
`had_active` (`pm.get(sk).inFlight`) DOES correctly see a live tmux
turn — `inFlight` is a plain boolean set in `_runTurn`, untouched by
the turn-ledger rewrite — and `interrupt()` DOES send C-c. But the
turn did not SETTLE: the new `interrupt-mid-turn` spike scenario
showed `_runTurn` ran the full 120 s `turnTimeoutMs` after an
interrupt.

**Root cause.** C-c stops the agent's work, but an interrupted turn —
especially a tool turn — writes no terminal JSONL `result`, and once
`_runTurn` has seen a tool-use it re-awaits the JSONL `result` ALONE
(capture-pane dropped). With no `result` ever arriving the turn hangs

## B6 — paste into a not-yet-quiescent slow-custom-agent TUI  **[FIXED — `_waitForReady` quiescence gate]**

**This is the real root cause of the 2026-05-18 Music-topic
recurrence B5 misdiagnosed.** shumorobot production, 2026-05-18, the
Music topic, TWICE in a row: polygram pasted the user's prompt into
the claude TUI but it sat **unsubmitted** in the input box (`❯
[Pasted text #1]/ … <untrusted-input>…`). The turn never started; the
reactor showed a fake THINKING→STALL.

> **First-cut correction.** This entry's first cut blamed a missing
> banner gate (`_waitForReady` returning while `TUI_BANNER_RE` was
> still on the pane) and shipped a banner gate as the fix (commit
> `5ddd23f`). The `slow-agent-large-prompt` real-TUI spike — added
> in this same investigation — **disproved that fix**: it spawned
> the production `music-curation:music-curator` agent and
> `_waitForReady` then **never resolved**, throwing
> `TMUX_READY_TIMEOUT` after the full 180 s. A live `capture-pane`
> showed why: the claude TUI's startup banner stays on the pane
> **indefinitely** — the agent emits nothing before the first turn,
> so the banner never scrolls into scrollback. The banner is *not* a
> "not ready" signal. The correct fix (below) supersedes `5ddd23f`.

**Root cause (verified — `lib/process/tmux-process.js`
`_waitForReady`; production debug log; live spike).** `_waitForReady`
(the gate `start()` blocks on before declaring the process usable)
returned **the instant `READY_HINTS_RE` matched**:

```
lastBuf = await this.runner.captureWide(this.tmuxName, { lines: 80 });
if (READY_HINTS_RE.test(lastBuf)) return;          // ← resolves on poll 1
```

The claude TUI renders its ready hint (`? for shortcuts` /
`bypass permissions on`) at the bottom of its startup banner
**immediately** — before MCP servers have loaded. The production
debug log for the incident
(`~/.polygram/shumorobot/logs/tmux-claude--1003807211164-3.log`)
shows MCP connections spanning **14:45:31→14:45:40** — playwright
2.9 s, context7 3.1 s, serena 3.8 s, peekaboo 2.2 s — with the
screen repainting hard the entire time (`High write ratio: blit=0,
write=3073 (100.0% writes)`). The user's message arrived at
`ts=14:45:27`, *before* MCP startup even began. `_waitForReady`
matched the ready hint on its first poll, `start()` resolved, and the
first `send()` pasted the prompt into a TUI mid-MCP-load. The
submitted Enter was dropped while the TUI was still ingesting
startup, so the prompt sat unsubmitted — the turn never began.

On a **no-agent** TUI the startup window is sub-poll, so the bug
never bit; a **slow custom-agent** spawn opens a multi-second window
every time the session is freshly spawned (after a daemon restart,
or an S2 session-config-drift respawn). `pasteAndEnter`'s B5
submit-confirm does not save it: a primary `send()` after a resolved
`start()` does run with `confirmSubmit:true`, but the paste lands in
a TUI whose input handler is not yet stable — the failure is upstream
of `pasteAndEnter`, in readiness detection.

**Fix (`_waitForReady` quiescence gate).** The startup banner is not
usable as a discriminator (it never leaves the pane pre-turn — proven
by the live spike). The real signal is **quiescence**: a
genuinely-ready idle TUI produces a **byte-stable `capture-pane`
between polls** (static banner + empty input box + ready hint),
whereas a mid-startup TUI repaints every tick. `_waitForReady` now
requires the ready hint present **AND** the captured pane unchanged
across consecutive polls for `quiesceMs` continuously:

```
const hintPresent = READY_HINTS_RE.test(lastBuf);
const paneStable  = prevBuf !== null && lastBuf === prevBuf;
if (hintPresent && paneStable) {
  if (readySinceAt == null) readySinceAt = this._now();
  if (this._now() - readySinceAt >= this.quiesceMs) return;
} else {
  readySinceAt = null;          // pane moved / hint gone → reset
}
prevBuf = lastBuf;
```

This is the same "must hold this long" idea `_awaitTurnComplete`
already uses for turn completion (`quiesceMs`, 500 ms in production).
Readiness needs at least two matching captures, so it can never
resolve from a single mid-startup poll. The loop stays bounded by
`readyTimeoutMs`, so a genuinely wedged spawn (pane never settles)
still throws `TMUX_READY_TIMEOUT` — the gate does not mask a hang.

**Test (deterministic red→green).** `tests/tmux-process.test.js`,
`describe('B6 — _waitForReady quiescence gate (slow custom-agent
startup)')` — 4 tests, a fake runner whose `captureWide` returns a
**changing** mid-startup pane (the ready hint present the whole time,
a moving MCP-loading spinner on the bottom line) for the first 4
polls, then a byte-stable settled pane. Verified red→green against
the **true pre-B6 `_waitForReady`** (`git show 50adc47`): ✖ all 4
fail before the fix — `_waitForReady` resolved on poll 1 while the
pane was still repainting; ✔ all 4 pass after. The four pins:
`_waitForReady` does not resolve while the TUI is still repainting;
it does not resolve on a single ready capture (stability is
unobservable from one poll); it resolves once the pane is byte-stable
with the hint; and `TMUX_READY_TIMEOUT` still fires if the TUI never
settles. (R7's wedged-capture test stub was updated — it now returns
a stable ready buffer for the first 3 captures so the spawn's
ready-check completes, then wedges; R7's intent — `_awaitTurnComplete`
abort handling — is unchanged.)

**Closed coverage gap — the spike now spawns WITH an agent.** The
real reason B5's fix did not hold: `setupRealTui` in
`scripts/spikes/autosteer-tui-real.mjs` spawned every TUI with **no
agent**, so no scenario ever exercised a slow startup. `setupRealTui`

## B7 — paste-without-submit: confirm via the JSONL token, not the pane  **[FIXED — JSONL-token submit confirmation]**

**This is the real fix B5 and B6 both missed.** shumorobot
production, the Music topic, msgs 789 / 791 / **803** (2026-05-19) —
the THIRD recurrence of paste-without-submit. polygram pasted the
user's prompt into the claude TUI but the Enter did NOT submit it;
the prompt sat unsent in the input box and the turn never started.

**Why B5 and B6 both missed it.**

- B5 added a submit-confirmation to `pasteAndEnter` that checked
  "did the paste submit?" by **reading the pane with capture-pane**
  and re-sending Enter if the input box still held the paste.
- B6 fixed a fresh-spawn readiness race (`_waitForReady` quiescence
  gate).
- Neither holds for msg 803 because (a) it was a **WARM,
  already-running** session — a previous turn had just completed, so
  it is not B6's fresh-spawn case; and (b) B5's capture-pane confirm
  **false-positives**. The claude TUI collapses a large paste into a
  `[Pasted text #N]` PLACEHOLDER — the actual pasted text is hidden
  behind that placeholder. B5's check "is the pasted text still in
  the input box?" looks for the text, cannot find it (it is
  collapsed to `[Pasted text #2]`), and wrongly concludes "submitted
  ✓" while the prompt is still sitting there.

**Production evidence (msg 803, 2026-05-19).** TUI capture: `❯
[Pasted text #2]/  / <channel … message_id="803" …><untrusted-input>
download previews …</untrusted-input></channel>` — the prompt
sitting unsubmitted. events DB: `handler-error {msg_id:803,
error:"turn produced no JSONL reply text within grace window"}`,
~5 s after THINKING. polygram now fails loud fast (the §6 fail-loud
work holds), but the paste-submit bug itself recurred.

**Did solution §5 exist?** Solution doc §5 ("paste gating on JSONL
confirmation") *was* implemented — as `_confirmPaste` /
`_awaitPasteConfirm` / `_pasteConfirms` in `tmux-process.js`
(`pasteConfirmMs`). But §5's purpose is a **next-paste barrier** so
two pastes cannot concatenate — `_awaitPasteConfirm` releases the
gate on a `user-message` OR a `queue-operation`, and it gates the
*next* paste asynchronously without blocking the current caller. It
is NOT a *this-paste-submitted* confirmation. B5, instead of
extending §5 into a submit-confirm, added an independent
capture-pane confirm in the runner — that was the regression. B7
adds the missing piece: a JSONL-token confirmation of the primary
paste.

**The fix.** The B5 capture-pane confirm is removed from the runner
entirely (`lib/tmux/tmux-runner.js` — `pasteAndEnter` is back to
pure mechanics: paste + Enter + drain; no `confirmSubmit`, no
`inputBoxHoldsPaste`, no `submitConfirm` tunables). Submit
confirmation lives in `TmuxProcess` and keys on the correlation
token. **It runs as a CONCURRENT racer in `_runTurn`, not a blocking
gate inside `_pasteAndEnter`** — an early cut tried the blocking-gate
shape and it deadlocked: `_pasteAndEnter` holds `_pasteLock`, so
blocking it on the confirm stalls *every following paste* — an
autosteer that should fold into the primary turn could never paste,
and 18 JSONL tests + the suite wedged. The watchdog design:

- `_pasteAndEnter(text)` (`lib/process/tmux-process.js`) — paste +
  Enter + drain, then releases `_pasteLock` via the existing §5
  `_awaitPasteConfirm` barrier. No submit-confirm here.
- `_runTurn` (`tmux-process.js`) — after the primary paste, arms
  `_confirmSubmitViaJsonl(turn.token, turn)` and derives two
  promises:
  - `submitConfirmP` — **rejects** `TMUX_SUBMIT_FAILED`; a racer in
    the turn's `Promise.race` → the turn fails fast and loud
    (`_runTurn`'s `catch` → `_errorResult` → `_finishTurn`) instead
    of running to the reactor grace window.
  - `submitOkP` — **resolves only once the submit is confirmed**; it
    **gates the capture-pane racer**. A capture-pane "idle" reading
    only means "the turn completed" once the turn has actually
    STARTED — for an unsubmitted prompt the pane is idle because the
    prompt sits in the input box, not because a turn finished.
    Without the gate the capture racer would win first with
    `TMUX_NO_JSONL_TEXT` and mask the real `TMUX_SUBMIT_FAILED`.
    (`captureCompleteP` still runs immediately — its rejection is
    awaited *inside* the racer so it is never an orphaned unhandled
    rejection — only the racer's eligibility to WIN is gated.)
- `_confirmSubmitViaJsonl(token, turn)` (`tmux-process.js`) — loops:
  `_awaitSubmitConfirm(token)` waits up to `submitConfirmMs`
  (1500 ms) for the token to surface in a JSONL `user-message`. On a
  miss it re-sends Enter (the absorbed Enter never registered the
  collapsed `[Pasted text #N]` block) and retries, bounded by
  `submitConfirmRetries` (4). If the owning `turn` reaches a terminal
  state first (the real result/capture racer won, or the turn was
  killed) the loop **bails** — no stray retry Enter into an unrelated
  turn. If the token never surfaces after all retries it throws
  `TMUX_SUBMIT_FAILED`.
- `_awaitSubmitConfirm` / `_confirmSubmit` / `_submitConfirms` — a
  token→resolver Map, fired ONLY by a JSONL `user-message`
  (`_routeUserMessage` calls `_confirmSubmit`), NOT by
  `queue-operation`. A `queue-operation enqueue` means the paste was
  *parked* in the TUI queue, not *registered* as a turn — so for a
  primary paste it is not proof of submission; the `user-message`
  is. `_routeUserMessage` also fires `_confirmSubmit` for a
  **token-less** `user-message` claimed by the orphan-primary
  fallback (under that orphan turn's own token) — that fallback IS
  proof the primary's prompt started.
- The correlation token is the matcher: exact, unique per paste, and
  **immune to the `[Pasted text #N]` placeholder entirely** — it
  travels inside the `<polygram-info>` block and reproduces verbatim
  in the JSONL `user-message` regardless of how the TUI renders the
  paste in the pane.
- Only a PRIMARY turn's paste into an idle TUI is confirmed
  (`_runTurn`). An autosteer paste into a busy TUI legitimately parks
  in the TUI queue and may produce no immediate `user-message` —
  confirming it would mis-fire, so autosteer is unchanged.
- `kill()` releases any pending `_submitConfirms` waiter so a confirm
  on a dead session does not burn its whole retry budget.

**Test (deterministic red→green) — keyed on the WARM-session
recurrence shape.** `tests/tmux-process.test.js`,
`describe('TmuxProcess B7 — JSONL-token submit confirmation')` — 5
tests. A test-helper option `autoSubmitOnEnter` (default `true`)
models a normal TUI: it hooks `_confirmSubmitViaJsonl` (called only
for a primary paste) to feed the tokened `user-message`, so every
non-B7 `send()` test stays faithful (a turn that later times out
still SUBMITTED first). The B7 tests pass `autoSubmitOnEnter:false`

- `confirmed: tokened user-message arrives → resolves, no retry

## B8 — B6's pane-stability readiness gate is fooled by a stable-but-loading pane  **[FIXED — `_waitForReady` debug-log quiescence gate, commits `ab94dea` / `55194c6`]**

**This is the real root cause behind the Music-topic
paste-into-not-ready-TUI break that B6 only partially fixed.**
shumorobot production, the Music topic, 5+ times: polygram pasted the
user's prompt into the claude TUI but the submitted Enter was
dropped — the prompt sat unsubmitted, the turn never began.

**Why B6 was insufficient.** B6's `_waitForReady` quiescence gate
declares the TUI ready when a READY hint is present **AND** the
`capture-pane` output is byte-stable across consecutive polls for a
settle window. B6's reasoning was "a mid-startup TUI repaints every
tick, a ready idle TUI is byte-stable". **That reasoning is wrong for
a slow-MCP startup.** Verified against the real production debug log
(`~/.polygram/shumorobot/logs/tmux-claude--1003807211164-3.log`): in
a cold-start block the claude `[REPL:mount]` fires *immediately* —
before any MCP server connects — and paints the ready hint at once.
The MCP servers then load **entirely off-screen**: the ~33 s
cold-start window (`plugin:serena:serena` **27.5 s**, context7 26 s,
playwright 24 s, peekaboo 9.3 s) has only a single `Slow render` line
in it. So during MCP load the **pane is BYTE-STABLE** — B6 reads
"stable = ready", `start()` resolves mid-MCP-load, the first `send()`
pastes into a TUI that is not yet interactive, the Enter is dropped.
rc.26's `isolateUserConfig` removes the MCP servers for the Music
topic specifically, but the readiness gate is still wrong for **any**
non-isolated topic that legitimately loads MCP servers.

**Debug-log investigation — explicit marker or quiescence?** The task
required reading a real slow-MCP `--debug-file` log first and
checking whether claude writes an explicit "startup complete" /
"ready" marker line after the MCP servers connect. **It does NOT.**
In every cold-start block of the production log, the last MCP
`Successfully connected … in NNNNms` line is followed only by a stray
`Slow render`, then silence (over an hour of it on an idle topic).
There is no "all servers connected" / "startup complete" / "ready"
marker. So the gate uses debug-log **QUIESCENCE**, not a marker.

**Root cause, precisely.** The pane is fooled; the claude
`--debug-file` log is NOT. During MCP startup that log is DENSELY
written (dozens of `MCP server "X": Starting connection` /
`…Successfully connected in NNNNms` lines across the cold-start
window); once the TUI is genuinely idle the log goes quiet. The debug
log is the readiness signal immune to the stable-stuck-pane illusion.

**The fix (`_waitForReady` debug-log quiescence gate).**
`_waitForReady` now requires **three** conditions, not two:

```
ready ⇔ (READY hint present in pane)
     AND (pane byte-stable across consecutive polls)   ← B6
     AND (the --debug-file log has not grown for
          readyDebugQuietMs, default 1 s)              ← B8, new
```

During MCP load the debug log grows every poll → the quiescence clock
resets → not ready. After MCP load the log falls silent → quiet →
ready. The gate stays bounded by `readyTimeoutMs`, so a genuinely
wedged spawn (the log never quiet, e.g. an MCP crash loop) still
throws `TMUX_READY_TIMEOUT` — the gate does not mask a hang.

**Mechanism — a synchronous size probe, not a second tailer.** The
readiness loop already polls `capture-pane` on a timer, so
`_waitForReady` does a synchronous `fs.statSync(debugLogPath).size`
each poll and treats any size increase since the previous poll as "the
log grew → claude is still writing". This is exactly `LogTail`'s
*approach* — stat-based size-delta detection, ENOENT-tolerant (an
absent log, before claude creates it, reads as quiet so a fast no-agent
spawn still gates on the B6 pane check alone) — without arming a
second async tailer or hand-rolling `fs.watch`. Fully deterministic in
tests via an injected fake `fs`.

**Scope — startup only, never mid-turn.** The debug log keeps being
written DURING normal turns (renders, tool activity), so
whole-log quiescence would wrongly block mid-turn. But `_waitForReady`
runs **only at startup, before any turn**, so startup-phase quiescence
is exactly the right window — and the `readyDebugQuietMs` clock lives
entirely inside `_waitForReady`, never consulted by
`_awaitTurnComplete`.

**Test (deterministic red→green).** `tests/tmux-process.test.js`,
`describe('B8 — _waitForReady debug-log quiescence gate (slow-MCP
startup)')` — 3 tests. A fake runner whose `captureWide` returns a
**byte-stable pane WITH a ready hint from the very first poll** (the
exact B6-fooling shape), plus a fake `fs` whose debug-log size **grows
on the first N polls then goes quiet**. The pins: `_waitForReady` does
NOT resolve while the debug log is still growing; it DOES resolve once
the log goes quiet; and a debug log that never goes quiet still hits
`TMUX_READY_TIMEOUT`. Verified red→green against the **true B6-only
`_waitForReady`** (`git show HEAD` before the fix): ✖ 2 of 3 fail —
`_waitForReady` resolves early on the stable pane (poll ~7, before the
20 writing polls finish), and the never-quiet-log case resolves
instead of timing out; ✔ all 3 pass after.

**Real-TUI spike.** `scripts/spikes/autosteer-tui-real.mjs` adds
`slow-mcp-startup-waits-out-load` — spawns the production
`music-curation:music-curator` agent (cwd `~/Music/rekordbox`)
**WITHOUT `isolateUserConfig`**, so the global MCP servers DO load and
startup is genuinely slow, then times `start()`'s readiness wait and
asserts the first prompt submits cleanly. Run result (warm MCP
caches): `[REPL:mount]` at startup +0.5 s, the last MCP server
(peekaboo) connected at +4.6 s; `_waitForReady` declared ready at
**8.5 s — after** the MCP load finished, then the first prompt
submitted cleanly ("Hey Ivan! What's up?" in 3.1 s, 7/7 assertions).
Pre-B8 the B6-only gate would have resolved within ~2 s of REPL mount,
while serena/peekaboo were still connecting. On a true cold start
(serena alone ~27.5 s) the gate waits proportionally longer — the
decisive property is that readiness is declared only **after** the
debug log falls quiet, i.e. after MCP startup genuinely finishes.
Integration guard, not a deterministic RED (MCP connect times vary
with cache warmth) — the deterministic proof is the unit suite above.

## B10 — turn declared done while an `Agent` subagent is still running  **[FIXED — `outstandingSubagents` tracking + §6 subagent re-check]**

Production incident, shumorobot Music topic, 2026-05-20 03:01. The
Music agent (`music-curation:music-curator`) delegated work to a
subagent via claude's **`Agent` tool** (the subagent/Task tool — in
CLI v2.1.142 it is named `Agent`). polygram closed the turn ~7 s in
with `handler-error {error:"turn produced no JSONL reply text within
grace window"}` — the §6 fail-loud — while the subagent was just
getting started. The real reply arrived MINUTES later via the
autonomous-wakeup path, out of band, with a stuck error reaction.

**Verified mechanism (real JSONL,
`~/.claude/projects/-Users-ivanshumkov-Music-rekordbox/2a494fcf-…jsonl`,
the 20:01 UTC turn).** The turn's JSONL:

```
20:01:06  user      — the prompt (turn starts)
20:01:10  assistant — thinking            stop_reason: tool_use
20:01:11  assistant — tool_use(Agent)     stop_reason: tool_use   id=toolu_…r3eMVD
   … ~11 minutes, MAIN pane quiescent, subagent runs in its sidechain …
20:12:08  user      — tool_result(for=toolu_…r3eMVD)   ← the subagent returned
20:12:10  assistant — text[174]           stop_reason: end_turn   ← the real reply
```

So between the `Agent` tool_use (20:01:11) and its `tool_result`
(20:12:08) there is an **outstanding `Agent` tool_use with no
matching `tool_result`** — directly analogous to an outstanding
foreground `Bash`. While it is outstanding the MAIN tmux pane is
quiescent (the main agent is just waiting on the subagent). The
subagent's own activity (`isSidechain:true` lines) lives in a
SEPARATE sidechain file, NOT this main session JSONL — so the
reliable signal in the main session JSONL is the **outstanding
`Agent` tool_use**, exactly mirroring how a long `Bash` is already
handled.

**Why it fired.** `_runTurn`'s capture-won branch already re-waits on
the JSONL `result` when `turn.toolUsedThisTurn` is set (a tool ran →
a transient idle between tool calls is not completion). But that flag
is set by the `tool-use` EVENT, which the JSONL tail delivers
asynchronously. In the production race capture-pane judged the MAIN
pane quiescent (`quiesceMs` 500 ms) BEFORE the `Agent` tool_use line
was tailed → `toolUsedThisTurn` still false → the §6 branch → the
1.5 s late-grace elapsed with no JSONL reply text (the main agent had
emitted only the `Agent` call) → §6 fail-loud threw.

**Fix.**

- `session-log-parser.js` — a user line with ARRAY content carries
  API-shaped `tool_result` blocks (tool feedback, not a prompt).
  Previously dropped entirely; now `extractToolResults` surfaces a
  `tool-result {toolUseId, isError}` event from both `parseLine` and
  the `SessionEventAggregator`. This is the "a subagent returned"
  signal.
- `tmux-process.js` turn ledger — each Turn carries
  `outstandingSubagents` (a `Set` of `Agent` tool_use ids). A
  `tool-use` event with `name === 'Agent'` adds its id; the matching
  `tool-result` event removes it. A non-empty set ⇒ a subagent is
  running ⇒ the turn is genuinely in flight.
- `_runTurn` §6 branch — after the late-grace elapses with `no-jsonl`,
  if `turn.outstandingSubagents.size > 0` the turn does NOT fail loud.
  It re-waits on the JSONL terminal `result` (emitting a
  `subagent-wait` event), bounded by the absolute `turnDeadlineP` and
  the interrupt signal so a genuinely wedged turn still fails loud and
  an interrupt still ends it promptly. The turn completes only when
  the subagent returns and the main agent emits its real terminal
  reply. The 1.5 s late-grace bridges the tail latency — the `Agent`
  line is parsed and `outstandingSubagents` populated well within it.
- The `toolUsedThisTurn` re-race (line ~773) is unchanged — the other
  ordering (the `Agent` line tailed BEFORE capture wins) was already
  safe; the §6 re-check covers the lost race.
