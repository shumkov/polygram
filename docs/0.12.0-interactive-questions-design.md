# 0.12.0 — Interactive questions → Telegram (AskUserQuestion as native buttons)

**Status:** design (revised after 2026-06-08 multi-persona review) · not yet built ·
supersedes the temporary "forbid AskUserQuestion" system-prompt rule shipped in rc.29.

## Problem

When claude wants to ask the user a multiple-choice question it uses its built-in
**`AskUserQuestion`** tool. On the **channels** backend that opens a *blocking
terminal selection widget* (`1/2/3 · Type something · Enter to select`). The
bridge talks to claude only via the `reply` tool (out) and `<channel>` messages
(in) — it has **no way to answer a TUI widget** — so the session **parks** until
someone manually presses Esc. Live incident: Shumabit@UMI WA topic 2026-06-08,
~9 min wedged, user's messages stuck behind the menu, `cli-mid-turn-unknown-prompt`
watchdog spinning.

Separately, even where it doesn't wedge, **polygram never renders claude's
questions as Telegram buttons.** The inline-keyboard machinery exists
(`lib/approvals/ui.js` for the SDK `canUseTool` approval cards, plus config + poll
keyboards) but was never wired to `AskUserQuestion`. The user expects to **tap a
button** (or type a free answer), like the approval cards.

**rc.29 mitigation (temporary):** the channels system prompt forbids
`AskUserQuestion`; claude must put choices as a numbered list in its reply text and
the user answers with the number/text. Stops the wedge, but no buttons. **This
design replaces that** — see §Cleanup.

## Goals

1. claude can ask a multiple-choice question and the user **taps a button** to
   answer. **End state covers both backends**, but reached in order: **channels
   first (P1–P3); SDK parity is P4** (and gated on Open Q1 — see Phased build).
2. Support the `AskUserQuestion` surface as a **capability ceiling**, not a
   committed deliverable: up to 4 questions/call, 2–4 options each (label +
   description, optional preview), **multiSelect**, **free-text "Other"**. **P1
   ships single-select / single-question; P2–P3 (multiSelect, Other, multi-question)
   are gated on P1 telemetry** showing the agent actually emits those shapes in
   real chat traffic — "the agent already uses all of it" is an upstream-CLI
   observation, not measured polygram usage.
3. **Never wedge — and this is the load-bearing guarantee, so it is designed
   explicitly against the real daemon timers** (see §"Keeping the turn alive").
   A question that times out, is ignored, or is interrupted resolves gracefully
   (claude gets a `{timedout}`/`{cancelled}` result and continues), never a parked
   session.

## Non-goals

- Rendering claude's *internal* tool-approval prompts (the existing SDK
  `canUseTool` card path — unchanged).
- Rich media inside option buttons (Telegram buttons are text-label only;
  descriptions/previews go in the message body).
- Cross-question back-navigation / revising an earlier answer in a 4-question set
  (P1–P3 treat a multi-question `ask` as one atomic, forward-only set; revisit later).

## Approach — a custom `ask` MCP tool (not TUI interception)

claude calls **`mcp__polygram-bridge__ask`** instead of native `AskUserQuestion`.
It is a normal tool call that **returns a value** — no TUI widget — so on channels
there is no TUI menu to navigate (driving the widget via `send-keys` would be
fragile and version-brittle, the class of pane-scraping we keep getting burned by).

**Channels** uses the bridge tool round-trip; **SDK** registers the same tool via
an in-process MCP server **— but see the P4 caveat: this is a spike, not a known-good
port** (no `createSdkMcpServer`-style host-supplies-a-result pattern exists in
`lib/sdk` today; Open Q1 must be resolved first).

### Tool shape (`ask`)

```
mcp__polygram-bridge__ask({
  chat_id, turn_id,                 // same routing contract as `reply`
  questions: [{
    header,                         // ≤12-char chip
    question,                       // the prompt text
    multiSelect: false,
    options: [{ label, description?, preview? }, ...],   // 2–4; label ≤40 chars
    allowOther: true                // show a "type my own" affordance
  }, ... up to 4 ]
})
→ returns { answers: [{ header, selected: [label...], other?: "free text" }, ...] }
   or { cancelled: true } / { timedout: true }
```

## Transport — the bits that don't exist yet (must be built in P1)

The original draft assumed the answer rides back on the existing `tool_ack`. **It
cannot** — the review confirmed against the protocol:

1. **Bridge→daemon: open the tool-name gate.** `ToolCallMessageSchema.name` is
   `z.enum(['reply','react','edit_message'])` (`channels-bridge-protocol.js`); an
   `ask` call is **dropped by schema validation before `_dispatchToolCall` runs**.
   Add `'ask'` to the enum. `_dispatchToolCall` currently assumes reply-shaped args
   (`{chat_id,text,files}`) — its chat_id-mismatch, content-dedup, and
   reply-turn-binding branches (`cli-process.js`) must be **gated off for `ask`**,
   which has a different arg shape.
2. **Daemon→bridge: a new answer-bearing message kind.** `ToolAckMessageSchema` is
   `{kind, tool_call_id, ok, error?}` — **no field for an answer** — and
   `resolveToolAck` calls `p.resolve()` with **no value**, so `awaitToolAck`
   resolves to `undefined` and the CallTool handler returns a hardcoded `'sent'`.
   Add a `question_answer` daemon→bridge kind `{tool_call_id, result}` where
   `result` is the `{answers}|{cancelled}|{timedout}` payload, and thread it: a new
   `awaitQuestionAnswer(tool_call_id)` (separate from the fast `awaitToolAck`) whose
   Promise resolves to `result`, which the `ask` CallTool handler returns as the
   tool result. The fast `reply` ack path stays exactly as-is.

## Keeping the turn alive — the anti-wedge core (P0 from review)

The original draft claimed an open `ask` "keeps the turn alive via the rc.28
tool-activity extension." **That is false as built** and inverted the anti-wedge
guarantee into a guaranteed wedge:

- `_extendQuietOnToolActivity` fires **once** per hook (`PreToolUse`/`PostToolUse`).
  A tool that blocks for minutes emits `PreToolUse` once at invocation, then nothing
  until it returns — so **no recurring activity resets the idle ceiling**.
- The daemon's **idle ceiling kills the turn at `DEFAULT_TURN_TIMEOUT_MS = 600_000`
  (10 min)** and the **absolute cap at `DEFAULT_TURN_ABSOLUTE_MS = 1_800_000`
  (30 min, never resets)**. A 15-min question wait blows straight through the 10-min
  ceiling → `TURN_TIMEOUT` rejects the turn **mid-question**, orphaning the live
  keyboard — the exact incident class this design exists to kill.

**Design:**
- When `_dispatchToolCall` opens a `pending_questions` row, start a **recurring
  keep-alive timer** (every ~60s, `unref`'d) that resets that turn's `hardTimer`
  (the 10-min idle ceiling) for as long as the question is open. Stop it on resolve.
  This is **new machinery, not a reuse of rc.28's one-shot extension.**
- The **question's own timeout drives expiry**, independent of the turn timers, and
  **defaults to 8 min — comfortably under the 30-min absolute cap** even if the turn
  already ran a while before asking. (Tune from telemetry; the hard constraint is
  `question_timeout + already_elapsed_turn_time < turnAbsoluteMs`. If a long turn is
  near the absolute cap when it asks, resolve `{timedout}` early rather than letting
  the absolute timer reject the turn.) On expiry → resolve `{timedout:true}`, strip
  keyboards, clear all per-session question state.
- **Watchdog suppression (also P0-adjacent):** while a `pending_questions` row is
  open, claude is idle (no "esc to interrupt"), so the 5s mid-turn pane poll would
  (a) escalate the reactor to STALL 🥱 and (b) fire `UNKNOWN_PROMPT_HEURISTIC_RE`
  against the idle pane on a loop (a `?`/numbered-list/`Yes/No` in the echoed
  question text matches it). Gate `_pollMidTurnDialogs`/`_checkMidTurnDialog`: if a
  question is pending for the session, **skip the unknown-prompt heuristic and pause
  STALL escalation**; the reactor shows a dedicated "waiting on your answer" state
  instead.

## Telegram rendering

One **question at a time** (sequential), each its own message + inline keyboard.
A **progress line** (`Question 2 of 4`) appears in the body when `questions.length>1`
so the user doesn't read Q2 as an unrelated new agent message.

**Message body** (rendered **plain-text, NO `parse_mode`** — see Security): the
`header` chip, the `question`, then each option as `label — description`
(+ `preview` in a fenced block). Buttons are label-only; descriptions live here.

**Keyboard:**
- *Single-select:* one button per option (`callback_data = q:<qid>:<token>:opt:<i>`).
  Tap → record → **edit the message to a text receipt** ("Selected: <label>"),
  remove the keyboard, advance to the next question (or finish). The receipt is the
  user's confirmation their tap registered.
- *Multi-select:* each option button toggles a ✅ prefix (state held in
  `state_json`), plus a final **`✅ Submit`** row. **Submit is disabled until ≥1
  option is toggled** (no ambiguous empty-submit). On Submit → receipt + advance.
- *Free-text "Other":* a **`✏️ Type my own`** button → see §Free-text state machine.
- *Pagination:* options never exceed the 8-row threshold (2–4 options + Submit +
  Other ≤ 7 rows), so **option-count pagination is out of scope**. Pagination exists
  **only** for a body that would exceed Telegram's 4096-char cap (long
  descriptions/previews): split the *body* across `‹ Prev / Next ›` pages
  (`q:<qid>:<token>:page:<n>`) with the keyboard repeated; selection state persists.
  Per-option `preview` is truncated to a stated cap so a single option can't blow
  the cap by itself.
- Long labels: `label ≤ 40 chars` validated at call time (incl. the ✅ prefix);
  one option per row when any label > 20 chars, else two per row.

Reuse `lib/approvals/ui.js` keyboard-builder patterns.

## Security model (P1 cluster from review)

The `ask` surface accepts **agent-authored** option text and **user-supplied**
answers, in chats that **may be groups**. The approval flow already solved the
analogous problems — reuse it:

- **Per-row callback token.** `callback_data = q:<qid>:opt:<i>` is forgeable (qid is
  a sequential row int; an attacker crafts a `callback_query` with any option index
  and injects an answer into claude without seeing the keyboard). Issue a **128-bit
  random token** per question (reuse `lib/approvals/store.js` `newToken`/`tokensEqual`,
  constant-time compare): `q:<qid>:<token>:opt:<i>`. **Single-use** — mark consumed
  via an atomic `WHERE status='pending'` UPDATE (replay protection).
- **Respondent authorization.** Store the originating `from.id` on the
  `pending_questions` row. The `callback_query` handler **rejects any `ctx.from.id`
  that doesn't match** (mirrors `approver_chat_id`), so a different group member
  can't answer someone else's question. The free-text "Other" path is gated on the
  **same `from.id`**. (If we ever want group-consensus answering, that's an explicit
  opt-in, not the default.)
- **No HTML/Markdown injection.** Render the body **plain-text only (no
  `parse_mode`)** — exactly the approval card's rationale ("tool_input originates
  from Claude and could contain Markdown specials or tg:// links crafted for
  phishing"). Agent-supplied `label`/`description`/`preview` never reach the
  Markdown→HTML pipeline.
- **Free-text bound.** The `other` value is truncated to **≤1000 chars** at the
  collection point and labeled as user-supplied in the tool result so claude applies
  appropriate skepticism (it enters the agent's context).
- **Payload size.** `questions_json` is size-capped before DB insert + before
  Telegram send.

## Answer round-trip + state

A `pending_questions` table mirrors `pending_approvals`:
`(id, bot_name, session_key, chat_id, turn_id, tool_call_id, from_id,
callback_token, questions_json, state_json, status, message_ids_json, created_ts,
answered_ts)`. `state_json` holds per-question multi-select toggles + current page;
`message_ids_json` the keyboard messages to edit/strip.

**`callback_query` routing — a NEW top-level branch + handler.** The router in
`polygram.js` dispatches `cfg:` → config, else → `handleApprovalCallback`; a `q:`
tap currently falls through to the approval handler and **silently no-ops** (its
regex won't match → no `answerCallbackQuery`). Add `else if
(data.startsWith('q:')) → handleQuestionCallback`, wired beside the existing
handlers. The handler validates token + `from.id`, mutates `state_json`, edits the
message, and on completion **resolves the tool** (channels: write the new
`question_answer` message; SDK: return the tool result), sets `status=answered`,
strips keyboards.

### Free-text "Other" state machine (P1 — was underspecified across 4 personas)

The interception is a **named hook**: an early check in `dispatchRegularMessage`
(before `dispatchHandleMessage`/`pm.send`) that looks up an open `pending_questions`
row for the session.

- **Trigger:** *only after* the user taps `✏️ Type my own` does the session enter
  `awaiting_other` (no implicit "any typed text is Other" — that's the swallow-a-new-
  turn hazard). Tapping sets `awaiting_other` + records the tapping user's `from.id`.
- **Capture:** the next inbound text **from that same `from.id`** becomes `other`;
  polygram replies with a receipt ("Got it — using your answer: …"). A second typed
  message **replaces** the first (doesn't append).
- **Identity:** text from any *other* user is **not** consumed — it gets the
  "answer the question above first" nudge (a reply that preserves their text, not an
  ephemeral toast, so nothing is silently lost), and `awaiting_other` stays set.
- **Commands escape:** `/stop` and `/new` are **never** consumed as Other — they
  cancel the question (`{cancelled}`) and clear `awaiting_other`.
- **No indefinite park:** `awaiting_other` is governed by the **same question
  timeout** as the keyboard state. On `{timedout}`/`{cancelled}` the flag is cleared
  unconditionally — the diversion can never outlive its `pending_questions` row.
- **Concurrency:** one pending question per session; a `pending_questions` row open +
  `awaiting_other` are cleared atomically together on resolve.

## Edge cases

- **Restart while pending:** commit to **expire on boot** (don't re-attach stale
  keyboards — a question can be open for minutes across a restart, unlike the
  seconds-long approval cards). On boot, edit each `pending_questions` keyboard
  message to "This question is no longer active" + remove the keyboard, mark
  `status=expired`. The agent's turn is already gone (restart drains it), so there's
  no tool to resolve.
- **`/stop` / `/new` while pending:** cancel, strip keyboards, resolve `{cancelled}`.
- **Concurrent `injectUserMessage` (autosteer) while a question is open:** an
  autosteered follow-up must NOT be eaten by `awaiting_other` (it's gated on the
  tapping user + the explicit Other state). If a question is open and a non-Other
  message arrives, it's nudged, not injected.
- **`PostToolUse` after resolve:** confirm the `ask` tool emits `PostToolUse` when it
  resolves via the new `question_answer` path (not a normal in-process return) so the
  turn's quiet/idle timers re-arm correctly for claude's continuation reply; if it
  doesn't, the resolve path must re-arm them explicitly.

## Cleanup (do not forget — tracked in code + test)

When P5 ships, in `lib/process/cli-process.js` the channels `--append-system-prompt`
block **swaps** the rc.29 rule: remove "NEVER use AskUserQuestion / numbered-list
workaround", add "ask multiple-choice questions via `mcp__polygram-bridge__ask`".
Update/remove the pinning assertion in `tests/cli-process.test.js`
(`/NEVER use the AskUserQuestion tool/`). The rc.29 commit comment + that test note
both point here. **Verify `--disallowed-tools AskUserQuestion` against the pinned
claude CLI** as belt-and-suspenders; if unsupported, channels safety is
prompt-based + the pane watchdog must actively *dismiss* a stray AskUserQuestion
widget (Esc), not just log it.

## Open questions

1. **(gates P4)** Does the Claude Agent SDK let the host *supply* a tool result
   (in-process MCP server returning a value)? If yes, SDK could stay native
   (`AskUserQuestion` intercept) instead of the custom tool — resolve before P4, and
   ideally before P1 freezes the contract, so the SDK path can diverge if it wins.
2. **Question timeout default** — 8 min is chosen to clear the 30-min absolute cap
   with margin; tune from telemetry (too short strands a thinking user, too long
   holds the turn). What's the real session-idle distribution on partner chats?
3. Should `pending_questions` and `pending_approvals` be **one `pending_interactions`
   table**, or kept separate to evolve independently? (Lean separate; revisit.)
4. **Sequential vs batched** 4-question rendering — start sequential; a partner
   facing 4 button-prompts in a row may feel interrogated. Validate against real
   behavior before committing P3.
5. **Operator visibility of a held question** — an `ask` open for minutes keeps the
   turn "alive"; surface it in telemetry (`question-pending` event) so a genuinely
   stalled agent isn't masked as "waiting on an answer".
6. **`--disallowed-tools` support** on the pinned CLI (gates whether channels safety
   is enforced or best-effort) — verify in P5 / Cleanup.
