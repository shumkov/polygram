## Findings (severity-ranked)

### HIGH — `pending_approvals.tool_use_id` is dead-write (pre-existing, made more visible by 0.9.0)
- File: `lib/approvals.js` lines 104–142 + `polygram.js:1523`.
- The column was added by `migrations/010-tool-use-id.sql` and has a partial index `idx_pending_approvals_tool_use_id`. Migration 010's comment claims "Boot-time sweep marks legacy 'pending' rows as 'expired' so the new dedup query (matching on non-NULL tool_use_id) doesn't accidentally match them" — neither the boot sweep nor the dedup-by-tool_use_id query was ever implemented.
- `polygram.js:1523` calls `approvals.setToolUseId?.(row.id, opts.toolUseID);` — optional-chained. **The method does not exist on the store** (grep confirms: only `setApproverMsgId`, `resolve`, `getById`, `listPending`, `sweepTimedOut`, `issue`). Every row written under SDK pm has `tool_use_id = NULL`.
- Dedup falls back to the legacy `(bot_name, turn_id, tool_input_digest)` tuple — which works, just not as advertised in the migration comment.
- Production-data impact: 100% of post-migration-010 rows have `tool_use_id = NULL`. The partial index is empty. The dedup contract claimed in the v4 plan is not enforced — JSON key reordering by the SDK between retries within the same turn would cause dedup-miss + duplicate approval cards. No corruption, just a silent loss of stated defense.
- **Operator query (count affected — should be all rows):**
  ```sql
  SELECT COUNT(*) AS total,
         SUM(CASE WHEN tool_use_id IS NULL THEN 1 ELSE 0 END) AS null_count
    FROM pending_approvals;
  ```
- Recommendation: either implement `setToolUseId` in approvals.js (single-line UPDATE) and add a dedup-by-tool_use_id query, OR delete the column + index in a follow-up migration. Don't leave the trap.

### MEDIUM — Legacy `pending_approvals` rows from CLI pm path are correctly drained, but Telegram card-edit on sweep is best-effort
- File: `polygram.js:1861–1896` (`startApprovalSweeper`), `lib/approvals.js:134-137`.
- Sweeper picks rows by `status='pending' AND timeout_ts < now`, regardless of which path created them. CLI-pm-era rows resolved to `'timeout'` on the next 30s tick. ✅
- Future-timeout rows naturally time out then sweep. ✅
- If a rogue pending exists hours/days old, the card edit at line 1887 will fail (Telegram edits limited to ~48h) and emit `approval-sweep-failed` log noise. Not data corruption.

### MEDIUM — `chat_tool_decisions` shape is identical in both flows; legacy rows honored cleanly
- File: `polygram.js:1707-1743` writes; `lib/db.js:439-458` reads.
- Pre-0.9.0: only the SDK canUseTool path populated this table (CLI pm's IPC translation in 0.8.0-spike's `handleApprovalRequest` mapped `approved-always → approved` and skipped persistence). 0.9.0 keeps the SDK persistence path unchanged.
- All rows in production today were written by SDK pm. Match semantics in `db.lookupChatToolDecision` (lines 446-456): exact / prefix / regex against canonical-JSON input. ✅ Identical between 0.8 and 0.9.
- No risk.

### MEDIUM — `sessions` table: CLI-era rows are readable + writable by SDK pm
- File: `polygram.js:3763-3772` (`onInit` callback), `lib/db.js:118-138` (`upsertSession`).
- Columns: `(session_key, chat_id, thread_id, claude_session_id, agent, cwd, model, effort, created_ts, last_active_ts)`. **No PID, no subprocess metadata, no CLI-specific fields.**
- Risk: zero. SDK pm's `onInit` upserts the same shape on first system/init event. Session resume on boot reads `getSession(sessionKey).claude_session_id` and threads it through `spawnContext.existingSessionId`, which the SDK accepts as `resume`.

### LOW — Dead event kinds in production from CLI pm; no doctor-allowlist conflict
- File: `scripts/doctor.js:195-201`.
- Deleted CLI pm emitted: `respawn-requested`, `respawn-draining`, `resume-fail`. The first two are NOT in doctor's allowlist. **No SQL breakage.**
- `resume-fail` IS in the doctor allowlist AND in the hard-error set. SDK pm doesn't emit `resume-fail`. Existing pre-cutover rows < 24h old will count as failures in `doctor --bot <bot>` for one day post-deploy, then age out. Cosmetic.
- New SDK-only kinds (`drain-queue`, `inject-user-message`, etc.) are also outside the allowlist; doctor never asks for them. ✅

### LOW — `POLYGRAM_USE_SDK` / `POLYGRAM_SDK_CHATS` env vars were never persisted
- File: per cleanup plan §Commit 5 — env-only routing, never written to DB.
- Rollback derivation: 0.8.x default behavior with neither env var set = CLI pm path. The deployed 0.8.x binary on shumabit currently runs with `POLYGRAM_USE_SDK=1`. **A revert to 0.8.x must be paired with re-setting `POLYGRAM_USE_SDK=1` in `start-sessions.sh`** or it falls back to CLI pm and tries to spawn `bin/approval-hook.js`. Not a data integrity issue but a deploy-procedure fragility worth calling out.

### LOW — Rollback safety: no schema or shape regressions
- SCHEMA_VERSION stays at 10. Migration files untouched. 0.8.x reading rows written by 0.9.0:
  - All retained tables keep their write shape identical.
  - `pending_approvals.tool_use_id` stays NULL on both branches (per HIGH finding).
- ✅ Safe rollback path: `npm i -g polygram@0.8.x && launchctl kickstart` should "just work" on existing DBs, modulo the env var caveat.

## Brief summary

The 0.9.0 cleanup is data-integrity safe. **No new migrations**, schema version stays at 10, all retained tables keep their write shape identical to 0.8.x. Rollback to 0.8.x is schema-safe — the only deploy-procedure caveat is restoring `POLYGRAM_USE_SDK=1` in `start-sessions.sh`.

One **HIGH-severity pre-existing finding (not introduced by 0.9.0 but more visible now):** `pending_approvals.tool_use_id` is a dead column. Recommend either implementing `setToolUseId` in `lib/approvals.js` OR dropping the column in a follow-up migration. Don't leave the trap.
