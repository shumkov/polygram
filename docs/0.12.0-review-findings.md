## #1 — [MEDIUM] Stop-hook turn-end fallback is not turn-scoped: one global 'stop-hook' event finalizes ALL grace-pending turns and cross-attributes last_assistant_message

- **Unit:** cli-process-core · **Category:** correctness · **Verifier vote:** 3/3 confirmed real
- **Location:** `lib/process/cli-process.js:1119-1142 (onStop registration in _resolveTurn) + 1553-1562 (Stop case in _handleHookEvent) + 1162-1164 (_finalizeTurn fallback)`

**What & why:**
_handleHookEvent emits a single global `stop-hook` event carrying lastAssistantMessage with NO turn correlation. _resolveTurn registers a fresh per-turn `onStop` listener via this.on('stop-hook', onStop) for EACH turn that enters the stopGraceMs window. Concurrent pending turns are a legitimate, designed-for state (the F#3 orphan-reply handling at 1013-1039 and the queueCap=50 multi-pending logic exist precisely because multiple pendingTurns coexist). When >1 turn is in grace, ONE Stop hook fires EVERY registered onStop; each writes the same `info` into its own pending._stopHookData and finalizes. Result: (1) every grace-pending turn is finalized off a single Stop event even if only one turn ended; (2) a turn that produced no reply-tool text is resolved with ANOTHER turn's assistant text via the empty-reply fallback at _finalizeTurn (`if (!text && pending._stopHookData?.lastAssistantMessage) text = pending._stopHookData.lastAssistantMessage`). This is the exact cross-attribution class the code went to great lengths to prevent for replies (F#3), left unguarded for the Stop fallback. New in 0.12 Phase 1.7 (stopGrace did not exist at base e288077). Field naming verified consistent: hook-event-tail.js:89 sets lastAssistantMessage and the Stop emit at cli-process.js:1559 forwards ev.lastAssistantMessage, so the fallback does fire.

**Evidence:**
_handleHookEvent: `case 'Stop': this.emit('stop-hook', { stopHookActive: ev.stopHookActive, lastAssistantMessage: ev.lastAssistantMessage, backend: this.backend }); return;` (no turn_id). _resolveTurn: `const onStop = (info) => { pending._stopHookData = info; clearTimeout(pending._stopGraceTimer); pending._stopGraceTimer = null; finalize(); }; ... this.on('stop-hook', onStop);`. With two turns in grace, both onStop closures receive the identical global event, both finalize, both pull the same lastAssistantMessage into the empty-reply fallback.

**Suggested fix:**
Apply the Stop fallback / Stop-driven finalize to a single turn only. Either have the Stop hook carry/echo a turn_id matched in onStop, or gate the fallback to when exactly one turn is in grace, or replace the per-turn listeners with one persistent turn-correlated handler. Never let one turn's last_assistant_message resolve a different turn.

## #2 — [MEDIUM] --resume respawn replays the entire prior session's hook ndjson (skipExisting hardcoded false + append-not-truncate), re-driving the turn state machine from stale Stop/PreToolUse events

- **Unit:** hook-infra · **Category:** correctness · **Verifier vote:** 3/3 confirmed real · **Severity adjusted during verification:** high → medium
- **Location:** `lib/process/cli-process.js:1418-1428`

**What & why:**
_armHookTail hardcodes `skipExisting: false` and justifies it with a comment that is factually wrong about the resume path. The comment (lines 1418-1424) says: 'For lazy-respawn on existingSessionId, we currently re-run writeHookFiles which touches a NEW file with the same name (overwrite).' But writeHookFiles does NOT overwrite the ndjson — it opens it with `openSync(ndjsonPath, 'a', 0o600)` (hook-settings.js:145), i.e. APPEND mode, which never truncates. On a --resume respawn the ndjson path is identical (path = `<sid>.ndjson` and sid = existingSessionId, reused on resume), so all hook lines written by the PRIOR claude process are still on disk. With skipExisting:false, LogTail.start() leaves _offset at 0 and replays every historic line through _handleHookEvent. createHookTail's own doc (hook-event-tail.js:127-137) spells out exactly this hazard: stale events 'replay into the fresh process, arming a Stop synth against the fresh turn and heartbeating it from stale events.' Concretely, a historic `Stop` line re-emits `this.emit('stop-hook', ...)` (cli-process.js:1557) and historic PreToolUse/PostToolUse re-emit bogus tool observability — against the freshly-spawned turn.

**Evidence:**
cli-process.js:1428 `skipExisting: false,` (hardcoded; there is NO conditional). Resume path reuses the id: cli-process.js:295 `this.claudeSessionId = opts.existingSessionId || crypto.randomUUID();` and :641 `sessionId: this.claudeSessionId` feeding writeHookFiles. Append (not truncate): hook-settings.js:145 `const fd = fsImpl.openSync(ndjsonPath, 'a', 0o600);`. The doc that contradicts the code: hook-event-tail.js:131-136 ('Without skipExisting they replay into the fresh process, arming a Stop synth against the fresh turn (H4) and heartbeating it (H3) from stale events').

**Suggested fix:**
Plumb the resume decision to the tail: store the local `canResume` (cli-process.js:523/532) on the instance (e.g. `this._resumedSession = canResume`) and pass `skipExisting: this._resumedSession` to createHookTail; OR truncate the ndjson on a resume respawn before arming the tail. Either way the comment's false 'overwrite' premise must be corrected. Add a regression test: pre-populate the ndjson with a Stop line, respawn with a resumable existingSessionId, assert no 'stop-hook' is emitted from the historic line.

## #3 — [MEDIUM] onHookEvent H2 reactor routing is dead on the CLI driver (known hook types never reach it) and its DB persist mislabels backend as 'tmux'

- **Unit:** callbacks-reactions · **Category:** spec-divergence · **Verifier vote:** 3/3 confirmed real
- **Location:** `lib/sdk/callbacks.js:461-545 (esp. 467 backend, 510-541 reactor switch)`

**What & why:**
onHookEvent contains an H2 reactor-routing switch (PreToolUse→classifyToolName setState; PostToolUse/SubagentStop/Notification→heartbeat) and an H1 DB persist hardcoded to `backend: 'tmux'`. On the 0.12 CLI driver this handler is effectively unreachable for every known hook type: cli-process._handleHookEvent (cli-process.js:1489-1665) has explicit `case` arms for UserPromptSubmit/PreToolUse/PostToolUse/SubagentStop/Stop/Notification/parse-error/unknown that each emit a typed event and `return`; only the `default:` arm (line 1660-1663) emits the raw 'hook-event' that maps to onHookEvent (process-manager.js:100). So 'hook-event' fires only for future event names added to KNOWN_EVENT_NAMES but not yet given a case — i.e. essentially never today. Consequences: (a) the H2 reactor escalation-prevention the comment describes (lines 441-447) does NOT run on the CLI driver — PreToolUse setState and PostToolUse/SubagentStop heartbeats from onHookEvent never execute; the reactor only gets heartbeats from the OTHER paths (onStreamChunk, onThinking, onToolUse). PostToolUse specifically has no heartbeat consumer on the CLI path (it's routed to onToolResult, which only logs). (b) if any future event does reach onHookEvent, it will be persisted with the false `backend:'tmux'` even though the sibling 0.12 handlers correctly default to 'cli' (e.g. onHookLagSample:637, onToolResult:661).

**Evidence:**
cli-process.js:1489 switch with `return` in every known case; line 1660-1663 default-only `this.emit('hook-event', ev)`. process-manager.js:100 `onHookEvent: 'hook-event'`. callbacks.js:467 `backend: 'tmux',`; callbacks.js:522-533 PostToolUse/SubagentStop heartbeat branch — unreachable on CLI. Compare callbacks.js:661 `backend: payload?.backend ?? 'cli'`.

**Suggested fix:**
If subagent/long-turn STALL-prevention is meant to work on the CLI driver, add heartbeat() to onToolResult and onSubagentDone (the handlers that DO fire on PostToolUse/SubagentStop), passing `entry` through so they can reach the head reactor — OR have cli-process route known liveness events into 'hook-event' as well as the typed events. At minimum change onHookEvent's persisted backend from hardcoded 'tmux' to `payload?.backend ?? 'cli'` and stamp ev.backend in cli-process before the default emit. Also re-check onTurnTimeout(558)/onHookTailError(581)/onStopHookResolved(599)/onSessionAgePromptDismissed(617) — all hardcode backend:'tmux' but several fire on the CLI path (e.g. hook-tail-error is emitted at cli-process.js:1432).

## #4 — [MEDIUM] subagent-start ↔ subagent-done cannot be JOINed on tool_use_id as documented — subagent-done carries no tool_use_id

- **Unit:** callbacks-reactions · **Category:** spec-divergence · **Verifier vote:** 3/3 confirmed real
- **Location:** `lib/sdk/callbacks.js:674-710 (onSubagentStart / onSubagentDone)`

**What & why:**
The handler comment (callbacks.js:678-682) documents the soak correlation query as a JOIN of subagent-start and subagent-done rows ON json_extract(detail_json,'$.tool_use_id'). But onSubagentStart persists tool_use_id (line 690) while onSubagentDone persists only agent_type, agent_id, duration_ms (lines 699-705) — NO tool_use_id. The root cause is upstream: cli-process emits subagent-start from the Agent PreToolUse (which has tool_use_id, line 1511) but emits subagent-done from the SubagentStop hook (cli-process.js:1544-1550), and SubagentStop carries agent_id/agent_type but NOT the originating tool_use_id (confirmed by hook-event-tail's normalized shape, which has no field linking SubagentStop back to the Agent tool_use_id; the file header even notes parent_tool_use_id is NOT a field). So the documented JOIN key is absent on one side and the pairing query returns zero rows — the entire subagent latency-correlation feature (Phase 1.3) is non-functional. The is_error/durations on tool-result are fine (camelCase emit at cli-process matches camelCase reads in the handler, verified end-to-end through hook-event-tail normalization).

**Evidence:**
callbacks.js:690 onSubagentStart persists `tool_use_id: payload?.toolUseId`. callbacks.js:699-705 onSubagentDone persists agent_type/agent_id/duration_ms, no tool_use_id. cli-process.js:1545-1550 `emit('subagent-done', { agentType, agentId, durationMs, backend })` — no toolUseId. hook-event-tail.js:38 header: '`parent_tool_use_id` is NOT a field'. Comment callbacks.js:678-682 documents JOIN ON $.tool_use_id.

**Suggested fix:**
Correlate on agent_id instead of tool_use_id (the field both sides can actually share once subagent-start learns the agent_id), OR have cli-process track the in-flight Agent tool_use_id and stamp it onto the SubagentStop-derived subagent-done. Then add tool_use_id (or agent_id) to onSubagentDone and fix the documented query. Add an integration test that feeds a real Agent PreToolUse + matching SubagentStop ndjson pair through the tail→cli-process→callbacks chain and asserts the two persisted rows are joinable; the current unit test (tests/sdk-callbacks.test.js) calls the handlers directly with hand-built payloads and so cannot catch this missing-key drift.

## #5 — [LOW] stop-hook listener leaks on kill / bridge-disconnect / reset when a turn is in stop-grace

- **Unit:** cli-process-core · **Category:** resource-leak · **Verifier vote:** 3/3 confirmed real
- **Location:** `lib/process/cli-process.js:1142 (registration), removed only at 1120 (finalize); not removed in _doKill 1685-1695, bridge-disconnected 422-433, resetSession drain`

**What & why:**
The per-turn onStop listener (this.on('stop-hook', onStop) at 1142) is only removed inside finalize() via this.off('stop-hook', onStop). All three teardown paths (_doKill, the bridge-disconnected handler, resetSession) clear pending._stopGraceTimer and reject the pending, but none has access to the onStop closure and so none calls this.off('stop-hook', ...). A turn torn down mid-grace leaves its onStop subscribed. Bounded impact: these paths set closed=true and discard the instance (GC reclaims), and a stray Stop after rejection calls finalize()->_finalizeTurn which no-ops on the deleted turn. Flagged for the unit's listener-leak dimension and because it compounds with the maxListeners issue below.

**Evidence:**
_doKill drain: `for (const [, pending] of this.pendingTurns) { ... if (pending._stopGraceTimer) clearTimeout(pending._stopGraceTimer); ... pending.reject(err); }` with no off('stop-hook'). bridge-disconnected and resetSession drains are structurally identical (timer clears + reject, no listener removal).

**Suggested fix:**
Store the closure on the pending (pending._onStop = onStop) at registration and, in every drain path, do `if (pending._onStop) this.off('stop-hook', pending._onStop);` alongside the timer clears; or call this.removeAllListeners('stop-hook') once in each teardown. Best: a single persistent turn-correlated stop-hook handler (also fixes the turn-scoping bug).

## #6 — [LOW] bridge-disconnected drain does not clear _interruptGraceTimer (inconsistent with _doKill)

- **Unit:** cli-process-core · **Category:** reliability · **Verifier vote:** 3/3 confirmed real
- **Location:** `lib/process/cli-process.js:419-440 (bridge-disconnected handler)`

**What & why:**
The bridge-disconnected handler clears each pending's quiet/hard/absolute/_stopGrace timers and rejects+clears pendingTurns, but does NOT clear this._interruptGraceTimer. If a bridge disconnect lands within interruptGraceMs after interrupt() (operator /stop then bridge dies), the interrupt grace timer survives. When it fires it iterates the now-empty pendingTurns map (resolvedAny stays false) so it is effectively a harmless no-op, but it is a stray timer that should be torn down with the rest of the lifecycle and briefly keeps a closure on the dead instance alive. _doKill DOES clear it (1680-1683); the disconnect path is the inconsistency.

**Evidence:**
bridge-disconnected handler clears pending.quietTimer/hardTimer/absoluteTimer/_stopGraceTimer then `this.pendingTurns.clear(); this.pendingQueue.length = 0; this.inFlight = false;` with no _interruptGraceTimer clear. _doKill: `if (this._interruptGraceTimer) { clearTimeout(this._interruptGraceTimer); this._interruptGraceTimer = null; }`.

**Suggested fix:**
In the bridge-disconnected handler, clear and null this._interruptGraceTimer alongside the per-pending timer clears, matching _doKill.

## #7 — [LOW] Dead pollScheduler param: factory destructures it but never uses it, while polygram.js still constructs a PollScheduler and passes it in

- **Unit:** factory-pm · **Category:** maintainability · **Verifier vote:** 2/3 confirmed real
- **Location:** `lib/process/factory.js:116 (destructure), 94-97 (docstring); polygram.js ~2259, ~2285`

**What & why:**
The 0.12 factory deleted the only consumer of pollScheduler (the pm:'tmux' branch that did `new TmuxProcess({... pollScheduler})`). The param is still destructured at lib/process/factory.js:116 (`pollScheduler = null,`) and documented as DEPRECATED/ignored, but the caller (polygram.js) still does `const pollScheduler = new PollScheduler({ intervalMs: tmuxPollIntervalMs })` and passes it to createProcessFactory. That allocates a live PollScheduler (potentially a setInterval-backed timer object) on every boot that nothing will ever consume. Not a crash, but a small permanent resource/clarity leak that should be removed alongside the tmux backend.

**Evidence:**
factory.js: `function createProcessFactory({ ... pollScheduler = null, ... })` with JSDoc `@param {object} [opts.pollScheduler] — DEPRECATED in 0.12 ... Param kept for caller back-compat; ignored.` — `pollScheduler` appears nowhere else in factory.js after the destructure. Grep of polygram.js shows `2259: const pollScheduler = new PollScheduler({ intervalMs: tmuxPollIntervalMs });` and `2285: pollScheduler,` passed into createProcessFactory.

**Suggested fix:**
Drop the `pollScheduler` construction + pass in polygram.js and remove the param from createProcessFactory now (it is already ignored), rather than waiting for 0.13. If PollScheduler/tmuxPollIntervalMs have no other consumer post-tmux-deletion, delete them too.

## #8 — [LOW] LogTail decodes each 64KB read chunk with toString('utf8') independently — multibyte chars split on the chunk boundary corrupt the hook JSON line

- **Unit:** hook-infra · **Category:** correctness · **Verifier vote:** 3/3 confirmed real · **Severity adjusted during verification:** medium → low
- **Location:** `lib/tmux/log-tail.js:263`

**What & why:**
_readNew() reads the tailed file in DEFAULT_CHUNK_BYTES (64KB) chunks and does `this._buf += buffer.slice(0, bytesRead).toString('utf8');` per chunk (line 263), with no StringDecoder and no carry-over of an incomplete trailing multibyte sequence between reads. If a UTF-8 multibyte sequence (emoji, accented path, CJK) straddles a 64KB read boundary, each half decodes to U+FFFD replacement characters, corrupting that region of the line. The hook ndjson routinely carries large tool_input/tool_response payloads (file write contents, command output) that can exceed 64KB and contain non-ASCII; polygram-hook-append.js does NOT cap the successful-payload size (its 64KB cap at line 56 only applies to the raw body of a parse-error record). A corrupted line then fails JSON.parse in pipeHookParser (hook-event-tail.js:106-114) and is surfaced as a parse-error event — silently degrading observability for precisely the largest/most-interesting events. Latent LogTail bug predating 0.12.0, but 0.12 promotes the hook stream from observe-only to load-bearing CliProcess IO and routes >64KB tool payloads through it, making it realistically reachable.

**Evidence:**
log-tail.js:255-264: `const buffer = Buffer.alloc(Math.min(bytesToRead, DEFAULT_CHUNK_BYTES));` then loop `this._buf += buffer.slice(0, bytesRead).toString('utf8');`. DEFAULT_CHUNK_BYTES = 64*1024. `grep -n StringDecoder lib/tmux/log-tail.js` => none. Success-path payload uncapped: polygram-hook-append.js:48-50 `const obj = JSON.parse(buf); ... line = JSON.stringify(obj);`.

**Suggested fix:**
Hold a `require('string_decoder').StringDecoder('utf8')` instance on the LogTail and replace the per-chunk `.toString('utf8')` with `decoder.write(buffer.slice(0, bytesRead))`; StringDecoder buffers an incomplete trailing sequence until the continuation bytes arrive in the next read. Flush via `decoder.end()` in close().

## #9 — [LOW] Plan's 'PreToolUse Agent→SUBAGENT' reaction state is unimplemented: cli-process emits subagent-start, but no SUBAGENT state exists and onSubagentStart never calls setState

- **Unit:** callbacks-reactions · **Category:** spec-divergence · **Verifier vote:** 3/3 confirmed real · **Severity adjusted during verification:** high → low

**What & why:**
The task/plan mapping says 'PreToolUse Agent→SUBAGENT'. **Evidence:**

**Suggested fix:**
Add a SUBAGENT state to reactions.js STATES (with a Telegram-default-available emoji + safe fallback chain), and in onSubagentStart resolve the head pending's reactor and call `reactor.setState('SUBAGENT')` (mirroring onToolUse's `entry.pendingQueue?.[0]?.context?.reactor`). onSubagentStart currently has the signature `(sessionKey, payload)` and does not receive `entry`, so the ProcessManager bridge must pass entry through (as it does for onToolUse/onHookEvent). Alternatively, if no distinct state is wanted, drop 'PreToolUse Agent→SUBAGENT' from the plan and remove the misleading cli-process.js:1510 comment — but then also emit 'tool-use' for Agent so the reactor at least shows a generic tool state during subagent runs.

## #10 — [LOW] hook-lag-sample is double-persisted on the CLI driver (cli-process logs it directly AND re-emits to onHookLagSample), inflating the soak-gate metric

- **Unit:** callbacks-reactions · **Category:** correctness · **Verifier vote:** 2/3 confirmed real
- **Location:** `lib/process/cli-process.js:1466-1487 (paired with callbacks.js onHookLagSample 632-645)`

**What & why:**
cli-process._handleHookEvent writes the hook-lag-sample to the events DB TWICE per hook event when both a db handle and the callback are wired. First directly: cli-process.js:1476-1486 `if (this.db?.logEvent) this.db.logEvent('hook-lag-sample', {...})`. Second via the event bridge: cli-process.js:1468 `this.emit('hook-lag-sample', {...})` → process-manager CALLBACK_TO_EVENT maps onHookLagSample→'hook-lag-sample' (process-manager.js:135) → callbacks.js onHookLagSample:632-645 calls logEvent('hook-lag-sample', ...) again. Since the Phase 1.8 soak GATE is defined on this exact metric (median<2s, p99<5s, computed by AVG/MAX over rows where kind='hook-lag-sample'), duplicate rows don't change median/p99 of the value itself but double the row COUNT and any count-based or percentile-by-rank computation, and the two rows carry slightly different shapes (the direct write omits tool_name when ev.toolName is null vs the callback's hook_event_name/lag_ms naming is identical, but chat_id is present only on the callback path). This is a real telemetry-integrity defect for the gate that decides 0.12 tag-out. Whether db is wired on Process directly depends on factory injection (comment at cli-process.js:1474 'db is optional'), so in production where both are present, every sample is counted twice.

**Evidence:**
cli-process.js:1468 `this.emit('hook-lag-sample', {...})` and cli-process.js:1478 `this.db.logEvent('hook-lag-sample', {...})` in the same `if (Number.isFinite(ev.receivedAtMs))` block. process-manager.js:135 `onHookLagSample: 'hook-lag-sample'`. callbacks.js:634 `logEvent('hook-lag-sample', {...})`.

**Suggested fix:**
Pick one persist path. Either drop the direct `this.db.logEvent('hook-lag-sample')` in cli-process (let the callback own DB writes, consistent with how subagent-start/tool-result/subagent-done are handled — they only emit, they do not double-write), or stop wiring onHookLagSample to logEvent and rely on the direct write. Add a test asserting exactly one hook-lag-sample row per hook event when both db and callback are present.

- **Unit:** supporting · **Category:** test-gap · **Verifier vote:** 2/3 confirmed real
- **Location:** `polygram.js:diff hunk @@ -2321,19 +2287,31 (onApprovalRequired, sdkCallbacks)`
