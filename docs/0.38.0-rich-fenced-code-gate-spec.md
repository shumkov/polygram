# Rich gate: fenced code blocks

Status: **draft — design agreed, not implemented**
Reviewed by four independent agents (feasibility, scope, testing, adversarial);
their must-fixes are folded in below.

## Problem

A reply that is structurally nothing but a wide fenced code block renders
plain today, and plain means Telegram `<pre>`, which wraps at ~36 monospace
chars on iPhone portrait (the budget measured in `lib/telegram/display-hint.js`).
Anything wider comes apart on the reader's screen.

Production case — chat `-1003369922517` ("Shumabit@UMI"), thread 4572,
turn `9b3ef91f`, both messages from the same agent turn via the `reply` tool:

| msg | content shape | gate | `rich-message-sent` |
|---|---|---|---|
| 5866 | prose + `**bold**` + hand-aligned table in a ``` fence | `false` | none |
| 5867 | `##` heading + real `\|` table | `true` | yes, `transport: send` |

Message 5866's fenced rows are 47–59 chars wide against a ~36-char wrap.

The gate declining is **proven, not inferred**: the stored text of 5866 was run
through `needsRichRendering` against a `rich.js` whose md5 is identical to the
installed copy on the VPS, and it returns `false`. That matters because a
renderer *throw* would look the same in telemetry — `rich-dispatch.js:222` and
`streamer.js:453` log to console and emit no event — so "no `rich-message-sent`"
alone would not have distinguished the two. It does now.

`stripFencedCodeBlocks` (`lib/telegram/rich.js:76-110`) blanks fenced content
before `needsRichRendering` reads it, and bold is not a trigger, so nothing
remained to trip it.

That specific message was an agent-authoring mistake, addressed separately by
the display-hint bullet shipped alongside this doc. The gap this spec covers is
different: **content that legitimately belongs in a fence** — a diff, a stack
trace, a SQL query, a `systemctl status` dump — has no "use the real construct
instead" escape hatch. It is code. It goes in a fence. Every such reply that is
otherwise unstructured renders through a `<pre>` that mangles it on a phone.

### Ruled out: the stale-hint hypothesis

Worth recording, because it would have inverted the fix. The display hint is
spawn-time state (`polygram.js:904-917`), so a session spawned before `richText`
was enabled would run the *plain* hint — whose HARD RULE forbids any table with
rows over 40 chars and sends the agent to row blocks. Under that hint, reaching
for a fence is compliance, not a mistake, and a bullet added only to
`richSection` would never reach it.

Refuted by production: thread 4572 has **61** `rich-message-sent` events, and
msgs 5835, 5837, 5841, 5846 and 5852 — all in that same thread, all rich —
landed in the hour immediately before 5866. The session was demonstrably
running the rich hint.

## Does a rich `pre` render better than a plain `<pre>`?

This was originally scoped as a blocking probe. It does not need one: the
answer is already in production. `LIST_ITEM_RE` (`rich.js:60`) trips on any
bullet or numbered item, so every bulleted reply containing a fence has been
shipping rich `pre` blocks all along. The five messages named above are exactly
that shape — fence + list, rendered rich — **in the thread this bug came from**.

Read one of them on a phone and compare against a plain fenced reply in the
same thread. Decision rule is unchanged:

- Rich `pre` does not wrap (or scrolls) → implement the design below.
- Rich `pre` wraps the same way → **abandon**; record it here and close out.
  The display-hint fix stands on its own either way.

`blockFromToken` emits `{ type: 'pre', text }` for a `code` token
(`rich.js:632-633`), reachable today only when another construct trips the
gate. For a forced comparison, `_blocksFromTokens` is exported (`rich.js:1316`),
so a probe can hand-build `[{type:'pre',text}]` without touching lib code.

## Proposed design

Add a fourth trigger class to `needsRichRendering`: a fenced block whose
content is too wide for the plain `<pre>`.

The scan already exists. `stripFencedCodeBlocks` walks lines tracking fence
state; extend it to also return the width tally rather than adding a second
scanner that can drift from the first:

```
scanFences(markdown) -> { scoped, wideFencedLines }
```

**Trigger: `wideFencedLines >= 2`.** One condition, not two. An earlier draft
also required `maxFencedWidth > 40`; that term is dead — `wideFencedLines`
counts lines exceeding the threshold, so a count of ≥2 already implies it.
Keep `maxFencedWidth` as telemetry if useful, never as a deciding term.

Why the count of two: one wide line is a URL, a `curl` invocation, a file path
— it wraps to a second line and stays readable, and flipping the whole reply
into document typography for that is the false positive the gate exists to
prevent. Two or more is aligned or columnar content — a table, a stack trace,
a log excerpt — where wrapping destroys the line-to-line relationship that
carries the meaning.

**The tally is a maximum across fence blocks, never a per-block counter that
resets.** This is a correctness requirement, not a preference. Under a naive
per-block reset, a stream that has drawn a qualifying open fence (tally 2 →
rich) drops back to `false` the moment the closing fence arrives, and the
streamer's plain branch (`streamer.js:600-623`) edits the bubble *back* to
plain text — a visible rich→plain revert that nothing refuses. Carrying a
sticky qualified flag keeps the trigger monotone under append-only growth,
which is what makes it safe to stream (simulation over streaming prefixes:
one `false→true` flip, zero downgrades).

Two blocks each contributing one wide line must NOT qualify — two unrelated
single-line fences are the false-positive case above. So the sticky flag is set
by a block reaching 2 *on its own*, and once set it stays set.

**Threshold constant.** Do not reuse `TELEGRAM_TABLE_WIDTH_BUDGET`. It is the
same number (40) but a different concept — it is the *plain-mode prompt's*
authoring budget, and `display-hint.js:85` explicitly tells rich chats no width
budget applies to their tables. Reusing it means a future copy tweak silently
moves the gate. Define a separate constant with its own rationale.

Measure in code points (`[...line].length`): the production case is Cyrillic
and Thai, and these blocks routinely carry emoji.

Two contract details the scan must settle explicitly:

- The fast path (`rich.js:77`, returns early when there is no backtick and no
  tilde) must return the new shape too, or the tally reads `undefined`.
- Fence *marker* lines never reach the content branch. A long info-string on
  the opening marker is therefore unmeasurable unless marker lines are counted.
  Decision: **do not count marker lines** — an info string is not content.

**Threshold margin is zero, by measurement.** Run over the nine existing fenced
gate tests (`tests/rich.test.js:147-219`), a threshold of 2 flips none of them.
Three sit at exactly *one* wide fenced line (`:185` max 87, `:197` max 46,
`:211` max 49) — at a threshold of 1 all three flip and the suite goes red.
That is the empirical floor; 2 is not an arbitrary round number.

### Second consumer: media demotion

`hasNonMediaTrigger` has two callers — `needsRichRendering` and the media-drop
demotion at `rich.js:1167`. Adding the wide-fence trigger to only the first
leaves "wide fence + an image that failed to resolve" demoting to plain while
the identical reply without media goes rich. Decide deliberately and state it;
do not let the two drift.

### Call sites

`stripFencedCodeBlocks` has three references: `rich.js:128`, `rich.js:1167`,
and the `_stripFencedCodeBlocks` export at `rich.js:1317`, which is referenced
nowhere in the repo. Changing the return shape means updating the two internal
callers and either keeping `_stripFencedCodeBlocks` as a thin string-returning
wrapper or dropping it. No existing test breaks.

## Alternatives rejected

**Any fence triggers rich.** Agent output is dense with fences — every command
echo, every JSON snippet — and most would exceed 40 chars on some line, so this
flips the majority of technical replies into document typography. This is the
hermes-agent #45762 failure the content-adaptive gate was ported to prevent
(`docs/0.18.0-rich-messages-plan.md:329`).

**Raise the plain-mode `<pre>` budget / reformat wide fences on the plain
path.** Rewriting the inside of a code fence is the one thing a code fence
promises not to do. Non-starter.

**Do the display-hint fix only, skip the gate.** Covers the authoring mistake,
not legitimate code. A stack trace still breaks on a phone with no construct to
switch to.

**Do the gate only, skip the display-hint fix.** Correct to reject, but an
earlier draft gave the wrong reason — it argued the gate change would "entrench"
the fake table in the agent. It cannot: the agent gets no rendering feedback and
never learns the fence "worked", so nothing about the gate reaches its authoring
decision. The real reason is simply that the two address different populations —
self-authored fake tables versus legitimately-fenced content — and neither
population is covered by the other's fix.

**Delivery-time detection instead of a prompt bullet.** Not rejected — deferred,
and worth taking seriously. `scanFences` produces exactly the measurement needed
to *detect* a hand-aligned pseudo-table at send time (≥2 wide fenced lines with
consistent internal column separators), which is strictly more reliable than
guidance. This repo has run the prompt-versus-code experiment before and lost:
an explicit HARD RULE was added to the display hint forbidding CLI canned
strings, the outcome was recorded as "partial — hint reached the live TUI but
the canned string fired again" (`docs/0.10.0-tmux-status.md:51`), and
`lib/telegram/sanitize-reply.js` is the code fix that followed. The honest
expectation for the fence bullet is **rate reduction, not elimination**. If it
recurs, the sanitize-reply-shaped fix is the next step, and this design already
builds its detector.

## Failure modes

| Mode | Consequence | Mitigation |
|---|---|---|
| Partial-render hold-back | **The real streaming problem.** `opts.partial` holds back the last top-level block (`rich.js:1162-1164`), so for a prose-then-fence reply the gate flips rich when the 2nd wide line arrives while the pre block is the one NOT drawn — the reader gets document typography around prose only, exactly the oversized-prose failure. Verified: `toTelegramRichBlocks('# H\n\nprose\n\n```\n<wide>\n<wide>', {partial:true})` → `[heading, paragraph]`, no pre. | Fix in `resolveRichPayload`/the gate. A fence-only reply is safe — one block is never sliced |
| Mid-stream downgrade | rich→plain revert visible to the reader | sticky max-across-blocks tally (above); nothing else refuses a downgrade |
| Typography flip rate | every streamed reply with a wide code paste now flips mid-stream, and code pastes are common | accepted transition (`rich-streaming-upgrade`), but measure rate in the corpus check |
| False positive on wide log/JSON | ordinary reply gets document typography | two-line condition; corpus check before merge |
| `edit_message` cap change | a fence-only body starts passing `hasStructuralBlock` (`rich-edit-dispatch.js:50`, `pre` is non-paragraph), moving the cap from 4096 plain to 32768 rich | intended, but note it — it is a behavior change beyond rendering |
| Unclosed fence at end of reply | trailing content read as fenced | existing scan already treats it as open to EOF; unchanged |

Note: `partialVisibleExtent` (`rich.js:1196`) is **not** involved in any of
this. It computes how much source a partial render put on screen and feeds only
the append-only guard at `streamer.js:324-335`; it never touches the gate. The
per-flush decision is `resolveRichPayload` (`streamer.js:437-457`).

## Verification plan

1. Read the existing production evidence (thread 4572, msgs 5835/5837/5841/
   5846/5852) on a phone; apply the decision rule above.
2. Unit: msg 5866's text → `true`; a one-long-line fence → `false`; a narrow
   fence → `false`; two separate fences with one wide line each → `false`;
   an unclosed fence → deterministic; ReDoS guard extended (measured: linear,
   worst case 8ms, far under the suite's 500ms guard at `rich.test.js:221-236`).
3. Streaming: assert monotonicity over every prefix of a prose+wide-fence reply
   — exactly one `false→true` flip, zero downgrades, including across the
   closing fence.
4. Regression: msg 5867 still `true`; the nine existing fenced gate tests
   unchanged.
5. Corpus: run the new gate over recent outbound messages in `shumabit.db` and
   report the plain→rich flip fraction. If it is not a small minority, the
   threshold is wrong.
6. Real-Claude E2E in a `richText: true` chat, screenshot on iPhone portrait.

## Open questions

1. Does the plain-mode hint need the same anti-fence-table rule? Its width HARD
   RULE fires only on markdown tables, so a fenced hand-aligned table evades it
   there too — with no rich table to switch to, the answer is row blocks.
   Deliberately out of scope until asked.
2. `pre` with a `language` field for syntax highlighting — separate change.
3. No test anywhere pins the current fenced-only → plain behavior, so if this
   ends in "abandon" that decision lives only in this doc. Worth a
   characterization test either way.
