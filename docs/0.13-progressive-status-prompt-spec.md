# 0.13 — Restore progressive status on CLI (strengthen the "stay responsive" contract)

> **Status: design / focused review then ship.** #9. Direction chosen by Ivan: prompt
> strengthening (not a mechanism build). **Severity:** UX — long CLI turns go silent
> (only reply at turn end), so the user thinks the bot is unresponsive; also exacerbates
> the #8 wedge-timeouts (a silent turn gives polygram no reply-activity signal).

## Root cause (established, not a code regression)
The `edit_message` tool + the "Staying responsive on a long task" prompt block both
shipped in `a6e14db` and are **still present and intact** (cli-process.js ~766-778,
channels-bridge.mjs edit_message tool). `edit_message` still fires (1-6/day) — mechanism
works when called. **The SDK backend auto-streams** intermediate assistant text
(`sdk-process.js` streamText/partial_assistant/forceNewMessage); **the CLI/channels
backend delivers only explicit `reply`/`edit_message` tool calls** (HARD CONTRACT: inline
text never reaches the user). So CLI progress depends entirely on Claude *choosing* to
call reply/edit mid-turn — and it largely stopped (behavior/compliance drift, likely with
the `claude` 2.1.158→2.1.173 pin, `b83bc0e`). Same class as #7's `consumed_turn_ids` miss.

## Fix — strengthen the prompt block (compliance), calibrated against over-trigger
Current (cli-process.js 766-778) says "for any task more than a few seconds, send a SHORT
status first." Too soft / ignorable. Strengthen to:
- **Sharper consequence:** the user sees SILENCE and the turn can hit the time-cap.
- **Concrete, hard-to-ignore trigger:** more than one quick step / research / multi-tool /
  >~10-15s → your FIRST action is a one-line status `reply`.
- **Explicit over-trigger guard** (the key risk): a quick answer you can give immediately
  needs just ONE reply — NO status. The rule is for work that takes time, not quick answers.
- Keep the PLAIN-language + "long final answer = fresh reply, not an edit" guidance.

### Proposed wording (replaces lines 766-778)
```
'### Staying responsive on a long task — send progress, never go silent',
'',
'The user sees NOTHING while you work — no inline text, no typing, no tool output',
'reaches them. A turn that runs a long time with zero replies looks BROKEN to the',
'user (they just see silence) and can hit the turn time-cap before you answer.',
'',
'So the moment a request needs more than one quick step — any research, any',
'multi-tool work, anything that will take more than ~10-15 seconds — your FIRST',
'action is a SHORT one-line status `reply` (it returns a `message_id`). Then call',
'`mcp__polygram-bridge__edit_message` with that `message_id` to update the SAME',
'bubble as you progress, ending with the result. One evolving bubble beats silence',
'or a flood of new messages.',
'',
'(A question you can answer right away needs just ONE `reply` — no status bubble.',
'This rule is for work that takes time, not for quick answers — do not spam status',
'on trivial requests.)',
'',
'Write status in PLAIN, friendly language about what you are doing FOR THE USER —',
'never tool names or mechanics. Say "Checking your config now…", not "Running Bash".',
'If the final answer is long, send it as a fresh `reply` rather than an edit (an edit',
'is one single bubble).',
```

## Risks (for review)
- **Over-trigger** (the main risk): Claude sends a status bubble on quick/trivial requests
  → clutter, double-bubbles. Mitigated by the explicit guard; review to stress it.
- **Coherence:** must not conflict with the reply HARD CONTRACT, the `consumed_turn_ids`
  contract (#7), or the `ask` rule. Adds ~6 lines to an already-long system prompt — worth it?
- **Effectiveness:** prompt compliance is probabilistic. If 2.1.173 is the cause, a prompt
  tweak may only partially restore it (the version-investigate option remains the fallback).

## Test plan
- `tests/cli-process.test.js` rc.7 spawn-args test: assert the strengthened wording is
  present in the assembled `--append-system-prompt` (presence check; red→green on the new
  phrasing). Same pattern as the 0.12.2 consumed_turn_ids tighten.
- Effect measured in prod (not unit-testable): edit_message + early-reply rate.

## Measure (soak)
Baseline: edit_message ~1-6/day; "early status reply" (a reply before the turn's first
tool batch) currently rare. After ship: track edit_message/day + the share of multi-tool
turns that send an early status. Target: noticeable rise. Bonus: #8 wedge-timeouts should
drop (progress replies keep the ceiling alive).
