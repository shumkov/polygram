# 0.12.0 — Background-work lifecycle (turn ends, work continues)

**Status:** PLAN · not started · grew out of the shumorobot Music `listen-sync
download` incident (2026-06-03). **Revised 2026-06-04** after a 5-persona
ce-doc-review — see "Review applied" at the bottom for what changed and why.

## Problem

An agent can finish a *turn* but leave *work* running:

- The Music curator backgrounded a `run_in_background:true` Bash
  (`music_curation … listen-sync download`, ~20-40 min estimate). It replied
  *"Starting download — will report back,"* the dispatch **turn resolved**, and
  the shell kept churning detached.
- That download then **hung** on a frozen SoundCloud-automation Chrome — ran
  **~7 hours** at 0% CPU, never completed, never woke up to report. Nothing
  detected it. The user discovered it only by asking *"music is working?"* and
  seeing no reaction/typing.

The headline failure is **no stall detection** — a backgrounded job that hangs is
invisible: no watchdog, no "still running / looks stuck" signal. A second,
**latent** failure (eviction killing a background job) is real only at scale and
is explicitly deferred below — it cannot occur on shumorobot today (≤3 cli
sessions, cost 9 < budget 10, no idle reaper).

## Current mechanisms (verified against the code)

| Mechanism | Where | What it actually does | Relevance |
|---|---|---|---|
| `probeBusyState()` / `isBusy()` | cli-process.js:1532 | Reads the TUI **`esc to interrupt`** hint (`STREAMING_HINT_RE`, :114) → claude is **streaming a turn** even after `inFlight=false` | Detects *streaming*, NOT a **detached background shell** while claude is idle — the download state |
| `fireUserMessage(text)` | cli-process.js:2175 | Writes a fresh `user_msg` with a new `turn_id`; **no `inFlight` gate** (only `closed`/`bridgeReady`) | **The idle-safe re-invoke primitive the watchdog must use** |
| `injectUserMessage(opts)` | cli-process.js:2115 | Mid-turn autosteer fold — **hard-returns `false` when `!inFlight`** (:2117) | ❌ NOT usable by the watchdog: the watchdog fires *after* the turn resolved (`inFlight=false`), where this is a guaranteed no-op |
| `pongWatchdog` timer | `PONG_CHECK_INTERVAL_MS = 5_000` (:81) | 5s tick, gated only on `bridgeReady` (idle-eligible) | The timer the probe/watchdog rides. (`PING_INTERVAL_MS` is **10s**, :79 — a different thing) |
| `_pollMidTurnDialogs` | cli-process.js | The existing pane-poll, **early-returns on `pendingTurns.size === 0`** | ❌ Cannot be reused for idle detection — it deliberately does NOT scan when idle |
| Autonomous-wakeup | sdk/callbacks.js `onAutonomousAssistantMessage` | **Outbound-only**: forwards an assistant message the agent already produced OUT to Telegram | NOT a polygram-side re-invoke route. Re-invocation is entirely claude-side (ScheduleWakeup *inside* claude), and a *hung* job never schedules one |
| `_evictLRU` | process-manager.js:267 | Synchronous, called under budget pressure (:236); skips `inFlight` | Doesn't know about background work (the latent eviction gap) |

The old tmux `hasBackgroundShell()` (read the TUI `N shell` indicator) was
**deleted** in the 0.12 refactor; `probeBusyState` is the "channels analog" but
covers only the streaming case.

## Core gap

polygram cannot answer *"does this idle session still have live background
work?"* — `probeBusyState` only sees claude *streaming a turn*. Every fix needs
that answer, so the **detection primitive is the crux**, and it is genuinely
uncertain (see P0).

## Detection primitive — a real decision, not an assumption (P0)

Two candidate mechanisms. **P0 is a hard go/no-go that picks one empirically —
the rest of the plan is conditional on its outcome.**

- **Mechanism B — agent declares its job (preferred robust path).** The agent
  emits a structured signal over the channels bridge when it backgrounds a job
  ("backgrounding X, ETA Y") and when it completes. polygram tracks an explicit
  per-session "open background job" set — no pane inference, no per-claude-version
  fragility, and it directly distinguishes *running* / *done* / (with a heartbeat)
  *hung*. Cost: an agent/protocol convention (a small system-prompt instruction +
  a bridge message type).
- **Mechanism A — pane-scrape (fallback only).** Extend `probeBusyState` into
  `hasLiveBackgroundWork()` returning
  `{ streaming, backgroundShell, busy: streaming||backgroundShell, inFlight,
  pendingTurns, captured, paneTail }`, where `backgroundShell` matches a
  `BACKGROUND_SHELL_RE` against the **live viewport region only** (NOT the
  ~1000-line `captureWide` scrollback — a stale indicator scrolled into history
  would match forever → permanent false-positive). This reintroduces the
  pane-scraping the 0.12 refactor deliberately dropped, and R1 (version drift) is
  its standing tax.

**P0 decides:** capture a real pane while a `run_in_background` Bash is live AND
again after it completes, on the pinned claude. Mechanism A is viable **only if**
a stable, always-present indicator exists in the captured viewport AND is
removed/decremented in-place on completion. If either fails, **Mechanism B is the
path** — do not ship pane-inference as disposable scaffolding. Default lean: B,
because it sidesteps R1 entirely and is the only one that cleanly tells *hung*
from *done*.

## v1 scope — detection primitive + stall-watchdog only

This is the whole incident fix. Everything else is deferred (below).

### Stall-watchdog (the failure that actually bit)

A new **idle-eligible** branch on the `pongWatchdog` 5s tick (NOT
`_pollMidTurnDialogs`, which skips idle sessions). If a session has had live
background work for **> STALL_MIN** with no new turn and no completion signal:

1. **First escalation — agent self-check via `fireUserMessage`** (NOT
   `injectUserMessage` — that no-ops when idle): *"Your background job has run N
   min with no update. **Report its status only — do not start new work or
   re-run the job.**"* The read-only framing matters: the agent runs
   `bypassPermissions`, so an open-ended "fix it" could spawn another hung shell
   unattended (R3). One self-check per stall window, with backoff.
2. **Second window — user-notify.** If still live, a calm, actionable line:
   *"⏳ A background job has run Nh and may be stuck — reply /stop to end it."*
   Never silent.

This must be validated against a **hung** job (0% CPU, shell still present), not
a healthy-running proxy — that is the actual incident state, and the P0 capture
must include it.

`STALL_MIN` is a module constant in v1 (first self-check ~5 min past a declared
ETA or an absolute default; user-notify ~15 min). Promote to config only when a
second consumer needs different timing.

## Deferred — each gated on a concrete trigger (NOT v1)

- **Eviction-pin** — skip a session with live background work in `_evictLRU`.
  **Trigger to build:** a real multi-session deployment under budget pressure
  exists (cannot occur on shumorobot). When built, it must also handle the
  **cold-start race**: `_evictLRU` runs synchronously on demand (:236), decoupled
  from the 5s tick, so a just-started shell has no cached flag until the next tick
  (~5s) and a competing `getOrSpawn` can evict it — set the flag eagerly on first
  observation + a one-interval grace window after a turn resolves.
- **Visibility ("⏳ working in background")** — deferred: the reactor is
  *per-turn* (`createReactionManager`, single inbound message) and has no
  cross-turn host on an idle session. Needs a standalone per-session status
  message, not a reaction — a real design unit, not a "nice-to-have" toggle.
- **Restart handling** — out of scope (it's a non-goal): background shells die
  with the tmux pane on restart and the agent context is gone, so jobs can't
  resume. A boot-time "you had a background job — re-run it" notice is **not** v1
  either, because the marker can't distinguish *interrupted* from *finished just
  before the restart* (a hung job never signals completion to clear it). If ever
  built, the notice must be a question, not an imperative. For now: the
  operators-avoid-restart note in known-issues stands.

## Phased build

| Phase | Deliverable | Gate |
|---|---|---|
| **P0** | Decide the detection mechanism: capture a live AND a post-completion pane on pinned claude; confirm whether a stable, in-place-updated indicator exists | **Go/no-go.** Stable in-place indicator → Mechanism A allowed. Otherwise → Mechanism B is the path. Output: the decision + (if A) `BACKGROUND_SHELL_RE` anchored to the viewport + a fixture test that matches the live indicator, not the streaming hint, and not a stale scrollback line |
| **P1** | The chosen detection primitive (`hasLiveBackgroundWork()` for A, or the declared-job tracking for B), refreshed on a **new idle-eligible `pongWatchdog` branch** | unit test: detects live bg work when `inFlight=false`; clears on completion; 4 states (streaming-only / bg-only / both / neither) |
| **P2** | Stall-watchdog: `fireUserMessage` read-only self-check → user-notify | test: > STALL_MIN with bg work and no new turn → exactly one `fireUserMessage` fires (asserts it writes to the bridge while `inFlight=false`); self-check text forbids new work; second window → user notify; all clear when work ends |

Ship P0→P2. Eviction-pin / visibility / restart are deferred per their triggers.

## Risk register

- **R1 — pane-scrape drift (Mechanism A only):** the indicator string changes
  across claude versions → bg work undetected. Mitigation: Mechanism B avoids it
  entirely (the reason B is preferred); if A is chosen, re-validate
  `BACKGROUND_SHELL_RE` on every pinned-claude bump (version-migration checklist,
  next to the e2e), and structured-log the probe signals to audit false ±.
- **R2 — false-positive "busy forever":** a stuck probe never clears → watchdog
  spams / (if eviction-pin ever ships) pins a dead session. Mitigation: the
  user-notify window doubles as a release — after it fires with no progress, stop
  trusting the probe for that session and offer /stop. Mechanism B's explicit
  completion signal makes this far less likely than A's inference.
- **R3 — self-check causes harm under `bypassPermissions`:** an open-ended
  re-invoke could spawn another hung shell. Mitigation: read-only self-check
  prompt (forbid new work), one per window, backoff; test asserts the prompt
  text.
- **R4 — detecting the wrong thing:** the watchdog must distinguish *hung* from
  *done*. Mechanism B gives an explicit done-signal; Mechanism A must verify
  (P0) the indicator clears in-place on completion or it'll false-alarm for up to
  the user-notify window after every finished job.

## Test plan

- Unit: detection primitive (4 states, idle-eligible), the watchdog timing +
  both escalations (assert `fireUserMessage` fires while `inFlight=false`, assert
  the read-only prompt), all clears. Deterministic with the existing
  cli-process / process-manager fakes.
- E2E (gated, real claude): spawn a real `run_in_background` job, resolve the
  turn, assert detection is true while it runs AND the watchdog `fireUserMessage`
  reaches the bridge — extends `tests/e2e-channels-real-claude.test.js`. Include a
  *hung* job variant (a `sleep` that never reports) since that is the incident.

## Open questions

1. **(P0, blocking)** Does pinned claude render a stable, always-present
   background-shell indicator in the captured **viewport**, removed in-place on
   completion? If not, Mechanism B it is. This is the first thing to settle.
2. Mechanism B's protocol shape: what's the minimal "backgrounding X / done X"
   convention (system-prompt line + bridge message type), and does it want a
   heartbeat so a hung job is detectable without the pane at all?
3. `STALL_MIN` defaults — start conservative (self-check ~5 min past ETA,
   user-notify ~15 min); too tight false-alarms legitimately long (20-40 min)
   jobs, too loose recreates the multi-hour blind spot.

## Review applied (2026-06-04, 5-persona ce-doc-review)

What the review changed (findings confirmed against the code before applying):

- **P0 design bug fixed:** the watchdog re-invoked via `injectUserMessage`, which
  hard-returns `false` when `!inFlight` (cli-process.js:2117) — the exact idle
  state the watchdog targets. Switched to `fireUserMessage` (:2175, no inFlight
  gate). *(coherence + feasibility + adversarial, conf 100)*
- **Idle poll path corrected:** `_pollMidTurnDialogs` early-returns on
  `pendingTurns===0`, so it can't host idle detection; specified a new
  idle-eligible `pongWatchdog` branch. Fixed the "ping ticks 5s" error
  (`PING_INTERVAL_MS`=10s; pong=5s). *(feasibility, conf 100)*
- **Detection mechanism elevated to a real P0 decision** between pane-scrape (A)
  and agent-declares-via-protocol (B), defaulting to B — the convergent signal
  from three personas that the pane-scrape foundation is fragile, may not exist,
  and reverses the refactor, while the protocol path was sitting deferred in Q3.
- **Pane-scrape (if used) anchored to the live viewport,** not the 1000-line
  `captureWide` scrollback (stale-indicator false-positive). *(adversarial)*
- **Scope cut to probe + watchdog;** eviction-pin (can't occur on shumorobot),
  visibility (per-turn reactor has no idle host), and restart (its own "non-goal")
  moved to explicitly-triggered Deferred items. *(product + scope, conf 75-100)*
- **Self-check scoped read-only** (bypassPermissions blast radius); autonomous-
  wakeup corrected to outbound-only; method name settled
  (`hasLiveBackgroundWork`); STALL_MIN a constant in v1; "four uses" framing
  dropped.
