## §0 Pre-flight reality checks

Before writing the plan, the assumptions worth checking:

### §0.1 The pm-interface exists but abstracts at the WRONG layer

`lib/pm-interface.js` is the canonical JSDoc-typed contract for a *ProcessManager* — i.e. the thing that holds many processes. Implemented by `lib/sdk/process-manager.js`. Pre-0.9.0, `lib/sdk/router.js` was an identity-passthrough wrapper that pm.send / pm.kill / etc. routed through.

**The v1 architectural mistake**: this typedef makes it tempting to instantiate TWO ProcessManagers (SDK + tmux), each with its own `procs` Map, dispatched per-chat via a router. v1 of this spec made that error.

**The v2 correction**: abstract at the **Process** level, not the ProcessManager level. ONE pm, ONE `procs` Map, but each entry is a `Process` instance — either `SdkProcess` (wraps an SDK Query) or `TmuxProcess` (wraps a tmux-hosted claude). Per-session choice happens at Process construction; pm doesn't care which concrete subclass it's holding. Killing all sessions of a chat iterates ONE Map. Boot replay scans ONE Map. Adding a third backend later = one new Process subclass.

The existing `pm-interface.js` typedef needs revision (it documents ProcessManager-level contract); the new `Process` interface needs to be authored. See §6.

### §0.2 The old CLI pm was `claude --print --input-format=stream-json`, not tmux-hosted TUI

Pre-0.8.0 polygram ran `lib/process-manager.js` (806 lines) that spawned `claude -p --input-format=stream-json --output-format=stream-json` as a subprocess and read line-delimited JSON from stdout. Deleted in commit 6 of 0.9.0-cleanup along with its 1201 lines of tests. **The historical "CLI pm" is NOT the same thing as "claude code under tmux session" the user is asking for** — that's a new backend.

### §0.3 `claude --remote-control` is NOT a programmatic control channel

It's a human-facing browser/mobile session-sharing feature ("research preview"). Routes messages from claude.ai/code web/mobile → Anthropic API → local Claude Code process. No socket, no structured event stream, no slash-command API. Not the path for polygram.

### §0.4 Structured events from Claude Code CLI are PRINT-mode only

Two CLI flags enable structured I/O:
- `--include-hook-events` — only works with `--output-format=stream-json`
- `--include-partial-messages` — only works with `--print AND --output-format=stream-json`

The **TUI itself does NOT emit a structured event stream over any documented channel**. To read assistant messages, tool uses, compact boundaries etc. programmatically, you either:
- (a) Run print-mode and pipe stdin/stdout (headless — no human-visible TUI)
- (b) Scrape `tmux capture-pane` output (TUI works, but parsing is screen-scrape territory)
- (c) Tail the `--debug-file <path>` log (possibly structured, possibly noisy — needs Phase 0 verification, see G7)

### §0.5 `--tmux` flag exists but is for Claude's worktree feature, not generic

`claude --tmux --worktree [name]` opens a tmux session that Claude manages itself. It's tied to git worktrees and is meant for human-driven worktree workflows. **Not a control surface polygram can use.** We'd run `claude` inside a tmux session that *polygram* manages, not the other way around.

### §0.6 Authentication — TUI uses macOS Keychain by default; SDK uses different paths

The TUI reads OAuth tokens from `~/Library/Keychains/login.keychain-db` automatically. The SDK respects `ANTHROPIC_API_KEY` env var or its own auth flow. Polygram's current pm runs in shumabit's launchd context which has Aqua/keychain access — that's why it works. If 0.10.0 spawns `claude` (TUI) inside tmux from the same daemon, **keychain access should transparently inherit**. Verify in Phase 0 (G3).

### §0.7 The `process.stdin EIO` regression class still applies

Per TODO.md follow-up: the rc.38-class fix to `proc.stdin.on('error')` got lost in the 0.9.0 cleanup. A tmux-backed implementation that spawns claude subprocesses via tmux send-keys avoids the polygram-process-spawning-direct-subprocess pattern entirely (tmux owns the child). **0.10.0 could side-step the EIO class for the new backend by design** — but the SDK pm still has it as a follow-up.

### §0.8 OpenClaw used a related approach for some workflows

OpenClaw (`@mariozechner/pi-coding-agent`) had a "tmux backend" pattern for running interactive coding agents that humans could observe. Not directly polygram-relevant — OpenClaw was operator-driven, not bot-driven — but the screen-scraping discipline (capture-pane polling cadence, ANSI parsing, prompt-pattern detection) is well-explored prior art worth surveying.

## §1 Goals

1. **Per-chat / per-topic backend selection.** Config field `pm: 'sdk'` (default) or `pm: 'tmux'` per chat (or per topic, with chat-level fallback).
2. **Operator-attachable sessions.** When `pm: 'tmux'` is set, the chat runs `claude` inside a tmux session humans can `tmux attach -t claude-<chat_id>` into to see Claude's TUI live.
3. **Feature parity within practical limits.** Tmux backend should support: send user message, receive assistant text, observe turn completion, abort, model/effort switching, /compact, /new, session resume after polygram restart.
4. **Stable contract.** The `lib/pm-interface.js` typedef remains canonical; both backends implement it. Optional methods may differ — feature-detect at call sites.
5. **Graceful degradation.** When a tmux backend can't do something the SDK can (e.g. live context-usage query, mid-turn `applyFlagSettings`), the polygram layer falls back to the closest available equivalent rather than crashing.

## §2 Non-goals

- **Not** going back to `claude --print --input-format=stream-json` as the second backend. That was the old CLI pm and it didn't provide the operator-attachable property the user wants.
- **Not** implementing a third backend (e.g. SSH-to-remote-claude, Docker-claude). Multi-backend extensibility is welcome but only SDK + tmux ship in 0.10.0.
- **Not** retrofitting features the SDK has natively into the tmux backend if they require deep TUI internals. Document the gap, let SDK be the default for those use cases.
- **Not** changing the persistence layer. claude_session_id still lives in SQLite. Both backends resume via `--resume <id>` (SDK does it programmatically; tmux passes it as a CLI flag at session start).
- **Not** running tmux on every backend selection — `pm: 'sdk'` does not spawn tmux. The tmux daemon is a per-chat thing.

## §3 The current state

`lib/sdk/process-manager.js` is 1178 lines. Exposes the contract documented in `lib/pm-interface.js`:

**Required** (must work for any backend polygram boots with):
- `has(sessionKey)` / `get(sessionKey)` / `keys()` / `size()`
- `getOrSpawn(sessionKey, ctx)` — cold-spawn on demand
- `send(sessionKey, prompt, opts)` → `Promise<PmSendResult>` — the hot path
- `kill(sessionKey)` / `killChat(chatId)` / `shutdown()` — lifecycle teardown

**Optional** (SDK has all; tmux may not have all):
- `injectUserMessage(...)` — autosteer + edit-correction
- `setModel(...)`, `applyFlagSettings(...)`, `setPermissionMode(...)` — live config switch (no respawn)
- `drainQueue(...)`, `interrupt(...)`, `resetSession(...)` — abort + reset

**Lifecycle callbacks** (constructor-injected): `onInit`, `onClose`, `onStreamChunk`, `onToolUse`, `onAssistantMessageStart`, `onCompactBoundary`, `onResult`, `onQueueDrop`. Each fires from inside the pm's event loop into polygram-side handlers.

## §4 Approach options for the tmux backend

Three feasible architectures. Each makes different trade-offs.

### §4.A Pure tmux + TUI + screen-scraping

```
polygram daemon
    └─ tmux new-session -d -s claude-<chat_id> -c <cwd> \
         'claude --resume <session_id> --model <m> --effort <e>'
    └─ tmux send-keys -t claude-<chat_id> -l "user prompt text"
    └─ tmux send-keys -t claude-<chat_id> Enter
    └─ poll: tmux capture-pane -t claude-<chat_id> -p
    └─ parse output for: assistant text, tool calls, "done" indicator, errors
    └─ tmux send-keys -t claude-<chat_id> C-c   (interrupt)
    └─ tmux kill-session -t claude-<chat_id>    (teardown)
```

**Pros**:
- Operator can `tmux attach -t claude-<chat_id>` and see exact TUI live
- All TUI features work: plugins, agents picker, slash commands, hook events visible
- Single source of truth (the TUI is the model + the view)
- No special CLI flags required; works with stock `claude`

**Cons**:
- Screen-scraping is fragile. ANSI codes, line wrapping, terminal width drift cause parse failures.
- Hard to distinguish "Claude is thinking" from "Claude finished and is awaiting input" without robust prompt-pattern detection.
- Tool call detection is parse-heavy. Tool diff display in TUI is rich; getting the *fact* that a tool ran requires either parsing the visible diff or detecting tool-name banner patterns.
- Cost / token usage not visible in TUI by default. Have to send `/cost` slash command and parse the response.
- Context-window usage not programmatically queryable. Have to send `/context` and parse.

**Risk grade**: HIGH. Multiple unknowns require Phase 0 verification.

### §4.B Hybrid — TUI in tmux + structured side-channel via debug log

```
polygram daemon
    └─ tmux new-session -d -s claude-<chat_id> -c <cwd> \
         'claude --resume <id> --debug-file /tmp/claude-<chat_id>.log'
    └─ tail -F /tmp/claude-<chat_id>.log  (polygram subscribes)
    └─ tmux send-keys -t claude-<chat_id> -l "user prompt" Enter
    └─ structured events come from debug log; UI is for humans
```

**Pros**:
- TUI still visible to operators via `tmux attach`
- Structured event observation from debug log (if it's structured enough — Phase 0 G7)
- Avoids most screen-scraping

**Cons**:
- `--debug-file` is for debug logging, not designed as a stable API. Format may drift across claude versions.
- Debug logs may not include all events polygram needs (assistant text, tool calls, compact boundaries) — Phase 0 verification critical.
- Two channels to keep in sync: send commands via send-keys, receive events via log tail. Race conditions if the TUI hasn't processed the send-keys before polygram is already reading log responses.

**Risk grade**: MEDIUM. Lower than §4.A if Phase 0 G7 confirms debug log is usable.

### §4.C Tmux-hosted print-mode (`claude -p --input-format=stream-json`)

```
polygram daemon
    └─ tmux new-session -d -s claude-<chat_id> -c <cwd> \
         'claude --print --input-format=stream-json --output-format=stream-json --resume <id> < /tmp/pipe-in-<id>'
    └─ Polygram writes JSON to /tmp/pipe-in-<id>
    └─ tmux capture-pane reads JSON output (or use --output redirect to a file)
    └─ tmux attach shows raw JSON scrolling (not useful for humans)
```

**Pros**:
- Stream-json is documented and stable (the OLD CLI pm pattern)
- Structured I/O — no parsing ambiguity
- Same protocol the deleted CLI pm used (we can revive some patterns)

**Cons**:
- Operator can't usefully `tmux attach` — they'd see raw JSON scrolling
- **Loses the user's primary motivation** for the tmux backend (operator visibility)
- Adds tmux indirection for no functional gain over running the subprocess directly
- The OLD CLI pm did this without tmux for 2 years and worked

**Risk grade**: LOW (well-trodden path) but **fails the goal** (operator visibility).

## §5 Recommended approach

**Phase 0 should evaluate §4.A and §4.B in parallel.** If §4.B (debug-log side channel) is usable per gate G7, ship it. Else fall back to §4.A (screen-scraping) — slower to build, more brittle, but functional.

**Do NOT ship §4.C** as the "tmux backend." If headless stream-json is needed (e.g. for batch ops or testing), revive the OLD CLI pm pattern as `ProcessManagerCli` — a separate backend, no tmux involvement. That's out of 0.10.0 scope but easy to add later.

**Recommendation as v1 default**: §4.B (hybrid). Falls back to §4.A if G7 fails.

### §6.2 The Process abstract interface

This is the new abstraction layer. Both `SdkProcess` and `TmuxProcess` implement it. Mirrors what SDK's `Query` object exposes, plus the lifecycle ProcessManager needs to maintain a collection.

```js
/**
 * Abstract Process — one running Claude session, regardless of backend.
 *
 * Subclasses: SdkProcess (long-lived SDK Query), TmuxProcess (claude
 * TUI hosted inside a tmux session, controlled via send-keys +
 * capture-pane / debug-log tail).
 *
 * State machine: spawn → ready → (turn-in-flight | idle) ↔ closed.
 *
 * Public surface mirrors SDK Query's contract so callers (polygram's
 * handleMessage, slash-commands, autosteer, etc.) don't branch on
 * subclass. Optional methods may not be implemented by some backends
 * — those throw `UnsupportedOperationError` and callers feature-detect.
 */
class Process {
  // Identity (set by ProcessManager at spawn time, immutable after)
  sessionKey;       // string — polygram session key
  chatId;           // string
  threadId;         // string | null
  label;            // string — human-readable for logs
  backend;          // 'sdk' | 'tmux' — for telemetry / pm-backend-mismatch detection

  // State
  closed;           // boolean — true once shutdown begins
  inFlight;         // boolean — true while a turn is being processed
  pendingQueue;     // Array — FIFO turns waiting to dispatch
  claudeSessionId;  // string | null — for --resume / Options.resume

  // Lifecycle — REQUIRED
  async start(opts) {}                  // cold-spawn this process
  async send(prompt, opts) {}           // queue/dispatch a user turn, returns PmSendResult
  async kill(reason) {}                 // close cleanly; returns when fully torn down

  // Mid-session controls — OPTIONAL (throws UnsupportedOperationError if unsupported)
  async interrupt() {}                  // /stop equivalent — non-destructive (preserves session)
  drainQueue(errCode) {}                // reject all pending turns with errCode
  async setModel(model) {}              // /model X
  async applyFlagSettings(settings) {}  // /effort X (or similar partial config)
  async setPermissionMode(mode) {}      // /permission-mode (rarely used)
  injectUserMessage(opts) {}            // autosteer / edit-correction — push mid-turn user input
  async resetSession(opts) {}           // close + clear session_id from DB; fresh start next send
  async getContextUsage() {}            // for /context slash-command and the 70% hint

  // Event subscription — REQUIRED (lifecycle callbacks fed from ProcessManager constructor)
  // The pm registers handlers on construction; the Process invokes them on event arrival.
  // Same callback shape as today's SDK pm: onInit, onClose, onStreamChunk, onToolUse,
  // onAssistantMessageStart, onCompactBoundary, onResult, onQueueDrop.
  on(eventName, handler) {}
  off(eventName, handler) {}
}
```

### §6.3 The ProcessManager — generic, collection-only

`lib/process-manager.js`. Holds `Map<sessionKey, Process>`. Doesn't know or care which concrete Process class it's holding. Most current `lib/sdk/process-manager.js` logic moves here, minus the SDK-specific bits that go into `SdkProcess`.

```js
class ProcessManager {
  constructor({ cap, db, logger, processFactory, callbacks }) {
    this.procs = new Map();        // sessionKey → Process
    this.cap = cap || 10;          // LRU cap
    this.db = db;
    this.processFactory = processFactory; // (sessionKey, ctx) → Process subclass instance
    this.callbacks = callbacks;    // onInit, onClose, ... fed to each Process at spawn
  }

  has(sessionKey) { return this.procs.has(sessionKey); }
  get(sessionKey) { return this.procs.get(sessionKey) || null; }
  keys() { return [...this.procs.keys()]; }
  size() { return this.procs.size; }

  async getOrSpawn(sessionKey, ctx) {
    if (this.procs.has(sessionKey)) return this.procs.get(sessionKey);
    await this._evictIfNeeded();
    // FACTORY decides which Process subclass to instantiate based on config
    const proc = await this.processFactory(sessionKey, ctx);
    // Wire callbacks
    for (const [event, handler] of Object.entries(this.callbacks)) {
      proc.on(event, handler);
    }
    await proc.start(ctx);
    this.procs.set(sessionKey, proc);
    return proc;
  }

  async send(sessionKey, prompt, opts) {
    const proc = await this.getOrSpawn(sessionKey, opts.context);
    return proc.send(prompt, opts);
  }

  async kill(sessionKey, reason) {
    const proc = this.procs.get(sessionKey);
    if (!proc) return;
    this.procs.delete(sessionKey);
    await proc.kill(reason);
  }

  async killChat(chatId) {
    const toKill = [...this.procs.entries()]
      .filter(([_, p]) => p.chatId === String(chatId));
    await Promise.allSettled(toKill.map(([sk]) => this.kill(sk)));
  }

  async shutdown() {
    const all = [...this.procs.keys()];
    await Promise.allSettled(all.map(sk => this.kill(sk, 'shutdown')));
  }

  // Optional methods — delegate to the Process; throw UnsupportedOperationError
  // if the underlying subclass doesn't support it.
  async interrupt(sessionKey) { return this.procs.get(sessionKey)?.interrupt(); }
  drainQueue(sessionKey, errCode) { return this.procs.get(sessionKey)?.drainQueue(errCode); }
  async setModel(sessionKey, model) { return this.procs.get(sessionKey)?.setModel(model); }
  async applyFlagSettings(sessionKey, s) { return this.procs.get(sessionKey)?.applyFlagSettings(s); }
  async setPermissionMode(sessionKey, m) { return this.procs.get(sessionKey)?.setPermissionMode(m); }
  injectUserMessage(sessionKey, opts) { return this.procs.get(sessionKey)?.injectUserMessage(opts); }
  async resetSession(sessionKey, opts) { return this.procs.get(sessionKey)?.resetSession(opts); }

  async _evictIfNeeded() { /* LRU eviction — agnostic to subclass */ }
}
```

### §6.4 Process factory — per-session backend choice

```js
// lib/process/factory.js
function createProcessFactory({ config, sdkOptions, tmuxRunner, db, logger }) {
  return async function(sessionKey, ctx) {
    const { chatId, threadId } = ctx;
    const chatCfg = config.chats[chatId];
    const topicCfg = threadId && chatCfg?.topics?.[threadId];
    const choice = topicCfg?.pm || chatCfg?.pm || config.bot?.pm || 'sdk';

    // DB record — set on spawn, reset to current choice on /new
    if (db) {
      db.setSessionBackend?.(sessionKey, choice);
    }
    logger.log?.(`[${sessionKey}] backend=${choice}`);

    if (choice === 'tmux') {
      return new TmuxProcess({ sessionKey, chatId, threadId, ctx, runner: tmuxRunner, logger });
    }
    return new SdkProcess({ sessionKey, chatId, threadId, ctx, sdkOptions, logger });
  };
}
```

### §6.6 TmuxProcess lifecycle

```
spawn(sessionKey, ctx):
  1. mint session_name = `polygram-${chatId}-${threadId || 'main'}`
  2. resolve --resume <id> from DB if available
  3. tmux new-session -d -s <name> -c <cwd> 'claude <flags>'
  4. wait for prompt indicator (G6 — Phase 0 must verify timing)
  5. arm debug-log tail (§4.B) OR start capture-pane poll (§4.A)
  6. return entry

send(sessionKey, prompt, opts):
  1. write prompt to pane via tmux send-keys -l (literal mode, handles special chars)
  2. send Enter
  3. arm idle/wall-clock timers (mirror SDK pm's defaults)
  4. wait for completion indicator
  5. parse final assistant text from capture-pane / debug log
  6. resolve with PmSendResult (text, cost, duration, error, metrics)

interrupt(sessionKey):
  1. tmux send-keys -t <name> C-c

resetSession(sessionKey, opts):
  1. send /new via tmux send-keys
  2. OR kill + respawn without --resume (preserves new session_id from claude's mint)
  3. clear claude_session_id in DB
```

## §9 Invariants (what we DON'T change)

- **lib/pm-interface.js typedef stays canonical.** Both backends implement it; no breaking changes to the contract.
- **SDK pm stays the default** for any chat that doesn't explicitly opt into tmux.
- **claude_session_id remains the resume key** across both backends. The SDK passes it via `Options.resume`; the tmux backend passes it as `--resume <id>` at spawn.
- **`polygram --bot <name>` daemon model unchanged.** One Node process per bot. Both backends live inside that one process.
- **Per-bot DB unchanged.** No per-backend tables; `pm_backend` column is just a routing hint.
- **Telegram surface unchanged.** Users don't see "backend: tmux" anywhere; operator visibility is via `tmux attach`, not user-facing.
- **Core slash commands (`/new`, `/compact`, `/model`, `/effort`, `/stop`) work in BOTH backends.** Implementation may differ; UX of these specific 5 commands must not. **Autosteer + edit-correction are GOALS for tmux backend** — Ivan's TUI experience indicates the underlying mechanism exists, but G8's 8-scenario protocol must PASS before this is invariant. If subset of scenarios fail (e.g. mid-Bash injects swallowed), polygram surfaces "queue for next turn" gracefully for those subset; if ALL fail, polygram surfaces a "feature not available in this backend" message. Per R3-F4: NOT overclaimed for `/context` or per-turn `getContextUsage` (depends on G7/G15 parsability). See §6.2 capability matrix + §10.G8-protocol.
- **Backend stability isolation.** Per R3-F12 + §0.7: an uncaught exception class (EIO stdin, child-proc spawn race) localized to one Process subclass cannot crash unrelated subclasses or the daemon. Each subclass's lifecycle owns its own error boundaries; the generic ProcessManager catches in `Process.start/send/kill` calls and emits via the `error` event instead of propagating to the daemon's unhandled-rejection guard. Verified by Phase 2 chaos-injection test.
- **Polygram's `events` table stays the forensic source of truth** for both backends. Backends emit equivalent event kinds.

### §10.G8-protocol — Verification scenarios for mid-turn inject

G8 is load-bearing for tmux backend's autosteer + edit-correction features. Ivan's TUI-user experience indicates human typing mid-turn works; this protocol verifies the SAME behavior holds for programmatic paste from polygram's daemon AND maps every edge case. Run all 8 scenarios; each gets a PASS/FAIL row in `phase0-findings.md`.

**S1. Baseline — inject during pure-text streaming**
- Setup: prompt = "Write a long essay on X" (no tool calls expected). Wait for streaming to start.
- Inject: paste "actually also include Y" + Enter at 3s into streaming.
- Expected: claude folds Y into the same turn's output. Same assistant message OR a new bubble appended within the turn (acceptable either way).
- Measure: (a) latency from paste to claude visibly acknowledging Y, (b) does original streaming pause or continue, (c) does cost get attributed to one turn or two, (d) does the SDK result event fire once at end or twice.

**S2. Inject between two tool calls**
- Setup: prompt = "Read file A, then read file B". Claude reads A, between the two Reads, polygram injects.
- Inject: paste "also read C" + Enter during the gap.
- Expected: claude reads B AND C (folded). Tool call sequence: A, then B, then C, OR A, B, C in some order.
- Measure: order of tool calls, whether C lands in same turn's tool_use_id namespace, total cost.

**S3. Inject during a long Bash tool call (>30s)**
- Setup: prompt = "Run `sleep 60 && echo done`". Mid-Bash, inject.
- Inject: paste "abort that and tell me the date" + Enter during sleep.
- Expected: HARD CASE. Either (a) claude buffers, lets Bash finish, then addresses the inject. (b) Claude treats inject as priority + interrupts Bash. (c) Claude ignores the inject until next natural step.
- Measure: which behavior, whether tool result rows are consistent.

**S4. Inject during MCP-tool call**
- Setup: Use an MCP server with a slow tool. Inject during the MCP call.
- Expected: same options as S3.
- Measure: MCP error handling if claude tries to interrupt.

**S5. Multiple rapid injects (autosteer queue stress)**
- Setup: turn in flight; inject 3 messages 500ms apart.
- Expected: claude folds all 3 into the turn's context. Or queues some / discards some.
- Measure: how many land, in what order, whether claude acknowledges each.

**S6. Inject during compaction**
- Setup: trigger `/compact`; while compaction is in progress, inject.
- Expected: WORST CASE. Compaction may swallow or reject the inject. Compaction may complete and the inject takes effect on the post-compact session.
- Measure: outcome; if rejected, polygram needs to detect compaction-in-progress and defer the inject.

**S7. Inject racing turn completion**
- Setup: short prompt expected to finish in ~2s. Inject at 1.9s (just before completion).
- Expected: TIMING-DEPENDENT. Either the inject lands in this turn (folds) or in the next turn (split — autosteer semantics broken).
- Measure: probability distribution over many trials; what's the safe gap before turn-end where polygram can still inject?

**S8. Inject when claude is at the input prompt (idle, not in turn)**
- Setup: claude is awaiting input (`inFlight=false`).
- Behavior: polygram's `injectUserMessage` should return `false` in this state (per §12.3) — caller falls through to normal `pm.send` path.
- Verify: §12.3 sketch's `if (!this.inFlight) return false` actually short-circuits, doesn't double-send.

**Required artifacts from G8 verification:**
1. Each scenario's outcome documented in `docs/0.10.0-phase0-spike-findings.md` with timing measurements + transcript samples.
2. **Decision tree per scenario outcome** added to §11 G8 row (currently aggregate; replace with per-scenario decisions).
3. If S6 or S7 fail: polygram needs new state-tracking (`compactionInProgress` flag, "safe inject window" before turn end).
4. If S3/S4 produce inconsistent behavior across runs: document as "tmux backend autosteer is best-effort during tool calls; SDK backend remains strictly ordered."

```js
// Two distinct error classes per R3-F9: separates "this backend
// fundamentally can't" from "implementable but not yet wired."
class UnsupportedOperationError extends Error {
  constructor(method, backend) {
    super(`Operation ${method} not supported by ${backend} backend`);
    this.code = 'UNSUPPORTED_OPERATION';
    this.method = method;
    this.backend = backend;
  }
}
class NotImplementedYetError extends Error {
  constructor(method, backend, phase) {
    super(`Operation ${method} not yet implemented in ${backend} (planned: ${phase})`);
    this.code = 'NOT_IMPLEMENTED_YET';
    this.method = method;
    this.backend = backend;
    this.phase = phase;
  }
}

// R1-F1 CRITICAL fix: optional methods that are HOT-PATH callers
// (autosteer, edit-correction) must NOT throw — autosteer's caller
// site at lib/handlers/autosteer.js:72 has no try/catch around
// pm.injectUserMessage. Default returns false; subclasses that
// support the method return true on success.
//
// Methods that are async-safe (caller will await + catch) MAY throw
// UnsupportedOperationError. Methods that are sync hot-path return
// a sentinel value (false / null / undefined per signature).

class Process {
  // Identity (set in ctor by subclass; immutable after)
  sessionKey;
  chatId;
  threadId;
  label;
  backend;        // 'sdk' | 'tmux'

  // State
  closed = false;
  inFlight = false;
  pendingQueue = [];
  claudeSessionId = null;

  // EventEmitter for lifecycle callbacks (Node's events.EventEmitter)
  emitter;

  constructor({ sessionKey, chatId, threadId, label }) {
    this.sessionKey = sessionKey;
    this.chatId = chatId;
    this.threadId = threadId;
    this.label = label;
    this.emitter = new (require('events').EventEmitter)();
  }

  on(event, handler) { this.emitter.on(event, handler); }
  off(event, handler) { this.emitter.off(event, handler); }
  emit(event, ...args) { this.emitter.emit(event, ...args); }

  // Subclass MUST override these
  async start(opts) { throw new Error('start() must be overridden'); }
  async send(prompt, opts) { throw new Error('send() must be overridden'); }
  async kill(reason) { throw new Error('kill() must be overridden'); }

  // Async methods MAY throw — caller is `await`-ing and has try/catch
  async interrupt() { throw new UnsupportedOperationError('interrupt', this.backend); }
  async setModel(_model) { throw new UnsupportedOperationError('setModel', this.backend); }
  async applyFlagSettings(_settings) { throw new UnsupportedOperationError('applyFlagSettings', this.backend); }
  async setPermissionMode(_m) { throw new UnsupportedOperationError('setPermissionMode', this.backend); }
  async resetSession(_opts) { throw new UnsupportedOperationError('resetSession', this.backend); }
  async getContextUsage() { throw new UnsupportedOperationError('getContextUsage', this.backend); }

  // Sync hot-path methods — return sentinel values, never throw
  drainQueue(_code) { return 0; }  // 0 = nothing drained
  injectUserMessage(_opts) { return false; }  // false = inject not available, caller falls through to normal pm.send
}

module.exports = { Process, UnsupportedOperationError, NotImplementedYetError };
```

### §12.3 `lib/process/tmux-process.js` — tmux backend impl

```js
// R2-F1 CRITICAL: bytes 0x00-0x08, 0x0b-0x1f, 0x7f must be stripped
// before send. `send-keys -l` writes literal UTF-8 bytes to the pty;
// the pty's line discipline interprets control chars REGARDLESS of
// the `-l` flag. Trivially exploitable from any Telegram user
// inserting Ctrl-C (0x03) into a message → silent turn abort.
const CONTROL_CHAR_RE = /[\x00-\x08\x0b-\x1f\x7f]/g;
function sanitizeForTmux(text) {
  if (typeof text !== 'string') return '';
  // Allow: tab (0x09), newline (0x0a). Strip everything else in C0/DEL.
  return text.replace(CONTROL_CHAR_RE, '');
}

class TmuxProcess extends Process {
  backend = 'tmux';

  constructor({ sessionKey, chatId, threadId, label, runner, logger }) {
    super({ sessionKey, chatId, threadId, label });
    this.runner = runner;
    this.logger = logger;
    this.tmuxName = null;
    this.debugLogPath = null;
    this.debugLogTail = null;
    this.captureInterval = null;
    this._spawning = null;       // Promise sentinel for in-flight spawn (R2-F7)
    this._killing = false;       // Flag for in-flight kill (R2-F7)
  }

  // R2-F8 + R3-F8: explicit attach() vs start() distinction. start()
  // ALWAYS calls `tmux new-session`; attach() ALWAYS connects to an
  // existing session that boot-replay's orphan-scan found alive from
  // before the daemon crashed. Boot-replay never calls start() for
  // a tmux session whose orphan was reconciled; it calls attach().
  async start({ existingSessionId, model, effort, cwd, chatConfig, botName }) {
    if (this._killing) throw new Error('TmuxProcess in killing state');
    // R2-F11: bot-prefixed tmux session name to avoid collision across
    // bot instances on same host.
    this.tmuxName = this.runner.sessionName(botName, this.chatId, this.threadId);
    // R2-F5: debug log path sanitized via same sanitizer as session name.
    this.debugLogPath = this.runner.debugLogPath(botName, this.chatId, this.threadId);

    // v5 (post-spike): args locked in by Phase 0 F-spike-1 + F-spike-4.
    // --permission-mode acceptEdits avoids the TUI "Do you want to
    //   create X?" blocking prompt without needing the
    //   --dangerously-skip-permissions companion (cleaner than
    //   bypassPermissions which TUI rejects without --dangerously...).
    // Per-chat override flows via chatConfig.permissionMode same as SDK pm.
    const permissionMode = chatConfig.permissionMode || 'acceptEdits';
    const args = [
      ...(existingSessionId ? ['--resume', existingSessionId] : []),
      '--model', model,
      '--effort', effort,
      '--permission-mode', permissionMode,
      ...(permissionMode === 'bypassPermissions' ? ['--dangerously-skip-permissions'] : []),
      '--debug-file', this.debugLogPath,
      ...(chatConfig.agent ? ['--agent', chatConfig.agent] : []),
    ];
    // R2-F8: new-session errors must FAIL LOUD, not silent-catch.
    try {
      await this.runner.spawn({
        chatId: this.chatId, threadId: this.threadId, botName,
        cwd, env: this._filterEnv(), command: 'claude', args,
      });
    } catch (err) {
      // EEXIST = orphan session still alive. Reconciliation should
      // have caught this on boot; if not, surface loudly so the
      // operator can investigate.
      throw Object.assign(new Error(`tmux spawn failed: ${err.message}`), {
        code: 'TMUX_SPAWN_FAILED', tmuxName: this.tmuxName, cause: err,
      });
    }
    // R2-F3: lock-pane against operator-write by default. Break-glass
    // via a documented admin command (TBD Phase 3).
    await this.runner.setPaneReadOnly(this.tmuxName);
    await this._waitForReady();   // G6 — prompt-ready indicator detect
    this._armEventStream();        // §4.B debug-log OR §4.A capture-pane fallback
    this.emit('init', { sessionId: existingSessionId, label: this.label });
  }

  // R2-F8: attach to a still-alive tmux session from before the crash.
  // Distinct from start() — no new-session call. Verifies the session
  // exists and arms event-stream + ready-detect against the existing
  // claude TUI without bouncing it.
  async attach({ tmuxName, botName }) {
    if (this._killing) throw new Error('TmuxProcess in killing state');
    const exists = await this.runner.sessionExists(tmuxName);
    if (!exists) {
      throw Object.assign(new Error('tmux attach: session vanished'), {
        code: 'TMUX_ATTACH_VANISHED', tmuxName,
      });
    }
    this.tmuxName = tmuxName;
    this.debugLogPath = this.runner.debugLogPath(botName, this.chatId, this.threadId);
    // Don't spawn claude. Don't waitForReady (already ready or mid-turn).
    // DO arm event-stream + diff-against-expected-bytes to detect any
    // operator activity during the daemon's absence.
    this._armEventStream({ fromHeadOfLog: false });
    this.emit('reattach', { tmuxName, label: this.label });
  }

  async send(prompt, opts) {
    if (this.inFlight) {
      // Queue per pm policy — caller's getOrSpawn / pendingQueue
      // mechanics handle FIFO.
    }
    this.inFlight = true;
    // R2-F1 CRITICAL: sanitize control chars before send.
    const safePrompt = sanitizeForTmux(prompt);
    if (safePrompt !== prompt) {
      this.logger.warn?.(`[${this.label}] stripped ${prompt.length - safePrompt.length} control chars from prompt`);
      this.emit('prompt-sanitized', { stripped: prompt.length - safePrompt.length });
    }
    // R1-F9 + R2-F1: ALWAYS use buffer-paste pattern. send-keys -l
    // does NOT neutralize control chars; using set-buffer+paste-buffer
    // is structurally safer (kernel-side bracketed-paste-aware) AND
    // handles long text, emoji, CJK without escape concerns.
    await this.runner.pasteText(this.tmuxName, safePrompt);
    await this.runner.sendKeys(this.tmuxName, 'Enter');
    return this._awaitCompletion(opts);  // G6 — turn-completion detect
  }

  async interrupt() {
    await this.runner.sendKeys(this.tmuxName, 'C-c');
  }

  async setModel(model) {
    await this.runner.sendText(this.tmuxName, `/model ${model}`);
    await this.runner.sendKeys(this.tmuxName, 'Enter');
    // TODO: parse confirmation from output
  }

  async applyFlagSettings({ effortLevel }) {
    if (!effortLevel) return false;
    await this.runner.sendText(this.tmuxName, `/effort ${effortLevel}`);
    await this.runner.sendKeys(this.tmuxName, 'Enter');
  }

  async resetSession(opts) {
    await this.runner.sendText(this.tmuxName, '/new');
    await this.runner.sendKeys(this.tmuxName, 'Enter');
    return { closed: false, drainedPendings: this.pendingQueue.length };
  }

  async getContextUsage() {
    // R3-F4: don't overclaim parity. Throw async (caller awaits) is
    // OK for getContextUsage — it's used in the /context slash-command
    // path which can handle "feature unavailable" gracefully.
    throw new NotImplementedYetError('getContextUsage', 'tmux', 'Phase 3 if G7+G9 pass');
  }

  // v4 / G8: TUI buffers input and folds it into the current turn at
  // the next natural pause (between tool calls / reasoning steps).
  // Same channel as send(), minus _awaitCompletion — the parent
  // turn's completion logic handles the new content folding in.
  //
  // Returns false only when there's no live turn to inject into;
  // caller (autosteer / edit-correction) falls through to normal
  // pm.send queue. Never throws (hot path — autosteer caller has
  // no try/catch).
  injectUserMessage({ content, priority = 'next', shouldQuery }) {
    if (!this.inFlight) return false;
    const safe = sanitizeForTmux(content);
    if (!safe) return false;
    if (safe !== content) {
      this.emit('prompt-sanitized', { stripped: content.length - safe.length, source: 'inject' });
    }
    // Fire and forget — claude TUI receives, buffers, folds at the
    // next pause. Errors here go to the inject-fail event, not the
    // caller (graceful degradation is the contract).
    this.runner.pasteText(this.tmuxName, safe)
      .then(() => this.runner.sendKeys(this.tmuxName, 'Enter'))
      .catch((err) => this.emit('inject-fail', { err: err.message }));
    this.emit('inject-user-message', { text_len: safe.length, priority, shouldQuery });
    return true;
  }

  async kill(reason) {
    this.closed = true;
    if (this.captureInterval) clearInterval(this.captureInterval);
    if (this.debugLogTail) this.debugLogTail.close();
    await this.runner.killSession(this.tmuxName);
    this.emit('close', { reason });
  }
}
```

```js
function createTmuxRunner({ logger }) {
  function sessionName(chatId, threadId) {
    return `polygram-${chatId}-${threadId || 'main'}`.replace(/[^\w-]/g, '_');
  }

  async function spawn({ chatId, threadId, cwd, env, command, args = [] }) {
    const name = sessionName(chatId, threadId);
    const fullCmd = [command, ...args].map(shellQuote).join(' ');
    await execFile('tmux', [
      'new-session', '-d', '-s', name,
      '-c', cwd,
      ...Object.entries(env).flatMap(([k, v]) => ['-e', `${k}=${v}`]),
      fullCmd,
    ]);
    await execFile('tmux', ['set-option', '-t', name, 'pane-width', '200']);
    return name;
  }

  async function sendKeys(name, keys, { literal = false } = {}) {
    const args = ['send-keys', '-t', name];
    if (literal) args.push('-l');
    args.push(keys);
    await execFile('tmux', args);
  }

  async function sendText(name, text) {
    // For multi-line / special-char text: use buffer-paste pattern
    await execFile('tmux', ['set-buffer', '-b', `polygram-buf-${name}`, text]);
    await execFile('tmux', ['paste-buffer', '-t', name, '-b', `polygram-buf-${name}`, '-d']);
  }

  async function capturePane(name, { lines = 1000 } = {}) {
    const { stdout } = await execFile('tmux', [
      'capture-pane', '-t', name, '-p', '-S', `-${lines}`,
    ]);
    return stdout;
  }

  async function killSession(name) {
    await execFile('tmux', ['kill-session', '-t', name]).catch(() => {});
  }

  async function listPolygramSessions() {
    try {
      const { stdout } = await execFile('tmux', [
        'list-sessions', '-F', '#{session_name}',
      ]);
      return stdout.trim().split('\n').filter(n => n.startsWith('polygram-'));
    } catch {
      return [];
    }
  }

  return { spawn, sendKeys, sendText, capturePane, killSession, listPolygramSessions, sessionName };
}
```

## §15 Open questions for v2 audit

These are unresolved at v1; the 3-round adversarial audit (per `big-refactor-planner` §3) should resolve them:

1. **Multi-line prompts via send-keys**: are there pathological characters (NUL, escape, control codes) that break `set-buffer`+`paste-buffer`?
2. **Approval surface split-brain**: if a chat uses tmux backend with PreToolUse hooks AND another chat uses SDK backend with in-process canUseTool, the same admin chat sees TWO approval card formats. Acceptable, or unify on one?
3. **Cost telemetry parity**: is `/cost` slash command output stable enough to parse? Or do we accept that tmux turns have zero cost data?
4. **Claude version pinning**: do we add `claude` as a peer dependency with a version range? How do we handle a user with claude older than 2.x?
5. **iTerm2-native pane integration**: the `--tmux` flag mentions iTerm2 native panes. If the operator's terminal IS iTerm2, do we want to use that mode? Or always classic tmux?
6. **macOS vs Linux**: tmux works the same; claude CLI works the same; but the launchd/keychain integration is macOS-specific. systemd-equivalent for Linux is out of scope but worth confirming.
7. **Session-name collisions**: two polygram instances on the same machine would collide on `polygram-<chat>-<thread>` tmux names. Bot-prefixed: `polygram-<bot>-<chat>-<thread>`?
