# Polygram 0.9.0 Cleanup — Architecture Review v3

> Branch: `0.9.0-cleanup` @ HEAD 6b7bfe4
> Base for v3: v2 baseline 42ad877 (commit 24)
> Scope of v3: commits 25–29 — extract autosteer + slash-commands +
> approvals; delete `lib/sdk/router.js`; drop dep-validation paranoia;
> add unit tests for the four previously-orphaned handler factories.
> polygram.js: 3978 → 2916 LOC (−1062, −27% from cleanup start; −676
> since v2). Tests: 1391 → 1446 (+55 net; +75 new handler tests, −7
> dep-validation tests, −7 router tests).
> Reviewer: architecture-strategist (focus: orchestrator coherence, boot
> wiring correctness, placeholder pattern, handlers/ vs sdk/ semantics).

## TL;DR

The good news: Phase B's extraction discipline held through commits
25–29. Three more factory-shaped slices left polygram.js cleanly
(autosteer 95 LOC, slash-commands 290 LOC, approvals 320 LOC, total
~700 lines including JSDoc/wrapper). The router-deletion in commit
27 closed v2 MEDIUM-2 + MEDIUM-3 + LOW-3 in one move. The dep-
validation purge (also commit 27) removed ~47 LOC of `if (!x) throw`
ceremony that the v2 simplicity reviewer correctly flagged as
dead-on-arrival paranoia. The four handler unit-test suites (commit
26) closed v2 MEDIUM-4 cleanly — voice/download/config-callback/
abort all have targeted branch coverage now.

The orchestrator core is **coherent**, not Swiss-cheesed. polygram.js
at 2916 LOC has shed the leaf orchestrators (slash, autosteer,
approvals, abort, config-callback, voice, download) and what remains
is a defensible boot-and-glue file: imports → top-level state → boot
helpers (loadConfig, recordInbound, dispatchHandleMessage, createBot,
pollBot) → main(). The 1100-line `handleMessage` is still inside it
but its body now reads as integration glue (call dispatchSlashCommand,
call autosteer, call handleAbortIfRequested, fall through to LLM
turn) rather than as the implementation of those concerns. This is
the right shape for a 2916-line file — the question becomes whether
the **boot wiring is correct**, and that's where v3 found the merge
gate.

**The merge gate**: the wiring order at `main()` lines 2531–2576
**captures `pm: null` and `bot: null`** in five factory closures
(`createApprovals`, `createHandleConfigCallback`, `createHandleAbort`,
`createAutosteerHandlers`, `createSlashCommands`). These factories
destructure `pm` and `bot` into parameter locals, then close over
those locals — not over the outer `let pm` / `let bot` bindings.
When the outer bindings get reassigned at lines 2576 (`pm = new
ProcessManagerSdk(...)`) and 2602 (`bot = createBot(...)`), the
closures keep seeing the original null. **Every handler that calls
`pm.has` / `pm.get` / `pm.injectUserMessage` / `tg(bot, ...)` will
throw `TypeError: Cannot read properties of null` on first invocation
in production.**

Tests pass (1446/1446) because every handler-factory test injects an
explicit non-null `pm` / `bot` mock. The integration tests don't
exercise main()'s boot wiring at all. v2's LOW-4 explicitly *predicted
the let-rebind pattern would work* — that prediction was **wrong**;
the destructure happens at call time and binds by value, not by
reference. v3 commits 22, 23, 25, 28, 29 each introduced one more
handler with this defect; commit 29 also moved `createApprovals`
ABOVE the pm assignment, fanning the failure surface from "config
callbacks + abort flow" to "approvals + every slash command + every
autosteer detection."

This is a clean fix (3-line move + closure-deferral or pure ordering
swap) — see HIGH-1 for the patch shape. Without it, **0.9.0 will
break the moment a real user sends `/stop`, `/model`, `/effort`,
taps a config-card button, autosteers a follow-up, runs a gated
tool, or types ANY slash command.** This is the entire user-facing
control surface.

The `handleMessage` extraction question (the second biggest concern)
resolves favorably: don't extract it as a single factory. The
remaining 1100 lines are integration glue that legitimately belongs
in the boot file. The factory-extraction strategy ran out of clean
seams when the leaves were all gone — recognizing that and stopping
is the architecturally honest call. See MEDIUM-1.

`lib/handlers/` vs `lib/sdk/` *is* a semantic boundary, but the
boundary is "things ProcessManagerSdk's constructor needs vs. things
called from handleMessage / callback_query." That's defensible; see
MEDIUM-2 for the framing.

## ❗ New since v2

### 🟥 HIGH-1 — **MERGE BLOCKER** — Boot wiring captures `pm: null` and `bot: null` in 5 factory closures

**Files**: polygram.js:2531–2576 (wiring), lib/handlers/{abort,
autosteer, config-callback, slash-commands, approvals}.js, lib/sdk/
callbacks.js (`bot` capture).

**The bug**: when the wiring block runs at boot, the outer `let pm
= null` (line 522) and `let bot = null` (line 125) are still null.
Each factory destructures these into parameter locals:

```js
function createHandleAbort({ pm, bot, ... } = {}) {
  return async function handleAbortIfRequested(...) {
    pm.has(sessionKey);                    // ← pm is the *parameter*, not the let
    await tg(bot, 'sendMessage', { ... }); // ← bot is the *parameter*, not the let
  };
}
```

The destructure binds `pm` and `bot` BY VALUE at call time. The
returned closure captures the parameter locals, not the outer
let-bindings. When `main()` later assigns `pm = new
ProcessManagerSdk(...)` at line 2576 and `bot = createBot(...)` at
line 2602, **only the outer let-bindings update**. The closures'
captured `pm` / `bot` remain the original null. First call to any
handler throws `TypeError: Cannot read properties of null (reading
'has' / 'get' / 'injectUserMessage')` (for pm) or undefined-property
behavior (for bot in `tg(bot, ...)`).

**Verification** — the JS semantics:

```
$ node -e "
let pm = null;
function create({ pm }) { return () => pm; }
const fn = create({ pm });
pm = { ok: true };
console.log(fn());  // → null  (NOT { ok: true })
"
```

**Affected handlers**:

| Handler | Wired at | First broken call | Surface impact |
|---|---|---|---|
| createApprovals | 2536 | `bot` null when callback_query fires | Every approval card breaks |
| createHandleConfigCallback | 2556 | `pm.applyFlagSettings` / `pm.setModel` | Tap on /model or /effort buttons |
| createHandleAbort | 2561 | `pm.has`, `pm.interrupt`, `pm.drainQueue`; `tg(bot, 'sendMessage')` | /stop, /abort, /cancel, "стоп", "отмена" |
| createAutosteerHandlers | 2566 | `pm.has`, `pm.get`, `pm.injectUserMessage` | Every mid-turn follow-up message |
| createSlashCommands | 2569 | `pm.get`, `pm.kill`, `pm.resetSession`, `pm.applyFlagSettings`, `pm.setModel`, `pm.has` | /context, /compact, /reload, /new, /reset, /model, /effort, /pair, /pair-code, /pairings, /unpair |
| createSdkCallbacks | 2510 | `tg(bot, 'sendMessage')` for autonomous-wakeup, compact-boundary, subagent-announce | Already has `if (!bot)` defensive check at line 126 — bot null silently drops the autonomous wakeup; OTHER callbacks (lines 87, 201) lack the check |

**Why tests pass**: every unit test injects a non-null mock pm /
mock bot. None of the tests construct the factories with `pm: null`
followed by reassignment. The integration tests don't exercise main().

**Why production might "look" fine for a few minutes**: a freshly-
deployed bot won't see `/stop` or autosteer attempts immediately. The
first inbound is typically a fresh user message → handleMessage →
no slash → no abort → no autosteer (no in-flight turn yet) → falls
through to pm.send. **pm.send works** because polygram.js calls
`pm.send` directly via `getOrSpawnForChat` / `sendToProcess` (lines
576–629), which read the OUTER let-binding via the closure that
captures `let pm`. Only the destructured-parameter copies are stale.
The control-surface failures show up the first time a user types a
slash, taps a button, or sends a stop message.

**The fix** — three options:

**(a) Move pm + bot assignment ABOVE the factory wiring** (smallest
diff):

```js
// In main(), reorder to:
pm = new ProcessManagerSdk({ ...pmOpts, spawnFn: buildSdkOptions });
bot = createBot(config.bot.token);
// THEN the factory wiring block (createApprovals, createHandle*, etc.)
```

This requires `buildSdkOptions` to be wired BEFORE pm (it already
is), and `makeCanUseTool` to be wired BEFORE buildSdkOptions (which
requires `createApprovals` to run first — but `createApprovals` itself
captures `bot`). So this is a true ordering puzzle — see fix (c).

**(b) Pass a getter or accessor**:

```js
// All factories take getPm/getBot accessors instead of pm/bot:
function createHandleAbort({ getPm, getBot, ... }) {
  return async (...) => {
    const pm = getPm();
    pm.has(sessionKey);
  };
}
// Wired:
createHandleAbort({ getPm: () => pm, getBot: () => bot, ... });
```

The lambda re-reads the let-binding every call. Robust, ~5
factories changed, ~10 lines per factory.

**(c) Inline the require + create into main() AS LOCAL CONSTS** —
this is the simplicity-v2 reviewer's recommendation for the
placeholder pattern more broadly. It also fixes this bug because
LOCAL `const pm = new ProcessManagerSdk(...)` followed by
`createHandleAbort({ pm })` IS the in-scope, post-assignment value.

**Recommended**: **(b) + reorder** — minimal-diff hybrid:

1. Add `getPm` / `getBot` accessors only where the handler reads pm
   or bot; keep `pm` / `bot` direct-passed where the factory only
   reads other things. Two factories (sdk-callbacks for bot,
   approvals for bot) keep direct-pass IF moved AFTER `bot =
   createBot(...)`.
2. Move `bot = createBot(...)` ABOVE `createApprovals(...)` — it's
   currently 26 lines later in main() and there's no reason for the
   gap.
3. Add a single boot-time assertion AFTER all wiring:
   ```js
   // Detect the capture-by-value bug class: every handler factory
   // reads pm/bot via accessor, so a missing assignment is a TypeError
   // at callsite — this assertion adds early signal at boot.
   if (!pm || !bot) throw new Error('boot wiring: pm or bot null after main() init');
   ```

**Severity rationale**: HIGH **and merge-blocking**. The user-facing
control surface (slash commands, abort, config buttons, autosteer)
is the entire reason polygram exists. Shipping 0.9.0 with these
flows broken at first use is a regression more severe than any
behavior-change since the rc.50 orphan-storm. Fix is mechanical and
self-contained — under 50 LOC across 5 files.

### 🟧 HIGH-2 — `let X = null` placeholder pattern is now nine names

**File**: polygram.js — `let transcribeVoiceAttachments = null;`
(449), `let downloadAttachments = null;` (453), `let buildSdkOptions
= null;` (560), `let makeCanUseTool = null;` (1076), `let
handleApprovalCallback = null;` (1077), `let resolveApprovalWaiter =
null;` (1078), `let startApprovalSweeper = null;` (1079). Plus
**implicit globals** (sloppy mode!) for `autosteer`,
`dispatchSlashCommand`, `handleConfigCallback`, `handleAbortIfRequested`
(no `let` declaration; assigned in main() at lines 2556–2575).

**Why this is HIGH not MEDIUM**: polygram.js does NOT enable `'use
strict'`. So when main() does `dispatchSlashCommand =
createSlashCommands(...)` without a prior declaration, JavaScript
silently creates a property on `globalThis`. This is the classic
sloppy-mode footgun — typo `dispatchSlasCommand` in main() and a
typo `dispatchSlashCommand` in handleMessage and the bug never
surfaces (both end up as separate globals).

In addition, the let-placeholder pattern is the structural enabler
of HIGH-1: factories run early, read null, capture null. If the
placeholders weren't there, the factories couldn't run early — they'd
have to be wired after the deps exist, which is exactly the fix.

**Recommendation**: pair with HIGH-1's fix (c). Replace the seven
let-null placeholders + four implicit-global assignments with `const
X = createX({ ... })` calls inside main(), where `pm` and `bot` are
already in scope. handleMessage and dispatchHandleMessage reference
these via closure capture from main() (which they already do for
`config`, `db`, `tg`).

The alternative (keep placeholders, only fix HIGH-1's pm/bot capture)
leaves the implicit-global hazard. Ship with `'use strict';` at the
top of polygram.js — that catches future typo-creates-global bugs
and forces `let dispatchSlashCommand = null;` declarations to be
explicit. Single line change, zero behavior change. Strongly
recommended for v0.9.0.

### 🟧 HIGH-3 — Hidden wiring-order dependency: makeCanUseTool → buildSdkOptions → ProcessManagerSdk

**File**: polygram.js:2531–2576

The block at lines 2531–2576 encodes a non-obvious chain:

```
createApprovals → emits makeCanUseTool
   ↓
createBuildSdkOptions({ makeCanUseTool, ... }) → captures makeCanUseTool
   ↓
new ProcessManagerSdk({ spawnFn: buildSdkOptions, ...sdkCallbacks })
   ↓
pm = sdkPmInstance
```

`createBuildSdkOptions` destructures `makeCanUseTool` by VALUE — same
class as HIGH-1. Today this works because `createApprovals` runs
FIRST (line 2536) before `createBuildSdkOptions` (line 2540), so
`makeCanUseTool` is non-null at capture time. The user explicitly
called this reordering out as something they had to do.

**The risk**: there's no comment in main() saying "approvals MUST
wire before buildSdkOptions because makeCanUseTool needs to be
non-null at destructure." A future contributor moving the
`createApprovals` block (e.g., to group all chat-callback wiring
together) would re-introduce the null-capture bug for buildSdkOptions
specifically. This is the same defect class as HIGH-1, just hidden
inside the wiring block instead of between blocks.

**Other hidden dependencies in main()**:

- `pm` (line 2576) depends on `buildSdkOptions` (line 2540) ✓ correct order
- `pm` (line 2576) depends on `sdkCallbacks` (line 2510) ✓ correct order
- `bot` (line 2602) depends on nothing in the factory block ✓
- `sdkCallbacks` captures `bot` at line 2510 — bot is null then →
  HIGH-1 finding for the `tg(bot, ...)` calls inside callbacks.js
- `dispatchSlashCommand` (line 2569) needs `pairings` (line 2456) ✓
  correct order
- `handleAbortIfRequested` needs `markSessionAborted` /
  `clearAutosteeredReactions` — these are top-level functions
  (lines 552, 676) that close over `let pm` / `bot` at MODULE scope,
  not destructured — so they DO see updated values ✓
- `dispatchSlashCommand` needs `getOrSpawnForChat` (line 576) which
  closes over `let pm` at module scope ✓ — but the `pm` parameter
  passed to `createSlashCommands` is null-captured (HIGH-1)

**Recommendation** (folds into HIGH-1's fix-(b) recommendation): use
accessor functions for cross-factory deps where capture-by-value
matters. For static-after-boot values (config, botName), direct-pass
is fine. For "values reassigned during boot but stable after"
(pm, bot, makeCanUseTool), use `getX: () => x`.

Add a header comment to the wiring block:

```js
// Boot wiring order constraints:
//   1. approvals → buildSdkOptions (makeCanUseTool dep)
//   2. buildSdkOptions → ProcessManagerSdk (spawnFn dep)
//   3. ProcessManagerSdk → bot (createBot doesn't depend on pm,
//      but every handler that uses bot OR pm must wire AFTER both
//      are assigned — see HIGH-1 fix in v3 review)
```

## MEDIUM (v3 NEW)

### MEDIUM-1 — handleMessage extraction: stop here

**File**: polygram.js:1102–1933 (~830 LOC after the slash/autosteer
extractions)

The user asked: "Should `handleMessage` be extracted next, or is
the cost/benefit poor?"

**Recommendation: stop**. The cost/benefit is poor, and the residual
shape is right.

The residual handleMessage body, post-extraction, is FIVE pipeline
stages plus their error handling:

1. **Inbound bookkeeping** (lines 1102–1170): set handler_status to
   'dispatched', set up `markReplied` + `sendReply` closures, parse
   text + thread_id + bot config. ~70 LOC.
2. **Slash dispatch** (1171–1185): one call to `dispatchSlashCommand`,
   plus the `/model | /config | /effort` ad-hoc routing for inline-
   keyboard cards (which can't go through the slash-commands handler
   because it needs `formatConfigInfoText` + `buildConfigKeyboard`
   from polygram.js scope). ~15 LOC.
3. **Attachment + voice** (1186–1280): pull persisted attachment
   rows, fall back to in-memory attachments for replays, run
   `downloadAttachments`, then `transcribeVoiceAttachments`. ~95
   LOC.
4. **Autosteer attempt** (1281–1500): build the prompt with
   `formatPrompt` (which closes over polygram-scope helpers like
   `resolveReplyTo`, `buildHistoryBlock`), then call
   `autosteer.tryAutosteer`. Returns early on autosteer match. ~220
   LOC including the prompt-build and history preload.
5. **Pm.send + streamer/reactor wiring** (1501–1933): get-or-spawn,
   build streamer + reactor + abortGrace, call `pm.send`, await
   the result, finalize/error/cleanup. ~430 LOC.

Stages 1–4 are integration glue. Stage 5 IS the LLM-turn pipeline
— the genuine business logic of "what happens when a user sends a
non-slash message." Extracting stage 5 as `lib/orchestrator/turn.js`
sounds appealing but the dep list would be 30+ entries (reactor,
streamer, abortGrace, autosteeredRefs, pm, db, dbWrite, config, tg,
bot, BOT_NAME, logEvent, classifyToolName, isTransientHttpError,
classifyError, errorReplyText, queueWarnThreshold, deliverReplies,
markSessionAborted, isSessionRecentlyAborted, attemptAutoResume,
clearAutosteeredReactions, ...). The factory wrapper would be the
biggest module in the codebase by dep count, and the factory would
contain its own 600-line closure.

**The honest framing**: handleMessage is the integration point where
all the leaf concerns merge. After leaf extractions, it's not
"orchestrator + helpers in one file" — it's "orchestrator only,
helpers extracted." That's the right shape.

**Counter-argument (weakly held)**: stage 5 could become a class
`Turn` whose instance per-message holds streamer/reactor/sourceMsgId
state and whose `run()` method drives the pipeline. Class-shaped
better matches the per-turn lifecycle. But: the existing functional
shape works, all tests pass, and the conversion is a v0.10.0
refactor, not a v0.9.0 cleanup task.

**Decision**: lock the extraction strategy at "leaf concerns only"
and document in plan v9 / decisions doc that the orchestrator core
stays in polygram.js by design.

### MEDIUM-2 — `lib/handlers/` semantic boundary

**Question raised**: "is `handlers/` just a dumping ground for
'extracted from polygram.js' files?"

**Reading**: there IS a coherent boundary, but it's not named in
the directory README (which doesn't exist). The boundary is:

- `lib/sdk/` = code that `ProcessManagerSdk`'s constructor needs
  (its lifecycle callbacks, its spawn factory, the pm itself).
  Nothing in lib/sdk/ is called outside of the SDK pm wiring.
- `lib/handlers/` = code called from the polygram entry-points that
  AREN'T pm-internal: `handleMessage` (slash, autosteer, voice,
  download, abort) and `bot.on('callback_query')` (approvals,
  config-callback). These are response handlers for user-driven
  events, not for SDK-driven events.

The split is **directional** (lib/handlers/ → lib/telegram/, lib/db/,
lib/error/, lib root primitives; lib/sdk/ → lib/telegram/, lib/error/,
lib/agents/, lib root primitives) and there are no cross-imports
between handlers/ and sdk/. ✓ correct layering.

**Honest gap**: a future contributor reading `lib/handlers/` cold
won't immediately see this distinction. The 7 files in there have
quite different shapes (approvals.js is 320 LOC + holds state in
`approvalWaiters`; abort.js is 88 LOC stateless predicate). The
naming is by domain ("voice", "download", "approvals") which works
but obscures the runtime-coupling story.

**If reorganizing from scratch**, alternative layout:

```
lib/orchestrator/    ← user-event handlers (callback_query, message)
  approvals.js       ← was lib/handlers/approvals.js
```

**But** the current `lib/handlers/` is FINE. The reorganization above

README.md` and leave the layout alone.

**Recommendation**: add a 5-line comment block at the top of each
of the 7 files (most already have one) explicitly identifying
"called from handleMessage" vs "called from callback_query handler"
— that surfaces the runtime-coupling story without renaming files.
abort.js, autosteer.js, voice.js, download.js, slash-commands.js
are message-path. config-callback.js, approvals.js are callback-
query path (mostly — approvals.js's `makeCanUseTool` is also called
from buildSdkOptions, so it's BOTH paths; the file's docstring
should say so).

### MEDIUM-3 — `let X = null` placeholders + cross-handler closure references

**File**: polygram.js (referenced in HIGH-2)

Beyond the implicit-globals point in HIGH-2, the let-placeholder
pattern has a subtler concern: handlers reference each other through
the let-bindings, not through the factory deps.

Example: `handleMessage` at line 1182 calls `dispatchSlashCommand`
(implicit global from line 2569). It does NOT receive
`dispatchSlashCommand` as a parameter or capture it through a
factory dep. Same for `autosteer.willAutosteer`, `autosteer.tryAutosteer`,
`handleAbortIfRequested`, `transcribeVoiceAttachments`,
`downloadAttachments`. handleMessage's lexical scope includes all
these names by virtue of being a top-level function in polygram.js.

This works because `handleMessage` is itself defined in polygram.js
(not extracted). If `handleMessage` were extracted, it would need
EVERY handler passed as a dep — 11+ entries. The let-binding pattern
thus locks `handleMessage` IN polygram.js — which is fine
(MEDIUM-1's call: don't extract it). But it does mean the
"placeholder pattern as temporal-coupling debt" framing from the
v2 simplicity review is partially backwards: the placeholder pattern
is what KEEPS handleMessage's dep list manageable. Eliminate the
placeholders (HIGH-2 fix-(c)) and you have to either (a) move
handleMessage inside main() too (massive function-in-function), or
(b) have handleMessage itself become a factory `createHandleMessage(deps)`
that takes 11+ handler refs (defeats MEDIUM-1's stay-in-polygram
recommendation).

**Resolution**: HIGH-2 fix-(c) has a nuance — it doesn't eliminate
the placeholder pattern, it just MOVES the assignment under
`'use strict'` AND uses accessors-not-values for the boot-time-mutated
ones. Still need module-level let-bindings; they're just declared
explicitly + read defensively.

So the recommended approach reverses my v2 reading:

```js
// At module scope (polygram.js top):
'use strict';
let pm = null;
let bot = null;
let dispatchSlashCommand = null;   // ← explicit let, was implicit global
let handleConfigCallback = null;   // ← explicit let
let handleAbortIfRequested = null; // ← explicit let
let autosteer = null;              // ← explicit let
let transcribeVoiceAttachments = null;
let downloadAttachments = null;
let buildSdkOptions = null;
// ... etc (already declared)

// Factory accessors for cross-boot capture (HIGH-1 fix):
const getPm = () => pm;
const getBot = () => bot;

// In main(), the wiring block stays where it is; factories take
// getPm/getBot for delayed reads:
handleAbortIfRequested = createHandleAbort({
  getPm, getBot, tg, logEvent, isAbortRequest,
  markSessionAborted, clearAutosteeredReactions, getSessionKey,
  botName: BOT_NAME, logger: console,
});
```

Combined patch is ~30 LOC. Net result: HIGH-1, HIGH-2, HIGH-3 all
addressed in one pass.

## LOW (v3 NEW)

### LOW-1 — `dispatchHandleMessage` still inlined in polygram.js (2916 LOC body)

**File**: polygram.js:777–937 (162 LOC)

This is a peer of `handleMessage` — wraps it with retry + auto-
resume + reactor lifecycle. It has the SAME closure-over-handlers
characteristic and would extract with the same dep-list pain as
handleMessage. v3 recommendation: leave it in polygram.js for the
same reasons as MEDIUM-1.

### LOW-2 — `createBot` (lines 1967–2299, 333 LOC) is a candidate for extraction

**File**: polygram.js:1967–2299

`createBot(token)` builds the grammy Bot and registers
`bot.on('callback_query')` + `bot.on('message')` handlers. This
function IS extractable as a factory:

```js
// lib/bot/setup.js
function createBotFactory({ config, BOT_NAME, ... }) {
  return function createBot(token) { ... };
}
```

But the dep list is 30+ entries (every handler, every state-machine
helper) and the function is essentially the registration of polygram-
scope handlers — moving it doesn't decouple anything, just relocates
333 LOC. **Don't extract**, same reasoning as MEDIUM-1.

If you DO extract: the factory boundary becomes a registration table:
`createBot({ token, handlers: { onCallback, onMessage }, ...other })`
where `handlers` is an object of pre-bound async functions. That
DOES decouple but requires more pre-binding in main(). Probably v0.10.0
work.

### LOW-3 — Approvals.js holds in-memory state (`approvalWaiters` Map)

**File**: lib/handlers/approvals.js:58 — `const approvalWaiters =
new Map();`

Every other extracted handler is stateless (closes over runtime deps,
all per-call state lives on the Telegram message / SDK callback).
Approvals.js holds a per-factory-instance `approvalWaiters` Map.

This is **fine** — approvalWaiters is intrinsic to the approval
flow's promise-resolver pattern, can't move outside the factory
without inventing a new abstraction. But it's worth noting:
approvals.js is the only handler that's NOT pure orchestration over
shared state. If multiple `createApprovals(...)` calls happened
(they don't in production; main() calls it once), each would have
its own Map.

**Recommendation**: zero action. Document in approvals.js header
that the factory is single-instance by contract (one polygram boot
= one approvals instance), and that the in-memory waiters Map is
appropriate state-scope. 1-line comment addition.

### LOW-4 — sdk-callbacks.js's bot null-check is one of three call sites; the other two will fail

**File**: lib/sdk/callbacks.js:126–129

The autonomous-wakeup callback has `if (!bot) { logger.error(...);
return; }` defensive check, presumably added when v2 LOW-4's "bot
is null at construction" surfaced for the early-firing autonomous-
wakeup case. But two other callbacks in the same file call `tg(bot,
...)` without the guard:

- Line 87: subagent-announce in `onToolUse`
- Line 201: compact-boundary in `onCompactBoundary`

These will fail the same way IF they fire before `bot = createBot()`
(line 2602). In practice they probably don't fire pre-bot — the
SDK pm doesn't emit subagent-announce or compact-boundary during
its own constructor. But the asymmetry is visible: one callback is
defensive, two aren't.

**Resolution**: HIGH-1's fix-(b) accessor approach makes this moot
(bot is read fresh per call). If keeping direct-pass, add the same
`if (!bot)` guard to the other two callbacks for consistency.

### LOW-5 — Implicit fan-out in slash-commands.js dispatch

**File**: lib/handlers/slash-commands.js (290 LOC)

The slash-commands handler is one factory that dispatches 11
commands inline as if-branches:

```js
if (text === '/context') { ... }
if (text === '/compact') { ... }
if (text.startsWith('/model')) { ... }
// ...
```

v2 HIGH-1 recommended one-file-per-command (`lib/commands/<name>.js`)
with a Map dispatch. The current monolithic shape is fine for 11
commands but starts to hurt the moment a new command lands AND
needs >50 LOC. Watch this — if `/agent`, `/transcript`, `/scope`,
or another command lands in 0.10.x, that's the trigger to split.

**No action** for 0.9.0.
