# 0.13 — Turn-wedge auto-recovery (kill the "⏱ ran past its time cap" apology)

> **Status: v1 auto-recovery design REJECTED by 4-persona review (2026-06-14). Revised
> to characterize-first (see "Review outcome" below).**
> **Severity: top user-reported pain** (Ivan, 2026-06-14: "most annoying problem now").
> Recurring `turn-timeout` → *"⏱ This one ran past its time cap with no reply. Resend if…"*
> across Shumabit@UMI threads, ~1/day.

## Review outcome (2026-06-14) — full auto-recovery rejected; characterize first

A code-grounded 4-persona review (feasibility, adversarial, coherence, scope) unanimously
rejected the v1 auto-recovery design below. Fatal findings:
1. **`resetSession()` is a full TEARDOWN, not a respawn** (`cli-process.js:3224` →
   `closed=true`, kills tmux, closes bridge, `pm` deletes the proc). Re-dispatch is then a
   **~11 s cold-spawn that LOSES the resumed transcript/context** — not "clear session id."
2. **The probe-busy gate is DEAD CODE.** `probeBusyState().busy` reads the *same*
   `STREAMING_HINT_RE` the pane heartbeat already gates on every 5 s (`3571` vs `2345`).
   For an idle ceiling to fire at all, that hint was absent the whole window — so the probe
   is ~never busy at kill-time. The gate reduces to "always reset+redispatch on ceiling,"
   killing slow-but-legit no-hint turns. Only the `backgroundShell` axis is real (and it's
   weaker than the abort path's dual-probe — TOCTOU).
3. **Double-answer is unresolved** either way: the `interrupt+resume` variant fully
   double-answers (old turn's late reply + recovery reply); the `resetSession` variant only
   avoids it by *accidentally* nuking the bridge (best-effort `killSession`).
4. **90 s wedge-detector = false-positive factory** for legit slow tool/MCP turns; bad
   asymmetry for a 1/day event.
5. **`pending._userMsgPayload` is a wire envelope, not a grammy `msg`** — must reconstruct
   from the DB by `msg_id` (like boot-replay) to feed `redeliverAsFreshTurn`/`shouldHandle`.
   (Good news: `redeliverAsFreshTurn` exists, is reusable, and is auth-gated.)

**Consensus revised plan (proportionate to ~1/day + an UNCHARACTERIZED upstream wedge):**
- **v1 (ship now, ~5 lines, zero risk): characterize.** Add `probeBusyState().paneTail`
  to the `turn-timeout` event so we capture WHAT claude is stuck in at wedge time. Soak
  ~1 week. Optionally soften the apology copy.
- **v2 (after data): targeted fix.** If the paneTail data shows wedges are one specific
  upstream state (a stuck MCP tool, an unrecognized prompt, a claude-version bug), fix THAT
  — likely far smaller than recovery infra. Only build re-dispatch/recovery if the data
  shows it's needed, and reconstruct the msg from the DB, interrupt-before-redispatch to
  kill the double-answer, and drop the dead probe-busy gate.

The original v1 design is preserved below for context (do not build as-is).

---

## Symptom & frequency
The bot works on a turn, then goes silent; after a long ceiling (10 min idle / 30 min
absolute / 60 min for chats with a high `maxTurn`) polygram kills the turn and posts an
apology asking the user to resend. Production (shumabit, 3 d): **6 turn-timeouts**
(`reason=idle` ×3, `reason=absolute` ×3); apology messages ~1/day. Correlated:
`cli-hook-stream-stalled` 11×, `bridge-disconnected` 7×, `startup-auto-retry` 6×.

## Root cause (traced)
Two activity signals feed the finalizer ladder's idle ceiling (`_noteActivity` resets it):
1. **Hook stream** (claude → ndjson tail → `_handleHookEvent`). **Dies mid-turn ~3-4×/day**
   (`cli-hook-stream-stalled`) — not tied to compaction/resume/bridge; looks like an
   upstream claude-CLI hook-emission death.
2. **Pane heartbeat** (`_pollMidTurnDialogs`, 5 s pong tick): if the TUI shows
   `STREAMING_HINT_RE` ("esc to interrupt") it calls `_noteActivity('pane-thinking')`.
   **This already keeps a *streaming* claude alive even when hooks die** (cli-process.js
   3571-3577).

So a turn only hits the ceiling when **BOTH** are quiet for the whole window —
i.e. claude shows no "esc to interrupt" AND fires no hooks AND delivers no reply.
That is a **genuine wedge** (claude truly stopped) or claude stuck at a prompt the
catalog doesn't recognize. **Detection is already good; the gap is the RESPONSE.**

`fireTimeout(reason)` (cli-process.js ~2071) on a **zero-reply** turn: deletes the
pending, emits `turn-timeout`, polygram.js posts the apology, rejects `TURN_TIMEOUT`.
It does **not** (a) re-probe liveness at kill-time, nor (b) attempt recovery. ~1/3 of
cases are borderline (a late reply arrives via `cli-late-reply-correlated`, salvaged);
~2/3 are genuine (nothing ever comes → the apology).

## Design — auto-recover instead of apologize
On a ceiling firing for a **zero-reply, not-consumed-acked** turn:

1. **Confirm-not-busy gate (belt-and-suspenders).** `await probeBusyState()`. If
   `busy` (streaming) OR `backgroundShell` → claude IS alive → **reschedule the idle
   ceiling** (treat as activity), do NOT kill. Eliminates any premature kill where the
   heartbeat missed a tick. (Skip for `reason=absolute` — that's the hard runaway cap.)
2. **Genuine wedge → auto-recover (bounded).** If not busy + zero replies + recovery
   budget remains (`wedgeRecoveryMax=1` per inbound msg):
   - **Reset the wedged session** so a re-dispatch doesn't land in a hung claude:
     `resetSession()` (drains pendings, clears session id, respawns claude — already
     exists) OR a targeted interrupt+resume.
   - **Re-dispatch the user's original message** as a fresh turn (the prompt + context
     are on `pending._userMsgPayload`). Reuse the boot-replay / `redeliverAsFreshTurn`
     path, `_isReplay`-tagged, re-gated via `shouldHandle`.
   - Emit `cli-turn-wedge-recovered` for telemetry.
   - The user gets an **answer**, not an apology.
3. **Last-resort fallback.** If recovery is exhausted (budget spent, or the re-dispatch
   also wedges) → THEN the apology (so the user is never left in pure silence).

### Faster relief (optional, sign-off decision)
Today the user waits the full ceiling (10-60 min) before anything happens. Add a
**wedge detector** on the 5 s tick: if pendingTurns>0, zero replies, no "esc to
interrupt", no hooks, and no bridge tool-call in flight for `wedgeStallMs` (e.g. 90 s),
trigger the step-2 recovery *early* instead of waiting for the ceiling. Risk: a claude
genuinely busy in a no-hint state (slow MCP/network wait) — mitigated because the TUI
shows "esc to interrupt" during tool execution, so no-hint for 90 s is a strong wedge
signal. Conservative default; tunable.

## Why not "just lower the ceiling"
Lowering the ceiling makes the apology come faster but doesn't fix it — the user still
gets "resend yourself." Auto-recovery removes the apology entirely for the common case.

## Upstream angle (separate track)
The wedge itself (claude stops emitting hooks AND the streaming hint mid-turn) is a
**claude-CLI behavior**. Worth: (a) capturing the pane tail at wedge time
(`probeBusyState().paneTail`) into the event so we can characterize WHAT state claude is
stuck in; (b) testing whether a different pinned `claude` version wedges less; (c)
reporting upstream. polygram's auto-recovery is the safety net regardless.

## Risks / edge cases (for review to break)
- **Recovery loop:** bound to `wedgeRecoveryMax=1` per inbound msg; a re-dispatch that
  wedges again → apology, no further retry.
- **Double-answer:** if the wedged turn actually completes late (the salvage path) AFTER
  recovery re-dispatched → two answers. Must dedup (the re-dispatch + late-reply-correlation
  must not both deliver). This is the sharpest risk.
- **resetSession scope:** resetting kills ALL in-flight work for the session (other
  pendings) — but the single-active-cycle invariant means there's ~1 pending. Confirm.
- **Re-dispatch into still-wedged claude:** must reset/respawn BEFORE re-dispatch, else
  the retry wedges identically.
- **Background shell:** a detached `run_in_background` Bash = legitimately busy → the
  `backgroundShell` gate must prevent recovery (don't kill a turn whose bg job is running).
- **Cost:** one `captureWide` per ceiling (rare) + per wedge-detector escalation; bounded.
- **Async fireTimeout:** adding `await probeBusyState()` makes the ceiling callback async —
  the pending could resolve during the await; re-check `pendingTurns.has(turnId)` after.

## Test plan (TDD)
- `cli-process-finalizer-ladder.test.js` / a new `cli-process-wedge-recovery.test.js`:
  1. ceiling fires, probe returns busy → turn NOT killed, ceiling rescheduled (RED→GREEN).
  2. ceiling fires, probe not-busy, zero replies, budget>0 → resetSession + re-dispatch
     called once; `cli-turn-wedge-recovered` emitted; NO apology.
  3. recovery budget exhausted → apology fallback (preserve current behavior).
  4. double-answer guard: late completion after recovery does not double-deliver.
  5. background-shell present → no recovery (turn treated as busy).
- Real-claude E2E: simulate a wedge (kill the hook stream mid-turn) → answer still arrives.

## Open decisions for sign-off
1. **Recovery aggressiveness:** ceiling-only (safe) vs the 90 s wedge-detector (faster, riskier).
2. **`wedgeRecoveryMax`:** 1 (recommended) vs 2.
3. **resetSession vs interrupt+resume** for clearing the wedge — which is cleaner/cheaper.
4. **Scope:** channels/CLI only (where the pain is); SDK backend later.

## Rollout
shumorobot/shumabit first → umi-assistant last. Soak metric: `turn-timeout` (zero-reply)
rate ↓ toward 0; `cli-turn-wedge-recovered` catching them; zero double-answer reports;
apology messages ↓.
