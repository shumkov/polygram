# 0.12.0 — Post-turn edit re-delivery (spec)

> **Revised twice (2026-06-10) — two review rounds folded in.** Round 1 found the original
> over-built (full-re-delivery + most-recent guard + old→new quoting + custom marker + debounce);
> we cut it to "an edit is just a message." Round 2 found the cut went one step too far — relying
> on "claude reconciles from reply_to alone" silently fails (by turn time the row is overwritten,
> so reply_to shows the *new* text — no before/after) and the self-reply_to broke the gate. This
> revision keeps the simple model but (a) conveys the edit by putting the **captured old text into
> the reply_to**, and (b) **gates on the real edited message, not the synthetic.**

**Status:** revised design — ready to build (TDD per the test plan).
**Parent:** the mid-turn edit-correction injector (`lib/handlers/edit-correction.js`, shipped 0.9.0).
**Motivating data (shumabit, 14 days):** 101 `message-edited` events, only 9 reached claude.
**~91% of edits are silently dropped** post-turn. Editing is normal, frequent (operator + UMI
partners); a post-turn edit currently does nothing.

---

## The model: an edit is just a message

| When you edit | What happens |
|---|---|
| **Mid-turn** (claude is processing) | feed it into the running turn — **unchanged**, the existing `maybeInjectEditCorrection` injector. |
| **Post-turn** (claude is idle) | re-dispatch the edited message as a **new turn**, replying to the edited message *with its old text* so claude sees the change, gated like any normal message. |

Mutually exclusive (`inFlight` vs not), so `bot.on('edited_message')` branches: `inFlight` →
injector; else → post-turn re-dispatch.

## Design

### 1. Convey the edit: reply_to carries the OLD text (round-2 fix)

The bet "claude reconciles a re-posted edit on its own, like the CLI's `^`-edit-resubmit" only
holds if claude is given the *change*. The CLI shows the edit in conversation position; we have no
position. And replying to the edited message does **not** supply it: by the time the re-dispatched
turn runs, `recordInbound` has already overwritten the row with the *new* text
(`db.js:94 text=excluded.text`), so `buildReplyToBlock`'s db-row fallback would quote the new text —
claude sees the new text twice and has zero signal anything changed.

So the synthetic turn is built as a reply whose `reply_to_message` carries the **captured old
text** (we read it anyway for the changed-guard, §3) and the editor's identity:

```
synthetic.reply_to_message = { message_id: N, from: <editor>, text: <OLD text>, date: <orig> }
synthetic.text             = <NEW text>
```

`resolveReplyTo` then takes the `telegram` branch → `<reply_to msg_id="N" user="…">OLD</reply_to>`
+ the body `<untrusted-input>NEW</untrusted-input>`. claude sees *"replying to my earlier message
that said OLD — it now says NEW"* and reconciles, exactly the before/after the CLI gives it. No
hand-built `[edit]` string; all user text is `xmlEscape`d by `buildPrompt` (closes the round-1
injection vector). A real-claude check still validates reconcile quality, but the design now
*provides* the signal rather than hoping claude infers it from nothing.

### 2. Gate on the REAL edited message, not the synthetic (round-2 fix)

Round 2: routing the synthetic (a reply to the user's own message, no real `from`) through
`shouldHandle` makes `repliesToOtherUser` true → kills the paired-user bypass → a paired operator
editing an un-mentioned message in a mention-gated group is **dropped**, *stricter* than a fresh
message. Fix: make the **gate decision** on the **edited message's own properties** (its current
text + real `from` + any real mention), via the normal pre-dispatch gate
(`dispatchRegularMessage`, `polygram.js:1841` — which also carries abort/admin/`/rewind`/question
gating, not just bare `shouldHandle`). Only if that passes do we dispatch the synthetic turn (whose
reply_to is for claude's context only and is **not** re-gated). "Would this message, as it now
reads, be handled if freshly sent?" — gate answers that on the real message; framing is separate.

### 3. The one guard — did the text actually change? (HARD requirement)

Telegram fires `edited_message` for non-content changes too (link-preview load; the prod data's
batch "edits" of msgs 2246–2248). Skip re-dispatch when text/caption is unchanged. This needs the
old value, and the handler **must** read it before the overwrite:

> **HARD:** read `db.getMessage(chatId, msgId)` as the FIRST step of `bot.on('edited_message')`,
> **before** `recordInbound` (which runs at `polygram.js:2056` and overwrites text). A test must
> **fail loudly** if the read happens after `recordInbound` — otherwise the guard compares
> new-vs-new, never fires, and *every* metadata edit spawns a turn (100% noise).

The captured old text feeds both the changed-check (here) and the reply_to (§1). No old text is
ever logged (`logEvent` records `text_len` only, never content).

### 4. Synthetic identity + no self-trigger / no replay (round-2 fix)

The synthetic reuses the **edited message's `msg_id`** (reply threads under it; the on-edit
reaction lands on it) and is tagged like the autonomous-wakeup reconstructed message
(`_isReplay`/equivalent, `polygram.js:2701/2725`) so that `handleMessage`:
- does **not** create a new editable inbound row (no loop), and
- is **excluded from boot replay** — without the tag, the row sits at `handler_status='dispatched'`
  during the re-run, inside both the `isInboundLive` and `getReplayCandidates` windows, so a crash
  mid-re-run would replay the edit on reboot. The tag also suppresses the "couldn't process" error
  reply on failure.

### 5. Immediate acknowledgment + per-message interlock (round-2)

- **Acknowledge on receipt.** A silent edit produces no new bubble, so put a reaction (👀/✏️) on
  the edited message the instant the re-dispatch is queued — before the turn — so you (and group
  bystanders) see it registered, instead of silence until the reply lands (the rc.33 lesson). The
  reply then threads under that message.
- **Per-`(chatId,msgId)` in-flight interlock** (the abuse/rate posture, in place of a full
  rate-limiter): at most one re-dispatch per message in flight. A new edit of the *same* message
  while its re-dispatch is running folds via the mid-turn injector rather than spawning a second
  turn — which also caps the silent edit→turn→edit→turn loop security flagged.

## What we deliberately do NOT build

- **No "most-recent" guard / time-window** — unimplementable cleanly (no edit-time ordering in the
  schema) and unnecessary; editing an older message just replies to it.
- **No hand-built `[edit]` marker** — the reply_to-with-old-text (§1) is the signal.
- **No full rate-limiter / load-bearing debounce** — the per-message interlock (§5) covers the
  realistic loop; rapid edits of *different* messages produce successive turns, same as messages.
- **No acknowledge-only path** — operator decision: an edit is *acted on*, not merely acknowledged.

## Scope

**In:** both SDK and channels/cli backends (`dispatchRegularMessage`, backend-agnostic).
**Out:** attachment/caption-media re-download on edit (text/caption delta only); daemon-restart
durability (an edit arriving while the daemon is down is lost).

## Edge cases

- **Edit arrives exactly as the trigger turn ends** (`inFlight`→done): the mid-turn injector's
  `inFlight` read can win the race and then no-op. **Self-contained fall-through (do NOT depend on
  #14 shipping first):** if `maybeInjectEditCorrection` returns false because the turn already
  settled, fall through to the post-turn re-dispatch here. (Shares the *fix shape* with the
  autosteer-drop spec #14, but ships independently.)
- **Partner-facing UMI bots act on an edit** — acceptable: same capability as sending a new message
  (passes the same gate + approval flow, §2). Bystander signal = the on-edit reaction + reply
  threading; no special prefix (revisit if confusing).
- **Edit of a message older than the most-recent** — allowed; replies to that older message.
- **Metadata-only / unchanged text** — skipped (§3).
- **Edited to blank / media-only** — a real delta but no meaningful text to act on → skip (note:
  blanking to retract produces no turn; the on-edit reaction still fires so it's not silent).

## Test plan

Unit (`tests/handlers-edit-correction.test.js` / a post-turn-edit test, deterministic fakes):
1. Post-turn changed-text edit → re-dispatches via the normal path; the synthetic's `reply_to`
   carries the **OLD** text and the body carries the NEW text (the before/after signal).
2. **Ordering test (fails loud):** asserts `getMessage` is read before `recordInbound` — i.e. the
   captured old text differs from the post-upsert row; a wrong order fails this test.
3. No text change (metadata / same text) → no re-dispatch.
4. Mid-turn edit (`inFlight`) → existing injector, NOT the post-turn path.
5. **Gate on the real message:** a paired user editing an un-mentioned message in a mention-gated
   group → re-dispatched (NOT dropped); an edit that genuinely fails the gate (unpaired, no
   mention) → not re-dispatched.
6. Synthetic creates no new editable inbound row AND is excluded from boot replay (`_isReplay`);
   a second edit during the re-run folds via the injector, does not spawn a second turn.
7. Boundary: injector no-ops because the turn just settled → falls through to post-turn re-dispatch
   (self-contained).
8. On-edit reaction fires on receipt, before the reply.
9. `editCorrection === false` → neither path fires.

A real-claude check (gated E2E) validates that claude reconciles the old→new reply_to correctly.

## Resolved decisions (post-review, operator-signed-off 2026-06-10)

- **Act on edits** (new turn idle / fold mid-turn), not acknowledge-only.
- **Convey the edit via reply_to carrying the captured OLD text** (not a hand-built marker, not
  "claude infers from nothing"). Validate reconcile with a real-claude check.
- **Gate on the real edited message** via `dispatchRegularMessage`; the synthetic's reply_to is
  framing-only and not re-gated — fixes the paired-user drop.
- **Changed-guard reorder is a HARD requirement** with a fail-loud ordering test.
- **`_isReplay`-tag the synthetic** — no new editable row, excluded from boot replay.
- **On-edit acknowledgment reaction + per-message in-flight interlock** (the rate/abuse posture, no
  full limiter).
- **Boundary fall-through is self-contained** — ships without depending on #14.
- **No most-recent guard, no old→new prompt quoting beyond reply_to, no debounce.**
