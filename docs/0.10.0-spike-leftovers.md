## L1 — TUI banner returned as reply text  **[FIXED rc.16 — e431986]**

**Scenarios failing:** `baseline-tool-call`, `multiple-tools-sequential`

**Symptom:** When a tool-using primary turn is the FIRST send on a
fresh TUI session, `pm.send` sometimes returns the claude welcome
banner as `result.text`:

```
res.text = "▐▛███▜▌   Claude Code v2.1.142\n▝▜█████▛▘  Sonnet 4.6 …"
res.metrics.numToolUses = 0
```

The agent never actually invoked Bash; pm.send returned with the
banner before the agent finished startup + tool dispatch.

**Hypothesis:** capture-pane race wins before the JSONL emits the
agent's first assistant message. The capture-pane fallback extracts
the visible pane text — which during early startup is the banner.

**Why baseline-text scenarios DON'T hit it:** the agent's reply is
fast and short ("BASELINE", "SOLO"). JSONL emits the result event
before capture-pane idle detection times out, so JSONL wins the race
and the banner extraction never runs.

**Investigation steps:**
1. Confirm by adding a debug log to TmuxProcess.send showing which
   path won the Promise.race (`resolvedVia`).
2. If `resolvedVia === 'capture-pane'` for these failures, the
   fallback is firing.
3. Fix candidates:
   - Strip welcome banner text from `_extractTurnReply` output
     (regex match `▐▛███▜▌.*Claude Code v\d+\.\d+\.\d+`).
   - Or: only fall back to capture-pane AFTER the JSONL file has
     received at least one assistant event for this session.

**Verify with:**
```sh
node scripts/spikes/autosteer-tui-real.mjs baseline-tool-call
```

## L2 — Sequential turn 3+ returns empty text  **[FIXED rc.16 — 1a18d35]**

**Scenarios failing:** `three-sequential-sends`, `send-tool-send`,
`three-sends-no-await`, `four-sequential-mixed`

**Symptom:** in a TmuxProcess session that processes 3 or more
turns sequentially (back-to-back `pm.send` calls), turns 3 and
beyond sometimes return `result.text === ''`. Turns 1-2 are fine.

**Pattern across failing tests:**
- `three-sequential-sends`: turns 1+2 PASS, turn 3 returns empty.
- `send-tool-send`: turns 1 PASS, turn 2 (with tool) PASS, turn 3 empty.
- `three-sends-no-await`: sends 1+2 PASS in queue order, send 3 empty.
- `four-sequential-mixed`: turns 1+2 PASS, turns 3+4 empty.

**Hypothesis:** TmuxProcess.send's `_turnState` or streamer
accumulator isn't reset cleanly between turns, OR the JSONL tail
falls behind after several turns, OR the capture-pane fallback
extraction returns empty (no diff vs previous turn's captureAtStart).

**Investigation steps:**
1. Add per-turn debug logging in TmuxProcess.send showing
   `resolvedVia`, `_turnState.text` at result time, and the
   capture-pane diff content if the fallback wins.
2. Check if `_turnState.text` accumulator from turn N's
   assistant-chunk events is empty (JSONL parser issue?) or full
   (extraction issue?).
3. Likely candidates:
   - `_extractTurnReply` diff logic — turn N's captureAtStart might
     contain turn N-1's reply, so the diff strips the new reply.
   - Late JSONL writes — claude TUI buffers JSONL on long sessions.

**Verify with:**
```sh
node scripts/spikes/autosteer-tui-real.mjs three-sequential-sends
node scripts/spikes/autosteer-tui-real.mjs four-sequential-mixed
```

## L3 — Intermittent multi-autosteer (multi-2-rapid, multi-4-rapid)  **[FIXED rc.16 — 4ddf42b]**

**Scenarios failing INTERMITTENTLY:** `multi-2-rapid`, `multi-4-rapid`

**Symptom:** In isolation these pass. In the full 50-run batch
they sometimes fail with msgId=2201 (multi-2) or msgId=2x03
(multi-4) never receiving an `autosteer-resolution` event.

**Pattern:** the second-or-later msgId in a rapid-fire multi-
autosteer batch is occasionally orphaned. The JSONL event ordering
varies run-to-run because of model timing.

**Hypothesis:** when the TUI emits two USER events back-to-back
followed by ONE combined ASST reply, sometimes the assistant chunk
+ result arrives BEFORE the second USER event in the tail's
processing — meaning the second match never starts an
`_extraTurnState` because the flush already cleared it.

The rc.14.2 append-to-existing fix handles the case where the
second USER arrives BEFORE the result. The other ordering needs
a different fix: maybe a short grace period after a flush during
which new USER messages that match still-pending autosteers can
either trigger a new `_extraTurnState` OR retroactively get
attributed to the just-flushed one.

**Investigation steps:**
1. Capture multiple JSONL files from passing AND failing runs of
   multi-2-rapid. Compare event ordering.
2. Add a `_recentlyFlushedExtraTurn` slot that holds the last-
   flushed state for ~500ms. New user-message matches against
   pending → if no current state but recent matches the same
   reply text, attribute the late msgId to that flushed reply.
3. Or: post-flush, drain remaining `_pendingAutosteers` whose
   content appears in the just-flushed text by emitting a delayed
   extra-turn-reply.

**Verify with:**
```sh
# Run 5 times — at least 3 should pass post-fix.
for i in 1 2 3 4 5; do
  node scripts/spikes/autosteer-tui-real.mjs multi-2-rapid 2>&1 | tail -3
done
```

## L4 — Late-inject after primary already returned  **[FIXED rc.16 — cascaded from L2 (1a18d35)]**

**Scenario failing:** `autosteer-2s-after-primary`

**Symptom:** when `injectUserMessage` is called >1s after the
primary `pm.send` resolved (TmuxProcess is no longer in-flight),
`injectUserMessage` returns `false` — but the scenario's
invariants still check for events that don't fire.

**This is a TEST bug, not a polygram bug.** The scenario should
either (a) skip invariants when `injectUserMessage` returned false
or (b) ensure the primary turn is still in flight when injecting.

**Investigation:** read the test, adjust assertions to match the
inject return value.

**Verify with:**
```sh
node scripts/spikes/autosteer-tui-real.mjs autosteer-2s-after-primary
```

## Observability — query the events DB

When a leftover regresses in production, the observability events
make diagnosis cheap (no need to re-run the spike). Run on the
relevant `.polygram/<bot>.db`:

```sql
SELECT id, datetime(ts/1000,'unixepoch','localtime') AS t, kind,
       substr(detail_json, 1, 300) AS detail
FROM events
WHERE kind LIKE 'autosteer%'
   OR kind LIKE 'extra-turn%'
   OR kind = 'autonomous-wakeup-message'
   OR kind = 'tool-only-completion'
ORDER BY id DESC
LIMIT 30;
```

`autosteer-match-miss` events include head + tail snippets + lengths
of both the JSONL text and the pending content — read these to see
exactly where content matching failed.
