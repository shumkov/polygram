# Spec — Secret redaction in the messages DB (polygram 0.15.0)

Status: **IMPLEMENTED — reviewed (3 lenses, GO), tests green, ready to ship.** Sweep ships DISABLED + dryRun-default; enable is an explicit post-deploy step (§7).
Origin: users send secrets (tokens, passwords, keys) in chat; polygram stores them **plaintext** in the per-bot SQLite (`messages.text` + the `messages_fts` index). A DB leak / backup / a 4 GB-bloat-style copy then leaks every secret ever pasted. Operator ask: *detect + obfuscate them; "it should be a background cleanup process," not hot-path*; and *"tell the model to mark secrets as well"* (the model already reads every message — let it flag the fuzzy ones a regex can't).

## 1. Threat model + honest scope

**Goal: data-minimization.** Reduce how long user-supplied secrets persist in the long-lived, queryable, agent-readable message store, to bound the blast radius of a DB leak.

**NOT in scope (stated so we don't over-claim):**
- Claude's own session transcripts (`~/.claude/.../*.jsonl`) also contain the secret — separate store, not touched here.
- Telegram's servers have the original message — unrecoverable by us.
- Attachment *file contents* (only DB text columns are scanned).

Defense-in-depth on the DB, not complete secret erasure.

## 2. Two complementary mechanisms

The model already processes every message, so we use **both** a deterministic floor and a model-flag — they cover different secret shapes:

| | **A. Deterministic sweep** | **B. Agent-flagged marker** |
|---|---|---|
| Catches | KNOWN-SHAPE tokens (regex) | FUZZY / prose secrets ("my password is hunter2value") |
| Trigger | background (boot + interval) | the agent emits `[redact:<secret>]` in its reply, same turn |
| Coverage | whole table, unbounded, incremental | the chat the agent is replying in (last 200 inbound rows) |
| Default | **disabled**, dryRun-on | always on (agent-driven) |
| Why split | code for deterministic transforms (CLAUDE.md rule 5) | model only for the judgment call ("is this a secret?") |

Neither runs a *second* model pass — B reuses the reply the model already produced.

## 3. Prod data (shumabit.db, 2026-06-17)
12,204 non-empty messages. Detected: **JWT ×10** (all inbound), **kv-secret ×3 in 2 msgs**, **0** of every known-prefix rule. Implications: footprint tiny → backfill cheap; JWT-dominated (handled, MEDIUM tier); generic kv-secret FP-prone (`password: required`) → **flag-only, never auto-destroy**.

## 4. A — Deterministic sweep

### 4.1 Tiered detection (`lib/secret-detect.js`, pure, shared)
- **HIGH** (near-zero FP → auto-redact): `AKIA…`, `gh[pousr]_…`, `github_pat_…`, `sk-ant-…`, `sk-…`(OpenAI), `xox[baprs]-…`, `AIza…`, `sk_live_…`, `-----BEGIN … PRIVATE KEY-----`, tg-bot-token `\d{8,10}:[35]`, `Bearer …` (group-captured).
- **MEDIUM** (auto-redact): JWT `eyJ….eyJ….sig`.
- **LOW** (FLAG only): `(password|secret|api_key|access_token|client_secret)\s*[:=]\s*…` — recorded for review, never auto-destroyed in v1.

Group rules (`bearer`, `kv-secret`) carry the `d` (hasIndices) flag and splice the **exact capture-group span** via `m.indices` — not `indexOf`, which mislocated when the value also appears in the key (e.g. the literal `secret` in `client_secret=secret`). Falls back to `lastIndexOf` (value is at the tail) if indices are unavailable.

### 4.2 Redaction + audit
- HIGH+MEDIUM → replace just the matched substring with typed placeholder `‹redacted:<rule>›` (preserves context, never re-matches → idempotent). `messages_fts` re-indexes via the existing UPDATE trigger (migration 002) so the secret leaves the search index.
- **Audit** (`secret_redactions` table): `{chat_id, msg_id, rule, tier, length, sha256(secret), action, ts}` — **fingerprint, never the secret**.

### 4.3 Sweep engine (`lib/db/secret-sweep.js`, models events-retention pruneEvents)
- Boot + interval (config `defaults.secret_sweep:{enabled,dryRun,batchSize,maxPerRun,intervalMs}`); **enabled defaults false, dryRun defaults true**, 6 h interval.
- Incremental id-cursor + `messages.secret_scanned_at` high-water → no full re-scan; one-time backfill scans history once. One transaction per batch (atomic: redact + audit + stamp together — a crash leaves no half-state).
- Bounded by `batchSize`/`maxPerRun`. Returns `reachedCap` + `remaining` so a capped run is visibly partial.
- **dryRun caveat:** dryRun doesn't stamp, so each interval run re-scans from id=0 → on a table larger than `maxPerRun` a dry-run **never previews rows past the first `maxPerRun`**. The run logs `HIT maxPerRun cap — N row(s) still unscanned`; the review must set `maxPerRun` above the row count (§7).
- Logging (operator's explicit ask): every run with `scanned>0` prints `[secret-sweep] (trigger) scanned N msg, WIPED M secret(s) in K msg, flagged F {ruleCounts}` + `secret-sweep` event; failures print `[secret-sweep] FAILED` + `secret-sweep-failed` event.

## 5. B — Agent-flagged marker `[redact:<secret>]`

The agent (prompt instruction in `lib/prompt.js`) copies a credential it sees in the user's message into `[redact:<secret>]`. Then, uniformly for SDK + CLI:
- **Strip from the reply** so it never reaches the chat: `parseResponse` extracts `redactions[]` + strips the tag (turn-end); `stripInlineTags` strips it at **stream-chunk time**, including a **trailing unclosed `[redact:…`** so a secret forming across a chunk boundary never flashes (the colon-anchored incomplete-tag guard). *Security invariant, test-pinned: for every prefix of a streamed `…[redact:SECRET]` buffer, the render contains no secret byte.*
- **Wipe the stored inbound** via `db.redactSecretInChat()`: literal `split/join` (no regex injection), scoped to `direction='in'` + chat (+ thread), last **200** inbound rows, audited by fingerprint, FTS re-indexes via the trigger.

Three firing paths (mutually exclusive, no double-redaction):
1. normal streamed reply → `handleMessage` (`polygram.js`, after `parseResponse`);
2. CLI-channels reply (short-circuits before #1 at `alreadyDelivered`) → the dispatcher's `deliverAgent`;
3. autonomous-wakeup → `lib/sdk/callbacks.js` → `process-agent-reply.js`.
All three call the module-level `redactInbound` helper. **Fail-loud:** if the agent flagged a secret but 0 rows matched (paraphrased value / older than the 200-row window / lived in an attachment), they log + emit `secret-redact-requested-no-match` — never a silent non-wipe.

## 6. Review outcomes (3 lenses — all GO)
- **Correctness:** kv `indexOf` mis-position (latent until LOW redaction) — **fixed** (`d`-flag indices). limit=50 silent miss — **fixed** (bumped to 200 + fail-loud no-match log). No double-firing across the 3 paths (verified).

User-typed `[redact:]` can't self-trigger (parse runs on agent output only); `redactInbound` is hard-scoped to the current chat.

## 7. Rollout (enable procedure — UMI VPS, per-bot)
The migration (014) runs on deploy and is metadata-only safe; a plain 0.15.0 deploy **mutates nothing** (sweep disabled). To enable the sweep on a bot:
1. **Back up** `shumabit.db` (+ `-wal`, `-shm`) — the sweep is destructive-in-place; backup is the only undo.
2. Set `defaults.secret_sweep.enabled=true` (dryRun stays default-on). For the **review pass set `maxPerRun` above the row count** (~13000) so the dry-run previews the whole table, not just the first 5000.
3. Restart; read the `[secret-sweep] DRY-RUN … scanned N, WIPED M, flagged F` log (expect ~10 JWT + a couple kv-flagged). Confirm no `HIT maxPerRun cap`.
4. Flip `dryRun=false`; restart; confirm the WIPED count + audit rows; spot-check placeholders.

## 9. Known limitations (documented, not bugs)
- Sweep is a **floor**: regex misses AWS secret-access-key (40-char), generic high-entropy blobs, delimiter-less passwords — those depend on the agent's `[redact:]`.
- Agent marker can't carry a secret containing `]`; `[redact:` written as benign trailing prose mid-chunk is stripped (the never-flash trade-off).
- kv-secret (LOW) over-captures trailing bytes in URLs — harmless (flag-only).
- `secret_redactions` has no retention (bounded: one audit per scan; first backfill may insert a batch of flagged rows).
- Follow-ups: LLM-verify LOW before redacting; sweep `events.detail_json`; sweep agent session JSONLs.
