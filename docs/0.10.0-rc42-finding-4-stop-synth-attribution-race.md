# #4 — Late Stop hook attributes synth settle to the wrong turn

> **Status: RESEARCH (rc.42).** Surfaced by the multi-agent code review
> of rc.40/rc.41 (adversarial reviewer adv-1, corroborated by
> correctness #5, testing T3, agent-native AN-2). 4-way cross-reviewer
> agreement, confidence anchor 100.
>
> Severity: **P1 silent wrong-reply**, but trigger conditions are
> narrow enough that the production blast radius isn't yet quantified.
> rc.42 ships defensive scaffolding (#6 `_stopSynthScheduled` guard +
> timer cleanup, #15 `stop-hook-resolved` event) so the race becomes
> observable in production. THIS DOC scopes the actual fix for rc.43
> once we have soak data on how often the race window actually opens.

## The race

The H4 Stop synth schedules a `settleResult` after `stopGraceMs`
(2 s default) against whichever primary turn is in
`_activeGroup.turns` AT HOOK-EVENT TIME. If polygram's turn rotation
happens between Stop arrival and synth-firing, the timer's captured
`primary` reference can be a turn that's already been retired —
worse, it can be a SECOND turn that's now the active primary.

### Exact failure path

```
t=0     Turn N is in flight. User has just sent "thanks" (next message).
t=10ms  JSONL `result` for Turn N lands → _flushActiveGroup →
        Turn N.settleResult(jsonl_event) → _awaitSettle returns
        {kind:'jsonl'} → _runTurn finishes Turn N → _finishTurn drains.

t=15ms  Turn N+1 (the "thanks" message) is the new pendingQueue head.
        _runTurn(N+1) starts → pastes → JSONL `user-message` for N+1
        lands → Turn N+1 enters _activeGroup as primary.

t=80ms  Stop hook for TURN N finally arrives via LogTail (50-300 ms
        is typical hook-tail latency observed in spike data).
        _handleHookEvent runs.
        `primary = activeGroup.turns.find(kind==='primary')` returns
        TURN N+1 (because Turn N is gone, Turn N+1 is the current
        primary).
        Code schedules `setTimeout(() => primary.settleResult(synth),
        stopGraceMs)` where `synth.text = primary.text ||
        ev.lastAssistantMessage` and `ev.lastAssistantMessage` is
        TURN N's final text.

t=2080  setTimeout fires. Turn N+1's primary.text is still '' (it's
        a short "thanks" turn the model hasn't streamed for yet —
        maybe still thinking, maybe decided to no-op).
        `synth.text = '' || ev.lastAssistantMessage` = TURN N's text.
        Turn N+1.settleResult(synth) resolves Turn N+1's resultPromise
        with TURN N's text + subtype:'success' + via:'stop-hook'.

t=2090  _awaitSettle for Turn N+1 sees the JSONL racer fire with
        outcome = {kind:'jsonl', ev:synth}. _runTurn N+1 returns
        successfully with Turn N's text. User receives "thanks" → a
        reply that is Turn N's content. **No error surface.**
```

## Trigger conditions

All of these must hold for the bug to fire:

1. Turn N completes via JSONL (Stop synth blocked by
   `_stopSynthScheduled` guard for its own turn — safe by rc.42 #6).
2. Stop hook for Turn N arrives 50-2000 ms after Turn N's JSONL
   settle (within `stopGraceMs`).
3. Turn N+1's `user-message` JSONL lands before Stop hook is
   processed (i.e. Turn N+1 is the active primary at hook-event time).
4. Turn N+1's `turn.text` is still empty at synth-fire time (no
   `assistant-chunk` events have populated it during the 2 s grace).

Condition #4 is the narrowest. A normal Turn N+1 starts streaming
within ~1 s of `user-message`, populating `turn.text`. The bug
needs a turn that takes >2 s to produce any text. Plausible cases:

- Short ambiguous follow-up that the model interprets as needing no
  response (the `No response requested.` shape — rc.39 sanitizer
  catches that on the OUTBOUND side, but Turn N+1's `turn.text` stays
  empty during the model's "thinking" phase before that decision).
- A turn with extended-thinking (opus/high) that thinks >2 s before
  emitting any text chunk.
- A turn that uses tools first, then text — `turn.text` only
  populates from `assistant-chunk` events, not tool events. If first
  tool runs >2 s, turn.text is empty when synth fires.

## Production prevalence — UNQUANTIFIED

We've never seen this in the wild because:
- Pre-rc.41 there was no Stop synth — race didn't exist.
- rc.41+rc.42 ship with the synth but only on shumorobot (1 user).
- Even on shumorobot, the trigger window requires fast back-to-back
  user messages plus a slow Turn N+1.

rc.42's `stop-hook-resolved` event (finding #15) lets us count how
often H4 synth fires AT ALL. The race count is bounded by that
number. Soak should run for ≥7 days before we have prevalence data
worth acting on.

## Fix options

### Option A — Verify primary identity at synth-fire time

Capture `primary.turnId` at SCHEDULE time. At FIRE time, look up the
current active primary and verify identity match. If activeGroup
rotated, drop the synth.

```js
if (ev?.type === 'Stop') {
  const primary = (this._activeGroup?.turns || [])
    .find((t) => t.kind === 'primary');
  if (primary && !primary._stopSynthScheduled
    && typeof primary.settleResult === 'function') {
    const scheduledForTurnId = primary.turnId;  // ← capture
    primary._stopSynthScheduled = true;
    primary._stopSynthTimer = setTimeout(() => {
      try {
        const currentPrimary = (this._activeGroup?.turns || [])
          .find((t) => t.kind === 'primary');
        if (!currentPrimary
          || currentPrimary.turnId !== scheduledForTurnId) {
          // Active group rotated; this Stop is stale.
          return;
        }
        if (typeof primary.settleResult === 'function') {
          primary.settleResult(synth);
        }
      } catch (err) { /* log */ }
    }, this.stopGraceMs);
  }
}
```

**Pros:** minimal change. Preserves H4's rescue contract for the
SAME turn the Stop belongs to. Idempotency-safe.

**Cons:** doesn't help when Stop is delayed >stopGraceMs (rare per
spike data: lag p95=22 ms). Doesn't help when Turn N+1 happens to
have the same turnId as Turn N (impossible — turnId is monotonic).

### Option B — Bind Stop to claude session-id, not active primary

Hook events carry `session_id` (claude's UUID). polygram's
`this.claudeSessionId` is per-TmuxProcess (per chat). A `--resume`
keeps the same claude session-id; an orphan-respawn assigns a new
one. So claude session-id alone can't distinguish Turn N from
Turn N+1 in the SAME chat.

claude does NOT scope Stop events by polygram-turn — it has no
concept of polygram turns. So we can't filter by hook payload alone.

**Verdict:** Option B insufficient. Falls back to Option A.

### Option C — Drop the synth entirely

H4's rescue contract is "if JSONL never lands, Stop carries the
turn." If we're worried about misattribution, just remove H4 —
rely on the idle ceiling (H3) to time out a JSONL-stuck turn.

**Pros:** simplest. Removes the race surface entirely.

**Cons:** loses the "rescue a stuck turn" capability. Idle ceiling
fires at 5 min idle by default — that's the user waiting 5 minutes
before getting a "turn timed out" error. H4 was designed to settle
the turn within `stopGraceMs` (2 s) of Stop hook arrival.

**Verdict:** loses real user value. Option A is better.

### Option D — Use claude's transcript_path scoping

claude hooks carry `transcript_path`. If we cache the
transcript_path of the turn that JUST resolved via JSONL, and only
fire Stop synth when `ev.transcript_path` matches a transcript_path
we haven't yet seen settle... actually this is complicated and
nothing guarantees that mapping.

**Verdict:** too speculative for rc.43; not worth the cost.

## Recommendation for rc.43

**Ship Option A.** ~20 LOC change, preserves H4's rescue contract,
closes the misattribution window. Add a test that:

1. Sets up active group with primary Turn N.
2. Fires Stop hook for Turn N.
3. _Before_ stopGraceMs elapses, simulates turn rotation: drop
   Turn N from activeGroup, add Turn N+1 with a new turnId.
4. Wait for stopGraceMs.
5. Assert Turn N+1.settleResult was NOT called (Turn N+1's
   resultPromise stays pending).

Plus an observability event when the stale-stop drop fires
(`stop-hook-stale-drop`) so we can count how often the race
ACTUALLY would have caused a misattribution in production.

## What rc.42 ships toward the fix

Direct scaffolding for the rc.43 fix:

- **`_stopSynthScheduled`** (#6) — prevents same-turn duplicate
  scheduling. Already in.
- **`_stopSynthTimer` + cleanup in `_finishTurn`** (#6) — clears
  the timer when the original turn retires. This means Option A's
  "stale primary" case fires LESS often: when Turn N retires via
  any path, its timer is cleared, so the rotation-followed-by-
  fire scenario only happens if Turn N retired AFTER its Stop
  hook scheduled and BEFORE the synth-fire moment. Narrow window.
- **`stop-hook-resolved` event** (#15) — soak metric for "how
  often H4 actually wins the race against JSONL." Subset of this
  is the misattribution case. After soak, decide if Option A is
  worth shipping or if the race rate is low enough to defer
  indefinitely.

## Risk profile if we ship rc.42 without this fix

- **User-visible:** silent wrong-reply on the narrow trigger.
  Severity: HIGH (chat surface integrity), prevalence: LOW (race
  window narrow).
- **Observability:** `stop-hook-resolved` event count gives us a
  ceiling on race incidence. If 0 events fire in soak, no
  misattribution can occur.
- **Reversibility:** Option A is forward-compatible with rc.42's
  scaffolding — no rework needed. Adding the identity check is
  purely additive.

## Open questions for follow-up

1. Does `_finishTurn` actually clear the timer in time? Worst case:
   JSONL settles Turn N → _finishTurn runs → next event loop tick
   processes the Stop hook for Turn N (timer cleared OK), but Turn
   N's `_stopSynthScheduled` is set so the new schedule attempt is
   blocked. Wait — the Stop arrives AFTER `_stopSynthScheduled` is
   relevant. Need to verify: if Stop arrives AFTER `_finishTurn`
   already retired Turn N, is the find() at hook-event time still
   matching Turn N (lingering reference) or Turn N+1?

   `_finishTurn` removes Turn N from pendingQueue AND
   `_dropFromActiveGroup`. So at Stop-arrival time, activeGroup's
   primary is either empty or already Turn N+1. The find() returns
   Turn N+1 → schedules for Turn N+1 → synth fires with Turn N's
   text → misattribution.

   So the timer cleanup added in rc.42 #6 is for the OPPOSITE
   direction: Turn N synth scheduled AT Stop arrival time, then
   Turn N retired before fire. NOT this race. This race is
   structurally different and needs Option A.

2. Could autosteer make this worse? Autosteer folds messages into
   the running turn — fewer Turn N+1 standalone turns to race
   against. Probably a net positive. Worth confirming.

3. What about NEW-TURN autosteer (`extra-turn-reply`)? Those are
   primary-kind turns too. Same race shape applies. Option A
   covers them.
