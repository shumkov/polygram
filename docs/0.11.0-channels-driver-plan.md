# 0.11.0 — Channels driver plan (rev. after 2026-05-24 multi-persona review)

Status: planning, pre-spike. This is the revised draft after the ce-doc-review pass identified two P0s, twelve P1s, and a handful of P2s. The revision resolves all P0/P1 findings inline and partially addresses P2.

## Goal

Add a third backend behind `lib/process/process.js` — `ChannelsProcess` — that uses Claude Code's official Channels feature (`--channels`) for IO. Tmux still owns lifecycle (spawn, abort, stop). Only IO swaps.

**All three drivers (SdkProcess, TmuxProcess, ChannelsProcess) are preserved indefinitely.** No driver removal is planned in 0.11.0 — this is additive only. A possible future consolidation (e.g., delete TmuxProcess once ChannelsProcess proves out) is explicitly deferred and out of scope.

## Why

### Cost (the load-bearing reason)

`SdkProcess` uses `@anthropic-ai/claude-agent-sdk`, which authenticates with an Anthropic API key and is billed per-token at Console rates. For a heavy-use chat bot, this is materially expensive. `TmuxProcess` spawns the `claude` CLI inside tmux; CLI sessions inherit the user's Pro/Max subscription pricing (flat monthly). Polygram's primary cost-control lever is keeping production on the subscription-priced path.

`TmuxProcess` already delivers subscription pricing. What it doesn't deliver is structured IO — every IO bug in polygram traces back to JSONL tailing or pane scraping. `ChannelsProcess` is a third backend that delivers **subscription pricing AND structured IO** by using the official Channels protocol (`--channels`) inside the same CLI binary.

So the cost/quality tradeoff matrix today is:

|              | Subscription pricing | Structured IO |
|---           | --- | --- |
| SdkProcess   | ❌ (per-token API) | ✅ |
| TmuxProcess  | ✅ | ❌ (JSONL+pane) |
| ChannelsProcess (new) | ✅ | ✅ |

There is no current configuration that gives both. Channels is what enables it.

### Maintainability (secondary)

Today's tmux + JSONL/pane path has structural fragility:
- TUI string drift on Claude Code releases (parser regex must keep up).
- Stuck buffer / rating-prompt swallow / compaction-race on `send-keys`.
- Approval prompt parsed out of the pane (`lib/approvals/*`).
- JSONL race conditions (mtime-aware tail-read, partial-line drops).

`ChannelsProcess` sidesteps all of these by using Anthropic's structured channel protocol. Per-driver, this is a maintainability win — bugs in the JSONL/pane parser don't follow Channels users. The codebase keeps those parsers (TmuxProcess still uses them), but production traffic that migrates to Channels stops hitting the failure modes.

### Baseline (calibrate the bet)

The TUI-string-drift / stuck-buffer / approval-scrape failure modes have appeared as distinct rc.NN findings across 0.10.0 (see `docs/0.10.0-tmux-status.md`, `docs/0.10.0-rc42-finding-4-stop-synth-attribution-race.md`, etc.). Phase 2 success criteria below pin against a measurable baseline drawn from those — no vague "more reliable" target.

## How Channels work (one-paragraph cheat sheet)

A channel is an MCP server that Claude Code spawns over stdio as a subprocess of `claude`. It declares `claude/channel` capability → Claude registers a notification listener. The server pushes events via `mcp.notification({ method: 'notifications/claude/channel', params: { content, meta } })`. They arrive in Claude's context as `<channel source="polygram" chat_id="…">body</channel>` tags. Claude replies via a normal MCP tool (we define `reply` only in Phase 1; `react`/`edit_message` deferred — see Decision #10). The server can also declare `claude/channel/permission` capability — Claude Code then forwards permission prompts as `permission_request` notifications; the server responds with a `permission` notification carrying the verdict. Required runtime: Claude Code v2.1.80+ (v2.1.81+ for permission relay). Authentication: Pro/Max subscription works, no admin gate needed. Phase 0 verifies the exact capability/notification names against the pinned binary before Phase 1 begins.

Bridge owns nothing semantic. State — chat→session mapping, user model, scheduling, history hydration, reactions, typing — stays in the daemon.

## Decisions made (post-review)

| # | Decision | Rationale |
|---|---|---|
| 1 | Build custom bridge, don't fork official Telegram plugin | Polygram daemon already owns the bot, user model, scheduler. Plugin assumes one bot per session. |
| 2 | Bridge runtime: Node | Matches polygram. ESM/CJS handled via `.mjs` file or dynamic `import()` (see Bridge spec). |
| 3 | Bridge ↔ daemon transport: unix socket | Single host, no port exposure. Path uses opaque random token, mode `0600`, plus a per-socket secret in env. |
| 4 | **Keep all three drivers indefinitely** | Different cost/structure tradeoffs. No deletion plans in 0.11.0. Future consolidation deferred. |
| 5 | Tmux owns lifecycle in Channels driver | Channels swap IO, not process management. Spawn / abort (SIGINT) / stop unchanged. |
| 6 | Heartbeat reactions for ChannelsProcess **only**; SDK/tmux drivers keep their per-tool reactions | Channels has no tool-call visibility (intentional protocol limitation), so it needs a liveness substitute. SDK/tmux have full tool events — no reason to downgrade their precision. Zero regression on existing drivers. |
| 7 | Per-tool reaction precision preserved on SDK + tmux drivers; lost only on ChannelsProcess | Different drivers, different signal availability. Users on tmux/sdk see `📂`/`🔧`/etc. as today. Users on Channels see heartbeat cycling. STALL detector works on all three. |
| 8 | SDK is the per-token cost path; Channels is the subscription path with structured IO | Resolves "why not SDK-only" — different billing rails. |
| 9 | All inbound TG content XML-escaped before placement in `<channel>` body | Prompt-injection defense. |
| 10 | Phase 1 ships `reply` tool only — `react` and `edit_message` deferred | Scope discipline: "Only IO swaps." Richer-output tools are a separate decision. |

## Reactions

**Per-driver behavior:**

| Driver | Reaction model |
|---|---|
| SdkProcess | **Unchanged.** Per-tool reactions driven by SDK callbacks (`lib/sdk/callbacks.js:58, 91, 552`). Existing chains, existing STALL, existing rc.32 progressive-deepening. No regression. |
| TmuxProcess | **Unchanged.** Per-tool reactions driven by JSONL tool_use events. Existing chains, existing STALL. No regression. |
| ChannelsProcess | **New: heartbeat reactions** — protocol gives no tool-call visibility, so cycle through `WORKING_POOL` for liveness. STALL detector preserved. |

### ChannelsProcess-only lifecycle

```
user msg arrives  → setMessageReaction([👀])              // received (daemon-side, driver-agnostic)
turn starts       → setMessageReaction([🤔])              // processing (daemon-side, driver-agnostic)
heartbeat tick    → setMessageReaction([WORKING_POOL pick]) every 8–12s with jitter   ← Channels only
STALL detected    → setMessageReaction([🥱])              // sticky, no further cycling ← all drivers
reply delivered   → setMessageReaction([])                // cleared (daemon-side, driver-agnostic)
```

### STALL preservation

The existing `STALL` reaction chain (rc.32, `lib/telegram/reactions.js:55`, calibrated against May 2026 production data) is preserved unchanged. It fires when a `Process` emits no event for ≥45s. It already works driver-agnostically because it subscribes to the Process EventEmitter — no changes needed for SDK/tmux. For ChannelsProcess, the new heartbeat respects STALL: if STALL fires, heartbeat cycling stops and `🥱` becomes sticky until events resume.

### ChannelsProcess working pool

Subject to Telegram Bot API whitelist verification at implementation time (the specific emojis are an implementer choice; Phase 2 swaps any rejected emoji for a known-good alternative like `👾`):

```js
const WORKING_POOL = ['👨‍💻', '⚡', '🤓', '🤖', '🦄', '🔥']
```

### Reserved emojis (NOT in working pool)

| Emoji | Used for | Defined at |
|---|---|---|
| `👀` | received / queued | reactions.js QUEUED chain |
| `🤔` | thinking / processing start | reactions.js QUEUED chain |
| `✍` | autosteered (handwriting) | reactions.js AUTOSTEERED chain |
| `🤯` | error / timeout | reactions.js ERROR + TIMEOUT chains |
| `😨` | timeout | reactions.js TIMEOUT chain |
| `🥱` | STALL detected | reactions.js STALL chain |

### Phase A scope (narrowed after review)

Phase A is now **ChannelsProcess-only infrastructure**, not a cross-driver refactor:

1. Add `turn-start` / `turn-end` event emission to ChannelsProcess (only — SdkProcess and TmuxProcess untouched).
2. Add a `HeartbeatReactor` module in `lib/telegram/reactions.js` that subscribes to those events for `Process` instances whose driver is `channels`. No-op for other drivers.
3. Verify STALL still fires correctly for ChannelsProcess (just needs `Process.event` emission on tool-call / notification arrival).
4. **Do NOT touch** `lib/sdk/callbacks.js` per-tool reaction calls.
5. **Do NOT touch** tmux-side per-tool reaction code.

Phase A estimate: **1d** (down from 1.5d after scope narrowing; was 0.5d in the original draft which underestimated even the narrow scope).

Phase A is now correctly described as **infrastructure-only — no UX change on any existing driver.** It only does visible work when ChannelsProcess launches in Phase 1. The "ships value alone" framing from the original draft is dropped.

## What we keep / lose / gain (revised)

### Keep (no regression on SDK + tmux drivers)

- `👀`, `🤔`, `✍`, `🥱` reactions — daemon-side, driver-agnostic
- **Per-tool reactions (`📂`, `🔧`, etc.) on SDK and tmux drivers** — existing code paths untouched
- rc.32 progressive-deepening cascade on SDK and tmux drivers
- Reply text parsing → stickers (`lib/telegram/parse.js:25`)
- History hydration on session resume
- Slash commands, scheduling, multi-user routing, db, user model, sender allowlist
- File attachments out (Channels driver adds via `reply(chat_id, text, files: [...])`; SDK/tmux unchanged)
- Typing indicator
- Hard abort via SIGINT through tmux
- **All three drivers operational** — config flag selects per-session

### Lose (only on ChannelsProcess; never on SDK/tmux)

| What | Severity | Mitigation |
|---|---|---|
| Per-tool reaction precision on Channels driver | Accepted for this driver | Heartbeat + STALL. SDK/tmux users see no change. |
| Mid-turn streaming partial text on Channels driver | Accepted for this driver | Reply tool delivers complete text. |
| Live token/cost mid-turn on Channels driver | Accepted for this driver | Per-turn totals at reply time. |
| Bedrock/Vertex users on Channels | N/A | Channels is config-gated; Bedrock users keep `driver=tmux`. |

### Gain

| What | Why |
|---|---|
| Subscription-priced structured IO | Cost goal — see "Why" |
| Structured permission relay | `permission_request` notification carries `{request_id, tool_name, description, input_preview}` — no pane scrape on Channels driver |
| File attachments via tool arg | `reply(chat_id, text, files)` — first-class |
| Mid-turn autosteer reliability on Channels driver | Channel notifications arrive between Claude tool calls cleanly; no stuck-buffer risk |
| Backpressure handled | Channels batch queued events into the next turn automatically |
| Choice of driver per session | Cost-conscious users on Channels; legacy-compat users on TmuxProcess; high-flexibility on SdkProcess |

Note: code reduction is **not** a goal of 0.11.0. The JSONL/pane parsers (`lib/process/turn-phase.js`, `lib/process/hook-event-tail.js`, `lib/tmux/session-log-parser.js`) all stay because TmuxProcess still uses them. `lib/approvals/*` stays because tmux and sdk drivers still feed it. Per-tool reaction wiring in `lib/sdk/callbacks.js` (lines ~58, 91, 552) and the tmux equivalent stay untouched in 0.11.0 — they continue serving SDK and tmux drivers.

## ChannelsProcess (revised sketch)

Sibling of `SdkProcess` / `TmuxProcess`. Implements the `Process` contract in `lib/process/process.js`. **This sketch matches the actual contract** (post-review: `interrupt`/`kill`, not `abort`/`stop`; `send(prompt, opts)` returns a Promise of `PmSendResult`; explicit `turn-end` signal from bridge).

```js
// lib/process/channels-process.js
'use strict';

const crypto = require('crypto');
const fs = require('fs');
const path = require('path');
const Process = require('./process.js');

class ChannelsProcess extends Process {
  async start(ctx) {
    // session-id discovery: generate ours OR reuse the one provided by ctx
    // (matches tmux-process.js:511-517 pattern so resume works)
    this.claudeSessionId = ctx.existingSessionId || crypto.randomUUID();

    // socket path uses opaque random token, NOT sessionKey, to avoid leaking
    // semantic identifiers via filesystem enumeration (security finding #6)
    const socketToken = crypto.randomBytes(16).toString('hex');
    this.sockPath = path.join('/tmp', `polygram-${socketToken}.sock`);
    this.sockSecret = crypto.randomBytes(32).toString('hex');

    this.sockServer = createUnixSocketServer(this.sockPath, {
      mode: 0o600,                          // P1 security: file-permission hardening
      secret: this.sockSecret,              // P1 security: handshake-auth on accept
      onMessage: this.onBridgeMsg.bind(this),
    });

    await this.spawnTmuxWithChannels({
      env: {
        POLYGRAM_SESSION_KEY:    this.sessionKey,
        POLYGRAM_SOCK:           this.sockPath,
        POLYGRAM_SOCK_SECRET:    this.sockSecret,
        POLYGRAM_CLAUDE_SESSION_ID: this.claudeSessionId,
      },
      // ARG ORDER MATTERS (Phase 0 interactive run, 2026-05-24):
      // - In dev mode, use ONLY --dangerously-load-development-channels server:NAME.
      //   The --channels flag is for production-allowlisted plugins; mixing them
      //   makes claude reject e.g. --strict-mcp-config as a malformed channel entry.
      // - --mcp-config is variadic (<configs...>) and MUST come last.
      // - --no-session-persistence is --print-mode-only; do NOT pass in interactive.
      args: [
        '--strict-mcp-config',                                              // isolation
        '--dangerously-load-development-channels', 'server:polygram-bridge', // dev-mode channel registration
        '--session-id', this.claudeSessionId,                               // for --resume on respawn
        '--mcp-config', this.buildMcpConfig(),                              // MUST be last (variadic flag)
      ],
      // Note: do NOT pipe claude's stdout/stderr through `tee` or similar — claude
      // detects non-TTY stdout and switches to --print mode silently. Capture via
      // tmux capture-pane instead, which preserves the pty.
    });

    await this.awaitBridgeHandshake({ timeoutMs: 15000 });
    this.emit('init');
  }

  buildMcpConfig() {
    // inline MCP-server registration so `--channels server:polygram-bridge` resolves
    return JSON.stringify({
      mcpServers: {
        'polygram-bridge': {
          command: 'node',
          args: [path.resolve(__dirname, 'channels-bridge.mjs')],
        },
      },
    });
  }

  // Process.send contract: returns Promise<PmSendResult> resolved at turn-end
  async send(prompt, opts = {}) {
    const turnId = crypto.randomUUID();
    const turnP = this.registerPendingTurn(turnId, opts);    // resolves on turn-end msg from bridge

    this.writeToBridge({
      kind:    'user_msg',
      turn_id: turnId,
      text:    prompt,
      files:   opts.context?.files,
      meta:    { chat_id: opts.context?.chatId, user: opts.context?.user, msg_id: opts.context?.sourceMsgId },
    });
    this.emit('turn-start');

    return turnP;   // resolves with { text, sessionId, cost, duration, error, metrics }
  }

  // contract: interrupt() not abort(); kill(reason) not stop()
  async interrupt() {
    await this.sendTmuxKeys('C-c');   // hard interrupt — tmux path unchanged
  }

  async kill(reason) {
    await this.gracefulShutdown(reason);  // /exit + wait + force kill, same as tmux
    this.sockServer.close();
    try { fs.unlinkSync(this.sockPath); } catch {}
  }

  onBridgeMsg(msg) {
    // every msg authenticated via secret on socket-accept; tampering rejected upstream
    switch (msg.kind) {
      case 'session_init':
        // bridge reports the canonical claude session_id back (in case --session-id was ignored)
        if (msg.claude_session_id && msg.claude_session_id !== this.claudeSessionId) {
          this.claudeSessionId = msg.claude_session_id;
          this.emit('session-id-refreshed', this.claudeSessionId);
        }
        break;

      case 'tool':
        this.handleToolCall(msg);            // chat_id validated against session before dispatch
        break;

      case 'turn_end':
        this.resolvePendingTurn(msg.turn_id, msg.result);
        this.emit('turn-end');
        break;

      case 'perm_req':
        this.emit('permission-request', {
          requestId: msg.request_id,
          toolName: msg.tool_name,
          description: msg.description,
          inputPreview: msg.input_preview,
          sessionKey: this.sessionKey,         // bound to session for sender-allowlist check upstream
        });
        break;

      case 'pong':
        this.lastPong = Date.now();
        break;

      case 'tool_ack':
        this.resolveToolAck(msg.tool_call_id, msg.ok, msg.error);
        break;
    }
  }

  // Called by upstream router after sender-allowlist check
  async respondToPermission(requestId, behavior) {
    this.writeToBridge({ kind: 'perm_verdict', request_id: requestId, behavior });
  }
}
```

Wire into `lib/process/factory.js` alongside `SdkProcess` / `TmuxProcess`.

## Bridge spec (revised)

Location: `lib/process/channels-bridge.mjs` (ESM file — explicit `.mjs` because polygram's `package.json` is `"type": "commonjs"`). MCP SDK is ESM-only; one isolated `.mjs` file is cleaner than dynamic-import gymnastics.

Realistic LoC: 200–300 (review found the original ~80 LoC estimate excluded error handling, reconnect, schema validation, stdin-EOF exit, ping/pong watchdog, sanitization).

```js
#!/usr/bin/env node
// lib/process/channels-bridge.mjs
import { Server } from '@modelcontextprotocol/sdk/server/index.js'
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js'
import { ListToolsRequestSchema, CallToolRequestSchema } from '@modelcontextprotocol/sdk/types.js'
import { z } from 'zod'
import { connect } from 'net'
import crypto from 'crypto'

const SESSION_KEY  = process.env.POLYGRAM_SESSION_KEY
const SOCK         = process.env.POLYGRAM_SOCK
const SOCK_SECRET  = process.env.POLYGRAM_SOCK_SECRET
const CLAUDE_SID   = process.env.POLYGRAM_CLAUDE_SESSION_ID

// P1: exit if parent (claude) EOFs our stdin — claude crashed
process.stdin.on('end',   () => process.exit(0))
process.stdin.on('close', () => process.exit(0))

// P1: socket handshake-auth
const sock = connect(SOCK)
sock.write(JSON.stringify({ kind: 'hello', session_key: SESSION_KEY, secret: SOCK_SECRET }) + '\n')

// announce ourselves to the daemon — includes claude session_id for resume
sock.write(JSON.stringify({ kind: 'session_init', claude_session_id: CLAUDE_SID }) + '\n')

const mcp = new Server(
  { name: 'polygram-bridge', version: '0.1.0' },
  {
    capabilities: {
      experimental: { 'claude/channel': {}, 'claude/channel/permission': {} },
      tools: {},
    },
    // Phase 0 finding: Claude refers to tools by their prefixed MCP name
    // (`mcp__<server>__<tool>`), not the bare name. Mention the prefixed
    // form explicitly so Claude's reasoning doesn't drift.
    instructions:
      'Inbound user messages arrive as <channel source="polygram" chat_id="..." user="...">. ' +
      'Always reply via the `mcp__polygram-bridge__reply` tool — passing chat_id verbatim — before ending a turn. ' +
      'For long tool calls, send a brief progress reply first so the user is not waiting in silence.',
  },
)

// XML-escape user content before placing into channel body (P1 security: prompt-injection defense)
function escapeChannelBody(s) {
  return String(s).replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;')
}

mcp.setRequestHandler(ListToolsRequestSchema, async () => ({
  tools: [{
    name: 'reply',
    description: 'Send a message to the originating Telegram chat. ' +
                 'chat_id MUST match the chat_id received in the inbound channel event.',
    inputSchema: {
      type: 'object',
      properties: {
        chat_id: { type: 'string' },
        text:    { type: 'string' },
        files:   { type: 'array', items: { type: 'string' } },
      },
      required: ['chat_id', 'text'],
    },
  }],
  // react and edit_message deferred to a follow-on phase (Decision #10)
}))

// Per-call promise so Claude waits on real delivery, not optimistic 'queued' (P2 reliability)
const pendingToolCalls = new Map()
mcp.setRequestHandler(CallToolRequestSchema, async req => {
  const callId = crypto.randomUUID()
  const ackP = new Promise((resolve, reject) => {
    pendingToolCalls.set(callId, { resolve, reject })
    setTimeout(() => {
      if (pendingToolCalls.has(callId)) {
        pendingToolCalls.delete(callId)
        reject(new Error('daemon ack timeout'))
      }
    }, 30000)
  })

  sock.write(JSON.stringify({
    kind: 'tool', session: SESSION_KEY, tool_call_id: callId,
    name: req.params.name, args: req.params.arguments,
  }) + '\n')

  try {
    await ackP
    return { content: [{ type: 'text', text: 'sent' }] }
  } catch (err) {
    return { content: [{ type: 'text', text: `delivery failed: ${err.message}` }], isError: true }
  }
})

mcp.setNotificationHandler(
  z.object({
    method: z.literal('notifications/claude/channel/permission_request'),
    params: z.object({
      request_id: z.string(),
      tool_name: z.string(),
      description: z.string(),
      input_preview: z.string(),
    }),
  }),
  async ({ params }) => sock.write(JSON.stringify({
    kind: 'perm_req', session: SESSION_KEY, ...params,
  }) + '\n'),
)

// inbound from daemon → forward to Claude
let buf = ''
sock.on('data', chunk => {
  buf += chunk
  let nl
  while ((nl = buf.indexOf('\n')) >= 0) {
    const msg = JSON.parse(buf.slice(0, nl)); buf = buf.slice(nl + 1)
    switch (msg.kind) {
      case 'user_msg':
        mcp.notification({
          method: 'notifications/claude/channel',
          params: {
            content: escapeChannelBody(msg.text),
            meta: {
              chat_id: msg.chat_id,
              user:    msg.user,
              msg_id:  msg.msg_id,
              turn_id: msg.turn_id,
            },
          },
        })
        break

      case 'perm_verdict':
        mcp.notification({
          method: 'notifications/claude/channel/permission',
          params: { request_id: msg.request_id, behavior: msg.behavior },
        })
        break

      case 'tool_ack':
        const pending = pendingToolCalls.get(msg.tool_call_id)
        if (pending) {
          pendingToolCalls.delete(msg.tool_call_id)
          msg.ok ? pending.resolve() : pending.reject(new Error(msg.error || 'unknown'))
        }
        break

      case 'ping':
        sock.write(JSON.stringify({ kind: 'pong' }) + '\n')
        break
    }
  }
})

// Heartbeat OUT and watchdog IN — daemon pings us
let lastPing = Date.now()
sock.on('data', () => { lastPing = Date.now() })
setInterval(() => {
  if (Date.now() - lastPing > 30000) {
    process.exit(2)            // daemon gone or stalled — exit so claude restarts cleanly
  }
}, 5000)

await mcp.connect(new StdioServerTransport())
```

## Daemon socket protocol (revised)

Newline-delimited JSON. First message after connect MUST be `hello` with the secret; daemon rejects all others until handshake completes.

Bridge → daemon:
- `{kind:'hello', session_key, secret}` (handshake)
- `{kind:'session_init', claude_session_id}` (resume info)
- `{kind:'tool', session, tool_call_id, name:'reply', args:{...}}`
- `{kind:'perm_req', session, request_id, tool_name, description, input_preview}`
- `{kind:'pong'}`

Daemon → bridge:
- `{kind:'user_msg', chat_id, user, msg_id, turn_id, text}`
- `{kind:'perm_verdict', request_id, behavior:'allow'|'deny'}`
- `{kind:'tool_ack', tool_call_id, ok, error?}`
- `{kind:'turn_end', turn_id, result:{text, sessionId, cost, duration, metrics, error?}}`
- `{kind:'ping'}`

Daemon-side enforcement (per review findings):

1. **Sender-allowlist gate on permission verdicts (P0 security).** When the daemon receives a `perm_req` from a bridge, it renders TG buttons. The user's tap MUST come from the same `user_id` that owns the session (`session.ownerUserId`). Verdicts from any other TG user are silently dropped.
2. **Request-id binding (P1 security).** Daemon keeps a `Map<request_id, {sessionKey, expiresAt}>` for outstanding `perm_req`s. Verdicts must match `{request_id, sessionKey}` and arrive before `expiresAt` (default 5 minutes). Single-use — removed after first verdict.
3. **chat_id validation on tool calls (P1 security).** When the daemon receives `kind:'tool', name:'reply', args:{chat_id, ...}`, it MUST verify `chat_id` matches the session's registered chat. Mismatches are dropped + logged. Same for `react`/`edit_message` if/when those ship.
4. **tool_ack roundtrip (P2 reliability).** Daemon attempts delivery to Telegram, then writes `tool_ack` back with `ok: true/false` and (on failure) `error`. Bridge surfaces failures as MCP tool errors so Claude can decide whether to retry.
5. **`turn_end` signal (P1 feasibility).** Daemon emits `turn_end` after the `reply` tool call has been delivered AND the bridge subprocess has gone quiet for ≥2s (no further tool calls). This is what resolves `ChannelsProcess.send()`'s Promise.

## Daemon-crash recovery

On daemon startup (P1 finding):
1. Sweep `/tmp/polygram-*.sock`. For each:
   - Try connecting. If it accepts and the bridge responds to a `ping` within 1s, reattach: pull the `session_key` from the bridge's first message and reconcile against DB.
   - If no response, the bridge is orphaned. Find its parent claude process (by walking `ps` for `--mcp-config` references to that socket path), send SIGTERM, then unlink the socket. This mirrors `lib/db/auto-resume.js`'s 300s reaper logic but runs synchronously at boot.
2. For DB-known active sessions whose sockets aren't found: mark stale, leave the resume decision to the autosteer / auto-resume path.

## Rollback strategy

Per-session: flip `session.driver` back to `tmux` or `sdk`, restart session. DB/history driver-independent.

Global default flip rollback: revert config default; existing channels sessions migrate back on restart via the per-session mechanism.

Phase A rollback: trivial — Phase A only adds new code (HeartbeatReactor module + ChannelsProcess events). Nothing existing is modified or deleted, so reverting Phase A is a clean removal of new files. SDK and tmux drivers are unaffected by Phase A in any state.
