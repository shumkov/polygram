# 0.10.0 — tmux-claude driver: prior-art comparison

## Why this doc

polygram's tmux backend (`lib/process/tmux-process.js` + `lib/tmux/*`)
drives the interactive `claude` TUI inside tmux. Before/around the
0.10.0 concurrency rework we should know: **did we reinvent the
wheel? Can we reuse an existing project, or at least learn how others
solve the same problems?**

Four public projects were researched at source level (2026-05-17).
Verdict up front: **the hard part is not reinvented — no surveyed
tool solves concurrent-message attribution.** But there is one
genuine architectural gap worth acting on (the Stop hook, F2), and a
few small things to learn.

## Tools surveyed

| Tool | What it is | Stack | License | Maturity |
|---|---|---|---|---|
| **CCGram** — `alexei-led/ccgram` | Telegram↔tmux bridge, forum-topic per tmux window | Python | MIT | ~500 commits, active May 2026 |
| **tmai** — `trust-delta/tmai` | Multi-agent monitor/control engine, REST+SSE, 3-tier detection | Rust engine (**private**), TS UI | MIT (public parts) | 670 commits, 6 stars, no public tests |
| **Claude-Code-Remote** — `JessyTsui/Claude-Code-Remote` | Telegram remote, hook-notify → send-keys | Node.js | MIT | ~1.2k stars, **stale (Aug 2025)**, no tests |
| **Codeman** — `Ark0N/Codeman` | WebUI + autonomous respawn loop manager | TypeScript, node-pty | MIT | 392 stars, active May 2026 |

Not a fit (different problem shape, noted for completeness):
**tmux-mcp** (MCP server letting Claude Desktop *control* tmux — the
inverse direction) and **claude-tmux** (Rust local session-manager
TUI — no bot, no remote).

## Feature matrix vs. polygram's tmux backend

| | polygram (tmux backend) | CCGram | tmai | Claude-Code-Remote | Codeman |
|---|---|---|---|---|---|
| **Turn-completion signal** | JSONL aggregator (coalesce by `message.id`, terminal `stop_reason`) primary; capture-pane = liveness only | **Stop hook** primary + JSONL transcript poll (`is_complete`) | **3-tier**: HTTP Stop hook → PTY wrap → capture-pane | **Stop hook** + capture-pane scrape for reply text | 6-layer confidence score (hook=bypass; regex; pty-silence; token-stable; no-spinner; AI check) |

## Findings

### F1 — Concurrent-message attribution: nobody else solves it *(validation)*

The 0.10.0 work (correlation token + turn ledger + fold-vs-new-turn,
Phases 2–3) has **no equivalent in any surveyed tool**:

- **CCGram** serialises a user's messages through one `asyncio.Queue`
  and *coalesces* them (merge up to ~3800 chars) — queue-merging, not
  causal attribution. It never answers "which of the N messages
  caused this reply."
- **tmai** attributes across *many agents* (`DispatchSnapshot.spawner`/
  `bundle_id`) — a different axis. polygram's problem is N messages to
  *one* chat session.
- **Claude-Code-Remote** has no queue/lock at all — concurrent
  messages race and interleave keystrokes.
- **Codeman** rejects a second `runPrompt` outright.

These tools are *remote-control / monitoring* tools (one human, one
agent, mostly one turn at a time). polygram is a *conversational
bot* with the OpenClaw per-chat model — people fire "a/b/c" seconds
apart and each needs a correctly-attributed reply. The failure modes
the 0.10.0 work fixed (empty turns, cross-attribution, concatenation)
**only exist because of that model**, so no remote-control tool ever
had to solve them. The 5-phase rework was not reinvention.

### F2 — Everyone uses the Claude Code Stop hook; polygram uniquely does not *(the real gap)*

**All four** tools take turn-completion from Claude Code's `Stop`
hook. polygram alone infers it by reading the JSONL file's
`stop_reason`. This matters for two reasons:

1. **Stability.** `AGENTS.md` pins the CLI version *because* polygram
   reads JSONL internals — "not a stable public contract." Hooks
   **are** a documented public contract. A hook-based completion
   signal would be more robust than JSONL `stop_reason` scraping, and
   could eventually let the version pin relax.
2. **Latency / cleanliness.** A hook is event-driven (tmai's HTTP
   variant is *synchronous* — claude blocks on the HTTP 2xx). It
   beats both the JSONL tail and the capture-pane poll.

This is the highest-value learning from the survey. It is **not
free** — see recommendation R-A.

### F3 — A real output stream beats capture-pane scraping

tmai's middle tier and Codeman both run the agent under a **PTY they
own** (`node-pty` / a `terminal.sock` bridge) and read the byte
stream directly; capture-pane is tmai's *last-resort* tier. polygram
scrapes `tmux capture-pane` on a poll — the fragile spot
(leftovers **R7**: a wedged `capture-pane` subprocess hangs a turn).
A streamed pane (tmux `pipe-pane`, or a node-pty layer) would remove
the poll. See R-B.

### F4 — Paste reliability: polygram is comparable or ahead

CCGram's concrete number — **500 ms** gap before Enter, because "the
TUI interprets a rapid Enter as a newline" — is worth noting:
polygram uses an **80 ms** post-paste drain. Claude-Code-Remote adds
confirmation-prompt auto-answering (polygram has full approval
handling already). polygram's §5 JSONL-confirm paste gate is more
sophisticated than anything surveyed. Only action: sanity-check the
80 ms drain against CCGram's 500 ms (R-C).

## Reuse verdict

**No tool is a drop-in.** polygram's tmux backend is one backend
behind a shared `Process` abstraction inside a multi-backend daemon
(SDK backend, per-chat sessions, SQLite transcripts, approvals,
reactions, multi-bot). Every surveyed tool is standalone with a
single-turn model — adopting one would be a *bigger* rewrite than
the 0.10.0 work, and would still leave F1 to build.

Cleanly liftable snippets exist but are small and polygram mostly has
equivalents already: CCGram `tmux_manager.py` (send-keys + delays),
Claude-Code-Remote `tmux-injector.js` (~100 lines, confirmation
auto-answer), Codeman's confidence-score idle model. None worth a
dependency. tmai's engine is private — design reference only.

## Recommendations

### R-A — Evaluate a Claude Code `Stop` hook as the turn-completion signal *(high value, real work)*

Adopt the pattern all four tools use. Integration cost is real and
must be designed, not hand-waved:
- **Where the hook config lives.** A user-level `~/.claude/settings.json`
  hook fires for *every* claude on the host, polygram or not. It must
  be scoped — a project-level hook in each chat's `cwd`, or a hook
  command that no-ops unless it recognises a polygram session.
- **How the hook signals the daemon.** polygram already has an IPC
  layer (`lib/ipc/`); the hook script can post the `Stop` event
  (carrying `session_id`) to it. (tmai runs an HTTP server; CCGram
  writes `events.jsonl`; Claude-Code-Remote runs a node script.)
- **Keep JSONL.** The hook is the *completion* signal; the JSONL
  aggregator still supplies reply *text* + correlation tokens. The
  hook would replace the capture-pane *liveness* race, not Phase 1.

Not urgent (Phase 1's aggregator already gives reliable completion) —
but it is the cleanest long-term turn-end signal and the only survey
finding that could reduce the CLI-version-pin coupling. Worth a spike.

### R-B — Harden / replace capture-pane *(ties to leftover R7)*

R7's cheap fix stands: an absolute timeout around the `_runTurn`
race so a wedged `capture-pane` cannot hang a turn. The bigger
structural option — stream the pane via tmux `pipe-pane` (stays in
tmux) or a node-pty layer (tmai/Codeman model) instead of polling —
is lower priority and only worth it if R-A does not already retire
the capture-pane liveness role.

### R-C — Compare the post-paste drain

Quick check: is polygram's 80 ms post-paste drain enough, or does
CCGram's 500 ms reflect a real TUI race we are under-margining? The
§5 paste gate masks most of it, but the first paste of a turn still
relies on the drain. Verify against the real TUI in the next spike.

## Bottom line

We did not reinvent the wheel on the part that mattered — concurrent
turn attribution is genuinely ours and genuinely necessary. The
survey's payoff is **F2/R-A**: every comparable tool uses the Stop
hook and polygram does not; that is the one architectural idea worth
importing.
