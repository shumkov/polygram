# CLI turns that end in an API error: tell the user promptly

Status: reviewed (four independent reviews, 2026-11-05; must-fixes folded in,
§7). Scope approved by Ivan 2026-11-05: "surface API errors to the user
promptly". No retry-policy change, no auto-restart, no change to the SDK or
Codex backends.

## 1. Problem

On the CLI backend (Orchestra `CliProcess`, claude 2.1.283 in tmux plus the
channels bridge), a turn whose model request fails stays silent until the turn
ceiling ends it. Production, VPS shumabit bot, 2026-11-04/05 (polygram 0.41.3,
orchestra 0.11.1): both Claude OAuth grants in the CLIProxy pool had expired.
For every new user message:

1. `cli-ups-seen`: the prompt was picked up.
2. About 3 minutes of CLI-internal retries.
3. The session JSONL gets a synthetic assistant entry (`model: "<synthetic>"`,
   `stop_reason: "stop_sequence"`, `isApiErrorMessage: true`,
   `error: "server_error"`) plus `system/turn_duration`. There is no
   `stop_hook_summary`, and no Stop hook fires.
4. Polygram keeps the turn in flight. Later messages are autosteered into it.
5. 25–30 minutes later, `turn-timeout` → `turn-timeout-pane` →
   `handler-error` → "⏱ This one went quiet…". Overnight users saw nothing
   for hours.

`cli-mid-turn-unknown-prompt` fired every 30 s with an empty `excerpt_head`.
Two causes: the pane showed `⏺ API Error: 500 …` above the idle `❯` prompt,
which `UNKNOWN_PROMPT_HEURISTIC_RE` matches; and Polygram's event-detail
schema drops `excerpt_head` as free text (`REMOVED_FIELDS`), so the field is
always empty. The event is a symptom of the stuck pending turn: polling stops
once no turn is pending. The heuristic itself is not changed here.

## 2. What the pinned CLI actually does (verified)

Binary reading of claude 2.1.283 (vendored pin, SHA-256 `d8cb1e5c…`) and a
real-CLI reproduction, `scripts/spikes/cli-api-error-stub.mjs`. The repro runs
the pinned binary under `CliProcess` with a launcher that points
`ANTHROPIC_BASE_URL` at a local stub. It is the same seam production uses for
CLIProxy, and it makes no paid or authenticated model call.

- The query loop ends an API-error turn with
  `if (msg.isApiErrorMessage) { executeStopFailureHooks(msg); return {reason: "api_error"} }`.
  Stop and SubagentStop hooks are skipped, which matches the incident.
- **`StopFailure` is a documented hook event.** Its payload is the common
  fields plus `error` (enum: `authentication_failed`, `oauth_org_not_allowed`,
  `account_on_hold`, `verification_required`, `billing_error`, `rate_limit`,
  `overloaded`, `invalid_request`, `model_not_found`, `server_error`,
  `unknown`, `max_output_tokens`, `cloud_credential_error`), optional
  `error_details`, and `last_assistant_message`. The last field is the
  rendered error, including the gateway host. The hook fires only if a
  `StopFailure` hook is registered, and Orchestra registers none today. It is
  fire-and-forget (not awaited); `prompt_id` is captured synchronously.
- The common fields include `prompt_id`. They include `agent_id` only for
  subagents: under `--agent` the main thread carries `agent_type` but no
  `agent_id` (verified).
- Always-500 run with `CLAUDE_CODE_MAX_RETRIES=2`: `UPS prompt_id=P` →
  `StopFailure prompt_id=P error=server_error`. The JSONL entry matches
  production exactly. The turn is still pending after 60 s.
- **Fold:** a follow-up injected during a tool call is folded at the tool
  boundary. Its extra UPS and the turn's final StopFailure carry the **same**
  `prompt_id`. `prompt_id` identifies the query.
- **Queued follow-up** (the overnight shape): a message autosteered during the
  retries runs as its **own** cycle after the failure, with a **new**
  `prompt_id`: `UPS(P2)` → retries → `StopFailure(P2)`.
- **Subagent:** a subagent whose request fails fires `StopFailure` with
  `agent_id` and the parent's `prompt_id`, and **no SubagentStop**. The
  parent's own failure is a separate StopFailure with no `agent_id`. A
  following background-notification cycle (UPS with no channel envelope) can
  fail too.
- **Retry recovers** (500, 500, success): no StopFailure; the bridge reply is
  delivered and the turn resolves.
- **401** under a bearer token: retried, then
  `StopFailure error=authentication_failed`.
- **The org-disabled notice** that Orchestra's `AUTH_DISABLED` pane detector
  matches is the content of the synthetic message with
  `error: "oauth_org_not_allowed"`, from a 401/403 "OAuth authentication is
  currently not allowed for this organization" (binary reading).
- **/stop (C-c) during retries:** no StopFailure, no API-error entry; the
  interrupt grace resolves the turn.
- **During the retry backoff** the pane footer shows `esc to interrupt`
  (`✻ 500 … · Retrying in 2s · attempt 5/10`). The pane heartbeat therefore
  counts as activity while a cycle retries.

## 3. Chosen approach

Detect in **Orchestra**, which owns the hook stream and the turn lifecycle.
Choose the copy in **Polygram**, which owns the chat surface. The Orchestra
half is mirrored in `orchestra/docs/CLI_API_ERROR_STOP_FAILURE_SPEC.md`.

### 3.1 Orchestra (`CliProcess`), patch release 0.11.2

1. **Hook registration and parsing.**
   - Register `StopFailure` in `HOOK_EVENTS` and add it to
     `KNOWN_EVENT_NAMES`.
   - Normalize `apiError` from `error`, but only when the value is one of the
     enum strings above; anything else becomes `'unknown'`. `error_details` is
     not normalized.
   - Normalize `promptId` (from `prompt_id`) on every event. `promptId` and
     `agentId` count as present only when they are non-empty strings.
2. **Subagent StopFailure** (`agentId` present) is handled exactly like a
   SubagentStop. It splices the in-flight start, emits `subagent-done`, and
   follows the same orphan/matched activity rule. It never touches a pending
   turn. Without this, the leaked start defers the parent's later Stop until
   the ceiling, blocks a clean restart, and leaves the "working" face on.
3. **Main-thread StopFailure is terminal, like Stop.** It sets
   `_lastHookEventAt` and does not bump `_workHookSeq`. It never runs
   `_noteActivity`, `emit('stop-hook')`, `_captureStopHookData`, the
   workflow-completion snapshot, or the generic `hook-event` emit. The
   workflow fallback would post `last_assistant_message`, which is the raw
   gateway text.
4. **`UserPromptSubmit` bookkeeping.**
   - A pending marked `seen` by this UPS records `pending._promptId`, unless
     one is already set.
   - A UPS whose `prompt_id` no pending owns adds an entry to the bounded map
     `_failureAnchors: promptId → { msgId, turnId }`. The map keeps the last 8
     entries, because the next prompt's UPS can be written before this one's
     StopFailure. `msgId` and `turnId` belong to the first **non-primary**
     ledger entry with a msgId that the prompt picked up (autosteer or
     inject); both are null if there is none.
   - A fold's second UPS for the same `prompt_id` keeps the existing entry.
   - A delivered **final** reply that answers the follow-up clears the
     entry's `msgId`. That covers a reply bound to its `turnId`, a reply
     listing it in `consumed_turn_ids`, and a reply with no turn of ours
     (the newest entry). The cycle answered the message, so a later
     API-error end must not claim it went unanswered.
5. **Attribution.** When `closed` or `_bridgeDisconnecting`, log
   `cli-stop-failure-ignored` and do nothing.
   - No `promptId` → log `cli-stop-failure-unattributed reason=no-prompt-id`
     and do nothing. The pin always sends `prompt_id`, and a lag-blind
     fallback would bring back misattribution.
   - Otherwise, the turns to settle are the pendings with
     `_promptId === promptId`.
   - A matched turn that was in flight at the last C-c
     (`_interruptRequested`, set from the interrupt's own snapshot) is left to
     the interrupt resolution and logged. A turn started after the C-c settles
     normally.
   - Each turn is re-checked before settling, because an earlier settle's
     synchronous listeners may have torn things down.
6. **Settling a matched turn** (`_settleTurnApiError`).
   - **Reply delivery still in flight:** record `pending._apiError`, cancel
     its stop-grace and activity-quiet timers, and decide when
     `_finishReplyDeliveries` settles. `_apiError` takes precedence over
     `_finalizeAfterReplyDelivery` and `_timeoutAfterReplyDelivery`. This is
     reachable when the bridge's 30 s ack timeout lets claude move on while a
     large upload is still dispatching.
   - **Final reply delivered** (`_turnHasFinalReply` or
     `_turnHasConsumedFinalReply`): the user has the answer, so
     `_finalizeTurn` resolves the turn, as the ceiling path already does for
     replied turns. Log `cli-turn-api-error` with `delivered: true`. Captured
     Stop data is cleared first: this query ended without a Stop, so any
     captured text belongs to another cycle.
   - **Otherwise** (no reply, or interim replies only): fail the turn.
     - Remove the pending and its `pendingQueue` row.
     - Clear quiet, hard, absolute, stop-grace and activity-quiet timers;
       reset `_stopGracePending`; remove the `stop-hook` listener.
     - Do **not** defer on `_openQuestions`: the query is over.
     - Recompute `inFlight` and move the primary ledger entry to `resolved`.
     - When nothing is pending, run the same idle cleanup as `_finalizeTurn`
       (staging purge, `_pendingSubagentStarts = []`).
     - Log `cli-turn-api-error`, **reject**, then emit `idle`. Rejecting first
       matters: the ceilings are already cleared, so a throwing listener must
       not be able to strand the turn.
     - `apiError === 'oauth_org_not_allowed'` rejects with the existing
       `AUTH_DISABLED` error (same message and code as
       `_rejectPendingTurnsAuthDisabled`) and logs
       `cli-auth-disabled-detected source=stop-failure`. This keeps the
       operator-only contract (the dispatcher notifies the operator);
       otherwise StopFailure would pre-empt the pane detector.
     - Every other kind rejects with
       `Error("Claude ended this turn with an API error")`,
       `code = 'CLAUDE_API_ERROR'`, `apiError = <kind>`. The kind is not in
       the message, so no consumer's text classifier can match it
       (`server_error`, `rate_limit` and `invalid_request` would).
7. **No pending matched.** Log `cli-stop-failure-unattributed`:
   - `reason` is `own-cycle` (an anchor entry exists) or
     `no-matching-pending`, plus `pending_count` and `anchor_msg_id` when
     known.
   - If `_failureAnchors` has the `prompt_id`, consume that entry (once) and
     emit `api-error { apiError, anchorMsgId, sessionId, backend }`.
     `anchorMsgId` is null for a cycle that picked up no follow-up (a wakeup);
     the consumer then only ends the cycle's visuals.
   - Anchors come only from non-primary inputs picked up by a prompt that
     owned no pending turn. A late StopFailure for a turn that already settled
     (by timeout, activity-quiet, interrupt or disconnect) therefore never
     produces a second reply.
   - `idle` is not emitted, matching a no-pending Stop.
   - `ProcessManager` maps `api-error` to a new `onApiError` callback.
8. **Telemetry flag for unknown classes.** A class outside the pinned enum
   is reported as `'unknown'` with `api_error_unlisted: true`, a typed bool
   in Polygram's schema. A CLI bump that adds classes therefore stays
   visible.
9. **No redelivery and no retry.** The drop-confirm sweep is not armed. A
   queued follow-up is still in claude's own queue and runs as its own cycle.

### 3.2 Polygram

1. **`classify`.** `CLAUDE_API_ERROR` is checked before the `CODES` lookup.
   The kind lookup is prototype-safe (`Object.hasOwn` on a frozen map). Every
   shape has `isTransient: false` and `autoRecover: null`. Copy:
   - temporary (`server_error`, `overloaded`, `rate_limit`, `unknown`, and
     any unmapped kind): "☁️ Claude's API kept failing, even after retrying,
     so I couldn't finish this. Please try again in a few minutes." This is
     the copy the incident gets: expired CLIProxy OAuth arrives as
     `server_error`.
   - account or configuration (`authentication_failed`,
     `cloud_credential_error`, `verification_required`, `billing_error`,
     `account_on_hold`, `model_not_found`): "🔑 Claude refused this request
     because of an account or configuration problem on my side, so I
     couldn't finish this. Please try again later." It names no billing
     detail and makes no claim that anyone was notified.
   - `invalid_request`: "⚠️ Claude rejected this request, so I couldn't
     finish it. If it keeps happening, send /new to start a fresh session."
   - `max_output_tokens`: "⚠️ Claude's reply hit its output limit and
     stopped. Ask me to continue, or split the request into smaller steps."
   - `oauth_org_not_allowed` arrives as `AUTH_DISABLED` from Orchestra. On the
     no-pending path Polygram maps it to the `AUTH_DISABLED` shape
     (`userMessage: null`).
2. **`classifyTurnEndError`.** For `CLAUDE_API_ERROR` the reactor is `ERROR`
   and the in-bubble suffix stays ("stream interrupted" marks a partial
   preview). The separate "⚠️ stream interrupted" message after delivered
   replies is skipped (`suffixMessage: false`), so the classified reply is
   the one error-class message.
3. **Dispatcher.**
   - Live turns use the existing catch path: the inbound is marked `failed`
     (not replayed), `handler-error` now also carries `api_error_code`, and
     the classified reply goes to the user's message.
   - Replays (boot replay during an outage) send the classified copy instead
     of the generic "interrupted… rephrase or simplify".
   - `isAutoResumable` is false for this code and the startup retry does not
     apply, so nothing is retried automatically.
4. **`onApiError`** (a no-pending cycle that carried a user's follow-up):
   1. End the session-feedback cycle (typing and the anchor 🤔), in its own
      try block so a failure there cannot cost the notice.
   2. Skip the send when there is no bot, the daemon is shutting down, or the
      session was just aborted.
   3. Otherwise send the classified message as a reply to `anchorMsgId`,
      with `allow_sending_without_reply` and the thread id, and meta
      `source: 'error-reply'`, `sessionKey`, `sourceMsgId`.
   4. Log `cli-cycle-api-error`. `outcome` is one of `replied`, `no-anchor`,
      `bad-anchor`, `auth-disabled`, `suppressed`, `no-bot`,
      `shutting-down` or `aborted`.
5. Consume `@shumkov/orchestra@0.11.2`; release Polygram 0.41.4 (patch).

### 3.3 What the user sees, and when

- A message on a dead API: the CLI's own retry window (about 3 minutes in
  production), then one reply to that message with the copy above. Before:
  25–30 minutes, then "⏱ went quiet".
- A follow-up sent during that window: its ✍ clears when the first turn fails.
  It runs as its own cycle and, after its own retry window, gets its own
  error reply. It is not swallowed.
  - Known cosmetic race: the first turn's catch/finally clears autosteered
    reactions asynchronously and can wipe the follow-up's 🤔. Typing and the
    reply are unaffected.
  - If ndjson ordering inverts (UPS(P2) is written before StopFailure(P1)),
    the follow-up cycle starts with `hasPending: true`, so its typing and 🤔
    do not start. Its anchor entry is still recorded, because no pending owns P2,
    so its failure is still answered. Accepted as rare: both hooks are
    separate processes, and the queued prompt is dequeued only after the
    failure is processed.
- A follow-up folded into the failing query at a tool boundary (same
  `prompt_id`) is part of that turn. The turn's single error reply, on the
  first message, covers it.
- A message after the failure: a fresh primary turn. If claude is still
  retrying a queued cycle, the pane heartbeat (`esc to interrupt`) counts as
  activity, so the delivery watchdog waits instead of rewriting.
- A turn that already delivered its final answer, then failed: no error. It
  resolves as answered.
- The CLI recovers within its retry window: the normal answer, no error.

## 4. Alternatives rejected

- **Tail the session JSONL for `isApiErrorMessage`.** JSONL is internal;
  hooks are the documented surface and the hook tail already exists. A JSONL
  tail would need its own lag handling and cycle identity.
- **Match the pane for "API Error:".** A reply can contain that text, and the
  TUI wording is not a contract. The auth-disabled detector needs a two-poll
  debounce for exactly this reason.
- **Treat StopFailure like Stop** (grace plus last-message fallback). That
  would deliver "API Error: 500 … gateway (host)" as the answer. The queued
  follow-up's UPS would also cancel the grace, delaying the error by one
  retry window per queued message.
- **Reject every pending on any StopFailure** (the `AUTH_DISABLED` drain
  shape). Simpler, but it fails a turn queued behind a foreign cycle.
  `prompt_id` costs one field.
- **Resolve with `result.error`.** Polygram's `result.error` path
  pattern-matches strings. Rejecting with a code reuses the `TURN_TIMEOUT` /
  `AUTH_DISABLED` flow.
- **Lower `CLAUDE_CODE_MAX_RETRIES`**, or shorten the ceiling. That is a
  retry-policy change (out of scope) and would cut legitimate long turns.

## 5. Failure modes

| Case | Behaviour |
|---|---|
| ndjson lag: StopFailure(P1) after UPS(P2) | The P1 pending still matches by `prompt_id`; P2's follow-up is still answered; P2 starts with `hasPending:true` (no typing/🤔). |
| StopFailure for a turn that already settled | No pending matches and no anchor entry exists for a prompt that owned a pending, so it is logged and nothing is sent. |
| Follow-up cycle answered, then its closing request fails | The answer cleared the anchor `msgId`; `api-error` ends the visuals only, nothing is sent. |
| /stop, then a new turn fails fast inside the grace | Only turns in the interrupt's snapshot defer; the new turn fails normally. |
| A listener throws during the settle | The turn has already been rejected. |
| Subagent API error | Handled as SubagentStop; the parent turn is untouched. |
| Two pendings (stdinLock contract broken) | Only those whose `_promptId` matches settle. |
| Reply delivery in flight | Decision deferred to the delivery's settlement; the API error wins over finalize/timeout. |
| Final reply already delivered | Resolves as answered; no error message. |
| Interim reply only | Fails; one classified reply (no separate suffix message). |
| /stop during retries | No StopFailure (verified); if one races an armed interrupt grace, the interrupt resolution wins. |
| Retry succeeds | No StopFailure; normal finalize (verified). |
| UPS line lost or no `prompt_id` | Logged as unattributed; the ceilings remain the backstop (residual gap, measurable via the event). |
| Org-disabled account | Pending turn: `AUTH_DISABLED` (dispatcher notifies the operator, chat silent), as today but faster. A no-pending cycle only logs `outcome=auth-disabled`; the next user turn notifies. |
| Hook stream dead | Unchanged: the ceilings end the turn. |
| Older Orchestra (no StopFailure) | Polygram's new code is dormant. |
| Water (other consumer) | After it upgrades, its classifier maps the code-free message to its generic "something went wrong" copy. Not upgraded here. |

## 6. Verification plan

- **Orchestra unit (TDD, red on 0.11.1):** "a turn whose model request ends
  in a synthetic isApiErrorMessage server_error is not left silent until the
  ceiling". Real-shaped payloads go through `normalizeHookEvent`. Plus:
  - hook registration and parsing (enum clamp, `promptId`);
  - fold UPS with the same `prompt_id`;
  - foreign `prompt_id`, which leaves the pending alone;
  - a queued follow-up cycle, which emits `api-error` with the follow-up
    anchor exactly once;
  - a late StopFailure after a timeout, which emits nothing;
  - a final-reply turn, which resolves;
  - an interim-only turn, which rejects;
  - subagent StopFailure, which drains its start and lets the parent's Stop
    finalize;
  - `oauth_org_not_allowed`, which rejects `AUTH_DISABLED`;
  - deferral, where the API error wins over finalize;
  - an interrupt grace that is armed, which the interrupt wins;
  - `send()` after the failure, which is a fresh pending;
  - `ProcessManager` forwarding.
- **Polygram unit:**
  - the classifier: per-kind copy, prototype safety, non-transient;
  - `classifyTurnEndError`;
  - the dispatcher: one classified reply on live and replayed turns,
    `api_error_code` on `handler-error`, no auto-resume;
  - the `onApiError` callback: reply to the anchor plus endCycle; skips
    without a bot, on shutdown or abort; `AUTH_DISABLED` sends nothing;
  - the full suite.
- **Real CLI, stub, no paid call** (`--orchestra <candidate>`):
  - always-500 rejects within the retry window with the copy above;
  - `--inject` produces `api-error` with the follow-up's anchor;
  - `--followup` is a fresh turn, with no `cli-delivery-rewrite` or
    `-escalate`;
  - flaky resolves with no error; 401 maps to the account copy;
  - subagent: no hang;
  - `/stop` is unchanged.
- **Pin discipline:** this adds a dependency the next CLI bump must re-check
  (StopFailure registration, the `prompt_id` semantics across folds and
  queued prompts, `agent_id` only on subagents). The spike is listed in
  `scripts/spikes/README.md` for pin bumps. Registering one more hook on the
  same binary is not itself a pin change; PreCompact and PostCompact were
  added the same way.
- **Not covered here:** deployment, a live CLIProxy outage, and how Telegram
  renders the reply (it uses the existing `error-reply` path).

## 7. Review record

Four reviewers (lifecycle, Polygram integration, simplicity/scope, failure
modes/privacy). Folded in:
- replied turns resolve;
- the anchor comes only from non-primary pickups of prompts that owned no
  pending turn, and is consumed once;
- `oauth_org_not_allowed` becomes `AUTH_DISABLED`;
- a subagent StopFailure is a SubagentStop;
- the no-`prompt_id` fallback is dropped;
- the enum is clamped and the lookup is prototype-safe;
- no kind in `err.message`;
- the exact clear set and idle cleanup;
- deferral precedence;
- interrupt wins;
- replay copy and `api_error_code` telemetry;
- the suffix handling;
- send protections for `onApiError`;
- copy collapsed to four groups, without notification promises;
- the change to Orchestra's own `classify.js` is dropped (only `sdk-process`
  uses it);
- the extra spike cells (`--agent`, subagent, watchdog).

Kept against one suggestion: the in-flight-delivery deferral, which is
reachable through the bridge ack timeout.

Code review of the diff, four further reviewers (lifecycle, Polygram
integration, test quality, silent failures). Folded in:
- reject before emit;
- a bounded anchor map instead of a single slot;
- a delivered final answer clears the anchor;
- the `/stop` race scoped to the interrupt's own snapshot;
- stale Stop data cleared before resolving;
- each turn re-checked in the settle loop;
- the unlisted-class flag;
- `cli-stop-failure-ignored`;
- the replay send guarded against null copy;
- `endCycle` isolated, plus the `bad-anchor` and `auth-disabled` outcomes;
- tests for a late StopFailure while a newer turn runs, inverted hook order,
  deferral resolving or beating a ceiling, an answered follow-up, and a turn
  started after `/stop`.
