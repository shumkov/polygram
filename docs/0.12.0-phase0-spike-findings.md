## 0.1 — Main spike (hooks + channels co-existence)

**Status: PASS.**

Proved: hooks fire alongside `--dangerously-load-development-channels` on the pinned claude binary, AND channel notifications still arrive in the same session.

Single-turn prompt ("Run `echo hello world` via Bash, then reply confirming what you did") produced:

```
✓ UserPromptSubmit                    (channel notification → hook)
✓ PreToolUse  ToolSearch  (dur: -)
✓ PostToolUse ToolSearch  (dur: 1ms)
✓ PreToolUse  Bash        (dur: -)
✓ PostToolUse Bash        (dur: 374ms)
✓ PreToolUse  mcp__polygram-bridge__reply
✓ PostToolUse mcp__polygram-bridge__reply (dur: 10ms)
✓ Stop                                (turn-end, after rc.41 H4 grace)
```

Channel events: `bridge-ready`, `init`, `tool-use`, `tool-dispatch` (reply delivered), `result`.
Reply text successfully delivered to the toolDispatcher: `"Ran \`echo hello world\` — output was \`hello world\`."`

**Finding 0.1.A — Stop hook race [CONFIRMED, fix understood, Phase 1 action item added to plan].**

Mechanics confirmed: the `Stop` hook fires AFTER the channel `result` event. In all 3 successful run.mjs trials, `Stop` was present in the on-disk ndjson but only landed in the in-memory tail when the spike added a 2s grace + disk reconciliation pass.

**Why this matters for production CliProcess:** in 0.12 the plan declares `Stop` as the **authoritative turn-end signal** (plan §"Reaction model"). If CliProcess resolves turns on the channel `result` event without waiting for `Stop`, three downstream concerns:

1. `Stop`'s `last_assistant_message` fallback (rc.41 H4 — text recovery when result text is empty) is unreachable.
2. Cost/usage metrics carried in `Stop` payload land too late to attribute to the turn.
3. Any future Phase that depends on `Stop` as the canonical close marker silently breaks.

**Phase 1 action (added to plan):** implement `stopGraceMs` (default 2s) in CliProcess's `_resolveTurn` — when channel `result` fires, schedule `Stop` to be the authoritative close; if `Stop` arrives within `stopGraceMs`, use its data; if not, fall back to the channel `result` payload alone. Mirrors `tmux-process.js:H4` from rc.41. ~15 LoC.

The spike's [run.mjs](../scripts/cli-driver-spike/run.mjs) already implements both the 2s grace AND a disk-reconciliation pass — production CliProcess only needs the first; the disk-pass is a spike-only diagnostic.

**Finding 0.1.B — Misleading "no MCP server" banner.** Claude TUI prints `server:polygram-bridge · no MCP server configured with that name` even when the bridge is working perfectly. Already documented in the 0.11 plan's risk register; re-confirmed here. No action needed — cosmetic only.

## 0.3 — Subagent observability (SEC-05)

**Status: PASS — SEC-05 finding resolved.**

Two questions, both empirically answered YES:

| Question | Answer | Evidence |
|---|---|---|
| Does `SubagentStop` fire for `Agent` tool spawns? | YES | `agent_id=a2b63eba768435947`, `agent_type=general-purpose` |
| Does `PreToolUse` fire for tools called INSIDE a subagent (SEC-05)? | **YES** | Bash call inside subagent context emitted PreToolUse with `agent_id=a2b63eba768435947`, `agent_type=general-purpose` |

This resolves [SEC-05 from the design review](./0.12.0-cli-driver-plan.md#open-questions-resolved-here): subagent inner activity (Bash/Read/Write fired by Agent-spawned subagents) IS visible to polygram via hooks. The `agent_id` field on the inner PreToolUse correlates to the outer SubagentStop, enabling lifecycle pairing.

**Finding 0.3.A — Cold-spawn flake [INVESTIGATED + ROOT-CAUSED].**

Original observation: 2/4 spike runs timed out on first attempt; claude TUI sat at the prompt with zero hook activity. Retry after killing orphan tmux sessions worked. Initial hypothesis (stale daemon socket state) turned out to be wrong.

**Root cause** (verified empirically via [`probe-cold-spawn.mjs`](../scripts/cli-driver-spike/probe-cold-spawn.mjs)):

Race between two handshakes that polygram conflates:
1. **Daemon ↔ bridge handshake** — bridge subprocess connects to daemon's unix socket and sends `hello`. polygram's `_waitForBridgeHandshake` resolves when this fires (`channels-process.js:626`).
2. **Bridge ↔ claude MCP handshake** — claude's MCP client discovers the bridge as a server (sends `Initialize`, then `ListTools`), registers `claude/channel` capability. This happens independently and asynchronously.

When (1) completes BEFORE (2), polygram considers the bridge ready and the spike script immediately calls `proc.send()` → bridge writes `user_msg` → bridge calls `mcp.notification()` to claude → **claude silently drops it because its server registration table hasn't included `polygram-bridge` yet**.

**Bridge logs prove the daemon side is fine:**
- Failed run: bridge `user_msg-notify-ok` fires at boot+15ms; then 180s of silence (claude never processed it).
- Working run: bridge `user_msg-notify-ok` fires at boot+153ms; claude processes it within ~30s.

The handshake → user_msg-rx gap correlates with success: **<50ms gap → flake**, **>100ms gap → reliable**.

**Empirical proof:**

| Scenario | Trials | Succeeded | Flaked |
|---|---|---|---|
| Spike sends user_msg immediately after `start()` (no delay) | 3 | 2 | **1 (33%)** |
| Spike sends user_msg after 500ms delay | 3 | **3** | 0 |

The 500ms delay reliably eliminates the flake. Probe artifacts: `<TMPDIR>/cli-probe-A-*/` and `<TMPDIR>/cli-probe-B-*/`.

**Production impact on 0.11.0-channels:** The race exists in production today. shumorobot avoids it because real-world startup paths have natural delay (large cwd, agent file loading, dialog handling) that lets claude finish registration. But the race is latent — any future change that speeds up startup could regress turn delivery.

**Phase 1 fix (added to the plan):** add a deterministic gate after `_waitForBridgeHandshake`. Two options, both viable:
- **Option A (cheap)**: 500ms `setTimeout` after handshake before signaling ready. Empirically proven; arbitrary number.
- **Option B (deterministic)**: instrument bridge.mjs to log when claude sends `ListToolsRequest` (which fires only AFTER claude registers the bridge as an MCP server). Bridge writes a new `kind: 'mcp-ready'` message to the daemon socket. Polygram's `_waitForBridgeHandshake` waits for BOTH `bridge-ready` AND `mcp-ready` before resolving. No magic delay; robust to changes in claude's MCP-init speed.

Recommend **Option B** for Phase 1 — the cost is ~20 LoC across bridge + channels-process, and it eliminates the arbitrary delay.

## 0.4 — Hook lag measurement

**Status: SOFT PASS (functional, slower than expected).**

Measured `t_emit_in_memory - polygram_received_at_ms` across 18 hook events from a 6-Bash-call prompt:

| Metric | CliProcess (this spike) | rc.42 tmux baseline | Within target? |
|---|---|---|---|
| Median | **426 ms** | 14 ms | NO (~30× higher) |
| p95 | **1041 ms** | 22 ms | NO (~47× higher) |
| Max | 1041 ms | — | — |

**Per-event type:**
```
UserPromptSubmit  count=1   median=1041ms
PreToolUse        count=8   median=630ms   p95=926ms
PostToolUse       count=8   median=381ms   p95=711ms
Stop              count=1   median=5ms
```

**Soft PASS rationale:** lag is functionally fine — well under the 8000ms heartbeat threshold and 45000ms STALL threshold the reactor uses. UX impact is zero. The measurement methodology is identical to rc.42's [h1-hook-lag-diag.mjs](../scripts/spikes/h1-hook-lag-diag.mjs), so the divergence is real, not artifactual.

**Finding 0.4.A — Lag divergence vs tmux baseline [INVESTIGATED, root cause unclear, NOT BLOCKING].**

Burst-contention hypothesis tested via [`probe-lag-baseline.mjs`](../scripts/cli-driver-spike/probe-lag-baseline.mjs): compared 1-Bash trial vs 6-Bash burst trial. **Hypothesis NOT supported** — single-call median (560ms) was HIGHER than burst median (253ms). Per-type breakdown shows lag is steady-state, not load-correlated:

| Trial | UserPromptSubmit | PreToolUse | PostToolUse | Stop |
|---|---|---|---|---|
| Single-call (Run A) | 331ms | 70ms | 858ms | 426ms |
| 6-Bash burst (Run B) | 905ms | 227ms | 169ms | 280ms |

So the original 4 hypotheses (bridge child overhead, helper subprocess contention, fs.watch slowness under load, burst-related) all unverified.

**Remaining plausible causes** (need production data to discriminate):
- **macOS fs.watch transient slowness** — known to have second-level latency variance.
- **Environmental noise** — spike ran in worktree #2 with worktree #1 attached, fresh `npm install`, etc. Not representative of clean production env.
- **Sample size noise** — 8 events per trial is too few for stable medians.

**Why this is not blocking 0.12:** functionally the lag is fine — even 1s p95 is well under the 8s heartbeat threshold and 45s STALL threshold. UX is unaffected. The rc.42 baseline (14ms median) was measured under different conditions; we can't rule out that the spike environment is just noisier.

**Phase 5 soak gate (added to the plan):** instrument CliProcess with the same `t_emit_lag` per-event metric. Production soak data is the discriminator. Tag-out gates on `median < 2s` and `p99 < 5s` — both well above what we're seeing here, both well below user-visible thresholds. If production data shows worse than spike, revisit. If better, the spike was just noisy.

## Phase 1 action items derived from Phase 0 investigation

Three concrete Phase 1 implementation tasks were surfaced by spike findings and added to the plan:

1. **(Finding 0.1.A) `stopGraceMs` for authoritative turn-end** — implement rc.41 H4 pattern: when channel `result` fires, schedule `Stop` to be authoritative; if Stop arrives within ~2s, use its data; else fall back to result payload. ~15 LoC in CliProcess `_resolveTurn`.

2. **(Finding 0.3.A) MCP-ready gate after bridge handshake** — fix the cold-spawn race. Recommended: instrument bridge.mjs to send a `kind: 'mcp-ready'` daemon message when claude's first `ListToolsRequest` arrives; polygram's `_waitForBridgeHandshake` waits for BOTH `bridge-ready` AND `mcp-ready` before resolving. Eliminates the empirically-confirmed 33% first-turn flake. ~20 LoC across bridge.mjs + channels-process.js.

3. **(Finding 0.4.A) Hook-lag soak instrumentation** — instrument CliProcess to log per-event `t_emit_lag` to events DB. Phase 5 soak gate: median < 2s and p99 < 5s. Discriminates between "spike was noisy" and "real CliProcess regression."
