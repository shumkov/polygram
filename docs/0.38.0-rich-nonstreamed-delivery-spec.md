# Rich delivery on the non-streamed reply path

Status: **draft — for review before implementation**

## Problem

A reply whose content qualifies for rich rendering is delivered as plain text
whenever the turn's answer arrives without having streamed. The gate says yes;
the delivery path never asks it.

Production evidence — chat `-1003369922517` ("Shumabit@UMI"), thread 4572, last
60 outbound messages:

| `source` | content qualifies | rendered rich | count |
|---|---|---|---|
| `channels-tool-dispatcher` | yes | **yes** | 41 |
| `channels-tool-dispatcher` | no | yes (other trigger) | 3 |
| `channels-tool-dispatcher` | no | no | 9 |
| `bot-reply-stream` | yes | **no** | 3 |
| `bot-reply-stream` | no | no | 4 |

**Methodology caveat — the table undercounts streamed rich.** It joins messages
to `rich-message-sent` on `message_id`, and the *edit*-path event
(`rich-edit.js:206-211`) carries no `message_id` and no `transport`, so a
streamed rich delivery can never match. Of 236 rich events in this DB, 201 carry
a message_id (`transport: 'send'`) and **35 are streaming edits** that this join
structurally cannot attribute. So "`bot-reply-stream` never renders rich" is
false as a general claim: streamed replies do go rich, via edit. The correct
claim is narrower and is what this spec fixes — **the non-streamed branch never
does**.

Msg 5964 is the reported case: 1451 chars, two `##` headings and
a five-column markdown table. Run through the renderer it yields
`usedRich: true` and five blocks (`heading, paragraph, table, heading,
paragraph`). It shipped plain. Msg 5967, five minutes later in the same thread
via the reply tool, rendered rich with 10 blocks.

`richText` and `streamPreview` are both `true` for this chat, so neither is the
cause.

## Root cause

Rich delivery was built twice and wired to two of three paths:

- **Streamer** — `streamer.js` finalize plus the `send`/`edit` callbacks at
  `polygram.js:1693-1752`. Rich works.
- **Reply tool** — `createRichDeliveryFactory` (`lib/telegram/rich-dispatch.js`),
  wired at `polygram.js:4084`. Rich works.
- **Non-streamed final reply** — `polygram.js:2909-2931`, guarded by the
  "Not streamed (response too short — never crossed minChars)" branch at
  `polygram.js:2887`. It chunks and calls `deliverReplies`, and
  `lib/telegram/deliver.js` contains no rich support whatsoever — no gate, no
  renderer, no sender. **Never wired.**

### This was a decision, not an oversight

`polygram.js:1552-1562` states it outright: *"A reply that never crosses
minChars … and any non-streaming send path … never render rich even when
richText is on and the content qualifies. Those delivery paths intentionally
remain plain."*

So this spec argues against a prior deliberate choice rather than filling a hole
someone forgot. The case for revisiting: that choice was made when rich was new
and unproven, to bound exposure. Rich has since produced 171 `rich-message-sent`
events in this chat alone with no capability latch trip, and the cost of the
bound is no longer "rich is limited" but "identical content is formatted two
different ways depending on whether the agent happened to call the `reply`
tool" — which reads as a bug to the user and cannot be reasoned about from the
chat. **The comment at `polygram.js:1552-1562` must be updated by this change**;
leaving it would leave the code documenting the opposite of what it does.

Note the trigger is not "short", and it is not `minChars` either. The streamer
tests the **full snapshot** length (`streamer.js:341-342`), so a single
1451-char chunk would have opened a bubble. This branch is reached when no
stream chunk arrived at all. Telemetry for msg 5964's turn (`565823d0`):

```
cli-turn-resolved-by-stop  reply_count: 0, via_text_fallback: true
cli-resolve-delivery       branch: "zero-reply", already_delivered: false,
                           reply_count: 0, interim_count: 0
```

The agent never called the `reply` tool. Orchestra's `CliProcess` (the
`@shumkov/orchestra` package, not this repo) resolved the turn through its
text-fallback and handed polygram the final assistant text; polygram delivered
it through this branch. That is why a 1451-char structured answer took a path
whose comment says "too short" — length was never consulted.

This also explains the clean split in the table above: replies the agent sends
by calling `reply` go through the dispatcher and render rich; replies it simply
*ends the turn with* go through here and never do. The user sees the same
assistant writing the same markdown, formatted two different ways, with no
pattern they can act on.

### Proving it was this branch, not another

`source: 'bot-reply-stream'` alone does **not** identify the branch. Five call
sites write that exact tag and three of them deliver reply bodies: the
streamer's plain open (`:1734`), the streamed-redeliver (`:2848`), the
orphaned-draft redeliver (`:1873`), and this one (`:2927`). A row carrying it
could equally be a streamed bubble whose rich *edit* was refused and fell back
to plain — which this change would not fix.

Settled against the events table for turn `565823d0`. All of the following are
**zero** in the turn window:

- `stream-seen` — the cli backend emits one per `stream` tool call. Zero means
  the streamer never went live, so no streamed path ran.
- `telegram-stream-redeliver`, `stream-orphan-finalized`,
  `stream-orphan-redelivered` — the two out-of-scope redeliver paths.
- `rich-content-fallback`, `rich-capability-strike`, `rich-capability-latched`,
  `rich-styling-fallback` — rich was never attempted and refused.

The agent called neither `stream` nor `reply`, so the turn resolved through
orchestra's text fallback into this branch. That is also the correct statement
of the trigger: **not** "never crossed minChars" (an SDK-backend mechanism; on
cli a single ≥30-char stream call opens the bubble), but "the agent called
neither `stream` nor `reply`".

Both arms of the branch are now tagged (`bot-reply-final-rich` and
`bot-reply-final`), so this ambiguity does not recur.

## Design

**Reuse `createRichDeliveryFactory`; do not hand-roll a second implementation.**

Its contract already fits this call site exactly:

```
makeDeliverText({ chatId, threadId, allowedRoots })
  -> deliverText({ text, replyToMessageId, meta })
  -> { handled: true } | { handled: false, text?: <media-stripped body> }
```

`handled: false` means "caller delivers plain itself". The change at
`polygram.js:2909` becomes: try `deliverText` first; on `handled: false`, run
the existing chunk-and-`deliverReplies` code.

**The decline does NOT always carry `text`.** `rich-dispatch.js:151` — the
chat-flag-off branch, i.e. most of the fleet — returns a bare
`{ handled: false }`. Feeding that `undefined` into `chunkMarkdownText` would
lose the reply entirely for every non-rich chat. The fallback must therefore be
`out.text ?? <today's expression at polygram.js:2916-2918>`, which is
byte-identical to current behavior in both directions: the returned body is
produced by the same `stripMediaMarkdown` call, and the `??` arm is literally
today's code. This is the single highest-risk detail in the change and needs its
own test.

Why reuse rather than build on `toRichPayload` (`polygram.js:1597`) and
`sendRichWithStylingRetry`: the factory already implements the per-chat gate,
the capability latch, the `richMaxLen` bound, the styling latch with
flatten-and-retry, and the fallback classification — and it is the path with
41/41 production successes in this very thread. A second implementation would
have to re-derive all of it and would drift.

`richSendMessage` is module-scope (`polygram.js:484`, assigned in `main()` at
`3693`), so it is already reachable from `handleMessage`. The factory instance
must become reachable the same way — assigned to a module-level binding in
`main()` rather than only passed into the channels dispatcher.

### Text-only on this path

Call with `allowedRoots: null`, so `makeMediaWiring` is skipped and the render
runs on the stripped body.

This is deliberate and matches what the path does today: `polygram.js:2916-2918`
already strips media markdown for rich-enabled chats, so media on this path
degrades to caption text right now. Keeping it that way means the change adds
*rendering* and no new media trust surface — no new resolver, no new preflight,
no TOCTOU boundary to get right. It also matches the reasoning already recorded
at `polygram.js:4072-4080` for consumed replies: a reply should not obey
different media rules depending on whether a preview happened to be live.

Media on this path stays a separate question, out of scope here.

### Size and chunking

The factory returns `handled: false` when the body exceeds `richMaxLen`, so
oversized replies keep today's chunked-plain behavior untouched — no new failure
mode at the top end.

One intended behavior change in the middle band, and it is wider than it first
looks: `TG_CHUNK_BUDGET` is **3,500** (`polygram.js:247`) while `RICH_MAX_LEN`
is **32,768** (`rich.js:1294`). So a large reply that is several plain bubbles
today becomes a single rich bubble.

Review raised the fair objection that "the reply tool already does this" was
true of the code but unproven in production, and proposed capping v1 at
`TG_CHUNK_BUDGET` until there was evidence. Measured instead — 236 rich sends
in this DB:

```
max 9508 · p95 4111 · median 1235 · over TG_CHUNK_BUDGET: 15
```

So the reply-tool path already ships rich bubbles well past the chunk budget,
up to 9.5k, fifteen times over. The band is **not** new behavior, and capping
would have made this path diverge from the one it is meant to match. Keep
`RICH_MAX_LEN`. Still a user-visible change worth a release note.

### Anchoring and double-post

`deliverText` takes `replyToMessageId`, so the reply keeps quoting the user's
message exactly as `deliverReplies` does on `chunks[0]`.

The safety argument must NOT be "no bubble exists yet" — that is false in
general. `onAssistantMessageStart` → `forceNewMessage` (`lib/sdk/callbacks.js:268`)
leaves earlier bubbles from the same turn on screen with state back to `idle`
(`preserveIntermediateBubbles` defaults true, `polygram.js:1817-1827`), and an
`interim: true` reply-tool reply detaches the preview leaving its bubble
standing (`live-preview.js:412-418`).

The correct argument is narrower: no bubble holds **this body**. Reaching 2909
requires `fin.streamed === false`, and of the three origins of that value
(`streamer.js:886`, `:891`, `:898`) only the idle one (`:898`, `msgId: null`) is
reachable in this tree — `consume` always reopens via `forceNewMessage`,
`detachCurrentPreview` early-returns on `finalized`, the streamer is per-turn,
and channels turns short-circuit at `result.alreadyDelivered`
(`polygram.js:2655`). Tests must pin the `forceNewMessage` and interim-preview
shapes explicitly, not just the empty-streamer shape.

### Telemetry: the fix must be provable

`rich-message-sent` (`rich-send.js:181-193`) carries no `source` field, and the
streaming rich open already passes `outMetaBase` — so it emits events whose
message row also says `source: 'bot-reply-stream'`. "First appearance of
rich-message-sent for this source" is therefore not a discriminator.

This call site gets its own source tag, `bot-reply-final-rich`, following the
existing `bot-reply-stream-open-rich` convention (`polygram.js:1710`). That
makes the fix directly observable in the messages table.

## Scope

**In:** the non-streamed final-reply branch, `polygram.js:2909-2931`.

**Out, and why:**

- `polygram.js:1866` (orphaned-draft redeliver) and the streamed-redeliver near
  `polygram.js:2841` — both redeliver text the streamer already owned, under
  failure/oversize conditions where chunked plain is the deliberate escape.
- `lib/telegram/process-agent-reply.js` — autonomous wakeup, auto-resume and
  autosteer. Documented as intentionally plain; changing it is a separate
  decision with its own blast radius.
- Cron and IPC sends.

Each is a real gap. None has the production evidence this one has, and bundling
them would make the diff impossible to review against the one behavior we can
actually verify.

## Failure modes

| Mode | Consequence | Mitigation |
|---|---|---|
| Rich send fails at the API | reply lost | factory returns `handled: false` on every non-success; caller falls through to the existing plain path with the stripped body |
| Capability latch trips mid-turn | rich attempted against a server that refuses | factory re-reads `getRichKnownUnsupported()` per call, same as the reply tool |
| Double delivery (rich lands AND plain fallback runs) | user sees the answer twice | Mostly closed by the single decision point — plain runs only on `handled: false`. **Not airtight**, and honestly so: `rich-send.js:138-157` documents a send that lands a bubble but returns no message_id, which reports `wentRich: false` → `handled: false` → the plain arm re-sends the same body. Upstream accepts this as the quieter of two failures; this change widens exposure because the branch fires on ordinary turns rather than only reply-tool calls. Inherited, not introduced |
| Rich attempt throws | reply lost entirely — the plain arm owns the only copy | the factory is *contracted* not to throw but its styling ladder evaluates `blocksAreStyled`/`flattenStyledBlocks` outside any try, and `process-agent-reply.js:185-201` already refuses to trust that contract for the identical call. Wrapped in try/catch → `richOut = null` → plain runs |
| Media markdown reaching the bubble as a raw path | local filesystem path shown to user | body is stripped before render *and* before fallback — the factory strips once at its entry (`rich-dispatch.js:155`) and returns that same body |
| Behavior change for non-rich chats | chats that never opted in get different delivery | factory returns `handled: false` immediately when the chat flag is off — but with **no `text`**, so the `??` fallback above is what preserves them |
| `linkPreview: false` silently ignored | opted-out chats get link previews back on this path — `sendRichMessage` is not in the link-preview method list (`api.js:234-241`) | zero chats set it in production today (checked); already true of the reply-tool path, so this aligns rather than diverges. Note it, do not special-case |
| Media-only reply renders as silence | body strips to `''` → no chunks (`deliver.js:44`) and `usedRich:false` → nothing sent | **pre-existing on this path**, not introduced here. The reply tool guards it with `MEDIA_ONLY_FALLBACK_TEXT` (`polygram.js:4159-4165`); this path never has. Out of scope, but it qualifies the "makes the two paths agree" claim |
| Transcript row content changes | the rich path stores the RAW `sourceText` (`rich-dispatch.js:246-248`), so absolute local paths land in the DB and in the agent's preloaded history, where today N media-stripped chunks land | accepted and already true of the reply-tool path, whose comment records the reasoning; the background secret sweep covers the row. Release-note item |
| Capability-latch asymmetry | this path reads `richSendKnownUnsupported` while the streamed path's rich rides the EDIT latch, so a server with rich edits but no `sendRichMessage` makes this path pay two doomed round trips before latching | self-limiting — the latch trips and stays tripped |
| Source-shape tests break | `tests/polygram-codex-delivery-settlement.test.js:104-108` requires `const deliveryResult = await deliverReplies({…});` immediately followed by `recordTextFailures(...)` | keep those two statements adjacent inside the fallback branch; add no new `finalizeResultDelivery(` call (`:95-96` pins exactly 8) and no new `telegramDeliveryComplete = false;` (`:112-117` pins exactly 2) |

## Verification plan

**What is actually testable here, and what is not.** The call site lives inside
a ~1600-line `handleMessage` in a file with no `module.exports`, so the branch
cannot be invoked from a test. Items below that read "unit at the call site"
are therefore delivered as **source-shape assertions plus a compile check**, not
as executed behavior. That is a real limitation, not a formality: the tests
cannot catch a wrong argument value at runtime, only a wrong argument in the
text. Two things compensate, and they are what make the net worth having —
the wiring is pinned separately (deleting the `main()` assignment silently
reverts the whole fleet to plain *and* takes the reply tool's rich with it, so
it gets its own test), and the decline contract the fallback depends on is
pinned as real executed behavior against `rich-dispatch`.

The suite was mutation-tested against four broken implementations, all of which
it now kills: assignment deleted from `main()`; body truncated and anchor
dropped; syntax error appended; throw guard removed. Making the branch properly
executable would mean extracting it into a callable helper — worth doing, out
of scope here.


1. Unit: msg 5964's text through the new call site → one rich send, zero
   `deliverReplies` calls.
2. Unit: same text with `richText` off → zero rich sends, `deliverReplies`
   called with today's chunks, text byte-identical to current behavior.
3. Unit: body over `richMaxLen` → falls through to chunked plain.
4. Unit: rich send fails → exactly one plain fallback delivery, no duplicate.
5. Unit: capability latch set → no rich attempt at all.
6. Regression: the streamed path and the reply-tool path are untouched; full
   suite green.
7. Unit: chat flag OFF → `deliverReplies` receives byte-identical text to
   today. This is the `handled:false`-without-`text` case and the one that
   would silently lose replies fleet-wide.
8. Unit: the `forceNewMessage` and detached-interim-preview shapes each still
   produce exactly one send.
9. Production check after deploy, two parts — either alone is ambiguous:
   a `bot-reply-final-rich` row appears in the messages table, **and** a
   `rich-message-sent` with `transport: 'send'` carries that row's
   `message_id`. The streamed path can never produce a message_id-bearing
   rich event, so a match is unambiguous proof this call site fired.

## Open questions

1. `process-agent-reply.js` should follow, and it is smaller than this doc
   first implied: it already accepts an injected `deliverText`
   (`process-agent-reply.js:68-70, 185-211`) and the dispatcher already injects
   the rich chain into it, so wiring autonomous-wakeup and auto-resume is on
   the order of three lines rather than a new design. Deliberately not bundled
   here — those replies land when no human is watching, so they deserve their
   own change and their own production check.
2. Should the middle-band behavior change (multi-bubble plain → single rich
   bubble) be called out in the release notes? It is user-visible.
