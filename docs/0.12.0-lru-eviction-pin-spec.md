# 0.12.0 — LRU eviction-pin for live background work (spec)

**Status:** ✅ IMPLEMENTED (2026-06-09). `Process.hasActiveBackgroundWork()` (base → false;
`CliProcess` → `_bgWorkSince !== null`), `_evictLRU` pin-skip + `pinnedSkipped` forensics,
`_hasPinnedSession`/`_pinnedSessionKeys`, and the Policy-C overflow-vs-park split in `getOrSpawn`
(`lru-overflow-pinned` event). 6 tests (`tests/process-manager-generic.test.js` ×5 +
`tests/cli-process.test.js` ×1), TDD red→green.
**Issue:** `docs/0.12.0-known-issues.md` → "OPEN (latent) — LRU eviction can kill a session's live background job"
**Parent:** `docs/0.12.0-background-work-lifecycle-plan.md` (detection primitive + stall-watchdog shipped; the eviction-pin was deferred there as "can't bite shumorobot today" — this spec un-defers it)

---

## Problem (one paragraph)

`ProcessManager._evictLRU` (`lib/process-manager.js:278`) frees a session slot under
cost-budget pressure by killing the oldest session that is **not `inFlight`**. But
`inFlight` means "a turn is being processed" — it does **not** mean "this session has
a detached background job running." A session whose dispatch turn has resolved but
left a `run_in_background` shell alive (the shumorobot Music topic's 50-min SoundCloud
`listen-sync download` is the canonical case) reads as idle → evictable. Eviction calls
`oldest.kill('evict')` → tmux session dies → the background job dies, and its
"report back" autonomous-wakeup has no session to land on. The work silently vanishes.

**Latent today** only because eviction fires solely on budget pressure and shumorobot
runs ≤3 cli sessions (cost 3 each = 9 < budget 10), so `_evictLRU` never runs. It
becomes real the moment a 4th session spawns, or on the multi-chat fleet where the
budget is genuinely pressured.

## Why the fix is small

The detection primitive **already exists** (shipped rc.23/26). `_pollBackgroundWork`
(`cli-process.js:1743`) runs on the 5s pong-watchdog tick **while the session is idle**,
pane-scrapes the `⏵⏵ N shells` mode line via `hasLiveBackgroundWork()`, and maintains:

- `_bgWorkSince` — timestamp when a live background shell was first observed while idle;
  `null` when there is none. Set on first idle observation, cleared when the shell count
  returns to 0.

So **`_bgWorkSince !== null` is a ready-made, ≤5s-fresh, synchronous pin signal** for a
cli session. No new detection, no probe at eviction time. The whole fix is: teach
`_evictLRU` to skip a session that reports active background work, the same way it already
skips `inFlight`.

## Design

### 1. Expose a sync pin signal on Process

Add to the `Process` base class (`lib/process/process.js`):

```js
// Default: nothing to pin. Backends that can detect detached background work override.
hasActiveBackgroundWork() { return false; }
```

Override in `CliProcess` (`lib/process/cli-process.js`):

```js
// Cached read of the rc.23/26 idle bg-work watchdog state. ≤5s fresh (pong tick).
hasActiveBackgroundWork() { return this._bgWorkSince !== null; }
```

SDK / tmux Process keep the base `false` — see Scope.

### 2. Pin in `_evictLRU`

```js
_evictLRU() {
  let oldest = null, oldestKey = null;
  let pinnedSkipped = 0;
  for (const [k, p] of this.procs.entries()) {
    if (p.inFlight) continue;
    if (p.hasActiveBackgroundWork()) { pinnedSkipped++; continue; }   // NEW
    if (!oldest || (p.lastUsedTs || 0) < (oldest.lastUsedTs || 0)) { oldest = p; oldestKey = k; }
  }
  if (!oldest) {
    // Decision A vs B (below) lands here when the only candidates are pinned.
    this._logEvent('lru-full', { active: this.procs.size, totalCost: this.totalCost, budget: this.budget, pinnedSkipped });
    return /* false, or last-resort evict — see Decision 1 */;
  }
  // …unchanged evict + log (add pinnedSkipped to the 'evict' detail for forensics)…
}
```

### 3. Anti-starvation — **Policy C: soft budget (operator decision, 2026-06-09)**

If every non-`inFlight` session has active background work, the normal pass frees nothing.
The budget exists to cap RSS (memory), not correctness — so under that specific pressure we
treat it as a **soft** limit: spawn the new session over budget, warn, and leave the manual
reclaim to the operator. No background job is auto-killed; no new chat is blocked.

`getOrSpawn`'s eviction loop becomes:

```js
while (this.totalCost + newCost > this.budget) {
  const evicted = this._evictLRU();          // skips inFlight + pinned
  if (evicted) continue;
  if (this._hasPinnedSession()) {
    // A DURABLE blocker (live background job) is holding a slot. Don't park on it
    // (could be 50 min) and don't kill it. Overflow the soft budget + warn; the
    // operator reclaims by /reset-ing a chat of their choice.
    this._logEvent('lru-overflow-pinned', {
      active: this.procs.size, totalCost: this.totalCost, budget: this.budget,
      newCost, pinned: this._pinnedSessionKeys(),   // names so the operator knows what's running
    });
    this.logger.warn?.(
      `[pm] budget ${this.budget} exceeded (now ~${this.totalCost + newCost}): all free slots hold ` +
      `live background jobs [${this._pinnedSessionKeys().join(', ')}]. Spawning over limit — ` +
      `/reset one of those chats to reclaim memory.`);
    break;                                     // spawn anyway (soft overflow)
  }
  // No pin — the blockers are all in-flight TURNS (transient, finish in seconds).
  // Keep the existing behavior: park briefly for a slot rather than overflow.
  await this._awaitLruSlot();
  if (this._shuttingDown) { /* unchanged */ }
}
```

**Park vs overflow split (deliberate):** the existing `_awaitLruSlot` park is *kept* for the
pure all-in-flight-turns case — those are transient (a turn finishes in seconds), so waiting
is correct and avoids needless memory overflow under bursty concurrent load. Overflow is used
**only** when a durable background-job pin is what's blocking — there, waiting is wrong (the
job can run for ~an hour) and killing is what we're trying to avoid.

**Manual reclaim tooling already exists:** `pm.killChat(chatId)` + per-chat `/reset` / `/new`
(kill + respawn that chat's session). The operator drops a session by `/reset`-ing the chat
they choose. The warning names the pinned session keys so they know what's running. *(Open
sub-decision: also ping the admin chat, not just the log — see Decisions.)*

### 4. No time-based pin cap — **rejected (operator 2026-06-09)**

An earlier draft proposed expiring a pin after `bgWorkPinMaxMs` (~20 min) to self-heal a
stuck shell. **Rejected:** legitimate background jobs routinely run far longer than 20 min
(the known-issue's own examples are a 50-min SoundCloud download and a 7h job). Elapsed time
cannot distinguish "stuck/zombie shell" from "slow-but-progressing job," so *any* time cap
would un-pin — and thus make evictable — exactly the long jobs this feature exists to protect.

**Decision: the pin tracks live-shell presence only** (`hasActiveBackgroundWork()` ⟺
`_bgWorkSince !== null`, no expiry). Accepted consequence: a shell that genuinely hangs
forever keeps its session pinned → the budget stays in overflow until the operator `/reset`s
that chat. That is acceptable under Policy C (never auto-kill a maybe-slow job; overflow is a
manual + external-monitoring concern). A smarter stuck-detector (e.g. acting on the rc.26
10-min self-check's *result* rather than the clock) is possible future work, out of scope here.

## Scope

**In:** cli backend eviction-pin (the only backend with detached-shell detection).

**Out:**
- **SDK / tmux backends** — no `run_in_background`-shell signal exists for them; they keep
  the `inFlight`-only behavior. A different detection mechanism would be its own effort.
- **Daemon-restart job survival** — `shutdown-drain` drains in-flight *turns*, not background
  *jobs*; a restart kills them regardless of this pin. Genuinely larger work (job persistence
  + re-attach); operators avoid restarting while a long background job runs. Explicitly out.
- **An idle reaper** — none exists; eviction is still budget-pressure-only. Not adding one.

## Test plan

Unit (`tests/process-manager*.test.js`), deterministic with fake Processes:
1. `_evictLRU` skips a session whose `hasActiveBackgroundWork()` is true and evicts the
   next-oldest unpinned one instead.
2. With one unpinned + one pinned, the unpinned is evicted even when the pinned is older.
3. **Policy C — overflow:** all free slots pinned → `getOrSpawn` spawns over budget, emits
   `lru-overflow-pinned` (with the pinned session keys), and the pinned sessions stay alive.
4. **Policy C — park split:** all blockers `inFlight` (no pin) → still parks via
   `_awaitLruSlot` (unchanged); does NOT overflow.
5. `getOrSpawn` end-to-end: spawning over budget with one pinned + one unpinned session
   evicts the unpinned one and leaves the pinned (background-job) session alive.

Unit (`tests/cli-process*.test.js`):
6. `hasActiveBackgroundWork()` mirrors `_bgWorkSince` (null → false; set → true). No time cap.

No real-claude E2E needed — detection is already E2E-validated (rc.26 bg-shell probe test);
this spec only adds a sync getter + an eviction branch, both deterministically unit-testable.

## Risks

- **Pin staleness (≤5s).** A job that ends between two pong ticks over-pins for up to 5s; a
  job that starts likewise goes unprotected for up to 5s. Both are benign (eviction is rare;
  a 5s window is far below job durations). No mitigation needed.
- **Spawn latency under full-pin pressure (Policy B).** New spawns wait one extra eviction
  pass. Bounded by `lruWaitMs`. Acceptable.
- **False pin from a mis-scrape.** `BACKGROUND_SHELL_RE` over-matching would pin a session
  with no real job. Bounded by `bgWorkPinMaxMs` (Decision 2) and Policy B's last-resort evict.

## Decisions (resolved — operator, 2026-06-09)

1. **Anti-starvation = Policy C** (soft budget: overflow + warn + manual operator reclaim). ✅
2. **Overflow ceiling = unbounded** — spawn over budget and warn; no hard cap (concurrent
   chats are naturally bounded by real users). ✅
3. **Warning surface = log + `lru-overflow-pinned` event only** — alerting is external
   monitoring's job, not polygram's; no admin-chat ping. ✅
4. **No time-based pin cap** — real jobs run >20 min, so any clock threshold would un-pin
   legitimate long work. Pin tracks live-shell presence only; stuck-shell overflow is resolved
   by the operator (`/reset`). ✅
5. **Park vs overflow split** — keep `_awaitLruSlot` parking for the transient all-in-flight
   case; overflow only when a durable background-job pin is the blocker. ✅ *(assumed — say if not)*
6. **Scope = cli-only**; SDK/tmux keep `inFlight`-only; daemon-restart job survival + idle
   reaper out. ✅ *(assumed — say if not)*
