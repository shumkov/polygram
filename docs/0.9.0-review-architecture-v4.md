## TL;DR

**`'use strict'` + 4 implicit-global names ⇒ polygram cannot start.**
Commit 31's commit message claims the four names "were already
declared via `let` after Phase B's wiring reorder." They were not.
A from-scratch boot under any ENV that gets past the `--bot`
argument check throws `ReferenceError: handleConfigCallback is not
defined` at line 1910 — the **first line of the wiring block** —
and `main()` exits before the bot ever opens its first poll. Reproed
locally with `node polygram.js --bot test-bot --db /tmp/.../test.db`.

This is a **harder break than v3 BLOCKER**. v3's
capture-by-value-of-null was "production breaks the moment a slash
or button fires" — v4's strict-mode reference error is "production
never starts." It got committed under v3 review's recommendation
without verifying the prerequisite (the `let X = null;` declarations
for the four names). The fix is one block of explicit declarations
near the existing module-scope hoists; under 8 lines.

**Plus a second capture-by-value regression** introduced by commit
34 (extract config-ui). `createHandleConfigCallback` is wired at
line 1910 and destructures `formatConfigInfoText` by value — but
`formatConfigInfoText` is itself bound on line 1923, **13 lines
later**. The closure captures `formatConfigInfoText: null`; first
button-tap on a `/model` or `/effort` card → `TypeError: null is
not a function`. Same defect class as v3 HIGH-1, just reintroduced
by a later extraction. Tests don't catch it because every
config-callback test injects an explicit non-null
`formatConfigInfoText` mock.

**Plus a stale-identifier bug** at lines 2041, 2044: the shutdown
drain reads `approvalWaiters.values()` and `approvalWaiters.clear()`
— but `approvalWaiters` was extracted into a private inner state
of `createApprovals` in commit 29, with no module-scope binding.
Under `'use strict'` (not strict-mode-needed — bare identifier
read), this throws `ReferenceError: approvalWaiters is not
defined` mid-shutdown, **stopping the drain before `pm.shutdown()`,
`db.raw.close()`, and PID-file release ever run**. rc.50-class
incident vector (orphan PID file, stuck pm subprocesses, dirty DB).

The good news: the v3 BLOCKER (capture-by-value of pm/bot) IS
fixed in commit 30 with the right approach (reorder, with a
header-comment audit trail). The wiring block has clean ordering
discipline now. The dispatcher extraction (commit 37) is the
boldest move since v3 and the architecture HOLDS — `getIsShuttingDown:
() => isShuttingDown` is exactly the accessor pattern v3 recommended,
and dispatcher's `attemptAutoResume` is a legitimate recovery
primitive, not "re-implementing handleMessage."

The architectural shape after −1678 LOC of extractions is **right**.
The orchestrator is glue, not implementation. handleMessage at
~1100 LOC is integration-glue that legitimately belongs in
polygram.js. createBot at ~360 LOC is grammy-event-handler
registration and there's no clean factory boundary for it. The
remaining concerns are tactical (the three boot/shutdown bugs
above) and surface (one weak module boundary in `lib/handlers/`,
a few documentation gaps). Fix the three production-blockers and
0.9.0 ships clean.

## ✅ Resolved since v3

### R1 — v3 BLOCKER (HIGH-1) capture-by-value of pm/bot

Commit 30 reordered main() so `bot = createBot(token)` and `pm = new
ProcessManagerSdk(...)` execute BEFORE every factory that destructures
them. The header comment at lines 1866–1881 explicitly documents
the constraint and the failure mode, so a future contributor
moving the wiring block has the load-bearing constraint in front
of them. This is the cleanest disposition possible — no accessor
indirection, just discipline + comment.

The trade-off accepted: ANY new factory that captures pm or bot by
destructure must be wired AFTER lines 1909 + 1882. The header
comment makes that visible; the boot-time `assert(pm && bot)`
recommendation from v3 was not adopted, so a future regression
(adding a factory above the pm/bot assignments) will surface as a
runtime `Cannot read properties of null` rather than a clean panic.
Acceptable but worth one more belt — see RECOMMENDED below.

### R2 — Hoisted dispatcher extraction (commit 37)

The dispatcher extraction was the most architecturally interesting
move since v3 — v3 said "leave it inlined" because of dep-list pain;
commit 37 found a clean shape via the `getIsShuttingDown: () =>
isShuttingDown` accessor. The `inFlightHandlers` Map moves to
dispatcher's closure (where it logically belongs — only the
dispatcher mutates it; only the shutdown drain reads its size). The
dispatcher returns it for that read. ~250 LOC out of polygram.js
into a coherent module.

`getIsShuttingDown` is the accessor pattern v3 HIGH-1 fix-(b)
recommended for pm/bot. Adopting it here for `isShuttingDown`
(which IS reassigned mid-life-cycle, unlike pm/bot which are
once-only) is exactly right and now stands as **the documented
idiom** for late-mutated module-scope state. handleMessage's
remaining `if (isShuttingDown)` direct-read at line 1344 closes
over the module let-binding directly and works for the same reason
the v3 BLOCKER's pm/bot direct-read in `getOrSpawnForChat` worked.

### R3 — handleMessage held the line at ~1100 LOC

v3 MEDIUM-1 recommendation honored: handleMessage was not
extracted further. The 5-stage shape v3 described (inbound mark →
slash dispatch → attachment+voice → autosteer attempt → pm.send
+ streamer/reactor) is **exactly what the residual body now is**.
Stages 1–4 are integration glue calling extracted handlers; stage
5 is the LLM-turn pipeline. Extracting stage 5 would require a
30+-entry dep list and does not improve coupling. v4 reaffirms:
don't extract.

### R4 — `'use strict'` added module-scope (commit 31)

Strict mode is on. This is correct in principle — it was the v3
HIGH-2 recommendation. The execution was incomplete (see HIGH-1)
but the directive itself is at line 20, before the first require,
applying to the whole module. ✓ correct placement.

### R5 — lib/db/index.js → lib/db.js + parsePairCodeArgsInline deleted

Phase D housekeeping from commit 31. Both clean wins; no
architectural impact.

## ❗ New since v3 (or surfaced by v3 fix attempts)

### 🟥 HIGH-1 — **MERGE BLOCKER + BOOT BLOCKER** — `'use strict'` + 4 undeclared assignments make `main()` throw at line 1910

**Files**: polygram.js (line 20 has `'use strict';`; lines 1910,
1915, 1920, 1953 assign to undeclared identifiers).

**The bug**: commit 31 added `'use strict'` and claimed in its
commit message *"the 4 undeclared assignments the reviewer noted
were already declared via `let` after Phase B's wiring reorder, so
this is just a belt."* They were NOT declared. `git grep -nE '^let
(dispatchSlashCommand|handleConfigCallback|handleAbortIfRequested|autosteer)'
polygram.js` returns zero matches (verified at HEAD).

Under strict mode, assigning to an undeclared identifier in a
function body throws `ReferenceError: <name> is not defined`
**immediately at the point of assignment**. The first such
assignment is at line 1910:

```js
handleConfigCallback = createHandleConfigCallback({ ... });
```

**Reproduction**:

```sh
$ node polygram.js --bot test-bot --db /tmp/test.db
[polygram] bot: test-bot (1 chats) db: /tmp/test.db
[db] applying migration 001-initial.sql
... (10 migrations) ...
[db] opened /tmp/test.db
Fatal: ReferenceError: handleConfigCallback is not defined
    at main (polygram.js:1910:24)
    at Object.<anonymous> (polygram.js:2297:1)
    at Module._compile (...)
```

main() exits with non-zero; the bot never opens its first poll;
launchd restarts polygram → same error → same exit → CrashLoopBackOff.
**0.9.0 cannot ship.** This is a 100% boot-time block, not a
fail-on-first-user-action defect like v3 HIGH-1. Your tag of
0.9.0 will not run.

**Why tests didn't catch this**: 60 `*.test.js` files; **zero of
them require polygram.js**. Every test imports a single lib module
and tests it in isolation. The integration-level "does main()
boot" surface has zero test coverage. v3 also noted this gap; it
is now the cause of v4's BLOCKER.

**The fix** — explicitly declare the four names alongside the
other module-scope placeholders:

```js
// Near line 247 (where recordInbound and friends are declared):
let dispatchSlashCommand = null;
let handleConfigCallback = null;
let handleAbortIfRequested = null;
let autosteer = null;
```

8 lines. The exact placement should be **immediately above
`let formatConfigInfoText = null;`** at line 520, so all
factory-emitted handlers are grouped:

```js
// Wired in main() — see the wiring-order block (~line 1880).
let dispatchSlashCommand = null;
let handleConfigCallback = null;
let handleAbortIfRequested = null;
let autosteer = null;
let formatConfigInfoText = null;     // (already declared)
let makeCanUseTool = null;           // (already declared)
let handleApprovalCallback = null;   // (already declared)
let resolveApprovalWaiter = null;    // (already declared)
let startApprovalSweeper = null;     // (already declared)
```

**Verification after fix**: `node polygram.js --bot test-bot --db
/tmp/test.db` should run past line 1910 and proceed to
`pollBot(bot)`. (It'll then 401 on the fake token, but that's a
test-config concern, not architectural.)

**Severity rationale**: HIGH **and merge-blocking**. Polygram
cannot run. This is severity beyond v3's BLOCKER — that broke at
first user interaction; this breaks at process start. Without the
fix, `npm publish polygram@0.9.0` ships an unrunnable package.

### 🟥 HIGH-2 — **MERGE BLOCKER** — `formatConfigInfoText` captured null by `createHandleConfigCallback`

**File**: polygram.js:1910–1925, lib/handlers/config-callback.js:30,95.

**The bug**: same defect class as v3 HIGH-1 (capture-by-value of
null), reintroduced by commit 34 (extract config-ui). The wiring
order is:

```js
// Line 1910–1914:
handleConfigCallback = createHandleConfigCallback({
  config, db, dbWrite, pm, getSessionKey,
  formatConfigInfoText, buildConfigKeyboard,    // ← captures null
  botName: BOT_NAME, logger: console,
});

// ... 12 lines of other wiring ...

// Line 1923–1925:
formatConfigInfoText = createFormatConfigInfoText({   // ← assigned LATE
  pm, db, getClaudeSessionId,
});
```

`createHandleConfigCallback` destructures `formatConfigInfoText`
into a parameter local; line 95 of its return body does
`const newInfo = formatConfigInfoText(chatConfig, showRow,
chatId);` — calling `null` → `TypeError: formatConfigInfoText
is not a function`. **First user button-tap on a /model or /effort
card** raises the error. The card-edit flow fails; the user sees
the spinner but no card update.

**Why tests pass**: `tests/handlers-config-callback.test.js`
injects a non-null `formatConfigInfoText` mock for every test
case. Same blind-spot pattern as v3 HIGH-1.

**The fix — two options**:

**(a) Reorder** (simplest, preferred): move the
`formatConfigInfoText = createFormatConfigInfoText({...})` block
to **immediately after** the `pm = new ProcessManagerSdk(...)` line
(1909), and BEFORE `handleConfigCallback = ...` at 1910.
`createFormatConfigInfoText`'s deps are `{pm, db, getClaudeSessionId}`
— pm is now bound, db has been bound since 1796, getClaudeSessionId
is a top-level require. So the reorder works.

**(b) Accessor**: change `createHandleConfigCallback` to take
`getFormatConfigInfoText: () => formatConfigInfoText` and call it
fresh per callback. More code but consistent with the
`getIsShuttingDown` idiom dispatcher uses.

**Recommendation**: (a). Reordering is what commit 30's discipline
established for pm/bot; do the same for formatConfigInfoText.
Update the wiring header comment at 1866–1881 to call out the new
constraint (`formatConfigInfoText must precede handleConfigCallback`).

**Severity**: HIGH and merge-blocking — once HIGH-1 unblocks boot,
the very first interaction with a config card breaks. This is a
direct user-visible regression in 0.9.0, exactly the class v3
flagged.

### 🟥 HIGH-3 — **MERGE BLOCKER** — Stale `approvalWaiters` reference in shutdown drain

**File**: polygram.js:2041–2044.

**The bug**: lines 2041 and 2044 read `approvalWaiters` directly
in module scope:

```js
for (const list of approvalWaiters.values()) {
  for (const fn of list) { try { fn('cancelled', 'polygram shutting down'); } catch {} }
}
approvalWaiters.clear();
```

But `approvalWaiters` was moved into a private closure variable
of `createApprovals(...)` in commit 29 (verified at
lib/handlers/approvals.js:58). polygram.js:121 has a comment
*"approvalWaiters Map moved to lib/handlers/approvals.js (commit
29)"* — so this was a planned migration that **left two callsites
behind**. There is no module-level `approvalWaiters` and never
was post-commit-29.

Under `'use strict'` (and even without it — bare-identifier reads
of undeclared vars throw ReferenceError outside assignment in
sloppy mode too), `for (const list of approvalWaiters.values())`
throws `ReferenceError: approvalWaiters is not defined` at the
moment SIGTERM/SIGHUP fires. The async shutdown function rejects;
**the rest of the drain — `pm.shutdown()`, `db.logEvent('polygram-stop')`,
`db.raw.close()`, `processGuard.releasePidFile(PID_PATH)`,
`process.exit(0)` — never runs**.

**Production impact** (mirrors the rc.50 incident):

- PID file is left on disk → next polygram boot's `claimPidFile`
  thinks our process is alive (until OS reaps the now-zombied
  process via SIGKILL after the parent's restart timeout)
- pm subprocesses (Claude Query children) never get pm.shutdown
  signal → orphaned, eventually reaped by the OS
- DB never gets `polygram-stop` event row, never gets a clean
  close → if WAL hasn't checkpointed, log replay on next open
- Shutdown signal handler hangs in `setTimeout(process.exit, 100)`
  that never executes — process eventually killed by launchd after
  its restart-timeout (usually 30s)

**The fix**: expose a cancel/cleanup method on the approvals
factory return:

```js
// lib/handlers/approvals.js
return {
  makeCanUseTool,
  handleApprovalCallback,
  resolveApprovalWaiter,
  dropWaiter,
  startApprovalSweeper,
  cancelAllWaiters: () => {                              // NEW
    for (const list of approvalWaiters.values()) {
      for (const fn of list) {
        try { fn('cancelled', 'polygram shutting down'); }
        catch {}
      }
    }
    approvalWaiters.clear();
  },
  _approvalWaiters: approvalWaiters,
};
```

Wire it through createApprovals destructuring at polygram.js:1884:

```js
({
  makeCanUseTool,
  handleApprovalCallback,
  resolveApprovalWaiter,
  startApprovalSweeper,
  cancelAllWaiters,                                       // NEW
} = createApprovals({ ... }));
```

Add `let cancelAllWaiters = null;` at module scope alongside the
others. Replace lines 2041–2044 with:

```js
if (cancelAllWaiters) cancelAllWaiters();
```

**Severity**: HIGH and merge-blocking — every clean shutdown
becomes an unclean shutdown. The §7.4 SIGHUP-shutdown work and
rc.50 PID-file claim discipline are precisely meant to prevent
this class of failure. Shipping 0.9.0 with this regression undoes
that work.

### 🟧 MEDIUM-1 — `lib/handlers/` semantic cohesion has degraded with 13 modules

**Files**: `lib/handlers/{abort, approvals, autosteer, config-
callback, config-ui, dispatcher, download, extract-attachments,
ipc-send, poll, record-inbound, slash-commands, voice}.js`.

**Read at HEAD**: `lib/handlers/` now holds 13 files with
semantically distinct relationships to polygram.js:

| Module | Caller path | Shape |
|---|---|---|
| **abort** | called from handleMessage | stateless filter |
| **approvals** | called from buildSdkOptions (canUseTool) AND from `bot.on('callback_query')` | stateful (waiters Map) |
| **autosteer** | called from handleMessage | stateless |
| **config-callback** | called from `bot.on('callback_query')` | stateless |
| **config-ui** | called from handleMessage AND from config-callback | pure utility (formatter/keyboard builder) |
| **dispatcher** | called from `bot.on('message')` (dispatchRegularMessage) and boot replay | stateful (inFlightHandlers Map, autoResumeTracker tied in) |
| **download** | called from handleMessage | stateless |
| **extract-attachments** | called from handleMessage AND recordInbound | pure |
| **ipc-send** | called from ipcServer.handlers.send | stateless |
| **poll** | called from main() bottom (drives bot.on dispatch) | stateful (offset/watchdog) |
| **record-inbound** | called from `bot.on('message' / 'edited_message')` | stateless DB-write wrapper |
| **slash-commands** | called from handleMessage (dispatchSlashCommand) | stateless dispatcher of 11 commands |
| **voice** | called from handleMessage | stateless |

The v3 reading was: lib/handlers/ = "user-event handlers". That
held when the directory had 7 modules all rooted in `bot.on(...)` or
`handleMessage`. With 13 modules, the framing breaks:

- **`config-ui.js` is a pure utility** (no DB, no async). It's not
  a handler at all — it produces text + a keyboard. It lives in
  `handlers/` because `handleConfigCallback` and handleMessage
  both consume it. By the v3 framing it doesn't belong.
- **`extract-attachments.js`** is also pure (parses a Telegram
  message into an attachments array). Not a handler.
- **`dispatcher.js`** isn't a handler — it's a *dispatcher of
  handlers*, a meta-orchestrator. Same shape as polygram.js's
  remaining `handleMessage`, just for the per-message lifecycle.
- **`poll.js`** is a *driver*, not a handler. It owns the
  long-poll loop that *invokes* the bot.on(...) handlers grammy
  registered. Different runtime layer.
- **`ipc-send.js`** is server-side IPC — not a Telegram handler.

The honest framing now is: `lib/handlers/` has become "extracted
factories from polygram.js." That is **not** a semantic boundary;
it's an extraction-history boundary, and v3 MEDIUM-2 specifically
called this risk out.

**Reorganization sketch** (would-do-from-scratch, not blocking):

```
lib/orchestrator/                  ← runtime per-message orchestration
  handleMessage helpers/         (currently inlined; future)
  dispatcher.js                  ← was lib/handlers/dispatcher.js
  poll.js                        ← was lib/handlers/poll.js (driver)
  
lib/handlers/                      ← Telegram event handlers
  message/                       ← bot.on('message') path
    abort.js
    autosteer.js
    voice.js
    download.js
    slash-commands.js
    extract-attachments.js
    record-inbound.js
  callback/                      ← bot.on('callback_query') path
    config-callback.js
    approvals.js
  ipc/
    ipc-send.js                  ← was lib/handlers/ipc-send.js (or lib/ipc/send.js)

lib/ui/                            ← pure UI builders (no I/O)
  config-card.js                 ← was lib/handlers/config-ui.js
```

But: **the cost of this rename is non-trivial** (13 require sites
to update) and the **return is purely cognitive**. The current
`lib/handlers/` reads as "stuff polygram.js used to have in it,"
which is honest if not aspirational. Tests still pass; runtime
unaffected.

**Recommendation for 0.9.0**: do NOT reorganize. Add a 30-line
README at `lib/handlers/README.md` that documents the runtime-path
table above. Tag the layout question for **0.10.0 hygiene** — by
then, if more extractions land or if `dispatcher.js` grows further
(stage-5 turn-pipeline extraction is the speculated next step),
the right cuts will be obvious. For now: name the gap, defer the
fix.

The v3 MEDIUM-2 reading "boundary is fine, just document it" was
correct at 7 modules; at 13 modules with this much shape diversity,
the boundary is now functioning more as filing convention than as
runtime-coupling story. That's drift, not failure — but worth
naming.

### 🟧 MEDIUM-2 — Wiring header comment is correct but doesn't cover all constraints

**File**: polygram.js:1866–1881.

The header comment added in commit 30 documents:

```
//   1. bot = createBot(token)              — needed by approvals + abort
//   2. createApprovals(...)                — provides makeCanUseTool
//   3. createBuildSdkOptions(...)          — uses makeCanUseTool
//   4. pm = new ProcessManagerSdk(...)     — uses buildSdkOptions
//   5. handler factories that need pm/bot  — see them as live refs
```

What it MISSES (post-commits 32–38):

- `formatConfigInfoText = createFormatConfigInfoText({pm, ...})`
  must precede `handleConfigCallback = createHandleConfigCallback({...
  formatConfigInfoText, ...})` — see HIGH-2.
- `recordInbound = createRecordInbound({extractAttachments, ...})`
  is fine because `extractAttachments` is a top-level require (not
  reassigned mid-life-cycle). But the comment doesn't say "deps
  that are stable through main() can pass by destructure; deps
  reassigned mid-main() must pass through a getter or be wired
  AFTER the assignment."
- `dispatcher`'s `getIsShuttingDown` is the ESTABLISHED IDIOM for
  late-mutated state; the comment should call it out as the
  pattern for any future "this thing changes during boot" deps.

**Recommended**: extend the header comment to ~20 lines:

```js
// Boot wiring order constraints. Three classes of dep:
//
//   (A) Top-level requires (config, db, tg, BOT_NAME)
//       — bound once before main()'s wiring block; safe to
//       destructure into factory params.
//
//   (B) Mid-main() reassigned (pm, bot, formatConfigInfoText,
//       recordInbound, dispatchHandleMessage, ...)
//       — destructured ⇒ captures at call time. MUST be
//       assigned BEFORE any factory that destructures them, or
//       the factory captures null and the closure stays stale.
//       v3 caught this for pm/bot; v4 caught it for
//       formatConfigInfoText.
//
//   (C) Live-mutated state (isShuttingDown)
//       — accessed via getter (`getIsShuttingDown: () =>
//       isShuttingDown`); the lambda re-reads on each call.
//       Use this pattern for any dep whose value changes
//       during the bot's lifetime, not just during boot.
//
// Order encoded below:
//   1. bot = createBot(token)              — needed by approvals + abort
//   2. createApprovals(...)                — provides makeCanUseTool
//   3. createBuildSdkOptions(...)          — uses makeCanUseTool
//   4. pm = new ProcessManagerSdk(...)     — uses buildSdkOptions
//   5. formatConfigInfoText = createFormatConfigInfoText({pm, ...})
//      — must precede handleConfigCallback (which captures it by destructure)
//   6. handler factories that need pm/bot  — see them as live refs
```

Lower-effort alternative: add a single boot-time assertion AFTER
the wiring block:

```js
// Catch the capture-by-value defect class: any null factory dep
// surfaces here as a clean panic, not a runtime TypeError 30
// minutes later when a user clicks a button.
for (const [name, val] of Object.entries({
  pm, bot, dispatchSlashCommand, handleConfigCallback,
  handleAbortIfRequested, autosteer, formatConfigInfoText,
  recordInbound, dispatchHandleMessage,
})) {
  if (!val) throw new Error(`boot wiring: ${name} is null after main() init`);
}
```

This is the v3 fix-(c) recommendation that was not adopted. Adopting
it now adds 12 lines and converts ANY future capture-by-value
regression from "production breaks at first user action" to
"polygram fails to boot, launchd loops, telemetry fires." Clean
panic > slow user-visible breakage.

### 🟨 LOW-2 — Dispatcher's auto-resume is a legitimate primitive, not a re-implementation

**File**: lib/handlers/dispatcher.js:67–135 (`attemptAutoResume`).

The user asked: *"Is this an architectural smell (re-implementing
handleMessage's tail half) or a legitimate recovery primitive that
keeps its own contract?"*

**Reading: legitimate primitive.** Three reasons:

1. **It runs against a no-streamer/no-reactor execution path.** The
   no-op streamer/reactor stubs (lines 91–103) tell pm "we don't
   want live UX for this turn — just give me the result text and
   I'll deliver it as one batch." handleMessage's tail half is the
   opposite: every chunk goes through the streamer to give live UX,
   and the reactor reflects per-stream state. These are different
   contracts; auto-resume's contract is "silent recovery" while
   handleMessage's is "live engagement."

2. **The contract surface is small.** Auto-resume builds a
   continuation prompt, calls sendToProcess, takes the result text,
   chunks it, delivers it. ~70 LOC. handleMessage's tail half is
   ~430 LOC including streamer flushing, finalize-then-edit-then-
   delete-then-redeliver, sticker injection, reaction inline tags,
   archive cleanup, context-full hint, autosteered-refs clear. They
   share `sendToProcess` (one call) and `deliverReplies` (one call).
   That's not duplication — that's reuse of two primitives with
   different surrounding pipelines.

3. **The error path is unique.** Auto-resume's caller (the
   dispatcher's `.catch`) treats failure as "fall back to the
   normal error reply." handleMessage's tail half throws into
   dispatchHandleMessage's `.catch`, which is auto-resume's
   *caller*. The two paths can't merge without circular reasoning.

**Architectural smell test**: would extracting this primitive
into `lib/orchestrator/auto-resume.js` improve anything? No — it
already lives in `lib/handlers/dispatcher.js` because the
dispatcher OWNS the autoResumeTracker cooldown logic and the
"is this turn auto-resumable" decision. The primitive is in the
right module.

**One small quibble**: the no-op streamer/reactor stubs (lines
91–103) duplicate what `lib/telegram/streamer.js` and
`lib/telegram/reactions.js` could expose as `createNoopStreamer()` /
`createNoopReactor()` named exports. ~20 LOC saved + the
"auto-resume uses no-op UX" intent becomes self-documenting. Not
blocking; nice-to-have.

### 🟨 LOW-3 — Module-scope `let X = null` placeholder count is now 30

**File**: polygram.js (counted via `grep -nE "^let " polygram.js`).

Up from v3's "9 placeholders" to 30 `let` declarations at module
scope. Of these:

- 9 are config/runtime (DB_PATH, PID_PATH, stickerMap, config, db,
  tg, pairings, approvals, BOT_NAME, bot, isShuttingDown,
  approvalSweepTimer, ipcCloser) — bound once, never reassigned
  after main() init. These are **fine**.
- 21 are factory-emitted handlers + helpers (recordInbound,
  transcribeVoiceAttachments, downloadAttachments, pm,
  buildSdkOptions, dispatchHandleMessage, attemptAutoResume,
  errorReplyText, queueWarnThreshold, inFlightHandlers,
  handleSendOverIpc, formatConfigInfoText, makeCanUseTool,
  handleApprovalCallback, resolveApprovalWaiter, startApprovalSweeper,
  pollBot, startPollWatchdog).

The pattern works because:
- handleMessage closes over the module-scope let-bindings
  directly → reads latest value at call time ✓
- Factory destructures (the v3 trap) only break for deps that
  CHANGE after wiring; pm and bot are stable post-assignment, so
  capturing them is fine once the wiring order puts them first ✓
- `getIsShuttingDown` accessor handles the one case (isShuttingDown)
  where a dep changes mid-bot-life

**Concern**: the placeholder count grew because more concerns got
extracted. Each `let X = null` is a mini-state-machine: declared
null, asserted non-null after wiring, used by some downstream
caller. There is no central place that says **"if you add a
factory-emitted handler, declare it HERE in this list, and the
boot assertion below will catch typos."** Without that discipline,
HIGH-1's bug recurs every time a new factory lands.

**Recommendation**: the boot assertion proposed in MEDIUM-2 IS the
central discipline mechanism. Adopt it; it converts the implicit
"these 30 lets must all be non-null after main()" contract into a
checked invariant. Future contributors adding a 31st handler
factory will see the assertion list and either add their handler
to it (catching null-capture bugs) or skip it (and see the runtime
break that surfaces as an assertion failure in a fresh boot,
not a user-facing TypeError).

The v3 reviewer said hoisting placeholders into main() wasn't worth
restructuring closures — that calculus is unchanged. The fix isn't
"move the lets into main()"; the fix is "add a boot-time
assertion AFTER the wiring block that lists every factory-emitted
handler and panics on any null." Same effect on regression
prevention; zero closure restructuring.

## What v4 confirms about the architecture (no action items)

**The factory+DI pattern is the right shape for leaf concerns.**
The 13 extractions left polygram.js at 2300 LOC of legitimate
glue — handleMessage (1100 LOC integration), createBot (330 LOC
grammy registration), main() (530 LOC boot+shutdown), helpers
(310 LOC). Each is the right layer; none is hiding business
logic that wants its own module.

**The dispatcher extraction is the model for future work.** The
`getIsShuttingDown: () => isShuttingDown` accessor pattern is
the documented idiom for late-mutated state. dispatcher.js's
`attemptAutoResume` is a legitimate recovery primitive with its
own contract, not "re-implementing handleMessage's tail." Stage
6 of handleMessage (the LLM-turn pipeline) could conceivably
extract similarly in 0.10.0 — but only if a future feature needs
to vary it.

**`lib/sdk/` and `lib/handlers/` ARE different runtime layers.**
sdk = "code ProcessManagerSdk's constructor needs"; handlers =
"code Telegram event paths need." There's zero cross-import
between them at HEAD. The directional flow holds. The semantic
boundary works as long as both directories stay disciplined about
what they accept (LOW-2 / LOW-3 from v3 about config-ui and
extract-attachments being utility-shaped, not handler-shaped, is
the only drift).

**No new circular dependencies.** Every factory takes its deps
explicitly; every cross-handler reference goes through module-
scope let-bindings (which read latest value) or through accessors.
The dependency graph is a strict DAG.

**Documentation surfaces are MISSING for the discipline.** The
wiring header at 1866–1881 documents the pm/bot constraint but
not the broader destructure-vs-accessor framing. The
`lib/handlers/` directory has no README. The `getIsShuttingDown`
pattern isn't surfaced as "the idiom for late-mutated module
state." These are MEDIUM-1 / MEDIUM-2's recommendations — adopt
them and the discipline transfers to future contributors.
