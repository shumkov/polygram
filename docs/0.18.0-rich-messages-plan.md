## 0. Reality-check pass (corrections to initial framing)

Corrections found while researching, before any design was locked in:

1. **"Automatic per-client enable/disable" is not achievable.** The Bot API
   exposes no `platform`/`client_type` field anywhere in `User` or `Message`.
   A `sendRichMessage` call to a Telegram-Web user **succeeds** (`ok: true`)
   — the failure is 100% client-side rendering (a dead "not supported"
   placeholder card) and produces **no error signal to the bot**, before or
   after. Confirmed independently three times: our own doc read, openclaw's
   issue #93263, hermes-agent's issue #45785. This is why both reference
   projects converged on manual opt-in rather than detection — there is
   nothing to detect.

2. **The Bot API "Checklist" object (`sendChecklist`/`editMessageChecklist`,
   Bot API 9.1, shipped 2025-07-03) is a different feature from Rich
   Messages (Bot API 10.1/10.2, shipped a year later, 2026-06-11/07-14) and
   is irrelevant here.** Checklist requires `business_connection_id` and can
   only be sent on behalf of a connected Telegram Business account — not
   usable by a normal bot. Rich Messages' `sendRichMessage` has
   `business_connection_id` as **optional** — any bot can use it in any
   chat type it can already post to. Don't conflate the two in code or
   in this doc.

3. **Rich Message checkboxes (`RichBlockListItem.has_checkbox`/`is_checked`)
   are not interactive.** No update/callback fires when a user taps one —
   confirmed via the API schema (no such field exists) and via both
   openclaw and hermes-agent's implementations, which source checkbox state
   purely from the agent's own authored markdown (`- [ ]` / `- [x]`), never
   from a user action. Anything that wants a user-toggleable task needs an
   inline keyboard button layered on top, which is out of scope here.

4. **Architecture fork — OPEN, not resolved (corrected in v2).** openclaw
   shipped an HTML-string renderer first (PR #93286), hit a real
   production bug from it (`\n` collapsing inside rich HTML — issue
   #95409), and **deleted the whole HTML layer** in favor of a typed
   `InputRichBlock[]` tree (PR #107986, merged 2026-07-15). hermes-agent,
   by contrast, passes raw markdown strings through `InputRichMessage.
   markdown` and has kept it working in production via targeted escaping
   (protected regions for code/tables, `\n`→hard break normalization,
   `$`-escaping).
   >
   > **v1 read this as "openclaw's experience indicts strings, build
   > blocks" — the scope review caught that this misapplies the evidence.**
   > openclaw deleted an **HTML-string round-trip** (markdown → HTML →
   > Telegram re-parses HTML), a different and more fragile thing than
   > **markdown-string passthrough** (hermes-agent's actual approach,
   > still in production). The approach v1 rejected is the one that's
   > working; the approach v1 cited as the cautionary tale is a third,
   > different thing nobody proposed building.
   >
   > The feasibility review also punctured v1's strongest pro-blocks
   > argument — that blocks are "a natural extension of `buildRenderer()`."
   > In reality `format.js`'s `_markedInstance` has a **fixed** HTML
   > renderer baked in at construction time and never exposes a reusable
   > token tree; a blocks renderer needs its own `marked.lexer()` call —
   > it's a **parallel** renderer, not an extension. And two things v1
   > claimed blocks would "avoid duplicating" — `wrapFileReferencesInHtml`
   > and the table column-padding logic — are HTML/`<pre>`-specific and
   > **not reusable for blocks either**, so blocks has to reimplement
   > those too. Net: the effort delta between the two approaches is
   > smaller than v1 argued, in both directions.
   >
   > **v2 left this as an open Phase-0 spike question. v3: decided —
   > build typed blocks**, the operator's explicit call: polygram already
   > leans on openclaw's prior art elsewhere (the existing HTML pipeline's
   > file-ref wrapping and spoiler handling are ported from them), they
   > iterated to the blocks design twice in production, and that's enough
   > trust to commit to it rather than re-run a cheapest-first bake-off.
   > **"Trust but verify" — this does not remove G1's round-trip and
   > adversarial-content checks (§6); it removes the passthrough A/B, not
   > the verification.** If G1 finds blocks genuinely broken against real
   > content, that's still a stop-and-reconsider signal, just not an
   > A/B comparison anymore. §13 Q1 is closed.

5. **Polygram is single-backend since the `@shumkov/orchestra` migration.**
   `AGENTS.md`'s "SDK backend vs tmux backend" framing is **stale** — `git
   log -- lib/process/` shows `lib/process/sdk-process.js` and
   `cli-process.js` were removed when polygram moved to depending on
   `@shumkov/orchestra` for the Claude session engine (commits `cec4d91`,
   `a9a12ed`). `lib/pm-interface.js` now states explicitly: "Implemented by
   `lib/sdk/process-manager.js` (the only pm impl post-0.9.0)." System-prompt
   composition is a single path: `lib/agents/loader.js` `composeSdkOptions()`
   → `lib/sdk/build-options.js`. This *simplifies* the plan — the "does our
   rich-authoring hint reach every runtime" concern from hermes-agent's
   #108264 lesson collapses to verifying one path, not several. (Caught by
   reading `git log` before drafting Gate 7 below — would have written a
   gate against files that no longer exist.)

6. **Polygram supports an optional self-hosted local Bot API server**
   (`config.bot.apiRoot`, see `docs/0.12.0-file-send.md`) for the 2GB file
   cap. That server is a separate binary (`telegram-bot-api`, built from
   TDLib) with **its own release cadence**, independently of cloud
   Telegram. It may not support Bot API 10.1/10.2 methods yet even after
   cloud Telegram does. Neither openclaw nor hermes-agent's research
   surfaced an equivalent concern (they appear cloud-API-only), so this is
   a polygram-specific capability axis with no prior art to lean on. Per
   fleet memory, `apiRoot` has a history of being unset/orphaned — G4
   (§6) is now gated on "only run if a bot currently has `apiRoot` set,"
   not treated as universally load-bearing.

7. **[v2, from failure-modes review] The plain-HTML fallback is NOT
   "always safe" for the checklist use case — this is a real, pre-existing
   correctness bug the whole fallback design depends on being fixed
   first.** `format.js` has no `checkbox()` renderer; `marked` (gfm:true)
   falls through to its default for a task-list item and emits literal
   `<input type="checkbox">` HTML. Verified by running the real renderer:
   `- [ ] first task` → `<input disabled="" type="checkbox"> first task`.
   **Telegram's `parse_mode: HTML` does not support `<input>`** — this is
   a guaranteed `400 can't parse entities: Unsupported start tag "input"`
   today, on the CURRENT plain pipeline, for any agent reply containing a
   markdown task list, rich text or not. `api.js`'s existing HTML→plain
   fallback (triggered on that 400) then reverts the **entire message** to
   raw markdown source — every `**bold**`/table/etc. in that reply
   degrades to literal characters, not just the checkbox line.
   This directly undermines §5/§10's "content-error fallback always
   degrades safely to `toTelegramHtml`" invariant — for a checklist reply,
   that fallback target is itself broken. **A `checkbox()` renderer in
   `format.js` (emit `☐`/`☑` text, never `<input>`) is a prerequisite for
   this entire plan, independent of the blocks-vs-string decision, and
   should ship as its own small fix before Phase 0 starts** (it's a latent
   bug in shipped code today, not new-feature work — see §11).

8. **[v2, from feasibility + failure-modes reviews] Rich delivery, as
   scoped in v1, only reaches ONE of polygram's several agent-text send
   surfaces.** v1 wired rich exclusively into `lib/telegram/streamer.js`'s
   `finalize()`. But: (a) short replies that never cross the streamer's
   `minChars` threshold stay in `state==='idle'` and are delivered by
   whatever calls `finalize()` on a never-gone-live streamer via the
   plain `deliverReplies` path, not through the rich-aware finalize edit;
   (b) `lib/telegram/process-agent-reply.js` — autonomous-wakeup,
   auto-resume, and autosteer extra-turn replies — sends via
   `chunkMarkdownText` + plain `deliverReplies` (`lib/telegram/deliver.js`)
   directly, bypassing the streamer entirely. Its own file header
   apparently documents this as exactly the class of surface that
   "silently missed protections" historically. So even with richtext on
   and a table-shaped autonomous-wakeup reply, it would render plain while
   an equivalent normal streamed reply renders rich — a real, silent
   inconsistency. v1 implicitly assumed "non-streamed single-shot replies
   can go rich too" (§7's G3-fail branch says so) without actually wiring
   them. **v2 makes this an explicit, named non-goal (§9) instead of an
   accidental gap** — `deliverReplies`/`process-agent-reply.js` integration
   is deferred, not silently missing.

9. **[v4, from live G5 observation] Degradation on an outdated client may
   be softer than §0.1 assumed — informal single observation, not yet
   systematically verified.** §0.1's "silent total failure" model was
   sourced from openclaw's and hermes-agent's GitHub issues, both
   describing **Telegram Web** specifically ("This message is currently
   not supported on Telegram Web" — a hard, content-blocking placeholder,
   confirmed via those projects' bug reports, not directly observed by
   us). Operator observation (2026-07-21, live G5 session): on an
   **outdated Telegram Desktop build for macOS**, the rich test messages
   showed some kind of notice/banner ABOVE the content, but the
   checklist/checkboxes remained VISIBLE below it — not the all-or-
   nothing placeholder card §0.1 assumed. This suggests degradation may
   differ meaningfully by client (Web vs. Desktop) and possibly by how
   far out of date the client is, rather than being one uniform failure
   mode across "any unsupporting client." **Not yet acted on** — no exact
   client version, no exact banner wording, and no test across Telegram
   Web / iOS / Android specifically were captured this session. Per
   operator instruction: keep the current opt-in default-off design as-is
   for now; this becomes a follow-up experiment, not an immediate design
   change. See §14.

## 1. Problem & use cases

Telegram Bot API 10.1 (2026-06-11) + 10.2 (2026-07-14) added `sendRichMessage`
/ `sendRichMessageDraft` / `editMessageText{rich_message}` — a genuine
structured-document format (headings, tables, checkbox/ordered/bulleted
lists, collapsible `<details>`, block quotes, collages, slideshows, math) any
bot can send, distinct from and much more capable than the HTML-flattened
markdown polygram already sends via `toTelegramHtml`.

Prioritized use cases for polygram (from operator brainstorm 2026-07-21):

| # | Use case | v1 scope? |
|---|---|---|
| 1 | Task/step progress checklist — agent authors `- [ ]`/`- [x]` markdown, rendered as a real checkbox list, edited in place as steps complete | **Yes** — the original motivating case |
| 2 | Structured reports — tables + headings for pulse reports, session-GC summaries, cost/usage breakdowns | **Yes** |
| 3 | Collapsible detail (`<details>`) for verbose logs/diffs, keeping the chat scannable | **Yes** |
| 4 | Visual walkthroughs — collage/slideshow for before/after screenshots | **Deferred to v2** — media blocks add real complexity (50-media cap, `tg://photo?id=` indirection) on top of an already-large v1; revisit after v1 soaks |
| 5 | Streaming "thinking" preview via `sendRichMessageDraft` | **Non-goal for v1** — see §9 |

## 2. Chosen approach

- **Renderer approach — DECIDED (v3): typed blocks.** New
  `lib/telegram/rich.js` module, runs its own `marked.lexer()` call (v1
  overstated this as "reusing" `format.js`'s parse — `format.js`'s
  `_markedInstance` has a fixed HTML renderer baked in and exposes no
  reusable token tree, so this is a **parallel** parser, not an
  extension) and walks the tokens into `RichBlock` JSON (heading/
  paragraph/list/table/blockquote/details/pre), following openclaw's
  post-#107986 architecture: `markdown → IR-equivalent token walk →
  typed InputRichBlock[]`, not a string. Exports
  `toTelegramRichBlocks(markdown) -> { blocks: RichBlock[], usedRich: bool }`.
  String passthrough (both openclaw's abandoned HTML-string and
  hermes-agent's still-working markdown-string approach) is not being
  built — see §3.

- **Content-adaptive gate, not "richtext on → everything is rich."**
  Mirrors hermes-agent's `_needs_rich_rendering` (their fix for issue
  #45762 — rich rendering makes ordinary prose look oversized with no
  Bot-API knob to fix that, so the fix was to reserve rich for content that
  actually needs it). `needsRichRendering(markdown)` returns true when the
  markdown contains a pipe-table separator row, a task-list item (`- [ ] `/
  `- [x] `), a `<details>` block, **or [v3, promoted from "stretch v1.1"]
  a heading (`#`/`##`/etc.)** — headings carry none of the oversized-body-
  text risk tables/long content do (no size/typography escalation, just a
  `RichBlockSectionHeading` with a `size` field), and "combine headers...
  together" was the original motivating ask, so there's no reason to defer
  them. Plain prose (no table/task-list/details/heading) always stays on
  the existing `toTelegramHtml` path even when the chat has richtext on.

- **Per-chat opt-in, default OFF.** Toggled through the existing
  `/config` surface (§13 Q2, closed — no new standalone command), same
  write mechanics as `/model X` in `lib/handlers/slash-commands.js`
  (`getConfigWriteScope` write + `saveConfig()` + `db.logConfigChange` +
  confirmation reply).
  **[v2 correction — this claim was self-contradictory in v1]** v1 said
  this needs "no reload/respawn" across the board. That's only true for
  **delivery** — `needsRichRendering()`/`sendRichMessage` read
  `chatConfig` live at send time, confirmed feasible against
  `resolveMaxFileOverride`'s identical precedence pattern in
  `attachments.js`. It is **not** true for the **prompt hint** (below) —
  `composeSdkOptions()`/`buildSdkOptions()` compose the system prompt at
  **spawn/resume time**; there is no live system-prompt swap anywhere in
  `@shumkov/orchestra` (`lib/pm-interface.js` exposes `setModel`/
  `applyFlagSettings`/`setPermissionMode`, nothing for the prompt).
  So `/richtext on` mid-session flips delivery instantly but the agent
  isn't *steered* to author rich constructs until its next (re)spawn —
  same situation `/model`/`/effort`'s `cliAwareSuffix` caveat exists for.
  The reply text should say so plainly, e.g. "Rich text → on (delivery is
  live now; the agent starts writing for it on your next fresh session)."
  Both openclaw (`channels.telegram.richMessages`, default `false`) and
  hermes-agent (`extra.rich_messages`, default `False`, restored after a
  same-week revert of an "always on" attempt — PRs #45584 → #45953 →
  #50322) landed on opt-in-default-off independently. Confirms rather
  than merely informs the operator's own call.

- **Two-tier error classification**, extending the existing
  `isHtmlParseError`/`isRateLimitError` family in `format.js`:
  - `isRichCapabilityError(err)` — endpoint missing / 404 / method-not-found
    style errors **only**. **Latches rich off for the process lifetime**
    — retrying a permanently-missing endpoint on every future send is
    pure waste. Mirrors hermes-agent's `_is_rich_capability_error` exactly.
    **[v2]** Keyed by `apiRoot` string alone (see §5 — collapses to a
    single boolean per process; never the raw bot token, per security
    review F2 — Telegram error strings/URLs can embed the token, so any
    latch key or logged error string MUST go through the existing
    `redactBotToken()` (`lib/error/net`, already used at `api.js:284/290`)
    before it's logged or compared). **[v2]** A transient error that
    matches **neither** classifier (network blip, 5xx, ETIMEDOUT) must
    **not** latch — treat as transient and fall through to the existing
    retry path. Only unambiguous 404/method-not-found latches. **[v2]**
    Trip the latch with a `rich-capability-latched` WARN-level `logEvent`
    (chat, bot connection, redacted error) — per this project's fail-loud
    convention, a permanent, un-clearable, process-lifetime state change
    must never happen silently.
  - `isRichContentError(err)` — parse errors, `RICH_MESSAGE_BLOCKS_TOO_MANY`,
    `RICH_MESSAGE_TABLE_COLS_TOO_MANY`, etc. **Falls back once, does not
    latch** — the next message may be fine. Mirrors openclaw's
    `rich-plain-fallback.ts` (error-driven, not speculative
    pre-validation) and hermes-agent's `_is_rich_fallback_error`.
  - On a content-error fallback, degrade the **same already-built content**
    — project the rich block tree back to the existing plain
    `toTelegramHtml` output, not a second independently-authored plain
    version. Single source of truth per reply. **[v2, security F1 —
    unresolved, needs a gate]** This degrade path is only as safe as
    `toTelegramHtml` itself, and per §0.7 that pipeline currently has a
    real gap (task-list → `<input>`) that must be fixed first. Separately,
    the inline-text representation *inside* rich blocks (bold/links/code-
    spans within a block's text) is not yet specified — if Telegram
    re-parses block text as markdown/entities rather than treating it as
    structured plain text, the escaping guarantee `escapeHtml`/
    `escapeHtmlAttr` provide today must be re-established per-block, or
    agent-relayed untrusted text (user messages, file contents) could
    inject formatting/links. Needs an explicit adversarial-content check
    in G1 (§6): send a block whose text contains `<b>`, `&`, markdown
    link syntax, and confirm literal rendering.

- **Streaming: progressive rich edit-in-place, no `sendRichMessageDraft`
  in v1.** **[v3 correction]** v2 stated both reference projects converged
  on "stream plain, upgrade to rich only at the final edit" — that's only
  true for hermes-agent. **openclaw actually streams rich the whole time**:
  the preview itself is sent/edited as `{blocks}` from early in the turn,
  via throttled `editMessageText{rich_message}` at ~1s cadence (same
  order of magnitude as polygram's existing `DEFAULT_THROTTLE_MS` in
  `streamer.js`) — not the native draft mechanism. Both projects agree on
  the parts that matter for architecture:
  - **Neither uses `sendRichMessageDraft`.** openclaw rejected it outright
    (issue #93438 — "conflicts with the established streaming contract").
    hermes-agent kept it but demoted it to disposable/best-effort/DM-only.
    Both edit the SAME message in place rather than send-fresh-and-delete
    — hermes-agent explicitly reverted the latter (issue #46206, "briefly
    shows two copies of the final answer… looks like duplicate delivery").
  - Where they differ is **whether the in-progress edits are themselves
    rich.** Given the operator's steer toward openclaw's design and
    toward UX quality, **v3 picks openclaw's shape: progressive rich
    streaming**, not finalize-only. The reply looks structured as it
    grows instead of flipping shape at the very end.

  Polygram's `lib/telegram/streamer.js` already edits a single message id
  in place with throttled edits — the integration is: once
  `needsRichRendering()` first triggers on the growing text (it may not
  trigger on chunk 1, e.g. a table's separator row hasn't arrived yet),
  every subsequent throttled edit uses `editMessageText{rich_message}`
  instead of plain text, including the final one. Before that point,
  stream plain as today (G1(b) from §6 already validates that an existing
  plain message can be upgraded to rich via edit — this is exactly that
  operation, just potentially happening mid-stream instead of only at the
  end).

  **New wrinkle from streaming mid-structure, needs its own gate (§6,
  folded into G1):** the growing text can produce a genuinely incomplete
  block tree — an unclosed table, a truncated list item, a `<details>`
  whose closing tag hasn't arrived. The renderer must only emit **complete**
  top-level blocks and hold the trailing incomplete one back (render it as
  plain text appended after the complete blocks, or omit it until
  complete) — mirroring how `truncateForLive` already handles the
  surrogate-pair-safe live-text truncation for the plain path today. If
  this proves unsafe/flickery in practice (G1 gate fails), the fallback is
  hermes-agent's more conservative shape — finalize-only — not abandoning
  rich streaming altogether; keep that as the documented decision-tree
  branch (§7), not a silent regression.

  **[v2, must-fix bug from failure-modes review, still applies — now to
  every throttled edit, not just the final one]** The overflow check
  (`body.length > maxLen`, `streamer.js:53,316`) runs **before** any rich
  decision, and `maxLen` defaults to **4096** — the plain `sendMessage`
  cap. Rich messages allow **32,768** chars. Now that rich edits can
  happen throughout the stream, not only at `finalize()`, every rich-path
  edit needs the rich-aware `maxLen` (32,768), not just the last one, or
  a mid-size structured reply gets discarded and redelivered plain
  partway through its own stream. Also make explicit (new invariant,
  §10): **rich is single-message only** — if a reply is long enough to
  need chunking even at the 32,768 rich cap, it is sent plain via the
  existing `deliverReplies` path. This confirms a mixed
  rich-chunk-1/garbled-plain-chunk-2 outcome is structurally impossible —
  `deliverReplies` has no rich awareness at all.

- **Retry/rate-limit.** `lib/telegram/api.js` already has a single retry
  honoring `getRetryAfterMs()` (capped at **30s** — `RETRY_AFTER_CAP_MS`,
  `api.js:262,309`; v1 said 60s, that number only survives in a stale
  code comment, corrected in v2) — see `api.js:~243-311`.
  hermes-agent's issue #46762 (a dropped final response under flood
  control) traced to a retry budget of 2 attempts being insufficient
  against 25-40s Telegram-reported waits; their fix combined honoring the
  server value **and** widening the budget. Polygram's existing single
  retry already honors the server value structurally — Gate 6 (below)
  measures whether one retry is enough for the larger, table/media-bearing
  rich payloads, or whether the budget needs raising specifically for
  rich sends.

- **Prompt hint, injected at spawn, one turn behind the toggle.** A rich-
  authoring system-prompt fragment (steer the agent toward `- [ ]` task
  lists / pipe tables / `<details>` when they help), injected only when
  the chat's `/richtext` is on. Both reference projects independently
  learned the hint and the delivery layer must be coupled — hermes-agent's
  base hint literally says "prefer bullet lists" when rich is off, and
  switches to encouraging tables/task-lists only when on; openclaw's
  #108264 fix was specifically about the hint not reaching a runtime that
  then authored content the delivery layer couldn't render. Per the
  corrected §0.5 finding, polygram has exactly one system-prompt assembly
  path — **[v2 correction]** the actual wiring point is
  `lib/sdk/build-options.js` (where `appendDisplayHint` already runs
  post-compose), not `composeSdkOptions()` itself, which just spreads
  `chatConfig` through unchanged. **[v2]** Per the opt-in bullet above,
  this hint is spawn-time, not live — accept a one-session authoring lag
  as v1 behavior: `/richtext on` makes delivery rich-capable immediately,
  but the agent isn't told to *write* for it until the session's next
  (re)spawn. Document this in the `/richtext` reply text; do not claim
  "lockstep" as if both halves updated together.

## 3. Rejected alternatives

- **[v3, decided]** Markdown-string passthrough into `InputRichMessage.
  markdown` (hermes-agent's approach, still working in their production).
  Not rejected on technical grounds — v2 confirmed it's viable — but not
  chosen: operator directive is to build typed blocks, trusting openclaw's
  twice-iterated design over re-running a cheapest-first comparison (§0.4).
  Worth revisiting only if Phase 0's G1 finds blocks genuinely broken
  against real content (§7).

- **Raw HTML string passthrough into `InputRichMessage.html`** (openclaw's
  now-abandoned first approach, PR #93286). Rejected on technical grounds
  — openclaw's own postmortem (§0.4) is direct evidence of the failure
  class: the round-trip was "a standing source of `can't parse entities`
  400s and formatting degradations," including the `\n`-collapsing bug
  (#95409). Not revisited.

- **Always-on by default.** Rejected — see §0.1 and §2's opt-in
  discussion. Every project that tried this (hermes-agent, twice) reverted
  within days of shipping, once because of a real total-outage bug
  (openclaw #93263) and once because of the silent-Web-failure risk
  (hermes-agent's #45785-driven revert).

- **`sendRichMessageDraft` for live streaming.** Rejected for v1 — see §2's
  streaming section and §9.

- **Any form of automatic client detection.** Not possible against the
  documented Bot API (§0.1). Not attempted.

## 4. Config & command design

Per-chat toggle, following the existing `topic → chat → bot → default`
precedence already used for `maxFileBytes` (`lib/attachments.js`,
`docs/0.12.0-file-send.md`):

```jsonc
{
  "defaults": { "richText": false },
  "bots": { "shumabit": { "richText": false } },
  "chats": {
    "-1003807211164": {
      "richText": true,
      "topics": { "3": { "richText": false } }
    }
  }
}
```

**[v3, §13 Q2 closed]** Folds into the existing `/config` surface rather
than becoming a new standalone top-level command — one less command for
the operator to remember, and `richText` shows up alongside `model`/
`effort` on the `/config` card the same way those already do. The write
path is unchanged regardless of exact command syntax (a Phase-1
implementation detail, not an architecture question): writes to
`getConfigWriteScope(chatConfig, threadIdStr).scope.richText` (same call
`/model` uses), persists via `saveConfig()`, logs via
`db.logConfigChange({field: 'richText', ...})`. No spawn/reload needed for
delivery — read live at send time by whatever composes the outgoing
message; the prompt-hint half still lags to next spawn (§2).

## 5. Interface sketches (not full implementations)

### `lib/telegram/rich.js`

```js
// needsRichRendering(markdown) -> boolean
// True iff markdown contains a pipe-table separator row, a task-list
// item ("- [ ] " / "- [x] "), or a <details> block. Conservative by
// design — false negatives mean "sent as today's plain HTML" — [v2:
// this is ONLY safe once the format.js checkbox() prerequisite (§0.7,
// §11 Phase -1) ships; today it is NOT safe for task-list content].
// False positives risk the oversized-body-text problem hermes-agent hit
// (issue #45762).

// toTelegramRichBlocks(markdown) -> { blocks: RichBlock[], usedRich: boolean }
// [v3: decided — typed blocks, see §0.4] Runs its OWN marked.lexer() call
// (NOT a shared parse with format.js — format.js's _markedInstance has a
// fixed HTML renderer baked in and exposes no reusable token tree, v1 was
// wrong about this being "the same parse"); walks the resulting tokens
// with a block-emitting renderer parallel in spirit to buildRenderer()'s
// HTML-emitting one, but not literally sharing code with it (file-ref
// wrapping and table column-padding are HTML-string-specific and need
// their own block-shaped reimplementation). usedRich=false (and
// blocks=[]) when needsRichRendering() was false — caller should use the
// existing toTelegramHtml() path in that case, not call sendRichMessage
// with a single-paragraph block.
//
// [v3, streaming] Also accepts a `partial: boolean` mode for mid-stream
// calls: when true, drops the trailing incomplete top-level block (an
// unclosed table/list/details) from the returned array rather than
// mis-rendering it, per §2's streaming bullet. The dropped tail is
// appended back in as it completes on the next chunk.

// isRichCapabilityError(err) -> boolean   — endpoint missing/404/method-not-found
// isRichContentError(err) -> boolean      — parse error, blocks/table/char limit rejection
// projectRichBlocksToPlainMarkdown(blocks) -> string
//   — degrade path for content-error fallback; feeds back into the
//   existing toTelegramHtml() so ONE renderer produces what the user
//   sees, whichever path was taken.
```

### Capability latch

```js
// [v2 — simplified from a Map to a boolean, per scope review] Polygram
// runs ONE bot per process, with a single config.bot.apiRoot resolved at
// boot (config.bot = config.bots[name]) — there is only ever one
// "connection" per process, so a Map<botConnectionKey, boolean> was
// modeling a multi-connection world that doesn't exist here. This also
// moots v1's §13 Q3 (per-connection vs per-chat latch) — both collapse
// to the same single boolean.
let richKnownUnsupported = false;  // module-level; never cleared this process

// On isRichCapabilityError(err): set richKnownUnsupported = true AND
// logEvent('rich-capability-latched', { chat_id, api_root: config.bot?.apiRoot
// ?? 'cloud', error: redactBotToken(errorMessage(err)) }) — see §2's error
// classification bullet. Never log/compare the raw bot token itself.
```

### `format.js` prerequisite — `checkbox()` renderer [v2, new]

Independent of the blocks-vs-string decision, ships before Phase 0:

```js
// buildRenderer()'s marked config needs an explicit checkbox extension/
// override so a task-list item ("- [ ] x" / "- [x] x") never falls
// through to marked's default `<input type="checkbox">` output — Telegram
// HTML parse_mode rejects <input> outright (400: Unsupported start tag).
// Render as literal "☐ "/"☑ " (or "[ ] "/"[x] ") text ahead of the
// listitem's normal content instead. This is a standalone bugfix to
// TODAY's plain pipeline (§0.7) — the rich work's fallback safety
// depends on it but doesn't require anything else about this plan.
```

### Instrumentation [v3, expanded from v2's capability-latch-only note]

Per operator request — cover the whole feature, not just the latch. New
`logEvent` calls, all following the existing shape (`telegram-html-
fallback`, `telegram-rate-limit` in `api.js`) — method/chat_id/thread_id +
a short classification, never full block/message content, error strings
always through `redactBotToken()` first (`lib/error/net`, already used at
`api.js:284,290`):

- `rich-message-sent` — a reply actually went out via `sendRichMessage`/
  `editMessageText{rich_message}`. Fields: `chat_id`, `streaming: bool`,
  `block_count`, `char_count`. Lets soak (§11 Phase 2) answer "is this
  feature actually being used, and how" without grepping raw logs.
- `rich-streaming-upgrade` — the moment a streaming reply's edits switch
  from plain to rich mid-turn (the "new wrinkle" in the streaming bullet
  above). Fields: `chat_id`, `msg_id`, `chunk_index_at_upgrade`. This is a
  real, visible UX transition (the bubble's shape changes mid-stream) —
  worth being able to correlate against user reports of "it looked weird
  partway through."
- `rich-content-fallback` — a single-message, non-latching
  content-error fallback fired. Fields: `chat_id`, `error_class`
  (`isRichContentError` match, e.g. `blocks_too_many`/`table_cols`/
  `parse_error`), redacted error string. This is the "did the safety net
  catch something" signal — should be rare; a spike in these post-ship is
  the first thing to check.
- `rich-capability-latched` — unchanged from v2 (§2's error-classification
  bullet): WARN-level, fires once per process lifetime max, chat + bot
  connection + redacted error. Given the latch is permanent and
  un-clearable, this is the most important of the four to never miss.

All four together answer, for soak (§11 Phase 2): is rich being used, is
the mid-stream transition visible/jarring, is the safety net firing more
than expected, and has the feature silently died for a bot connection.

## 7. Decision tree per gate failure

- **G1(a) round-trip fails** → block everything else; re-read the API
  reference, this is foundational. Does not fall back to string
  passthrough automatically — per the operator's decision (§0.4), a
  failure here is a "figure out what we misread" signal, not an
  architecture-swap trigger; re-raise to the operator if it looks like a
  genuine blocker rather than a fixable misunderstanding.
- **G1(b) text→rich edit fails** → drop both "finalize in place" AND
  progressive mid-stream upgrade; streaming replies never go rich in v1
  (only the single-shot content-adaptive path does, via whichever surface
  is wired per the §9 non-goal note) — smaller v1 scope, not a blocker.
- **G1(c) misclassification** (overflow mistaken for capability error) →
  tighten the regex/error-shape match in `isRichCapabilityError`/
  `isRichContentError` before shipping; this check exists specifically to
  catch that class of bug pre-ship — a false capability-latch from one
  oversized reply would incorrectly disable rich fleet-wide.
- **G1(d) adversarial-content check fails** (injected formatting/link
  renders live) → blocks ship outright; fix the inline-text escaping/
  representation before any further work, per security review F1.
- **G1(e) partial-block streaming proves unsafe** (malformed blocks sent,
  or the held-back-tail approach looks visibly glitchy) → fall back to
  hermes-agent's more conservative shape: stream plain throughout,
  upgrade to rich only at `finalize()`. This is a documented, deliberate
  downgrade path, not an unplanned one — the operator's preference for
  progressive streaming (§0's v3 note) is UX-driven, and a broken UX is
  worse than a simpler one; finalize-only remains fully specified (v2's
  original design) as the fallback shape.
- **G4 fails** (local server too old, when applicable) → latch rich off
  automatically for that bot connection; cloud-routed bots unaffected. No
  code change needed beyond the latch itself — this is what it's for.
- **G5 shows worse-than-expected breakage** (e.g. more clients affected
  than Web alone, an actual error DOES surface in some client/version
  combo, or a checkbox turns out interactive) → revise §0.1/§0.3 and the
  fallback design; any of these would be a significant, welcome surprise
  that should change the plan, not just get noted.

## 10. Invariants

- Rich text is **off by default** for every chat, always.
- The plain `toTelegramHtml` pipeline remains the source of truth for
  content whenever richtext is off, whenever the content gate says no, and
  on any content-error fallback — never a second, independently-maintained
  "plain version." **[v2]** This invariant is only trustworthy once the
  §0.7 `checkbox()` fix ships — track that as a hard dependency, not a
  parallel nice-to-have.
- **[v3, revised]** At most one markdown parse per outgoing message on the
  *plain* path. The rich path (typed blocks, decided §0.4) runs its own
  `marked.lexer()` call — a parallel parse, not shared with `format.js`
  (v1's "reuses the same parse" claim was wrong, corrected in §2). The
  **content-error fallback re-parses** (`projectRichBlocksToPlainMarkdown`
  → `toTelegramHtml`) — that double-parse on the fallback path is accepted
  as a fallback-only cost, not a violation of this invariant.
- **[v3, new]** Rich streaming edits emit only complete top-level blocks;
  an in-progress/incomplete block is held back rather than sent malformed
  (§2's streaming bullet, G1(e)).
- One system-prompt assembly path (`lib/sdk/build-options.js`) gets the
  rich-authoring hint, gated on the same `richText` flag the delivery
  layer checks — but **[v2]** the two reads happen at different times
  (spawn-time for the hint, send-time for delivery); "same flag" does not
  mean "simultaneously applied." See §2's opt-in and prompt-hint bullets.
- **[v2, security F3]** The `html`/`markdown` string fields of
  `InputRichMessage` are never populated directly from agent/model output.
  If a future contributor uses them (e.g. as the passthrough approach,
  should it win §13 Q1), model output must first pass through the
  existing `escapeHtml`-equivalent treatment `format.js` already applies
  to the HTML path — Telegram's server-side markdown parser is not itself
  a substitute for that, since the risk is agent-relayed *user* content
  being mis-interpreted as formatting/links, not Telegram mis-parsing
  well-formed markdown.
- **[v2, failure-modes L-equivalent]** `richText` resolves through the
  same `topic → chat → bot → default` precedence chain `maxFileBytes`
  uses (`lib/attachments.js`) — never read directly off `config.bot`,
  which is silently overwritten at boot by the per-bot alias
  (`config.bot = config.bots[name]`, the same footgun that orphaned
  `apiRoot` for weeks in 0.13.0).

## 15. Implementation-review corrections (v5)

The first implementation review found four correctness gaps. These are
limited corrections to the agreed design, not new feature scope.

1. **Delivery state must describe what Telegram accepted.** The streamer
   currently records payloads before Telegram accepts them. A later identical
   final payload can therefore be mistaken for already delivered after a
   failure. Commit rich or plain trackers only after success: a thrown edit
   leaves both trackers unchanged, while any successful plain delivery
   updates `currentText` and clears the rich tracker. Regression tests must
   cover failed rich and plain edits followed by successful final retries.
   Edits for a bubble must also be serialized so a slow older rich edit cannot
   land after a newer plain edit and invalidate the trackers; verify this with
   controlled promises that would otherwise resolve in reverse order. If a
   bubble is superseded while an edit is in flight, that edit may finish for
   the old Telegram message but must not commit state into the new bubble.
2. **The config card must display the effective rich-text value.** Delivery
   resolves `topic → chat → bot → default`, while the card currently inspects
   only topic/chat values. Compute the effective value with the existing
   resolver at both card call sites and pass that boolean into the pure UI
   builders. Keep their existing local-value behavior as a backwards-
   compatible default for direct callers. Tests must cover inherited `true`
   and an explicit effective override.
3. **Live configuration and the capability latch must affect the current
   turn.** Do not snapshot rich enablement when the streamer is created.
   Instead, let each rich-payload attempt re-read the resolver and latch.
   Keep a defensive latch check in the rich editor so a latched connection
   cannot issue another rich API request. Because a live toggle can now move
   a stream from rich back to plain, a successful plain edit must clear the
   stored rich payload and synchronize `currentText`; the same applies when a
   rich attempt resolves through the editor's plain fallback. Plain no-op
   checks are valid only when no rich payload is active. Tests must cover live
   rich→plain switching, rich success followed by `wentRich:false`, and a
   capability-latched edit that goes directly through the plain path. The
   `rich-streaming-upgrade` event represents each visible plain→rich
   transition, so a later off→on transition may emit it again.
4. **Every details block must contain a summary.** Telegram's
   `InputRichBlockDetails.summary` field is required. For source `<details>`
   without a non-empty `<summary>`, emit the stable fallback label
   `Details`. Dropping the entire rich rendering or rejecting otherwise
   useful content would be a larger user-visible degradation. Tests must
   cover both single-token and blank-line token-stream details shapes.
5. **Rich-text writes must match rich-text resolution in topics.** The generic
   model/effort write helper intentionally collapses non-isolated topics to the
   chat root because those settings belong to a shared process. Rich delivery
   is instead resolved per outgoing message and already honors topic overrides
   regardless of process isolation. Allow the rich-text callback to write its
   current topic even when `isolateTopics` is false; ignoring such overrides
   would contradict the agreed `topic → chat → bot → default` contract and the
   existing `maxFileBytes` precedent. Test a non-isolated topic whose inherited
   topic value is turned off.
6. **Every table cell must include alignment.** Telegram requires `align` and
   `valign` on `RichBlockTableCell`. Preserve Marked's horizontal alignment
   when it is `left`, `center`, or `right`, default missing alignment to
   `left`, and use `top` for vertical alignment. Unit tests and the live spike
   fixture must assert these fields so tables do not silently content-fallback.

Failure handling remains the same outside these corrections: content errors
fall back to plain, capability errors latch the connection, and transient
errors remain retryable. Verification is the focused rich/config suite plus
the full offline test suite; real-Telegram spikes are unnecessary because
the fixes concern local state transitions and a documented required field.

## 16. Media blocks — photos, collages, slideshows (v6)

Scope: use case #4 from §1 ("visual walkthroughs — collage/slideshow for
before/after screenshots"), deferred by §9/§13 Q4. This section is the v2
design. §9's "Media blocks" bullet is superseded by this section; the
other §9 non-goals stand.

### 16.1 Research — exact Bot API shapes (read from the live reference, not the changelog)

Field-level facts, verified against the current Bot API reference
(sections "Rich messages", "Rich Message Formatting Options", "Rich
Message Limits"):

- **`InputRichBlockPhoto`** = `{ type: "photo", photo: InputMediaPhoto,
  caption?: RichBlockCaption }`. The `photo` field is the **standard
  `InputMediaPhoto`** used by `sendMediaGroup` — its `media` string takes
  a `file_id`, an HTTP URL, or `attach://<name>` for a multipart upload
  **in the same request**. Its own `caption`/`parse_mode` are documented
  as ignored in this position; the visible caption is the block-level
  `RichBlockCaption`.
- **Version split that matters for self-hosted servers**: rich messages
  (`sendRichMessage` + the html/markdown string modes) are Bot API
  **10.1**; the typed `blocks` field of `InputRichMessage` and the
  `InputRichBlock*` classes are Bot API **10.2**. A 10.1-era
  `telegram-bot-api` build accepts the method but ignores `blocks`
  entirely (see §16.7 G6 results — this is the fleet's current state).
- **`InputRichBlockCollage` / `InputRichBlockSlideshow`** =
  `{ type: "collage"|"slideshow", blocks: InputRichBlock[],
  caption?: RichBlockCaption }`. Elements are themselves media blocks
  (the reference's own examples mix photo and video elements).
- **`RichBlockCaption`** = `{ text: RichText, credit?: RichText }` —
  and `RichText` may be a **plain JS string** (the type is
  "String | RichText[] | typed nodes"), so captions compose with this
  module's existing plain-strings-only invariant without touching the
  unverified typed-inline-node surface.
- **The `tg://photo?id=` indirection does not exist on the blocks path.**
  `InputRichMessage.media` (`InputRichMessageMedia[]`, ids referenced via
  `tg://photo?id=` links) is documented exclusively for the `markdown` /
  `html` string fields. Polygram's typed-blocks path (§0.4, decided v3)
  never touches it. The §13 Q4 deferral was partly priced on this
  indirection — that cost is void.
- **No pre-upload / two-phase sequencing exists.** `sendRichMessage`
  uploads new files directly ("If the message contains a block with a
  media element, then the bot must have the right to send the media to
  the chat"), and `editMessageText`'s `rich_message` parameter documents
  only ONE upload restriction: "Direct upload of new files isn't
  supported **when an inline message is edited**." Polygram never edits
  inline messages (no inline handlers), so the streamer's existing
  edit-in-place finalize can introduce photo blocks with fresh uploads.
  `sendRichMessageDraft` is the only rich method that can't upload —
  already a §9 non-goal.
- **grammy (1.42) makes `attach://` automatic.** Its payload serializer
  (`collectFiles` in `core/payload.js`) deep-walks the whole params tree
  — objects and arrays — replacing ANY `InputFile` instance with a
  generated `attach://<id>` string and appending the bytes as a
  multipart part. So placing `new InputFile(path)` at
  `rich_message.blocks[i].photo.media` works with zero polygram-side
  multipart code, same as `sendMediaGroup`. (This is exactly the
  mechanism `coerceFileValue` in `lib/telegram/input-file.js` already
  relies on for `sendPhoto`.)
- **Limits** (reference, "Rich Message Limits"): ≤32,768 chars,
  ≤500 blocks, ≤16 nesting levels, **≤50 media attachments in total**
  (photos+videos+audio combined), ≤20 table columns. No documented
  per-collage element cap beyond the global 50 — treated as a spike
  question (§16.7), since classic albums cap at 10.
- **Telegram's own rich-markdown authoring syntax** for media is
  standard image markdown plus wrapper tags:
  `![](url)` and `<tg-collage>…</tg-collage>` /
  `<tg-slideshow>…</tg-slideshow>`. This matters for §16.2: teaching the
  agent this syntax means teaching it *Telegram's documented dialect*,
  not a polygram invention.
- **Client-support caveat**: media blocks inherit the same §0.1/§0.9
  degradation story as all rich messages (no per-client detection, no
  error on unsupporting clients). No media-specific caveat found in the
  reference; the per-chat opt-in already caps the blast radius.

### 16.2 The design question — how the agent says "include this photo"

The agent's reply is a markdown string streamed through
`streamer.js`; files it wants to share today go through the reply tool's
`files: [paths]` parameter (`channels-tool-dispatcher.js`), which sends
them as separate `sendPhoto`/`sendDocument` messages AFTER the text.
Three real alternatives for media-in-rich-replies:

**A — markdown image syntax in the reply text itself (CHOSEN).** The
agent writes `![caption](/abs/path/to/screenshot.png)` (or an https URL)
inline in its streamed reply; consecutive images grouped inside
Telegram's own `<tg-collage>`/`<tg-slideshow>` wrapper tags become a
collage/slideshow block. The renderer maps image tokens →
`InputRichBlockPhoto` (alt text → `RichBlockCaption.text`), wrapper
spans → collage/slideshow blocks; local paths become `InputFile`
instances that grammy uploads via `attach://` in the same
`editMessageText{rich_message}` call. Why it wins:
  - It's the *same single delivery flow* — no second API call, no
    sequencing, no new protocol surface. The photo lands inline at the
    exact narrative position the agent put it, which is the entire point
    of the "visual walkthrough" use case (text → before screenshot →
    text → after screenshot).
  - The authoring syntax is standard markdown plus Telegram's own
    documented wrapper tags — lowest possible prompt-hint cost, and an
    agent that gets it wrong degrades to a visible literal link in plain
    mode rather than a broken call.
  - It composes with everything v1 built: the content gate, partial-mode
    holdback, the rich-edit fallback ladder, `richSourceText` transcript
    persistence — all unchanged in shape.

**B — extend the reply tool (`files:` + a rich flag / structured media
argument) — REJECTED.** The reply tool lives on the channels/CLI
dispatcher path, which §9 explicitly keeps plain (still true); rich
delivery lives on the streamer path. Wiring media through the tool would
either create a second, non-streaming rich surface (splitting the §9
scope cut polygram deliberately made) or require threading tool-call
side-channel state into the streamer mid-turn — a new coupling between
the tool protocol (owned by `@shumkov/orchestra`, a different repo) and
`streamer.js`. Also loses inline positioning: the tool fires once,
after the text.

**C — pre-upload then reference (agent sends the photo via the existing
file path first, then references its `file_id` / `tg://photo?id=` in the
rich text) — REJECTED.** The research premise for this alternative is
dead: typed blocks take `attach://` uploads directly, and the `tg://`
indirection doesn't exist on the blocks path at all (§16.1). What
remains is pure cost: a visible extra message (or send-then-delete
churn), agent choreography around opaque `file_id` strings, and a
two-phase failure surface (upload succeeded, reference failed) — for
zero capability gain.

### 16.3 Upload sequencing under progressive streaming

The one place media DOES interact with v1's design is the throttled
mid-stream edit loop. A naive integration re-uploads every local file's
bytes on every changed edit (~1/s during streaming) — multipart
round-trips 10-50× per reply for the same pixels. Decision:

- **Media blocks materialize only at `finalize()`** (`partial: false`).
  During streaming (`partial: true`), an image renders as a lightweight
  plain-paragraph placeholder (`🖼 <caption, or a generic label — never
  a filesystem-derived basename, see §16.4>`), so the narrative position
  is visible and the bubble doesn't jump when the photo lands. The final
  edit is the ONE call that carries an upload. This mirrors the v1
  pattern of holding back incomplete trailing blocks — a deliberate "the
  stream previews, the finalize commits" contract. `partial` is already
  threaded through `toRichPayload`, and `currentRichJson` dedup
  guarantees the finalize edit fires (media blocks differ from
  placeholder blocks). The offline suite must assert the resolver is
  NEVER invoked in partial mode — a slip here reintroduces a
  realpath+stat storm on every ~1s throttled edit.
- **`InputFile` never enters the block tree** (feasibility/failure-modes
  review catch — this voids the draft's "streamer needs no changes"
  claim and replaces it with a carriage rule instead of a streamer
  change). grammy's `InputFile.toJSON()` THROWS by design
  (`types.node.js`: "InputFile instances must be sent via grammY"), and
  the streamer dedups rich payloads via `JSON.stringify(blocks)`
  (`streamer.js` flushOnce + finalize) — an `InputFile` at
  `photo.media` would crash every media finalize. Instead, resolved
  local files ride in the blocks as the repo's existing JSON-safe
  `{ source: '<realpath>' }` envelope (same shape `input-file.js`
  coerces for top-level file fields), and `rich-edit.js` materializes
  `new InputFile(resolvedPath)` from the envelope immediately before
  each send attempt (injected `makeInputFile` dep). Consequences, all
  good: `JSON.stringify` stays safe; placeholder-vs-media dedup keys
  differ naturally; a fresh `InputFile` per attempt makes the 429/
  pre-connect retry in `api.js` trivially safe (and grammy path-backed
  `InputFile.toRaw()` re-reads anyway — verified; streams/iterators are
  the only single-use sources, so the invariant is: media `InputFile`s
  are ALWAYS path-backed, never stream/supplier-backed).
- **Multi-bubble turns — narrow, documented limitation.** Traced in
  `@shumkov/orchestra`'s `sdk-process.js`: `stream-chunk` emits
  CUMULATIVE turn text (segments joined with blank lines), and
  `assistant-message-start` → `forceNewMessage` fires **only on steered
  turns** (`pendingSteerCausesNewBubble`), where the accumulated text
  also resets. So the motivating walkthrough shape — text, tool call,
  screenshot, more text — lands in ONE bubble and works. The one gap:
  a steered turn whose pre-steer bubble contained an image keeps that
  bubble's 🖼 placeholder forever (media resolves only in the finalized
  last bubble). Accepted for v1 and listed in §16.9; the fix shape if
  soak shows it matters (a "seal" edit materializing media at the
  `forceNewMessage` boundary) is recorded there.
- Follow-up, not v1 (recorded here so the thread isn't lost): cache
  `path → file_id` from the returned `Message`'s `RichBlockPhoto.photo`
  sizes and reuse across edits/messages. Deliberately out of scope —
  mapping response photos back to source paths is order-inference, and
  the win only appears for repeated sends of the same file.

### 16.4 Security

- **Path allowlist — same trust boundary as `reply(files)`.** Image
  paths come from agent output, which is prompt-injectable. Telegram
  would reject a non-image payload, but that's no defense: a staged
  copy of a sensitive file with a `.png` extension uploads fine — the
  exact exfiltration class the dispatcher's file-allowlist hardening
  closed for `reply(files)`. Media resolution reuses the SAME validation:
  `validateAttachmentPath()` + `buildAllowedRoots()` (already exported
  from `channels-tool-dispatcher.js`) — absolute path required, realpath
  before check (symlink-safe), roots = per-session staging dir + session
  cwd + the SAME configured extra roots the dispatcher receives (roots
  parity: `reply(files)` and rich media must accept identical path sets
  for a session). A path outside the roots → the block is dropped to a
  placeholder paragraph + `rich-media-rejected` event; never an upload
  attempt. **The upload consumes the REALPATH'D path** —
  `validateAttachmentPath` returns `{ resolved }`, and that resolved
  path is what goes into the `{source}` envelope (and later the
  `InputFile`), exactly as the dispatcher uploads `check.resolved`;
  building the upload from the original agent-authored path would
  reopen the symlink hole validation just closed.
  Honest scope note: like `reply(files)`, this closes OUT-OF-ROOTS
  reads only. A same-uid agent copying a readable file into its own cwd
  and uploading the copy is inherent to the agent's local-FS trust
  model and unchanged by this feature.
- **src classification is a trichotomy, decided by a literal prefix
  test** (`/^https?:\/\//i`), never a URL parser (a colon in a local
  path must not be read as a scheme): (1) `http(s)://` → URL
  passthrough as the `InputMediaPhoto.media` string — Telegram fetches
  server-side (its documented 5 MB URL-photo limit applies; polygram
  reads nothing); (2) no scheme, absolute path → allowlist validation
  above; (3) everything else — `data:`, `file:`, `tg:`, `attach:`,
  relative paths — rejected. An agent-authored literal `attach://x`
  must never pass through: it would dangle against a multipart part
  that doesn't exist or collide with a grammy-generated id.
- **URL media is cloud-only.** When `config.bot.apiRoot` is set (a
  self-hosted `telegram-bot-api` server on a trusted host), whether URL
  media gets fetched by that local server (SSRF from inside the
  perimeter — `![](http://169.254.169.254/…)`) or forwarded to Telegram
  DCs is unverified — so the resolver rejects URL srcs under `apiRoot`
  until G6 verifies the fetch origin. Local-file media is unaffected.
- **Size caps**: local files stat'd before upload against
  `min(PHOTO_UPLOAD_CEILING (10 MB), resolveMaxFileOverride(...) ??
  PHOTO_UPLOAD_CEILING)` — note the `??`: `resolveMaxFileOverride`
  returns `null` for "no override", and `Math.min(cap, null)` is 0,
  which would silently reject every photo. Same topic → chat → bot →
  default precedence, same reject-before-upload-with-a-clear-reason
  posture as the dispatcher's `maxOutboundFileBytes` check. A per-reply
  TOTAL media budget (50 MB, matching `attachments.js`'s
  `MAX_TOTAL_BYTES`) additionally bounds the single multipart finalize
  request. Note `api.js`'s outbound-cap choke point does NOT cover rich
  media (`FILE_FIELD_BY_METHOD` has no `rich_message` entry), so these
  resolver-side checks are the ONLY enforcement — load-bearing, not
  defense-in-depth.
- **No filesystem-derived text leaks into chat or logs.** Placeholder
  and unavailable-image paragraphs render the agent's own caption when
  present, else a generic label — NEVER a basename (a rejected
  `![](/etc/passwd)` must not echo "passwd" into the chat).
  `rich-media-rejected` events log a reason class only — never the raw
  src (URLs can carry basic-auth userinfo, paths leak workspace
  structure); same discipline as v1's `redactBotToken`/`stripUrlCreds`
  usage.
- **Every plain-text surface a rich-enabled chat can reach is
  sanitized.** `stripMediaMarkdown` (image syntax → caption text,
  wrapper tags removed, and a dangling UNTERMINATED trailing
  `![shot](/abs/pa…` fragment cut — the code-review catch: the live
  preview streams plain until the closing `)` arrives, so complete-
  syntax stripping alone still leaks the path mid-stream) is applied
  at: rich-edit's content-error/latch fallback edits, the streamer's
  plain live-preview send/edit callbacks, and both chunked-redelivery
  sites. Applied only when the chat's richText is on — plain chats'
  behavior is untouched. (The transcript DB keeps full source text;
  local paths at rest in the operator's own DB are accepted, including
  the low-likelihood TOCTOU case where a validated-then-deleted file's
  path lands in a transient-error event.)
- **Captions are plain strings** (§16.1's `RichText`-as-String) — the
  existing flatten-inline-tokens invariant applies to alt text
  unchanged. Whether Telegram re-parses a caption string for entities
  is NOT asserted here — it's a G6 adversarial check (§16.7), the same
  posture v1 took with G1(d).
- **Extension gate**: v1 accepts `.jpg/.jpeg/.png/.webp` local files
  only (the photo-block set; a selection mechanism, not a security
  control — the path allowlist is the security control, and Telegram
  validates actual bytes server-side). `.gif` is an animation block in
  the API — deferred (§16.9), not silently sent as a broken photo. The
  dispatcher's own image list includes `.gif` — two deliberately
  different lists (send-as-photo-message vs photo-block), each
  commented to point at the other.
- **New gate regexes** (`IMAGE_RE`, `MEDIA_WRAP_RE`) follow the same
  anchored, no-nested-quantifier discipline as the v1 gate regexes and
  join the existing ReDoS regression guard in `tests/rich.test.js`.
  Wrapper-span extraction uses the token-stream open/close scan (the
  `<details>` precedent in `blocksFromTokens`), NOT a doubled-lazy
  `[\s\S]*?` block regex, which backtracks on an unclosed wrapper with
  a large body.

### 16.5 Failure modes

| Failure | Behavior |
|---|---|
| Local path invalid / outside roots / missing / oversized / wrong extension | Block degrades to a plain paragraph carrying the agent's caption (never a basename — §16.4) plus an "(image unavailable)" marker; `rich-media-rejected` event with a reason class. Reply always delivers. |
| Every media dropped AND the text has no other gate construct (heading/table/etc.) | The whole reply falls back to `usedRich: false` → existing plain path. Prevents the §2 oversized-prose regression for a reply that was only "rich" because of images that didn't resolve. Because media resolves only at finalize, this demotion is finalize-only: a bubble that streamed rich 🖼 placeholders can collapse to plain in its final edit. One visible transition, not a flap — `needsRichRendering` is source-driven and stable across ticks. |
| >50 media in one reply | Resolver resolves the first 50 in document (flattened, wrapper-children included) order; the rest degrade like invalid media (placeholder + `media-cap` reason). Deliberately minimal — no dedicated event machinery; the flat descriptor list makes the count honest. |
| Collage/slideshow empty after validation | Wrapper block dropped entirely (a zero-element collage is malformed) — consistent with the renderer's existing "never emit an empty container block" guards. |
| Telegram rejects the finalize edit as a CONTENT error (bad media, rights missing, cap misjudged) | v1 fallback ladder in `rich-edit.js`: one-shot plain edit of the SANITIZED source (`stripMediaMarkdown`, §16.4) — text and captions preserved, **images dropped** (a local path can't render as a working link; pre-review wording "visible as literal markdown links" was wrong for local paths). Capability error → latch; transient → rethrow. |
| Finalize fails TRANSIENT, or body overflows `richMaxLen` | Existing v1 route: discard preview + redeliver plain chunks via `deliverReplies`. Media-bearing replies on this path deliver text with media markdown sanitized out (`stripMediaMarkdown` applied before chunking when the chat's richText is on) — **images are not delivered**. Accepted v1 degradation, now explicit instead of implied; a `sendPhoto`-per-dropped-image rescue is a recorded §16.9 follow-up, not silently missing. |
| Overflow accounting caveat | The `richMaxLen` check runs on SOURCE markdown length, where `![cap](/long/abs/path.png)` counts its full path — an over-count vs Telegram's rendered-text limit (captions only). Safe direction (never a Telegram rejection), but a path-heavy reply can hit the discard-and-redeliver cliff earlier than its rendered size warrants. Documented, not corrected, in v1. |
| Short reply (< streamer `minChars`) with an image | Never goes live → plain `deliverReplies` → no rich, no image (§9 scope cut). Media markdown is caption-sanitized here too (same `stripMediaMarkdown` rule as the redeliver path) so the bubble never shows a raw local path. The prompt hint steers the agent to accompany images with substantive text; noted as a known authoring edge. |
| Upload mid-stream | Structurally impossible — media only exists in the `partial: false` render (§16.3), and tests pin that the resolver is never called in partial mode. |
| Steered multi-bubble turn with an image in a pre-steer bubble | Placeholder persists in the superseded bubble (§16.3); media renders only in the finalized last bubble. Documented v1 limitation. |
| Unsupported client | Same story as every rich message (§0.1/§0.9); opt-in default-off unchanged. |

## 17. v7 addendum — media rescue, bubble sealing, `file_id` reuse, and video/animation

**Status (2026-07-23): reviewed specification awaiting operator
alignment; implementation has not started.** This section is
append-only relative to the shipped §16 design. It defines the four
deferred follow-ups in their requested priority order. Independent
coherence, feasibility, security, scope, product, design, and
adversarial passes have been folded in, including phase-bounded rescue,
immutable per-turn validation context, ordered seal jobs, fail-closed
cache learning/materialization, and explicit ambiguity policy.

### 17.1 Goals, success criteria, and rollout boundary

The primary rescue goal is that an accepted rich-media reference is not
silently lost on the three deferred §16.5 paths: terminal content-error
fallback, transient discard/redelivery, and rich-body overflow. The
full addendum succeeds when:

1. A terminal rich content-error fallback first lands its sanitized
   plain text, then sends every accepted media item as a separate typed
   Telegram message in authored document order.
2. A streamed reply that is discarded because the final rich edit was
   transiently rejected or the body exceeded the single-rich-message
   limit first redelivers all plain text chunks, then sends every
   accepted media item separately in authored document order.
3. A preserved intermediate bubble that contains a streamed media
   placeholder gets one final `partial:false` seal edit at its
   `forceNewMessage` boundary, so its media can converge to the real
   inline block instead of remaining a placeholder forever.
4. Repeated local media references can reuse a Telegram `file_id`
   across edits and messages without bypassing path validation or
   accidentally serving bytes from an overwritten path.
5. The existing `![](source)` authoring surface emits photo, video, or
   animation typed blocks for supported sources; `.gif` is an
   animation and `.mp4` is a video.

All behavior remains behind the existing resolved `richText` opt-in.
When `richText` is false, there is no rich-media parse/resolution,
filesystem validation, cache lookup, seal, or rescue side effect. This
PR changes no defaults and enables no production chat. Both production
Bot API connections remain unable to execute the rich-block contract
recorded by G6 (§16.7).

The requested rescue scope is narrow. The already-documented short
reply case (a response that never crosses `streamMinChars`) still
sanitizes media away, as do the other non-streamer surfaces excluded by
§9/§16.9. They remain named non-goals rather than being accidentally
expanded here.

### 17.2 Research corrections and API facts

The current Telegram contract supports the proposed extension, with
two cautions:

- Bot API 10.2 defines asymmetric typed request/response shapes:
  `InputRichBlockPhoto.photo: InputMediaPhoto` returns
  `RichBlockPhoto.photo: PhotoSize[]`; video and animation return a
  `Video` and `Animation` object respectively. A non-inline
  `editMessageText` returns the edited `Message`, so a successful edit
  can teach the cache a reusable `file_id`. Direct uploads are forbidden
  only for inline-message edits, which polygram does not use here.
  ([input blocks](https://core.telegram.org/bots/api#inputrichblock),
  [response blocks](https://core.telegram.org/bots/api#richblock),
  [editMessageText](https://core.telegram.org/bots/api#editmessagetext))
- Telegram documents ordered block arrays but does not explicitly
  promise an identity-preserving request-block → response-block
  mapping. Learning from a rich response is therefore a guarded
  inference, never a delivery dependency.
- Telegram's own rich Markdown uses the same image syntax for a photo,
  MP4 video, and GIF animation, but typed-block construction requires
  polygram to choose the concrete type. Extension classification is the
  deterministic bridge; no file probing or new author syntax is needed.
- The portable upload ceilings remain 10 MiB for photos and 50 MiB for
  other multipart files. The existing shared 50 MiB request budget and
  50-media rich-message cap continue to apply across all supported
  kinds. ([sending files](https://core.telegram.org/bots/api#sending-files),
  [rich-message limits](https://core.telegram.org/bots/api#rich-message-limits))
- Telegram and grammY recommend `file_id` reuse, but the identifier is
  bot-specific and media-type-specific. One process hosts one bot in
  polygram, so a bounded process-memory cache supplies the correct
  scope without a persistent bot-identity schema.
  ([Telegram file rules](https://core.telegram.org/bots/api#sending-files),
  [grammY file guidance](https://grammy.dev/guide/files))

The overflow rescue needs a real sequencing correction. Today
`streamer.resolveRichPayload()` returns before `toRichPayload()` when
the source exceeds `richMaxLen`, so no resolver runs and no validated
`{source}` envelopes exist to reuse. Final-mode overflow must perform
one `partial:false` parse/resolution pass, retain only its accepted
media, and skip the rich edit. Partial streaming ticks retain the
shipped invariant: no filesystem access and no upload.

The steering hook also has a hard local constraint. Orchestra's
`ProcessManager` invokes the polygram callback without returning its
promise, and `onStreamChunk` is fire-and-forget in polygram. Making
`forceNewMessage()` `async` would therefore not order the upstream
events. The seal must snapshot and enqueue at the synchronous boundary,
serialize behind work already targeting the old message and earlier
seal boundaries, and be tracked/drained internally. It is a convergent
edit: the new bubble may begin streaming before the old bubble's
network edit completes.

### 17.3 One generalized media envelope and traversal

The renderer remains filesystem-free and the streamer remains
JSON-serializable. The shipped local envelope grows without losing its
source authority:

```text
accepted local media:
  { source: <realpath>, fingerprint: <stable string>, fileId?: <cached id> }

accepted URL media:
  <the validated http(s) URL string>

rescue entry:
  { kind: photo | video | animation,
    media: <envelope-or-URL>,
    caption: <authored caption or empty string> }
```

The fingerprint is one stable composite string. Every `BigInt` stat
component (`dev`, `ino`, `size`, `mtimeNs`, `ctimeNs`) is converted to
its decimal string before composition; no `BigInt` enters a block tree
that the streamer will pass to `JSON.stringify`.

Captions stay on the rich block and in the sanitized plain projection.
For rescue, a non-empty authored caption at or below Telegram's
1024-character caption limit is also attached as plain text to its
sidecar. This deliberate small duplication preserves media-to-text
association after all text chunks have landed. A longer caption is
omitted from the sidecar rather than truncated or followed by another
message; its complete text already exists in the plain projection.

One recursive, depth-first, document-order traversal owns media
collection for:

- rich materialization;
- media counting and the 50-item cap;
- fallback rescue extraction;
- cache request/response correlation; and
- nested collage/slideshow, list, quotation, and details trees.

Accepted duplicate references remain duplicate authored occurrences
and are rescued twice. Rejected sources, over-budget sources, and
attachment 51+ never enter the traversal's rescue output.

Polygram creates a per-turn media-delivery context beside the resolver.
It owns an immutable copy of that turn's active allowed roots, the
chat/thread and original reply target, envelope preflight, typed
sidecar sends, access to the process-scoped cache, and accumulated
partial-delivery outcome. The stateless rich editor receives this
context on each call, and each seal snapshot retains the same
originating context reference. The roots are never embedded in the
JSON-safe blocks or finalize result; neither the editor, rescuer, nor
process cache stores mutable "current chat" roots.

The context accumulates text, media, and placeholder-deletion failures
until outstanding seals and rescue work drain. Its terminal
`flushPartialDeliveryWarning()` sends at most one aggregate warning,
latches the reactor in `ERROR`, and records that the normal
streamed-success path must not clear that state. If the warning itself
cannot be sent, the source-free error is logged and the `ERROR` latch
remains.

### 17.4 Follow-up 1 — text-first typed media rescue

#### Terminal rich content-error fallback

`rich-edit.js` continues to own capability/content classification and
the one-shot sanitized plain edit. The streamer marks rich edit calls
with `preview`, `final`, or `seal` phase. A classified content error on
a `final` or `seal` call is the rescue boundary: once the plain edit
succeeds, it sends the accepted media from the already-resolved block
tree sequentially:

```text
photo      → sendPhoto
video      → sendVideo
animation  → sendAnimation
```

When the sanitized projection is empty, the editor skips the empty
plain edit, makes a best-effort `deleteMessage` call for the existing
placeholder bubble, then proceeds to typed media rescue. It returns an
explicit `bubbleRemoved` result so the streamer clears the deleted
message from its state. Deletion failure does not suppress the media,
but it is included in the one partial-delivery warning because the
placeholder may remain visible. The delegation rule below applies only
when a non-empty fallback edit was actually attempted.

Deleting that media-only placeholder also removes the first bubble's
reply anchor when it was the turn's first bubble. Each initial-send and
seal snapshot records `hadReplyAnchor`. The per-turn context puts the
original inbound `reply_parameters` on the first rescued media message
only when the deleted/discarded bubble had that anchor and no
replacement text chunk inherited it; later sidecars remain sequential
in the same thread. A later unanchored intermediate bubble never
re-quotes the user merely because its fallback projection is empty.

The rescue uses the validated local `{source, ...}` envelope as the
upload authority even if the failed rich request used a cached
`fileId`. Accepted URL strings remain strings. This both avoids
reparsing the authored Markdown and gives a stale cached ID a
source-upload recovery path.

Immediately before each local rescue upload, re-resolve the envelope's
stored source (never the original Markdown), require the canonical path
to remain identical and inside the active allowed roots, and require
the current stat fingerprint to match the envelope. Any mismatch rejects
that rescue item without an API call. This closes the longer fallback
window in which a path could be replaced or a symlink retargeted after
final resolution. As with every path-backed upload, a narrow same-UID
filesystem race remains between that final preflight and grammY opening
the file; the existing local-agent trust model accepts that residual.

A preview-phase content error performs the shipped sanitized plain edit
but does not rescue or delete anything. The terminal pass resolves the
complete source and owns the one rescue attempt; this prevents the same
growing media set from being resent on every throttled preview edit.

Capability fallback stays at the shipped v1 boundary: it latches the
connection and lands sanitized plain text without media rescue. That
case means the server cannot execute the rich-block contract at all,
and §16.9 deliberately named content error rather than capability
fallback. Keeping it out also prevents a partial capability failure
from forcing an early, incomplete sidecar set before the turn's final
source exists.

If the plain fallback edit fails, no media is sent there. Phase owns
the outcome:

- `preview` logs the failure and allows a later tick/final pass to retry;
- `final` propagates with the accepted rescue entries to the streamer's
  discard/redeliver path, which becomes the single owner of text and
  media recovery; and
- `seal` records a failed seal and keeps the old bubble's last
  successful shape; the active bubble is never discarded on the old
  generation's behalf.

This prevents two rescue attempts for one reply.

#### Transient/overflow discard and redelivery

`streamer.finalize()` returns the JSON-safe accepted rescue entries
alongside `finalEditOk:false` when:

- the final rich edit throws an unclassified/transient error; or
- the final rich body exceeds `richMaxLen`.

`polygram.js` then preserves a strict user-visible order:

1. discard the unreliable preview;
2. deliver every sanitized plain text chunk through
   `deliverReplies`;
3. send each accepted typed media item sequentially; and
4. if either text chunks or media items failed, send one aggregate
   partial-delivery warning and leave the reactor in `ERROR`.

A media-only fallback may have an empty sanitized text projection. It
skips the empty edit/send and proceeds directly to the accepted media;
no synthetic text bubble is introduced.

Rescue is best-effort and non-atomic. Each item gets one application
attempt (inside the existing `tg()` retry policy); a failure is recorded
and the remaining items continue. Once plain text has landed, a rescue
failure must not reject the editor/finalizer and trigger another text
redelivery, which would duplicate the answer. Telegram offers no
idempotency key, so an ambiguous timeout can still produce a duplicate
media message if Telegram accepted the request before the connection
failed. That is an accepted platform failure mode, not an exactly-once
claim.

The same ambiguity can affect the failed final rich edit itself:
Telegram may have applied it before the response was lost. Recovery
explicitly prefers completeness over deduplication. Polygram makes one
best-effort preview deletion and then performs one redelivery even when
the edit or deletion result is ambiguous. A deletion failure joins the
aggregate warning so the user is told the answer may be duplicated
rather than silently risking a missing answer.

`rich-media-rescue` telemetry records trigger
(`content-error`, `edit-failed`, `overflow`), attempted, sent, failed,
and counts by kind. It never records a path, URL, caption, or `file_id`.

`bubbleRemoved` has context-specific state transitions:

| Observer | State transition |
|---|---|
| Finalization | Clear `msgId` and rich dedup state; the final edit is considered delivered, subject to the media-delivery context's partial-failure latch. |
| Live flush | Never receives `bubbleRemoved`; preview fallback does not delete or rescue. |
| Detached seal | Update only the seal snapshot bookkeeping; never mutate the active bubble generation. |
| Placeholder deletion failed | Retain the prior message state so later cleanup still has its ID; record a partial-delivery failure. |

### 17.5 Follow-up 2 — seal preserved steered-turn bubbles

At `forceNewMessage()`, when the outgoing bubble exists and
`preserveIntermediateBubbles` is true:

1. cancel its pending throttle timer;
2. snapshot its generation, source text, current message ID or
   in-flight initial-send promise, and any edit already in flight;
3. synchronously detach/reset the state used by the next bubble;
4. after the old initial send/edit settles, run one final
   `partial:false` render for the snapshot; and
5. only when that final tree contains accepted media and differs from
   the last landed rich tree, target the old message ID with the normal
   rich editor.

Waiting for an old flush is mandatory: otherwise its placeholder edit
can arrive after the seal and overwrite the newly materialized media.
The initial send also needs a generation guard so a late result cannot
write its message ID into the new bubble's state.

Seal jobs append to one turn-local promise chain in force-boundary
order. A later seal waits for the earlier seal job, and final
redelivery/rescue waits behind the chain; streaming the active bubble
does not. This preserves sidecar chronology across rapid A→B→C
boundaries without blocking B or C's live text.

Seal failures are caught and logged without media sources inside that
chain. `flushDraft()`, `finalize()`, `discard()`, and terminal turn
cleanup observe/drain it so failures are not unhandled or silently
abandoned. Old-generation completions never mutate the new bubble's
`msgId`, `currentText`, or rich dedup state. A failed seal leaves the
intermediate bubble at its last successful shape and never poisons the
next bubble.

The seal deliberately does not run when:

- `preserveIntermediateBubbles` is false — the old bubble is archived
  for deletion, and fallback sidecar media would otherwise be orphaned;
- no outgoing message exists (including text below `minChars`);
- rich mode is disabled/latched; or
- the final snapshot contains no accepted media.

The in-flight initial-send promise is still tracked in terse mode. When
`preserveIntermediateBubbles` is false, an old-generation send that
resolves after the force boundary contributes its eventual message ID
to `archived` cleanup instead of being lost by the generation guard.

Because the upstream callbacks do not await, this is not a promise that
the seal finishes before the next bubble is sent. Inline success edits
the older message in place regardless of completion order. If the seal
itself falls back to plain plus sidecar rescue, those sidecars can land
after the next bubble has begun; the turn-end drain makes the final chat
complete, not strictly network-ordered.

### 17.6 Follow-up 3 — bounded local `path → file_id` reuse

Create one cache at daemon startup and inject it into every per-turn
media-delivery context; the context exposes it to that turn's resolver,
stateless rich-editor calls, and rescue sender. The cache is:

- scoped to the single bot process;
- local-path-only (URLs are mutable and have no local identity);
- keyed by media kind plus canonical realpath;
- guarded by a stat fingerprint containing device, inode, size, and
  nanosecond mtime/ctime where Node exposes them, encoded as the stable
  decimal-string composite defined in §17.3; and
- a fixed 256-entry LRU with no new operator configuration.

Every reference still performs the current URL/path classification,
`realpath` allowlist check, extension check, stat, per-kind cap, shared
budget, and count cap before cache lookup. A deleted, moved,
no-longer-allowed, changed, or retyped file cannot be sent merely
because its old path has a cached ID. A hit adds `fileId` to the
source-authoritative JSON-safe envelope; rich materialization prefers
that string, while rescue deliberately prefers `source`.

Immediately before materializing any local envelope — cached ID or
source upload — the editor repeats the context's canonical-path,
allowlist, and fingerprint preflight. A mismatch makes that occurrence
unavailable without an API call, evicts any matching cached ID, and
routes the terminal attempt through the same sanitized-text plus
remaining-media recovery as a local content failure. This prevents a
path mutation between resolution and edit invocation from serving
either pre-mutation cached bytes or unvalidated replacement bytes.

Cache population has two paths:

1. **Direct rescue result — authoritative.** One `sendPhoto`,
   `sendVideo`, or `sendAnimation` response corresponds to exactly one
   local rescue entry. Direct `sendPhoto` learning selects the
   `PhotoSize` with the largest width × height, the same rule used for
   a returned rich photo block. Re-stat before storing; if the
   fingerprint changed during upload, learn nothing.
2. **Successful rich edit — single-media only.** Flatten the outgoing
   and returned media trees, including URL entries. Learn only when each
   side contains exactly one media item of the same kind and the
   outgoing item is a local envelope. Equal count/kind sequences are
   insufficient for multi-media requests: Telegram does not explicitly
   guarantee request/response identity, so a same-kind permutation could
   poison one path with another file's ID. On multi-media, missing
   `rich_message`, `_notModified` synthetic result, missing `file_id`, or
   kind mismatch, learn nothing. For a photo, choose the returned
   `PhotoSize` with the largest width × height rather than assuming
   array order; video/animation expose their `file_id` directly. Store
   only when the current stat still matches the envelope fingerprint.

If a classified content error involved cached IDs, evict those request
entries before source-based rescue. This version does not retry the
rich edit with fresh uploads: error strings for the weeks-old block API
are not yet fleet-verified, and an unconditional second multipart edit
would delay every unrelated content fallback. Successful sidecar rescue
refreshes the exact entries instead.

The cache is an optimization only. A cold start, eviction, fingerprint
change, response-shape mismatch, or learning failure falls back to the
normal upload and cannot change delivery correctness.

### 17.7 Follow-up 4 — video, animation, and `.gif`

The agent authoring contract stays small:

```markdown
![diagram](/absolute/path/to/diagram.png)
![demo](/absolute/path/to/demo.mp4)
![motion](/absolute/path/to/motion.gif)
```

Local source classification is case-insensitive and strict:

| Extension | Rich block | Request media | Rescue |
|---|---|---|---|
| `.jpg`, `.jpeg`, `.png`, `.webp` | `photo` | `InputMediaPhoto` | `sendPhoto` |
| `.mp4` | `video` | `InputMediaVideo` | `sendVideo` |
| `.gif` | `animation` | `InputMediaAnimation` | `sendAnimation` |

For an accepted HTTP(S) URL, classify a `.gif` pathname as animation
and `.mp4` as video after stripping query/fragment. Every other URL
retains v1's photo behavior rather than breaking extensionless photo
URLs. URL media remains disabled whenever `apiRoot` is configured.

There is intentionally no silent-MP4 animation guess. `.mp4` is always
video and `.gif` is the supported animation form. Detecting an audio
track with `ffprobe` would add a process dependency and still would not
express author intent; a future explicit syntax is preferable if
silent-MP4 animations become important.

Collage/slideshow substitution accepts mixed supported media children
and preserves their authored order. Photo-specific placeholder and
instrumentation wording becomes media-generic. The message-wide 50
attachment cap and 50 MiB budget count all three types. The per-file
ceiling is 10 MiB for photos and 50 MiB for video/animation, each
clamped by the existing operator max-file override.

Only the `richText:true` display hint changes. It teaches the three
supported extension groups, the unchanged `![]()` syntax and group
wrappers, absolute/allowed paths, and the substantive accompanying-text
rule. Plain-mode agent context remains media-free. It never exposes
`file_id` values or asks the agent to choreograph uploads.

### 17.8 Failure-mode matrix

| Failure | Required result |
|---|---|
| Final/seal rich content error; sanitized fallback text succeeds | Keep the plain edit, then rescue each accepted media item by type. Evict cached IDs used by the failed request. Media failures continue and produce one aggregate warning. |
| Preview rich content error | Keep the sanitized plain edit; do not rescue or delete. The terminal final/seal phase owns the one complete rescue attempt. |
| Rich capability error | Preserve the shipped latch + sanitized plain fallback. Do not rescue media on a contract-unsupported connection. |
| Local media changes between resolution and rich materialization | Make the occurrence unavailable without an API call, evict its cached ID, and use terminal sanitized-text/remaining-media recovery. |
| Preview content fallback text edit fails | Log and leave the bubble at its last landed shape; a later tick/final pass may retry. |
| Final content fallback text edit fails | Send no media in the editor; throw to the single discard/redeliver owner. |
| Seal content fallback text edit fails | Send no media; preserve the old bubble's last landed shape and fail only that detached seal. |
| Classified fallback has an empty sanitized projection | Best-effort delete the placeholder bubble, clear streamer message state on success, rescue accepted media, and include deletion failure in the aggregate warning. |
| Final rich edit is transient/unclassified | `finalize()` returns accepted rescue entries; discard, redeliver all text chunks, rescue media, then warn once for aggregate failures. |
| Final rich source exceeds `richMaxLen` | Perform final-only resolution without a rich edit; discard, redeliver all text chunks, then rescue accepted media. |
| Rescue item fails | Continue later items; never retry/redeliver the landed text; log counts only and warn once. |
| Final rich-edit outcome and preview deletion are ambiguous | Prefer completeness: record the deletion failure, redeliver text and media once, and include possible duplication in the aggregate warning. |
| Seal races an old flush | Seal waits for the old request so the placeholder cannot overwrite it; generation guards isolate new state. |
| Rapid seals complete out of order | One turn-local seal chain preserves force-boundary order; final redelivery/rescue drains behind it. |
| Seal fails | Preserve the old bubble's last landed shape; log and let the next bubble/turn finish. |
| Cached path no longer validates or fingerprint changes | Treat as cache miss/rejection according to the ordinary resolver; never use the stale ID. |
| Rich response contains zero or multiple media, or its single media item is not same-kind/pairable | Skip all cache writes from that response; delivery remains successful. |
| Unsupported local extension or oversize media | Existing unavailable-media projection and source-free rejection telemetry; never rescue it. |
| `richText` false or capability already latched before resolution | Existing plain behavior; no resolver, cache, seal, or rescue work. |

### 17.9 Alternatives rejected

- **Reparse Markdown during rescue.** Rejected: it repeats an impure
  validation pass after failure, risks drift from what the rich attempt
  accepted, and cannot satisfy the already-validated-envelope
  requirement.
- **`sendMediaGroup` rescue.** Rejected: it requires 2–10 items, excludes
  animations, changes the requested separate-message behavior, and
  makes partial failure less isolated.
- **Rescue the latch-triggering capability fallback.** Rejected for this
  iteration: §16.9 names content-error and discard/redelivery loss, and
  a capability error commonly arrives during an incomplete preview.
  Keeping the shipped latch behavior avoids an early partial sidecar
  set. A future expansion would need one explicit final-only resolution
  pass after the latch, without retrying the unsupported rich request.
- **Make `forceNewMessage()` async and await it at the current callback.**
  Rejected locally: the orchestra callback wrapper does not return the
  promise. A cross-repository callback-contract change is unnecessary
  for a convergent edit and outside this branch.
- **Persistent SQLite cache.** Rejected: persistence needs bot/API-root
  identity and stale-content lifecycle policy. A restart cold miss is
  harmless; storing canonical paths durably adds risk without a delivery
  benefit.
- **Full-file hash on every lookup.** Rejected: reading up to 50 MiB to
  prove every cache hit defeats much of the upload-reuse benefit. A
  strong stat fingerprint plus validation is the proportionate local
  identity.
- **Order-infer cache learning for multi-media rich responses.**
  Rejected: count and kind checks cannot detect a same-kind permutation,
  which could associate a path with another attachment's bytes.
  Single-media rich responses and one-item rescue responses are the
  only safe learning surfaces without an explicit Telegram identity
  guarantee.
- **Pre-upload media to obtain IDs.** Rejected: Telegram has no invisible
  generic upload endpoint; it would create visible throwaway messages
  and reintroduce the sequencing §16 avoided.
- **Retry every cached-ID content error as a rich source upload.**
  Deferred until live error shapes are known. Source-based typed rescue
  is deterministic and refreshes exact one-item mappings without a
  second speculative multipart edit.
- **MIME/`ffprobe` classification or new animation syntax.** Rejected for
  this scope. Extension classification matches the existing authoring
  contract; explicit syntax is the future answer if `.mp4` animation
  intent is needed.

### 17.10 Interfaces and implementation order

Expected implementation surfaces:

- `lib/telegram/rich.js` — kind-aware descriptors/blocks, generic
  traversal/count/placeholders, mixed wrappers.
- `lib/telegram/rich-media.js` — kind/path/size validation, JSON-safe
  envelope fingerprints, bounded cache and typed rescue primitives.
- `lib/telegram/rich-edit.js` — kind-aware materialization, guarded
  response learning, classified text-first rescue via the passed
  per-turn delivery context, cached-ID eviction.
- `lib/telegram/streamer.js` — overflow final-resolution handoff,
  rescue entries in finalize results, initial-send/flush-safe seal
  tracking and draining.
- `polygram.js` — one process cache, one media-delivery context per
  turn, text-chunks-then-media redelivery, reply anchoring, aggregate
  warning, and reactor-state ownership.
- `lib/telegram/display-hint.js` — rich-only `.mp4`/`.gif` authoring
  guidance.
- `scripts/spikes/rich-media-blocks.mjs` — dry-run-safe G6 extensions
  for video, animation, mixed wrappers, response shapes, and cached-ID
  reuse.

Implementation follows the requested priority with a green checkpoint
after each numbered follow-up. The first slice introduces only a small
depth-first media walker and typed rescue entry over the shipped photo
descriptors. It does not pull cache behavior or future media kinds
forward merely to avoid a later mechanical extension.

### 17.12 Non-goals retained

### 17.13 v8 implementation record — 2026-07-23

The v7 design above is implemented without changing its rollout
boundary:

- terminal content-error fallback and discard/redelivery now deliver
  accepted media as typed, ordered sidecars after plain text;
- steered intermediate bubbles are sealed with a final media-aware edit

  late-initial-send handling;
