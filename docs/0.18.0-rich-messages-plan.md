## 0. Reality-check pass (corrections to initial framing)

Corrections found while researching, before any design was locked in:

1. **"Automatic per-client enable/disable" is not achievable.** The Bot API
   exposes no `platform`/`client_type` field anywhere in `User` or `Message`.
   A `sendRichMessage` call to a Telegram-Web user **succeeds** (`ok: true`)
   — the failure is 100% client-side rendering (a dead "not supported"
   placeholder card) and produces **no error signal to the bot**, before or
   after. Confirmed independently three times: our own doc read, openclaw's
   issue #93263, hermes-agent's issue #45785. This is why both reference
   projects converged on manual opt-in rather than detection — there is
   nothing to detect.

2. **The Bot API "Checklist" object (`sendChecklist`/`editMessageChecklist`,
   Bot API 9.1, shipped 2025-07-03) is a different feature from Rich
   Messages (Bot API 10.1/10.2, shipped a year later, 2026-06-11/07-14) and
   is irrelevant here.** Checklist requires `business_connection_id` and can
   only be sent on behalf of a connected Telegram Business account — not
   usable by a normal bot. Rich Messages' `sendRichMessage` has
   `business_connection_id` as **optional** — any bot can use it in any
   chat type it can already post to. Don't conflate the two in code or
   in this doc.

3. **Rich Message checkboxes (`RichBlockListItem.has_checkbox`/`is_checked`)
   are not interactive.** No update/callback fires when a user taps one —
   confirmed via the API schema (no such field exists) and via both
   openclaw and hermes-agent's implementations, which source checkbox state
   purely from the agent's own authored markdown (`- [ ]` / `- [x]`), never
   from a user action. Anything that wants a user-toggleable task needs an
   inline keyboard button layered on top, which is out of scope here.

4. **Architecture fork — OPEN, not resolved (corrected in v2).** openclaw
   shipped an HTML-string renderer first (PR #93286), hit a real
   production bug from it (`\n` collapsing inside rich HTML — issue
   #95409), and **deleted the whole HTML layer** in favor of a typed
   `InputRichBlock[]` tree (PR #107986, merged 2026-07-15). hermes-agent,
   by contrast, passes raw markdown strings through `InputRichMessage.
   markdown` and has kept it working in production via targeted escaping
   (protected regions for code/tables, `\n`→hard break normalization,
   `$`-escaping).
   >
   > **v1 read this as "openclaw's experience indicts strings, build
   > blocks" — the scope review caught that this misapplies the evidence.**
   > openclaw deleted an **HTML-string round-trip** (markdown → HTML →
   > Telegram re-parses HTML), a different and more fragile thing than
   > **markdown-string passthrough** (hermes-agent's actual approach,
   > still in production). The approach v1 rejected is the one that's
   > working; the approach v1 cited as the cautionary tale is a third,
   > different thing nobody proposed building.
   >
   > The feasibility review also punctured v1's strongest pro-blocks
   > argument — that blocks are "a natural extension of `buildRenderer()`."
   > In reality `format.js`'s `_markedInstance` has a **fixed** HTML
   > renderer baked in at construction time and never exposes a reusable
   > token tree; a blocks renderer needs its own `marked.lexer()` call —
   > it's a **parallel** renderer, not an extension. And two things v1
   > claimed blocks would "avoid duplicating" — `wrapFileReferencesInHtml`
   > and the table column-padding logic — are HTML/`<pre>`-specific and
   > **not reusable for blocks either**, so blocks has to reimplement
   > those too. Net: the effort delta between the two approaches is
   > smaller than v1 argued, in both directions.
   >
   > **v2 left this as an open Phase-0 spike question. v3: decided —
   > build typed blocks**, the operator's explicit call: polygram already
   > leans on openclaw's prior art elsewhere (the existing HTML pipeline's
   > file-ref wrapping and spoiler handling are ported from them), they
   > iterated to the blocks design twice in production, and that's enough
   > trust to commit to it rather than re-run a cheapest-first bake-off.
   > **"Trust but verify" — this does not remove G1's round-trip and
   > adversarial-content checks (§6); it removes the passthrough A/B, not
   > the verification.** If G1 finds blocks genuinely broken against real
   > content, that's still a stop-and-reconsider signal, just not an
   > A/B comparison anymore. §13 Q1 is closed.

5. **Polygram is single-backend since the `@shumkov/orchestra` migration.**
   `AGENTS.md`'s "SDK backend vs tmux backend" framing is **stale** — `git
   log -- lib/process/` shows `lib/process/sdk-process.js` and
   `cli-process.js` were removed when polygram moved to depending on
   `@shumkov/orchestra` for the Claude session engine (commits `cec4d91`,
   `a9a12ed`). `lib/pm-interface.js` now states explicitly: "Implemented by
   `lib/sdk/process-manager.js` (the only pm impl post-0.9.0)." System-prompt
   composition is a single path: `lib/agents/loader.js` `composeSdkOptions()`
   → `lib/sdk/build-options.js`. This *simplifies* the plan — the "does our
   rich-authoring hint reach every runtime" concern from hermes-agent's
   #108264 lesson collapses to verifying one path, not several. (Caught by
   reading `git log` before drafting Gate 7 below — would have written a
   gate against files that no longer exist.)

6. **Polygram supports an optional self-hosted local Bot API server**
   (`config.bot.apiRoot`, see `docs/0.12.0-file-send.md`) for the 2GB file
   cap. That server is a separate binary (`telegram-bot-api`, built from
   TDLib) with **its own release cadence**, independently of cloud
   Telegram. It may not support Bot API 10.1/10.2 methods yet even after
   cloud Telegram does. Neither openclaw nor hermes-agent's research
   surfaced an equivalent concern (they appear cloud-API-only), so this is
   a polygram-specific capability axis with no prior art to lean on. Per
   fleet memory, `apiRoot` has a history of being unset/orphaned — G4
   (§6) is now gated on "only run if a bot currently has `apiRoot` set,"
   not treated as universally load-bearing.

7. **[v2, from failure-modes review] The plain-HTML fallback is NOT
   "always safe" for the checklist use case — this is a real, pre-existing
   correctness bug the whole fallback design depends on being fixed
   first.** `format.js` has no `checkbox()` renderer; `marked` (gfm:true)
   falls through to its default for a task-list item and emits literal
   `<input type="checkbox">` HTML. Verified by running the real renderer:
   `- [ ] first task` → `<input disabled="" type="checkbox"> first task`.
   **Telegram's `parse_mode: HTML` does not support `<input>`** — this is
   a guaranteed `400 can't parse entities: Unsupported start tag "input"`
   today, on the CURRENT plain pipeline, for any agent reply containing a
   markdown task list, rich text or not. `api.js`'s existing HTML→plain
   fallback (triggered on that 400) then reverts the **entire message** to
   raw markdown source — every `**bold**`/table/etc. in that reply
   degrades to literal characters, not just the checkbox line.
   This directly undermines §5/§10's "content-error fallback always
   degrades safely to `toTelegramHtml`" invariant — for a checklist reply,
   that fallback target is itself broken. **A `checkbox()` renderer in
   `format.js` (emit `☐`/`☑` text, never `<input>`) is a prerequisite for
   this entire plan, independent of the blocks-vs-string decision, and
   should ship as its own small fix before Phase 0 starts** (it's a latent
   bug in shipped code today, not new-feature work — see §11).

8. **[v2, from feasibility + failure-modes reviews] Rich delivery, as
   scoped in v1, only reaches ONE of polygram's several agent-text send
   surfaces.** v1 wired rich exclusively into `lib/telegram/streamer.js`'s
   `finalize()`. But: (a) short replies that never cross the streamer's
   `minChars` threshold stay in `state==='idle'` and are delivered by
   whatever calls `finalize()` on a never-gone-live streamer via the
   plain `deliverReplies` path, not through the rich-aware finalize edit;
   (b) `lib/telegram/process-agent-reply.js` — autonomous-wakeup,
   auto-resume, and autosteer extra-turn replies — sends via
   `chunkMarkdownText` + plain `deliverReplies` (`lib/telegram/deliver.js`)
   directly, bypassing the streamer entirely. Its own file header
   apparently documents this as exactly the class of surface that
   "silently missed protections" historically. So even with richtext on
   and a table-shaped autonomous-wakeup reply, it would render plain while
   an equivalent normal streamed reply renders rich — a real, silent
   inconsistency. v1 implicitly assumed "non-streamed single-shot replies
   can go rich too" (§7's G3-fail branch says so) without actually wiring
   them. **v2 makes this an explicit, named non-goal (§9) instead of an
   accidental gap** — `deliverReplies`/`process-agent-reply.js` integration
   is deferred, not silently missing.

9. **[v4, from live G5 observation] Degradation on an outdated client may
   be softer than §0.1 assumed — informal single observation, not yet
   systematically verified.** §0.1's "silent total failure" model was
   sourced from openclaw's and hermes-agent's GitHub issues, both
   describing **Telegram Web** specifically ("This message is currently
   not supported on Telegram Web" — a hard, content-blocking placeholder,
   confirmed via those projects' bug reports, not directly observed by
   us). Operator observation (2026-07-21, live G5 session): on an
   **outdated Telegram Desktop build for macOS**, the rich test messages
   showed some kind of notice/banner ABOVE the content, but the
   checklist/checkboxes remained VISIBLE below it — not the all-or-
   nothing placeholder card §0.1 assumed. This suggests degradation may
   differ meaningfully by client (Web vs. Desktop) and possibly by how
   far out of date the client is, rather than being one uniform failure
   mode across "any unsupporting client." **Not yet acted on** — no exact
   client version, no exact banner wording, and no test across Telegram
   Web / iOS / Android specifically were captured this session. Per
   operator instruction: keep the current opt-in default-off design as-is
   for now; this becomes a follow-up experiment, not an immediate design
   change. See §14.

## 1. Problem & use cases

Telegram Bot API 10.1 (2026-06-11) + 10.2 (2026-07-14) added `sendRichMessage`
/ `sendRichMessageDraft` / `editMessageText{rich_message}` — a genuine
structured-document format (headings, tables, checkbox/ordered/bulleted
lists, collapsible `<details>`, block quotes, collages, slideshows, math) any
bot can send, distinct from and much more capable than the HTML-flattened
markdown polygram already sends via `toTelegramHtml`.

Prioritized use cases for polygram (from operator brainstorm 2026-07-21):

| # | Use case | v1 scope? |
|---|---|---|
| 1 | Task/step progress checklist — agent authors `- [ ]`/`- [x]` markdown, rendered as a real checkbox list, edited in place as steps complete | **Yes** — the original motivating case |
| 2 | Structured reports — tables + headings for pulse reports, session-GC summaries, cost/usage breakdowns | **Yes** |
| 3 | Collapsible detail (`<details>`) for verbose logs/diffs, keeping the chat scannable | **Yes** |
| 4 | Visual walkthroughs — collage/slideshow for before/after screenshots | **Deferred to v2** — media blocks add real complexity (50-media cap, `tg://photo?id=` indirection) on top of an already-large v1; revisit after v1 soaks |
| 5 | Streaming "thinking" preview via `sendRichMessageDraft` | **Non-goal for v1** — see §9 |

## 2. Chosen approach

- **Renderer approach — DECIDED (v3): typed blocks.** New
  `lib/telegram/rich.js` module, runs its own `marked.lexer()` call (v1
  overstated this as "reusing" `format.js`'s parse — `format.js`'s
  `_markedInstance` has a fixed HTML renderer baked in and exposes no
  reusable token tree, so this is a **parallel** parser, not an
  extension) and walks the tokens into `RichBlock` JSON (heading/
  paragraph/list/table/blockquote/details/pre), following openclaw's
  post-#107986 architecture: `markdown → IR-equivalent token walk →
  typed InputRichBlock[]`, not a string. Exports
  `toTelegramRichBlocks(markdown) -> { blocks: RichBlock[], usedRich: bool }`.
  String passthrough (both openclaw's abandoned HTML-string and
  hermes-agent's still-working markdown-string approach) is not being
  built — see §3.

- **Content-adaptive gate, not "richtext on → everything is rich."**
  Mirrors hermes-agent's `_needs_rich_rendering` (their fix for issue
  #45762 — rich rendering makes ordinary prose look oversized with no
  Bot-API knob to fix that, so the fix was to reserve rich for content that
  actually needs it). `needsRichRendering(markdown)` returns true when the
  markdown contains a pipe-table separator row, a task-list item (`- [ ] `/
  `- [x] `), a `<details>` block, **or [v3, promoted from "stretch v1.1"]
  a heading (`#`/`##`/etc.)** — headings carry none of the oversized-body-
  text risk tables/long content do (no size/typography escalation, just a
  `RichBlockSectionHeading` with a `size` field), and "combine headers...
  together" was the original motivating ask, so there's no reason to defer
  them. Plain prose (no table/task-list/details/heading) always stays on
  the existing `toTelegramHtml` path even when the chat has richtext on.

- **Per-chat opt-in, default OFF.** Toggled through the existing
  `/config` surface (§13 Q2, closed — no new standalone command), same
  write mechanics as `/model X` in `lib/handlers/slash-commands.js`
  (`getConfigWriteScope` write + `saveConfig()` + `db.logConfigChange` +
  confirmation reply).
  **[v2 correction — this claim was self-contradictory in v1]** v1 said
  this needs "no reload/respawn" across the board. That's only true for
  **delivery** — `needsRichRendering()`/`sendRichMessage` read
  `chatConfig` live at send time, confirmed feasible against
  `resolveMaxFileOverride`'s identical precedence pattern in
  `attachments.js`. It is **not** true for the **prompt hint** (below) —
  `composeSdkOptions()`/`buildSdkOptions()` compose the system prompt at
  **spawn/resume time**; there is no live system-prompt swap anywhere in
  `@shumkov/orchestra` (`lib/pm-interface.js` exposes `setModel`/
  `applyFlagSettings`/`setPermissionMode`, nothing for the prompt).
  So `/richtext on` mid-session flips delivery instantly but the agent
  isn't *steered* to author rich constructs until its next (re)spawn —
  same situation `/model`/`/effort`'s `cliAwareSuffix` caveat exists for.
  The reply text should say so plainly, e.g. "Rich text → on (delivery is
  live now; the agent starts writing for it on your next fresh session)."
  Both openclaw (`channels.telegram.richMessages`, default `false`) and
  hermes-agent (`extra.rich_messages`, default `False`, restored after a
  same-week revert of an "always on" attempt — PRs #45584 → #45953 →
  #50322) landed on opt-in-default-off independently. Confirms rather
  than merely informs the operator's own call.

- **Two-tier error classification**, extending the existing
  `isHtmlParseError`/`isRateLimitError` family in `format.js`:
  - `isRichCapabilityError(err)` — endpoint missing / 404 / method-not-found
    style errors **only**. **Latches rich off for the process lifetime**
    — retrying a permanently-missing endpoint on every future send is
    pure waste. Mirrors hermes-agent's `_is_rich_capability_error` exactly.
    **[v2]** Keyed by `apiRoot` string alone (see §5 — collapses to a
    single boolean per process; never the raw bot token, per security
    review F2 — Telegram error strings/URLs can embed the token, so any
    latch key or logged error string MUST go through the existing
    `redactBotToken()` (`lib/error/net`, already used at `api.js:284/290`)
    before it's logged or compared). **[v2]** A transient error that
    matches **neither** classifier (network blip, 5xx, ETIMEDOUT) must
    **not** latch — treat as transient and fall through to the existing
    retry path. Only unambiguous 404/method-not-found latches. **[v2]**
    Trip the latch with a `rich-capability-latched` WARN-level `logEvent`
    (chat, bot connection, redacted error) — per this project's fail-loud
    convention, a permanent, un-clearable, process-lifetime state change
    must never happen silently.
  - `isRichContentError(err)` — parse errors, `RICH_MESSAGE_BLOCKS_TOO_MANY`,
    `RICH_MESSAGE_TABLE_COLS_TOO_MANY`, etc. **Falls back once, does not
    latch** — the next message may be fine. Mirrors openclaw's
    `rich-plain-fallback.ts` (error-driven, not speculative
    pre-validation) and hermes-agent's `_is_rich_fallback_error`.
  - On a content-error fallback, degrade the **same already-built content**
    — project the rich block tree back to the existing plain
    `toTelegramHtml` output, not a second independently-authored plain
    version. Single source of truth per reply. **[v2, security F1 —
    unresolved, needs a gate]** This degrade path is only as safe as
    `toTelegramHtml` itself, and per §0.7 that pipeline currently has a
    real gap (task-list → `<input>`) that must be fixed first. Separately,
    the inline-text representation *inside* rich blocks (bold/links/code-
    spans within a block's text) is not yet specified — if Telegram
    re-parses block text as markdown/entities rather than treating it as
    structured plain text, the escaping guarantee `escapeHtml`/
    `escapeHtmlAttr` provide today must be re-established per-block, or
    agent-relayed untrusted text (user messages, file contents) could
    inject formatting/links. Needs an explicit adversarial-content check
    in G1 (§6): send a block whose text contains `<b>`, `&`, markdown
    link syntax, and confirm literal rendering.

- **Streaming: progressive rich edit-in-place, no `sendRichMessageDraft`
  in v1.** **[v3 correction]** v2 stated both reference projects converged
  on "stream plain, upgrade to rich only at the final edit" — that's only
  true for hermes-agent. **openclaw actually streams rich the whole time**:
  the preview itself is sent/edited as `{blocks}` from early in the turn,
  via throttled `editMessageText{rich_message}` at ~1s cadence (same
  order of magnitude as polygram's existing `DEFAULT_THROTTLE_MS` in
  `streamer.js`) — not the native draft mechanism. Both projects agree on
  the parts that matter for architecture:
  - **Neither uses `sendRichMessageDraft`.** openclaw rejected it outright
    (issue #93438 — "conflicts with the established streaming contract").
    hermes-agent kept it but demoted it to disposable/best-effort/DM-only.
    Both edit the SAME message in place rather than send-fresh-and-delete
    — hermes-agent explicitly reverted the latter (issue #46206, "briefly
    shows two copies of the final answer… looks like duplicate delivery").
  - Where they differ is **whether the in-progress edits are themselves
    rich.** Given the operator's steer toward openclaw's design and
    toward UX quality, **v3 picks openclaw's shape: progressive rich
    streaming**, not finalize-only. The reply looks structured as it
    grows instead of flipping shape at the very end.

  Polygram's `lib/telegram/streamer.js` already edits a single message id
  in place with throttled edits — the integration is: once
  `needsRichRendering()` first triggers on the growing text (it may not
  trigger on chunk 1, e.g. a table's separator row hasn't arrived yet),
  every subsequent throttled edit uses `editMessageText{rich_message}`
  instead of plain text, including the final one. Before that point,
  stream plain as today (G1(b) from §6 already validates that an existing
  plain message can be upgraded to rich via edit — this is exactly that
  operation, just potentially happening mid-stream instead of only at the
  end).

  **New wrinkle from streaming mid-structure, needs its own gate (§6,
  folded into G1):** the growing text can produce a genuinely incomplete
  block tree — an unclosed table, a truncated list item, a `<details>`
  whose closing tag hasn't arrived. The renderer must only emit **complete**
  top-level blocks and hold the trailing incomplete one back (render it as
  plain text appended after the complete blocks, or omit it until
  complete) — mirroring how `truncateForLive` already handles the
  surrogate-pair-safe live-text truncation for the plain path today. If
  this proves unsafe/flickery in practice (G1 gate fails), the fallback is
  hermes-agent's more conservative shape — finalize-only — not abandoning
  rich streaming altogether; keep that as the documented decision-tree
  branch (§7), not a silent regression.

  **[v2, must-fix bug from failure-modes review, still applies — now to
  every throttled edit, not just the final one]** The overflow check
  (`body.length > maxLen`, `streamer.js:53,316`) runs **before** any rich
  decision, and `maxLen` defaults to **4096** — the plain `sendMessage`
  cap. Rich messages allow **32,768** chars. Now that rich edits can
  happen throughout the stream, not only at `finalize()`, every rich-path
  edit needs the rich-aware `maxLen` (32,768), not just the last one, or
  a mid-size structured reply gets discarded and redelivered plain
  partway through its own stream. Also make explicit (new invariant,
  §10): **rich is single-message only** — if a reply is long enough to
  need chunking even at the 32,768 rich cap, it is sent plain via the
  existing `deliverReplies` path. This confirms a mixed
  rich-chunk-1/garbled-plain-chunk-2 outcome is structurally impossible —
  `deliverReplies` has no rich awareness at all.

- **Retry/rate-limit.** `lib/telegram/api.js` already has a single retry
  honoring `getRetryAfterMs()` (capped at **30s** — `RETRY_AFTER_CAP_MS`,
  `api.js:262,309`; v1 said 60s, that number only survives in a stale
  code comment, corrected in v2) — see `api.js:~243-311`.
  hermes-agent's issue #46762 (a dropped final response under flood
  control) traced to a retry budget of 2 attempts being insufficient
  against 25-40s Telegram-reported waits; their fix combined honoring the
  server value **and** widening the budget. Polygram's existing single
  retry already honors the server value structurally — Gate 6 (below)
  measures whether one retry is enough for the larger, table/media-bearing
  rich payloads, or whether the budget needs raising specifically for
  rich sends.

- **Prompt hint, injected at spawn, one turn behind the toggle.** A rich-
  authoring system-prompt fragment (steer the agent toward `- [ ]` task
  lists / pipe tables / `<details>` when they help), injected only when
  the chat's `/richtext` is on. Both reference projects independently
  learned the hint and the delivery layer must be coupled — hermes-agent's
  base hint literally says "prefer bullet lists" when rich is off, and
  switches to encouraging tables/task-lists only when on; openclaw's
  #108264 fix was specifically about the hint not reaching a runtime that
  then authored content the delivery layer couldn't render. Per the
  corrected §0.5 finding, polygram has exactly one system-prompt assembly
  path — **[v2 correction]** the actual wiring point is
  `lib/sdk/build-options.js` (where `appendDisplayHint` already runs
  post-compose), not `composeSdkOptions()` itself, which just spreads
  `chatConfig` through unchanged. **[v2]** Per the opt-in bullet above,
  this hint is spawn-time, not live — accept a one-session authoring lag
  as v1 behavior: `/richtext on` makes delivery rich-capable immediately,
  but the agent isn't told to *write* for it until the session's next
  (re)spawn. Document this in the `/richtext` reply text; do not claim
  "lockstep" as if both halves updated together.

## 3. Rejected alternatives

- **[v3, decided]** Markdown-string passthrough into `InputRichMessage.
  markdown` (hermes-agent's approach, still working in their production).
  Not rejected on technical grounds — v2 confirmed it's viable — but not
  chosen: operator directive is to build typed blocks, trusting openclaw's
  twice-iterated design over re-running a cheapest-first comparison (§0.4).
  Worth revisiting only if Phase 0's G1 finds blocks genuinely broken
  against real content (§7).

- **Raw HTML string passthrough into `InputRichMessage.html`** (openclaw's
  now-abandoned first approach, PR #93286). Rejected on technical grounds
  — openclaw's own postmortem (§0.4) is direct evidence of the failure
  class: the round-trip was "a standing source of `can't parse entities`
  400s and formatting degradations," including the `\n`-collapsing bug
  (#95409). Not revisited.

- **Always-on by default.** Rejected — see §0.1 and §2's opt-in
  discussion. Every project that tried this (hermes-agent, twice) reverted
  within days of shipping, once because of a real total-outage bug
  (openclaw #93263) and once because of the silent-Web-failure risk
  (hermes-agent's #45785-driven revert).

- **`sendRichMessageDraft` for live streaming.** Rejected for v1 — see §2's
  streaming section and §9.

- **Any form of automatic client detection.** Not possible against the
  documented Bot API (§0.1). Not attempted.

## 4. Config & command design

Per-chat toggle, following the existing `topic → chat → bot → default`
precedence already used for `maxFileBytes` (`lib/attachments.js`,
`docs/0.12.0-file-send.md`):

```jsonc
{
  "defaults": { "richText": false },
  "bots": { "shumabit": { "richText": false } },
  "chats": {
    "-1003807211164": {
      "richText": true,
      "topics": { "3": { "richText": false } }
    }
  }
}
```

**[v3, §13 Q2 closed]** Folds into the existing `/config` surface rather
than becoming a new standalone top-level command — one less command for
the operator to remember, and `richText` shows up alongside `model`/
`effort` on the `/config` card the same way those already do. The write
path is unchanged regardless of exact command syntax (a Phase-1
implementation detail, not an architecture question): writes to
`getConfigWriteScope(chatConfig, threadIdStr).scope.richText` (same call
`/model` uses), persists via `saveConfig()`, logs via
`db.logConfigChange({field: 'richText', ...})`. No spawn/reload needed for
delivery — read live at send time by whatever composes the outgoing
message; the prompt-hint half still lags to next spawn (§2).

## 5. Interface sketches (not full implementations)

### `lib/telegram/rich.js`

```js
// needsRichRendering(markdown) -> boolean
// True iff markdown contains a pipe-table separator row, a task-list
// item ("- [ ] " / "- [x] "), or a <details> block. Conservative by
// design — false negatives mean "sent as today's plain HTML" — [v2:
// this is ONLY safe once the format.js checkbox() prerequisite (§0.7,
// §11 Phase -1) ships; today it is NOT safe for task-list content].
// False positives risk the oversized-body-text problem hermes-agent hit
// (issue #45762).

// toTelegramRichBlocks(markdown) -> { blocks: RichBlock[], usedRich: boolean }
// [v3: decided — typed blocks, see §0.4] Runs its OWN marked.lexer() call
// (NOT a shared parse with format.js — format.js's _markedInstance has a
// fixed HTML renderer baked in and exposes no reusable token tree, v1 was
// wrong about this being "the same parse"); walks the resulting tokens
// with a block-emitting renderer parallel in spirit to buildRenderer()'s
// HTML-emitting one, but not literally sharing code with it (file-ref
// wrapping and table column-padding are HTML-string-specific and need
// their own block-shaped reimplementation). usedRich=false (and
// blocks=[]) when needsRichRendering() was false — caller should use the
// existing toTelegramHtml() path in that case, not call sendRichMessage
// with a single-paragraph block.
//
// [v3, streaming] Also accepts a `partial: boolean` mode for mid-stream
// calls: when true, drops the trailing incomplete top-level block (an
// unclosed table/list/details) from the returned array rather than
// mis-rendering it, per §2's streaming bullet. The dropped tail is
// appended back in as it completes on the next chunk.

// isRichCapabilityError(err) -> boolean   — endpoint missing/404/method-not-found
// isRichContentError(err) -> boolean      — parse error, blocks/table/char limit rejection
// projectRichBlocksToPlainMarkdown(blocks) -> string
//   — degrade path for content-error fallback; feeds back into the
//   existing toTelegramHtml() so ONE renderer produces what the user
//   sees, whichever path was taken.
```

### Capability latch

```js
// [v2 — simplified from a Map to a boolean, per scope review] Polygram
// runs ONE bot per process, with a single config.bot.apiRoot resolved at
// boot (config.bot = config.bots[name]) — there is only ever one
// "connection" per process, so a Map<botConnectionKey, boolean> was
// modeling a multi-connection world that doesn't exist here. This also
// moots v1's §13 Q3 (per-connection vs per-chat latch) — both collapse
// to the same single boolean.
let richKnownUnsupported = false;  // module-level; never cleared this process

// On isRichCapabilityError(err): set richKnownUnsupported = true AND
// logEvent('rich-capability-latched', { chat_id, api_root: config.bot?.apiRoot
// ?? 'cloud', error: redactBotToken(errorMessage(err)) }) — see §2's error
// classification bullet. Never log/compare the raw bot token itself.
```

### `format.js` prerequisite — `checkbox()` renderer [v2, new]

Independent of the blocks-vs-string decision, ships before Phase 0:

```js
// buildRenderer()'s marked config needs an explicit checkbox extension/
// override so a task-list item ("- [ ] x" / "- [x] x") never falls
// through to marked's default `<input type="checkbox">` output — Telegram
// HTML parse_mode rejects <input> outright (400: Unsupported start tag).
// Render as literal "☐ "/"☑ " (or "[ ] "/"[x] ") text ahead of the
// listitem's normal content instead. This is a standalone bugfix to
// TODAY's plain pipeline (§0.7) — the rich work's fallback safety
// depends on it but doesn't require anything else about this plan.
```

### Instrumentation [v3, expanded from v2's capability-latch-only note]

Per operator request — cover the whole feature, not just the latch. New
`logEvent` calls, all following the existing shape (`telegram-html-
fallback`, `telegram-rate-limit` in `api.js`) — method/chat_id/thread_id +
a short classification, never full block/message content, error strings
always through `redactBotToken()` first (`lib/error/net`, already used at
`api.js:284,290`):

- `rich-message-sent` — a reply actually went out via `sendRichMessage`/
  `editMessageText{rich_message}`. Fields: `chat_id`, `streaming: bool`,
  `block_count`, `char_count`. Lets soak (§11 Phase 2) answer "is this
  feature actually being used, and how" without grepping raw logs.
- `rich-streaming-upgrade` — the moment a streaming reply's edits switch
  from plain to rich mid-turn (the "new wrinkle" in the streaming bullet
  above). Fields: `chat_id`, `msg_id`, `chunk_index_at_upgrade`. This is a
  real, visible UX transition (the bubble's shape changes mid-stream) —
  worth being able to correlate against user reports of "it looked weird
  partway through."
- `rich-content-fallback` — a single-message, non-latching
  content-error fallback fired. Fields: `chat_id`, `error_class`
  (`isRichContentError` match, e.g. `blocks_too_many`/`table_cols`/
  `parse_error`), redacted error string. This is the "did the safety net
  catch something" signal — should be rare; a spike in these post-ship is
  the first thing to check.
- `rich-capability-latched` — unchanged from v2 (§2's error-classification
  bullet): WARN-level, fires once per process lifetime max, chat + bot
  connection + redacted error. Given the latch is permanent and
  un-clearable, this is the most important of the four to never miss.

All four together answer, for soak (§11 Phase 2): is rich being used, is
the mid-stream transition visible/jarring, is the safety net firing more
than expected, and has the feature silently died for a bot connection.

## 7. Decision tree per gate failure

- **G1(a) round-trip fails** → block everything else; re-read the API
  reference, this is foundational. Does not fall back to string
  passthrough automatically — per the operator's decision (§0.4), a
  failure here is a "figure out what we misread" signal, not an
  architecture-swap trigger; re-raise to the operator if it looks like a
  genuine blocker rather than a fixable misunderstanding.
- **G1(b) text→rich edit fails** → drop both "finalize in place" AND
  progressive mid-stream upgrade; streaming replies never go rich in v1
  (only the single-shot content-adaptive path does, via whichever surface
  is wired per the §9 non-goal note) — smaller v1 scope, not a blocker.
- **G1(c) misclassification** (overflow mistaken for capability error) →
  tighten the regex/error-shape match in `isRichCapabilityError`/
  `isRichContentError` before shipping; this check exists specifically to
  catch that class of bug pre-ship — a false capability-latch from one
  oversized reply would incorrectly disable rich fleet-wide.
- **G1(d) adversarial-content check fails** (injected formatting/link
  renders live) → blocks ship outright; fix the inline-text escaping/
  representation before any further work, per security review F1.
- **G1(e) partial-block streaming proves unsafe** (malformed blocks sent,
  or the held-back-tail approach looks visibly glitchy) → fall back to
  hermes-agent's more conservative shape: stream plain throughout,
  upgrade to rich only at `finalize()`. This is a documented, deliberate
  downgrade path, not an unplanned one — the operator's preference for
  progressive streaming (§0's v3 note) is UX-driven, and a broken UX is
  worse than a simpler one; finalize-only remains fully specified (v2's
  original design) as the fallback shape.
- **G4 fails** (local server too old, when applicable) → latch rich off
  automatically for that bot connection; cloud-routed bots unaffected. No
  code change needed beyond the latch itself — this is what it's for.
- **G5 shows worse-than-expected breakage** (e.g. more clients affected
  than Web alone, an actual error DOES surface in some client/version
  combo, or a checkbox turns out interactive) → revise §0.1/§0.3 and the
  fallback design; any of these would be a significant, welcome surprise
  that should change the plan, not just get noted.

## 10. Invariants

- Rich text is **off by default** for every chat, always.
- The plain `toTelegramHtml` pipeline remains the source of truth for
  content whenever richtext is off, whenever the content gate says no, and
  on any content-error fallback — never a second, independently-maintained
  "plain version." **[v2]** This invariant is only trustworthy once the
  §0.7 `checkbox()` fix ships — track that as a hard dependency, not a
  parallel nice-to-have.
- **[v3, revised]** At most one markdown parse per outgoing message on the
  *plain* path. The rich path (typed blocks, decided §0.4) runs its own
  `marked.lexer()` call — a parallel parse, not shared with `format.js`
  (v1's "reuses the same parse" claim was wrong, corrected in §2). The
  **content-error fallback re-parses** (`projectRichBlocksToPlainMarkdown`
  → `toTelegramHtml`) — that double-parse on the fallback path is accepted
  as a fallback-only cost, not a violation of this invariant.
- **[v3, new]** Rich streaming edits emit only complete top-level blocks;
  an in-progress/incomplete block is held back rather than sent malformed
  (§2's streaming bullet, G1(e)).
- One system-prompt assembly path (`lib/sdk/build-options.js`) gets the
  rich-authoring hint, gated on the same `richText` flag the delivery
  layer checks — but **[v2]** the two reads happen at different times
  (spawn-time for the hint, send-time for delivery); "same flag" does not
  mean "simultaneously applied." See §2's opt-in and prompt-hint bullets.
- **[v2, security F3]** The `html`/`markdown` string fields of
  `InputRichMessage` are never populated directly from agent/model output.
  If a future contributor uses them (e.g. as the passthrough approach,
  should it win §13 Q1), model output must first pass through the
  existing `escapeHtml`-equivalent treatment `format.js` already applies
  to the HTML path — Telegram's server-side markdown parser is not itself
  a substitute for that, since the risk is agent-relayed *user* content
  being mis-interpreted as formatting/links, not Telegram mis-parsing
  well-formed markdown.
- **[v2, failure-modes L-equivalent]** `richText` resolves through the
  same `topic → chat → bot → default` precedence chain `maxFileBytes`
  uses (`lib/attachments.js`) — never read directly off `config.bot`,
  which is silently overwritten at boot by the per-bot alias
  (`config.bot = config.bots[name]`, the same footgun that orphaned
  `apiRoot` for weeks in 0.13.0).

  it can be quoted precisely rather than paraphrased; (d) if degradation
  turns out to reliably preserve checklist/text content on MOST outdated
  clients (not just this one build), reconsider whether the risk register
  entry "Telegram Web (or another client) silently drops rich content"
  (§8) is overstated for the non-Web case specifically, and whether the
  opt-in messaging/warning (or even the default-off posture itself) needs
  revisiting. Do not change the default posture based on one observation
  — this needs a real spread of clients/versions first.
- Once the above is characterized, revisit whether a one-time "heads up,
  rich text may not render on some clients" notice when `/richtext` is
  turned on (mentioned as a "consider" in §8's risk register) is still
  warranted, or can be scoped more precisely (e.g. "may look different on
  Telegram Web" instead of a generic warning).

## 15. Implementation-review corrections (v5)

The first implementation review found four correctness gaps. These are
limited corrections to the agreed design, not new feature scope.

1. **Delivery state must describe what Telegram accepted.** The streamer
   currently records payloads before Telegram accepts them. A later identical
   final payload can therefore be mistaken for already delivered after a
   failure. Commit rich or plain trackers only after success: a thrown edit
   leaves both trackers unchanged, while any successful plain delivery
   updates `currentText` and clears the rich tracker. Regression tests must
   cover failed rich and plain edits followed by successful final retries.
   Edits for a bubble must also be serialized so a slow older rich edit cannot
   land after a newer plain edit and invalidate the trackers; verify this with
   controlled promises that would otherwise resolve in reverse order. If a
   bubble is superseded while an edit is in flight, that edit may finish for
   the old Telegram message but must not commit state into the new bubble.
2. **The config card must display the effective rich-text value.** Delivery
   resolves `topic → chat → bot → default`, while the card currently inspects
   only topic/chat values. Compute the effective value with the existing
   resolver at both card call sites and pass that boolean into the pure UI
   builders. Keep their existing local-value behavior as a backwards-
   compatible default for direct callers. Tests must cover inherited `true`
   and an explicit effective override.
3. **Live configuration and the capability latch must affect the current
   turn.** Do not snapshot rich enablement when the streamer is created.
   Instead, let each rich-payload attempt re-read the resolver and latch.
   Keep a defensive latch check in the rich editor so a latched connection
   cannot issue another rich API request. Because a live toggle can now move
   a stream from rich back to plain, a successful plain edit must clear the
   stored rich payload and synchronize `currentText`; the same applies when a
   rich attempt resolves through the editor's plain fallback. Plain no-op
   checks are valid only when no rich payload is active. Tests must cover live
   rich→plain switching, rich success followed by `wentRich:false`, and a
   capability-latched edit that goes directly through the plain path. The
   `rich-streaming-upgrade` event represents each visible plain→rich
   transition, so a later off→on transition may emit it again.
4. **Every details block must contain a summary.** Telegram's
   `InputRichBlockDetails.summary` field is required. For source `<details>`
   without a non-empty `<summary>`, emit the stable fallback label
   `Details`. Dropping the entire rich rendering or rejecting otherwise
   useful content would be a larger user-visible degradation. Tests must
   cover both single-token and blank-line token-stream details shapes.
5. **Rich-text writes must match rich-text resolution in topics.** The generic
   model/effort write helper intentionally collapses non-isolated topics to the
   chat root because those settings belong to a shared process. Rich delivery
   is instead resolved per outgoing message and already honors topic overrides
   regardless of process isolation. Allow the rich-text callback to write its
   current topic even when `isolateTopics` is false; ignoring such overrides
   would contradict the agreed `topic → chat → bot → default` contract and the
   existing `maxFileBytes` precedent. Test a non-isolated topic whose inherited
   topic value is turned off.
6. **Every table cell must include alignment.** Telegram requires `align` and
   `valign` on `RichBlockTableCell`. Preserve Marked's horizontal alignment
   when it is `left`, `center`, or `right`, default missing alignment to
   `left`, and use `top` for vertical alignment. Unit tests and the live spike
   fixture must assert these fields so tables do not silently content-fallback.

Failure handling remains the same outside these corrections: content errors
fall back to plain, capability errors latch the connection, and transient
errors remain retryable. Verification is the focused rich/config suite plus
the full offline test suite; real-Telegram spikes are unnecessary because
the fixes concern local state transitions and a documented required field.
