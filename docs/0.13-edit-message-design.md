# 0.13 — `edit_message` bridge tool + `reply` returns `message_id` (design)

**Status:** retroactive design (implementation landed in `a6e14db`; this documents the
contract + closes the test/review gaps flagged by the operator 2026-06-09).
**Why retroactive:** the feature was built straight-to-TDD without a design doc — wrong call,
because it **changed the `reply` tool's return contract**, which is not trivial. This doc is
the spec it should have had; the follow-up commit adds the missing edge/failure tests, and a
reviewer pass runs after.

---

## Goal

Recover most of the "something is happening" feel on the CLI backend without token streaming
(impossible — claude-as-CLI never exposes its partial text). claude sends a short status,
then **edits that one bubble in place** as it works, ending with the answer. Plain language
only — never tool names (operator decision: raw tool activity is too technical for partner
chats).

## The two coupled changes

### 1. `reply` now returns `{ok, message_id}` (was the string `'sent'`)

The enabling change: for claude to edit a bubble it must know that bubble's `message_id`.
`reply` previously returned the opaque string `'sent'`. It now returns
`{"ok": true, "message_id": <id>}` (JSON, machine-readable in claude's context).

- The dispatcher surfaces the **first delivered bubble's** id from `deliverReplies().sent`
  (tolerates deliver.js's numeric `sent[]` and the `{message_id}` object shape). `null` for a
  solo sticker/reaction reply (no text bubble) or a files-only path.
- Carried daemon→bridge on the `tool_ack` (`message_id` field, `nullish`), then handed to
  claude as the tool result.

**Why the contract change is safe:** nothing in the codebase asserts `reply` returns `'sent'`
(grep-verified — the only `'sent'` matches are DB `status='sent'`, unrelated); the full suite
is green; claude reads the tool result as text and the system prompt explains the new shape.
A real-claude E2E confirms claude reads the id and uses it.

### 2. `edit_message` tool

`edit_message(chat_id, message_id, text)` edits a bubble previously sent via `reply`.

- **Single bubble, no chunking.** Length-guarded: text over `maxChunkLen` (4000) is rejected
  with a clear error telling claude to use `reply` for long content (an edit can't span msgs).
- **Same agent-text hygiene as reply:** `parseResponse` strips inline `[sticker:…]`/`[react:…]`
  markers, `sanitizeAssistantReply` intercepts canned strings — so neither leaks as literal
  text into the edited bubble. (No sticker/reaction *side effects* on an edit — text only.)
- **Formatting + no-op handling are free:** the `send` wrapper (`lib/telegram/api.js`) already
  lists `editMessageText` in `FORMATTABLE_METHODS` (auto markdown→HTML) and treats Telegram's
  "message is not modified" as a graceful no-op (`isMessageNotModifiedError`).

## Data flow

```
claude → reply(text)                 [bridge CallTool, fast tool_ack]
  → daemon _dispatchToolCall → toolDispatcher → deliverReplies → TG sendMessage
  → tool_ack {ok, message_id} → bridge → claude reads {ok, message_id:500}
claude → edit_message(message_id:500, text)
  → daemon _dispatchToolCall → toolDispatcher → TG editMessageText(500)
  → tool_ack {ok, message_id:500} → bridge → claude
```

## Security

- **chat_id is pinned to the session.** `_dispatchToolCall` rejects any tool call whose
  `args.chat_id !== this.chatId` BEFORE dispatch (`cli-process.js:1090`), edit_message included.
  claude cannot edit a bubble in another chat.
- **Telegram constraint:** `editMessageText` only edits messages the *bot itself* sent. The
  worst a prompt-injected claude can do is edit one of its own bot's prior messages in its own
  chat by guessing a `message_id` — low severity, no cross-chat or cross-user exposure.
- The `message_id` is not a capability/secret; it's a per-chat sequential Telegram id.

## Anti-hang

`edit_message` is a **fast tool_ack** path (like `reply`), NOT a blocking await (unlike `ask`,
which parks on `question_answer`). A failed edit returns `{ok:false, error}` → `tool_ack ok:false`
→ the bridge returns `isError` → claude sees the error and continues or retries. **No code path
blocks**, so a failed/slow edit cannot wedge a turn. (The bridge's 20-min ceiling is irrelevant
here — it only governs `ask`.)

## Rate limit & idempotency

- Edits share the per-session **5/s token bucket** (`toolRatePerSec`). Adequate for
  human-paced status (claude edits seconds apart); a burst past the bucket gets a clean NACK,
  not a wedge. (If progressive status ever needs a higher edit rate, raise the bucket — not in
  scope now.)
- **Idempotent:** a retried edit with the same `tool_call_id` re-ACKs without re-dispatching
  (`recentToolCallIds`, applies to all tools on success). An identical edit (same text) is a
  Telegram "not modified" no-op handled in the send wrapper. (The reply-only **content-hash**
  dedup does NOT apply to edits — distinct edits of the same text to different messages must
  go through.)
- **Re-ACKs replay the `message_id`** (reviewer Finding 2 fix): both re-ACK paths — the
  `tool_call_id` idempotency cache AND the reply **content-hash** dedup — now cache and replay
  the delivered `message_id`. Without this, a retried identical `reply` (e.g. after a slow ack
  → 30s bridge timeout → claude resends the same text with a new `tool_call_id` → content-dedup
  hit) re-ACKed with `message_id: null`, silently destroying claude's edit handle for exactly
  the slow-delivery case progressive status exists to cover. Pinned by
  `cli-process-dispatch.test.js` ("re-ACK preserves the message_id", both paths).

## Scope / non-goals

- **NOT token streaming** — impossible on the CLI protocol; this is the closest buildable
  substitute.
- **Plain-language status only** — the system prompt forbids tool-name narration (operator
  decision). No per-tool/subagent activity is surfaced.
- **`react` tool** stays deferred (inline `[react:…]` in reply text still works).
