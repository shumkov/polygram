# 0.12.0 — CliProcess driver plan

Status: draft. Pre-review. Worktree: `polygram-0.12.0`, branch `0.12.0-cli-driver` (off `0.11.0-channels` at `e288077`).

## Goal

Collapse the **tmux** and **channels** drivers into a single driver — `CliProcess` — that uses one mechanism per concern, with no overlapping responsibilities. After 0.12.0 polygram has **two** backends:

| Driver | Path | Billing | Use case |
|---|---|---|---|
| `SdkProcess` | `claude --output-format stream-json --input-format stream-json` (headless print) | API key, per-token | Programmatic per-token API integrations |
| `CliProcess` (new) | `claude` interactive TUI in tmux + channels MCP bridge + hooks `--settings` | Pro/Max subscription | Default production path |

The current 0.11.0 channels driver is the **architectural seed** — same lifecycle, same IO. CliProcess differs from it in one substantive way: **all runtime observability moves to hooks**; capture-pane drops to a narrow set of jobs (startup-gate, liveness heartbeat, mid-turn watchdog); JSONL tail is not introduced. Three layers, three responsibilities, three mechanisms.

### Success criteria

LoC removed is an input metric, not an outcome — by itself it doesn't justify the work. The refactor is justified by these **maintainer-facing outcomes**, which the 7-day soak (Phase 5) is expected to demonstrate against the 0.11.0-channels baseline:

| Outcome | Why it matters | Measured by |
|---|---|---|
| One driver = one mental model | Debugging IO bugs today requires knowing whether the chat is on tmux (JSONL+pane), channels (bridge+JSONL fallback), or SDK (typed stdout) — three independent failure modes. CliProcess collapses to one. | Time-to-localize on the next post-0.12 IO bug, vs. average time-to-localize across rc.29–rc.45 (whose findings docs already enumerate per-backend root causes). |
| JSONL parser scar tissue retired | `session-log-parser.js`'s message-id coalescing, empty-turn bug workaround, and 7–8 flaky tmux-process-jsonl tests vanish. The maintenance cost is observable in the rc.NN cycle frequency. | Count of rc.NN bumps fixing JSONL/pane parser issues in the 90 days post-0.12 vs. the 90 days pre-0.12. Target: 0 post, vs. ~4 pre (rc.37, 39, 43, 45 all had a JSONL/pane parser angle). |
| Hooks become the documented contract | Hooks are an Anthropic-published API with versioning discipline. JSONL is a reverse-engineered artifact format. After 0.12, polygram's observability surface is built on a contract rather than an artifact. | Any future "claude broke our parser on upgrade" incidents trace to hooks (where Anthropic owns the SLA) rather than to JSONL (where we owned the brittleness). |
| Subscription pricing preserved (no regression) | Cost is load-bearing for the install base. CliProcess inherits the channels subscription path; the refactor must not regress it. | Anthropic Console shows zero per-token spend on bots running `pm:'cli'` throughout the 7-day soak. |
| Approvals available at user choice | The deleted tmux pane-scrape approval path is replaced by the Q4 hook-driven path on CliProcess + SdkProcess's existing canUseTool. Operators don't lose approvals; they choose the billing path. | Smoke test: a chat with `permissionMode: 'default'` on CliProcess surfaces approval cards end-to-end (Phase 2 exit gate b). |

**Net code reduction (~5400 LoC delete)** is a *consequence* of consolidating to one mechanism per concern, not the goal. It's tracked in the [Diff size estimate](#diff-size-estimate) section because reviewers want to see the magnitude of the change — but it's not what the work is for.

## The factoring

Polygram needs exactly three things from a running claude:

| Concern | Mechanism | Why |
|---|---|---|
| **Lifecycle** | tmux | Only path to interactive TUI (= subscription billing). Survives daemon restart. Provides spawn/cwd/env, SIGINT via `C-c`, graceful exit via `/exit`, capture-pane for startup-gate. Not replaceable in 0.12.0. |
| **IO** | channels MCP bridge | Structured. `reply` tool forces claude to be explicit about user-visible text. XML-escape on inbound. File attachments first-class. Permission relay exists. |
| **Observability** | hooks (`--settings` ndjson) | Documented public API. Median 14ms latency (rc.42 measured). Has `tool_input`, `tool_response`, `duration_ms`, `agent_id`, `agent_type` first-class. Future-proof. |

Each concern owned by exactly one mechanism. Everything else gets deleted.

### Reaction model

CliProcess reuses the **same reaction surface SDK and tmux already have today** — no new random-cycling logic. The existing `lib/telegram/reactions.js` chains define the UX:

- **Tool running** → per-tool emoji (`📂` Read, `🔧` Bash, `✍` Write, `⚡` Web, etc. — defined in `reactions.js` `CODING`/`WEB`/`TOOL`/`WRITING` chains).
- **No tool, claude is thinking** → THINKING chain progresses through `🤔` (THINKING) → `🤨` (THINKING_DEEPER) → `🤓` (THINKING_DEEPEST) on time elapsed. This is the rc.32 progressive-deepening cascade already in production for SDK + tmux. CliProcess just hooks the same reactor up.
- **Switch from tool to thinking** → reactor transitions out of the per-tool emoji into THINKING; if the turn returns to tools, transitions back to per-tool emoji. Same flip-flop SDK does today.
- **STALL** → after the calibrated silence threshold across all signal sources (hooks, capture-pane heartbeat, bridge), reactor lands on `🥱`.

```
on UserPromptSubmit                  → reactor.setState(THINKING)
on PreToolUse, name='Agent'          → emit('subagent-start', {agentType}) + reactor.setState(SUBAGENT)
on PreToolUse, other tools           → reactor.setState(classify(name))   ← CODING/WEB/TOOL/WRITING
on PostToolUse                       → reactor.heartbeat()                ← resets cascade clock
on SubagentStop                      → reactor.heartbeat() + emit('subagent-done')
on Stop                              → reactor.setState(DONE) → emit('result')
on Notification                      → admin approval card (Phase 4.5, non-bypass modes only)

between hook events, while turn in flight:
  capture-pane "esc to interrupt" tick → reactor.heartbeat()
  no signal for the cascade timeout    → progressive deepening (🤔→🤨→🤓→🥱)

unknown tool name → reactor.setState(TOOL)  ← generic 🔧 fallback (defined in reactions.js)
```

The `SUBAGENT` reaction state is a new addition to `reactions.js` — pairs the Agent PreToolUse + SubagentStop into a distinct in-progress reaction (e.g., `🤖`). Replaces the rc.NN "subagent looks like any other tool" UX gap surfaced in review.

This means **zero UX divergence from the existing tmux/SDK backends.** No new random WORKING_POOL cycling, no new "heartbeat-only fallback" mode. The HeartbeatReactor that 0.11.0-channels introduced gets replaced by the rc.32 cascade for CliProcess — one reaction model across all drivers.

## Security posture (deliberate trade-off)

CliProcess defaults to `permissionMode: bypassPermissions` + `--dangerously-skip-permissions`. This is a **deliberate default**, not an oversight, and is overridable per-chat. Recorded here so future operators (and audits) see the threat model explicitly.

**What the default means:** every claude subprocess spawned by CliProcess with the default permission mode can run arbitrary `Bash`, `Read`, `Write`, `Edit`, `WebFetch`, and MCP tool calls without operator approval. This applies to all bots running `pm:'cli'` that don't override `permissionMode` in chat config, including partner-facing umi-assistant unless explicitly configured otherwise.

**Opt-in approvals are available:** chats that set `permissionMode` to `'default'`, `'acceptEdits'`, or `'plan'` get approval cards via Q4's hook `Notification` → admin card → tmux send-keys verdict path. See [Q4 resolution](#open-questions-resolved-here) for the mechanics and [R11](#risk-register) for the best-effort caveats.

**Threat model assumed (for the bypassPermissions default):**
- **Operator trust:** the operator (the person running polygram) trusts claude with the cwd they configured. polygram runs as the operator's user on macOS LaunchAgents — same trust scope as if the operator ran `claude` interactively in that cwd themselves.
- **Sender allowlist:** sender-allowlist gating (`lib/approvals/store.js`-driven sender checks) ensures only approved Telegram users can submit messages that become claude prompts. An attacker would need to compromise both the bot token AND an allowlisted Telegram user to inject prompts.
- **No untrusted users in the chat:** polygram's chat model assumes the chat members are operator-trusted partners, not the open internet. `requireMention` + `paired-users` config gates who can prompt the bot.

**What this is NOT:**
- This is NOT a posture for opening polygram to anonymous Telegram users.
- This is NOT acceptable for chats with untrusted members — those should configure `permissionMode: 'default'` to get approval gating.
- The previous tmux backend's pane-scrape approval gating (`lib/tmux/tui-tool-input.js`) is deleted with TmuxProcess in Phase 4. The replacement is the Q4 hook-driven path, NOT the SDK fallback — both CliProcess (any non-bypass mode) and SdkProcess offer approval gating in 0.12. Operators choose between them on cost-and-billing grounds, not on whether approvals exist.

**Roadmap:** the `Approvals v2` follow-on milestone replaces the send-keys verdict response (R11 race window) with the channels permission relay once Anthropic productionizes it. Detection path (hook `Notification`) is unchanged. Not blocking 0.12 — 0.12 ships working approvals via send-keys.

## Why "CliProcess"

Both 0.11 drivers spawn the same `claude` binary; the distinction is **what mode it runs in**:

- `SdkProcess` runs claude in **headless print mode** (`--output-format stream-json --input-format stream-json`) → API billing, structured stdout, no TUI.
- `CliProcess` runs claude as a **CLI** (interactive TUI) → subscription billing, structured IO via channels + hook events.

The name describes the runtime mode, not the implementation detail. "TmuxProcess" and "ChannelsProcess" both name implementation details; "CliProcess" names intent.

## What gets deleted

### Source files removed
- `lib/process/tmux-process.js` (~3300 LoC) — superseded by CliProcess. The brittle orchestrator that wired JSONL tail + pane scrape + hooks into a Process subclass. Every IO bug in 0.10–0.11 traced here.
- `lib/process/channels-process.js` (~1700 LoC) — renamed and reduced to CliProcess.
- `lib/tmux/tui-tool-input.js` — no pane-scrape tool-input parsing (hooks deliver structured `tool_input`). **This is the only pane-scrape approval input parser.** Pure brittle code, no reusable value.

### Source files KEPT as standalone utilities (split decision)

The split rule: **delete the brittle orchestrator + scrape parsers; keep the pure libraries that have standalone value beyond the deleted backend.**

- `lib/tmux/session-log-parser.js` — **KEEP** as a pure JSONL utility, **not** as part of any production driver. It's a pure function (`ndjson lines → typed events`) with no tmux dependency, useful for:
  - Ad-hoc debugging / analysis scripts (already used by Phase 0 spike scripts).
  - Future tooling that wants to read `~/.claude/projects/*.jsonl` files.
  - Recovery / forensics if CliProcess hits an unknown issue and you need to compare against claude's own session log.

  Action in Phase 4: **rename** to make its non-backend-specific nature clear (suggested: `lib/util/claude-session-jsonl.js`), update the file header to document its standalone-utility status (*"Not consumed by any production driver as of 0.12; preserved as a standalone utility — no tmux dependency."*). Tests stay too. Future code that re-tails JSONL (e.g., a debugging slash command or a "show me what claude has been doing" admin tool) can import it directly.

**Approvals infrastructure preserved for SdkProcess:** `lib/approvals/store.js`, `lib/approvals/ui.js`, and `lib/handlers/approvals.js` are NOT deleted — they are the SDK `canUseTool` callback infrastructure (token generation, row persistence, Telegram card builders) and remain in use by `SdkProcess`. Only the tmux-specific pane-scrape path (`lib/tmux/tui-tool-input.js` above) is removed. Phase 4 exit criteria must verify the SDK approval flow still functions end-to-end.

### Code paths retired
- All capture-pane usage for runtime state observation. Capture-pane keeps three narrow jobs (per Phase 3 reframing): startup-gate dialog dismissal, rc.45 liveness heartbeat, mid-turn dialog watchdog. After those, capture-pane has no other runtime role.
- The H3 idle-ceiling JSONL plumbing in CliProcess (the idle ceiling stays, fed by hook events only).
- `tools/scripts` referencing the JSONL paths via tmux-process imports (cleanup pass). Scripts that want JSONL parsing migrate to the kept utility from above.

### Tests removed
- `tests/tmux-process-jsonl*.test.js` lineages — no live JSONL tail in any production driver.
- The 7–8 pre-existing flaky tmux-process-jsonl tests cited in `0.11.0-channels-status.md` simply go away.
- `tests/session-log-parser*.test.js` — **KEPT** alongside the utility itself; cheap insurance the parser still works when future code uses it.

## What stays

- `tmux-runner.js` — spawn, capture-pane, send-keys, kill primitives. Used by CliProcess for tmux lifecycle and the three narrow capture-pane jobs (Phase 3).
- `startup-gate.js` (already extracted in rc.10) — used for dialog dismissal at spawn.
- `channels-bridge.mjs` + `channels-bridge-protocol.js` + `channels-bridge-server.js` — bridge unchanged.
- `channels-tool-dispatcher.js` — receives `reply` (+ later `react`/`edit_message`) calls.
- `hook-settings.js` + `polygram-hook-append.js` + `hook-event-tail.js` — moved from "tmux-only" into the CliProcess core path. Now load-bearing.
- `lib/telegram/reactions.js` — unchanged; the rc.32 progressive-deepening cascade (THINKING → THINKING_DEEPER → THINKING_DEEPEST → STALL) drives CliProcess the same way it drives SDK + tmux today. CliProcess just feeds it from hook events instead of JSONL.
- `lib/util/claude-session-jsonl.js` (renamed from `lib/tmux/session-log-parser.js` in Phase 4) — standalone JSONL parser utility. Not consumed by any production driver as of 0.12; preserved because it has standalone value beyond the deleted tmux backend.

### Reaction-reactor consolidation

The `heartbeat-reactor.js` introduced in 0.11.0-channels (random WORKING_POOL cycling) is **superseded by the rc.32 thinking-chain cascade** for CliProcess. Two options for the file itself:
- **Delete `heartbeat-reactor.js`** — clean. CliProcess doesn't use it; channels-only random cycling is gone.
- Or: keep the file unused with a deprecation note (lower-risk if any test still imports it).

Default: delete in Phase 4 alongside other channel-specific dead code. Tracked under Phase 4.4.

### Phase 4.5 — Permission-mode parity (last code phase, ~0.5d)

The bypassPermissions default works for shumorobot / shumabit / umi-assistant out of the box. This phase adds **opt-in support for non-bypass permission modes** so chats that explicitly configure `permissionMode: 'default'` / `'acceptEdits'` / `'plan'` get approval cards.

Sequenced AFTER deletion (Phase 4) and BEFORE soak (Phase 5) so the soak validates the full permission-mode matrix.

- **4.5.1** Wire hook `Notification` → admin approval card on `_handleHookEvent`'s `Notification` branch:
  - Parse the notification payload for tool name + input preview.
  - Call `makeCanUseTool(sessionKey)(toolName, toolInput)` — same upstream plumbing tmux/SDK already use (sender-allowlist check, admin card post, response wait).
  - On verdict: send `"1\n"` (approve) or `"2\n"` (deny) via `tmuxRunner.sendKeys(tmuxName, ...)`.
  - **Gating:** only run this path when chat config sets `permissionMode` to something other than `'bypassPermissions'`. Default chats (bypass) never reach this branch — Notification doesn't fire for them.
- **4.5.2** Sender-allowlist check uses the same path as the bridge `permission_request` handler — verdicts are bound to the session via existing `lib/approvals/store.js` token plumbing.
- **4.5.3** Add R12 mitigation: at boot, if a chat's config dropped from `pm:'tmux'` → `pm:'cli'` (alias) without setting `permissionMode`, emit a per-chat warning naming the change in approval behavior.

Exit gate: on a chat with `permissionMode: 'default'`, claude attempting a gated tool surfaces a Telegram admin card with [Approve]/[Deny] buttons, and clicking through delivers the verdict back to claude. R12 warning fires for chats that previously had implicit approvals via tmux pane-scrape and didn't migrate `permissionMode`.

### Phase 3 — Capture-pane reduction (~1d)

**Reframed (review):** "Retirement" is too strong. Capture-pane keeps three narrow jobs after Phase 3, all justified empirically. The goal is **eliminate capture-pane for state observation**, not eliminate capture-pane entirely. Even with the three retained jobs, this is a ~90% reduction in capture-pane usage vs today's tmux backend.

- **3.1** Audit `tmux-runner.js` — every `capturePane` call. Classify each:
  - **STATE-OBSERVATION** (delete): runtime tool detection, JSONL fallback, tool-call parsing. Hooks supply these now.
  - **STARTUP-GATE** (keep): trust prompt dismissal, dev-channels WARNING dismissal, rc.43 session-age `/compact` menu. Runs once at spawn, then never again for that session.
  - **LIVENESS-HEARTBEAT** (keep, narrow): rc.45 "esc to interrupt" indicator polling. ONLY feeds `HeartbeatReactor.heartbeat()` — does NOT drive any tool detection or state machine. See 3.2 for rationale.
  - **MID-TURN-WATCHDOG** (keep narrow, see 3.3 / Q1): unknown-prompt detection on a 5s cadence.
- **3.2** Keep the `rc.45` "esc to interrupt" heartbeat — DO NOT retire. Originally this plan retired it; review flagged that hooks fire only at UserPromptSubmit/Stop, with NO interim signal during pure-thinking turns. Production thinking turns exceed 45s regularly; without this heartbeat, the STALL detector (`🥱` at 45s) fires false-positives. The "esc to interrupt" regex match is ~5 LoC and was empirically validated in rc.45. Mark the code path with a `// TODO(0.13): polish heartbeat strategy` comment so we can revisit after soak data shows real thinking-turn duration distribution. Future replacement candidates: a richer hook event from Anthropic, or a periodic ping from a long-lived hook process.
- **3.3** Mid-turn dialog watchdog (`rc.10` F#17) — keep narrow, capture-pane-based at 5s cadence. **Q1 resolution (review):**
  - **Detection catalog:** the F#17 catalog enumerates the known prompts the watchdog matches — currently the rc.43/44 session-age `/compact` menu pattern. New prompts get added to the catalog explicitly with a named test, not via permissive regex.
  - **Unknown-prompt UX:** when capture-pane sees text that *looks* like an interactive prompt but doesn't match any catalog entry, polygram posts an **admin card** to the approvals chat showing: (a) the pane-text excerpt (last ~10 lines), (b) buttons `[Dismiss with Enter]` / `[Send /exit]` / `[Send custom keys]`. Operator can respond directly from Telegram without SSH. The `[Send custom keys]` button opens a follow-up text input.
  - **Heuristic for "looks like a prompt":** lines ending with `?`, `(y/N)`, `Yes/No`, `❯`, or numeric option markers (`1.`/`2.`). Conservative — false positives surface as admin cards the operator dismisses, false negatives surface as the existing idle-ceiling timeout. We tune from soak data.

Exit gate: greppable confirmation that capture-pane runs ONLY in startup-gate paths, liveness-heartbeat, and the mid-turn watchdog after `emit('init')`. State-observation capture-pane is gone.

## Open questions resolved here

- **Driver name** — `CliProcess`. Rationale in [Why "CliProcess"](#why-cliprocess) above.
- **Branch name** — `0.12.0-cli-driver`. Worktree at `polygram-0.12.0`.
- **Parent branch** — `0.11.0-channels` (carries all the channels + hook plumbing). Not `main`, since main lags behind.
- **JSONL tail in CliProcess** — NO. Hooks for liveness, channels reply tool for content. JSONL stays for SdkProcess content extraction only (and SdkProcess doesn't actually read JSONL — see `0.11.0-channels-driver-plan.md` for why; the SDK reads stdout stream-json).
- **Q2 — Default `pm` value** — Auto-detect at boot. `SdkProcess` when `ANTHROPIC_API_KEY` is set; `CliProcess` when Pro/Max subscription auth is detected. Resolves the "new install cost story" without forcing one path on users.
- **Q5 — Migration messaging** — Aliases `'channels'` and `'tmux'` remain silent aliases for `'cli'` throughout 0.12. Alias removal deferred to a post-soak release (0.13 or later, not in 0.12). Factory warns **once at boot** when an alias is in use (not per-spawn — see Phase 4.5). The "once at boot, not per spawn" detail is a deliberate UX choice: per-spawn warnings would flood logs on a multi-chat deploy; once-at-boot surfaces the migration nudge without log noise.
- **Q1 — Mid-turn dialog watchdog** — Keep narrow capture-pane at 5s cadence. Detection catalog explicit (F#17 + named entries). Unknown-prompt UX is an admin card with pane-text excerpt + `[Dismiss with Enter]` / `[Send /exit]` / `[Send custom keys]` buttons. Detail in [Phase 3.3](#phase-3--capture-pane-reduction-1d).
- **Q3 — TmuxProcess as no-subscription backend** — Default no, delete in Phase 4 as planned. Install base is internal/personal use (sole maintainer + 3 partner bots) — no untapped no-subscription users to preserve a path for. If Phase 0.5's R2 verdict surprises us with medium/high probability of dev-flag removal, the deletion gate (Phase 4) revisits keeping TmuxProcess as a kill-switch; otherwise close Q3 cleanly.
- **Inline reactions / stickers in 0.12** — Already work via the existing `parseResponse` hook in `channels-tool-dispatcher.js`: claude includes `[react:🔥]` or `[sticker:NAME]` inline in `reply` tool text, polygram converts at delivery time. CliProcess inherits this — no new code needed. Standalone `react`/`edit_message` MCP tools (richer first-class API) remain a follow-on milestone for 0.13.
- **Q4 — Hook `Notification` → approvals routing** — Wire it, mode-aware:
  - Chats with `permissionMode: 'bypassPermissions'` (the default) — no approval cards. Claude runs everything. Documented in [Security posture](#security-posture-deliberate-trade-off).
  - Chats with non-bypass `permissionMode` (`'default'`, `'acceptEdits'`, `'plan'`) — hook `Notification` event fires when claude wants permission. Polygram posts admin approval card. Operator clicks [Approve] / [Deny]. Polygram sends the verdict back via narrow `tmux send-keys` (`"1\n"` for approve, `"2\n"` for deny).
  - The send-keys response path is **narrow** — used only in response to a hook-detected permission event, not for navigating unknown TUI states. send-keys remains a tmuxRunner primitive (already preserved for SIGINT). This is NOT the brittle pane-scraping we're retiring.
  - Best-effort caveat: the window between hook fire (~14ms) and operator click (seconds-to-minutes) means TUI state could in principle change. In practice claude is waiting for input → TUI is stable. Tracked as a P2 risk (see [R11](#risk-register)).
  - Approvals v2 (post-Anthropic-allowlist) replaces the send-keys response with the channels permission relay once Anthropic ships a stable version.

## Acceptance criteria for the 0.12.0 tag

1. Two drivers in `lib/process/`: `sdk-process.js`, `cli-process.js`. No `tmux-process.js`. No `channels-process.js`.
2. `npm test` green (all suites, no skips that weren't skipped on 0.11.0).
3. Contract suite passes for `['sdk', 'cli']`.
4. Per-tool reactions visible on a CliProcess chat (smoke test).
5. Subscription billing (no Console-tab API spend on bots running `pm:'cli'`) — verified via Anthropic Console.
6. 7d soak on shumorobot + 24h on shumabit + umi-assistant, no STALL false-positives, no missed replies.
7. **SDK approval flow still functions end-to-end** — sanity test verifies `lib/approvals/store.js` + `lib/approvals/ui.js` + `lib/handlers/approvals.js` are untouched and SDK `canUseTool` callbacks still post admin cards (regression guard for the "what gets deleted" scope ambiguity).
8. **Streaming reply cadence is unchanged from 0.11.0-channels** — channels mode already only streams at reply-tool boundary (not per assistant step). Smoke test confirms reply edits land on Telegram at the same cadence post-migration. No regression on streamMinChars / streamThrottleMs behavior.
9. **Each new failure mode has a distinct human-readable user-facing message + recovery hint.** Technical detail goes to logs (events DB + `~/polygram/logs/<bot>.log`); Telegram users see plain-language guidance. Match the existing "contextual error replies" standard the README documents.

   | Failure mode | What broke | User-facing Telegram message |
   |---|---|---|
   | Hook ndjson writer crashes | Per-event helper subprocess failed open or write (disk full, permissions) | "Something went wrong with my activity log and I lost track of this turn. Try sending the message again — I'll start fresh." |
   | Bridge socket dies after spawn | Bridge subprocess crashed mid-turn; daemon detects via `bridge-disconnected` event | "I lost connection to claude mid-thought. Restarting now — please resend your last message." |
   | Orphan turn (no Stop, no reply) | Turn fires neither `Stop` hook nor a `reply` tool call; idle ceiling triggers | "Claude finished but didn't send a reply — that's usually a transient glitch. Try asking the same thing again, or rephrase if it keeps happening." |

   Each message also includes a one-line technical hint suffix when the chat config has `verboseErrors: true` (default false). Acceptance test: trigger each failure mode in a smoke harness, verify the named Telegram message is delivered.

## Out of scope for 0.12.0 / Future follow-on milestones

Deliberately deferred. Each carries its own justification for why now is the wrong time:

- **`react` / `edit_message` bridge tools** — deferred from 0.11 follow-on phase. User-visible value (richer Telegram UX), but independent of the driver consolidation. Should ship as a 0.13 standalone bump.
- **`ask_user_question` bridge tool** — new follow-on opportunity surfaced in review. Today claude proactively asks the operator clarifying questions via the `reply` tool with plain text ("do you want A or B?"). A richer model: add an `ask_user_question` MCP tool that the bridge renders as a Telegram **inline keyboard**; operator's button click flows back as the structured next-turn input. Distinct from approvals (which gate tool calls). Should ship alongside `react`/`edit_message` in 0.13.
- **Approvals v2 (response-path upgrade)** — replace the `send-keys` permission-verdict response (Q4 resolution in 0.12) with the channels permission relay once Anthropic ships a stable version. The current channels relay is experimental and doesn't fire for regular MCP tool calls (rc.9). When the relay productionizes, swap the response path. Detection path (hook `Notification`) stays the same. Eliminates the R11 send-keys race window. 0.12 already delivers working approvals for chats with non-bypass `permissionMode` — Approvals v2 is a robustness upgrade, not a feature gap.
- **TmuxProcess preservation as a third backend** (Q3 above — default no). Recoverable from git history if R2 forces a fallback.
- **Removing the `--dangerously-load-development-channels` flag** — needs Anthropic allowlist. R2 in the risk register tracks this.
- **Telegram-side UX changes** — progress text in reply bubbles, multi-emoji status, per-tool-call live notifications. Worth doing once the foundation is stable, not bundled with the refactor.
- **Multi-bot horizontal scale-out** — still single-host-only; not on the roadmap.
- **Cross-backend session migration tooling** — moving an existing `pm:'sdk'` chat to `pm:'cli'` mid-session. Not needed for fresh installs; existing chats can stay on their current backend and migrate on session-reset.
