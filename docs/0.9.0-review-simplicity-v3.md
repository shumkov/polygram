## ❗ Still open / new findings (severity-ranked)

### 1. CRITICAL — `lib/handlers/approvals.js` ignores `lib/approvals/waiters.js` (204 LOC dead code + duplication)

`lib/approvals/waiters.js` (204 LOC, 200-waiter cap, 5 cleanup paths, full test suite at `tests/approval-waiters.test.js`) was written specifically to be the structured replacement for the inline `approvalWaiters Map`. Its own header even says so (line 9: *"as of 0.9.0 commit 12, polygram.js still uses an inline `Map` for this purpose; this factory is the structured-replacement target for the polygram.js extraction (Phase B commit 19)"*).

Phase D shipped `lib/handlers/approvals.js` (commit 29) and **re-implemented the inline Map from scratch** (lines 58–79: `dropWaiter` + `resolveApprovalWaiter`) instead of consuming the structured factory. Result:

- `lib/approvals/waiters.js`: 204 LOC, currently called by **zero** production code (`grep -rn createApprovalWaiters lib/ polygram.js` → only its own definition + test).
- `lib/handlers/approvals.js`: re-rolls the same Map without the 200-waiter cap, without the typed `code:'CAPACITY'` / `code:'TIMEOUT'` errors, without the `rejectAllForSession` path, without timeout sweeping (it has its own setTimeout-per-call inside `makeCanUseTool` — different mechanism, same bug surface).

**Action**: either delete `lib/approvals/waiters.js` + its test (it's an unused alternative implementation), OR rewrite `lib/handlers/approvals.js` to consume it. Picking — and shipping — exactly one is the only way to honor the simplicity cost. Right now we pay for both.

**Estimated LOC delta**:
- Delete `lib/approvals/waiters.js` + `tests/approval-waiters.test.js` → −204 LOC + ~250 test LOC = **−454 LOC** if `lib/handlers/approvals.js` is the canonical version.
- Or refactor `lib/handlers/approvals.js` to delegate → ~−40 LOC inside the handler + tests still cover the 5-path matrix from one place.

Recommend the **delete** path (simpler-now > theoretically-better-architected): `lib/handlers/approvals.js` is in production, has tests via integration, and the extra capacity cap from `waiters.js` solves a problem polygram doesn't have at scale today.

### 2. HIGH — 9 `let X = null` placeholders are still there

v2 flagged this; commit 27 didn't touch it. Confirmed in tree:

```

1079: let startApprovalSweeper = null;
```

The factory placeholders (449, 453, 522, 560, 1076–1079) are in tension with one another: they require module-scope mutation because top-level functions like `dispatchHandleMessage` (line 777), `handleMessage` (1102), and `dispatchRegularMessage` (2076) close over them by name BEFORE `main()` runs. Hoisting `require()` + `createX(deps)` calls into `main()` scope (v2's suggestion) is doable but requires either:

- **Option A (small)**: keep the placeholders, document them with one collective comment block at the top instead of 8 scattered ones. Cost: ~6 lines saved, zero behavior change. Ships in ~5 minutes.
- **Option B (medium)**: convert `handleMessage` + `dispatchRegularMessage` into closures created inside `main()`. They'd close over locals instead of module-scope `let`s. Costs ~2 hours of indentation churn and complicates stack traces.

**Recommendation**: don't pursue Option B at this point. The temporal coupling here is real (factories need runtime `config`, `BOT_NAME`, `db`, `pm` which only exist after main() boot) and the placeholders are honest about it. Move `transcribeVoiceAttachments` / `downloadAttachments` / etc. **closer** to the handlers that call them (i.e., delete the placeholder declarations at line 449/453/560/1076–79 and just assign them as `const` inside main() — but that requires inlining the call sites that reference them, which crosses function boundaries). Net: not worth it.

**Verdict**: signal accepted; the temporal coupling is acceptable. Document it once at top (`// Module-scope handlers wired in main() — see L2536+ for factory calls`) and stop apologizing per-line.

### 3. HIGH — Duplicate logger boilerplate across 7 factories

v2 said "logger fallback footgun: `logger = console` default + `logger.error?.()` optional chaining coexist in every factory." Confirmed still present. The audit:

| File | `logger = console` default | `logger.error?.` calls | `logger.log?.` calls |
| --- | --- | --- | --- |
| `lib/handlers/abort.js` | yes (L36) | 2 | 0 |
| `lib/handlers/approvals.js` | yes (L55) | 6 | 0 |
| `lib/handlers/config-callback.js` | yes (L33) | 1 | 0 |
| `lib/handlers/download.js` | yes (L41) | 4 | 3 |
| `lib/handlers/slash-commands.js` | yes (L45) | 5 | 0 |
| `lib/handlers/voice.js` | yes (L30) | 3 | 1 |
| `lib/sdk/callbacks.js` | yes (L38) | 6 | 1 |

`logger = console` means the default `logger.error` IS defined (it's `console.error`). So `logger.error?.(...)` optional chaining is dead code — it can never short-circuit. Either:

- **Pick one**: drop the `?.` everywhere (`logger.error(...)` is fine because the default is non-null). Saves ~30 character-tokens per call but no LOC.
- **Or**: drop the `console` default and require callers to inject. Then `?.` is justified. Forces callers to be explicit.

Lowest-friction fix: `replace_all` of `logger.error?.(` → `logger.error(` and `logger.log?.(` → `logger.log(` across `lib/handlers/*.js` + `lib/sdk/*.js`. ~30 sites, zero behavior change because the default is `console` which has both methods. Mechanical, ships in 2 minutes.

`lib/handlers/autosteer.js` is the right model: no logger param, no fallback, no optional chains, doesn't need them. Other handlers should follow.

**Estimated remaining cleanup**: ~30 LOC from #3 and #6, ~250–450 LOC from #1 (depending on which way you resolve it). Everything else is noise.

The simplicity-first move is to *stop extracting* once the test boundary is clean, which it now is.
