# 0.9.0 cleanup — simplicity review v2

**Branch:** `0.9.0-cleanup`
**Diff scope:** `5d9f88e..HEAD` (Phase A reorg + 5 Phase B handler extractions)
**v1 baseline:** `docs/0.9.0-review-simplicity.md`

## Scope of v2 review

Re-evaluate over-engineering / YAGNI risks introduced by:

- **Phase A (commits 13–17):** flat `lib/*.js` → 7 nested subdirs. 41 files moved + renamed.
- **Phase B (commits 18–23):** 5 handler/factory modules extracted from `polygram.js` (3978 → 3592 LOC). Pattern: `createX({deps}) → fn`, wired in `main()` against module-level `let X = null` placeholders.

Total addition this branch: **+933 LOC of new lib files** in exchange for **−386 LOC from polygram.js** — i.e. a net +547 LOC for the codebase, minus ~100 LOC of new tests. The shape change is real (handlers now isolated + nominally testable), but the cost is also real and worth interrogating.

## Severity-ranked findings

### HIGH — `let X = null` module-level placeholders are temporal-coupling debt (concern #2)

**Files:** `polygram.js:445`, `polygram.js:449`, `polygram.js:556`, `polygram.js:1379`, `polygram.js:1381`

5 module-level `let` variables sit in dead `null` state from `require()` time until `main()` runs — including `transcribeVoiceAttachments`, `downloadAttachments`, `buildSdkOptions`, `handleConfigCallback`, `handleAbortIfRequested`. Plus `pm` (line 518) makes 6.

```js
// polygram.js:443-449
// transcribeVoiceAttachments extracted to lib/handlers/voice.js.
// Wired in main() once db + tg + config are available.
let transcribeVoiceAttachments = null;

// downloadAttachments extracted to lib/handlers/download.js. Wired
// in main() once config + db + dbWrite + INBOX_DIR are available.
let downloadAttachments = null;
```

Why it's a smell:

- **Implicit boot-order dependency.** Any function that calls `transcribeVoiceAttachments` (e.g. `handleMessage` at line 1893) will throw `TypeError: transcribeVoiceAttachments is not a function` if the call happens before `main()`'s wiring at line 3233. Today this is OK because `bot.on()` doesn't fire pre-`main()` — but it's a load-bearing assumption with no test.
- **Sharded comprehension.** Five separate `let X = null` placeholders + five matching `// extracted to lib/...` comment blocks fragment polygram.js. Each adds 3 lines of "this is going to be wired later, trust me" mental tax on every read.
- **Code climbing the import graph.** `polygram.js` requires 6 factory creators at the top of the file — even though it only actually instantiates them inside `main()`. Better: only require what's used at module scope; defer factory `require()` and instantiation into `main()` so the names are local-scoped.

**Recommendation:** Inline the `require()` + `createX()` calls into `main()` and bind the resulting handlers to local variables passed downstream. Functions in polygram.js that need the handlers should be converted to closures created inside `main()`, OR receive handlers as parameters. This eliminates the temporal-coupling smell at the cost of restructuring polygram.js's body — but that restructuring is the *real* simplification work Phase B was supposed to do.

A lighter alternative: bundle the 5 placeholders into a single object so reads + assignments are colocated:

```js
const handlers = {
  transcribeVoiceAttachments: null,
  downloadAttachments: null,
  buildSdkOptions: null,
  handleConfigCallback: null,
  handleAbortIfRequested: null,
};
// in main():
Object.assign(handlers, {
  transcribeVoiceAttachments: createTranscribeVoiceAttachments({...}),
  ...
});
// at call site:
await handlers.transcribeVoiceAttachments(downloaded, {...});
```

Cost: ~5 lines of module-level boilerplate gone, single touchpoint. Worth doing if the bigger restructure isn't.

**Estimated LOC savings:** 15–20 (kill the 5 explanatory comment blocks + the 5 `let` lines).

### HIGH — Dep-validation boilerplate is paranoid noise (concern #3)

**Files:** all 6 factories total **47 `throw new TypeError` lines**.

Distribution:
- `lib/sdk/callbacks.js`: 13
- `lib/handlers/voice.js`: 8
- `lib/handlers/abort.js`: 8
- `lib/handlers/config-callback.js`: 8
- `lib/handlers/download.js`: 5
- `lib/sdk/build-options.js`: 4
- `lib/sdk/router.js`: 1

```js
// lib/sdk/callbacks.js:40-52 — typical pattern
if (!db) throw new TypeError('db required');
if (typeof dbWrite !== 'function') throw new TypeError('dbWrite required');
if (!config) throw new TypeError('config required');
if (!botName) throw new TypeError('botName required');
if (typeof tg !== 'function') throw new TypeError('tg required');
if (typeof logEvent !== 'function') throw new TypeError('logEvent required');
if (typeof classifyToolName !== 'function') throw new TypeError('classifyToolName required');
if (typeof announce !== 'function') throw new TypeError('announce required');
if (typeof shouldAnnounce !== 'function') throw new TypeError('shouldAnnounce required');
if (!(contextHintShown instanceof Set)) throw new TypeError('contextHintShown (Set) required');
if (typeof extractAssistantText !== 'function') throw new TypeError('extractAssistantText required');
if (typeof getChatIdFromKey !== 'function') throw new TypeError('getChatIdFromKey required');
if (typeof getThreadIdFromKey !== 'function') throw new TypeError('getThreadIdFromKey required');
```

Why it's overkill:

1. **There is exactly one production call site** for each factory (in `main()`). It wires every dep. Tests are the only callers that exercise the missing-dep branches, and each `throws when X missing` test exists *only because the throw exists* — circular justification.
2. **Node's natural failure mode is no worse.** If you forget to pass `db`, the very next call into the returned function does `db.upsertSession(...)` and throws `Cannot read properties of undefined (reading 'upsertSession')` with a full stack. The custom `TypeError('db required')` message replaces a perfectly informative native error with a slightly nicer one — at the cost of N lines of boilerplate per module.
3. **Validation happens at boot, not at use.** A typo in one of the 47 typeof checks (e.g. `if (!log_event)` instead of `if (!logEvent)`) is itself an undetected bug. The validations have no tests catching their own correctness — they're trusted.
4. **It's not consistent.** `build-options.js` only validates 4 of its ~7 deps. Some deps are silently optional. The set of "required" deps is determined by what the factory author felt like writing that day, not by any analysis.

**Recommendation:** Delete all 47 dep-validation lines. Trust Node's natural failure mode. If a particular dep needs *runtime semantic* validation (e.g. "must be a Set, not just any object"), keep just that one — the `contextHintShown` Set check in callbacks.js:49 is the only one that catches a real mistake (passing a Map or Object).

If wholesale deletion is too aggressive, replace 47 lines with one helper:

```js
// lib/_assert-deps.js
function requireDeps(deps, names) {
  for (const n of names) if (deps[n] == null) throw new TypeError(`${n} required`);
}
```

Then each factory becomes a single `requireDeps(deps, ['config', 'db', 'tg', ...])` line. Drops ~40 LOC, keeps the boot-time validation.

**Estimated LOC savings:** 47 lines if deleted, ~40 if consolidated.

**Tests to delete alongside:** every `test('throws when X missing', ...)` in `tests/build-options.test.js` (~5 tests), plus matching ones in `sdk-callbacks.test.js`. ~20–30 LOC of test code that exists purely to validate the validation.

### HIGH — Three of four handler extractions added zero unit tests (concern #6)

**Files:** `lib/handlers/voice.js`, `lib/handlers/download.js`, `lib/handlers/config-callback.js`, `lib/handlers/abort.js`.

Of the 4 handler extractions in commits 20–23:

| File | Factory tests | Pre-existing tests touching it |
|---|---|---|
| `lib/handlers/voice.js` | **0 (no test file)** | `tests/voice.test.js` covers the underlying `transcribeVoice` only |
| `lib/handlers/download.js` | **0 (no test file)** | none |
| `lib/handlers/config-callback.js` | **0 (no test file)** | none |
| `lib/handlers/abort.js` | **0 (no test file)** | `tests/abort-detector.test.js` covers `isAbortRequest` predicate only |

Compare: `lib/sdk/build-options.js` (25 tests) and `lib/sdk/callbacks.js` (22 tests) DO have dedicated test files.

This is the worst of both worlds:

- The factory pattern's main argument ("now testable in isolation") is unrealised.
- The caller (`polygram.js`) is now LESS testable than before, because handler bodies are no longer in scope for the integration-style tests that *did* cover them.
- The dep-validation `TypeError`s at the top of each factory exist with NOTHING calling them in CI — pure dead code.

**Recommendation:** Either write the unit tests (12–15 each, 50ish total), OR delete 75% of the dep-validation boilerplate (those throws will literally never fire in production, and there's no test to even prove they fire correctly). Probably do both.

In practice the higher-leverage fix is the dep-validation deletion above — that removes the dead code without forcing 50 new tests. Then add tests later, focused on real branches (e.g. voice's `ackEmitted` short-circuit, download's three-layer size enforcement, config-callback's `oldValue === value` no-op, abort's bilingual ack).

### MEDIUM — `lib/sdk/router.js` is still pure ceremony (carryover from v1)

**File:** `lib/sdk/router.js` (40 lines including header doc).

```js
function createPmRouter({ pm } = {}) {
  if (!pm) throw new TypeError('pm required');
  return pm;
}
```

v1 flagged this; v2 keeps it. The router renamed to `lib/sdk/router.js`, the test renamed to `tests/pm-router.test.js`, but the function body is still **identity passthrough**. Test asserts:

```js
// tests/pm-router.test.js:22
assert.strictEqual(router, pm,
  'wrapper currently returns the underlying pm — extension point preserved');
```

A test asserting `f(x) === x`. That's the definition of a no-op.

**Recommendation:** Delete `lib/sdk/router.js`, delete `tests/pm-router.test.js`, replace `polygram.js:3252` `pm = createPmRouter({ pm: sdkPm })` with `pm = sdkPm`. **−45 LOC, −1 require, −1 test file.**

If the abstract "future alternate pm impl" arrives (a `pi-agent-core` adapter, etc.), THAT future PR can introduce the routing layer. Today, the layer ships nothing it doesn't already have without itself.

This applies double now that v2 also kept `lib/pm-interface.js` (97 lines of JSDoc-only typedef). The interface IS useful for the test fake — keep it. But the interface and the router are independent concerns; you don't need an `identity` impl as proof-of-concept.

### MEDIUM — `logger = console` default + `logger.error?.()` is a footgun (concern #5)

**Files:** all 6 factories.

Every factory takes `logger = console`, then uses `logger.error?.()` and `logger.log?.()`. The `?.` is a footgun:

- If a caller passes `logger: customLogger` and `customLogger` lacks `.error`, errors silently disappear. Optional chaining gates the call instead of letting Node throw `customLogger.error is not a function`.
- The default `logger = console` always has `.error` and `.log`, so `?.` is dead syntax in the production path.
- The combination "default to a logger that has all methods + use optional chaining everywhere" is incoherent: either the logger always has methods (use unconditional calls) or it sometimes doesn't (the default is wrong).

The handler factories with `logger.error?.()` calls (download.js:147, voice.js:84, abort.js:66, abort.js:91, callbacks.js:152, callbacks.js:161, config-callback.js:112, build-options.js:93) ALL silently swallow legitimate error reporting if a caller passes a non-conforming logger.

**Recommendation:** Pick one:

- **A (preferred):** Drop the `?.` everywhere. If a caller passes a partial logger, fail loudly. `logger.error()` and `logger.log()` unconditional. Default `= console` ensures production never breaks.
- **B:** Drop the default. Make logger required. Fail-fast at factory call time if missing.

A is less typing and matches the "I'm always going to pass a logger" reality. ~16 `?.` removals across 6 files.

### MEDIUM — `lib/db/index.js` fights Node's auto-resolution (concern #4)

**File:** `lib/db/index.js`, all 7 callers.

The file lives at `lib/db/index.js`. Node would auto-resolve `require('./lib/db')` → `./lib/db/index.js`. But:

```bash
$ grep -rn "require.*lib/db" polygram.js lib scripts tests
polygram.js:24:                       require('./lib/db/index')
scripts/split-db.js:22:                require('../lib/db/index')
tests/sessions.test.js:12:             require('../lib/db/index')
tests/chat-tool-decisions.test.js:17:  require('../lib/db/index')
tests/db.test.js:10:                   require('../lib/db/index')
tests/split-db.test.js:12:             require('../lib/db/index')
tests/helpers/db-fixture.js:27:        require('../../lib/db')           ← only one using auto-resolve
tests/history-preload.test.js:15:      require('../lib/db/index')
```

7 of 8 callers explicitly include `/index`. One uses auto-resolve. Inconsistency = bikeshedding waiting to happen.

More importantly: `lib/db/` has 7 sub-files (auto-resume, inbox, index, pairings, replay-window, sent-cache, sessions) — but `index.js` doesn't re-export ANY of them. It's just `lib/db.js` renamed. Callers that need `lib/db/sessions` import it directly, NOT through `lib/db`.

So `lib/db/index.js` is misleadingly named. It's not an index. It's a sibling.

**Recommendation:** Two options, both improve clarity:

1. **Flatten** `lib/db/index.js` back to `lib/db.js`. Keep the rest of `lib/db/` (sessions, pairings, etc.) as the subdir. Callers do `require('./lib/db')` for the bridge, `require('./lib/db/sessions')` for utilities. Crisp distinction.
2. **Make it a real index** — re-export the sub-files via `lib/db/index.js`'s exports so callers can `const { open, sessions, pairings } = require('./lib/db')`. Bigger refactor, more consistent API, also helps future tree-shaking.

Option 1 is faster and matches what the file actually is. ~7 import sites get shorter.

Same critique applies to `lib/telegram/api.js` (everyone imports `'./lib/telegram/api'` directly; there's no `lib/telegram/index.js` aggregating). At least `lib/telegram/` is consistently NOT-an-index, which is fine. The mistake is specifically the `lib/db/index.js` filename.

### LOW — Factory pattern is overkill for at least 2 of 6 modules (concern #1)

**Files:** `lib/sdk/router.js` (already covered), `lib/sdk/build-options.js`.

`build-options.js` has 7 deps closure-baked at boot. One call site (`pm-sdk constructor`). The factory-vs-direct-args trade:

- Factory: `createX({deps})` → returns `fn(args)`. Closure cost. 47 dep-validation lines included.
- Direct: `buildSdkOptions(deps, args)`. No closure, no validation, caller passes deps explicitly per-call. Same testability — pass test deps in arg position instead of factory position.

For modules with N call sites, factory wins (DRY). For modules with 1 call site, factory is pure ceremony — there's no wiring to deduplicate.

Of the 6 factories:

| Module | Call sites in polygram.js | Factory worth it? |
|---|---|---|
| `build-options.js` | 1 (line 3251 via `spawnFn`) | **No** — could be `buildSdkOptions(sessionKey, ctx, deps)` |
| `callbacks.js` | 1 (line 3217 via `...sdkCallbacks`) | **No** — could be `getSdkCallbacks(deps)` returning the object directly without closure |
| `voice.js` | 1 (line 1893) | **No** — same |
| `download.js` | 1 (line 1861) | **No** — same |
| `config-callback.js` | 1 (line 2906) | **No** — same |
| `abort.js` | 1 (line 2785) | **No** — same |

Every Phase B factory has exactly one production call site. The factory pattern's payoff (DRY across multiple call sites) is zero. The cost (closure ceremony, dep-validation, `let X = null` placeholders) is full price.

**Recommendation:** Don't fight to remove the factory pattern across the board — the extracted modules are still better than the in-line versions, and the factory-vs-curry distinction is largely cosmetic. BUT do drop the dep-validation (HIGH above) and the `let X = null` placeholders (HIGH above). Those are the real costs; the factory wrapper itself is cheap once those are gone.

If you want to go further: collapse build-options.js + callbacks.js into a single `lib/sdk/wiring.js` that exposes both. Both are SDK-pm-coupled, both are wired only in `main()`, both have similar dep sets (`config`, `db`, `tg`, `logEvent`, `botName`). One file would consolidate the SDK boot story.

### LOW — Test files for new modules are 25 + 22 cases. Some are tautological.

**File:** `tests/build-options.test.js`.

The factory-contract tests (lines 60–80):

```js
test('throws when config missing', () => {
  assert.throws(() => createBuildSdkOptions({}), /config required/);
});
test('throws when botName missing', () => {
  assert.throws(() => createBuildSdkOptions({ config: {} }), /botName required/);
});
// ...etc, one test per dep
```

These tests literally re-assert the `if (!config) throw` lines they shadow. They prove nothing about behavior — they prove only that the validation code is *present*, not that it catches real bugs. If you delete the validation (HIGH item above), you can also delete these.

**Recommendation:** Delete the per-dep "throws when X missing" tests. Keep the *behavior* tests (env scrubbing, agent overlay, permissionMode gating, resume passthrough) — those validate real logic.

Same story for `sdk-callbacks.test.js`'s `'throws on missing required deps'` test.

**Estimated LOC savings:** 30–40 LOC of test code.

## Final assessment

### Recommended action: **Proceed with simplifications** (Phase C)

The Phase B extractions are net positive — handlers in their own files DO help readability — but the **execution chose every layer of ceremony** (factories + dep validation + module-level placeholders + JSDoc-heavy headers + dedicated test files only for half the modules). Each layer alone is defensible; together they multiply.

### Sorted-by-impact deletion candidates

| # | Item | Files | Est. LOC saved |
|---|---|---|---|
| 1 | Drop dep-validation throws (or consolidate to helper) | 6 factories | 47 (or 40 with helper) |
| 2 | Delete `lib/sdk/router.js` + `tests/pm-router.test.js` | 2 files | 45 |
| 3 | Drop `let X = null` placeholders → bundle into `handlers` object or local-scope | polygram.js | 15–20 |
| 4 | Drop `logger.error?.()` `?.` (use unconditional `logger.error()`) | 6 factories | 0 LOC, but kills bug surface |
| 5 | Delete tautological "throws when X missing" tests | build-options.test.js, sdk-callbacks.test.js | 30–40 |
| 6 | Either write voice/download/abort/config-callback unit tests OR drop their unused dep-validation | 4 factories | (covered by #1) |
| 7 | Rename `lib/db/index.js` → `lib/db.js` (clarify it's not an index) | 1 file rename + 7 import sites | 0 LOC, clarity win |

**Combined: ~140–170 LOC removable**, plus material clarity wins.

### Complexity score: MEDIUM

The structural reorg (Phase A) is fine. The factory-extractions (Phase B) are over-cautious — they ship the ceremony of "this might have multiple call sites someday" without the tests that would actually exercise the seam. Dropping the ceremony costs nothing today and trims future-Ivan's mental tax.

### YAGNI violations specifically

- **`lib/sdk/router.js` createPmRouter** — identity passthrough kept as "future-extension point" with no concrete future plan. Same v1 critique, same answer: delete now, re-add when needed. The git history is the seam.
- **`lib/pm-interface.js`** (v1 carryover) — JSDoc-only typedef. Different story than router: it's actively used by `tests/_helpers/fake-pm.js` as a documentation anchor. Keep.
- **`logger = console` + `logger.error?.()` combo** — anticipates a "what if someone passes a logger without .error?" world that doesn't exist. The default is `console`, which always has `.error`. Drop the `?.`.
- **47 dep-validation throws** — anticipates "what if a future caller forgets a dep?" The future caller is `main()`. There is one. The throws are overhead with no payoff.
- **Factory closures around 1-call-site fns** (5 of 6 Phase B modules) — anticipates multi-call-site reuse that won't materialise for any of them. Cost is small but real (the `let X = null` debt above stems entirely from the closure pattern).

### What's GOOD (don't undo)

- The lib/ subdir reorg (Phase A) is clean. `lib/sdk/`, `lib/handlers/`, `lib/telegram/` etc. group sensibly.
- `lib/sdk/build-options.js` extraction itself is good — `polygram.js` is materially cleaner without the 190 lines of env-allowlist + agent-overlay machinery inline.
- `lib/sdk/callbacks.js` extraction is good — the 6 callbacks are now testable (and 22 tests were written).
- Test coverage for the two extractions that DID get tests (build-options + callbacks) is solid.
- The pre-cleanup deletion of CLI pm + dual-pm router (commits before 5d9f88e) was correct.
