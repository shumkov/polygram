# Claude Code 2.1.220 Compatibility Upgrade - Plan

## Goal Capsule

Upgrade Orchestra's hard-pinned Claude Code CLI from `2.1.173` to `2.1.220`
without regressing channels delivery, autonomous Workflow completion, isolated
Telegram-topic routing, session resume, or the SDK-backed path, and prove that
the candidate's Opus selection resolves to `claude-opus-5`.

Current baseline:

- Polygram `origin/main` is `0.21.0` and declares exact
  `@shumkov/orchestra: 0.5.0`.
- Orchestra `origin/main` is `0.5.0`; it owns
  `CLAUDE_CLI_PINNED_VERSION = "2.1.173"` in `lib/claude-bin.js`.
- The Mac runtime copy is available at
  `~/.local/share/polygram/claude-bin/2.1.173`; the candidate is available at
  `~/.local/share/claude/versions/2.1.220`. Both report their expected versions.
- The Workflow delivery fix is already released. A 2026-07-25 production
  validation in an isolated topic delivered the delayed result out of turn,
  suppressed the later duplicate callback, and completed without process or
  resume errors. Direct channels delivery succeeded, so that run did not need
  the transcript fallback.

Authority, in descending order:

1. The hard-pin and upgrade contract in Polygram's `AGENTS.md`.
2. The released Workflow delivery contract and production validation.
3. Anthropic's official `2.1.218`, `2.1.219`, and `2.1.220` release notes.
4. Current Polygram and Orchestra main branches and their test/spike conventions.
5. This plan's focused gate and release sequencing.

Execution profile:

- Polygram owns the reproducible old/new live gates and rollout evidence.
- Orchestra owns the pin and the compatibility release.
- The gate PR, pin PR, and dependency-integration PR remain separately
  attributable.
- No pin edit occurs until every mandatory old/new gate is `PASS`.
- No package publication, tag, merge, or deployment occurs without the
  corresponding later approval.

Stop immediately if the selected executable cannot be attested end to end, the
old rollback binary cannot be copied and verified outside mutable/garbage-collected
locations, the candidate changes a transcript or lifecycle contract without a
small deterministic adapter fix, or any mandatory old/new gate is `FAIL` or
`BLOCKED`. A broad rewrite of the CLI lifecycle is not authorized by this plan.

## Product Contract

### Summary

This is not a mechanical constant bump. Polygram's CLI backend observes
undocumented Claude Code behavior: TUI readiness, hooks, channel MCP delivery,
session JSONL ancestry, Stop ordering, background work, resume, compaction, and
worker handover. Releases between `2.1.173` and `2.1.220` change several of those
surfaces.

The upgrade therefore starts by making the real-Claude spikes select and attest
one explicit executable. The same adapter commit and bounded scenarios then run
serially against `2.1.173` and `2.1.220`. Only equivalent, fully passing evidence
permits a one-line pin change in a separate Orchestra `0.6.0` release. Polygram
consumes that release exactly in `0.22.0`, stages it on shumorobot, then treats
the two legacy-topology VPS bots as one separately approved promotion.

### Problem Frame

The previous delivery plan targeted `2.1.218` and reserved Orchestra `0.5.0` for
the pin. That plan is no longer executable: the user selected `2.1.220`, and
Orchestra `0.5.0` has already shipped platform-neutral session containment.

The upstream delta also changes behavior relevant to this incident:

- `2.1.218` changes `/deep-research`, fork-context skill backgrounding, paste
  handling, and engine teardown.
- `2.1.219` makes Opus 5 the default Opus model, adds nested subagent forwarding,
  defaults dynamic Workflows to a medium guideline aiming for fewer than 15
  agents, and allows nested subagents to depth 3 by default.
- `2.1.220` is described by Anthropic as bug fixes and reliability improvements
  without a detailed public itemization.

These changes make model/default behavior and Workflow topology separate from
adapter compatibility. The gate must not accidentally attribute a model or
workflow-policy change to the CLI transport layer.

### Requirements

- **R1 — Exact target.** The only candidate in this wave is Claude Code
  `2.1.220`.
- **R2 — Current release baseline.** Upgrade work starts from current Polygram
  `origin/main` (`0.21.0`) and Orchestra `origin/main` (`0.5.0`), not the
  historical delivery branches.
- **R3 — End-to-end executable attestation.** Every live gate privately records
  the absolute root executable path, `--version`, SHA-256, CLI and SDK selector
  values, and correlated worker provenance. Candidate self-spawns that honor
  `CLAUDE_CODE_PROCESS_WRAPPER` record a unique run id plus the executed
  binary's version, checksum, and path hash. The wrapper also records the PID of
  its own bounded `--version` attestation probe, which is the only
  selected-binary descendant excluded from worker coverage when the sampled
  process tree independently confirms that wrapper PID as its parent. Wrapper
  records must also match the selected run id and contain valid, unambiguous
  wrapper/parent/probe process identities. An observed selected-binary worker
  without a wrapper record, an observed claimed probe with the wrong sampled
  parent, any wrapper mismatch, or any process sampling failure is `BLOCKED`.
  `2.1.173`, which predates that contract, uses initial-process plus immediate
  process-tree evidence. The gate does not claim that a process path alone can
  identify an arbitrary different executable as a Claude worker when that
  process also bypasses the wrapper contract. Wrapper-backed workers are
  correlated by run-scoped PID because their parent can legitimately change
  after launch. Distinguishing same-run PID reuse would require a process
  generation token captured by both the wrapper and sampler; current-parent
  matching is not a substitute because it would reject reparented workers.
- **R4 — Per-host offline rollback.** Before any candidate live gate or candidate
  service restart, preserve that host/OS's `2.1.173` outside both Claude's
  auto-updated versions tree and Polygram's garbage-collected vendor tree.
  Verify version/checksum and rehearse the exact old-package/old-binary start
  path. Mac evidence cannot stand in for the Linux VPS.
- **R5 — Same-code old/new comparison.** Both binaries run the same gate commit,
  argv, explicit comparator model `claude-sonnet-4-6`, effort, permissions,
  fixture, and sanitized evidence collector. The init event must resolve the
  same model id. Only binary-specific paths and isolated run directories differ.
- **R6 — Production-shaped Workflow gate.** A bounded Workflow launches, the
  launch turn closes, and completion arrives without a later user prompt. One
  variant returns a successful direct-reply receipt and proves fallback
  suppression; another forces a synthetic direct-reply failure and proves one
  fallback delivery. Both assert the sentinel is absent from every foreign
  chat/topic route.
- **R7 — Lifecycle coverage.** Mandatory gates cover channels readiness and
  reply, follow-up queuing, cancellation, multiline input, a small file reply,
  both Workflow delivery branches, delayed MCP completion, subagents, resume,
  compaction, and tool-less drain.
- **R8 — JSONL and hook comparison.** Old and new runs capture and normalize
  hook names/fields, queue events, task-notification provenance, assistant
  ancestry, channel tool results, Stop ordering, and session JSONL. Unknown
  schema or missing evidence blocks the pin. The matrix compares a
  scenario-declared contract projection: pivotal queue/notification/Stop
  ordering plus only the hook shapes that express the scenario's transport
  contract. Model-selected local-tool hooks and assistant-generation row counts
  remain in sanitized evidence but are not assumed repeatable. A reviewed
  version-specific JSONL delta may pass only when it is declared in the scenario
  manifest with exact record shapes, counts, streams, and a bounded compatibility
  proof. Every projected run must first match the manifest's absolute projected
  baseline; each run may remove only the exact applicable candidate-only and
  optional insertions before that check. A position-independent removal set
  additionally requires one source-bound composite proof that every captured
  target record's own parser push emits no events, every retained input line
  emits the same deep-equal event batch after removing the complete set, and
  the final flush batch is deep-equal. The CLI scenario manifest declares two runs per
  version, same-version comparison first, and all cross-version pairings. The
  generic default remains one run per version with the existing strict
  `shape-equal` comparison. Any unrecognized or malformed normalized record,
  incomplete baseline, missing or false compatibility proof, or undeclared
  projected difference fails the gate.
- **R9 — Separate adapter and default-policy evaluation.** Compatibility gates
  use an explicit model and bounded three-agent Workflow. A separate
  candidate-only synthetic projection of production configuration must prove
  that an Opus selection resolves to `claude-opus-5`, bind the documented
  Workflow-size default to the no-override branch fingerprint in the exact
  attested candidate executable, and record
  `workflowSizeGuideline`, nesting depth/topology, elapsed time, and report
  completeness without silently overriding new defaults.
- **R10 — Separate compatibility release.** The pin ships in Orchestra `0.6.0`,
  keeping the lifecycle-changing CLI upgrade outside the already released
  `0.5.x` containment line. Polygram later adopts exact `0.6.0`.
- **R11 — Fail closed and stay scoped.** A failed gate may receive only the
  smallest deterministic compatibility repair needed for `2.1.220`. A lifecycle
  redesign, concurrency override, nesting override, or generic delivery rewrite
  requires a new design decision.
- **R12 — Privacy-safe artifacts.** Review bundles contain versions, checksums,
  hashed routing/session identifiers, lengths, counts, event shapes, and
  ordering, but no production bodies, credentials, usernames, absolute private
  paths, or raw command lines. Raw JSONL/pane data remains mode 0600 beneath a
  mode-0700 directory and is deleted after the sanitized bundle is accepted.
  Acceptance also deletes Claude's source transcript directories for the
  isolated gate-owned cwds after a complete preflight; it never targets a cwd
  outside the corresponding run directory.
- **R13 — Topology-honest rollout.** First record a production-shaped
  `0.21.0`/Orchestra `0.5.0`/Claude `2.1.173` baseline on shumorobot, then stage
  Polygram `0.22.0` there for at least 24 hours. The current VPS legacy service
  owns Shumabit and umi-assistant together, so they are one joint
  partner-facing promotion with one explicit approval and rollback boundary.
  Splitting their deployment belongs to the separate topology-cutover project.
- **R14 — Independent review.** The gate implementation and pin/integration
  diffs each receive independent multi-agent review before handoff.
- **R15 — Short compatibility payload.** The fixture uses a short sentinel so
  the separate Telegram formatting-length issue cannot confound this upgrade.

### Acceptance Examples

- **AE1 — Attested mismatch fails loudly.** Given the CLI or SDK root selector
  names `2.1.220`, a wrapper record names another executable, an observed
  selected-binary worker lacks its wrapper record, an observed claimed
  attestation-probe PID has a sampled parent other than that exact wrapper PID,
  wrapper identity is malformed or belongs to another run, or process sampling
  fails, the run is `BLOCKED`, never `PASS`.
- **AE2 — Autonomous completion survives.** Given a Workflow whose launch turn
  has ended, when its terminal result arrives with no new Telegram input, one
  short sentinel reaches the originating synthetic channel and no duplicate is
  observed.
- **AE3 — Direct delivery and fallback are both safe.** A successful direct
  channels reply suppresses the fallback; a synthetic failed direct reply is
  rescued once by the released transcript fallback; neither appears on a
  foreign route.
- **AE4 — Topology change is not mistaken for loss.** A candidate run may use
  fewer or differently nested agents under `2.1.219+` defaults and still pass
  when completion, evidence quality, routing, and report completeness meet the
  contract. The observed topology is reported.
- **AE5 — Default-model drift is visible.** The controlled old/new comparison
  uses the same explicit model. The production-configuration run separately
  proves that the candidate's Opus selection resolves to `claude-opus-5`;
  any different resolved model blocks rollout.
- **AE6 — Schema drift blocks the pin.** If task-notification provenance, Stop
  ancestry, reply receipts, queue events, or readiness signals cannot be mapped
  confidently, the pin remains `2.1.173`.
- **AE7 — Rollback is offline.** With the candidate unavailable, each rollout
  host can restore its recorded pre-upgrade Polygram package and preserved
  platform-specific `2.1.173`, rebuild the native binding, restart the owning
  service, and pass IPC/events checks without downloading Claude.
- **AE8 — Compatibility is repeatable before it is comparative.** The two old
  CLI runs and two candidate CLI runs each satisfy their same-version
  projection after independently proving and removing zero or one eligible
  interrupt `hook_cancelled` record. Every old/candidate pairing then differs
  only by the exact manifest-declared candidate `task_reminder` insertion, and
  every non-empty removal set carries one true composite parser-invariance
  proof for its actual records and placement; any other projected difference
  blocks the upgrade.

### Success Criteria

- A tracking issue exists with exact title
  `bump claude CLI v2.1.173 → v2.1.220`.
- Every selected root, wrapper invocation, wrapper-owned attestation probe, and
  observed selected-binary worker is classified; process-sampling gaps fail
  closed.
- All mandatory scenarios are `PASS` for both old and candidate binaries.
- The normalized old/new JSONL and hook report has no unexplained contract drift.
- Polygram and Orchestra full suites are 100% green with no silent skips.
- The Orchestra pin diff is limited to the version, directly required
  compatibility changes, tests, package version/lock, and upgrade documentation.
- Polygram declares exact Orchestra `0.6.0`; no caret or local tarball/path remains.
- The exact pre-upgrade Polygram package plus its Orchestra dependency and the
  host-specific `2.1.173` executable are rehearsed before each host promotion.

### Scope Boundaries

In scope:

- A reusable explicit-executable helper for the named real-Claude spikes.
- One current Orchestra-backed CLI contract harness and an auditable matrix
  manifest.
- A bounded Workflow completion fixture and delayed-MCP scenario.
- Repairing only the named current spikes and their documentation.
- Old/new JSONL, hook, TUI, channel, worker, and lifecycle comparison.
- Small deterministic compatibility fixes proven necessary by a red gate.
- Orchestra `0.6.0` pin release and exact Polygram integration.
- Staged rollout evidence after later authorization.

Out of scope:

- Reworking the released Workflow delivery model.
- Generic forwarding of background Agent output.
- Raising/lowering Claude's Workflow size guideline or subagent nesting limits.
- Changing chats explicitly configured to non-Opus models. Existing
  Opus/default-Opus selections must resolve to Opus 5 under the candidate.
- Repairing every historical spike or resurrecting deleted tmux modules.
- Solving Telegram HTML expansion/message splitting.
- Merging, publishing, tagging, or deploying without later explicit approval.

## Planning Contract

### Key Technical Decisions

- **KTD1 — Target Claude Code `2.1.220`.**
  (session-settled: user-directed — chosen over the previously approved
  `2.1.218` candidate: the user requires the release line whose default Opus
  model is `claude-opus-5`.)
- **KTD2 — Supersede, do not mutate, the completed incident plan.** The
  `2.1.218` units remain historical evidence of the delivery-fix design; this
  focused plan owns the new upgrade from the actual `0.21.0`/`0.5.0` baseline.
- **KTD3 — Release the pin as Orchestra `0.6.0`.** The previous plan's `0.5.0`
  number is already used by session containment. A new minor boundary keeps
  existing exact `0.5.0` consumers from silently taking the CLI lifecycle
  change.
- **KTD4 — Make executable selection a shared gate primitive.** One Polygram
  helper resolves the requested path, verifies version and checksum, configures
  `ORCHESTRA_CLAUDE_BIN` and `POLYGRAM_CLAUDE_BIN`, and supplies
  `pathToClaudeCodeExecutable` plus the wrapper/run-id environment to SDK
  queries. One version-controlled matrix maps every mandatory scenario to its
  driver, environment, oracle, cost, and artifact collector; spikes must not
  each invent their own selector.
- **KTD5 — Compare transport separately from changing defaults.** The old/new
  matrix fixes `claude-sonnet-4-6`, effort, fixture, and maximum agent count. A
  candidate-only synthetic production-config projection then proves the intended
  Opus selection resolves to `claude-opus-5`. Because the public SDK does not
  emit `workflowSizeGuideline`, that projection also fingerprints the documented
  default and its no-override resolver in the exact SHA-attested executable.
  Missing or changed semantic anchors block the pin. This distinguishes CLI adapter
  regressions from the desired model/default-policy change.
- **KTD6 — Use a project-local bounded Workflow fixture.** Copy a
  version-controlled `.claude/skills/completion-sentinel/SKILL.md` into a private
  temporary cwd and start `CliProcess` with isolated user config so its existing
  `project,local` setting sources load the Workflow. This avoids a production
  `CliProcess` API change solely to pass `--plugin-dir`. The fixture emits a
  unique short sentinel with at most three agents and proves tool-use, native
  notification, closed launch turn, and the direct-success and forced-failure
  delivery branches.
- **KTD7 — Treat worker provenance as part of the pin.** Absolute selection of
  the parent binary is insufficient across daemon-handover releases. Candidate
  runs use one private gate executable as `CliProcess.sessionLauncher`; it
  exports `CLAUDE_CODE_PROCESS_WRAPPER` to itself, records run id, pid/ppid,
  executable path hash, SHA-256, and version, then `exec`s its first executable
  argument. This injects the wrapper inside the tmux-launched process even when
  the tmux server predates the gate. The shared helper also merges the wrapper
  and run id into standalone SDK query environments. Immediate process-tree
  capture supplements it and records selected-binary descendants. The wrapper
  records the PID of its own bounded `--version` child so validation can exclude
  that narrowly typed attestation probe only when the sampled process tree
  independently records the same wrapper PID as its parent. An unobserved probe
  needs no exclusion; a sampled PID with another parent remains subject to
  worker coverage. Run id, wrapper PID, parent PID, and probe PID are validated
  as one unambiguous record before any exemption is applied. A failed
  process-snapshot attempt blocks the gate. The old binary predates the
  self-spawn wrapper contract and therefore uses initial-process/tree evidence
  rather than false parity. A different executable that also bypasses the
  wrapper is not classified as Claude from its process path because the same
  tree legitimately contains arbitrary helper executables. The remaining
  same-run PID-reuse-plus-wrapper-bypass case needs process-generation evidence
  and is outside this practical gate; binding a worker to its launch-time parent
  would instead create a known false block after legitimate reparenting.
- **KTD8 — Fail closed on unexplained upstream drift.** Missing or changed
  readiness, hook, queue, JSONL, notification, or Stop evidence is a blocker,
  not a reason to weaken assertions.
- **KTD9 — Keep production validation as baseline, not proof of the candidate.**
  The 2026-07-25 isolated-topic run proves released `0.4.3` delivery and
  duplicate suppression on `2.1.173`. It does not validate `2.1.220`, and it did
  not exercise the fallback because direct delivery succeeded.
- **KTD10 — Promote the VPS fleet jointly under the current topology.** The
  enabled `shumabit-sessions.service` owns both Polygram bots and shared tmux
  state; split bot units are absent. A Shumabit-only candidate restart is not
  possible without the separately reviewed topology cutover, so this plan uses
  one explicitly approved partner-facing promotion and does not touch Water.
- **KTD11 — Canary only fresh sessions.** A package restart does not replace
  already-running Claude processes. Every live candidate proof uses a new
  dedicated session/topic or a durable reset of only the canary session and
  attests its pid/version. Existing production sessions migrate naturally; no
  fleet-wide session reset is part of this upgrade.
- **KTD12 — Keep release versioning separate from feature review.** The
  dependency-integration PR remains attributable. After it is approved and
  merged, the release workflow aligns Polygram's package and plugin-manifest
  versions at `0.22.0`, then publishes only after separate approval.
- **KTD13 — Encode reviewed JSONL drift, not model interleaving.** Lifecycle
  comparison uses a manifest-declared contract projection and exact projected
  baseline, checked independently for every run before same- or cross-version
  comparison. Repeat count and pairing policy are scenario-manifest data, never
  a CLI-id branch in the runner. The CLI projection keeps strict session pivotal
  order and strict canonical order for `UserPromptSubmit`, `Stop`, and
  reply-tool `PreToolUse`/`PostToolUse`. It excludes model-selected local-tool
  hooks, assistant/tool-result rows outside the pivotal session projection, and
  `SubagentStop` because all three vary across compatible old runs. The one
  candidate addition passes only through an exact manifest declaration and a
  per-run stateful-parser proof that removing exactly one matching raw record
  preserves every retained input boundary and final flush. This accommodates
  observed timing-dependent placement without weakening record shape, count,
  stream, absolute baseline, or hook checks.
- **KTD14 — Synchronize the live CLI gate to turn-anchored event sequences.**
  Fixed sleeps and uncorrelated event names are not evidence that the target
  input was observed or that its terminal Stop reached the transcript. The
  queue/fold step waits in order for `turn-start(anchorMsgId=3)` and then
  `tool-use("Bash")`. The final file step waits in order for
  `turn-start(anchorMsgId=7)`, `tool-use-detail` carrying that run's unique file
  marker, the successful `tool-result` with the captured tool-use id, and the
  subsequent `stop-hook`. It then waits for a new exact
  `stop_hook_summary`/`turn_duration` pivotal-session suffix beyond the
  pre-turn terminal count. Both event sequences are registered before their
  target sends, all waits are bounded, and failures reject the cell rather than
  retrying or accepting a partial capture.
- **KTD15 — Give Claude-side MCP registration a bounded 30-second window.**
  `2.1.220` can render a ready TUI and connect the bridge while taking longer
  than Orchestra `0.5.0`'s five-second allowance to send the first
  `ListToolsRequest`. Increase the upstream default to 30 seconds on a separate
  reviewed compatibility commit, send startup-only pings from authenticated
  bridge readiness until the normal liveness loop takes over, and reject the
  handshake immediately on bridge disconnect. Do not retry or weaken the
  two-handshake requirement: a CLI that never registers the channel still fails
  before the first user message.
- **KTD16 — Opt SDK gates into MCP auto-background and correlate its native
  lifecycle.** `2.1.220` deliberately returns a zero MCP auto-background
  threshold in non-interactive SDK sessions unless
  `CLAUDE_AUTO_BACKGROUND_TASKS=1`; lowering only
  `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` therefore exercises the foreground
  opt-out path. The matrix runner removes any ambient
  `CLAUDE_AUTO_BACKGROUND_TASKS` value before constructing every child
  environment, then the candidate delayed-MCP cell alone sets it to `1`; the
  preserved old binary remains the foreground comparator. Candidate acceptance
  requires the threshold-timed synthetic tool result plus one correlated native
  `mcp_task` lifecycle: listed membership, task start, completed update,
  cleared membership, and completed notification all refer to the task/tool-use
  created by the one delayed tool call. It does not require
  `task_updated.patch.is_backgrounded`, because a directly auto-backgrounded MCP
  call starts as an `mcp_task`; that patch describes a foreground task being
  detached later.
- **KTD17 — Settle the autonomous Workflow completion turn before copying
  evidence.** A successful channel reply receipt proves delivery, but it can
  precede the completion turn's `Stop` hook and durable
  `stop_hook_summary`/`turn_duration` JSONL suffix. Before releasing the
  Workflow's completion marker, the driver first settles the launch turn
  against its pre-launch terminal count, then registers a bounded ordered
  waiter from that durable baseline. Direct delivery requires the exact
  completion marker's reply tool use, its matching tool result, and the
  subsequent `stop-hook`. The forced-fallback path has no `PostToolUse` event,
  so it requires the marker-bound reply use and subsequent `stop-hook`, then
  verifies the matching application-level `{ok:false}` result by tool-use id in
  the durable raw transcript. It then waits for a new exact terminal suffix
  before copying session or hook evidence. Fixed sleeps, uncorrelated Stops,
  and favorable retries cannot satisfy the gate.
- **KTD18 — Make the Workflow launch acknowledgement exactly-once.** The
  bounded fixture's launch turn may call the channel reply tool exactly once,
  with exactly its unique `WF-LAUNCHED:` marker and no files, then make no
  further channel call and end. Freeze the launch-turn dispatcher slice after
  its durable terminal settlement and before releasing the completion marker;
  require one successful reply to the origin route with exact text, no interim
  flag, zero files, and no other channel call. Persist only the sanitized launch
  count and field-match booleans. The strict reply-hook projection remains
  unchanged so an unsolicited progress reply is a gate failure rather than
  accepted model volatility.
- **KTD19 — Compare SDK subagents by their attributed task contract.** The
  SDK subagent gate uses a version-specific `sdk-subagent-v1` lifecycle oracle
  rather than comparing the complete model stream. Both versions must resolve
  the configured model, invoke exactly one `Agent`, emit exactly one task
  start, retain one raw Agent identity across every child message and the
  top-level returned tool result, retain one raw task identity across every
  task event, emit exactly one completed task notification, and finish
  successfully in that partial order. Every child tool result must match a
  child tool use and be non-error. Every auxiliary top-level non-Agent tool
  result must likewise match exactly one auxiliary top-level tool use, follow
  that use, and be non-error; the returned Agent result remains a separate
  exact join and must also be non-error. Every result follows its uniquely
  matching use, and Agent, auxiliary, and child tool-use ids are non-empty and
  mutually disjoint. Auxiliary operation pairs may complete wholly before the
  Agent use or wholly after the returned Agent result; no top-level assistant
  or user record is allowed between task start and notification, so a child
  record whose parent attribution disappears cannot be reclassified as ambient
  in-boundary work. A top-level assistant record may not mix Agent and
  auxiliary tool uses. Only an absent or exactly `null`
  `parent_tool_use_id` denotes a top-level record; reject an empty string or
  every other non-string/non-null value. The exact order starts with
  `Agent use < task_started`; the first and final child records must both occur
  after task start and before notification. The preserved version must emit no
  `task_updated`; the candidate must emit exactly one completed update after
  the final child record and before notification. The sanitized proof contains
  only exact counts, ordinals, and identity/status booleans, never raw ids.
  Known hook setup, thinking-token, rate-limit, task-progress, top-level
  narration, exactly joined auxiliary top-level tool operations, and
  correlated child-operation multiplicities are explicitly ambient; task
  progress remains inside the task boundaries and every child operation
  remains on the one Agent lineage. Unknown lifecycle record types or system
  subtypes, extra task-bearing boundaries, lost or mixed attribution,
  unmatched, reordered, or cross-scope tool uses/results, ambient system rows
  carrying unexpected task/tool identity, reordered task events, and
  unsuccessful results remain hard failures.
- **KTD20 — Forbid marker transformation in the bounded Workflow prompt.**
  The Workflow script must return the exact existing
  `WF-COMPLETE:[a-f0-9]{32}` line read from the marker file. The fixture
  explicitly forbids hashing, digesting, encoding, checksumming, prefixing, or
  otherwise transforming that line, including `md5`, `md5sum`, `shasum`, and
  `sha256sum`; the first agent returns the raw line and the Workflow's ordinary
  JavaScript extracts and returns that same match. The marker file contains the
  exact line token followed by one LF byte; removing only that record
  delimiter is the permitted boundary normalization. Live reply input,
  durable reply tool use, direct/fallback transport text, and raw Workflow
  metadata result must equal the pre-generated line token. The notification's
  serialized `<result>` must equal `JSON.stringify(marker)` and decode to that
  canonical token. Prefixes, suffixes, quotes in delivered text, code fences,
  whitespace/case changes, and every other transformation fail. The gate does
  not accept a dynamically discovered substitute or retry for a favorable
  generated Workflow script.
- **KTD21 — Admit only proof-inert interrupt cancellation metadata.** The
  repeated CLI scenario may contain zero or one normalized
  `attachment.type="hook_cancelled"` on either version because the deliberate
  interrupt can race the CLI's `UserPromptSubmit` hook bookkeeping. A
  manifest-declared optional insertion is removable only when its exact raw
  record count is within the declared maximum; every raw row is mainline,
  names `UserPromptSubmit` in both `hookName` and `hookEvent`, and has a
  `parentUuid` equal to the deliberate interrupt's channel-input `uuid`. The
  candidate-only `task_reminder` declaration remains exact and separate.
  One source-bound composite replay removes the union of all applicable rows
  and proves every target `push()` batch empty, every retained batch identical,
  and the final flush identical. Missing, stale, duplicate, excessive,
  overlapping, mixed-record, parser-visible, unanchored, or undeclared proofs
  fail; the complete source-bound normalized lifecycle remains reviewable.
- **KTD22 — Fail closed at every gate-evidence boundary.** A run is not valid
  merely because its self-reported proof is internally consistent. Delayed-MCP
  and subagent drivers persist their immutable raw SDK streams; CLI/Workflow
  persist both session and hook streams. Every stream carries source hashes,
  raw/normalized counts, and exact normalized lifecycle; the parent runner
  verifies each private source and independently regenerates applicable
  structural proofs before accepting the sanitized result. Every projected-compatible
  result must match its absolute baseline even when the version has only one
  run. Common attestations, wrapper records, process evidence, normalized
  lifecycle records, and each scenario's top-level sanitized result use exact
  allowlisted schemas; unknown fields fail before review evidence is written
  or accepted. The SDK option builder rejects overrides of the selected
  executable, cwd, custom spawn function, model, effort, or selector/wrapper
  environment. The parent also hashes and attests the selected binary
  independently from the run's immutable selector. Every SDK gate requires a positive sample count, at least one
  unique selected root, and exact root/process consistency. Candidate
  self-spawns still require wrapper provenance, while the SDK-owned root
  remains the explicitly selected unwrapped process.
- **KTD23 — Resolve process executables by platform before attestation.**
  Process snapshots carry pid/ppid plus a canonical executable path, never an
  assumed `ps comm` path. Absolute macOS `comm` values are canonicalized;
  relative/basename values fail closed. Linux resolves `/proc/<pid>/exe` and
  canonicalizes the target; resolution failure fails closed. Unsupported
  platforms fail closed. A vanished target makes CLI capture fail immediately
  and records an SDK sampling failure; it is never silently treated as
  unrelated. A root recorded synthetically at spawn does not satisfy coverage:
  a positive snapshot must resolve every root to the selected executable. CLI
  and SDK evidence then require selected-binary coverage, so wrapper records
  alone cannot make zero observed coverage pass.

### Alternatives Rejected

- **Change the pin and rely on unit tests.** Rejected because unit tests simulate
  precisely the undocumented TUI/JSONL contracts most likely to drift.
- **Reuse the previous `2.1.218` plan verbatim.** Rejected because the selected
  target and package baseline changed, and `0.5.0` is no longer available as the
  pin release.
- **Run only `2.1.220`.** Rejected because a candidate-only failure cannot
  distinguish pre-existing gate defects from upgrade regressions.
- **Let each spike use its own executable environment.** Rejected because current
  SDK spikes do not pass `pathToClaudeCodeExecutable` and can silently test a
  different binary.
- **Override Workflow size/nesting to reproduce the historical 102-agent shape.**
  Rejected because that topology is not the product contract and overriding new
  defaults would hide candidate behavior.
- **Bundle the Telegram length fix.** Rejected because it is independent of the
  Claude pin and the observed send already recovered by splitting.

### Assumptions and Residual Risks

- The locally present binaries are sufficient to begin the gate, but each run
  recomputes rather than trusts the planning-time version/checksum.
- The old Mac binary currently exists in Polygram's managed vendor path. The VPS
  has its own Linux copy. Each host needs a separate rollback copy outside every
  vendor/auto-update tree before its candidate live gate or restart.
- A synthetic Workflow can prove lifecycle delivery, not research quality.
  Representative FAQ research remains a staging criterion.
- Anthropic's generic `2.1.220` note cannot prove the absence of internal changes.
- The worker proof assumes Claude self-spawns honor
  `CLAUDE_CODE_PROCESS_WRAPPER`. A different Claude executable that also
  bypasses that wrapper is indistinguishable from an ordinary helper process
  without OS-level execution tracing or isolation. This double-failure case is
  an accepted residual risk, not evidence the gate observed a mismatch.
- A real-Claude gate consumes tokens and may encounter upstream service failures.
  Infrastructure/auth failures are recorded `BLOCKED`, rerun only after the cause
  is identified, and never converted to `PASS`.
- The production formatting-length failure is real but does not affect the short
  compatibility sentinel and remains outside this upgrade.

#### U3 gate finding: SDK auto-background is explicitly opt-in

The first authoritative candidate delayed-MCP cell completed the five-second
handler in the foreground despite
`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=1000`. Exact-binary inspection confirmed
that `2.1.220` computes a zero MCP auto-background delay for non-interactive
sessions unless `CLAUDE_AUTO_BACKGROUND_TASKS` is enabled. The initial gate had
therefore tested a deliberate SDK opt-out, not the release feature.

A diagnostic run changed only that missing opt-in. The delayed tool returned an
asynchronous tool result after the one-second threshold, emitted a native
`background_tasks_changed` membership plus `task_started` for an `mcp_task`,
finished the handler after five seconds, cleared membership, emitted a
successful `task_updated`, sent a completed `task_notification`, and delivered
the unique marker once. The preserved `2.1.173` binary contains no MCP
auto-background threshold path and remains the foreground comparator.

The diagnostic also invalidated the initial
`task_updated.patch.is_backgrounded` assertion. Direct MCP auto-background
creates an already-backgrounded `mcp_task`; its update patch records terminal
status, not a later foreground-to-background transition. The final gate must:

1. Remove `CLAUDE_AUTO_BACKGROUND_TASKS` from the inherited parent environment
   before constructing every matrix child environment. Then set it to `1` only
   for the candidate delayed-MCP cell, while keeping the same explicit
   one-second MCP threshold in both cells.
2. Capture the delayed MCP tool-use id and the native MCP task id without
   persisting raw identifiers in the sanitized artifact.
3. Emit a strict `nativeLifecycleProof` object with no raw ids and exact keys:
   schema version and expected mode; exact counts for target tool use, target
   tool result, non-empty membership, empty membership, MCP task start,
   completed update, and completed notification; stream ordinals for the target
   tool use/result/marker and every candidate native event; membership sizes;
   equality booleans tying listed/start/result/update/notification task and
   tool-use identities together; and booleans for the asynchronous placeholder
   plus completed update/notification statuses. Missing or unknown fields fail.
4. Require the candidate's non-empty membership to contain exactly the target
   task and the later clear membership to be exactly empty. Require tool use
   before membership-add and task-start (without ordering those two against one
   another), both before the asynchronous result; require membership-clear and
   completed update after that result (without ordering those two against one
   another); require the completed notification after both; and require the
   final unique marker after notification.
5. Record the asynchronous placeholder delay from handler start. Require it no
   earlier than 250 ms before the configured one-second threshold, no later than
   two seconds after that threshold, and at least two seconds before handler
   completion. These declared tolerances prove the threshold path while
   allowing scheduler jitter.
6. Replace `lifecycle: "shape-equal"` only for delayed-MCP with a strict
   `delayed-mcp-v1` version-specific oracle. The matrix independently recomputes
   the old zero-native-event or candidate correlated proof for each run, then
   compares the declared shared fields without requiring intentionally different
   normalized streams to match. A missing, null, or unknown lifecycle policy
   fails validation; no other scenario receives this exception.
7. Keep the one-marker, one-tool-use, successful-result, and minimum-duration
   assertions. Missing, duplicated, uncorrelated, or out-of-order terminal
   evidence fails closed.
8. Add red-to-green unit tests for ambient opt-in removal, candidate-only
   opt-in, the scenario-local version-specific comparator, threshold/lead
   timing, exact proof schema, and rejection of lifecycles assembled from
   mismatched task/tool-use ids. Do not weaken the cell to marker-only success.

Rejected alternatives:

- Reclassify the candidate as foreground-compatible. That would discard the
  release behavior this cell exists to validate.
- Set only the timeout variable and treat foreground completion as a flaky
  background failure. The exact implementation and the controlled opt-in run
  show deterministic configuration, not timing.
- Keep cross-version lifecycle shape equality or delete lifecycle validation.
  The former contradicts the observed candidate events; the latter converts
  the cell into marker-only success. The bounded version-specific oracle
  preserves both contracts.
- Accept any task start and notification counts. Concurrent unrelated tasks
  could then produce a false pass.
- Require `patch.is_backgrounded`. That field is absent by design when an MCP
  task is created directly in the background.
- Require a fixed ordering between membership clear and completed update.
  Their relative order is not the contract; both must be correlated and precede
  the terminal notification.

#### U4 compatibility finding: Stop can precede the terminal JSONL append

The old-version failed-reply gate exposed two deterministic Orchestra `0.5.0`
defects before the pin changed:

1. Native Workflow completion ancestry can cross same-session, non-sidechain
   `system/stop_hook_summary` and `system/turn_duration` rows. Excluding those
   rows from the UUID graph breaks an otherwise linear launch ancestry.
2. Claude's Stop hook can carry the correct `last_assistant_message` before the
   corresponding terminal assistant row has been appended to `transcript_path`.
   In the captured synthetic trace, the immutable Stop-time snapshot ended on
   the failed reply receipt; the matching terminal row appeared shortly
   afterward, before Claude appended the Stop summary rows. This matches the
   current Claude Code hooks reference, which says transcript writes are
   asynchronous and may lag hook inputs.

The compatibility fix remains fail-closed:

- Include every same-session, non-sidechain UUID row in ancestry lookup while
  continuing to define conversational mainline and terminal selection from only
  assistant/user rows.
- Hash at most 16 MiB of the transcript from an open file descriptor during
  Stop handling. Correlation must retain that exact device, inode, byte boundary,
  and prefix digest; larger transcripts fail closed without affecting direct
  reply delivery.
- On only the retryable `terminal-not-last-mainline` result, poll for bounded
  transcript growth for at most one second. Growth must be append-only: file
  device/inode must remain unchanged, size must never shrink, and the original
  byte prefix must retain the same digest. Each growth creates a new immutable
  byte boundary and re-runs the complete correlation. Delivery remains
  ineligible unless the appended terminal has the exact Stop text, end-turn
  identity, native Workflow ancestry, and unambiguous same-branch receipts.
- A split terminal write may temporarily return `partial-line` after settlement
  has begun and continue polling until the same deadline. A complete malformed
  line or any other schema/provenance failure fails immediately.
- The settlement loop stays inside one active decision with the original
  delivery generation and one decision identity independent of changing byte
  size. It checks generation and process closure around every asynchronous
  step, so teardown cancels it and a later Stop cannot start a parallel retry.
- Capture the existing monotonic work-hook sequence at Stop. Any work hook or
  consumer turn that begins before fallback emission changes that sequence and
  permanently withdraws eligibility even if its pending turn settles during the
  retry window.
- A user row present before the first otherwise-eligible retry snapshot, a fork,
  malformed append, different final, teardown, generation change, intervening
  work, or pending consumer turn still suppresses fallback. Activity appended
  only after the fallback has already emitted is outside the polling decision
  and remains governed by the existing delivery/turn lifecycle.

Rejected alternatives:

- Trusting `last_assistant_message` as a synthetic terminal would discard the
  persisted terminal UUID/request identity used to prove branch ownership.
- Reading the unbounded live file once would let unrelated later activity enter
  the decision without a bounded settlement phase.
- Retrying every correlation failure would weaken intentional fail-closed schema
  and provenance checks.

The regression test must first fail with a Stop-time transcript ending at the
failed reply receipt, append the real terminal row asynchronously, and then pass
only after the fix. Companion tests split the terminal across writes, reject a
complete malformed append, reject replacement/shrink/prefix mutation, suppress
a user row present before the candidate terminal snapshot, suppress a consumer
turn that begins and settles during polling, and prove duplicate Stop events
cannot create duplicate fallback decisions.

#### U4 gate finding: automatic compaction pressure is not deterministic

The inherited `compact-boundary.mjs` spike assumes roughly 210K input tokens are
near the selected model's automatic-compaction threshold. That assumption is no
longer stable. Current Claude Code documentation states that automatic
compaction uses a 200K window for standard models or 1M for extended-context
models, with `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and
`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` available as calculation overrides:
[environment variables](https://code.claude.com/docs/en/env-vars).

The preserved `2.1.173` binary completed the large prompt successfully without a
compact boundary. A two-turn diagnostic with a 250K effective window and 50%
threshold also completed twice without a boundary. Repeating with a 1% threshold
produced the same result. Both selected binaries contain the documented
environment-variable names, but those controls do not force a deterministic
automatic boundary in this SDK stream path.

The compatibility matrix should therefore use manual compaction:

- Send a short first SDK turn that establishes a random marker and capture its
  session id.
- Continue that same SDK session and submit `/compact`. Current official Agent SDK
  documentation explicitly defines prompt-string `/compact` as the supported
  manual compaction path and says the SDK emits
  `system/compact_boundary`: [agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop).
- Require exactly one `PreCompact` hook with `trigger: "manual"` after that
  prompt and exactly one subsequent `system/compact_boundary` attributed to the
  same session. Only after the boundary may the harness send the recall prompt.
- The recall prompt must not contain the marker. Record hashes for the
  marker-establishing prompt/result, compact prompt, ordered hook/boundary, and
  marker-free recall prompt/result. The final result must recall the marker
  exactly once and finish successfully.
- Compare the sanitized hook/boundary/result shape across `2.1.173` and
  `2.1.220` using the same selected-binary SDK harness.

This gate proves the parser and same-session lifecycle contract across a real
compaction boundary. It intentionally no longer claims to prove when automatic
compaction fires. Automatic-trigger behavior remains a 24-hour staging
observation using normal context telemetry. Staging records zero or more ordered
`PreCompact(trigger:"auto")` / `compact_boundary` pairs and the subsequent
same-session outcome. Any malformed or missing pair, session loss, or failed
post-boundary turn blocks promotion. If no automatic boundary occurs, the report
must say `not observed`; that is residual risk, not a pass.

Rejected alternatives:

- Inflate the fixture toward a 1M-token window. This is expensive, slow, and
  still depends on model/window policy rather than the adapter contract.
- Keep lowering the documented threshold overrides. The old selected binary
  failed to emit a boundary even at 1%, so treating the override as proof would
  be false confidence.
