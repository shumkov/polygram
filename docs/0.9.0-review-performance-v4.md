# 0.9.0 Cleanup — Performance Review v4

> Reviewer: performance-oracle
> Branch: `0.9.0-cleanup` (HEAD `cea6419`)
> Scope: 7 new handler factories (config, extract-attachments, config-ui,
>        record-inbound, ipc-send, dispatcher, poll) + the wiring block in
>        `polygram.js` `main()`.
> Baseline: `docs/0.9.0-review-performance.md` (v2).
> Date: 2026-05-05

## TL;DR

Factory-extraction layer is **performance-neutral**. Microbench of the
pre/post-extraction `dispatchHandleMessage` shape shows the closure form
runs within noise of the direct form (mean delta ≤ 5 ns/call, often
*faster* due to V8 inlining the closure-captured locals). Boot cost
of constructing 13 factories is ~210 ns total (16 ns/factory) —
amortised across a ~10×/day kickstart cadence, ~2 µs/day. The
`inFlightHandlers` Map cleanup is correct; auto-resume Map decays
naturally; teardown is via `process.exit(0)` so closure lifetime is
not a leak surface.

The user's intuition was right: at 100s of msg/day per bot, none of
this is measurable. Recording the analysis so v5 doesn't have to
re-do it.

## ✅ Confirmed / no regression

### 1. Closure-traversal cost is unmeasurable (Q1 — hot path)

**Microbench** (`/tmp/claude-502/closure-bench.js`, 1M calls × 3 runs,
Node 24, M1 Mac):

| Form | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| direct (pre-extraction) | 248 ns/call | 252 ns/call | 242 ns/call |
| factory-closure (post)  | 257 ns/call | 256 ns/call | **235 ns/call** |

Delta ≤ 5 ns/call, sometimes negative (closure form *faster* on run
3 — within run-to-run jitter, not a real signal).

**Why no slowdown.** V8 SSA-promotes closure-captured locals into the
inner function's stack frame after the function inlines. The
"closure-traversal" mental model — N hash-lookups per call — is
accurate for source-level reasoning but doesn't survive Crankshaft /
TurboFan optimization. Once `dispatchHandleMessage` is hot, the
captured `config`, `db`, `inFlightHandlers`, `logEvent` etc. become
stack slots; access cost is identical to module-level `let`.

**Hot path actually exercised in production:**
`bot.on('message')` → `dispatchRegularMessage` (closure inside `createBot`)
→ `dispatchHandleMessage` (factory output) → `handleMessage` (module-
level). Steps 2 and 3 each capture some free variables. Bench
emulates step 3; step 2's `dispatchHandleMessage` reference is itself
a module-level `let` (line 450) read once per call — a single
load+jump on the optimised path.

**Verdict.** No measurable regression. At ~100 msg/day/bot peak, even
a hypothetical 20 ns/msg overhead would total 2 µs/day — invisible
against multi-second LLM turn times.

### 2. Boot wiring cost is microsecond-class (Q2)

**Microbench** (`/tmp/claude-502/boot-bench.js`, 100k iterations of
the full 13-factory wireAll):

```
wireAll (13 factories) × 100000: 21.00ms
per wireAll: 210ns (0.21µs)
per factory call: 16ns
```

**Comparison to v2's findings:**
- v2 measured `~210 µs faster boot` from removing dual-pm
  instantiation. That win dwarfs the cost of the new factories by
  3 orders of magnitude (210 µs saved vs. 0.21 µs added).
- Per launchctl kickstart (~10×/day), the wiring block adds <1 µs to
  total boot time. v2's pm consolidation more than paid for it.

**Verdict.** The 13-factory wiring block is invisible against the
pm constructor (~50 µs), the SQLite bootstrap (~ms), the `bot.init()`
network call (~100 ms), and the polling start. No action.

### 3. Memory footprint: bounded, no leak (Q3)

**Per-instance retained state from the 13 factories:**

| Factory | Captured deps | Retained state |
|---|---|---|
| createDispatcher | 18 named deps | `inFlightHandlers` Map |
| createPollLoop | 7 named deps | `running`, `offset`, `stalled` (per-call locals) |
| createRecordInbound | 5 named deps | none |
| createHandleSendOverIpc | 4 named deps | none |
| createFormatConfigInfoText | 3 named deps | none |
| createHandleConfigCallback | 9 named deps | none |
| createHandleAbort | 9 named deps | none |
| createAutosteerHandlers | 4 named deps | none |
| createDownloadAttachments | 5 named deps | none |
| createTranscribeVoiceAttachments | 8 named deps | none |
| createBuildSdkOptions | 5 named deps | none |
| createApprovals | 8 named deps | sweep timer ref |
| createSlashCommands | 13 named deps | `contextHintShown` Set (passed in) |

**Total retained heap:** ~13 closure objects × (~10-20 captured refs +
function code) ≈ <2 KB total. The captured refs are pointers to objects
that exist anyway (`config`, `db`, `pm`, `bot`, `logEvent`) — no
duplication. The 15 `let X = null` placeholders in `polygram.js` are
each a single V8 slot (~8 bytes); ~120 bytes of module-level overhead.

**GC + teardown.** `shutdown()` ends with `process.exit(0)` (line 2054),
so closure liveness is not a concern — the entire heap is dropped at
process death. Even if we wanted graceful Node-level GC of the
factories, the strongest references (the module-level `let`s) would
need explicit nulling. Current code doesn't do this; doesn't need to.

**Verdict.** No leak surface. Closure footprint is <2 KB above the
direct-call baseline. v2's CLI-pm removal saved ~200-500 KB of RSS;
the factories give back <2 KB. **Net memory delta still strongly
positive vs. 0.8.0.**

### 4. inFlightHandlers Map cleanup is correct (Q4)

`lib/handlers/dispatcher.js:241-245`:

```js
}).finally(() => {
  const n = (inFlightHandlers.get(sessionKey) || 1) - 1;
  if (n <= 0) inFlightHandlers.delete(sessionKey);
  else inFlightHandlers.set(sessionKey, n);
});
```

**Audit of leak paths:**

| Path | Increments | Decrements | Balanced? |
|---|---|---|---|
| Normal success | +1 | finally(-1) | ✓ |
| Error (handled by .catch) | +1 | finally(-1) | ✓ |
| Auto-resume triggered (early `return` in catch) | +1 | finally(-1) — finally runs *after* catch returns, JS semantics | ✓ |
| Auto-resume succeeds (independent attemptAutoResume call) | 0 (doesn't go through dispatchHandleMessage) | 0 | ✓ |
| Auto-resume fails (independent path) | 0 | 0 | ✓ |
| Shutdown drain (line 2004) | reads `.size > 0` | finally still fires for the in-flight handlers | ✓ |
| Concurrent finallys for same sessionKey | sequential (single-threaded JS) | atomic read-modify-write | ✓ |

**Key check — does `.finally()` run after `return` inside `.catch()`?**
Yes. `.catch().finally()` chains the finally on the resolved-or-rejected
result of the catch; the catch's `return` only returns from the catch
callback, not the chain. Verified by the JS Promise spec.

**Auto-resume path's effect on the Map:**
`attemptAutoResume` is called *fire-and-forget* outside the
`dispatchHandleMessage` chain (lines 205-225). It runs `sendToProcess`
directly, NOT through `dispatchHandleMessage`. Therefore it does not
add to `inFlightHandlers`. The original handler's `.finally()` decrements
once. **No double-counting, no orphaned entries.**

**Stale entries — not possible.** Every `+1` on increment has a
matching `-1` in a guaranteed-to-run `.finally`. Worst case: a handler
that hangs forever keeps its entry, but `inFlightHandlers` would still
reflect reality (1 stuck in-flight). The shutdown drain at line 2004
correctly observes `.size > 0` and waits.

**Verdict.** Cleanup logic is correct. No leak.

### 5. Poll loop closure overhead is N×~5 ns vs. 25s idle (Q5)

`lib/handlers/poll.js` `pollBot` captures `db`, `dbWrite`, `config`,
`botName`, `isWellFormedMessage`, `getTopicName`, `logger` — 7 free
variables. Per loop iteration:
- 1 read each of `db`, `dbWrite`, `config`, `botName` (~5 ns × 4 = 20 ns)
- N reads inside the per-update for-loop (proportional to update count)

**Cadence:** long-poll blocks up to 25 seconds when idle. A typical
day at 100 msg/day = ~4 polls/hour with updates, ~140 polls/hour empty.
Per-iteration overhead: ~50 ns of closure access. Per-hour cost:
~140 × 50 ns = 7 µs.

**Vs. the 25s blocking call:** 7 µs / 90,000,000 µs ≈ 0.000008%.

**Verdict.** Imperceptible. No action.

### 6. attemptAutoResume allocation profile is comparable to handleMessage (Q6)

`attemptAutoResume` allocates per-call:
- 1 `noopStreamer` object literal (5 method props, ~80 bytes)
- 1 `noopReactor` object literal (4 method props, ~64 bytes)
- 1 `continuation` string (constant, hoisted to module scope by V8)
- N `chunks` from `chunkMarkdownText` (proportional to result.text length)
- 2 `tg(...)` argument objects (`sendMessage` + `deliverReplies`)

**Vs. `handleMessage`'s normal path:**
`handleMessage` allocates a real streamer, a real reactor (with
heartbeat timer, batched emoji updates), runs the slash-command
pre-check (allocates regex match arrays), runs autosteer detection
(2 Set lookups + 2 Map lookups), runs the typing indicator (per-chat
circuit breaker state), and the streaming-result accumulator.

**Allocation delta:** auto-resume is ~5x *cheaper* per turn than
the normal handleMessage path because the streamer+reactor are stubs
and there's no slash-command preflight. Frequency: auto-resume fires
only on 300s no-activity timeout, gated by 10-min cooldown. At
production rates, maybe ~0-2 invocations/day/bot.

**Verdict.** Strictly less allocation than the normal path. No concern.

## ❗ Real concerns

### `_isAutoResume` is checked but never set — dead branch

`lib/handlers/dispatcher.js:195`:
```js
const isResumeTurn = msg._isAutoResume === true;
const resumable = !isResumeTurn && isAutoResumable(...);
```

A grep for `_isAutoResume` in the whole repo finds **only** this read
— nothing sets it. Either:

1. **The intent was for `attemptAutoResume` to mark the resumed turn
   so a *second* auto-resume of the same msg is suppressed.** In this
   case, `attemptAutoResume` should set `originalMsg._isAutoResume = true`
   (or pass a fresh msg through with the flag) before calling
   `sendToProcess`. The current code relies entirely on
   `autoResumeTracker.isInCooldown(sessionKey)` (10-min window) which
   provides the same protection at session granularity. So functionally
   equivalent, just the per-msg guard is dead.

2. **The check is residual from a prior design** — earlier rcs may
   have set `_isAutoResume` and the setter got dropped during the
   extraction. Code archaeology would confirm.

**Severity:** LOW. The 10-min cooldown is doing the work. Either
remove the dead branch (`isResumeTurn` always false) or wire the
setter for defence-in-depth.

**Performance impact:** zero — the dead read is one property access.

## 🚦 Merge verdict

**Ship it.** The 0.9.0-cleanup factory extraction is performance-
neutral. None of the six investigation areas surface a regression.
Microbenchmarks confirm closure overhead is below V8's optimisation
noise floor. Boot wiring is sub-µs. Memory footprint is unchanged.
The dispatcher's in-flight Map is correctly maintained. Auto-resume
allocation profile is *cheaper* than the normal path, not more
expensive.

Single LOW-severity follow-up: the `_isAutoResume` check in dispatcher.js
is a dead branch (nothing sets it). Either remove or wire the setter.
Out of scope for this merge; track for 0.9.1 cleanup pass.
