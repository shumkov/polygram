# Polygram 0.8.0 — SDK Migration Plan (v4)

**Goal:** Replace `child_process.spawn('claude', [...])` + stream-json
parsing in `lib/process-manager.js` with `@anthropic-ai/claude-agent-sdk`
typed control-plane, **without** regressing any user-visible behaviour or
losing existing operational features.

**Revision history (3 audit rounds, 4 agents per round):**

- **v1**: 305-line sketch. Audit found ~30 HIGH findings (SDK API
  shapes, OpenClaw misreads, regression risks, leftover code paths).
- **v2** (914 lines): rewritten after 1st audit. Adopted every finding
  as a Phase 0 spike gate, phase-internal acceptance test, code
  commitment, or out-of-scope decision. 2nd audit found ~25 new
  issues v2 introduced.
- **v3** (1310 lines): corrected v2 — SDK API drift,
  OpenClaw cross-reads, missing leftovers, vague UX commitments. 3rd
  audit found 8 internal contradictions, 7 implementation BLOCKERs,
  17 HIGH/MEDIUM ship-breaker risks. SDK final-drift check verified
  green (0.2.123 stable since v3 audit).
- **v4 (THIS doc)**: applies the 3rd-round patch — pins canonical
  commits across 5 contradicting sections, adds API sketches for
  the 7 BLOCKERs, makes explicit code commitments for the 17 ship-
  breakers (in-process ordering races, cross-version cutover, tail-
  risk shutdown bounds). Doc-only; no scope change. Audit
  transcripts in `/private/tmp/claude-502/.../tasks/`.

## 1. Architecture: before vs after

### Before (today, 0.7.6)

```
shumabit launchd plist
  └─ polygram daemon (Node, one per bot)
      ├─ ProcessManager (LRU-among-idle of claude subprocesses, default cap=10
      │     via config.maxWarmProcesses; in-flight entries pinned, getOrSpawn
      │     parks via _lruWaiters with 5-min timeout if every slot is busy)
      │   └─ 1 claude subprocess per active sessionKey
      │       ├─ sessionKey is `chatId` by default; `chatId:threadId` if
      │       │     chatConfig.isolateTopics=true (per-topic isolation).
      │       │     Multiple sessionKeys NEVER share a process.
      │       ├─ stdin: JSON-encoded user messages (1 per turn);
      │       │     pendingQueue maps N user msgs → N result events FIFO,
      │       │     queueCap=50 with drop-oldest-non-active policy
      │       ├─ stdout: stream-json events (init / assistant / result)
      │       └─ approval hook subprocess (bin/approval-hook.js) →
      │             IPC socket (Unix) → polygram daemon
      ├─ Telegram bot loop (grammy primitives, but a CUSTOM long-poll wrapping
      │     bot.api.getUpdates with persisted last_update_id in
      │     polling_state table; poll watchdog + 409 handling — NOT bot.start())
      ├─ IPC server (Unix socket) for cron `send` op + approval hook
      └─ SQLite (better-sqlite3): sessions, chat_migrations, messages +
            messages_fts, config_changes, events, pair_codes, pairings,
            pending_approvals, polling_state, attachments, turn_metrics
```

### After (target, 0.8.0)

```
shumabit launchd plist
  └─ polygram daemon (Node, one per bot)
      ├─ ProcessManager (LRU pool of Query objects + their writable input iterables)
      │   └─ 1 Query per active sessionKey
      │       ├─ Input: AsyncIterable<SDKUserMessage> (writable end owned by pm)
      │       ├─ Output: AsyncGenerator<SDKMessage> (typed events: assistant, partial-assistant,
      │       │         tool-progress, hook-progress, status, api-retry, result, ...)
      │       └─ canUseTool callback: in-process, awaits user via Telegram inline keyboard
      ├─ Telegram polling loop (grammy)               [unchanged]
      ├─ IPC server (Unix socket) for cron only       [approval hook removed]
      └─ SQLite                                        [unchanged schema]
```

**Invariants preserved (explicit acceptance tests in Phase 5 soak):**
1. One Node daemon per bot — separate launchd plists; shumabit crash
   cannot affect umi-assistant.
2. One Query per chat sessionKey — each chat's iterator runs in
   try/catch; a thrown error in chat A's iterator does not crash the
   whole daemon nor affect chat B's iterator.
3. The pendingQueue per session preserves FIFO correlation between
   user messages and `result` events — the SDK emits one `SDKResultMessage`
   per user message in the same order they were pushed.
4. Stream-event routing to head-pending only — same as today.

**Two architectural choices the spike (Phase 0) must validate before
Phase 1 begins:**

- **Long-lived Query vs per-turn Query.** The plan assumes ONE Query
  per sessionKey for the lifetime of the chat session, with multiple
  user messages pushed onto its input iterable. If the SDK doesn't
  support a long-lived input stream that stays open across many user
  turns, fall back to per-turn `query({resume: sessionId})`. The cost
  difference is significant: long-lived = one warm-up cost per chat;
  per-turn = warm-up per user message. **Phase 0 spike result decides
  Phase 1 architecture.**

- **`SDKAssistantMessage` (final) vs `SDKPartialAssistantMessage`
  (delta) for live preview.** Final-only kills the "preview-becomes-
  final" UX (one bubble at end of turn, no progress). Deltas need a
  proper accumulator (deltas are NOT cumulative, unlike stream-json's
  `assistant` events). **Phase 0 spike subscribes to both, picks the
  branch that preserves today's UX, commits to one accumulator design
  in `lib/process-manager.js`.**

**Loss inventory (regressions we accept):**
1. **pid-level SIGKILL.** SDK exposes `interrupt()` (graceful) and
   `close()` (terminates underlying process). For "kill stuck worker"
   use `Query.close()` — it tears down the subprocess. Hard SIGKILL is
   only available via the `Options.spawnClaudeCodeProcess` hook
   (sdk.d.ts:1777, public API) — we can keep a reference to the
   spawned proc if we ever need pid-level control. **Phase 0 task**:
   query the events table for SIGKILL paths in production data over
   the last 90 days — has the SIGTERM-then-SIGKILL escalation ever
   actually fired? If never, we drop the workaround entirely and rely
   on `interrupt()` + `close()`. If yes, we keep the spawn hook
   escape hatch documented as a private extension.
2. **Per-bot CLI binary version pinning.** Today: `CLAUDE_BIN` env
   per bot. SDK: pins one CLI version per SDK module. Mitigation: each
   polygram daemon is a separate launchd job and could pin a different
   `@anthropic-ai/claude-agent-sdk` version via its own `package.json`.
   We've never needed divergent binaries; flag this as a non-issue.
3. **Stream-json scraping ergonomics** — the typed event stream is
   strictly more useful, but folks debugging today's `tail -f
   /tmp/...stdout` will need to retrain on `kind:'event'` JSON logs.

**Things that DON'T change** (acceptance tests verify each):
- Bot-level + chat-level isolation invariants (above).
- All polygram features: streaming preview, chunked redelivery, voice
  transcription, sticker map (incl. 0.7.5 `[sticker:NAME]` fix), status
  reactions (incl. 0.7.4 stall timers, available_reactions probe,
  voice ack), /pair-code, /approvals, /status, /logs, IPC for cron,
  /split-db, /doctor, mark-replied lifecycle, boot-replay of
  dispatched-but-unfinished messages, abort grace window, link-preview
  opt-out, archived-bubble cleanup, reply_parameters.quote, queue
  overflow drop (0.7.6 H), turn_metrics insertion (0.7.6 F).
- Database schema (no changes).
- Telegram polling (grammy unchanged).
- IPC server for cron (`approval_request` op REMOVED in Phase 4; `send`
  op stays).

## 3. Pre-migration patches (land before Phase 0)

These are pure improvements that are useful regardless of the migration
and reduce the regression surface during the soak.

### 3.1 Port OpenClaw error classification to `lib/error-classify.js` (0.7.7)

**Why:** Polygram's current `errorReplyText` (polygram.js:845-869) matches 4
cases (idle / wall-clock / process-exit / error_during_execution). OpenClaw
classifies 429/402/auth/context-window/role-alternation/missing-tool-input
with bespoke user-facing messages (pi-embedded-helpers-CNhhELVT.js:5640-5766).

**Scope:**
- New `lib/error-classify.js` with regex tables per OpenClaw's
  `ERROR_PATTERNS` — adapted to our voice and emoji style.
- `errorReplyText` becomes a thin wrapper that consults the classifier.
- Tests covering each pattern with sample error strings.

**Why before migration:** The SDK migration changes the strings flowing
into errorReplyText (no more `Process exited (code 137)`). Doing the
classifier first means the migration only has to add new mappings, not
build the pattern infrastructure.

### 3.2 Transient HTTP retry (0.7.7)

**Why:** OpenClaw retries transient 5xx errors (500/502/503/521/522/
523/524/529) ONCE with a 2.5s delay before surfacing the error to the
user (`pi-embedded-helpers-CNhhELVT.js:5485-5535`,
`pi-embedded-Vt2x_Jl3.js:39210-39216`). Polygram has no retry today —
a transient 503 means the user retypes the message. Easy
ergonomics win that's independent of the SDK migration.

**Scope:**
- `lib/error-classify.js` exposes `isTransientHttpError(err)` returning
  true for the 5xx class above (matched on err.message regex, since
  SDK error strings carry HTTP status codes).
- pm's iteration loop catches transient classifications and retries
  the same user message once with 2.5s delay before pushing the user-
  facing reply. After retry exhaustion, surface the
  classifier-mapped error message.
- New `events.kind = 'transient-retry'` for telemetry.
- Tests: synthetic 503 → 2.5s delay → success; double 503 → after-
  retry user message.

**Why before migration:** the retry loop is symmetric across stream-
json and SDK transports. Land it once, port it forward.

### 3.3 (DELETED — was based on a misread)

v2's "STEER_RATE_LIMIT_MS = 2000 per session" claim was wrong.
OpenClaw's `STEER_RATE_LIMIT_MS` (pi-embedded-Vt2x_Jl3.js:35380) is
the **subagent-tool's** caller-to-target rate limit (preventing a
parent agent's tool calls from rapidly steering its subagent), NOT a
user-to-bot DM rate limit. Polygram's queue cap (0.7.6 H) is already
the correct analogue of OpenClaw's user-message queue handling
(`DEFAULT_QUEUE_CAP=20` in OpenClaw, 50 in polygram). No additional
rate-limit infrastructure is needed.

## 4. canUseTool: complete spec (replaces v1's one-liner)

The most error-prone part of the migration. v1's "drops bin/approval-hook.js
IPC" hides ~250 LOC of reimplementation across daemon-restart, dedup,
inline-keyboard, /stop semantics. Full spec:

### 4.1 Callback signature

```typescript
canUseTool(toolName, input, {
  signal,           // AbortSignal — abort if SDK cancels (e.g. interrupt())
  suggestions,      // pre-computed PermissionUpdates from CLI
  blockedPath,      // for filesystem tools
  decisionReason,   // CLI's reason for invoking us
  title,            // pre-rendered "Claude wants to read X" — pass through to user
  displayName,      // tool display name
  description,      // longer description
  toolUseID,        // stable per-call ID — USE THIS as dedup key
  agentID,          // present if invoked from a subagent
}) → Promise<PermissionResult>

PermissionResult:
  | { behavior: 'allow'; updatedInput?; updatedPermissions?: [...]; toolUseID? }
  | { behavior: 'deny'; message: string; interrupt?: boolean; toolUseID? }
```

### 4.2 Daemon flow

```
canUseTool(name, input, opts) →
  1. Check config.bot.approvals.gatedTools — if not gated, allow immediately.
  2. Compute dedup key: hash(opts.toolUseID + name + canonicalize(input))
     — opts.toolUseID is stable across CLI retries of the same call.
  3. Check approvals store for an existing decision (always-allow / always-deny
     persisted from a previous turn): if found, return that decision.
  4. db.insertPendingApproval({ chat_id, tool_use_id, name, input_digest,
                                 status: 'pending', issued_ts: now }).
  5. Post inline-keyboard card to admin chat (Allow / Deny / Always allow / Always deny).
  6. Park resolver in approvalWaiters Map keyed by tool_use_id.
  7. Race: opts.signal.aborted | timeout (configurable, default 60s) | resolver.
  8. On user click → callback_query → handleApprovalCallback updates DB row,
     resolves the parked Promise with the decision.
  9. On daemon restart mid-await: see §4.4 below.
 10. Edit the inline-keyboard card with the resolution.
 11. Return PermissionResult.
     - behavior:'allow' (one-time): just allow.
     - behavior:'allow' + updatedPermissions:[{type:'addRules', ...}]: also tell
       SDK to remember "this tool from this chat is allowed forever" — this is
       the new "always allow" UX. (PermissionUpdate `type` values are
       `'addRules'\|'replaceRules'\|'removeRules'\|'setMode'\|'addDirectories'\|
       'removeDirectories'` — sdk.d.ts:1849. v2 wrote 'addRule' singular; wrong.)
       Bonus: PermissionResult also has `decisionClassification`:
       `'user_temporary'\|'user_permanent'\|'user_reject'` — feed this into
       turn_metrics for approval-flow telemetry.
     - behavior:'deny' + interrupt:true: deny AND abort the current turn.
       Used when user picks "deny + stop".
```

### 4.3 Dedup contract

`opts.toolUseID` is the SDK's stable identifier for this exact tool call
(across retries). Use it as the primary dedup key. Hash of `name +
canonicalize(input)` is the secondary key for the case where the SDK
rotates toolUseIDs across retries (verify in Phase 0).

### 4.4 Daemon restart during await

**Scenario:** canUseTool returns a Promise that's parked waiting for the
user's button click. The polygram daemon is restarted (deploy, crash,
launchctl kickstart). The Promise dies with the daemon. The user clicks
Approve, but there's nothing to wake.

**Today's flow handles this** because the approval hook is an
independent subprocess of `claude`, not of polygram. Daemon restart
doesn't touch it.

**Under SDK** the canUseTool callback runs IN polygram's event loop.
Restart kills it.

**Mitigation for 0.8.0:**
1. On user click after restart: `handleApprovalCallback` UPDATEs the
   `pending_approvals` row with the decision but finds no in-memory
   resolver. We log this. The SDK turn that originated this call has
   already been killed by the daemon restart; the next time the user
   retries the original message, the approval persists in the DB and
   `canUseTool` short-circuits (step 3 above).
2. **Phase 0 spike adds a test** for "approve after restart resumes the
   original turn cleanly via persisted approval." If it doesn't work
   smoothly, escalate to a deferred 0.8.x patch (e.g. resume-on-boot
   re-sends the original prompt).

This is a regression vs today: today the approval survives polygram
restart because the hook is independent. Calling this out explicitly so
it doesn't surprise us in soak.

### 4.5 Cancellation on `/stop`

When user types "стоп" mid-canUseTool-await:
1. polygram detects via abort-detector.js, calls
   `pm.interrupt(sessionKey)`.
2. SDK fires `opts.signal.aborted = true` on the in-flight canUseTool.
3. Our race in step 7 resolves on signal → return
   `{behavior:'deny', message:'aborted', interrupt:false}`.
4. SDK's interrupt cleanup runs.
5. polygram updates the approval card to "(stopped)".

### 4.6 Tests

- canUseTool resolves on user click, approval card updates.
- canUseTool resolves on signal abort (returns deny+aborted).
- canUseTool resolves on timeout (returns deny+timeout).
- Persistent always-allow short-circuits (step 3) without prompting.
- Restart-during-await is documented; persisted DB row stays for next turn.
- Two concurrent canUseTool calls for different toolUseIDs each get their
  own card.

## 5. Compaction observability

SDK auto-compacts but emits `SDKCompactBoundaryMessage` (sdk.d.ts:2356-
2375) AND fires `PreCompact`/`PostCompact` hooks. **Phase 0 gate 8
verifies which path provides the more useful payload** (the boundary
message is in the message stream; the hooks are settings.json-driven
externally). **Phase 2 wires whichever pm picks:**

```typescript
// In pm's iteration loop:

  // Field path is NESTED — v2 had this wrong.

  //     subtype: 'compact_boundary',
  //     compact_metadata?: {
  //       trigger?: 'manual' | 'auto',
  //       pre_tokens?: number,        // snake_case, optional
  //       post_tokens?: number,       // snake_case, optional
  //       duration_ms?: number,
  //     }
  //   }
  this._logEvent('compact-boundary', {
    session_key: sessionKey,
    trigger: msg.compact_metadata?.trigger ?? null,
    pre_tokens: msg.compact_metadata?.pre_tokens ?? null,
    post_tokens: msg.compact_metadata?.post_tokens ?? null,
    duration_ms: msg.compact_metadata?.duration_ms ?? null,
  });
  if (this.onCompactBoundary) this.onCompactBoundary(sessionKey, msg);
  break;
```

**OpenClaw note:** OpenClaw doesn't show users a per-category context

### 6.5.3. `lib/approval-waiters.js` (B3)

```js
// New helper module owning the parked-Promise Map. Extracted from
// polygram.js so canUseTool tests can verify lifecycle without
// spinning up the full daemon.

function createApprovalWaiters({ logger = console } = {}) {
  const waiters = new Map();           // tool_use_id → { resolve, reject, signalCleanup, parkedAt }
  const MAX_WAITERS = 200;             // hard memory bound; reject new park if exceeded

  function park(toolUseId, signal) {
    if (waiters.size >= MAX_WAITERS) {
      throw Object.assign(new Error('approval waiter cap exceeded'),
                          { code: 'WAITER_CAP' });
    }
    return new Promise((resolve, reject) => {
      const signalCleanup = () => reject(Object.assign(new Error('aborted'), { code: 'ABORTED' }));
      signal?.addEventListener('abort', signalCleanup, { once: true });
      waiters.set(toolUseId, {
        resolve: (decision) => {
          signal?.removeEventListener('abort', signalCleanup);
          waiters.delete(toolUseId);
          resolve(decision);
        },
        reject: (err) => {
          signal?.removeEventListener('abort', signalCleanup);
          waiters.delete(toolUseId);
          reject(err);
        },
        signalCleanup,
        parkedAt: Date.now(),
      });
    });
  }

  // Five cleanup paths (audit B3):
  //   1. resolveByClick(id, decision)         — user pressed inline-keyboard button
  //   2. signal abort (passed at park())      — SDK called Query.interrupt() / Query.close()
  //   3. timeoutSweeper                       — periodic sweep, reject any waiter parked > timeoutMs
  //   4. resetSession                         — when pm.resetSession fires, all waiters for that session abort
  //   5. shutdown                             — daemon SIGTERM; reject all with code 'DAEMON_SHUTDOWN'
  function resolveByClick(toolUseId, decision) { waiters.get(toolUseId)?.resolve(decision); }
  function startTimeoutSweeper(timeoutMs = 60_000, intervalMs = 5_000) { /* ... */ }
  function rejectAllForSession(sessionKey, prefix) { /* iterate, reject those matching */ }
  function rejectAll(code = 'DAEMON_SHUTDOWN') { /* iterate, reject all */ }

  return {
    park,
    resolveByClick,
    rejectAllForSession,
    rejectAll,
    startTimeoutSweeper,
    get size() { return waiters.size; },
  };
}
```

```js
// Production-critical fallback if Phase 0 gate 15 reveals SDK has

const fs = require('fs');
const path = require('path');

// Cache: agentName → resolved AgentBundle (avoids re-reading on
// every send). Invalidate on SIGHUP if needed.
const cache = new Map();

async function loadAgent(agentName, { homeDir = process.env.HOME, logger = console } = {}) {
  if (cache.has(agentName)) return cache.get(agentName);
  const agentDir = path.join(homeDir, '.claude', 'agents', agentName);
  if (!fs.existsSync(agentDir)) {
    throw Object.assign(new Error(`agent not found: ${agentName}`),
                        { code: 'AGENT_NOT_FOUND' });
  }
  const settingsPath = path.join(agentDir, 'settings.json');
  const settings = fs.existsSync(settingsPath)
    ? JSON.parse(fs.readFileSync(settingsPath, 'utf8'))
    : {};
  // Read agent-level CLAUDE.md if present (system prompt)
  const claudeMdPath = path.join(agentDir, 'CLAUDE.md');
  const systemPrompt = fs.existsSync(claudeMdPath)
    ? fs.readFileSync(claudeMdPath, 'utf8')
    : null;
  // Skills: enumerate <agent>/skills/* directories
  const skillsDir = path.join(agentDir, 'skills');
  const skills = fs.existsSync(skillsDir)
    ? fs.readdirSync(skillsDir).filter(d =>
        fs.statSync(path.join(skillsDir, d)).isDirectory())
    : [];
  // MCP servers from settings.json
  const mcpServers = settings.mcpServers ?? {};
  const bundle = { agentName, systemPrompt, skills, mcpServers, raw: settings };
  cache.set(agentName, bundle);
  return bundle;
}

    ...(agentBundle?.skills?.length && { skills: agentBundle.skills }),
    ...(agentBundle?.mcpServers && { mcpServers: agentBundle.mcpServers }),
    ...chatConfig,                         // chat overrides win
  };
}
```

## 6.6. Ship-breaker mitigations (17 concrete commitments)

The 3rd-round adversarial audit found 17 HIGH/MEDIUM risks v3
hand-waved with "verify in spike." This section commits each to a
concrete code path so engineers don't re-discover them.

### In-process ordering races (7 commitments)

**H1 — write-before-send order in pm callbacks.** All polygram
callbacks fired by pm (onResult, onClose, onStreamChunk, onToolUse,
onAssistantMessageStart, onCompactBoundary, onQueueDrop) MUST
internally `await dbWrite(...)` BEFORE calling any Telegram API.
Pattern: `await dbWrite(() => db.setHandlerStatus(...), label); await
tg(bot, 'sendMessage', ...);`. **Test:** synthetic onResult with
mock dbWrite that resolves after a delay; assert tg() was not called
until dbWrite resolved.

**H2/H3/H4 — canUseTool / click / signal / Query.close races.** The
approval-waiters Map (§6.5.3) holds a single `signalCleanup` closure
per parked Promise. On `resolveByClick`, `signalCleanup` is removed
from the AbortSignal listener BEFORE resolve, so a late signal
abort cannot race with the click resolution. Tests:
(a) click then signal → click wins, signal is no-op;
(b) signal then click → signal wins (deny+aborted), click silent;
(c) Query.close() during await → signal fires via SDK, waiter
   rejects with `ABORTED`;
(d) resetSession during await → `rejectAllForSession` rejects
   waiter with `RESET_SESSION`.

**H8 — compact-boundary mid-turn races onAssistantMessageStart.**
Already mitigated by Phase 1 step 6's "sequencing guarantee" —
events dispatched strictly via `await` between iterator ticks.
Test included: synthetic `assistant(id=A) → compact_boundary →
assistant(id=B)` sequence asserts B's chunks land in a different
bubble than A's, and "memory compacted" message appears between.

**H10 — in-flight 401 mid-turn.** When pm sees per-message
`SDKAssistantMessage.error === 'authentication_failed'`:
1. Reject the in-flight pending immediately with
   `Error('auth-expired')` (classifier maps to user-visible 🔑
   message).
2. Call `Query.interrupt()` to cancel the SDK turn.
3. `pm.drainQueue(sessionKey, 'auth-expired')` — every queued
   pending also gets the 🔑 message.
4. Emit the 5-behaviour auth-expired UX (Phase 0 gate 25):
   `auth-expired` event, pause new-turn dispatch (`pm.pauseBot()`
   sets a flag `getOrSpawn` and `send` check), admin-chat post via
   `tg(bot, 'sendMessage', { chat_id: config.bot.adminChatId, ... })`,
   user reply via the classifier message, doctor.js alarm path.
5. Un-pause is manual (operator runs `claude /login`, then
   `polygram-doctor --resume-bot=BOT_NAME` clears the flag).

**H15 — getContextUsage warning races /new.** The 85%-context-full
hint posts via `await onCompactBoundaryAck` THEN checks
`getContextUsage()`. If a `/new` was processed in the same iteration
tick, `entry.resetting === true` (set by pm.resetSession step 1) —
the hint is suppressed. Test: synthetic /new + immediate end-of-
turn → no hint posts.

**H17 — inFlightHandlers counter sync.** The pm.send Promise
ALWAYS resolves or rejects in finite time. Five rejection paths:
(a) result event with non-success subtype, (b) iterator throw, (c)
Query.close(), (d) interrupt, (e) idle/wall-clock timeout, (f)
QUEUE_OVERFLOW drop. Each is wired in pm to call
`pending.reject(err)`. Test: synthetic iterator throw → pm.send
rejects within event-loop tick → polygram handler's `try/finally`
decrements inFlightHandlers.

### Cross-version / cross-bot cutover (5 commitments)

**H5/M5 — mid-deploy SDK upgrade or 0.7.7→0.8.0 transition.** Boot
sequence (polygram.js main(), in this order):
1. Run migrations (010 included).
2. **Sweep stale 0.7.x callback cards**:
   `UPDATE pending_approvals SET status = 'expired' WHERE status =
   'pending' AND issued_ts < (boot_ts - 60_000)`. Edit each card's
   text to "(stopped — daemon restart)" and remove inline-keyboard
   via tg.editMessageReplyMarkup. (Cards from THIS boot — issued_ts
   ≥ boot_ts - 60s — are still live.)
3. **Sweep stale `claude_session_id`**: per Phase 0 gate 26-27,
   if pre-0.8.0 JSONLs are unreadable, mark all
   `sessions.claude_session_id` rows as stale on first 0.8.0 boot.
   Subsequent boot replays start fresh sessions. **Decision goes
   into Phase C** based on gate 27 result.
4. Boot replay continues per polygram.js:2887-2965 (no schema
   change).

**H7 — settings.local.json cross-bot leakage.** Each polygram bot
runs as the same OS user (shumabit). Without explicit isolation,
all bots load the same `~/.claude/settings.local.json`. Decision:
**explicitly omit `settingSources: ['user', 'project']`** in

### Tail-risk shutdown / liveness (3 commitments)

**H6 — killChat Promise.all hangs.** Already mitigated in Phase 1
step 3 seam-F clarification: per-Query `Promise.race` against 5s
timeout, `Promise.allSettled` to prevent one slow Query from

### Other ship-breaker fixes (2 commitments)

**M1 — `applyFlagSettings({effortLevel})` mid-tool semantic.** Phase
0 gate 19 explicitly tests two cases:
(a) `/effort high` mid-tool — does the tool's next thinking step
    use the new effort?
(b) `/effort high` between turns — applies cleanly to the next user
    turn?
Polygram contract: only support case (b). Defer the call until
`pendingQueue.length === 0`; queue a pending flag-change op.

**M2 — `transient-retry` mid-turn idempotency.** Pm only retries if
the failing turn produced ZERO assistant messages (no tools ran).
Tracked via `entry.firstAssistantSeen` flag, set on first
`SDKAssistantMessage`. After flag set, transient errors fall
through to the user without retry. Test: synthetic 503 after one
tool_use → no retry; synthetic 503 before any model response →
retry once.

**Seam F clarification (`pm.killChat` semantics):** `killChat(chatId)`
fires on Telegram chat→supergroup migration (polygram.js:2517). Three
sub-cases per the audit:
- Idle entries (no in-flight pending): `Query.close()` directly.
- In-flight entries with pending tool_use: prefer
  `Query.interrupt() → wait 1s → Query.close()` so the SDK can flush
  any pending tool_result back to its session JSONL before tear-down.
  Avoids the "dangling tool_use on resume" failure mode flagged by
  gate 7. (Resume is impossible after killChat — the new chatId has
  a new session — but the JSONL is still on disk and may matter for
  forensics.)
- Stuck entries (Query.close hangs >5s): `evict-close-timeout` event,
  orphan and continue. Don't await indefinitely (ship-breaker H6
  mitigation).
- Whole `killChat` wraps each per-session close in a `Promise.race`
  against a 5s timeout, then `Promise.allSettled` (NOT `Promise.all`)
  so one slow Query doesn't deadlock the others. Single supergroup
  migration completes in ≤ N×5s worst case (N = matching sessionKeys).

21. `extractAssistantText` and `sumUsage` exports — used by tests
    (tests/stream-reply.test.js:10). KEEP exported, rewire to consume
    `SDKAssistantMessage` shape. Don't drop the helpers.
22. `chat_migrations` table — Telegram group-to-supergroup migration

    user-visible regressions.

    🔥 / 👍 / 🤯 / 🥱 / 😨). Don't drift.
25. **`stdinLock` per-session ordering invariant** (polygram.js:798,
    964 + lib/async-lock): per-session lock around stdin writes. Today
    proven load-bearing — without it 3 messages produced 2 results
    (polygram.js:782-797 doc comment). Under SDK preserved via Phase 0
    gate 40. If the SDK has the same batching hazard, the lock moves
    INTO pm; if not, the lock can be dropped.

    onResult/onClose hooks, so the counter increments/decrements

    don't drift, don't add, don't remove without explicit decision.

## 9. Explicit non-goals (out of scope for 0.8.0)

To keep regression surface small:

- ❌ Migration to SDK's pluggable `sessionStore` (it's `@alpha`).
- ❌ OAuth-in-process refresh (`claudeAuthenticate*` is private).
- ❌ Subagent multi-process spawn (`sessions_spawn` from OpenClaw).
- ❌ Multi-provider (we're Anthropic-only forever).
- ❌ Removing `claude` CLI dep (SDK still spawns it).
- ❌ One Node worker per chat (overkill given current isolation
  invariants).
- ❌ Anything not in the in-scope phases above.

These are deferred to 0.8.x or wontfix. **No "we might add this in 0.8.0
if there's time" — that's how regressions creep in.**
