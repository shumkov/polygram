# 0.13 — Autosteer-fold silent drop (`input-fold-suspected`) — DESIGN (review-corrected)

> **Status: design v2, post multi-persona review (2026-06-13).** v1 proposed a
> "Stop-gated autosteer completion" mechanism. **A 4-persona review (feasibility,
> adversarial, coherence, scope) unanimously rejected it** — it was A1-redux. This v2
> records why, the production data that reframes the problem, and the proportionate fix.
> **Severity:** partner-facing but LOW-volume (~1 genuine drop / 3 days). Found on
> Shumabit@UMI/37 (the "Telnyx ignored" report).

## Why v1 (Stop-gate) was rejected — keep, so we don't repeat it

1. **Infeasible primitive (fatal).** v1 needed the daemon to make the claude-CLI **Stop
   hook return `{decision:"block"}`** on live ledger state. The CLI Stop hook is
   `lib/process/polygram-hook-append.js` — a fire-and-forget ndjson appender ("Stdout:
   nothing, observe-only"). The daemon *reads* hook events off a file tail with **250 ms–5 s
   lag** (`cli-process.js:1697`); there is **no return channel**. The proven `{continue:false}`
   primitive (`scripts/spikes/hookstop.mjs`) is **SDK in-process-callback only** — it does
   not exist on the CLI/channels backend shumabit runs. This is the same failure shape as the
   rejected A1 heuristic (assume a CLI capability because it exists on SDK/conceptually).
2. **Base-rate inversion returns.** The gate would fire predominantly on *already-folded*
   (answered) entries and re-prompt claude → double-answer the common case — the exact thing
   that killed A1. "Claude self-disambiguates with context" is model-dependent, and the prior
   brief rejected A3 *for* model-dependence.
3. **Contradicts D2.** The existing 0.13 input-ledger D2 design **deliberately parks
   `fold-suspected` (telemetry-only, no redeliver)** to avoid that inversion, and has a
   runtime echo-anomaly guard (Q-B). v1 treated the parked state as a blockable bug.
4. **Finalizer-ladder conflict + load amplification + scope** (see review notes).

## Production data that reframes the problem (the measurement v1 skipped)

Of the 15 `input-fold-suspected` entries in the trailing window (shumabit), read fold-vs-drop
by whether the **next outbound reply addressed the message**:

| split | count | examples |
|---|---|---|
| **genuine FOLD** (answered, just not echoed) | **~14 (93%)** | 3057 "asterisk vs alt"→"Depends on the country…"; 3011 "also Indonesian?"→"Telnyx DOES offer…"; 2741 "move it in calendar"→"All moved ✅"; 2719, 2709, 2700, 2954, 2960… |
| **genuine DROP** (ignored) | **1 (7%)** | 3034 "If we take Telnyx…" → next reply was about n8n (unrelated) |

**Conclusions:**
- `fold-suspected` is **mostly correct parking** — in ~93% the user *got their answer*; the
  only defect is the missing `consumed_turn_ids` echo (cosmetic — telemetry shows a false
  "suspected" signal, but no user harm).
- **Genuine drops are ~1 per 3 days.** Low urgency.
- **Blind redelivery of `fold-suspected` is wrong** (would double-answer the 93%). This also
  kills the scope-reviewer's "redeliver fold-suspected" fallback — it only works if the bucket
  is mostly drops, and it is the opposite.

## Recommended fix — strengthen the `consumed_turn_ids` contract (proportionate, feasible)

The root mechanism is sound; the only failure is **claude folds (answers) without echoing
`consumed_turn_ids` ~8% of cycles.** Make the echo reliable and the EXISTING machinery handles
everything correctly:

- **Fold** → claude echoes `consumed_turn_ids` → `_ledgerAckConsumed` → entry `resolved`
  (no parking, no false `fold-suspected`).
- **Drop** → contract observed for the cycle but this entry unacked → `_dropConfirmFire`
  declares **`input-dropped` → redeliver** (the path that ALREADY ships and already works for
  the 92% of cycles).

So strengthening contract adherence shrinks the ambiguous `fold-suspected` bucket toward zero
and routes the rare genuine drop into the existing redeliver path. **No new Stop-gate, no new
primitive, no redelivery-of-folds, no D2 contradiction.**

### Implementation (minimal)
1. **Tighten the contract instruction** where it's authored:
   `lib/process/channels-bridge.mjs` (~308: "ALWAYS set consumed_turn_ids to the turn_id of
   EVERY <channel> message this reply covers") and the system-prompt hint. Make it imperative,
   with a one-line example, and emphasize it applies *even to short/quick replies* (the likely
   miss case). Low risk — a prompt change, no lifecycle changes.
2. **(Optional, only if step 1 underperforms) a runtime nudge:** when a `reply` lands while
   pending autosteered turn_ids exist and the reply omits `consumed_turn_ids`, emit a
   diagnostic event (`consumed-ack-omitted`) — *measure*, don't auto-act. Feeds the soak.
3. **Nothing else.** Genuine drops continue to flow through the existing
   `input-dropped → redeliverAsFreshTurn` path. (Extracting `redeliverAsFreshTurn` into a
   shared module from `lib/handlers/edit-redelivery.js` remains good hygiene but is independent.)

### Measure first (the order the review demanded)
1. Baseline the **contract-miss rate**: cycles with ≥1 autosteered entry where the cycle's
   reply omitted `consumed_turn_ids` ÷ all such cycles (currently ~8%).
2. Ship step 1 (prompt tighten) to shumorobot/shumabit. Soak 5–7 days.
3. Re-measure. Target: miss rate < 2% → `input-fold-suspected` volume falls toward the genuine-
   drop floor (~1/3d), and those route to `input-dropped → redeliver`.
4. Only if the miss rate stays high AND genuine drops rise materially: revisit a heavier
   mechanism — and *first* prove a real CLI force-continue primitive with a spike (v1's
   open-decision #4, as a gate not a footnote). Do NOT build on the assumption it exists.

## Test plan
- `tests/channels-bridge*.test.js` / prompt-assembly tests: the tightened contract instruction
  is present in the assembled channels system prompt.
- `tests/cli-process-input-ledger.test.js`: existing behavior preserved — a reply WITH
  `consumed_turn_ids` resolves the entry (`cli-input-acked`), a contract-observed cycle with an
  unacked entry still emits `input-dropped` → redeliver. (These already exist; assert no
  regression.) No new red→green is needed for step 1 beyond the prompt-presence assertion,
  because step 1 changes *claude's compliance*, not polygram logic — its effect is measured in
  prod, not unit-tested.

## Open decisions for sign-off
1. **Do we even act now?** Genuine drops are ~1/3d and `fold-suspected` parking is mostly
   harmless. Legitimate to (a) ship the cheap prompt tighten + measure, or (b) accept the
   current behavior as the documented known-limitation (the prod watcher already flags
   recurrence) and revisit only if drops trend up. Recommend (a) — it's nearly free.
2. **Prompt wording** for the contract tighten — draft + a reviewer pass before shipping.

## Rollout
shumorobot/shumabit first → umi-assistant LAST (partner-customer; per the deploy rollout rule).
Soak metric: contract-miss rate ↓, `input-fold-suspected` ↓ toward the genuine-drop floor,
`input-dropped`/`redelivered-as-fresh-turn` correctly catching the rare real drop, zero
double-answer reports.
