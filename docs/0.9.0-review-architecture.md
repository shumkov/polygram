# Polygram 0.9.0 Cleanup — Architecture Review

> Branch: `0.9.0-cleanup` @ HEAD f4649d0
> Base: `0.8.0-spike` (rc.68 tree)
> Net: 18 files, +307 / −3226
> Reviewer: architecture-strategist (focus: interface coherence, layering, forward-compat)

## TL;DR

The cleanup is structurally sound: all the dead conditional branches
(`isSdkFor`, `pickFor`, `requestRespawn`) were inlined correctly, the
router collapsed cleanly to a single-pm pass-through, and the SDK pm
remains the only impl behind the same `Pm` interface. Boot sequence
in `main()` is unchanged in shape — `createPmRouter({ pm: sdkPm })`
still sits at the same layering seam (lib/process-manager-sdk.js:992
→ lib/pm-router.js:35), no god-function emerged.

The risks that landed are not in what was deleted but in two adjacent
issues: (1) the SDK pm's internals (`entry.inputController`,
`entry.pendingQueue`, `entry.query`) leak into polygram.js at four
sites — these existed pre-cleanup but the deletion of the dual-pm
abstraction makes the leakage more visible because there's nothing
forcing discipline anymore; (2) several CLI-pm-era artifacts
(`onRespawn` callback, `entry.needsRespawn` field, stale JSDoc on the
canonical interface) survived the cleanup and should be swept before
0.9.0 cuts.

The "router stays for forward-compat" claim from the plan holds, but
only weakly — see LOW-2.

## MEDIUM

### MEDIUM-1 — `onRespawn` callback wired but never fires

**Files**: `polygram.js:3971-3987`, `lib/process-manager-sdk.js`
(no occurrences)

`pmOpts.onRespawn` is registered in polygram.js at boot:

```js
onRespawn: (sessionKey, reason, entry, wasDrained) => {
  if (!wasDrained) return;
  ...
  tg(bot, 'sendMessage', { chat_id, text: '✓ Using <model> now.' ... })
}
```

But `lib/process-manager-sdk.js`'s constructor (lines 180-228) never
reads `onRespawn`, never stores it on `this`, and the file has zero
references to the name. The SDK pm applies model/effort changes via
`setModel` / `applyFlagSettings` directly on the live Query — there
is no respawn event to fire on.

This is leftover plumbing from the CLI pm era (where `requestRespawn`
triggered a subprocess kill+respawn whose completion would fire
`onRespawn` to confirm). Commit 1 deleted `requestRespawn` call
sites and the interface field, but missed the corresponding
callback registration on the consumer side.

**Why it matters**: silent dead code that survives a `git grep` for
"respawn" reads as live wiring. A future maintainer touching the
`/model` or `/effort` flow will reasonably believe the user-facing
"✓ Using sonnet now" confirmation message comes from this callback —
it does not. The actual confirmation comes from inline reactor /
toast updates inside the callback handler around polygram.js:1818.
Anyone trying to "fix the missing confirmation" will edit dead code.

**Recommendation**: drop `onRespawn` from `pmOpts` (just the 17-line
block at polygram.js:3971-3987). Either as a follow-up commit on
this branch before 0.9.0 cuts, or call it out in the architecture-
review-fix commit.

### MEDIUM-2 — `entry.needsRespawn` field unreachable but still gated

**File**: `lib/process-manager-sdk.js:333, 640-642`

```js
// _spawnEntry, line 333:
needsRespawn: null,
...
// send(), line 640:
if (entry.needsRespawn) {
  return reject(new Error(`Session awaiting respawn (${entry.needsRespawn})`));
}
```

`entry.needsRespawn` is initialized to `null` and read in `send()`,
but no code path in the file (or anywhere in lib/, polygram.js, or
tests/) ever assigns to it. Dead branch. Carryover from the CLI pm
where `requestRespawn` set this flag.

**Why it matters**: it's a defensive guard against a state that
cannot be reached, which means the test suite can't cover it (no
trigger), which means a future change that does set the field would
land without test coverage of the guard path.

**Recommendation**: delete the field initialization (line 333) and
the gate (lines 640-642) together. 5-line change.

### MEDIUM-3 — `Pm` interface JSDoc still describes the dual-pm world

**File**: `lib/pm-interface.js:1-12, 53-56`

The canonical contract document still reads:

```js
/**
 * Canonical Pm interface (JSDoc typedef).
 *
 * Both `lib/process-manager.js` (CLI pm) and `lib/process-manager-sdk.js`
 * (SDK pm) implement this. `lib/pm-router.js`'s `createPmRouter()`
 * forwards calls to one or the other based on per-chat policy.
 *
 * Optional methods are marked `?` — the router exposes them too but
 * returns documented sentinels when the routed pm doesn't implement
 * them. Sites that need to feature-detect should call
 * `pm.pickFor(sessionKey)` and probe `typeof X === 'function'` on
 * the returned pm instance, not on the router.
 */
```

After commit 6, `lib/process-manager.js` does not exist. After
commit 3, `pm.pickFor` does not exist. After commit 4, the router
does not "forward calls based on per-chat policy" — it returns the
pm verbatim.

The `@typedef` annotations are fine; only the prose header is stale.

Lower-blast-radius than MEDIUM-1/2 because it's documentation-only,
but it's the *canonical* documentation — a new contributor lands
here first to understand the pm contract, gets a wrong mental model,
debugs around a router that no longer routes, then has to discover
the truth from `git log`.

**Recommendation**: rewrite the prose header to reflect the
post-cleanup reality. Something like: "Implemented by
`lib/process-manager-sdk.js`. Future alternate pms slot in behind
`lib/pm-router.js`'s `createPmRouter` factory." Keep the @typedef
typedefs as-is. Also drop the "Optional (only one of the two pms
implements these — feature-detect)" wording at lines 68 — there is
only one pm, the optional methods are simply optional on the
contract.

### MEDIUM-4 — Stale doc and dead `spawn` import in polygram.js header

**File**: `polygram.js:1-17, 20`

The file header still describes the architecture as:

```js
 * Each chat gets a persistent claude process (stream-json multi-turn).
 * Process stays warm: no cold start, full prompt caching.
 *
 * Architecture:
 *   Telegram (grammy long-poll) → polygram receives message
 *   ...
 *   → sends to persistent claude process via stdin (stream-json)
 *   → reads response from stdout (stream-json)
```

Post-cleanup, no claude subprocess is spawned and no stream-json
parsing happens at the polygram layer — it's all `query()` calls
from `@anthropic-ai/claude-agent-sdk`. Line 20:

```js
const { spawn } = require('child_process');
```

`spawn` has zero call sites in polygram.js post-cleanup (verified:
no `spawn(` matches in the file). Dead import.

This is the same class of issue as MEDIUM-3 — orientation
documentation that's now misleading — but at the entrypoint where
every contributor lands.

**Recommendation**: rewrite the header (one paragraph: "SDK Query
per chat, in-process tool approval via canUseTool") and drop the
`spawn` import. 8 lines total.

## LOW

### LOW-1 — SDK pm internals leak into polygram.js at 4 sites (pre-existing, exposed by cleanup)

**Files**:
- `polygram.js:2061, 2070` — `/compact` handler reads `entry.inputController.push`
- `polygram.js:2799-2807` — context-full hint reads `entry.query.getContextUsage`
- `polygram.js:4264, 4267` — boot-replay orphan recovery reads `entry.inputController.push`
- `polygram.js:3782, 3795, 3828` — pm event callbacks read `entry.pendingQueue[0]`

The `Pm` interface (lib/pm-interface.js:14-23) documents `PmEntry`
as `{ sessionKey, chatId, threadId, closed, inFlight, pendingQueue }`
— so `pendingQueue` access is contract-sanctioned (the three
callback sites at 3782/3795/3828 are fine). But `entry.inputController`
and `entry.query` are SDK-pm-specific implementation details, not
part of the contract.

This leakage existed pre-cleanup — the `/compact` push and the
context-hint readout were both added during 0.8.x development with
the SDK pm assumption baked in. The CLI pm in 0.8.x didn't expose
`inputController` or `query`, so these sites were never reachable
under CLI pm — they were silently SDK-only paths.

**Why the cleanup makes this worse, even though it changed nothing
about these sites**: pre-cleanup, the fact that the `Pm` interface
documented a "this is optional, one pm has it" contract was the
implicit signal that some methods could be feature-detected. With
the dual-pm narrative gone, the four direct-attribute-access sites
look like first-class API use even though they're reaching past the
interface. A future "alternate pm impl" (per the plan's stated
forward-compat motivation) would have to either fake-implement the
SDK's exact `inputController` shape or break these four sites.

**Recommendation** (not blocking 0.9.0):
1. For `/compact` and orphan-replay (the two `inputController.push`
   sites): hoist the `push slash-command` semantic onto the `Pm`
   interface as `pm.pushUserMessage(sessionKey, text)` — analogous
   to `injectUserMessage` but without the priority-hint
   complications.
2. For `getContextUsage`: hoist as `pm.getContextUsage(sessionKey)`
   — interface returns `{ percent, tokensUsed, ... } | null` for
   pms that don't support it.

Both of these are 5-10 line additions on the SDK pm, plus interface
JSDoc. They convert "polygram.js reaches past the pm" into "pm
exposes a documented method that polygram.js calls."

If the team accepts that the SDK pm is forever the only pm and the
forward-compat seam is theatre, these aren't worth doing. But the
plan explicitly justifies keeping the router for forward-compat —
which means the leaks should be fixed too, or the forward-compat
claim should be retracted.

### LOW-2 — Router is now thin enough to be ceremony, not architecture

**File**: `lib/pm-router.js:35-38`

```js
function createPmRouter({ pm } = {}) {
  if (!pm) throw new TypeError('pm required');
  return pm;
}
```

This is `(x) => x` with a null-check. The plan justifies keeping it
as a "forward-compatible seam." That's defensible if a future
alternate pm impl is realistic — but consider:

1. The `Pm` interface is now narrow (single impl, JSDoc-only). When
   a second pm arrives, the contract will need re-validation
   anyway because the SDK pm has shaped the interface to its own
   conveniences (e.g. `applyFlagSettings`, `interrupt`, `setModel`
   are all `Query.*` passthroughs).
2. The four leakage sites (LOW-1) are NOT routed through the
   router today — they grab `entry.inputController` etc directly.
   Adding a second pm requires fixing those leaks first; the
   router-stays decision doesn't help.
3. The router has no per-call logic (no logging, no metrics, no
   feature-flag guard). It exists only to provide an import name
   for polygram.js to call.

**This isn't a bug** — the router's cost is one require + one
function call per boot. But the architectural justification is
weak: the *interface* (lib/pm-interface.js) is the seam, the
*router file* is just an import indirection. A future contributor
asking "why does this file exist?" gets a less convincing answer
post-cleanup than the plan suggests.

**Recommendation** (not blocking): either accept this and tighten
the lib/pm-router.js header comment to "this is currently a
no-op factory, kept for the import-name seam"; or, when the
second pm arrives, decide *then* whether the router is the right
place to put the dispatch. The current state is fine — flagging
because the plan's "Why router stays" rationale (lines 153-156 of
0.9.0-cleanup-plan.md) overpromises.

### LOW-3 — Plan's commit 5 was silently merged into commit 4

**Files**: docs/0.9.0-cleanup-plan.md:101-108 (plan), commit 783c244

The plan listed commit 5 as a separate "Drop POLYGRAM_USE_SDK /
POLYGRAM_SDK_CHATS env vars" commit. The branch has commits
1-4 + 6-8 but no commit 5. Inspection shows the env-var deletion
landed inside commit 4 (the router collapse). Both kinds of dead
code (env-vars + dual-pm router) being deleted together is
defensible — they're tightly coupled — but the plan said
"each commit must keep the test suite green" and "commit per
logical change."

Logical-merge-into-commit-4 isn't wrong, but the plan should reflect
reality. Either:
- Update the plan v9 retro to note that commits 4+5 collapsed
  (commit 8 is "housekeeping (2-button kb, plan v9)" — there's
  presumably already a v9 retro commit body landing somewhere);
  OR
- Re-split if a future bisect would benefit.

Bisecting between "router collapse" and "env-var removal" has very
low value (both are pure deletions with no behavior change in the
single-pm world), so re-splitting is probably not worth it. Just
note the merge.

### LOW-4 — Stale "CLI pm" prose strewn across non-deleted files

**Files**: `lib/process-manager-sdk.js:6-8, 23, 25, 60, 63, 83`,
`lib/error-classify.js:120`, `lib/agent-loader.js:5`,
`lib/stream-reply.js:214`, `lib/telegram-prompt.js:101-103`,

Every comment that says "matches CLI pm", "CLI pm has no
equivalent", "stream-json", "today's IPC flow", or "deleted in
Phase 4" now points at code that doesn't exist. The volume isn't
huge (~20 sites total) but they're scattered across the lib so
that anyone learning the codebase by reading comments builds a
mental model with phantom layers.

`lib/process-manager-sdk.js` is the worst offender — its file
header (lines 6-8) still says "Public API matches
`lib/process-manager.js` (the CLI version) so polygram.js can
swap implementations via env flag (POLYGRAM_USE_SDK=1). Phase 4
deletes the CLI version after Phase 5 soak..." Since the CLI
version is deleted and the env flag doesn't exist, this is
actively false.

**Recommendation**: a single "stale-comment sweep" follow-up
commit. Mechanical, low-risk, doesn't block 0.9.0 but should
land before the version cuts so the post-cut tree is internally
consistent.
