# 0.11.0 — Channels backend divergence

Companion to `docs/0.10.0-backend-divergence.md`. Lists ways the **channels** backend behaves differently from **sdk** and **tmux**, so operators routing chats to `pm: 'channels'` can anticipate the cumulative UX delta.

Each entry shows what SDK/tmux do, what channels does, and whether the divergence is **accepted** (Channels protocol genuinely doesn't expose the signal, e.g. mid-turn streaming) or **deferred** (could be implemented but isn't in 0.11.0).

## Internal tool-use visibility (parity audit P12)

SDK + tmux see EVERY tool call Claude makes (Bash, Write, Edit, Read, Glob, WebFetch, etc.) via SDK callbacks / JSONL `tool_use` events. ChannelsProcess only sees the bridge's own tools (`reply`, future `react` / `edit_message`) — internal Bash/Write/Edit calls are invisible. This is a fundamental Channels protocol limitation, not a polygram choice.

Implication: per-tool reaction icons (`📂 ls`, `🔧 edit`) work on SDK/tmux but not channels. HeartbeatReactor provides liveness-cycling as the substitute.

## Hook observability (parity audit P11)

TmuxProcess writes a per-session hook ndjson file and tails it for `hook-event` rows (rc.32 H1 observability). Channels has no equivalent — turn-end signal comes from the bridge's `reply` quiet-window heuristic instead of stop-hook detection. Not a correctness gap; live-tool telemetry would be additive in a future round.

## Inject-user-message / steer events (parity audit P16)

`injectUserMessage` and `steer` methods are not implemented on channels (Process default false). The corresponding events (`inject-user-message`, `inject-fail`, `steer`) are therefore never emitted. Cross-backend observability subscribers see nothing on channels — this is expected given the methods themselves are deferred.

## Result payload — missing fields (parity audit P18)

`emit('result', ...)` second argument:
- SDK: `{streamText, usageByMessage, ...}`
- tmux: `{streamText, stopReason, resolvedVia}` — `resolvedVia` distinguishes `'stop-hook'` / `'idle'` / `'jsonl'` per rc.42 #15
- channels: `{streamText}` only

Channels has no equivalent for `resolvedVia` (no hooks, no JSONL) or `stopReason` (Channels protocol doesn't expose claude's internal stop_reason). Consumers branching on these see `undefined` on channels — by design.

## Assistant-message-start boundary (parity audit P23)

SDK + tmux emit `assistant-message-start` per new assistant message bubble so polygram's streamer opens a new Telegram bubble. Channels concatenates all `reply` tool calls within a turn into one PmSendResult.text (joined with `\n\n`) — there's no mid-turn message-boundary signal. UX delta: a turn with 3 progress replies + 1 final reply renders as 4 separate TG messages on SDK/tmux (one per assistant turn) but as 1 message with embedded separators on channels.

## Permission decision — no 'always-allow' (parity audit P25)

TmuxProcess `respondToApproval` accepts `'allow' | 'always-allow' | 'deny'` (TUI menu option 2 = "yes, always for similar commands"). The Channels protocol's `permission` verdict notification only exposes `'allow' | 'deny'` per the official Anthropic spec — there is no third value. ChannelsProcess `respondToPermission` validates that constraint. Polygram's admin-card UI could surface always-allow as a button, but channels can't honor it. Operators on channels chats lose the "remember this approval" affordance.

## Context hooks — onActivate / onFirstStream (parity audit P26)

SDK calls `context.onActivate()` when a queued turn becomes head, `context.onFirstStream()` on first assistant chunk. Polygram uses these for reactor priming + spinner-to-progress transitions. Channels never calls them — replies arrive whole, not streamed, so there's no first-stream signal. Callers passing `context.onFirstStream` on a channels-routed chat get no callback.

## Control-char sanitization on prompt (parity audit P13)

SDK + tmux strip `[\x00-\x08\x0b-\x1f\x7f]` from user prompts and emit `prompt-sanitized`. Channels accepts the prompt as-is and forwards to bridge → MCP notification. The assumption is that polygram sanitizes upstream before calling `ChannelsProcess.send()`. Defensive sanitization at `send()` entry would be cheap belt-and-suspenders for callers that bypass the polygram dispatch path (e.g. future test/API harnesses). Documented but not implemented.

| `idle` | ✓ on turn end | ✓ on JSONL result | ✓ on `_resolveTurn`, turn-timeout, resetSession, interrupt-grace-resolve (`47aa1c1`) | matched |
| `result` | ✓ with full metrics + cost | ✓ with full metrics + cost | ✓ but `cost: null`, token-fields `null` (P2 AC4) | partial — unmeasured-subscription semantics |
| `close` | ✓ | ✓ | ✓ | matched |
| `thinking` | ✓ | ✓ implicit | ✓ on `send()` | matched |
| `tool-use` | ✓ per SDK tool block | ✓ per JSONL `tool_use` | ✓ per bridge `tool` msg (Channels exposes only reply/react/edit_message) | matched (subset of tools) |
| `autonomous-assistant-message` | ✓ when assistant msg has no parent_tool_use_id | ✓ when JSONL assistant msg fires outside in-flight turn | ✓ when reply arrives with no pending turn | matched |
| `stream-chunk` | ✓ per SDK partial-text event | ✓ per JSONL text increment | ✗ — Channels protocol doesn't expose mid-turn partial text | **accepted** — reply tool delivers complete text only |

| `phase-change` | ✗ (tmux-only) | ✓ patience-model predicate | ✗ | **accepted** — tmux-specific |
| `prompt-sanitized` | ✓ on control-char strip | ✓ on control-char strip | ✗ — channels accepts prompt as-is; sanitization runs upstream in polygram | **accepted** — different layer |

| `interrupt-applied` | ✓ on Query.interrupt | ✓ on tmux SIGINT | ✓ on tmux SIGINT (channels also delegates to tmux for lifecycle) | matched |
| `session-id-refreshed` | ✗ (SDK manages session_id internally) | ✗ | ✓ if bridge reports a different claude_session_id than our generated one | additive |
| `bridge-disconnected` | ✗ | ✗ | ✓ when per-session socket closes | channels-only |
| `session-reset` | ✗ (resetSession returns directly) | ✗ | ✓ on `resetSession({reason})` | additive |

## `PmSendResult` shape

| Field | SDK | tmux | channels |
|---|---|---|---|
| `text` | full assistant text | full assistant text | concat of all `reply` tool calls (`\n\n`-joined) |
| `sessionId` | from SDK init event | from JSONL session-init | from bridge's session_init |
| `cost` | numeric USD per turn | numeric USD per turn | `null` — Channels protocol doesn't expose per-turn cost |
| `duration` | ms | ms | ms |
| `error` | string or null | string or null | string or null |
| `metrics.inputTokens` | number | number | `null` |
| `metrics.outputTokens` | number | number | `null` |
| `metrics.cacheCreationTokens` | number | number | `null` |
| `metrics.cacheReadTokens` | number | number | `null` |
| `metrics.numAssistantMessages` | number | number | number (count of reply tool calls) |
| `metrics.numToolUses` | number | number | `null` |
| `metrics.resultSubtype` | `'success'` / `'error'` / etc. | same | `'success'` / `'interrupted'` |

**Implication for billing aggregations:** any sum/average over `cost` MUST skip null entries rather than treat them as $0. Channels traffic appears unmeasured (because it IS — Pro/Max flat-rate subscription).

## Cost / subscription path

| Backend | Auth path | Billing |
|---|---|---|
| SDK | `@anthropic-ai/claude-agent-sdk` + Console API key | per-token Console rates |
| tmux | claude CLI inside tmux + claude.ai/Console OAuth | Pro/Max subscription flat rate |
| channels | claude CLI inside tmux + claude.ai/Console OAuth | Pro/Max subscription flat rate |

For polygram operators, picking `pm: 'channels'` over `pm: 'sdk'` is primarily a cost decision; over `pm: 'tmux'` it's a reliability decision (structured IO vs JSONL/pane parsing).

## Bedrock / Vertex / Foundry

| Backend | Bedrock | Vertex | Foundry |
|---|---|---|---|
| SDK | ✓ supported | ✓ | ✓ |
| tmux | ✓ via env auth | ✓ | ✓ |
| channels | ✗ — Anthropic Channels feature requires direct Anthropic auth | ✗ | ✗ |

If a chat configures `pm: 'channels'` but the underlying claude CLI is configured for Bedrock auth, the channel won't activate. Factory's `pickBackend` will silently return 'channels', but the channel registration fails downstream. Document risk; consider adding a pre-flight check in a future round.

## Operator decision matrix

| Workload | Recommended backend |
|---|---|
| Personal / Pro/Max account, structured IO desired | **channels** |
| Personal / Pro/Max account, agent-side richer features (injectUserMessage, setModel, autosteer) | **tmux** |
| Org with per-token Console billing, full SDK feature set | **sdk** |
| Enterprise via Bedrock/Vertex/Foundry | **sdk** or **tmux** (not channels) |
