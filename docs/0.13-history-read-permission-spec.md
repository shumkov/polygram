# 0.13 — Permission control on reading polygram history (#4)

> **Status: design / spike-gated, then build.** Direction (Ivan): admin sessions read all;
> non-admin sessions read only their own surfaces. Enforcement: defense-in-depth, OS-level.
> **Severity:** privacy — partner/customer transcripts currently readable cross-chat.

## SHIPPED — cheap real wins (0.12.5, 2026-06-15)
Ivan chose **"Cheap real wins + accept residual"** over the full OS-boundary build (the only
airtight boundary — privsep — is keychain-blocked on this Mac; sandbox `denyRead` is
self-removable by a bypass-flag agent that can rewrite its own `--settings`). The wins,
all landed in 0.12.5, are **real reductions in attack surface**, not the full boundary:

1. **#10 — history-preload prompt-injection closed.** `lib/history-preload.js#formatRow` now
   `xmlEscape`s both the username and the message body before they're injected inside
   `<polygram-history>`. A stored message containing `</polygram-history><system>…` can no
   longer break the container and land instructions outside the fence on every fresh session.
   Plus `lib/prompt.js` POLYGRAM_INFO now names `<polygram-history>` as untrusted alongside
   `<untrusted-input>`/`<reply_to>`. Regression test: 3 cases in `tests/history-preload.test.js`.
2. **query.js backdoors closed.** `deriveBotScope` no longer honors `POLYGRAM_ADMIN=1` or
   `CLAUDE_CHANNEL_BOT` env overrides — both were agent-settable on a subprocess, i.e. a
   cross-chat read backdoor reachable from any bot's Bash. Scope is now cwd-only, fail-closed.
3. **History stays strictly preload-scoped** (already true; no read TOOL added).

### Residual (ACCEPTED, documented per Ivan's choice)
These wins stop **accidental over-reads via the sanctioned skill** and the **easy env
backdoor**. They do **not** stop a determined same-uid agent from reading other chats' DBs
directly: it can still `cd` to another chat's mapped cwd and run `query.js`, or raw-`sqlite3`
/ `python3 -c "import sqlite3"` against `~/polygram/*.db`. Closing that requires the OS-level
boundary below (sandbox `denyRead`, spike-proven Tier 1 — or privsep). Tracked as the 0.13
build; until then the residual is a known, accepted exposure (operator-trusted same-uid agents).

## Policy (the goal)
- **Admin session** (the operator's chat) → may read ANY chat's history.
- **Non-admin session** (a partner/customer chat:topic) → may read ONLY its own surfaces:
  its own chat + that chat's topics, its own DM, and shared groups it is a member of.
  At the session level this reduces to: **a non-admin session reads only its own chat;
  admin reads any.** (A partner-topic agent must not see another partner's chat.)

## Threat model & exposure (grounded)
- Agent sessions run `--permission-mode bypassPermissions` **+ `--dangerously-skip-permissions`**
  (cli-process.js:712,720) — REQUIRED for the channels first-turn. This **disables the
  permission engine**, so `permissions.deny` (any tier, incl. managed/root-owned) is **NOT
  enforced** (verified against Claude Code docs). Bash deny-matching is leaky anyway
  (`python3 -c "import sqlite3"`, `dd`, `cp`).
- Daemon + agents run as the **same OS user**; `shumabit.db` holds EVERY chat.
- ⇒ Any agent's Bash can `sqlite3 ~/polygram/shumabit.db` and read all transcripts.
- The legit path (`history-preload`) is already scoped to the session's own chat; there is
  no read TOOL; nothing blocks raw reads.
- Adversary = an off-task or prompt-injected agent reading cross-chat (not a root attacker).

## Mechanism — what actually enforces it
Permission/deny rules can't help (skipped by the flag). Two things that DO:

### (1) Sandbox `filesystem.denyRead` — the OS-level boundary
Claude Code's **sandbox is a separate layer**: `--dangerously-skip-permissions` disables
prompts but NOT the sandbox. `sandbox.filesystem.denyRead` is **OS-level (kernel open()
block) — airtight for Bash**, no python/dd/cp workaround. Surgical: deny ONLY the DBs.
```
sandbox.filesystem.denyRead: ["/Users/<user>/polygram/*.db", "/Users/<user>/.polygram/*.db"]
(+ -wal/-shm/-journal siblings)
```
polygram already writes a per-session settings file and passes `--settings <path>`
(cli-process.js:842-854, `writeHookFiles` → `~/.polygram/<bot>/hooks/<sid>.settings.json`).
The sandbox block goes there (or a merged settings) so it applies per agent session.

### (2) Gated, scoped `history` MCP tool — the sanctioned read path
With raw reads blocked, give agents a legitimate scoped path. New bridge tool alongside
`reply`/`edit_message`/`ask`. The bridge socket is **per-session**, so the tool inherently
knows the caller's chatId — scope is enforced server-side, not by trusting an argument:
- non-admin caller → returns only its own chat (+ topics); a cross-chat request is rejected.
- admin caller → may target any chat.
- params: `query?` (FTS5 search), `chat_id?`/`thread_id?` (admin only), `limit`. Reuses
  `lib/history.js` (FTS5) under an authz wrapper.
- **admin determination**: reuse the `/rewind` model — `isOperatorIdentity`
  (`operatorUserId` / `adminChatId`, see rewind.js:41, approvals.js:122). A session is
  "admin" iff its chat is the operator's DM or a config-flagged admin chat.

### (3) Audit log
Every history read (tool call AND, if detectable, the daemon's own queries) → an
`events` row: `history-read {requester_chat, scope, target_chat, query, row_count}`.
Detectability of raw reads dies once denyRead lands (good), but the tool path is fully
audited.

## SPIKE RESULT — Tier 1 PASS (2026-06-14)
Ran `claude --print --permission-mode bypassPermissions --dangerously-skip-permissions
--settings <sandbox+denyRead>` against a test `secret.db`:
- `cat` → "Operation not permitted"; `sqlite3` → "authorization denied"; **`python3 import
  sqlite3` → "unable to open database file"** — all 3 read vectors BLOCKED (OS-level;
  the python/dd bypass that defeats `permissions.deny` is also blocked).
- `cat allowed.txt` (home) → OK; `curl https://example.com` → 200. Non-denied FS + network
  unaffected → surgical, broad-allow-except-the-DBs.
**Verdict: the denyRead mechanism is viable + airtight under the bypass flag.** (claude
2.1.177; confirm the agents' pinned version matches — feature predates both.)
**Remaining (Tier 2, verify at sandbox-enable on shumorobot, with rollback):** the channels
bridge UNIX socket is `/tmp/polygram-<bot>.sock` (NOT denied; default-allowed FS per the
spike, so it should connect) — confirm first-turn + MCP `reply` still work under the sandbox;
and check no current agent reads the DB via Bash.

## SPIKE FIRST (gate — do not build before this passes)
Enabling the sandbox on a channels agent is UNTESTED and could break it. Spike
(`scripts/spikes/sandbox-denyread.mjs` or a one-off shumorobot session):
1. Spawn a channels agent with `sandbox.enabled:true` + `filesystem.denyRead` on the DB
   paths (+ `autoAllowBashIfSandboxed:true` so no prompts under bypass).
2. **Must still work:** channels first-turn replies (the bypass reason); the `/tmp`
   bridge socket connects (MCP `reply` works); network tools (WebFetch / an API call);
   normal cwd FS read/write; the agent's actual skills (music `mc`, bill-creator Xero, etc.).
3. **Must be blocked:** `sqlite3 ~/polygram/shumabit.db …`, `cat …db`, AND
   `python3 -c "import sqlite3; sqlite3.connect('…db')"` (prove the OS-level airtightness).
4. Check: does any CURRENT agent workflow read the DB via Bash (would denyRead break it)?
   If yes → those reads migrate to the `history` tool before denyRead ships.
**Spike fails → fall back to OS privilege-separation** (agents as a separate uid; DB 0600)
as the only remaining hard boundary, or ship (2)+(3) functional+audit without the hard block.

## Build order (after spike passes)
1. `history` MCP tool + authz wrapper + audit (the sanctioned path) — ship first, no risk.
2. Migrate any agent DB-read workflows to the tool (from spike step 4).
3. Enable sandbox `denyRead` on agent sessions (the boundary) — the risky step, gated by 1+2.

## Test plan
- Authz unit tests: non-admin session tool call scoped to own chat; cross-chat request
  rejected; admin call returns target chat; audit row emitted.
- Sandbox: the spike (manual/real-claude) is the proof; plus a settings-assembly test that
  agent sessions get the denyRead block in their `--settings`.
- Negative: a Bash `sqlite3`/`python sqlite3` read of the DB fails under the sandbox.

## Rollout (sandbox is the risky bit → test ground-up)
shumorobot (Ivan's, isolated) FIRST — soak the sandbox there; confirm no agent breakage →
shumabit → umi-assistant LAST. Watch for: broken tools, blocked network, first-turn 401s,
any agent that silently lost a needed file read.

## Open decisions
1. Does the `history` tool ship even if NO agent currently needs raw history? (Recommend yes
   — it's the safety valve once denyRead lands; harmless if unused.)
2. denyRead path globbing — confirm Claude's sandbox supports `*.db` globs + the -wal/-shm
   siblings, else enumerate.
3. Admin scope granularity — is "operator DM = admin-all" enough, or do we need a per-chat
   `historyAccess` flag (like rewind's `rewindAccess`)?
