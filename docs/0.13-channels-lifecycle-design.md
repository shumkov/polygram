## 1. The end-to-end lifecycle map

### 1.1 The planes

```
                        INTAKE PLANE (polygram.js + handlers)
  bot.on('message') ─► recordInbound ─► dispatchRegularMessage ─► gates ─► dispatchHandleMessage
  bot.on('edited_message') ─► oldText ─► recordInbound ─► inFlight? injector : edit-redelivery
  boot-replay / startup-retry / compact-replay ······· (each its own re-dispatch shape)
                                   │
                                   ▼
                        TURN PLANE (handleMessage + CliProcess)
  handleMessage: prework ─► [intentLock] autosteer? ─► inject (fire&forget, untracked)
                                       └ primary ──► [stdinLock across FULL turn] sendToProcess
                                                          │
   CliProcess.send: turnId ─► pendingTurns + pendingQueue{context} ─► bridge user_msg
                                                          │
   replies (bridge tool msg) ─► dedup/rate/chat-guard ─► toolDispatcher → Telegram (delivered NOW)
                              ─► _recordReplyForPendingTurn (turn_id echo routing)
                                                          │
   turn end: reply-quiet 2s ──► _resolveTurn ─► stop-grace 2s ─► _finalizeTurn
             or Stop hook (single pending, no quiet armed)        │ resolve {alreadyDelivered}
                                                                  │ splice pendingQueue
                                                                  ▼ emit result + idle
                        FEEDBACK PLANE (per-turn, parasitic on the turn object)
  reactor + typing: created in handleMessage closure; mid-turn reachable ONLY via
  entry.pendingQueue[0].context; ALL hook routing (callbacks.js) head-gated; torn down at
  handleMessage exits. Session-scoped exceptions: ✍ refs, question cards, bg-work status.
                        OBSERVABILITY PLANE (hooks)
  UserPromptSubmit ─► emit('turn-start')  ← ZERO consumers; prompt payload DISCARDED
  Pre/PostToolUse  ─► reactor routing (head-gated) + _extendQuietOnToolActivity
  Stop             ─► authoritative-ish turn end (graced); carries no turn_id
```

### 1.2 The claude-side contract (verified from prod artifacts)

Every `user_msg` the daemon writes to the bridge becomes an MCP channel notification; claude
renders it into its conversation as a user entry whose **content is the full envelope**:

```
<channel source="polygram-bridge" chat_id="…" user="…" msg_id="…" turn_id="<uuid>">TEXT</channel>
```

(verified in `~/.claude/projects/-Users-ivanshumkov-Music-rekordbox/*.jsonl`, entries carry
`origin:{kind:"channel"}`). The 0.12 Phase-0 spike confirmed channel notifications fire
**UserPromptSubmit**. The hook tail already normalizes a `prompt` field
(`lib/process/hook-event-tail.js:90`) — but `cli-process.js:1935` discards it and emits a
payload-free `'turn-start'` that **nothing consumes** (verified: no `onTurnStart` in
`CALLBACK_TO_EVENT`, zero listeners repo-wide). **The signal needed for input-delivery
observability is already arriving and being thrown away twice.**

Escaping detail that the seen-parser design relies on (§3 D2): the bridge body-escape
(`channels-bridge.mjs:85–86`) escapes `&`, `<`, `>` but NOT quotes; the attribute escape
(`:93–95`) escapes quotes too. So user body text can contain a literal `turn_id="…"` string, but
can never contain a raw `<` — a raw `<channel ` tag prefix is bridge-authored by construction.

### 1.4 The single-active-cycle invariant (load-bearing, with its limits)

Verified: every production turn-send goes through `sendToProcess`, which holds the per-session
`stdinLock` from before `pm.send` until the turn promise settles (polygram.js:521–532); every
settle path deletes the pendingTurns entry synchronously before resolving. Therefore
**`pendingTurns.size ≤ 1` always, in production**. Two hard limits the design must respect:

1. The invariant is enforced *only* in polygram.js — `CliProcess.send` itself has no
   serialization. The design makes the invariant explicit as an **assertion** (see D1) whose
   failure mode is drop-and-log (never throw, never misattribute), not a trusted assumption.
2. **`pendingTurns.size ≤ 1` does NOT mean "the running claude cycle is the pending turn."**
   Claude-side concurrency survives the invariant: injected user_msgs, fire-and-forget cycles
   (/compact, bg-work self-check, compact-replay), ScheduleWakeup cycles, post-finalize late
   work, and a fresh send queued while claude is blocked on a *previous finalized* turn's ask.
   Any turn-end signal that lacks cycle identity (Stop today) can therefore belong to a foreign
   cycle even with a single pending. This drives D1's attribution rule.

## 2. The structural roots

Five symptoms, four roots. Mapping to the cluster (#1–#5 from the brief) and the open
known-issues (KI-drop = channels inbound drop; KI-verbatim = re-delivery of old messages):

### ROOT A — The polygram "turn" is a delivery-accounting heuristic, not claude's work cycle.

The pending turn resolves on **reply-quiet(2s) + stop-grace(2s)** — a guess that "no more replies
soon = done" — while claude's actual cycle boundary (UserPromptSubmit → Stop) is observable and
already wired. The mismatch fires in both directions: the turn ends while claude still works
(S1, S2 — the WA incident, the mid-question finalize), and the turn hangs when claude never
received the input (S6 — no cycle ever started, nothing notices until the 10-min ceiling).
Everything parasitic on the turn object — reactor, typing context, watchdog, LRU pin,
markReplied — tears down at the wrong moment. *Causes #2, #5; amplifies #1; underlies the
late-reply orphans (34–83% of "autonomous" messages).*

### ROOT B — Input delivery is fire-and-forget at every layer; there is no message lifecycle.

`send()` assumes the bridge write is delivery (S6 drops it). `injectUserMessage` mints a turn_id
and forgets it before returning (S4). `fireUserMessage` likewise (S12). No state exists between
"written to socket" and "a reply happened to echo something" — so folded, new-turn, and dropped
are indistinguishable, live and forensically. A second face of the same root: **cycle identity is
unobserved** — Stop and UPS arrive without being bound to the input that started the cycle, so
even turn-end attribution is a guess (S5). The SDK backend has none of this class: its inject is
a push-or-throw into the input iterator, tied to the head pending. *Causes #3; causes KI-drop's
silent half; makes #14's Q3 (fold/drop ratio) unmeasurable; contributes to KI-verbatim's
unresolvability.*

### ROOT C — Feedback is parasitic on the turn object instead of owned per session.

Reactor + typing live in the handleMessage closure and are reachable only via the head pending's
context; every hook router is head-gated (S7). Anything that outlives or sidesteps the pending —
ask-waits, post-answer work, autonomous cycles, injected messages — is invisible. Each prior fix
(question-resume re-arm, extra-turn visuals, bg-work status) re-derived a session-scoped feedback
fragment ad hoc; the re-arm no-ops in the common S2 shape. *Causes #1, #2; the "dead air" class.*

### ROOT D — Recovery and gating are per-incident copies, not primitives.

Five re-dispatch implementations (S10) and four gate depths (S11) — each new failure mode got a
bespoke path with subtly different one-shot, ack, gating, and reconstruction semantics. The
divergences are now themselves bugs (edit-to-/stop injection, interlock-before-gate, the
edit-during-Other dead end, the pre-gate bystander abort). *Causes #4's review churn; would have
made the #14 drain a sixth copy.*

**Why five bugs in one area in two days:** the area is where all four roots intersect — an
interactive question is (C) feedback during (A) a mis-modeled boundary; an autosteer drop is (B)
unobservable input at (A) a boundary; an edit is (D) a recovery copy crossing (D) a gate variant.
Individual patches keep landing on symptoms because each root spans several mechanisms.

## 3. The design

Four pieces, each dissolving a root. They compose but ship independently, ordered by
leverage-per-risk. A deliberate non-goal: no bridge-protocol changes (the channels protocol is
Anthropic's research preview — F#24's "no true mid-stream merge" stands; we design around it).

### D1 — Cycle-aligned turn end: an attributed-Stop + activity-quiet finalizer ladder (ROOT A)

**The finalizer ladder.** A pending turn finalizes via the first applicable rung:

1. **Attributed Stop** (primary). On Stop, finalize the single pending turn **only if the ending
   cycle is attributable to it**: the pending has ≥1 turn_id-bound reply, OR its UPS-seen marker
   fired (the minimal ledger slice below — and in Tier 1/2, a seen-marker observed *before* the
   Stop in tail order is the preferred evidence). An *unattributable* Stop — foreign cycles:
   /compact, bg-work self-check, wakeups, a non-folded inject running as its own cycle — must
   NOT finalize the pending (today's `:2042` branch would, delivering the foreign cycle's
   `lastAssistantMessage` as the user's answer — the panel's constructed misattribution). An
   unattributable Stop instead *starts* rung 2's check immediately. Two hardenings (round 2):
   an attributed Stop finalizes **through the existing 2s stop-grace, and any same-session
   activity during the grace (hook event, bound reply, pane heartbeat) CANCELS it** — Stop
   arrives via the ndjson tail with 250ms–5s lag, so a foreign cycle's lagged Stop can land
   *after* the new turn's fast first reply; activity-in-grace proves the Stop was stale and the
   turn falls back to rung 2. And a Stop with `stopHookActive=true` never finalizes — a
   stop-hook-forced continuation means the cycle is, by definition, not over.
2. **Activity-quiet window** (secondary). After a turn has ≥1 delivered reply, it finalizes when
   the session has had **no activity for `activityQuietMs`** (default ~15–20s), where activity =
   hook events **+ the capture-pane "thinking" heartbeat + bridge tool dispatches**. Hook-only
   quiet would fire mid-thought: pure-thinking stretches exceed 45s with zero hooks (that is why
   the pane heartbeat exists — cli-process.js:105–114, emitted on the 5s pong tick while a
   pending turn exists, so it bounds busy-phase inter-activity gaps at ~5s; the implementation
   must not reorder finalize vs the `_pollMidTurnDialogs` size-gate). This single mechanism
   replaces v1's separate quiet-candidate, max-tail timer, and `maxRepliesPerTurn`
   instant-resolve (the ≥20-replies cap now switches to this window instead of resolving
   instantly), and it **covers mid-session hook death**: if the whole activity surface goes
   silent (helper crash kills hooks; pane heartbeat requires only tmux), the turn ends
   ~15–20s after the last activity rather than rejecting with TURN_TIMEOUT 10 minutes later
   (v1's `_sawHookStream`-boolean fallback had exactly that hole — the flag is set once at
   cli-process.js:1895 and never reset). Emits `cli-activity-quiet-finalize` + a
   `cli-hook-stream-stalled` event when it fires with a previously-live hook stream. Caveat
   (accepted, logged): an auto-compaction inside the tail resets this clock via its own hook
   events — a tail can legitimately stretch to minutes; bounded by the ceilings.
3. **Legacy reply-quiet (2s)** — only for sessions where hooks never came up
   (`_sawHookStream === false`): byte-identical to today for the hooks-never-alive class.
4. **Idle (10 min) / absolute (30 min) ceilings** — backstops, with one semantic change
   (round 2): a ceiling expiring on a turn with **≥1 delivered reply RESOLVES it** with its
   accumulated replies (`alreadyDelivered=true`, event `cli-turn-ceiling-resolved`) — the user
   already has their answer; rejecting would send a scary timeout *after* a successful reply
   (and the v2 soak gate contradicted the design's own ask-timeout-then-ceiling path).
   TURN_TIMEOUT rejection is reserved for turns with **zero** delivered replies.

**The P1 seen-slice (pulled forward from D2 by panel finding).** Rung 1's attribution needs the
UPS marker, so P1 carries a *minimal* slice of the ledger: parse `turn_id` out of the
UserPromptSubmit `prompt` (anchored parser, §D2) and mark the matching pending turn (and, P3+,
ledger entry) as `seen`. If the P0 spike lands Tier 3 (UPS prompt unusable), rung 1 keeps
**today's** single-pending Stop-finalize semantics for *no-reply* turns (rung 2 requires a
delivered reply, so demoting them would regress no-reply turn-end from ~0s to the 10-min
ceiling) — i.e. Tier 3 accepts today's pre-existing S5 foreign-Stop residual for that class
rather than trading it for a hang; replied turns still get reply-bound attribution. Attribution
precision note: for a *replied* pending in its tail, a foreign cycle's Stop may finalize it a
few seconds early — harmless (its text is its own bound replies; the dangerous case, foreign
`lastAssistantMessage` delivered as the answer to a never-started turn, is exactly what the
seen/reply test blocks).

**Ask-wait semantics.**
- The `ask` branch sets a `waiting-on-user` flag on the cycle; rung 2's clock is suspended while
  a question is open (claude is legitimately silent); the keep-alive's hardTimer extension stays.
- **Typing pauses while `waiting-on-user` and resumes on the answer** — a ~10-line point fix in
  P1 (pause the per-turn typing loop on `question-asked`, resume on `question-resumed`), later
  subsumed by D3. Without this, D1 would *extend* S8's inverted typing to every reply→ask wait
  for the whole P1→P4 window — three reviewers flagged it independently.
- When the cycle hits its absolute ceiling with questions open, resolve open questions
  `{timedout}` first, then time the turn out (implements what the questions design prescribed).
- On daemon shutdown, expire open questions `{cancelled}` (card stripped) *before* the drain
  wait, so an ask-blocked cycle can end within the 30s drain instead of forcing
  `replay-pending` → a boot-replay re-ask becomes a deliberate, documented recovery path (the
  question died with the daemon), not an accident.
- `_evictLRU` skips sessions with `_openQuestions.size > 0` (belt-and-braces — with D1 the turn
  stays `inFlight` through the wait).

**What the user sees (explicit, was implicit in v1).** The *visible* done-signal is unchanged
from today: the reactor clears when the final reply is delivered, exactly as now — D1 aligns the
*bookkeeping* lifetime, not the UX of "answer = done." During the post-reply tail (claude's
housekeeping between the last reply and Stop) the user sees a clean message (reactor cleared,
no typing); if claude sends a *further* reply in the tail, it now attributes to the same turn
(today it orphans into the autonomous path). Follow-ups arriving during the tail autosteer into
the still-open cycle — acceptable because the tail is bounded by rung 2 (~15–20s of activity quiet)
and, post-P3, the inject is ledgered so a tail-boundary drop is detected. This is a deliberate
decision-log row, not a side effect.

**What it dissolves.** #2 and #5 *structurally*: through reply→ask waits the pending turn — and
with it the reactor context, the head-gated hook routing, the question-resume re-arm, the
mid-turn watchdog, and the LRU pin — survives to the real end of claude's cycle. The late-reply
orphan class (S1) collapses: post-reply work keeps the turn open until attributed-Stop or
activity-quiet, so its replies attribute correctly. The invisible post-finalize wedge (S7's
watchdog gap) closes. The S5 Stop-identity gap closes for replied turns in **all** tiers and for
no-reply turns in Tier 1/2; under Tier 3 the no-reply class keeps today's pre-existing residual
as a deliberate trade (see the Tier-3 paragraph above) — the summary and the carve-out are the
same claim.

**Costs / risks.** Turns are held longer (to Stop or activity-quiet): stdinLock held longer →
more follow-ups autosteer (matches claude's actual busy state; measured — see soak gates);
`markReplied`/turn_metrics shift to cycle end → **a deploy during a long ask-wait now marks the
inbound `replay-pending`** (the 30s drain can't outwait a question) → mitigated by the
shutdown-question-expiry above + the deploy-during-ask E2E + replay-on-boot counts in the soak.
Stop reliability is NOT load-bearing (rung 2 backstops it); Stop *attribution* is, and it fails
safe (unattributed → rung 2). The dead `size>1` branches become an assertion whose failure mode
is **log + drop-rather-than-misattribute** (never throw). **Named interim exposures, P1→P3**
(round 2): (a) an S6-dropped primary no longer gets accidentally fast-closed by a passing
foreign Stop — it now correctly holds the stdinLock to the 10-min idle ceiling until the D2
watchdog ships; the P1 soak therefore tracks `TURN_TIMEOUT`-with-zero-replies rate vs the rc.33
baseline, and **if it worsens, the cold-start slice of the D2 primary watchdog (regime (i)
below) pulls forward into a P1.x rc**; (b) D1 increases autosteer volume into injects that
remain unledgered until P3 — accepted (the drop class is rare and P3 closes it), watched via
the same soak.

### D2 — The InputLedger: every user-shaped input gets an observable lifecycle (ROOT B)

**Change.** A per-session ledger inside CliProcess records every `user_msg` written to the bridge
— `send`, `injectUserMessage`, `fireUserMessage` — as
`{turnId, source: primary|autosteer|edit-fold|system, msgId?, text?, writtenAt, state}` with
states `written → seen → resolved | dropped | superseded`. Schema notes (panel-tightened):
- `text` is stored **only for sources with no DB row to reconstruct from** (`autosteer`,
  `edit-fold`, `system` — their content is the *formatted prompt*, not the raw message);
  `primary` entries store `msgId` only and reconstruct via `db.getMessage` at redelivery time.
- **Ledger transition events log `text_len` only, never content** — the events DB stays
  content-free per the L13 convention (cli-process.js:1005–1008); a test asserts no transition
  row carries a `text` field.
- Entries GC at resolution + LRU cap (64/session). The ledger is in-memory: after a daemon
  restart the first cycle runs with an empty ledger (today's behavior — noted, accepted).

**Transitions.**
- **seen**: the UserPromptSubmit `prompt` is parsed with an **anchored parser**: match
  `<channel\s[^>]*turn_id="([0-9a-f-]{36})"` — the raw `<` prefix is bridge-authored by
  construction (body text cannot contain a raw `<`, §1.2), and the captured uuid must exist in
  the ledger's known set before it marks anything `seen`. A pasted envelope in a message *body*
  cannot spoof `seen` (its `<` arrives escaped); a unit test pins this. A `seen` entry can never
  be re-delivered — drop detection is *absence of pickup*, not absence of a distinguishable
  reply, which kills the base-rate-inversion objection **in Tier 1**.
- **resolved**: a reply echoes the entry's turn_id (existing correlation at :1188), or the cycle
  that `seen` it reaches its attributed end.
- **dropped**: the entry is still `written` after **trigger-cycle end + next-cycle-start +
  grace** (the next-cycle term is required in EVERY tier — a queued non-folded inject's UPS only
  fires at next-cycle pickup, which auto-compaction can defer well past any flat grace; v1 had
  this window only in Tier 2). A late `seen`/`resolved` transition **cancels** any not-yet-
  dispatched redelivery. Then: emit `input-dropped` → redeliver ONCE via D4, subject to the
  redelivery constraints below.
- **superseded**: a newer processed `primary` from the same user arrived before the drop was
  confirmed — the user already re-sent or moved on; log `input-dropped-no-redeliver` instead of
  redelivering.

**The primary-delivery watchdog** (KI-drop's missing half — same primitive, panel-hardened,
**two regimes** after round 2 caught that warm-only conditions exclude exactly the spawn-time
S6 population):
- **Regime (i) — cold/idle** (no hook event within the last ~120s before dispatch, including
  fresh spawns where none has EVER fired): after bridge-ready + mcp-ready, a dispatched
  `primary` with **no UPS and no hook events at all within ~10s** triggers the single
  idempotent re-write — hook-history "recency" is meaningless here (idle silence is just
  idleness; the pong stream is the liveness proxy). This is the regime that covers the
  channel-bind race.
- **Regime (ii) — warm** (a hook event within ~120s before dispatch): recovery requires (a)
  the hook stream live AND recent (otherwise hook silence is an observability failure, not a
  delivery failure — the message likely arrived), and (b) no foreign-cycle activity since
  dispatch (any hook event means claude is busy and the queued message's UPS is legitimately
  deferred — extend the window).
In both regimes: first recovery = one re-write of the user_msg (idempotent because
never-`seen` + the regime's no-activity evidence ⇒ claude never had it — the rc.25 argument now
properly scoped); escalation to kill+respawn+redeliver additionally requires **bridge-level
silence** (no tool calls, no pong anomalies). Never on hook silence alone in regime (ii).

**Tiering on the P0 spike (now two unknowns, not one).**
- **Q-A**: does each queued/injected channel message fire its **own** UPS (including folds)?
- **Q-B** (new, from the panel): when claude folds an injected message and emits one *combined*
  reply, **which turn_id does it echo**? The reply tool schema carries a single `turn_id`
  (channels-bridge.mjs:306–314), so a fold answering primary+inject can echo at most one.
- **Tier 1** (Q-A yes): full design — `seen` at pickup regardless of reply echo.
- **Tier 2** (Q-A no, Q-B reliable for folds): `seen` inferred by reply-echo + next-cycle UPS
  content; drop detection keeps the long window. **Tier 2 with Q-B unreliable: redelivery is
  DISABLED for `autosteer`/`edit-fold` sources** — entries park as `fold-suspected` (telemetry
  only), because a fold whose combined reply echoes only the primary's id is indistinguishable
  from a drop, and auto-redelivering it double-answers the *common* case (the exact A1-killing
  inversion). Primary watchdog still ships (it doesn't depend on fold semantics).
  **Q-B is a runtime guard, not a ship-time constant** (round 2): which id claude echoes is a
  model behavior that can drift with server-side updates — no binary bump, so preflight alone
  can't catch it. The ledger records which id each fold reply echoed; an echo-anomaly rate over
  a trailing window past a threshold **auto-disables fold redelivery** (parks new entries as
  `fold-suspected`) and alerts the operator. The spike's Q-B verdict only sets the *initial*
  flag value and must state its N and decision threshold.
- **Tier 3** (UPS prompt unusable): ledger ships for telemetry + the primary watchdog
  (reply-echo + cycle-end correlation only); inject-drop detection stays best-effort, no
  auto-redelivery. **If P0 returns Tier 3, bug #3 is NOT auto-fixed** — the plan then forks: a
  dedicated follow-up design (e.g. cycle-end expected-vs-seen diff over claude's session JSONL,
  or waiting on a protocol-level ack from Anthropic) rather than silently shipping detection
  that can't detect. The honest outcome is recorded, not papered over.

**Redelivery constraints (security/product-driven).** Auto-redelivery applies to `primary` and
(Tier-1/Q-B-reliable Tier-2) `autosteer`/`edit-fold` entries; `system` never redelivers. The
redelivered turn re-enters via D4 → D5's gate at tier `redelivery`, which **evaluates but does
not execute** abort/admin side effects — an abort-phrase or admin-command-shaped dropped message
is not auto-re-executed in a changed context; it logs `input-dropped-no-redeliver` for the
operator. Presentation: the redelivered turn replies to the original message (reply_to msgId)
with a one-line frame ("answering your earlier message — it didn't go through the first time"),
so a minutes-late answer is attributable and distinguishable from the KI-verbatim
bot-repeats-itself class; the supersession rule above prevents double-answering a user who
re-sent. Both pinned by E2E.

**What it dissolves.** #3 precisely (A2 from the brief, generalized) in Tier 1/2+Q-B — the prod
incident (msg 2385) becomes `written → never seen → dropped → redelivered` with an ack + frame.
KI-drop's mid-turn half gets the hook-based watchdog the known-issues doc asked for. Edit-folds
and bg-work self-checks inherit tracking. The `==1` reply-attribution heuristic (S5) tightens:
a reply echoing a *ledgered non-pending* turn_id is recognized as a late reply to cycle X —
logged, never misattributed into a foreign turn's result. Telemetry: every transition is an
events row → the Q3 fold/drop ratio becomes measurable in prod for free, and
`autosteer-resolution`-class telemetry returns (as ledger rows) instead of remaining dead
infrastructure.

### D3 — Session-scoped feedback controller (ROOT C)

**Change.** Lift reactions + typing out of the handleMessage closure into a per-session
`FeedbackController` owned at the polygram layer (factory-injected like the dispatcher), with
explicit user-legible states: `idle / received / working(detail) / waiting-on-user /
post-reply-tail / background / done|error` (the tail state is now named — it was the panel's
"undefined contract" gap). Inputs: ledger transitions (D2), hook events, question lifecycle,
bg-work status — all already emitted; most currently unconsumed (`turn-start`, `idle`, the
discarded UPS payload). handleMessage's reactor becomes a *view*: it registers the anchor message
(`controller.track(sessionKey, msgId)`) and the controller drives the same
`createReactionManager` instance(s); teardown moves to cycle-end and the controller persists
across cycles for autonomous/injected work — anchored to the most recent user message of the
consuming cycle (the ledger knows it; a true wakeup cycle with NO user message gets typing only,
no reaction — there is no message to anchor to).

**Residual gap after D1+D2 that D3 closes (scope justification, panel-requested).** D1 keeps
feedback alive *through* the pending turn's real lifetime, but: (a) autonomous/wakeup cycles
have no pending turn at all — no working indicator until text lands; (b) an injected message
processed as its own next cycle has feedback only if its ledger entry is wired to a surface —
the per-turn reactor object can't follow it; (c) the typing pause in P1 is a point fix inside
the per-turn loop — `waiting-on-user` as a *state* with consistent reaction+typing semantics
needs an owner; (d) the voice-ack 👂 never promotes on cli (dead `onFirstStream`); (e) the
rc.34 re-arm path and `extraTurnTracker` remain as vestiges until an owner subsumes them. Those
five are D3's concrete payload — not anticipatory generalization.

**Risks.** Largest refactor (touches handleMessage's closure economy). Mitigation: ships last;
`reactions.js` state machine unchanged underneath (only ownership moves); SDK backend wiring
untouched (the deletions — extraTurnTracker, rc.34 re-arm — are verified dead on every backend:
zero `extra-turn-started` emitters exist post-tmux-deletion).

### D4 + D5 — One redelivery primitive, one gate (ROOT D)

**D4 `redeliverAsFreshTurn(sessionKey, chatId, msgRef, opts)`** (new module
`lib/handlers/redeliver.js`): reconstruct (DB row à la boot-replay, or provided synthetic à la
edit-redelivery, or ledger-stored text for row-less sources) → **gate via D5 at tier
`redelivery`** → `_isReplay` tag → one-shot guard (handler_status `redelivery-attempted`, the
boot-replay pre-mark pattern) → ack reaction (👀) + reply_to framing for drop-redeliveries →
`dispatchHandleMessage`. Callers collapse onto it: boot-replay, edit-redelivery, the D2
drop-redeliverer, startup-auto-retry (keeps its in-memory msg + delay, calls the same tail).
Compact-replay stays on `fireUserMessage` — a system re-push of the operator's own command, by
design outside the user-message gate (stated explicitly; it was implicit). Auto-resume stays (a
*continuation*, not a redelivery) but gains a ledger entry like every send. Accepted residual
(risk table): a Tier-2/3 false-positive redelivery runs under `_isReplay` (no new editable row);
if that re-run also fails, the message is unrecoverable — bounded by the once-only guard.

**D5 `gateInbound(msg, ctx, tier)`** extracted from `dispatchRegularMessage`. Honest scoping
(panel correction): this is **not move-only** — the chain embeds side-effectful flows (abort
kills turns; pair-claim writes config; rewind consumes; admin dispatches), so the extraction is
a factory with ~a dozen injected deps following the established `createX({deps})` pattern, and
its core artifact is a **tier × stage table that declares, per tier, whether each stage
*evaluates*, *executes side effects*, or is *skipped*** — e.g.:

| stage | fresh | edit | redelivery |
|---|---|---|---|
| abort | evaluate + execute | evaluate + execute (an edit-to-"stop" aborts) | evaluate, **never execute** — matched ⇒ no-redeliver |
| admin/pair | evaluate + execute | evaluate + execute | evaluate, never execute ⇒ no-redeliver |
| rewind | evaluate + execute | skip (edited /rewind is nonsensical) | skip |
| question-consume / ownsOpenOther | evaluate + execute | **evaluate + execute** (an edit while that user owns an open "Other" becomes the answer) | skip (already consumed once) |
| shouldHandle | evaluate | evaluate (real msg, real from) | evaluate |

Specific closures (each a red→green test in P2):
- **Abort is identity-gated as part of D5** (promoted from "found en route" by three reviewers):
  the abort stage requires paired ‖ mentioned ‖ reply-to-bot ‖ DM — closing the pre-existing
  bystander-abort hole *before* the edit path gains abort semantics (otherwise D5 would add a
  second, stealthier ungated abort entry).
- The **admin/pair branch routes through `dispatchHandleMessage`** (gaining the dispatcher's
  error wrapper + handler_status semantics) instead of bare `handleMessage` (polygram.js:1866).
- The redelivery/edit interlock **gates before injecting** and goes per-`(chatId,msgId)` as the
  edit spec required; the mid-turn injector path additionally requires the editor to be the
  author of a row that is live in the *current* pipeline (closing the bystander-inject hole from
  both directions).
- The mid-turn `[edit]` inject content routes through the same prompt formatting/escaping as
  every other inject (closes the hand-built-marker deviation from the edit spec).

**What it dissolves.** #4's review-churn class; prevents drain-#6; the S11 holes including the
bystander abort. Remaining tracked-not-blocking items move to §6.
