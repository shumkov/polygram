## Root causes (what the investigation actually found)

The handoff doc's suspect for the dropped reply — turn_id ↔ pending-turn
correlation desync — is **disproven**. Prod events for the 2026-06-10 19:32
"2+2 → 4" incident show the rc.36 correlation machinery worked end-to-end:
`cli-input-acked(turn 44e10b45, primary)` → reply tool-result ok →
`cli-turn-resolved-by-stop reply_count:1 attributed:seen`. The reply died
LATER, in the parse/delivery layer:

### Root A1 — `\p{Emoji}` matches digits (parse.js:97-98)

```js
const emojiOnly = /^\p{Emoji_Presentation}$/u.test(trimmed)
  || /^\p{Emoji}️?$/u.test(trimmed);
```

The Unicode `Emoji` property includes `0-9`, `#`, `*` (keycap bases).
Verified: `/^\p{Emoji}️?$/u.test('4') === true`. So claude's reply "4"
parses as a SOLO REACTION with `text: ''` — no text bubble is ever sent.

### Root A2 — cli backend never passes `sourceMsgId` to the tool dispatcher

`channels-tool-dispatcher.js:186` is built to receive it
(`replyToMessageId: sourceMsgId || null, applyReactions: sourceMsgId != null`)
but `cli-process.js _dispatchToolCall` (~:1206) doesn't include it in the call.
Net: on the channels backend `applyReactions` is ALWAYS false → every solo
reaction (legit `👍` included) hits the `channels-tool-dispatcher-reactions-dropped`
branch and vanishes. A1×A2 stacked = the user-visible "claude said 4, user got
nothing". Smoking-gun event: `channels-tool-dispatcher-reactions-dropped
{"dropped":["4"]}` at 19:32:34.

### Root B — the session-age dialog's pre-selected option is `/compact`

Binary-verified (claude 2.1.158, "resume-return" feature):

- Gate: statsig `tengu_gleaming_fair` AND NOT `state.resumeReturnDismissed`
  AND sessionAge ≥ `CLAUDE_CODE_RESUME_THRESHOLD_MINUTES` (default **70**)
  AND estTokens ≥ `CLAUDE_CODE_RESUME_TOKEN_THRESHOLD` (default **1e5**).
- Options: `compact` ("Resume from summary", pre-selected — **literally runs
  `/compact`**), `continue` ("Resume full session as-is"), `never`
  ("Don't ask me again" → persists `resumeReturnDismissed: true`).

polygram's startup-gate `session-age` trigger answers bare `Enter` → selects
`compact` → silently compacts the resumed session: context degradation PLUS
an extra compaction's token burn, on every aged-session respawn (including
every `/model`-drift reload of a >70min/>100k session — directly violating
the rc.36 "/model keeps the conversation" guarantee).

### Root C (out of scope here, evidence recorded) — the ~32s resume death

All three observed TMUX_SESSION_GONE deaths cluster at ~32s (32275ms Music
2026-06-10; 32443ms + 31732ms UMI 2026-06-11 — the race struck twice
back-to-back). Hypothesis: big-session `--resume` loading (~58s for 115k
tokens) starves the dev-channels bind, which times out ~30s and exits claude.
This is the known upstream channel-bind race (`docs/0.12.0-known-issues.md`);
the rc.25 auto-retry + history-preload contain it. NOT fixed by this spec —
folded into the known-issues TODO (the "channel subscribed" protocol signal).
Consequence worth recording: until upstream fixes it, an aged-big-session
resume on the channels backend likely dies and falls back to fresh+preload
regardless of dialog handling.

## Fixes

### Fix A1 — exclude keycap bases from solo-emoji detection (lib/telegram/parse.js)

A reply that is exactly one of `0-9`, `#`, `*` is TEXT, never a reaction.
Surgical guard before the emojiOnly branch; all genuine emoji behavior
(`👍` → reaction, `❤️`/`❤` → reaction, mapped emoji → sticker) unchanged.
Multi-char strings ("42", "ok", "4️⃣" keycap sequence) unaffected (already text).

Tests (red on current code): `parseResponse('4')` → `{text:'4', reaction:null}`;
same for `'7'`, `'#'`, `'*'`, and (review F5) `'4️'` = digit+VS16 — one stray
variation selector away from the same drop class. Guard: `/^[0-9#*]️?$/`.
Green-guards: `'👍'` stays reaction, `'❤️'` stays reaction, `'4️⃣'` stays text,
`'42'` stays text. Note: A1 fixes the SDK backend too — its reaction branch
currently calls setMessageReaction with `'4'`, which Telegram 400s and the
catch swallows (same silent loss, different layer). `©®™🅰` remain reactions
(pre-existing behavior, not the incident class; Telegram rejects them — out
of scope here).

### Fix A2 — thread the reply's source msg through to the dispatcher (cli-process.js)

In `_dispatchToolCall`, resolve the originating Telegram msg_id for the reply:
`args.turn_id` → InputLedger entry's `msgId` (entries are created with it at
send/inject time); fallback to the single pending turn's ledger entry (F7);
else null. Pass it as `sourceMsgId` in the `toolDispatcher` call — the
dispatcher already consumes it (no dispatcher change needed).

Effect: solo emoji replies become reactions ON the user's message (instead of
dropped); text replies gain reply-quoting parity with the dispatcher's design
intent. The existing `…-reactions-dropped` event remains for the
genuinely-unattributable case.

Review folds:
- **F1 — quote only the FIRST delivered reply per turn.** SDK fires
  deliverReplies once per turn (one quote); the channels dispatcher fires per
  reply tool call, and an N-reply turn must not produce N quote-headers all
  pointing at the same user message. A per-ledger-entry `_quoteUsed` flag set
  on `result.ok` (a FAILED delivery doesn't spend it — the retry still quotes).
- **F6 — coerce the ledgered msgId to Number** (ledger stores it stringified;
  every other delivery site passes numeric message_id).
- **F7 — the fallback resolves through the LEDGER** (pendingTurns entries carry
  no context): echoed turn_id → ledger entry; no echo + exactly one pending →
  that pending's ledger entry; else null. Strictly mirrors
  `_recordReplyForPendingTurn`, so quote/reaction attribution can never
  disagree with reply attribution (late replies correctly quote the OLD msg).

Tests (red→green): T15a turn_id→msgId (as Number); T15b single-pending
fallback; T15c unattributable → null (never misattribute); T15d second reply
of same turn does not re-quote.

### Fix B1 — suppress the resume dialog at spawn (cli-process.js `_spawnTmuxClaude`)

Pass `envExtras: { CLAUDE_CODE_RESUME_THRESHOLD_MINUTES: '525600' }` (1 year)
through `runner.spawn` for channels claudes. Age-gate then never trips → resume
is always "full session as-is" (the pre-dialog behavior; "conversation kept"
holds). Per-process env — does NOT touch the operator's interactive claude or
global `~/.claude.json` (`resumeReturnDismissed` stays untouched).

Why full-resume (decision): polygram's contract after the rc.34/35 /model fix
is "conversation kept". The dialog's compact default silently breaks it. Token
cost of full resume is the status-quo-ante cost; proactive compaction policy
already exists separately (`compactionWarnings`) and a per-chat resume policy
knob is YAGNI until someone asks.

Test: spawn-args unit test (existing `_spawnTmuxClaude` capture pattern from
the ledger tests) asserts envExtras carries the var.

### Fix B2 — belt-and-braces: gate fallback picks FULL, not compact

If the dialog still appears (upstream renames the env var or changes defaults
on a future binary bump), the `session-age` startup-gate trigger must select
option 2 ("Resume full session as-is") — key sequence `Down`,`Enter` — instead
of bare `Enter` (= compact), and emit a `session-age-dialog-fallback` event so
the env-suppression regression is visible in telemetry.

Requires `runStartupGate` trigger support for a key SEQUENCE (`keys: [...]`)
and a per-trigger `onTrigger` callback. Review folds:
- **F4 — the event fires AT TRIGGER TIME, not gate resolution.** The prod
  incident matched session-age and THEN died (TMUX_SESSION_GONE); a
  success-path check would miss exactly that. Sequence keys are sent as
  separate send-keys calls with a short inter-key delay (Ink dialogs can
  swallow the second key of a same-batch sequence).
- **F2 — the MID-TURN watchdog catalog gets the same treatment.**
  `MID_TURN_PROMPTS` had its own `session-age → bare Enter` entry (the F#17
  watchdog exists precisely because this dialog can render post-gate) —
  switched to the Down,Enter sequence + the same `session-age-dialog-fallback`
  event with `phase: 'mid-turn'`.

Tmux-backend's separate Enter-dismissal (tmux-process.js:2637) is legacy and
intentionally untouched.

Tests (red→green): gate keys-sequence + single-key back-compat; fire-time
onTrigger surviving a gate that later dies (TMUX_SESSION_GONE); mid-turn
watchdog Down,Enter + phase:'mid-turn' event; spawn envExtras assertion.

## E2E / verification

- Unit suites above (red→green surfaced per commit).
- Real-claude E2E (existing harness, `tests/e2e-channels-real-claude.test.js`):
  prompt engineered to elicit a bare single-digit reply ("Reply with exactly
  the character 4 and nothing else") → assert a text bubble reaches the fake
  TG sink. Covers A1+A2 wiring live.
- Dialog repro (manual, cheap): craft a synthetic aged session JSONL >100k-token
  estimate with timestamps >70min old; `--resume` it WITHOUT the env var →
  dialog appears (control); WITH the env var → no dialog. No real-usage burn
  beyond the spawn itself.
- Soak: watch `channels-tool-dispatcher-reactions-dropped` (should go ~zero),
  `session-age-dialog-fallback` (should stay zero), and the already_delivered
  / startup-auto-retry gates from rc.36.
- **Review F3 — measure the actual goal, not just the mechanisms.** All the
  above can pass while aged-big-session context is still lost to Root C (the
  ~32s bind death overlaps B1's trigger class: ≥100k tokens → slow resume).
  Add to the soak: the rate of `history-preloaded` events with
  `session_source: "fresh"` on sessions that HAD a resumable id — each one is
  a conversation polygram failed to carry over, whatever the mechanism. B1's
  measurable benefit for the >100k class may be near zero until Root C lands
  upstream; below-100k aged sessions (70min–100k band) get the full win now.
