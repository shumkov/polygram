## Workstream A — patience-model unification

Goal: replace 14+ uncoordinated patience timers with one `TurnPhase`
predicate fed by all signals; timers only **demote** on silence,
never **advance**; 3 wall-clock floors remain. See the solution doc
for the full design + the 3-commit migration plan.

| Commit | What | Status | rc |

## Workstream B — session continuity (independent bug chain)

Triggered while soaking Workstream A: the shumorobot Music topic was
losing conversation context. Three distinct, compounding bugs — all
shipped, all with red→green regression tests.

| rc | Bug | Fix | File |
|---|---|---|---|
| **31** | tmux orphan blocks respawn. Chat's `pm_backend` drifted tmux→sdk→tmux; polygram dropped its in-memory handle but the live tmux session kept running headless; next spawn collided ("duplicate session"). | Spawn-time reconcile: `sessionExists` → `killSession` → 50 ms settle → spawn, in `TmuxProcess.start()`. | `lib/process/tmux-process.js` |
| **32** | Backend flip discarded context. `pm_backend` was in `SPAWN_IDENTITY_FIELDS`, so any sdk↔tmux flip invalidated the session row. But both backends share the same on-disk JSONL — the flip is replayable. | Drop `pm_backend` from `SPAWN_IDENTITY_FIELDS` (keep `agent`, `cwd`). | `lib/db/sessions.js` |
| **33** | **The real one.** `onInit` upserted the session row from **chat-level** config only, ignoring **topic-level** overrides. Music topic (thread :3) → row written with chat-level `agent=shumabit` / `cwd=$HOME` / `pm_backend=sdk` (defaulted) instead of topic-level `music-curation:music-curator` / `.../Music/rekordbox` / `tmux`. Every turn re-poisoned the row → S2 drift fired → row dropped → fresh session → **context lost every single turn, forever.** | `onInit` resolves topic config the same way `buildSpawnContext` does (`getTopicConfig` + `pickBackend`), passes `pm_backend` explicitly. | `lib/sdk/callbacks.js` |

**Dependency**: #31 and #32 were prerequisites but **ineffective
without #33** — for any chat with a topic-level override, the row
got re-poisoned on the next spawn regardless. #33 is the linchpin.

**One-time production heal (done)**: the poisoned
`-1003807211164:3` row was manually deleted post-rc.33 deploy so the
next spawn re-upserts with correct topic-resolved values:
```
DELETE FROM sessions WHERE session_key='-1003807211164:3';
```

### Audit hint for OTHER topic-override chats

Any chat with `topics.<id>` overrides on `agent`/`cwd`/`pm` had the
same poisoning. After rc.33, each self-heals on its next spawn (the
row re-upserts correctly, and if the *resolved* config matches, drift
stops). To force-heal proactively:
```sh
# List rows whose stored identity disagrees with config — inspect
# by eye; delete any that look chat-level when they should be
# topic-level.
sqlite3 ~/.polygram/shumorobot.db \
  "SELECT session_key, agent, cwd, pm_backend FROM sessions \
   WHERE thread_id IS NOT NULL;"
```
