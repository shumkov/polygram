## Workstream A — patience-model unification

Goal: replace 14+ uncoordinated patience timers with one `TurnPhase`
predicate fed by all signals; timers only **demote** on silence,
never **advance**; 3 wall-clock floors remain. See the solution doc
for the full design + the 3-commit migration plan.

| **1b — persist phase-change** | `onPhaseChange` → `turn-phase-change` events in the DB, so the soak can verify the predicate trajectory against real traffic. | ✅ shipped | rc.30 |

| **3 — collapse `_runTurn` race** | 5-way `Promise.race` (+ nested re-wait) replaced with one `_awaitSettle` subscription. ## Workstream C — hook-based turn observability (H1 BUILT, not deployed)

Full design: `0.10.0-tmux-hook-observability.md`. **Pre-build spike
gates passed 2026-05-21** (all three checks against the pinned
2.1.142 binary with the Music-topic flag set):

- `--settings` hooks block layers in alongside `--strict-mcp-config
  --setting-sources project,local`. ✓
- Subagent inner Pre/Post carry `agent_id` + `agent_type` (NB:
  `parent_tool_use_id` doesn't exist on 2.1.142, `SubagentStart`
  doesn't fire for general-purpose subagents — design corrected; we
  don't depend on either). ✓
- Hooks are non-blocking by default — `sleep 2` × 6 firings added
  0 ms to a 3-tool turn. `async: true` not required. ✓

**H1 built (observer-only):**

If `unknown` event-type fires for `SubagentStart` on real Music
traffic (when the music-curator agent dispatches), record the
spike-2 conclusion was wrong-for-this-agent — does NOT block H1
since the design doesn't depend on `SubagentStart`. Just useful

**Why it exists.** Two things converged:
1. Ivan's reframe (2026-05-21): the tmux backend shows only "scary
   emotions" (reactor 🥱→😨→🤯) on long turns because it has no
   understanding of what the agent is doing inside — unlike the SDK
   backend, which streams typed events. He asked for a system that
   *understands* what's happening (agents running, tools, step
   completion) and *shows it properly* instead of scaring the user.
2. The motivating incident (msg 884, 2026-05-21 12:16): a
   `music-curator` subagent running "Run SoundCloud re-likes" was
   killed by the 30-min W1 wall-clock while **demonstrably alive** —
   its sidechain JSONL + debug-log kept writing until 12:35 (14 min
   past the kill). SoundCloud re-likes are DataDome-rate-limited, so
   the batch legitimately runs 45+ min. The predicate held
   `subagent-running` correctly the whole time; the dumb wall-clock
   W1 was the cliff edge. (Cross-channel silence on that healthy turn
   peaked at 233 s — above the patience-model doc's 180 s estimate.)

**The decision that got superseded.** Mid-investigation I asked Ivan
to choose a "progress-aware W1" deadline shape (idle ceiling vs
absolute). He reframed instead: don't tune timeouts — *understand the
turn*. The keystone is **Claude Code hooks** (PreToolUse/PostToolUse
fire INSIDE subagents, tagged `agent_id`/`agent_type`/
`parent_tool_use_id`; plus SubagentStart/Stop and an authoritative
Stop; injectable via `--settings` without user-config pollution;
`async:true`+`timeout:5` so they never slow the agent). With a hook
firing per tool step, "is the turn progressing?" stops being inferred,
and the timeout problem dissolves as a side effect.

**Phased plan** (see the design doc): H1 emit+observe (no behaviour
change) → H2 feed the reactor (kills the fear) → H3 feed
progress+deadline (retires the timeout) → H4 authoritative completion
(`Stop`). H1's spike must first confirm `async`/`SubagentStart` behave
on the pinned 2.1.142.

detail — exact field names, settings schema, the verified binary

## Known-not-fixed (deliberate)

- **Commit 3 deploy** — built + committed (`02358dd`), held undeployed
  pending rc.34 soak. Ships as rc.35 with its own soak.
- **Commit 3b** — full §6→`wedged`-timer deletion + `system
  turn_duration` parsing. Largely **subsumed by Workstream C / hook
  H4**: the `Stop` hook is a better authoritative-completion signal
  than a quiet→wedged timer. Revisit only if hooks don't pan out.
- **Progress-aware W1 (timeout tuning)** — explicitly **abandoned** in
  favour of Workstream C. Hooks make progress observable rather than
  inferred, so the deadline becomes "no hook event for N min =
  wedged" with no config gymnastics. Do NOT resurrect the idle-vs-
  absolute timeout debate; build hooks instead.
- **Drift-time teardown (orphan fix #2 from the brief)** — skipped.
  rc.31's spawn-time reconcile covers the orphan case from any
  source; #2 is redundant unless an orphan pile-up emerges that
  spawn-time reconcile doesn't catch.
- **The LogTail batch-flake** (`useWatch:true …` + `16MB-buffer …`)
  — pre-existing, passes 15/15 in isolation, fails intermittently in
  the full-suite batch run. Not a regression; not chased.
- **B9 garbled approval-menu detection** — orthogonal; Music is
  `bypassPermissions` so doesn't trigger it. Tracked in the
  concurrency-leftovers doc.
- **Tmux control mode (`tmux -CC` / `-C`)** — TODO, deferred behind
  hooks. The current backend shells out individual `tmux` subcommands
  (`new-session`, `send-keys`, `set-buffer`, `capture-pane`) and
  polls `capture-pane` every 50 ms. Control mode would stream
  `%output` / pane-state events instead, dropping the steady-state
  poll cost and giving us push-based pane I/O. Does **not** replace
  hooks — control mode tells us tmux's view of the pane (output
  bytes, window events); it doesn't surface what claude is doing
  inside (tools, subagents, completion). Hooks own that. Revisit
  only after H1/H2/H3 ship and only if `capture-pane` polling shows
  up as a real CPU/throughput cost in production. Useful pointer:
  <https://github.com/tmux/tmux/wiki/Control-Mode>.
