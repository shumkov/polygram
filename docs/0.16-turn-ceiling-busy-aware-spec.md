# Spec — Busy-aware turn ceiling: extend-while-working, don't abandon (#15)

Status: **BUILT + code-reviewed (NO-SHIP finding fixed) — shipping 0.16.0.** Two spec-review rounds + one code-review round.

## Code-review outcome (folded)
- Fixed #1 (was NO-SHIP): `classifyTurnEndError` must keep the legacy message regex as a fallback — SDK/tmux backends reject timeouts with a MESSAGE and no err.code, so branching on code alone flipped their timeouts from ⏱ TIMEOUT to scary ERROR. Regex fallback restored + regression-tested.
- Fixed #2: `_checkpointAbsolute` re-checks `_stopGracePending`/replies/consumed-acked AFTER the async probe (a turn can enter finalization during the capture-pane round-trip → don't resurrect/ping it).
- Fixed #4: progressPings precedence (per-chat overrides default).
- **Accepted limitation (#3):** the MF-A progress signals (`_lastActivityAt`, shared tmux pane) are process-scoped, so under CONCURRENT pending turns on one CliProcess a zombie turn could look like it's progressing because a sibling is active. Bounded by the hard max (it still terminates), and concurrent turns are abnormal (stdinLock holds one turn per session). Documented, not fixed.

Target: polygram 0.16.0.

## v3 changelog (folded review must-fixes)
- **MF-A (load-bearing):** the `working` test must require **evidence of progress**, not just a shell's existence — a hung/zombie `run_in_background` shell keeps `shellCount>0` forever and would extend to the hard max. Extend only if the pane content / `_lastActivityAt` **advanced since the previous checkpoint**. Reuses the existing `activitySince` idiom (cli-process.js:1687) + `_lastActivityAt` (1726). Store `pending._lastCheckpointAt` / `_lastCheckpointPaneHash`.
- **MF-B (fleet regression):** an extended in-flight turn is **unevictable** (`_evictLRU` skips inFlight, process-manager.js:313) and the in-flight escape valve is a **5-min reject** (`_awaitLruSlot`, :366), so concurrent long turns can **starve other chats**. Fix: once a turn extends past its FIRST checkpoint, treat it as a **soft-overflow pin** in `getOrSpawn` (spawn-over-budget + warn, same as background-job pins at :261) instead of park-then-reject; emit an `lru-overflow-extended` event. Default lowered (MF-D) to bound the window.
- **MF-C (interrupt race):** the re-arm MUST reassign `pending.absoluteTimer = setTimeout(...)` (so teardown sites clear the live handle) AND the async checkpoint MUST re-check `this.pendingTurns.has(turnId)` AFTER the `await probeBusyState()` (the turn can resolve/abort/kill during the capture-pane round-trip — TOCTOU).
- **MF-1 (control flow):** `fireTimeout` tears down synchronously at the top today; the probe-then-decide path must be a dedicated **async `_checkpointAbsolute(turnId, pending)`** that awaits the probe BEFORE teardown, leaving the synchronous idle/zero-reply reject path intact.
- **MF-2 (event wiring):** `turn-extended` needs a `CALLBACK_TO_EVENT` row (`onTurnExtended`) + an `onTurnExtended` handler in `lib/sdk/callbacks.js` modeled on `onBgWorkStatus` (the one-time-keyed tg send), else the ping fires into the void.
- **MF-D:** default `turnHardMaxMs` = **5_400_000 (90 min)**, not 3h (bounds the MF-A/MF-B blast radius); per-chat override for the music topic.
- **MF-3:** current `CODES.TURN_TIMEOUT` copy is `'⏱ This one ran past its time cap with no reply. Resend if the answer still matters.'` (the "before"); reword as in §2.2.
- Soak note: `turn-timeout-pane` data is sparse (VPS: 1 event; shumorobot pre-0.13) → can't statistically validate the busy heuristic, which is WHY MF-A (progress-delta, robust by construction) is mandatory rather than relying on streaming/shell alone.

Origin: user reports recurring "⚠️ stream interrupted / ⏳ I went quiet too long" on long music-download turns (shumorobot, **cli backend**, session -1003807211164; "wall-clock ceiling" ×4 over 06-19/06-20). v1 (message-only) was reviewed and rejected: it renamed the failure instead of fixing it, and a single `stillWorking` boolean produced false affordances ("ask how it's going" while foreground-busy; "/stop" that no-ops). v2 = the real fix the reviews pointed to: **keep waiting while the turn is provably working, bounded by a hard max; only message when we genuinely give up.**

## 1. Problem (verified)
`cli-process.js` arms per-turn: an **idle cap** (`maxTurnMs`, resets on any activity — for an active download it keeps getting pushed out, so it rarely fires) and an **absolute ceiling** (`turnAbsoluteMs`=30min, NO reset, fires 30min after turn START regardless). A long download stays active, so the absolute ceiling fires first and, with zero delivered replies, `reject()`s `TURN_TIMEOUT` (line 2167) → polygram caps the bubble with "stream interrupted" + the dispatcher sends classify()'s timeout copy.

polygram does NOT kill claude on the cli TURN_TIMEOUT (process-manager kills only on config-reload/shutdown/evict/abort/bridge-disconnect) — the process stays warm, the download keeps running — but the **turn slot is freed and the turn promise rejected**, so the eventual answer is orphaned (delivery then depends on claude re-emitting a reply to an abandoned turn) and the bubble shows a scary, false "interrupted". The ceiling already runs `probeBusyState()` → `{streaming(=esc-to-interrupt), backgroundShell, shellCount}` but only logs it.

(Backend note: this fix is **cli-only**. The SDK backend has no pane to probe and its ceiling genuinely calls `query.interrupt()` (sdk-process.js:538) — a separate fix, out of scope; tracked under #15 follow-up.)

## 2. Design — bounded extension (option 2)
Repurpose the absolute timer from a one-shot 30-min guillotine into a **liveness checkpoint** that re-arms while the turn is provably working, capped by a hard max.

### 2.1 `cli-process.js` — checkpoint logic at the absolute timer
At turn start, record `startedAt`. When the absolute timer (`turnAbsoluteMs`, the checkpoint interval, default 30min) fires:
1. Run `probeBusyState()` ONCE (merge the existing telemetry probe at ~2156 — no double `captureWide`). Log `turn-timeout-pane` with `still_working`.
2. `elapsed = now - startedAt`. `working = probe.streaming || probe.backgroundShell || probe.shellCount > 0`.
3. **If `working && elapsed < turnHardMaxMs`** → `clearTimeout` + **re-arm the absolute timer** for another `turnAbsoluteMs` window. Do NOT reject; the turn stays pending, the bubble stays live, `inFlight` stays true (so `/stop` keeps working). Emit `turn-extended` once-per-turn-flagged for the first extension (drives §2.3 progress ping). Loop.
4. **Else** (not working → wedged/idle, OR elapsed ≥ hard max) → reject as today, with the code picked by reason:
   - not working → `err.code = 'TURN_TIMEOUT'` (genuinely stuck)
   - hit hard max while still working → `err.code = 'TURN_MAX_EXCEEDED'`
   The synchronous cleanup (delete pending, free `inFlight`, emit `idle`) runs before the (async, post-probe) reject — same ordering the v1 feasibility review confirmed safe.

The replied-turn graceful-resolve at line 2118 is unchanged (a turn that delivered replies still resolves at the checkpoint, never extends into a reject).

New config (per-chat/topic, like `maxTurn`): `turnHardMaxMs` ← `chatConfig.maxTurnHard` (sec) → ms, **default 10_800_000 (3h)**. Plumbed in polygram.js alongside `maxTurnMs` (the line-512 resolver) and passed via `pm.send` opts.

### 2.2 `lib/error/classify.js`
- `CODES.TURN_TIMEOUT` (stuck): reword → `'⏱ This one went quiet with no progress — send /stop, or resend if the answer still matters.'`
- New `CODES.TURN_MAX_EXCEEDED`: `{ kind:'turnMaxExceeded', userMessage:'⏱ This ran past the max time and I had to stop it. Resend if you still need it — or break it into smaller steps.', isTransient:false, autoRecover:null }`
Typed-code short-circuit (classify.js:252) ensures these win over PATTERNS. The dispatcher already sends `classify(err).userMessage`.

### 2.3 Progress ping (honest "still working") — once per turn, first extension only
On the first `turn-extended`, polygram sends ONE subtle message: `'⏳ Still working on this — it's taking a while. Send /stop to cancel.'` (NO "ask how it's going" — foreground-streaming can't answer; the review's F1). Gated by `chatConfig.progressPings !== false` (default on). This is the user's "tell me it's still working" ask, made honest: it only fires when the probe CONFIRMS active work, the bubble is genuinely live, and `/stop` genuinely works (turn still in-flight).

### 2.4 `polygram.js` (~1713 catch) — branch on code
Extract the suffix/reactor decision into a small pure helper `classifyTurnEndError(err)` → `{ errorSuffix, reactorState }` so it's unit-testable (the review noted the catch is not unit-reachable):
- `TURN_MAX_EXCEEDED` / `TURN_TIMEOUT` → keep current terminal handling (suffix `'stream interrupted'` is acceptable here — the turn really did stop), reactor ERROR. (Correct the v1 claim: cli `err.message` is `turn timeout (...)`, which does NOT match the line-1715 regex, so cli already sets ERROR not TIMEOUT — branch on `err.code`, not the regex.)
- The abort/shutdown/replay quiet-finalize guard (1696) is untouched.

## 3. How v2 resolves the review findings
- **F1 (false "ask how it's going")** → no such copy; the only mid-turn message is "still working — /stop", honest for every busy sub-state.
- **F2 (answer never arrives)** → turn stays PENDING through extension; claude's reply resolves the SAME turn/bubble. No orphan routing.
- **F3 (/stop no-op)** → turn stays in-flight during extension → `/stop` interrupts normally.
- **F4 (permanent stale msg)** → no "still working" terminal state; the live bubble is the signal; terminal message only on real give-up.
- **F5 (zombie/stale-pane false-busy)** → bounded by `turnHardMaxMs`; a turn that fakes "busy" forever is still cut at the hard max.
- **F6 (band-aid)** → this IS the structural fix (don't abandon an active turn).
- Feasibility: single merged probe; async-reject ordering safe; classify short-circuit; reactor branch on code; testable helper.
