# 0.13 — Telegram `/rewind` (conversation rewind) — spec

**Status:** design for review (not implemented). Gated on a P0 spike (below) that
proves the core mechanism on the pinned CLI before any feature code.
**Origin:** operator idea (2026-06-09) — "reply to my message with `/rewind`; you run
it when the turn ends; use esc-esc, or any claude-CLI option if one exists."

---

## ⚠️ Scope boundary — read this first

`/rewind` reverts the **conversation** — claude's memory of the turns, and the visible
chat. It does **NOT undo real-world side-effects** claude already performed: files
created in Google Drive, a published Sheet, emails sent, external API calls. Those
persist. claude's own checkpoints track **file edits only** (snapshots before its edit
tools), not bash side-effects and not external systems (confirmed in the CLI docs).

So `/rewind` means **"take back what was said and re-decide from here,"** not **"undo
what the bot did in the world."** (The hiring incident's Drive folder + Sheet would
still exist after a rewind — claude would just forget it made them.) Undoing actions is
a *separate* feature and out of scope here; if both are wanted, `/rewind` can end by
asking claude "you've been rewound to before X — do you want to reverse anything you did?"

## UX

- The operator **replies to one of their own past messages `M`** with the text `/rewind`.
- `M` is the rewind target: the conversation is restored to **just before `M`** — claude
  forgets `M` and everything after; the chat is trimmed to match.
- Executes **after the current turn ends** (you can't rewind a live turn — the transcript
  is mid-write and the agent is busy). polygram queues it and fires on turn-resolved.
- Confirmation back to the chat: "⏪ Rewound to: «first line of M». N messages removed."

## What the claude CLI actually offers (investigation, 2026-06-09)

- **Esc-Esc / `/rewind`** opens an interactive rewind menu — **TUI-only**. There is **no
  programmatic/headless API** and **no way to target a checkpoint by id**; the menu is
  positional (arrows + Enter). Actions: restore code+conversation / conversation / code,
  or summarize.
- **Checkpoints** = per-prompt snapshots of **file edits only** (not bash effects, not
  external systems). Persist across resumes; 30-day cleanup.
- **`--fork-session`** (with `--resume`/`--continue`) creates a **new session id** from a
  resume point — a documented flag.

## Approaches

### A — drive the native rewind UI (Esc-Esc via tmux send-keys)
claude runs in a tmux pane (TUI) on the channels backend, so polygram can: ensure the
prompt is empty (`Esc`), open the menu (`Esc Esc`), navigate to the target prompt, pick
"Restore conversation", confirm. **Fragile:** the menu is positional — there's no way to
say "go to message M"; polygram would have to capture-pane + parse the menu and count
keypresses, handle render timing, and re-map TG messages → menu rows (autosteer batching
breaks the 1:1). Uses claude's own (correct) rewind logic, but the automation is brittle.

### B — transcript fork + resume (polygram-side) — **recommended**
polygram already owns the session (it manages `claude_session_id` + `--resume` + the
ghost-session guard). The session transcript is a JSONL whose user entries carry the
`<channel … msg_id="M">` wrapper — so polygram can find the **exact** cut point
deterministically (no positional guessing):
1. Locate the transcript entry wrapping `msg_id="M"`; the cut is the clean **turn
   boundary just before it**.
2. Write the prefix to a **forked session id** (`--fork-session` semantics) — original
   preserved, new id = the rewound conversation.
3. Update polygram's session → `claude_session_id` mapping to the fork.
4. Kill the live claude proc; respawn with `--resume <fork>`.

Deterministic target, no TUI fragility, fits polygram's existing resume machinery. The
cost: it reads/writes claude's **transcript JSONL, an undocumented format** — the main
risk (below).

### C — ask claude to "rewind itself" — rejected
claude can't remove its own prior turns from its context; telling it to "pretend we're
back at M" leaves the context intact. Not a real rewind.

## Recommendation

**B**, gated on the P0 spike. The deterministic `msg_id` → cut-point mapping (via the
`<channel msg_id>` wrapper already in the transcript) is the decisive advantage over A's
positional TUI navigation, and it reuses the `--resume` path polygram already trusts.

## Design (Approach B)

| Step | Detail |
|---|---|
| Trigger | inbound message, reply-to `M`, text `/rewind` (admin-gated — only the paired operator). Distinct from the `ask` free-text path. |
| Defer | enqueue `{sessionKey, targetMsgId}`; execute on the next `stop-hook`/turn-resolved for that session (reuse the turn-end signal the question keep-alive already hooks). Never mid-turn. |
| Locate cut | read the session JSONL; find the user entry containing `msg_id="M"`; cut at the turn boundary immediately before it (no dangling `tool_use` → must end on a complete assistant turn). |
| Fork | `claude --resume <old> --fork-session` *or* copy the JSONL prefix to a new id; record the new `claude_session_id` for the sessionKey. |
| Respawn | `pm.kill(sessionKey)` → next message (or an immediate synthetic resume) spawns on the forked session. |
| TG cleanup (opt) | delete the bot's messages after `M` (always allowed) + the operator's (only if the bot is admin) so the chat matches. |

## Hard parts / risks

- **Undocumented transcript format** — the JSONL shape isn't a public API; a CLI upgrade
  could change it. Mitigate: pin to the tested CLI version, add a format-sanity check, and
  **fail safe** (no-op + alert the operator) if the structure is unrecognized rather than
  corrupting a session.
- **Clean turn boundary** — cutting mid-turn orphans a `tool_use` (claude expects its
  `tool_result`). Cut only at complete-turn boundaries.
- **`msg_id` → transcript mapping** under autosteer — several TG messages can fold into one
  claude prompt; the cut must land on the prompt that *contains* `M`.
- **TG deletion asymmetry** — the bot deletes its own messages freely; the operator's only
  if the bot is a group admin. Document that user messages may remain visible.
- **Backend scope** — cli/channels only. The SDK backend holds the conversation in-process
  (no on-disk JSONL to fork); out of scope (or a separate mechanism).
- **Concurrency** — a `/rewind` racing a newly-arriving turn; the deferral + a per-session
  lock handle it.

## Phased plan

- **P0 — spike (gates the feature).** On the pinned CLI (2.1.158): confirm the transcript
  JSONL location + shape, that `--fork-session` (or a hand-truncated prefix) resumes a
  rewound conversation cleanly, and that `<channel msg_id>` is reliably present to locate
  the cut. If B fails the spike, fall back to A (TUI) or shelve. **No feature code before P0.**
- **P1** — `/rewind` detection + admin gate + turn-end deferral + the confirmation message.
- **P2** — locate-cut + fork + respawn (the core).
- **P3** — Telegram message cleanup (bot's own; operator's if admin).
- **P4** — UX polish: preview of the target, "N messages removed", and the optional
  "want me to reverse anything I did?" prompt for side-effects.

## Open questions

1. **Fork vs truncate-in-place?** Fork preserves the original transcript (safer, auditable);
   truncate is simpler but destructive. Lean fork.
2. **Trigger surface** — `/rewind` reply only, or also a reaction (e.g. ⏪) on a message?
   `/rewind` reply is unambiguous; esc-esc isn't expressible over Telegram, so it's an
   internal *mechanism* (approach A) at most, not the user trigger.
3. **Side-effect reversal** — keep strictly out, or add the end-of-rewind "reverse actions?"
   prompt (P4)?
4. **Scope of cleanup** — delete bot messages after M always, or only on explicit `/rewind --clean`?
