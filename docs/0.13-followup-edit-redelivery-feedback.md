## What the operator reported

disabled" — connecting it to the reactions-disappear diagnosis (the Music topic,

## Finding (so the handoff is accurate, not alarmist)
edit-redelivery (`lib/handlers/edit-redelivery.js`) re-dispatches a post-turn edit
as a synthetic `_isReplay` message via `dispatchHandleMessage(...)` →
`handleMessage(...)` — **the same intake path as a normal message**. `_isReplay`
only changes:
- the error-path terminal status (`lib/handlers/dispatcher.js:165` — replay vs failed)
- replay-eligibility / no new editable row (`polygram.js:694`)

It does **NOT** suppress reactor/typing. So the edit re-turn arms the per-turn
reactor + typing exactly like any turn. The pre-turn `👀` ack
(`edit-redelivery.js:82`, set outside the reactor on the edited msg_id) then hands
off to the synthetic turn's reactor (`👀 → 🤔 → tool → clear`), reusing the same
edited msg_id.

**Conclusion:** edit-redelivery does not introduce a new feedback suppression. It
**inherits ROOT C (feedback parasitic on the turn object) / S7 (feedback dies with
the turn object)** — identical to every other cli turn. When claude replies early
then keeps working (the S7 case), the edit re-turn goes dark for the same reason a
normal turn does.

## ANSWERED (2026-06-10, #15 implementation session — P1–P4 merged as 6a45152)

**Q1 — does D3/D1 cover synthetic `_isReplay` turns? YES, structurally.** An
edit re-turn flows through `dispatchHandleMessage → handleMessage` and gets the
same per-turn reactor/typing as any turn; under D1 (P1, the finalizer ladder)
that turn now stays pending to claude's REAL cycle end (attributed Stop /
activity-quiet), so the S7 keep-working-after-finalize dark window is closed
for edit re-turns exactly as for normal turns — same mechanism, no special
case. The 👀-ack → reactor handoff has no gap: the ack is a single
`setMessageReaction` that the synthetic turn's reactor then overwrites on the
same msg_id (`👀 → 🤔 → tool states`); the reactor serializes its own applies
(applyChain), and the worst case is a momentary 👀→🤔 flicker, never a stuck
👀 (the reactor always lands after).

**Q2 — the S7 case on an edit re-turn specifically.** Pinned by the P1 suite:
the WA-shape late-tool test + the reply-then-ask test
(tests/cli-process-finalizer-ladder.test.js) assert a replied turn survives
post-reply tool work / ask-waits — synthetic turns share that code path
end-to-end (no `_isReplay` branch exists anywhere in the turn-lifecycle or
feedback plane; verified by grep — `_isReplay` only touches dispatcher error
status + replay-eligibility + row creation). The real-claude E2E
`e2e/D1: reply-then-ask` exercises the keep-working shape live.

**Note for the operator's original report** ("edit starts sending but reaction
+ typing are disabled"): pre-0.13 that was the S2/S7 premature-finalize class —
fixed by P1 for all turns including edit re-turns. If it recurs post-deploy,
the soak query is `reactor-state` rows for the edited msg_id around the
re-turn; zero rows after `edit-redelivered` would falsify the analysis above.
