# 0.8.0 Architecture Decisions (Phase C)

Consolidates Phase B (spike) findings into the canonical answers
Phase 1 implementation will follow. Cross-references to v4 plan
sections (`docs/0.8.0-sdk-migration-plan.md`) and spike gate results
(`docs/0.8.0-phase0-findings.md`).

## Decisions

### D1. Streaming model: cumulative `SDKAssistantMessage`

**Source:** Phase 0 gate 3 PASS — without `includePartialMessages: true`,
2 distinct assistant events arrived for a 3-paragraph reply.

**Decision:** Pm subscribes to `SDKAssistantMessage` only. No
`SDKPartialAssistantMessage` deltas. `extractAssistantText` rewires to
consume `event.message.content[]` text blocks (cumulative within a
message id, like today's stream-json shape — minimal change to
`lib/stream-reply.js` integration).

**Resolves v4 plan §1 architecture choice (gate 5).**

### D2. Long-lived Query per chat

**Source:** Phase 0 gate 1 PASS — three sequential messages on one
Query produce three distinct ordered `SDKResultMessage` events.

**Decision:** Pm holds one Query per active sessionKey for the chat
lifetime. `inputController` is the writable end of an
`AsyncIterable<SDKUserMessage>` open for the chat session;
`pm.send()` pushes onto it. Same pendingQueue FIFO correlation as
today.

**Resolves v4 plan §1 + Phase 0 gate 1.**

### D3. `/effort` no longer needs respawn — DELETE `requestRespawn` machinery

**Source:** Phase 0 gate 19 PASS —
`applyFlagSettings({effortLevel: 'high'})` live-changes effort
mid-session without error.

**Decision:** Phase 4 step 4 **deletes** `requestRespawn`,
`onRespawn`, `_killAndNotifyRespawn`, `needsRespawn` from pm AND
their call sites in polygram.js. Phase 3 step 3 `/effort` handler
calls `pm.applyFlagSettings(sessionKey, { effortLevel: X })` instead.

**Resolves v4 plan seam A (canonical: gate 19) — was PROVISIONAL,
now DELETE.**

### D4. `/model` mid-session via `setModel()`

**Source:** Phase 0 gate 16 PASS — `query.setModel('claude-sonnet-4-6')`
mid-conversation succeeds.

**Decision:** Phase 3 step 2 calls `pm.setModel(sessionKey, model)`
which delegates to `query.setModel()`. polygram.js posts confirmation
immediately (no drain wait); model change applies to NEXT user turn,
not the in-flight one (per SDK docstring).

**Resolves v4 plan §7 Phase 3 step 2.**

### D5. `Options.env` is SHADOW — explicit allowlist required

**Source:** Phase 0 gate 33 PASS — Options.env replaces `process.env`
entirely; the spike's `process.env.SPIKE_MARKER` was NOT visible to
spawned bash because Options.env didn't include it.

**Decision:** `buildSdkOptions` (per v4 plan §6.5.7) must explicitly
include:
- `HOME = CHILD_HOME` (for ~/.claude/* resolution)
- `CLAUDE_CHANNEL_BOT = BOT_NAME` (history skill scopes by this)
- `POLYGRAM_IPC_SECRET` (when set; cron-driven Claude jobs need it)
- `TELEGRAM_BOT_TOKEN` (only if `config.bot.needsToken === true`)
- The full `filterEnv(process.env)` allowlist (matches today's
  CHILD_ENV_ALLOWLIST + CHILD_ENV_PREFIXES).

**Drop** from passthrough: `POLYGRAM_BOT`, `POLYGRAM_CHAT_ID` (were
only consumed by `bin/approval-hook.js` which Phase 4 deletes).

**Resolves v4 plan §6.5.7 commitment.**

### D6. `Query.close()` is fast — shutdown bounds are not a problem

**Source:** Phase 0 gates 30 + 32 PASS — Query.close() returns in
0ms across 5 samples.

**Decision:** Today's `process.exit(0)` after 100ms post-drain
(polygram.js:2862) is safe. Plan §6.6 M6's "p99*3 hard ceiling 15s"
is over-engineered. Set `shutdownExitTimeoutMs = 1000ms` (10× headroom
over observed close latency); Phase 5 monitors actual close
durations.

**Resolves v4 plan §6.6 M6 + Phase 0 gates 30/32.**

### D7. `pm.killChat` uses Promise.allSettled per-Query

**Source:** v4 plan §6.6 H6 + Phase 0 gates 30/32.

**Decision:** `pm.killChat(chatId)`:
1. Find every entry in `procs` whose sessionKey starts with `chatId`.
2. Per entry: `Promise.race([entry.query.close(), timeout(5000)])`.
3. Wrap all in `Promise.allSettled` (NOT `Promise.all`) so one slow
   close doesn't block the others.
4. Whether each close resolved or timed out, `procs.delete(sessionKey)`
   and emit `evict-close-timeout` on the slow path.

**Resolves v4 plan §6.6 H6.**

### D8. `pm.drainQueue(sessionKey, errCode)` — drain owned by pm

**Source:** v4 plan seam H + Phase 1 step 3 commitment.

**Decision:** New pm public method `drainQueue(sessionKey, errCode)`
rejects every pending in `pendingQueue` (head + queued) with
`Error('drained:' + errCode)`. polygram.js `/stop` handler calls
`pm.interrupt()` then `pm.drainQueue(sessionKey, 'INTERRUPTED')`.
Seals encapsulation — pendingQueue stays internal to pm.

**Resolves v4 plan seam H.**

### D9. Resume uses `claude_session_id` from the existing `sessions` table

**Source:** Phase 0 gate 26 PASS — `resume: sessionId` works across
separate `query()` calls.

**Decision:** No schema change. polygram's `sessions.claude_session_id`
remains the resume key. pm captures `event.session_id` from the SDK's
`init` system event (same shape as today's stream-json) and writes
via `db.upsertSession()`.

**Resolves v4 plan Phase 0 gate 26.**

### D10. Settings sources: rely on SDK 0.2.123 default (loads all)

**Source:** v4 plan §0 row + audit findings.

**Decision:** **Don't set `settingSources` explicitly.** Current SDK
default loads `'user' | 'project' | 'local'`. Setting an explicit
allowlist would be MORE restrictive than default (would skip
`local` = `~/.claude/settings.local.json` operator allowlists). If
Phase 0 gate 11 (manual verification) shows memsearch hook doesn't
fire under default, revisit.

**Resolves v4 plan §0 settingSources contradiction.**

### D11. `stdinLock` likely deletable

**Source:** Phase 0 gate 1 PASS (3 messages produce 3 ordered results).
Gate 2 (5-message stress) was killed by OAuth contention but inferred
PASS.

**Decision:** **Drop `lib/async-lock.js`'s stdinLock from polygram.js.**
SDK's `streamInput` queues messages internally; FIFO is preserved at
the Query level. If Phase 5 soak shows ordering issues, re-add a
per-session lock around `inputController.push()`.

**Resolves v4 plan seam B.**

### D12. canUseTool spec stands as written

**Source:** Phase 0 gate 9 FAIL (harness issue, not SDK bug). v4 plan
§4 + §6.5.3 specs the canUseTool flow + approval-waiters module.

**Decision:** Implement per v4 plan §4 + §6.5.3. Hand-test during
Phase 2 via real Telegram bot once polygram.js is wired. The plan's
canUseTool architecture (Map, signal cleanup ordering, 5 cleanup
paths, `'addRules'` PermissionUpdate) is correct.

**Resolves v4 plan §4 + Phase 0 gate 9.**

### D13. error-classify.js extends in Phase 1 + Phase 2

**Source:** v4 plan §3.1 + §6.5.1 + 0.7.7 ship.

**Decision:** Layered ship order:
- 0.7.7 (already shipped): transport-agnostic patterns + classify()
  signature + CODES short-circuits (QUEUE_OVERFLOW, INTERRUPTED stub).
- Phase 1: extend with SDK error subtypes (already in 0.7.7's
  SDK_MESSAGE_ERROR_MAP / SDK_RESULT_SUBTYPE_MAP — works today, just
  fires under the new pm). Add `INTERRUPTED` typed match in pm via
  `err.code = 'INTERRUPTED'` set on Query.interrupt() rejections.
- Phase 2: wire AUTO_RECOVER actions to `pm.resetSession()`.

**Resolves v4 plan §6.5.1 layered-ship.**

### D14. Per-chat agent fallback via `lib/agent-loader.js`

**Source:** v4 plan §6.5.5 + Phase 0 gate 15 (DEFER — production-
critical for shumabit).

**Decision:** Phase 1 step 14 implements `lib/agent-loader.js` per
v4 §6.5.5 sketch. Phase 0 audit task (TBD with operator approval):
`SELECT chat_id FROM chats WHERE config_json LIKE '%"agent"%'` to
enumerate which chats pin which agents on shumabit. Each must
compose successfully via `loadAgent() + composeSdkOptions()`.

If any chat's pinned agent fails to compose: keep `POLYGRAM_USE_SDK`
unset on the bot it lives in (so the affected chat falls back to
the CLI path automatically). Roll the env-flag forward only after
0.8.x adds proper agent loading.

**Note (corrected 2026-04-29):** original v4 plan said "ship to
umi-assistant only" — wrong direction. Per the project rule,
shumabit is the testing-first bot (Ivan's DM); umi-assistant is
partner-facing and gets new flags last. See memory entry
`feedback_polygram_rollout_order.md`.

**Resolves v4 plan §6.5.5 + Phase 0 gate 15.**

### D15. Migration 010 schema with three-state match_type

**Source:** v4 plan §6.5.4.

**Decision:** Implemented as Phase 1 step 1. Adds `tool_use_id TEXT`
column to `pending_approvals` + `chat_tool_decisions` table with
`match_type CHECK ('exact' | 'prefix' | 'regex')`. Default UI button
posts with `match_type: 'exact'`; "Always allow this command" posts
with `prefix`; `regex` is power-user only (not exposed in UI for
0.8.0).

**Resolves v4 plan §6.5.4.**
