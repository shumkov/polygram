## Findings (severity-ranked)

### HIGH — none.

No DB write shape, transaction boundary, or status-state-machine

### MEDIUM — `polling_state.last_update_id` is not monotonically guarded against decrease

- File: `lib/db.js:506-512` (`savePollingOffset`).
- The UPSERT is unconditional: `ON CONFLICT(bot_name) DO UPDATE SET
  last_update_id = excluded.last_update_id`. If two polygram processes
  for the same bot were briefly co-alive (launchd respawn race,
  manual `npm i -g` restart that overlapped a still-draining old
  process), the second poller's older `last_update_id` could
  overwrite a newer one — re-replaying already-handled updates after
  the older process died.
- Real-world likelihood: low. Telegram's getUpdates returns 409 to
  the second poller (`lib/handlers/poll.js:98` handles this with a
  3s sleep), so the second poller never gets a batch of its own to
  persist. **The 409 path in poll.js is what saves us — not the DB
  layer.** This is a defense-in-depth gap, not an active bug.
- **NOT introduced by 0.9.0-cleanup.** The `savePollingOffset` shape
  has been unchanged since migration 005 in 0.6.x; the move from
  polygram.js → `lib/handlers/poll.js` is verbatim (same call site:
  `dbWrite(() => db.savePollingOffset(botName,
  updates[updates.length - 1].update_id), 'save polling offset')`).
- **Operator query — detect a backwards-jump (would only catch
  it after the fact, since UPSERT overwrites):**
  ```sql
  -- Run from any bot DB. If a bot's last_update_id ever went
  -- backward, you'd see it in the events table as anomalous
  -- replays. There is no audit trail in polling_state itself —
  -- consider this a known structural limitation.
  SELECT bot_name, last_update_id, datetime(ts/1000, 'unixepoch') AS saved_at
    FROM polling_state;
  -- Cross-check for replay anomaly: handler-error events
  -- spiking shortly after a known restart timestamp.
  SELECT datetime(ts/1000, 'unixepoch') AS at, kind, COUNT(*)
    FROM events
   WHERE kind IN ('handler-error', 'replay-on-boot')
     AND ts > (strftime('%s','now') - 86400) * 1000
   GROUP BY kind, strftime('%Y-%m-%d %H:%M', ts/1000, 'unixepoch')
   ORDER BY ts;
  ```
- **Recommendation (out of scope for 0.9.0-cleanup but worth a
  follow-up):** add a `WHERE excluded.last_update_id >
  polling_state.last_update_id` guard to the UPSERT, so a stale
  writer is a no-op rather than a regression. Migration would be
  one-line, no data backfill needed.

### LOW — auto-resume's deliverReplies does not inspect `failed[]` (pre-existing; not introduced by extraction)

- File: `lib/handlers/dispatcher.js:122-132` (`attemptAutoResume`).
- The normal handleMessage path inspects `r.failed.length` after
  `deliverReplies` and surfaces a partial-delivery warning to the
  user (`polygram.js:1269-1278`, `telegram-stream-redeliver` event).
  Auto-resume's `deliverReplies` (lines 122-132) just `await`s and
  ignores the return value.
- Effect: if 1+ chunks of an auto-resume reply fail to send, the user
  sees a partial reply with no warning, AND `auto-resume-success` is
  logged. The DB's `messages` table for that turn ends up with
  `status='failed'` rows for the missing chunks (handled correctly
  by `tg`'s write-before-send), so the integrity story for the table
  itself is fine — it's only the user-facing signal that's lost.
- **Pre-existing**: confirmed via `git show d5558e9 -- polygram.js |
  grep -A 8 "^-  await deliverReplies"` — pre-extraction code also
  swallowed `r.failed`. The commit-37 extraction is verbatim.
- **Operator query — count auto-resume turns that had partial
  delivery in the last 7 days:**
  ```sql
  SELECT bot_name,
         strftime('%Y-%m-%d', ts/1000, 'unixepoch') AS day,
         COUNT(*) AS partial_auto_resumes
    FROM messages
   WHERE direction = 'out'
     AND status = 'failed'
     AND error NOT IN ('crashed-mid-send')
     AND ts > (strftime('%s','now') - 7*86400) * 1000
     -- Heuristic: outbounds clustered within 60s of an
     -- auto-resume-success event. Run in app or join in a script.
   GROUP BY bot_name, day
   ORDER BY day DESC;
  ```
- Recommendation: in `attemptAutoResume`, after `deliverReplies`, if
  `r.failed.length > 0`, log a `auto-resume-partial` event AND send
  the same partial-delivery warning the normal path does. One-line
  follow-up; not a 0.9.0-cleanup blocker.

### LOW — auto-resume's `messages` writes go through the same `tg`-wrapper write path as the normal handler

- File: `lib/handlers/dispatcher.js:122-132`, `lib/telegram/api.js:1-100`.
- `deliverReplies` does NOT write `messages` rows itself — it just
  loops `send(bot, 'sendMessage', params, meta)`, where `send` is the
  `tg` wrapper. `tg` does the write-before-send dance (insert
  pending row → call Telegram → UPDATE row to 'sent' or 'failed'),
  same as the normal path.
- Therefore: a partial failure in auto-resume's reply delivery
  cannot leave the DB in a "weird state" any more than the normal
  path can. Crashes between (1) and (2) leave an orphan `pending`
  row that `markStalePending()` sweeps to `'failed'` on next boot.
  Same recovery story.
- The original (failed) inbound row is correctly marked `'failed'`
  by the dispatcher BEFORE the auto-resume attempt fires (line 164,
  `setInboundHandlerStatus({status: 'failed'})`). So even if
  auto-resume itself dies mid-flight, the inbound is already
  terminal — no boot replay re-fire. ✅
- **Operator query — count outbounds stranded `pending` (would
  indicate a `tg` crash between INSERT and UPDATE):**
  ```sql
  -- Should be 0 in steady state; markStalePending sweeps these
  -- on the next boot. Anything older than ~30 min is suspicious.
  SELECT chat_id, msg_id, ts, error,
         (strftime('%s','now')*1000 - ts) / 1000 AS age_seconds
    FROM messages
   WHERE direction = 'out' AND status = 'pending'
     AND ts < (strftime('%s','now') - 1800) * 1000
   ORDER BY ts DESC;
  ```

## Brief summary

Phase-B extractions (commits 29-38) are data-integrity safe.
ZERO new migrations; schema version stays at 10. Every DB write
shape, transaction boundary, and status-state-machine path was
moved verbatim out of polygram.js — verified by side-by-side diff
of each extract commit. `recordInbound`'s `db.raw.transaction(...)`
atomic message + attachments wrap is intact. `approvals.issue`
parameters are byte-identical (8 keys). `chat_tool_decisions`
lookup + insert still canonicalize input on both sides.
Dispatcher's `setInboundHandlerStatus` writes the same 4 statuses
under the same conditions as pre-extraction. Auto-resume's
`messages` writes go through the same `tg` write-before-send
wrapper, so partial-failure recovery is identical to the normal
path.

Two LOW + one MEDIUM finding, all PRE-EXISTING (not introduced by
0.9.0-cleanup): (1) `savePollingOffset` has no monotonic guard,
relying on Telegram's 409 lockout for safety — defense-in-depth
gap, candidate for a follow-up one-line migration; (2) auto-resume's
`deliverReplies` doesn't inspect `failed[]`, so partial reply
delivery is silently masked by `auto-resume-success` (mirror the
normal path's `telegram-stream-redeliver` warning); (3) outbound
`messages` row write-path is unchanged but operators should monitor
for stranded `pending` rows past 30 min.

**Recommendation: ship 0.9.0-cleanup. None of the v4 findings are
release blockers, and the v1 HIGH was fixed in commit 10.**
