## Preflight — production backend of Ivan's DM

U13's first preflight asks whether Ivan's production DM resolves to `pm: "cli"`,
and requires implementation to stop and amend the plan if it resolves to the
**SDK** backend instead.

Evidence read from the production Shumabit host (read-only; no configuration
changed, no secret-bearing content captured):

| Source | Finding |
| --- | --- |
| `config.json` chat `68861949` | `pm: "codex"`, `codexEnabled: true` (current state) |
| `sessions` / `agent_runtime_sessions` for that chat | `pm_backend: "cli"`, namespace `claude:channels` |
| `config_changes` where `field='pm'` | `codex → cli` (2026-07-30T10:27Z), `cli → codex` (2026-07-31T01:32Z), both by Ivan via inline button |
| `inbound_runtime_selections` for that chat | 19 inbound resolved to `claude`, 22 to `codex` |
| Bot-wide `sessions.pm_backend` | 27 `cli`, 2 `sdk`; both `sdk` rows belong to a different chat and are stale (last active 2026-06-23) |

**Verdict: the stop condition is not triggered, and the MVP transport pair holds.**
The DM has never run on the SDK backend. Its Claude-side sessions are CLI-backed,
and the recorded `pm` history moves only between `cli` and `codex` — exactly the
two transports the MVP targets. The chat is presently toggled to `codex`, which
is the other half of the same pair rather than a different backend.

**Fragility worth carrying into U15/U19:** the resolution depends on the
chat-level `pm` key being explicitly set. `bots.shumabit.pm` is unset and the
daemon passes `pmDefault: 'sdk'`, so a binding that ever loses its chat-level
`pm` key would silently resolve to the SDK backend — the case U13 says must stop
implementation. Memory eligibility must not assume the CLI backend from the
binding alone.

## Deletion gate — R54 mechanism selection

The gate answers whether deleting one Markdown source and running the pinned
**public** rebuild removes that record from search, using documented `MemSearch`
calls only and never `store.drop()`.

- Harness: `scripts/spikes/memsearch-deletion/`.
- Environment: the same production-class Linux host and pinned packages as the
  U1 isolation gate — `memsearch=0.4.17`, `pymilvus=3.0.1`, resolved offline from
  the existing package cache into a disposable mode-0700 directory that was
  removed after the run.
- Embeddings: the loopback-only deterministic stub reused from the isolation
  gate. No credential, no embedding network request. As in U1, this measures
  storage and removal behaviour, not semantic quality or production embedding
  latency.

Authoritative result of the first run:

```json
{
  "backend_version": "memsearch=0.4.17;pymilvus=3.0.1",
  "authoritative": true,
  "selected_mechanism": "record-level-removal",
  "passed": true
}
```

| Phase | Role | Result |
| --- | --- | --- |
| `record-level-force` — delete source, `index(force=True)` | selector | PASS |
| `record-level-incremental` — delete source, `index()` | informational | PASS |
| `scope-level-fallback` — relocate scope sources, rebuild from empty, restore siblings | fallback | PASS |

**Decision: R54 uses record-level removal**, subject to the precondition below.
The runbook documents deleting the record's Markdown source and running the
public rebuild. The scope-level rebuild also passed and remains available, but it
is not the selected mechanism and should not be written into the runbook as the
default.

### Precondition the runbook must state

Record-level removal is **configuration-dependent**. memsearch prunes chunks for
sources that have vanished only when a scope is configured with a **directory**
root. Configured with explicit file paths, a rebuild is a partial update and the
deleted record stays searchable — upstream documents this, and it was confirmed
against the pinned version during review: same pins, same public calls, only
`paths` changed, and the record survived.

An operator following "delete the Markdown, run the public rebuild, prove
negative recall" against a file-path-configured scope would believe a record was
redacted when it was not. The gate therefore pins this as an explicit
precondition phase and the emitted evidence carries a configuration fingerprint,
so the mechanism can never be read without the condition it depends on.

### Status after review

Two independent reviews (adversarial false-pass, and security/production-safety)
both reproduced `record-level-removal` against the real pinned stack, so the
**conclusion holds**. Both also found that the first harness did not *prove* it:
it accepted several backends that remove nothing. Those gaps are now closed —
the gate additionally requires

- **attribution** — the target must still be retrievable after its source is
  deleted but before the rebuild, so the rebuild is proven load-bearing rather
  than the file merely having vanished;
- **containment** — every other scope survives each rebuild, so a rebuild that
  damages another principal's scope cannot pass;
- **durability** — the result survives closing and reopening the store, since a
  removal visible only in one live handle is not a redaction;
- **a non-saturated result window** — "absent" is only accepted while the window
  is larger than the scope, so absence cannot be a top-k artifact.

### Why the harness can be believed

- `PublicSurface` holds each `MemSearch` instance in a closure behind
  `__getattribute__`, `__slots__`, and guarded `__setattr__`/`__delattr__`, so
  only `{index, search, close}` resolve. The first version kept the instance in
  an attribute and review demonstrated four working bypasses to `store.drop()`;
  all four are now closed and pinned by tests. The claim that private surfaces
  are unreachable by construction is true of the current version, and was not
  true of the first.
- `test_gate.py` (16 tests) pins that each oracle rejects a misbehaving backend,
  including the specific false-pass backends review demonstrated: one that only
  hides records whose source file vanished, one whose rebuild wipes other scopes,
  one whose removal does not survive a reopen, and one that saturates the result
  window. Two self-tests failed when first written — the scope-level fault
  injection never fired, and the precondition phase — and both fault models were
  corrected rather than the assertions relaxed.

### Limits

- The loopback embedding stub means this is a storage-semantics result. It does
  not retire the open **G1 latency precondition** recorded in the U1 findings,
  which remains a U16 precondition at the unchanged 2x ratio.
- Removal was proven for a scope that is not concurrently being written. The
  runbook's stop-the-gateway step remains required.
- **Negative recall does not generalize by itself.** The gate proves absence over
  a small scope with a window larger than the corpus. R54 must require a bound
  that could actually surface the record — never the production recall path,
  which R40 caps at five results — and a real redaction check searches the
  sensitive phrase, not a unique fixture sentinel.
- **The scope-level fallback relocates plaintext, it does not erase it.** After a
  fallback run the removed record's Markdown still exists beside the corpus, so
  the runbook must say where it goes and R58 backup isolation must cover it.
  Review separately confirmed no plaintext residue remains in the Milvus-Lite
  files after record-level removal, but that is emergent segment-rewrite
  behaviour rather than a memsearch guarantee.

### Where the first run executed, and how to repeat it

The first authoritative run executed **on the production UMI VPS** — the host
running both live Telegram bots — in a disposable directory that was removed
afterwards. It was uncontained: it started a loopback HTTP listener and three
Milvus-Lite instances outside the `claude.slice` bounds that scope every Claude
CLI session on that host, and it ran without first checking whether either bot
was busy. Measured cost was small (about 208 MiB peak RSS and roughly 8 seconds
of wall time for the three-scope run), so this is a procedure and disclosure
defect rather than a capacity one.

Repeat runs should go under a memory-bounded transient scope behind the same
bot-busy gate the deploy flow already uses, so a gate run can never become a
production incident.
