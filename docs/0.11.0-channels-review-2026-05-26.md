# 0.11.0 channels review — 2026-05-26

**Audit base**: `origin/0.11.0-channels` HEAD = `97d2631` (rc.9 — channels backend defaults to bypassPermissions). Audit was originally run against rc.8 (`546effe`); rc.9 was published mid-audit. Findings re-evaluated against rc.9 below.

**Method**: six specialised agents in parallel (architecture, correctness, adversarial, pattern-parity, reliability, doc-coherence). All 21 findings consolidated here. Each entry tracks investigation + status + outcome through to fix.

**Process** (per finding):
1. **Investigate**: confirm the bug exists against current HEAD. Read referenced code paths.
2. **Test (red)**: write a failing test that pins the bug. Commit as a separate test commit.
3. **Fix (green)**: minimum change that makes the test pass. Commit as the fix commit.
4. **Sweep**: run `node --test tests/<affected>.test.js` + broader regression suite. If green, mark `fixed`.
5. **Disproven**: if investigation reveals the agent was wrong, mark `disproven` with the trace. No fix.
6. **Proven-by-trace**: race conditions where a deterministic test isn't feasible — capture the event sequence + line numbers, mark `it.skip` with comment, fix still required.

**Status legend**: `open` (not investigated yet) · `proven` (test written, red, fix pending) · `proven-by-trace` (race; skip-test + trace doc, fix pending) · `disproven` (investigation showed not a bug) · `fixed` (test green, regression sweep clean) · `deferred` (real bug, but out-of-scope for this round; documented for follow-up)

## rc.9 impact on the original 21 findings

rc.9 defaults `permissionMode = 'bypassPermissions'` for channels because the TUI was showing an interactive permission prompt for **every** `mcp__polygram-bridge__reply` call, hanging every turn. Two consequences for this audit:

- **Finding #2 (double-send) becomes load-bearing.** Pre-rc.9, NO reply tool calls reached the daemon because the TUI was stuck on permission prompts. rc.9 unblocks the path; now the double-send fires on every reply. Severity confirmed P0.
- **Findings #11 (always-allow inverted), #14 (perm schema rejects missing fields), F11 (always-allow drops)** become **default-unreachable** — bypassPermissions skips the entire permission relay. Still real bugs for operators who explicitly override `permissionMode` to non-bypass. Downgrade from P1 → P2 unless evidence shows production usage of the override.

## Finding #1 — Dispatcher bypasses sanitizer/sticker/react helper

**Severity**: P0
**Cluster**: dispatcher
**Reported by**: pattern-parity agent
**Files**: `lib/process/channels-tool-dispatcher.js:131-141`; helper: `lib/telegram/process-agent-reply.js`; SDK/tmux caller: `polygram.js:1373` (call to `sanitizeAssistantReply`).

**Claim**: The shared rc.51 helper (`processAndDeliverAgentText` in `lib/telegram/process-agent-reply.js`) handles parseResponse + sanitizer + sticker/react + deliver in one place. So `No response requested.`, `[sticker:pumped]`, `[react:👍]` all reach the chat as literal text.

3. Read `process-agent-reply.js` — verify it's the canonical helper.
4. Construct a test fixture: a channels `reply` tool call with `[sticker:pumped]` payload — assert no literal `[sticker:` reaches Telegram + assert sendSticker fires.

## Finding #2 — Double-send (dispatcher + post-pm.send delivery)

**Severity**: P0 (load-bearing post-rc.9; pre-rc.9 it was masked by the permission-prompt hang)
**Cluster**: dispatcher
**Reported by**: pattern-parity agent
**Files**: `lib/process/channels-tool-dispatcher.js:131-141` (dispatcher delivers); `lib/process/channels-process.js:829` (pm.send resolves with `result.text` = concat of replies); `polygram.js:1364-1556` (post-pm.send pipeline).

**Claim**: Every channels reply is delivered twice — once via dispatcher (immediately on tool call), once via the standard post-pm.send `parseResponse → streamer.finalize / deliverReplies` flow in `polygram.js`. There is no `entry.backend === 'channels'` short-circuit. Pre-rc.9 masking: zero replies were getting through, so the double-path was invisible.

**Investigation TODO**:
1. Trace `polygram.js:1364-1556` — confirm the post-pm.send delivery doesn't conditionally skip on `backend === 'channels'`.
2. Run a live channels turn in a test harness (mock bot, real ChannelsProcess) — count `tg(sendMessage)` calls per reply.
3. Verify the second send isn't a no-op due to `MESSAGE_NOT_MODIFIED` swallowing — that would mask the bug but not eliminate it for the chunked/overflow branches.

**Status**: open

## Finding #3 — Multi-turn reply misattribution when turn_id omitted

**Severity**: P0
**Cluster**: dispatcher
**Reported by**: correctness agent (confidence 70%)
**Files**: `lib/process/channels-process.js:774-785` (`_recordReplyForPendingTurn`); `lib/process/channels-bridge.mjs:217` (system prompt says turn_id is required); same file: tool inputSchema only requires `['chat_id', 'text']`.

**Claim**: When two `send()` calls are in flight (`pendingTurns.size > 1`) and Claude omits `turn_id` from the `reply` tool args, `_recordReplyForPendingTurn` falls back to the OLDEST pending turn (Map insertion order). If Claude is answering Q2 first (legitimate per the inputSchema), the answer to Q2 is delivered as a reply to Q1's source message. Q2 hangs until `hardTimer` (10 min).

**Investigation TODO**:
1. Read `channels-process.js:774-785` — confirm the fallback path.
2. Read `bridge.mjs:217` and the `reply` tool's `inputSchema` registration — confirm `turn_id` is not in `required: [...]`.
3. Write a test that constructs two `pendingTurns` entries and feeds a reply with no `turn_id` — assert it does NOT auto-attribute to the older one (i.e., the desired behavior post-fix is to emit `autonomous-assistant-message` and warn, NOT to silently misroute).

**Status**: open

## Finding #4 — `_teardownOnStartFailure` references dead fields → bridgeServer FD leak

**Severity**: P0
**Cluster**: misc
**Reported by**: correctness agent (confidence 95%)
**Files**: `lib/process/channels-process.js:251-270`

**Claim**: Post-M1 refactor, socket plumbing moved to `this.bridgeServer` (a `ChannelsBridgeServer` instance). `_teardownOnStartFailure` still checks `this.sockClient` and `this.sockServer` — neither is assigned anywhere. On any `start()` throw (handshake timeout, dialog timeout, claude crash pre-bridge), the socket file is unlinked but the `net.Server` listener and any half-attached bridge connection remain open. FD leak compounds across spawn retries.

**Investigation TODO**:
1. `grep -n "sockClient\|sockServer" lib/process/channels-process.js` — confirm the fields are never assigned.
2. Inspect `_teardownOnStartFailure` and compare against `_doKill` (which closes `bridgeServer` correctly).
3. Write a test that simulates a `start()` failure (handshake timeout) — assert `bridgeServer.close()` was called.

**Status**: open

## Finding #7 — Bridge auth has no nonce / replay protection

**Severity**: P0
**Cluster**: misc
**Reported by**: adversarial agent (confidence 80%)
**Files**: `lib/process/channels-bridge-server.js:138`

**Claim**: Static `sockSecret` from `process.env`, readable via `/proc/<pid>/environ` for any same-uid process. No challenge/response — equality check on a static token. If an OLD bridge survives a crash (GC pause, scheduler hiccup) and reconnects late after a respawn, it can authenticate against the NEW ChannelsProcess.

**Investigation TODO**:
1. Read `channels-bridge-server.js:138` — confirm static-equality auth.
2. Race scenario: harder to test deterministically — likely `proven-by-trace`.
3. Decide: add nonce-handshake now, or document as P0-deferred pending threat-model.
