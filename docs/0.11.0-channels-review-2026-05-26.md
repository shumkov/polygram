# 0.11.0 channels review — 2026-05-26

**Audit base**: `origin/0.11.0-channels` HEAD = `97d2631` (rc.9 — channels backend defaults to bypassPermissions). Audit was originally run against rc.8 (`546effe`); rc.9 was published mid-audit. Findings re-evaluated against rc.9 below.

**Method**: six specialised agents in parallel (architecture, correctness, adversarial, pattern-parity, reliability, doc-coherence). All 21 findings consolidated here. Each entry tracks investigation + status + outcome through to fix.

**Process** (per finding):
1. **Investigate**: confirm the bug exists against current HEAD. Read referenced code paths.
2. **Test (red)**: write a failing test that pins the bug. Commit as a separate test commit.
3. **Fix (green)**: minimum change that makes the test pass. Commit as the fix commit.
4. **Sweep**: run `node --test tests/<affected>.test.js` + broader regression suite. If green, mark `fixed`.
5. **Disproven**: if investigation reveals the agent was wrong, mark `disproven` with the trace. No fix.
6. **Proven-by-trace**: race conditions where a deterministic test isn't feasible — capture the event sequence + line numbers, mark `it.skip` with comment, fix still required.

**Status legend**: `open` (not investigated yet) · `proven` (test written, red, fix pending) · `proven-by-trace` (race; skip-test + trace doc, fix pending) · `disproven` (investigation showed not a bug) · `fixed` (test green, regression sweep clean) · `deferred` (real bug, but out-of-scope for this round; documented for follow-up)

## rc.9 impact on the original 21 findings

rc.9 defaults `permissionMode = 'bypassPermissions'` for channels because the TUI was showing an interactive permission prompt for **every** `mcp__polygram-bridge__reply` call, hanging every turn. Two consequences for this audit:

- **Finding #2 (double-send) becomes load-bearing.** Pre-rc.9, NO reply tool calls reached the daemon because the TUI was stuck on permission prompts. rc.9 unblocks the path; now the double-send fires on every reply. Severity confirmed P0.
- **Findings #11 (always-allow inverted), #14 (perm schema rejects missing fields)** are **default-unreachable** in the rc.9 config (bypassPermissions skips the permission relay), but they remain real bugs for operators who explicitly override `permissionMode` to a non-bypass value. **Per operator directive 2026-05-26**: fix both for default and explicit-override modes — severity stays at P1, just deprioritized within the band (fix after the load-bearing P1s).

## Finding #2 — Double-send (dispatcher + post-pm.send delivery)

**Severity**: P0 (load-bearing post-rc.9; pre-rc.9 it was masked by the permission-prompt hang)
**Cluster**: dispatcher
**Reported by**: pattern-parity agent
**Files**: `lib/process/channels-tool-dispatcher.js:131-141` (dispatcher delivers); `lib/process/channels-process.js:829` (pm.send resolves with `result.text` = concat of replies); `polygram.js:1364-1556` (post-pm.send pipeline).

**Claim**: Every channels reply is delivered twice — once via dispatcher (immediately on tool call), once via the standard post-pm.send `parseResponse → streamer.finalize / deliverReplies` flow in `polygram.js`. 3. Verify the second send isn't a no-op due to `MESSAGE_NOT_MODIFIED` swallowing — that would mask the bug but not eliminate it for the chunked/overflow branches.

**Status**: fixed
**Test commit**: `0292f83` — red test pinning `result.alreadyDelivered=true` contract.
**Fix commit**: `dd3c5ac` — `_resolveTurn` adds `alreadyDelivered: true` on the resolved result; `polygram.js` post-pm.send pipeline checks the flag and short-circuits the `streamer.finalize` / `deliverReplies` branch while still emitting `channels-turn-resolved` for telemetry and keeping transcript/DB writes.

## Finding #3 — Multi-turn reply misattribution when turn_id omitted

**Reported by**: correctness agent (confidence 70%)

**Investigation TODO**:

**Status**: fixed
**Test commit**: `0292f83` — red test pinning that neither pending turn absorbs the orphan reply.
**Fix commit**: `dd3c5ac` — `_recordReplyForPendingTurn` drops the orphan at the binding layer when `pendingTurns.size > 1` and no `turn_id` matches; logs warn + emits `channels-orphan-reply-dropped` event for forensics. ## Finding #7 — Bridge auth has no nonce / replay protection

**Severity**: P0
**Cluster**: misc
**Reported by**: adversarial agent (confidence 80%)
**Files**: `lib/process/channels-bridge-server.js:138`

**Claim**: Static `sockSecret` from `process.env`, readable via `/proc/<pid>/environ` for any same-uid process. No challenge/response — equality check on a static token. If an OLD bridge survives a crash (GC pause, scheduler hiccup) and reconnects late after a respawn, it can authenticate against the NEW ChannelsProcess.

**Investigation TODO**:
1. Read `channels-bridge-server.js:138` — confirm static-equality auth.
2. Race scenario: harder to test deterministically — likely `proven-by-trace`.
3. Decide: add nonce-handshake now, or document as P0-deferred pending threat-model.

**Status**: fixed
**Test+fix commit**: `f1d5714` — `_verifyHelloAuth` extracted as pure method using `crypto.timingSafeEqual`; on first successful auth, `this.sockSecret` is cleared (one-shot per ChannelsProcess instance, safe because bridge is one-shot too — exits on socket close). Closes the post-disconnect replay window without a full HMAC challenge-response protocol change. Tests in `tests/channels-bridge-server-auth.test.js`.

**Note**: full nonce-challenge protocol (daemon issues `hello_challenge {nonce}`, bridge HMACs `(secret, nonce)`) was considered but deferred. The rotation approach achieves the same replay-prevention goal with a smaller protocol surface — and the threat model (same-uid attacker who can read `/proc/<pid>/environ`) is already past most security boundaries.

## Finding #11 — Always-allow inverted to deny

**Severity**: P1 (default-unreachable per rc.9, but real bug for explicit non-bypass overrides; operator directive: fix anyway)
**Cluster**: misc
**Reported by**: architecture agent (F11)
**Files**: `lib/process/channels-process.js:614-619`

**Claim**: `respond` closure: `decision === 'allow' ? 'allow' : 'deny'`. Polygram's approval handler passes `'approved-always'` / `'denied-always'` for the "always" buttons. `'approved-always'` becomes `'deny'`.

**Investigation TODO**:
1. Confirm polygram passes `'approved-always'` and `'denied-always'`.
2. Confirm channels' adapter inverts.
3. Bug only fires when `permissionMode` is explicitly non-bypass. Fix regardless so the path is correct when an operator overrides the default.

**Status**: disproven
**Investigation**: Traced the full approval data flow. The 'approved-always' / 'denied-always' strings only exist inside `lib/handlers/approvals.js` (the Telegram button handler). At line 169-184 of that file, `wrappedResolve` explicitly coerces:
  - `'approved' | 'approved-always'` → `settle({ behavior: 'allow' })`
  - `'denied' | 'denied-always'` → `settle({ behavior: 'deny' })`
By the time `canUseTool` returns, `behavior` is already either `'allow'` or `'deny'`. polygram.js's `onApprovalRequired` then does `const verdict = decision?.behavior === 'allow' ? 'allow' : 'deny'` (line 2328) and calls `respond(verdict)`. The channels respond() closure at `channels-process.js:634` receives only `'allow' | 'deny'` — never the always-variants. The check is an identity pass-through, not an inversion bug. No fix needed.

## Finding #22 — Autonomous-message double-send (F#2-class on the wakeup path)

**Severity**: P0
**Cluster**: dispatcher
**Reported by**: production observation (OUT 1148 + 1149, identical text + same timestamp), 2026-05-27, after rc.11 diagnostic logging pinned the path.
**Files**: `lib/process/channels-process.js:910-925` (autonomous-emit branch); `lib/sdk/callbacks.js:205-240` (`onAutonomousAssistantMessage` handler).

**Claim**: F#2's `result.alreadyDelivered=true` flag closed the in-turn `pm.send().then(...)` pipeline but the autonomous path bypasses it. Claude calls `reply` after its turn resolved (a "ScheduleWakeup"-style self-fire). Path:

1. Dispatcher delivers in `_dispatchToolCall` (the rc.10/F#1 helper path → Telegram) — delivery #1.
2. `_recordReplyForPendingTurn` finds `pendingTurns.size === 0` (turn already resolved).
3. Falls into the `!target` branch → emits `'autonomous-assistant-message'` event with `{text, sessionId, backend}` — NO `alreadyDelivered` flag.
4. `pm._wireCallbacks` routes to polygram's `onAutonomousAssistantMessage` handler.
5. Handler does unconditional `tg(bot, 'sendMessage', ...)` — delivery #2.

User sees the same text twice in chat, microseconds apart. Audit didn't catch this in rc.10 because rc.9's `bypassPermissions` + the test fixtures didn't exercise post-turn-resolve replies; the bridge file logging added in rc.11 (`c34e8f0`) exposed the path.

**Investigation TODO**:
1. Read `channels-process.js:_recordReplyForPendingTurn` autonomous emit branch.
2. Read `lib/sdk/callbacks.js:onAutonomousAssistantMessage`.
3. Write red tests: (a) channels emit must carry `alreadyDelivered: true`; (b) handler must skip tg(send) when flag is set; (c) SDK/tmux shape (no flag) still delivers.

**Status**: fixed
**Test+fix commit**: `0f04b29` — channels emit now sets `alreadyDelivered: true`; handler checks the flag and skips the second send (logs `autonomous-wakeup-message` with `already_delivered: true` for transcript continuity). Three new tests: one in `tests/channels-process-lifecycle.test.js` (channels emit shape) + two in `tests/sdk-callbacks.test.js` (handler skip + SDK regression-safety). All RED at HEAD before the patch, GREEN after.

**Related latent (filed as follow-up, NOT fixed here)**: The handler's tg(sendMessage) path is RAW — no `parseResponse`, no `sanitizeAssistantReply`, no inline sticker/react. For SDK/tmux autonomous wakeups, `[sticker:NAME]` and `No response requested.` still leak as literal text. The rc.51 spike-branch helper (`processAndDeliverAgentText`, backported to channels-fixes in F#1) should also be wired here. F#22 specifically targets the channels regression; the SDK/tmux sanitizer-bypass on the autonomous path is a separate (older) latent bug worth a dedicated finding.
