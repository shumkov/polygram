## Current behavior (evidence)

### Channels `/stop` HARD-kills, then the next turn pays for `--resume`

`lib/handlers/abort.js:103-114` — when the backend is `cli` and a turn is
live, abort calls `pm.kill(sessionKey, 'abort')`, NOT the cheap interrupt.
The comment records the 2026-06-04 decision: *"/stop should stop everything
including background, like the SDK backend … Kill the session: the whole
process tree (claude + every subagent + all background shells) dies at once …
the next message respawns fresh (--resume restores the conversation)."*

The SDK branch right below (`abort.js:115-120`) does the opposite —
`pm.interrupt(sessionKey)`, *"non-destructive interrupt cancels the in-flight
Query turn WITHOUT tearing down the Query (cheap to reuse next message)."*

So the cost asymmetry is **backend-specific by design**, not by accident:

| backend | cancel path | cost |
|---|---|---|
| SDK | `query.interrupt()` (sdk-process.js:617) | cheap — Query stays warm |
| **CLI/channels** | `pm.kill()` → next msg `--resume` | **expensive — see below** |

### Why kill+resume is expensive — RELIABILITY first, tokens second (corrected v3)

1. **Reliability (the real, unconditional win).** `--resume` is exactly the
   path that triggers the upstream ~32s startup-death race we root-caused
   2026-06-11 (`docs/0.12.0-known-issues.md` — MCP connect-timeout vs resume;
   5 deaths across 2.1.158 + 2.1.173, all on `--resume`, all at +30s). So
   every channels `/stop` arms a ~1-in-N chance the *next* turn dies on resume
   and has to fresh-retry, losing the conversation to the history-preload
   digest. Cancel should not increase resume frequency; today it maximizes it.
   **This is Ask A's headline.**
2. **Tokens (conditional, not the headline — corrected).** The draft claimed
   kill "drops the warm in-memory cache → 100k re-billed as cache-write." That
   is mechanically WRONG: Anthropic prompt caching is **server-side ephemeral**
   (5-min default TTL), keyed on the rendered prefix bytes — a process exit
   does NOT drop it. A kill→`--resume` within the TTL with an unchanged prefix
   pays **cache-reads (~0.1× input)** on the history, not cache-writes. The
   full-reprefill cost (~1.25× write of 100k+) only bites when the session has
   **aged past the TTL** or the prefix drifted (model/effort reload,
   system-prompt change, compaction). And the backend is on the **Max
   subscription** (known-issues) so the dollar cost is moot regardless — the
   real token-side cost is **prefill latency/throughput**, largest on aged
   sessions, near-zero on hot ones. There is **zero in-repo measurement** of
   resume token cost today; quantify with `usage.cache_read_input_tokens` vs
   `cache_creation_input_tokens` across a real kill→resume before asserting a
   number. Do NOT lead with tokens.

### The cheap CLI path already exists and is unused by `/stop`

`cli-process.js:2147 interrupt()` sends `C-c` to the tmux session — interrupts
the running turn in place, claude stays resident, no resume. It is wired
through `pm.interrupt()` (process-manager.js:456) but `/stop` on channels
never calls it (abort.js chose kill).

### probeBusyState already distinguishes the two cases

`cli-process.js:2227 probeBusyState()` returns `{ busy, streaming,
backgroundShell, shellCount, … }`. `backgroundShell`/`shellCount` come from
the TUI mode-line `· N shell ·` (BACKGROUND_SHELL_RE, tail-anchored). So
polygram can ALREADY tell, before deciding kill-vs-interrupt, whether a
detached `run_in_background` shell exists that an in-place interrupt would
leave running. The 2026-06-04 "kill for completeness" decision predates
having this signal at the abort site (it was added for the stall-watchdog).

## Ask A — make cancel cheap (the win)

### Design: tiered cancel (interrupt by default, kill only when needed)

Replace the unconditional `pm.kill` on the channels abort path with a gate
that **fails toward kill** (Finding 5 — the cheap path must be chosen only
when we're confident no background work and no ghost):

```
# Ghost case (O3): turn already resolved but claude still streaming → KILL.
if hadActive and pendingTurns.size == 0 and probe.streaming:
    await pm.kill(...)                       # close-drain clears the ghost
    return

# Detached background work an in-place interrupt can't reach → KILL.
# Cross-check the durable signal, not a single pane scrape (Finding 5):
hasBg = probe.backgroundShell \
        or proc.hasActiveBackgroundWork()    # bg-work watchdog state
        or second_probe_after(~1s).backgroundShell   # dual-probe
if hasBg:
    await pm.kill(...)
    # ack: 👍 reaction on the stop message (uniform, see below)
    return

# COMMON case: claude thinking / replying, nothing detached → cheap interrupt.
await proc.interrupt()                        # in-place; warm; NO resume
# MANDATORY on every interrupt-cancel: the O2 BLOCKER ledger cleanup —
# transition ALL non-terminal ledger entries (primary AND autosteer/fold)
# to a no-redeliver terminal state. Not optional, not a side branch.

# Ack (UNIFORM across all paths, D-A2 locked): emit a 👍 reaction on the
# user's stop message IF something was actually stopped; nothing-to-stop →
# no reaction. NEVER a text reply.
```

Rationale:
- **The common case is cheap.** Cancelling a turn that's just thinking/
  streaming/running foreground tools → in-place interrupt → zero resume, zero
  resume-race exposure.
- **The "stop everything" guarantee is preserved** for detached background
  shells — but the gate that decides this is a **known-unreliable pane scrape**
  (`probeBusyState().backgroundShell` reads the TUI `· N shell ·` mode line;
  cli-process.js:2250). It false-negatives in ≥3 modes: a just-spawned shell
  (mode line not yet rendered), a count scrolled past the 400-char tail window,
  and subagent-vs-detached-shell ambiguity. A false-negative → interrupt runs →
  background work survives while we ack "Stopped" — the EXACT regression the
  2026-06-04 kill-everything decision prevented. So: cross-check
  `hasActiveBackgroundWork()` (cli-process.js:2292, watchdog-maintained, more
  durable than a scrape) and/or dual-probe, and **when uncertain, kill** (the
  cost of an unnecessary kill is one resume; the cost of a false interrupt is
  a broken guarantee + an orphaned job).

### O-sub — does interrupt reach SUBAGENTS? (verify in the O1 check, don't assert)

The gate assumes subagents die with the turn-interrupt while detached
`run_in_background` shells don't. That's **plausible but unverified** — subagents
are claude-internal and opaque to polygram (the 0.12 bg-work design notes
polygram can't see work "inside the claude process"). Fold into the O1
channels-TUI check: mid-turn, spawn a subagent + a `run_in_background` shell,
send C-c, capture-pane → confirm the subagent stops while the `N shell`
indicator persists. If C-c does NOT stop subagents, the gate logic inverts
(kill far more often) — so pin it empirically.

### Concurrency — the 5s interrupt-grace timer (Finding 7, was un-scoped)

Switching cli to interrupt-default activates `_interruptGraceTimer`
(cli-process.js:2164-2200) in ways the kill path never did. Three handled-by-spec
interactions:
1. **Stop-listener leak.** The interrupt grace deletes pendings WITHOUT
   `this.off('stop-hook', pending._onStop)`. Over repeated cancels on the
   kept-warm proc (the proc we're deliberately keeping resident), this leaks
   listeners. Fix: remove each resolved pending's `_onStop` in the grace loop.
2. **Double-cancel is NOT idempotent (R5 was wrong for interrupt).** Two
   `/stop`s in the 5s window: the second `interrupt()` resets the grace timer
   (clearTimeout at 2164) → pushes synthetic resolution out another 5s, and the
   handler re-acks "Stopped." again (`hadActive` recomputed per call). R5's
   "second is a no-op" holds only for the kill path (proc gone). Fix: if an
   interrupt grace is already pending for the session, the second cancel is a
   no-op ack (or escalates to kill).
3. **Ghost idle gated on `resolvedAny`** — see O3; promoted to mandatory kill.

### O1 — `C-c`: VERIFIED LIVE on the 2.1.173 channels TUI (2026-06-12)

Probe run (real claude 2.1.173, `--dangerously-load-development-channels`,
stub bridge): started a long thinking turn ("esc to interrupt" showing) →
`tmux send-keys C-c` → footer dropped "esc to interrupt" (turn stopped),
TUI stayed resident (NOT a shell prompt) → sent a fresh message "Reply with
just the word: ALIVE" → claude answered `⏺ ALIVE` **in the same session, no
respawn**. Confirms: C-c interrupts the turn, claude stays warm, next message
is served in-place. The cheap-cancel foundation holds on the pinned binary.
Still to confirm at build (O-sub): C-c's cascade to a subagent + that a
detached `N shell` persists. Below kept for the prior-art trail:

### O1 (prior art) — `C-c` vs `Esc`: ALREADY ANSWERED, de-risked

`interrupt()` sends `C-c`. The draft feared `C-c` might exit claude rather
than interrupt. **The repo already answers this:**
`docs/0.10.0-phase0-spike-findings.md` G4 (✅ PASS) tested `tmux send-keys C-c`
mid-stream → produced `⎿ Interrupted · What should Claude do instead?` and
returned to a live `❯` prompt — claude stayed **resident, did not exit**. The
"press again to exit" double-tap is C-c at an EMPTY prompt; `interrupt()` only
sends C-c when a turn is in flight (`hadActive` gate), so that path isn't
reached. The existing startup-gate already sends single control keys to
navigate without exiting. **So C-c is the right key; no Esc switch needed.**
Residual: G4 was on the standalone TUI (Sonnet 4.6), not the channels TUI on
2.1.173 — confirm G4 reproduces there (a 5-min check, NOT a gate on the design).

### O2 → **BLOCKER**: interrupt-cancel strands a D2 ledger entry the next turn re-delivers

This is not "verify later" — it is a known defect against the SHIPPED 0.13
D1/D2 code (rc.38). `CliProcess.interrupt()`'s 5s grace (cli-process.js:2165-
2199) **synthesizes** the resolution inline — its own `pendingTurns.delete` +
queue splice + `emit('idle')` — and **never calls `_finalizeTurn`**. So it
skips `_ledgerTransition(turnId,'resolved')`, `_armDropConfirmSweep()`, the
per-pending `_onStop` removal, and the entry's `_watchdogTimer` clear.

**Exploit (autosteer):** a turn with a mid-turn autosteer inject holds an
InputLedger entry `{source:'autosteer', state:'written'}`. User cancels →
interrupt synth-resolves the pending but leaves that entry `written`. The
NEXT legitimate turn finalizes → `_finalizeTurn` → `_armDropConfirmSweep()`
sweeps all `written` non-primary entries → `_dropConfirmFire` → `emit(
'input-dropped')` → `drop-redeliver.js` re-injects the autosteer source as a
fresh turn. **The cancelled-context message gets answered minutes later.**
`onInputDropped` is a live consumer (process-manager.js), so this fires.

**Cleanup contract (required; approach is implementer's choice — D-A3):** the abort/interrupt
path must transition EVERY ledger entry of the aborted turn — primary AND
autosteer/fold — to a terminal state that `_dropConfirmFire`/`drop-redeliver`
treat as no-redeliver. Two options: (a) route interrupt-cancel through
`_finalizeTurn` so the ledger settles + sweep runs now where supersession
applies; or (b, more surgical) add a `'cancelled'` terminal ledger state and
transition all of the turn's entries in the abort handler around `interrupt()`.
**Red→green test:** autosteer-inject mid-turn → interrupt-cancel → next turn
finalizes → assert ZERO `input-dropped`, ZERO re-delivery. (Note: `drainQueue`
at abort.js:102 does NOT touch the ledger — it only rejects queued promises —
so the cleanup must live in the abort handler or `interrupt()`, not there.)

### O3 → mandatory ghost-kill (was "fall back if needed")

If the turn already resolved via activity-quiet but claude is still streaming
(a "ghost"), `interrupt()` finds `pendingTurns` empty, the grace loop resolves
nothing, and `emit('idle')` is **gated on `resolvedAny`** (cli-process.js:2198)
— so no idle fires and a HeartbeatReactor keeps cycling. The kill path cleared
this for free via close-drain. **Make it mandatory:** detect
`hadActive && pendingTurns.size === 0 && streaming` (a ghost) → `kill`, not
interrupt. Not optional.

### Scope note

SDK backend already does the cheap thing — **no change there.** This is a
CLI/channels-only fix. The natural-language + slash detection, drainQueue,
autosteer-reaction clearing, and bilingual ack all stay; only the
kill-vs-interrupt branch at abort.js:103-120 changes.

## Ask B — "delete my message" as a cancel trigger

### Hard platform wall: the Bot API delivers no deletion event

polygram polls `getUpdates` with
`allowed_updates: ['message', 'edited_message', 'callback_query']`
(`lib/handlers/poll.js:64`). There is no deletion update to add: the Telegram
**Bot API has never delivered "user deleted a message" for regular chats.**
The only deletion-shaped update is `deleted_business_messages`, which fires
ONLY for a bot connected to a Telegram **Business** account via a business
connection — not for a normal group/DM bot (which is what these are). The
local Bot API server (:8082) does not change this; it's the same Bot API
surface. MTProto/userbot WOULD see `updateDeleteMessages`, but that's a
different client class polygram isn't (and a bot token can't become one).

**Verdict: literal "delete my Telegram message → cancel" is NOT implementable
as specified on the current bot architecture.** Do not build toward the
deletion event; it will never arrive.

### Pivot: an observable cancel gesture (pick one)

The UX intent — "a lightweight gesture takes back the turn I just sent" —
is achievable with a signal the Bot API DOES deliver:

- **B1 (recommended, with a sharp chat-type limit): reaction-cancel.** Add
  `message_reaction` to `allowed_updates` (it is EXCLUDED by default — must be
  opted in) + a `bot.on('message_reaction')` handler. A user reacting to their
  own in-flight message with a designated cancel emoji (e.g. 🛑 / ❌) routes to
  the SAME tiered cancel as Ask A.
  - **CORRECTED feasibility (was inverted in draft v1; verified against the
    Bot API docs 2026-06-12):** `message_reaction` requires *"The bot must be
    an administrator in the chat"* (core.telegram.org/bots/api#update). A bot
    can never be admin of a 1:1 DM → **`message_reaction` is NEVER delivered
    in private chats** (empirically confirmed: a 10-min listener on a DM got
    zero events). So the per-chat table is the OPPOSITE of the draft:
    - **DM / private chat → UNAVAILABLE.** Reaction-cancel cannot work here at
      all. Many of Ivan's own sessions are DMs (positive session keys) — they
      get NO reaction-cancel.
    - **group / supergroup + bot-is-admin → AVAILABLE.** UMI/partner topics
      are supergroups; the bot manages topics so is likely already admin —
      VERIFY per chat, and log when it isn't (R4).
  - **Anonymous-reactor hole:** if the user reacts anonymously (anonymous
    group admin / on behalf of a chat), Telegram sends the aggregated
    `message_reaction_count` (no `user`, delayed up to minutes) INSTEAD of
    `message_reaction`. A per-user cancel gesture silently fails for anonymous
    reactors. The author-gate must also handle `user` being ABSENT (anonymous
    → `actor_chat` set, `user` undefined) to avoid a null-deref.
  - **Bot-set reactions produce no update** — polygram cannot self-test the
    path with its own token (harmless; the human reacts).
  - Caveat: reactions are also used today for stickers/acks — the cancel
    emoji must be one polygram doesn't already emit, and the handler must
    gate on "reaction by the message's author on an in-flight turn."
  - **`message_reaction` on the BOT's bubble vs the USER's own message:** both
    are deliverable in an admin group; gate on the reacting `user.id` matching
    the in-flight turn's author either way.
- **B2: edit-to-cancel.** We already observe `edited_message` (edit-redelivery).
  Special-case "edited to a blank/sentinel" → cancel instead of re-dispatch.
  Weak: Telegram forbids truly-empty edits (min 1 char), the semantics
  collide with edit-redelivery ("an edit is a message"), and it's
  unintuitive. Not recommended; documented for completeness.
- **B3: Business mode.** If a bot runs as a Telegram Business connected bot,
  `deleted_business_messages` gives literal deletion. Large architectural
  change (business connection, different token mode) for one gesture —
  out of scope unless Business is already on the roadmap.

### Recommendation on B

Ship Ask A regardless (it's the actual cost win and needs no gesture). For the
trigger, the honest position got WEAKER after feasibility review:
- Literal delete = stop: **impossible** (no bot-API deletion event, confirmed
  definitively).
- B1 reaction-cancel: works ONLY in admin groups, NEVER in DMs, and fails for
  anonymous reactors. So it's a partial gesture available in *some* of Ivan's
  chats (supergroup topics like Music/UMI if the bot is admin) and absent in
  others (his DMs). A cancel UX that exists in half your chats and silently
  no-ops in the other half is a usability trap.
- Given that, the strongest honest recommendation is: **ship Ask A (cheap
  cancel) and keep the EXISTING trigger** (type "stop"/"/stop", which works
  everywhere). The text trigger already covers every chat type; making it
  *cheap* (Ask A) is the real win. Add B1 reaction-cancel only if Ivan
  specifically wants a no-typing gesture AND accepts it's group-only. The
  muscle-memory of *deleting* is not reproducible on a bot token — say so
  plainly rather than ship a near-miss that works in only some chats.

## Risks

- **R1 (O1): largely retired.** G4 already shows C-c interrupts cleanly and
  stays resident; `interrupt()` only sends C-c mid-turn (never the empty-prompt
  exit path). Residual = confirm on the channels TUI / 2.1.173.
- **R2 (Finding 5), upgraded from "short race" to correctness hole:** a
  `backgroundShell` false-negative → interrupt leaves detached work running
  while acking "Stopped" — breaks the "stop everything" guarantee. Mitigated by
  dual-probe + `hasActiveBackgroundWork()` cross-check + **fail-to-kill when
  uncertain**, NOT by accepting the race.
- **R3 (Finding 3) = the BLOCKER:** interrupt-cancel strands an autosteer
  ledger entry that the next turn re-delivers (the cancelled message answered
  minutes later). Mitigated ONLY by the O2 ledger-cleanup contract + its
  red→green test. Without it, do not ship.
- **R3b (Finding 7):** interrupt-grace leaks Stop listeners on the warm proc +
  double-cancel non-idempotency. Mitigated by listener-off in the grace loop +
  grace-pending guard on re-ack.
- **R4 (B1), re-scoped:** reaction-cancel is unavailable in TWO ways, not one:
  (a) ALL private chats (admin requirement unsatisfiable — the gesture simply
  cannot exist in DMs), and (b) groups where the bot isn't admin. Plus it
  degrades to the userless `message_reaction_count` for anonymous reactors.
  Mitigated by: a per-chat admin-status check at startup, logging when
  reactions can't be received, and — critically — NOT advertising the gesture
  to users in chats where it can't fire (a cancel that silently no-ops is
  worse than no cancel). If Ivan mainly interacts via DM, B1 buys him nothing.
- **R5:** double-signal — user reacts-to-cancel AND types "stop". Both route
  to the same idempotent tiered cancel; the second is a no-op ("Nothing to
  stop"). Verify idempotency.
