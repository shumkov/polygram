## ProcessManager-Generic Tests (27 tests)

All 27 tests in `process-manager-generic.test.js` use MockProcess and are backend-agnostic. They test:
- **LRU eviction logic** (cost weighting; inFlight protection; all-inFlight waiter park)
- **kill / killChat / shutdown** lifecycle
- **Optional method delegation** (interrupt, setModel, applyFlagSettings, resetSession)
- **Hot-path no-throw** (drainQueue, injectUserMessage, steer)
- **Event callback forwarding** (onInit, onResult; callback exception isolation)

**Verdict:** These tests prove the ProcessManager abstraction is solid but **do not exercise both backends together**. The LRU cost weighting is exercised with mock costs, not real (sdk=1, tmux=3) costs. Recommend: **add integration test pairing: PM with SdkProcess×10 + TmuxProcess×3 to verify LRU eviction under real cost pressure**.

## Gap Analysis & Prioritization

### Total Gap Count: **20 gaps** (12 SDK + 8 Tmux)

---

### Critical Gaps (Risk: Real regression if shipped)

#### 1. **RC.47 Autonomous Messages — Not Implemented on Tmux** [SDK-GAP]
- **Behavior:** ScheduleWakeup fires within SDK Query without a pending pm.send(); SDK routes via onAutonomousAssistantMessage callback.
- **Tmux Status:** No async scheduling in TUI context; cannot implement without moving Schedule logic outside Query.
- **Risk:** If partner chat uses rc.47 feature on SDK, switching to tmux loses the autonomous message delivery entirely. Scheduled reminders disappear.
- **Action:** **DEFER to Phase 4 (async scheduling design)**. For 0.10.0, document as SDK-only. Consider phase gate in ProcessManager.getOrSpawn.

#### 2. **JSONL Log-Tailing Result Events — Not Implemented on SDK** [TMUX-GAP]
- **Behavior:** TmuxProcess (v9+) opens JSONL log file, tails for `result` event with `stop_reason` and `sessionId`; races against capture-pane timeout.
- **SDK Status:** SDK Query emits result event synchronously; no log file, no stop_reason field (RC.50 future work).
- **Risk:** If tmux chat produces a stop_reason-based result fast (JSONL beats 500ms capture timeout), but then is switched to SDK, the faster path is gone. Latency regression: turn resolves ~50ms slower via capture-pane diff.
- **Action:** **Add stop_reason field to SDK result event (Phase 4)**. Meanwhile, **document:** tmux turns may be faster due to JSONL; SDK turns go via capture-pane diff (observable latency delta ~100–200ms).

#### 3. **RC.45 Multi-Segment Bubble Semantics — Not Tested on Tmux** [SDK-GAP]
- **Behavior:** Consecutive assistant messages (tool-heavy turns: text + tool_use, tool-result, more text) should stay in ONE bubble unless user steers; each steer opens a new bubble.
- **Tmux Status:** Capture-pane diff accumulates text; never tested that bubbles coalesce correctly or that steer forces a split. Likely works by accident (text is text) but semantics unverified.
- **Risk:** If a tool-heavy flow works on SDK (verified by 7 tests), switch to tmux, and the UI shows 3 bubbles instead of 1, the UX is jarring even if text is identical.
- **Action:** **Promote 3 of the 7 rc.45 tests to contract suite** (two assistant messages no-steer → append; steer between → new bubble; flag reset). Tmux will auto-pass if semantics hold.

#### 4. **Prompt-Sanitized Event & C0/DEL Stripping — SDK Doesn't Strip** [TMUX-GAP]
- **Behavior:** TmuxRunner.pasteText sanitizes control chars (C0, DEL); emits prompt-sanitized event with stripped count.
- **SDK Status:** inputController doesn't strip anything; no event equivalent.
- **Risk:** If a prompt with control chars is sent on tmux (captured in logs), and then replayed on SDK, SDK won't sanitize it. May cause input errors or unexpected TUI behavior if SDK later forwards it.
- **Action:** **Add C0/DEL stripping to SDK input path** (ProcessManager.injectUserMessage validates content). **Add prompt-sanitized event to contract** (both backends must fire on >0 chars stripped).

#### 5. **Concurrent Send Call Tracking — SDK Not Tested Explicitly** [TMUX-GAP]
- **Behavior:** Tmux verify via runner._calls that pasteText + sendControl fire in the correct order across concurrent send() calls.
- **SDK Status:** SDK sends are serialized by PendingQueue; no explicit test of call order (implicit in C20 correctness).
- **Risk:** If SDK send serialization ever regresses, the test won't catch it (fakeQuery doesn't track call order the same way).
- **Action:** **Add call-order verification test for SDK** (track fakeQuery.pushedMessages order across 3 concurrent sends; verify FIFO).

### High-Priority Gaps (Risk: Feature gap; works on one backend, not the other)

#### 6. **Attach + Reattach Event — SDK Has No Attach** [TMUX-GAP]
- **Behavior:** TmuxProcess.attach(tmuxName) binds to existing session and emits reattach event.
- **SDK Status:** SdkProcess has no attach() method; always spawns fresh Query.
- **Risk:** ProcessManager can't orphan-recovery with tmux (if a session becomes detached mid-process, no way to re-bind). SDK doesn't have this problem (Query is ephemeral).
- **Action:** **Either (a) remove attach() from TmuxProcess (sdk baseline = no orphan recovery), or (b) implement attach() for SdkProcess (requires Query pool idea, not in 0.10.0 scope)**. For now, **document:** tmux orphan recovery deferred.

#### 7. **Injectuser Message Async Paste Execution — SDK Different Semantics** [TMUX-GAP]
- **Behavior:** Tmux injectUserMessage returns immediately; paste fires async via queueMicrotask. SDK push is synchronous.
- **SDK Status:** inputController.push is synchronous (adds to queue immediately).
- **Risk:** Race condition on tmux: if runner.pasteText is slow or errors, the event arrives out-of-phase with the returned boolean. SDK never has this race (push is atomic).
- **Action:** **Document:** injectUserMessage async behavior is tmux-specific; SDK synchronous. **Consider:** add smoke test for tmux paste error delivery timing (inject-fail event fires within Nms of return).

#### 8. **ResetSession Semantics Differ** [TMUX-GAP]
- **Behavior:** SDK resetSession closes Query, spawns fresh one (closed=true). Tmux pastes /new, keeps same PTY (closed=false).
- **Risk:** Caller code that uses `res.closed` to decide next action will behave differently per backend.
- **Action:** **Promote C13 (contract only checks shape, not semantics) to a note:** "closed field meaning is backend-specific; both values are valid." **Consider:** unify on one semantics in Phase 4.

---

### Medium-Priority Gaps (Incomplete test coverage; feature likely works)

#### 9. **TMUX_TURN_TIMEOUT Error Path — SDK No Timeout** [TMUX-GAP]
- **Behavior:** If capture-pane never signals quiescence (≥turnTimeoutMs), return error result with TMUX_TURN_TIMEOUT subtype.
- **SDK Status:** SDK Query runs continuously; no turn timeout concept (or timeout is much higher, imposed externally).
- **Risk:** Tmux has a safety valve SDK lacks; turning off a tmux chat and switching to SDK may hang indefinitely if the agent loops.
- **Action:** **Document:** tmux has built-in turn timeout; SDK relies on external timeout (parent process, heartbeat monitor). **Consider:** add SDK-side turn timeout in Phase 4 (Polygram handler calls interrupt on stalled queries).

#### 10. **JSONL Tail + Stop Reason — SDK Missing Implementation** [TMUX-GAP]
- **Behavior:** Tmux JSONL tailing (7 tests) verifies stop_reason event parsing, resolvedVia metric, and last-prompt fallback.
- **SDK Status:** SDK result event has subtype (success/error/user_feedback) but no stop_reason (end_turn, tool_use, etc.).
- **Risk:** Telemetry is less precise on SDK; can't drill down on why a turn stopped.
- **Action:** **Phase 4 milestone:** add stop_reason field to SDK result event (requires Claude SDK update).

---

### Low-Priority Gaps (Unlikely to cause regression; cosmetic or future feature)

#### 11. **Warm-Query Respawn Semantics — SDK Specific** [SDK-GAP]
- **Tests:** 2 tests (process-manager-sdk.test.js:956–1051) verify /stop command doesn't respawn Query.
- **Tmux Equivalent:** TmuxProcess has no warm/cold distinction; PTY stays alive after kill.
- **Risk:** None; SDK-specific optimization (preserves cache over /stop).
- **Action:** Keep in SDK test suite; no cross-backend parity required.

#### 12. **Subagent Filtering — SDK Only** [SDK-GAP]
- **Tests:** 4 tests verify parent_tool_use_id filtering in streaming path.
- **Tmux Equivalent:** Tmux has no parent_tool_use_id concept (no subagent architecture).
- **Risk:** None; architecture mismatch, not a parity issue.
- **Action:** Keep in SDK test suite; document subagent feature as SDK-only.
