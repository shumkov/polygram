# 0.10.0 — tmux backend: concurrent messages & autosteer correctness

> **Status: OPEN. This is the problem statement that briefs the
> multi-agent investigation. Every investigating agent must read
> this doc in full before touching code.**

## Why this matters now

polygram is migrating **all chats to the tmux backend** and retiring
the SDK backend. That makes this problem mandatory to solve: every
chat, every user, will exercise the tmux backend's concurrent-message
paths. Today those paths produce visibly wrong output under everyday
Telegram usage (a person sending two or three messages in a row).

The tmux backend has shipped 12+ release candidates (rc.7 → rc.19)
each fixing a concurrency symptom. The symptoms keep returning in new
forms. That pattern means we have been **patching symptoms, not the
root model**. This doc exists to stop that: define the problem
precisely, then fix the turn-tracking model once.

## How the tmux backend works (required background)

polygram wraps the interactive `claude` CLI (the TUI), one tmux
session per chat. It is pinned to a specific CLI version
(`CLAUDE_CLI_PINNED_VERSION` in `lib/process/tmux-process.js`, spawned
by absolute path — see `AGENTS.md`).

There is no API. polygram drives the TUI by **scraping**:

- **Send a message** — paste text into the TUI input box, press Enter
  (`pasteAndEnter` in `lib/tmux/tmux-runner.js`, serialized per
  session by an async-lock for paste+Enter atomicity). The CLI
  applies a `MULTILINE_SEPARATOR` transform: `\n` → ` / `.
- **Read the reply** — tail the per-session JSONL file the CLI writes
  at `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`
  (`lib/tmux/log-tail.js` → `lib/tmux/session-log-parser.js`).
  capture-pane is a fallback when JSONL is slow.
- A **turn** = one user message → agent works → assistant message
  with a terminal `stop_reason` (`end_turn` / `max_tokens` /
  `stop_sequence`). `tool_use` is NOT terminal.

### Turn-state machinery (`lib/process/tmux-process.js`)

- `_turnState` — accumulator for the in-flight **primary** turn
  (`text`, `toolUses`, `resolveResult` promise, `resultEvent`,
  `pastedPromptOneLine`).
- `pendingQueue` — primary turns queued because a turn was already in
  flight when `send()` was called. Drains FIFO.
- `_pendingAutosteers` — `[{ content, msgId }]` for messages injected
  via `injectUserMessage()` (autosteer) that have not yet resolved.
  `content` is stored in oneLine form (post `\n → ' / '`).
- `_extraTurnState` — accumulator for a **second** turn's reply when
  the TUI dequeues an autosteered paste as a fresh NEW-TURN
  (`{ msgIds: [...], text }`).

### Autosteer (the core mechanic)

When a user sends a follow-up while the bot is still replying,
polygram **autosteers**: it injects that message into the in-flight
turn rather than queuing a separate turn — OpenClaw-style "merge into
active". Feels conversational, saves a turn.

For the tmux backend, autosteer = paste the follow-up into the TUI
while a turn runs. The TUI's native input queue then does **one of
two things, non-deterministically** (depends on model timing and
where in the turn the paste lands):

- **FOLD** — the TUI absorbs the paste into the current turn (a
  `queued_command` attachment). The agent's single reply addresses
  the original *and* the folded message. polygram sees a
  `queue-folded` JSONL event → emits `autosteer-resolution via:fold`.
  No separate reply is delivered.
- **NEW-TURN** — the TUI's queue dequeues the paste as a fresh user
  turn *after* the current turn ends. polygram sees a top-level
  `user-message` JSONL event, starts `_extraTurnState`, accumulates
  the second reply, emits `extra-turn-reply` routed back to the
  autosteered Telegram `msgId`.

polygram cannot choose the path — it must correctly *detect* whichever
path the TUI took and route the reply accordingly.

## The problem

When **multiple messages arrive close together** — a rapid burst, or
genuinely concurrent — the machinery races and produces wrong output.
This is everyday Telegram behaviour (people send "a", "b", "c" as
separate messages seconds apart), not an exotic edge case.

### Failure modes observed in production

1. **Empty turn** — a queued turn's accumulator never receives text;
   `send()` resolves with `''`; polygram delivers
   "No response generated. Please try again."
2. **Cross-attribution** — turn A's reply text is attributed to
   message B's `msgId` (B's `extra-turn-reply` carries A's text).
3. **Duplicate reply** — the same text is flushed to multiple
   `msgId`s, or sent to Telegram twice.
4. **Echoed input** — the delivered reply is literally the user's
   input text ("a", "b / da / das") rather than an agent response.
5. **Empty out-messages** — zero-length replies delivered to Telegram.
6. **Canned agent strings** — the agent itself emits non-answers
   ("No response requested.", "No response generated.") because the
   TUI handed it concatenated/garbled input.
7. **Stuck reactions** — the reactor's thinking-emoji (🤔/🤨) never
   clears because the turn-completion signal never reaches it.

### Underlying mechanics that cause them

- **Paste concatenation** — two pastes landing in the same TUI tick
  are concatenated into ONE input (`Inject1\rInject2`). One JSONL
  `user-message` then contains multiple messages' content. Substring
  matching against `_pendingAutosteers` was the rc.14 mitigation; it
  is fragile.
- **Turn-boundary ambiguity** — the backend infers "turn N ended,
  N+1 started" by watching JSONL. Under bursts the events interleave
  in orders the parser does not expect:
  - primary prompt + autosteer prompt arrive as one concatenated
    `user-message`;
  - two autosteers dequeue as separate `user-message`s but produce
    ONE combined assistant reply;
  - an assistant reply + `result` arrive *before* the `user-message`
    that "should" have started their turn;
  - `last-prompt` fires when a prompt is *registered*, not when a
    turn *ends*.
- **Accumulator desync** — `_turnState` / `_extraTurnState` /
  `_pendingAutosteers` / `pendingQueue` fall out of sync with the
  TUI's actual turn structure. Every failure mode above is a
  desync symptom.
- **Concurrent handler races** — each Telegram message runs its own
  `handleMessage` in `polygram.js` with its own reactor, calling into
  `pm` / `TmuxProcess` concurrently. `getOrSpawn`-during-spawn
  (fixed rc.18) was one such race; the message-ordering / autosteer-
  vs-primary-turn decision is another (it depends on a `inFlight`
  check that races the first turn's start).

### Production traces

- **2026-05-16 09:24** — 3 messages "Hi / Hey / How" on a
  freshly-spawned session. Turn 2 ("Hey") returned empty →
  "No response generated." Root cause: `getOrSpawn` returned a
  still-spawning proc; the 2nd send pasted into a not-ready TUI.
  **Fixed in rc.18** — but it is one instance of the broader class.
- **2026-05-16 12:59** — 5 messages "a / b / c / da / das".
  Delivered output: "No response requested.", the inputs echoed
  back as replies ("a", "b / da / das", "c"), 2 empty messages, one
  duplicated message, and `extra-turn-reply` firing the *same*
  10-char text for two different `msgId`s. **Unsolved — this is the
  reference failure to reproduce and fix.**

## What "correct" means — the invariants

For **N messages arriving in any timing pattern** (sequential with
gaps, rapid burst, concurrent, during spawn, during a tool call,
during another turn's reply):

1. **Completeness** — every message produces exactly one delivered
   reply, OR is folded such that another message's delivered reply
   demonstrably addresses it. No message is silently dropped.
2. **Attribution** — no reply text is delivered against the wrong
   `msgId`. A Telegram reply threads to the message it answers.
3. **No spurious output** — no empty replies, no duplicate replies,
   no echoed-input replies, no canned-string replies.
4. **Reaction fidelity** — the reactor emoji reflects true state and
   always clears at turn end. No stuck 🤔/🤨.
5. **Agent never sees garbage** — the agent must receive each user
   message as coherent input, never a concatenated paste blob that
   makes it emit a canned non-answer.

These invariants must hold against the **real** claude TUI (pinned
2.1.142), verified by the real-claude spike
(`scripts/spikes/autosteer-tui-real.mjs`), not just unit mocks.

## Constraints

- The claude CLI is upstream code, pinned and unmodifiable. The
  backend must work WITH the TUI's actual (non-deterministic FOLD vs
  NEW-TURN) behaviour.
- All chats migrate to the tmux backend; the SDK backend is retired.
  There is no fallback.
- Autosteer UX must be preserved — folding follow-ups into an
  in-flight turn is a deliberate, valued behaviour.
- Per-session paste atomicity (async-lock) and the pinned-binary
  spawn must be preserved.

## Goal of the investigation

Stop patching symptoms. Produce a **correct turn-tracking model** for
the tmux backend that satisfies all five invariants under concurrent
messages + autosteer, verified by spike scenarios that reproduce the
09:24 and 12:59 production traces (red before fix, green after).
