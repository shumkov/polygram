# 0.12.0 — SessionStart-driven cwd auto-pairing spec

Status: design, not yet scoped to a release. Filed during the 0.11.0-channels review cycle (2026-05-28) after the deep-research pass identified Claude Code's `SessionStart` hook as a high-ROI signal source polygram is only partly using. See `docs/0.11.0-channels-review-2026-05-26.md` for the broader audit context.

## Goal

Let the operator pair a new Telegram chat to a project cwd in **one command**, without editing `config.json` or pre-setting `pairedChatDefaults.cwd`.

Today's gap: `/pair-code` is for **user-ACL** ("who can talk to the bot"), not for **chat-cwd binding** ("which project this chat works on"). Cwd today is hardcoded from `config.bot.pairedChatDefaults.cwd` or inherited from the first existing chat. Multi-project bots require manual `config.chats` edits.

## Operator scenario (the user-facing pitch)

```text
# In a terminal, on the host where polygram runs:
$ cd ~/projects/foo && claude
> /exit   # just needed claude to fire SessionStart; doesn't have to talk

# In Telegram, create or open a new group/topic/DM with the bot:
me> /use ~/projects/foo
bot> ✅ Paired this chat with ~/projects/foo (sonnet/medium, agent=default).
     Send any message to start.

me> review the latest PR
bot> [spawns claude in ~/projects/foo, replies inline]
```

If the operator skips step 1, `/use` refuses:

```text
me> /use ~/projects/bar
bot> ❌ No recent claude session in ~/projects/bar. Run `claude` there first
     (within the last 30 min) so I can confirm the cwd exists on this host,
     then retry.
```

Variant for "let me pick from recent cwds":

```text
me> /here
bot> Recent cwds I've seen:
     [ ~/projects/foo  (2m ago, sonnet) ]
     [ ~/projects/bar  (8m ago, opus)   ]
     [ ~/work/audit    (24m ago, opus)  ]
     (tap one to pair this chat)
```

## How polygram observes external claude sessions

The key trick (borrowed from [moshi-hooks](https://github.com/rjyo/moshi-hooks)): install a tiny hook script in `~/.claude/settings.json` that fires on `SessionStart` and POSTs the payload to polygram's existing IPC socket (`/tmp/polygram-<bot>.sock`). Polygram is already listening there for the `polygram-send` skill and the `polygram-ipc` smoke check; this design adds a new IPC op.

```json
// ~/.claude/settings.json (managed by `polygram install-hooks`)
{
  "hooks": {
    "SessionStart": [
      { "command": "/usr/local/bin/polygram-hook-relay session-start" }
    ]
  }
}
```

The `polygram-hook-relay` is a ~30-line shell or node binary polygram ships:

- Reads claude's hook JSON from stdin.
- Picks the configured / discoverable polygram socket(s) from `~/.polygram/sockets/` (or `/tmp/polygram-*.sock`).
- Sends `{op: "hook-session-start", payload: {cwd, session_id, model, hookEventName}}` to each.
- Exits within 50ms (must not block claude startup).

The polygram daemon receives the event via `lib/ipc/server.js`, validates the shape, and updates an in-memory `recentCwds` map.

## Data model

```js
// In polygram main state (in-memory, no DB persistence)
recentCwds = new Map(); // key = realpath(cwd), value = {
  cwd:        '/Users/u/projects/foo',
  sessionId:  '8e1c…',
  model:      'sonnet',
  observedAt: 1716938400_000,
};
```

Eviction:

- TTL: 30 min (default; configurable via `config.bot.recentCwdsTtlMs`).
- Cap: 32 entries (drop oldest on insert).

No DB persistence — losing this on daemon restart is fine; operator re-runs `claude` to re-register. SQLite churn for an ephemeral cache is overkill.

## New IPC op

`lib/ipc/server.js` adds a handler for `op: 'hook-session-start'`:

```js
case 'hook-session-start': {
  const { cwd, session_id, model, hookEventName } = payload;
  if (typeof cwd !== 'string' || !cwd) return { ok: false, error: 'cwd required' };
  let resolved;
  try { resolved = fs.realpathSync(cwd); }
  catch { return { ok: false, error: 'cwd not on this host' }; }
  if (!fs.statSync(resolved).isDirectory()) {
    return { ok: false, error: 'cwd not a directory' };
  }
  recentCwds.set(resolved, {
    cwd: resolved,
    sessionId: session_id || null,
    model: model || null,
    observedAt: Date.now(),
  });
  // Evict over cap (oldest first).
  while (recentCwds.size > 32) {
    const oldestKey = [...recentCwds.entries()].sort((a, b) => a[1].observedAt - b[1].observedAt)[0][0];
    recentCwds.delete(oldestKey);
  }
  return { ok: true };
}
```

## New slash commands

**`/use <cwd>`** in `lib/handlers/slash-commands.js`:

1. Require unpaired chat (refuses if `config.chats[chatId]` exists — pairing twice is an operator error).
2. Canonicalize: `realpath(cwd)` + tilde expansion.
3. Look up canonical cwd in `recentCwds`. If miss → reply `❌ No recent claude session in <cwd>…`.
4. Build `newChat` entry inheriting from `config.bot.pairedChatDefaults` but with the resolved cwd and observed model:
   ```js
   {
     name: ctx.chat.title || ctx.chat.first_name || `Chat ${chatId}`,
     bot:    BOT_NAME,
     agent:  paired.agent  || 'default',
     model:  recentCwds.get(cwd).model
          || paired.model
          || 'sonnet',
     effort: paired.effort || 'medium',
     cwd,
     timeout: paired.timeout || 600,
   }
   ```
5. `config.chats[chatId] = newChat; saveConfig();`
6. `logEvent('chat-auto-created', { source: 'session-start-hook', cwd, … });`
7. Reply with confirmation.

**`/here`** = `/use` with no arg → list `recentCwds` via inline keyboard, callback handler pairs on tap.

## Threat model

| Actor | Today (without F#25) | After F#25 |
|---|---|---|
| **Operator (single-user setup)** | Edit `config.json` + restart bot | Run `claude` + `/use` from Telegram |
| **Guest (Telegram-only, no shell access on operator's host)** | `/pair-code` → single default cwd | Same. `/use` refuses because no recentCwds entry without shell access. |
| **Random Telegram user (no ACL row)** | Bot ignores them | Bot ignores them (existing `knownChat()` gate fires first; `/use` is downstream). |

Net: **`/use` is implicitly operator-only**. The recentCwds entry IS the auth credential — only someone who can run `claude` on the host can produce one. Guest flows stay on `/pair-code`.

## Out-of-band concerns

- **Multi-bot fan-out.** If the operator runs `shumorobot` + `audit-bot` + `partner-bot`, the hook should fan out to all of them. The relay reads `~/.polygram/sockets/` (or `/tmp/polygram-*.sock`) and POSTs to each.
- **Hook installation collision.** The operator may already have moshi-hooks / ccbot hooks in `~/.claude/settings.json`. The installer must append, not replace. Reuse moshi-hooks's idempotent pattern (their setup CLI handles this; copy the approach).
- **Tilde expansion.** Hooks run in claude's spawn context — `~` expansion is shell-dependent. Always `realpath` on both sides before comparing.
- **Cwd absent on operator host.** If hook fires for `/Users/u/projects/foo` but polygram-side `fs.statSync(path)` says not-a-dir, drop the entry (probably stale).
- **Concurrency.** Two `/use` from two chats targeting same cwd → both succeed, both bound to same cwd. That's fine (existing model supports multiple chats per cwd).
- **Polygram-spawned claudes.** When polygram itself spawns claude (the normal flow), the same SessionStart hook fires. Two options:
  - Ignore: set `POLYGRAM_INTERNAL=1` in the env polygram passes to the spawned claude; the relay checks the env and exits early.
  - Record: track them too. Slightly more useful for `/here` listings but floods recentCwds with already-paired paths.
  - Default: ignore.
- **Race condition.** Hook fires AFTER claude starts. If the operator is fast, they could type `/use` before the hook arrives. `/use` should wait up to 2s for a matching recentCwds entry before erroring.
- **/use over /pair-code precedence.** For chats with no `config.chats` entry yet, the gate today is `knownChat() === false`. `/use` needs to bypass that gate — but only `/use`, not arbitrary commands. Implementation: check command name BEFORE the knownChat gate in handleMessage.

## What this design does NOT solve

- Guest onboarding (guests have no shell access on operator's host → can't produce a recentCwds entry → still need `/pair-code`).
- Polygram running in a container / VM where the operator's normal `claude` usage runs in a different namespace.
- Identity-based pairing for users who happen to share a host with the operator (the cwd is the credential here; can't distinguish multiple users on the same host).

## Open questions (need operator decision before implementing)

1. **Operator-only or also guest-usable?** My instinct: operator-only for the cwd-binding step; guests stay on `/pair-code` for ACL. Alternative: `/use` requires BOTH a recentCwds entry AND a claimed pair code — defense-in-depth + audit trail.
2. **Should polygram-spawned claudes' SessionStart also populate `recentCwds`?** Default: skip (noise). Minor call.
3. **Are you OK with polygram installing hook entries in `~/.claude/settings.json`?** It's a global setting on the operator's machine and affects every claude invocation. Some operators don't want that side effect; offer `polygram install-hooks --project` as a local alternative that only fires inside polygram-managed projects.

## Out-of-scope follow-ups (tracked as future spec items)

- Hook-based session-end (`Stop`) signal for cleaner channels turn-resolve. Today channels uses a 2s quiet-window heuristic (`turnQuietMs`) that fires after the last reply tool call. Hooks `Stop` would be deterministic. Requires the same hook-installation infrastructure as this spec.
- Hook-based `Notification` mirroring as a backup approval channel. If MCP perm-request fails on channels, hooks `Notification` could be a fallback. Marginal; only worth doing if production sees the MCP path failing.
- Auto-detecting agent name from cwd contents (e.g. read `.claude/agents/` if present) so `/use` also pre-picks an agent rather than defaulting to `'default'`.
