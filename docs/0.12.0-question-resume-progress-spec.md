## Problem

When claude calls the blocking `ask` tool, it has typically just posted its reply + the question,
so the per-turn reactor **clears** (nothing is "thinking" — the bot is waiting on the user) and
typing stops. The `ask` call then blocks the turn until the answer arrives. **When the answer is
delivered and claude resumes working, neither the reactor nor typing comes back** — the reactor
is hook-driven and was cleared, and `writeQuestionAnswer` does nothing to re-light it. So all the
post-answer work (which for a "build it" answer can be minutes of tool calls) is invisible: no
reaction on any message, no "typing…", until claude finally emits a `reply`. From the user's seat
the bot looks dead the moment they submit.

## Mechanism (verified)

- The reactor (`createReactionManager`, `polygram.js:1016`) and typing (`startTyping`, `:856`) are
  **per-turn** — created at the top of `handleMessage`, torn down in its `finally`.
- During an `ask` block the turn is **still in flight**: `pm.send` is awaiting the
  `question_answer`, and `_startQuestionKeepAlive` (`cli-process.js:2636`) resets the idle ceiling
  every 60 s so it isn't killed. So `handleMessage` has NOT reached its `finally` — **the reactor
  object is still alive**, just in a cleared state.
- The reactor is driven by claude's hooks. While blocked, **no hooks fire** (the keep-alive comment
  says so). After the answer, hooks fire again — but the reactor was cleared and is not re-engaged,
  and `writeQuestionAnswer` (`:2630`) only writes the answer to the bridge; it doesn't touch the
  reactor or typing.

So the fix is a **positive re-arm on answer delivery**, not a reliance on the cleared reactor
auto-resuming.

## Design

### 1. Re-arm point — answer delivery

`writeQuestionAnswer(toolCallId, result)` is the moment claude is about to resume. After it writes
the `question_answer` for a **non-terminal** result (an actual answer, not `cancelled`/`timedout`
on the LAST open question where the turn is about to end anyway), re-light the turn's progress
indicators:

- **Reactor → a working state** (`THINKING`, the normal "processing" reaction).
- **Typing → resume** the chat action for this session/thread.

Only when `_openQuestions` becomes empty after this answer (the turn truly resumes vs. moving to a
next still-open question — though the sequential model means one open `ask` at a time per session).

### 2. Reaching the live turn's reactor/typing

The reactor/typing live in `handleMessage`'s closure, but the proc already carries the per-turn
context — `entry.pendingQueue[0].context` exposes `{ streamer, reactor, sourceMsgId }`
(`cli-process.js:1498-1505`). Two candidate wirings (Decision B):

- **(B1) Direct:** `writeQuestionAnswer` reads the active turn's `context.reactor` and re-arms it +
  the typing controller directly. Fewest hops; but couples cli-process to the reactor object shape.
- **(B2) Event:** `writeQuestionAnswer` emits a `'question-resumed'` proc event
  (`{ sessionKey, sourceMsgId }`); the existing pm→sdkCallbacks wiring (which already owns reactor
  state transitions) handles it and calls `reactor.setState('THINKING')` + resumes typing. Mirrors
  how `'question-asked'` is already an event consumed in polygram. **Recommended** — keeps reactor
  ownership in one place and matches the existing pattern.

### 3. Which message the reaction lands on

The reaction re-arms on the **turn's `sourceMsgId`** (the original user message that opened the
turn) — the same message the reactor was on before `ask` cleared it. (Not the answer message; the
answer was a button tap / typed reply that already got its `✓ receipt` card edit in rc.33.) This
keeps a single, consistent "this message is being worked on" reaction across the whole turn.

### 4. Typing resume

`startTyping` returns a `stopTyping` handle and self-renews on an interval. Resuming after an `ask`
gap means re-starting that loop for the session. If the per-turn `startTyping` loop was stopped
when claude went quiet (Decision C — confirm whether it self-stops on quiet), the resume must
restart it; if it merely paused, re-arm is a no-op on typing and only the reactor needs it.

## Scope

**In:** channels/cli backend (where `ask`/`writeQuestionAnswer` + the keep-alive live; the prod
case). **Out for now:** SDK backend — its `ask` path differs (no bridge keep-alive); a follow-up if
it shows the same gap. **Out:** the *wait-phase* itself (while the question is open, before an
answer) — the keyboard is the "waiting on you" indicator; we are NOT adding a "waiting" reaction
here (Decision D). **Out:** cancelled/timeout terminal answers (turn ends → normal teardown).

## Edge cases

- **Cancelled / timeout answer** → no re-arm (the turn is ending; let the normal finally clear).
- **Multi-question `ask`** (count ≥ 2): the model is sequential — re-arm only when the FINAL answer
  resolves the `ask` and claude resumes; intermediate next-question renders keep the keyboard as
  the indicator. (With the current single-blocking-`ask` design, one `writeQuestionAnswer`
  resolves the whole call, so this is naturally one re-arm.)
- **Turn already torn down** (proc killed / evicted during the wait) → `context.reactor` gone →
  re-arm is a guarded no-op (never throw on a dead turn; mirrors the hot-path contract).
- **Answer arrives, claude replies immediately with no further work** → re-arm sets THINKING, the
  reply lands, the normal reply-path clears it. Brief flicker, harmless.

## Test plan

Unit (`tests/cli-process*.test.js` / a reactor-wiring test, deterministic with a fake context):
1. `writeQuestionAnswer` with a real answer + `_openQuestions` now empty → re-arms: sets the
   turn-context reactor to THINKING and resumes typing (B2: emits `'question-resumed'` with the
   sourceMsgId).
2. `writeQuestionAnswer` with `{cancelled:true}` / `{timedout:true}` → does NOT re-arm.
3. Re-arm targets the turn's `sourceMsgId`, not the answer message.
4. Dead/torn-down turn (no context) → no throw, no-op.
5. (If B2) polygram consumer: `'question-resumed'` → `reactor.setState('THINKING')` + typing
   resume on the right session.

Plus a forensic assertion mirror of the prod trace: after `question-answered`, at least one
`reactor-state`→working event is emitted for the session (the regression guard for "zero reactor
after submit").

## Decisions (for sign-off)

- **A. Re-arm only on a real answer, skip cancelled/timeout.** Recommended: yes. *Confirm.*
- **B. Wiring = event (`question-resumed`) vs direct context access.** Recommended: **event (B2)** —
  matches `question-asked`, keeps reactor ownership single. *Confirm.*
- **C. Typing:** does the per-turn typing loop self-stop on quiet (needs restart) or just pause?
  Confirm during implementation; the re-arm restarts it either way.
- **D. No "waiting on you" reaction during the open-question wait** (keyboard is the signal).
  Recommended: yes, out of scope. *Confirm — or do we want a subtle ⏳ on the user's message while
  the question is open?*
