# Channels turn-lifecycle — full investigation & design mission (handoff prompt)

> Hand this whole file to a fresh session/model. It is self-contained.

You are investigating the **polygram** Telegram↔Claude daemon's **channels (cli) backend
turn-lifecycle seam**. Your job is **NOT** to fix individual bugs. It is to understand the
**structural root** behind a recurring cluster of failures and propose a **coherent design**, with
refactoring where warranted. **Explicitly avoid monkey-patches.** The deliverable is a design doc
that gets adversarially reviewed before any code is written.

## Why this investigation exists — the evidence

Over 2026-06-09/10, **five distinct bugs surfaced in ONE area** (channels turn lifecycle ↔
interactive questions ↔ autosteer ↔ message edits). Each got an individual fix, but the recurrence
is the signal: the seam has a structural weakness, not five coincidences.

| # | Symptom (prod) | What it exposed about the lifecycle | Status |
|---|---|---|---|
| 1 | Typed "Other" question answer → no feedback (dead-air) | a consumed answer produced no acknowledgment; the question/answer path runs *beside* the turn lifecycle, not through it | patched (rc.33) |
| 2 | After submitting a question, no typing/reaction while claude works | reactor + typing are **per-turn + hook-driven**; they CLEAR when claude calls the blocking `ask` tool and **don't re-arm** when the turn resumes after the answer | patched (rc.34) |
| 3 | Autosteer drop: a mid-turn follow-up vanished at a tool-less turn boundary | `injectUserMessage` is **best-effort** ("fold, or maybe next turn, or maybe dropped") with **NO observability** of which happened | unfixed (see #14 brief) |
| 4 | Post-turn edits silently ignored | edits weren't re-dispatched; the `inFlight→done` boundary race drops them; **THREE parallel "re-dispatch a message" paths** exist (boot-replay, edit, autosteer) | patched (edit re-delivery) |
| 5 | `ask`-block + keep-alive + idle/Stop-hook turn-end interactions | the "turn" boundary is fuzzy; blocking tools pause it; the reactor treats the pause as an end | partially (question-resume) |

**The common threads (the suspected root):**
- **(a) The channels "turn" is best-effort and unobservable at its seams.** You cannot tell whether
  an injected / follow-up / edited message was *folded*, *processed as a new turn*, or *dropped*.
- **(b) Feedback (reactor + typing) is per-turn and hook-driven**, so it tears down / clears at turn
  boundaries and does not survive `ask`-blocks or resume after them → silent-no-feedback.
- **(c) There is no unified primitive for "a user message was dropped → re-dispatch it."** It has
  been re-implemented **three times** (boot-replay, edit-redelivery, the proposed autosteer-drain).
- **(d) Message intake has several entry points with subtly inconsistent gating** (message,
  edited_message, the injector, question-consume, rewind).

## Your mission

1. **Map the channels turn lifecycle end-to-end** — intake → gating → dispatch → in-flight (tools,
   autosteer/inject, the `ask`-block) → reply → idle/Stop-hook turn-end → teardown (reactor/typing/
   ref-clear). Document every mechanism that touches a "turn" and **every seam where a message or a
   feedback signal can be dropped or desynced.**
2. **Name the STRUCTURAL ROOT** behind the cluster — not the five symptoms. State the leaky
   abstractions explicitly.
3. **Propose a coherent design** that fixes the *class*: an observable turn lifecycle, a unified
   re-dispatch primitive, resilient (session-scoped) feedback, and consistent intake/gating.
   Refactor where warranted; **justify each refactor against the cluster** (which bugs it dissolves).
4. **Phase it** (lowest-risk, highest-leverage first) with a test strategy (edge/failure unit +
   real-claude E2E) and a risk register.

## The hard questions — your design targets

- **Observability.** Can polygram learn whether an injected/follow-up message was folded vs
  processed vs dropped? Today the bridge is best-effort with no signal. The injected `user_msg`
  carries a `turn_id` (cli-process ~2396) and `CliProcess` already correlates reply `turn_id`s →
  pending turns (~1201). What makes injected messages first-class enough to track resolution? (This
  is the surviving direction from the autosteer-drop review — see the #14 brief.)
- **Unified re-dispatch.** boot-replay, edit-redelivery, and the proposed autosteer-drain all
  "reconstruct a message → dispatch as a fresh `_isReplay` turn → re-gate via `shouldHandle`."
  Should there be ONE `redeliverAsFreshTurn(sessionKey, chatId, msg, bot)` primitive (re-gate,
  `_isReplay`, reconstruct from DB row, immediate-ack reaction)? Design it; show the three callers
  collapsing onto it.
- **Resilient feedback.** Reactor + typing are per-turn and hook-driven. The question-resume fix
  re-armed the reactor after `ask` resolves — a point fix. Generalize: should feedback be a
  **session-scoped** concern that survives the WHOLE turn including `ask`-blocks, tool gaps, and
  cold-spawns — with explicit states the user can read (received / thinking / waiting-on-you /
  working / done)?
- **The "turn" model on channels.** A turn is a `pm.send` + `turn_id`, but `ask`-blocks, injects,
  and edits interact with it implicitly. Is the right model a **session-scoped input queue** with
  explicit per-message states (queued / in-flight / folded / answered / dropped) so drops become
  detectable by construction rather than inferred?
- **Intake/gating.** Several entry points with subtly different gating (e.g. the synthetic
  reply_to that broke `shouldHandle.repliesToOtherUser` in the edit-redelivery review). Unify the
  gate so every path — fresh message, edit, re-dispatch, autosteer — passes the same check.

## Discipline (project norms)

- **No monkey-patches** — find the root, fix the class. A patch that doesn't reduce the seam's
  total complexity is the wrong answer here.
- **Spec-first for non-trivial changes**; prove with edge/failure tests + reviewers + real-claude
  E2E, not just the happy path.
- **Surface conflicts; recommend, don't average.** If two mechanisms contradict, pick one and say why.
- **TDD red→green** for any bug fix that falls out (failing test first, surfaced in the commit).
- Verify every line/function reference against the current code before relying on it — the codebase
  moves; some refs in this brief are approximate.
