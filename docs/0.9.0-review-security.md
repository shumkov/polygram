## Verdict

**Cleanup is structurally sound. No CRITICAL or HIGH security regressions introduced.** The single in-process canUseTool path is correctly wired, IPC auth is preserved, the `approval_request` op deletion fails closed against any orphan-hook callers, and env-var passthrough was correctly narrowed when `spawnClaude` was deleted.

## Findings

### LOW-1 — Stale README install instructions point to deleted `bin/approval-hook.js`
- File: `README.md:343-378`
- The "Approvals" section still tells users to install a `PreToolUse` hook at `/abs/path/to/polygram/bin/approval-hook.js`. That file no longer exists, and `package.json` no longer declares a `polygram-approval-hook` bin.
- Impact: Claude Code's PreToolUse hook spawn will fail (`ENOENT`). Per Claude Code's hook contract, a non-zero exit blocks the tool — i.e. fail-closed. Users get a denial-of-service on every gated tool call, NOT an ungated execution. UX-level break, not exploitable.
- Fix: replace `## Approvals` with the new SDK in-process flow description (4-button keyboard, `chat_tool_decisions` persistence, `permissionMode: 'default'` when `approvals.gatedTools` is configured). Drop the `settings.json` hook block entirely.

### LOW-2 — Orphaned `lib/approval-waiters.js` module is dead code, never imported
- File: `lib/approval-waiters.js`
- This module exposes a richer `createApprovalWaiters({ maxWaiters: 200, timeoutMs: 60_000, ... })` factory with cap-enforcement, signal-abort, session-scoped reject, and a periodic timeout sweeper. `polygram.js` does **not** import it — it uses an unbounded `let approvalWaiters = new Map()` (line 108) directly.
- Impact: Two concrete risks:
  1. **No cap enforcement**: a runaway agent that emits 10k+ gated tool calls in a loop while the approver is asleep will park 10k waiters in the Map. Memory grows unbounded.
  2. **Confusion**: the next contributor will reasonably assume the module is wired up because tests pass.
- Severity LOW because realistic admin chats see a few approvals per turn. But the cleanup is the right time to either wire up `lib/approval-waiters.js` (so the cap fires) or delete it.

### LOW-3 — `POLYGRAM_IPC_SECRET` still exported into every SDK child env
- File: `polygram.js:856-858` (in `buildSdkOptions`)
- Pre-cleanup this was needed for `bin/approval-hook.js` to authenticate to the IPC server. Post-cleanup, the only remaining IPC consumers are cron-driven scripts, which run as separate processes with their own access to `/tmp/polygram-<bot>.secret`.
- Impact: A prompt-injected child under `permissionMode: 'bypassPermissions'` can read `process.env.POLYGRAM_IPC_SECRET` and authenticate to the local IPC socket as if it were polygram itself. The `send` op restricts target chats to those owned by the bot, so the worst attack is sending arbitrary text from the bot to its own chats. Same-UID is already the implicit trust boundary, so this doesn't cross a privilege bound — but it IS a useful injection-amplification vector.
- Fix: gate the env passthrough behind a config opt-in (e.g. `config.bot.exposeIpcSecretToChildren: true`, defaulting false).

### LOW-4 — IPC server's secret/auth path is uncovered by tests
- File: `tests/ipc.test.js`
- Pre-existing — not introduced by 0.9.0. The cleanup deleted `tests/approvals-integration.test.js`, which was the only end-to-end test exercising `ipcServer.start({ ..., secret })` with a real authenticator. Now: the secret-validation branch at `lib/ipc-server.js:121-127` (`timingSafeEqual`, ping exemption, `error: 'auth'` on bad secret) has no test coverage at all.
- Fix: add 3 unit tests:
  1. server with secret, client without → `ok: false, error: 'auth'`
  2. server with secret, client with wrong secret → `ok: false, error: 'auth'`
  3. server with secret, client calls `'ping'` without secret → `ok: true, pong: true`

## Verified safe (no regression)

1. **IPC auth preserved**. `lib/ipc-server.js:108-127` still validates `req.secret` against the per-boot secret using `crypto.timingSafeEqual`.
2. **`approve` callback regex backward-compatible**. `polygram.js:1622` regex still matches the legacy 2-button format.
3. **Old hook callers fail closed**. If an external Claude Code config still has `bin/approval-hook.js` configured, the IPC server returns `{ ok: false, error: 'unknown op: approval_request' }`, and the hook's failure policy blocks the tool. Fail-closed.
4. **canUseTool flow integrity**: 4-button callback resolution, token-validation, atomic SQL UPDATE, `chat_tool_decisions` persistence, timeout, signal-abort — all intact.
5. **`canonicalizeToolInput` + `matchesApprovalPattern`** still used by `makeCanUseTool`. No sanity-check orphaned.
6. **Env scrubbing for SDK children intact**. `filterEnv` still allowlists. `POLYGRAM_BOT` and `POLYGRAM_CHAT_ID` are correctly NOT re-added.
7. **All 56 approval/approval-ui tests pass**.
8. **Approval cards still posted with `plainText: true`**, preserving the prompt-injection defense.

## Summary

The deletion of `handleApprovalRequest`, `approval_request` IPC op, `bin/approval-hook.js`, and the 2-button keyboard variant did not introduce a security regression. All sanity checks, auth, and timeout/signal/click resolution paths are correctly preserved. Old callers fail closed; old keyboards remain compatible.

The four LOW findings are housekeeping debt the cleanup deferred:
- **LOW-1**: README install instructions point to deleted hook.
- **LOW-2**: `lib/approval-waiters.js` is orphan code with cap-enforcement that the live inline Map lacks.
- **LOW-3**: `POLYGRAM_IPC_SECRET` propagates to every SDK child for a use case most chats don't have.
- **LOW-4**: IPC secret/auth path has no test coverage.
