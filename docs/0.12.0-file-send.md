# 0.12.0 — File send/receive (channels + IPC)

## What this fixes

File-send **never worked** on this codebase. Root cause: callers passed
grammy a Telegraf-style `{ source: '/abs/path' }` envelope as the file
param. grammy 1.x doesn't recognize that shape, so it serialized the
object and Telegram tried to read it as a URL → every upload failed with
`400 Bad Request: invalid file HTTP URL specified: Wrong port number`.
This hit both the channels `reply(files=[...])` path and the IPC send
path (same error in the logs). The existing dispatcher test used a fake
`send` and only asserted the *method*, so it never caught the bad shape.

Surfaced live in the shumorobot Music topic (2026-05-31): claude tried to
send tracks via `reply(files)`, hit the upload bug + an allowlist gap +
the size cap, and flailed across `/Volumes/…`, `~/Downloads`, `/tmp`, and
the IPC URL path — all failing.

## The fixes

1. **Upload coercion** (`lib/telegram/input-file.js`) — at the single send
   choke point (`tg()` → `send()` in `lib/telegram/api.js`),
   `coerceFileParams(method, params)` turns a `{ source: path }` file param
   into a real grammy `new InputFile(path)`. No-op for file_id / URL
   strings, existing InputFile instances, Buffers. Fixes channels **and**
   IPC at once.

2. **Staging dir** (`lib/process/cli-process.js`) — at spawn, CliProcess
   creates `<tmpdir>/polygram-attachments/<sessionKey>/` (always on the
   dispatcher allowlist, but previously never created → the literal path
   claude guessed didn't exist / didn't realpath-match). Stored as
   `this.attachmentStagingDir` (realpath'd) and surfaced to the system
   prompt. Auto-purged when the session goes idle (`_finalizeTurn`); the
   whole dir is removed on kill. You don't tell claude to delete.

3. **System prompt** — the channels HARD CONTRACT now teaches claude to
   send files via `reply(files=["<staging-dir>/name.flac"])`, NOT via
   Bash/curl/Telegram-API/IPC, and states the 50 MB upload limit.

4. **Caps** (`lib/attachments.js`) — inbound (user → bot) per-file cap
   raised 10 MB → **20 MB** (Telegram cloud's getFile ceiling), total
   20 MB → 50 MB.

## Limits (cloud Telegram)

| Direction | Cloud Bot API hard limit |
|---|---|
| bot → user (sending tracks) | **50 MB** |
| user → bot (adding tracks)  | **20 MB** (getFile download) |

Big lossless WAVs (50–64 MB) cannot cross on cloud regardless of our caps —
that's Telegram's limit. FLAC/MP3 under the limits work. Conversion is the
right move for large lossless on cloud.

## Optional: 2 GB via a self-hosted Bot API server

To send/receive up to **2 GB** both ways, run the official
`telegram-bot-api` server locally and point polygram at it.

### polygram side (already wired)

Set in `config.json`:
```jsonc
"bot": {
  "apiRoot": "http://localhost:8081"
}
```
Omitted → cloud Telegram, unchanged (this is the only polygram change; it's
additive and reversible). Boot logs `using local Telegram Bot API server`
when set.

### Companion server (separate daemon — set up when ready)

It is a **standalone process**, not part of polygram, and is
**localhost-only** — it makes OUTBOUND connections to Telegram's DCs; nothing
external connects to it. No public port, no webhook, no exposure.

1. Get `api_id` + `api_hash` from <https://my.telegram.org> (apps).
2. Install the server: `brew install telegram-bot-api` (or build from
   <https://github.com/tdlib/telegram-bot-api>).
3. Run it bound to loopback:
   ```
   telegram-bot-api --api-id=<ID> --api-hash=<HASH> \
     --http-port=8081 --local
   ```
   (`--local` enables the 2 GB limits + local-file paths.)
4. Keep it alive with a launchd job (like the bot daemon), then set
   `config.bot.apiRoot = "http://localhost:8081"` and restart polygram.

Operational note: it's another daemon to babysit. If it's down while
`apiRoot` points at it, file calls fail until it's back. Cost is
operational, not code.
