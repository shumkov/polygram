### 1. CRITICAL — `approvalWaiters` undefined in `shutdown()` (runtime ReferenceError on every clean exit)

**File**: `/Users/ivanshumkov/Projects/shumkov/polygram/polygram.js` lines 2041–2044.

```js
for (const list of approvalWaiters.values()) {        // <-- not declared anywhere in polygram.js
  for (const fn of list) { try { fn('cancelled', 'polygram shutting down'); } catch {} }
}
approvalWaiters.clear();
```

Commit 29 moved the `approvalWaiters` Map into the closure inside `lib/handlers/approvals.js` (line 58). The createApprovals factory exposes it only as `_approvalWaiters` for test introspection (line 338). polygram.js's shutdown handler still references the bare module-scope identifier, which no longer exists. Comment at L121 acknowledges the move (`// approvalWaiters Map moved to lib/handlers/approvals.js (commit 29).`) but the consumer at L2041 wasn't updated.

**Symptoms** (will show in production on first deploy):
- Every SIGTERM / SIGINT / SIGHUP that reaches step 4 of `shutdown()` throws `ReferenceError: approvalWaiters is not defined`.
- The throw is *outside* any try/catch. It aborts shutdown before `pm.shutdown()` (L2045), `db.logEvent('polygram-stop')` (L2047), and `processGuard.releasePidFile(PID_PATH)` (L2053).
- Result: pm subprocesses leaked (zombie SDK Queries), no `polygram-stop` event logged (so the events table will lie about clean restarts), PID file not released → orphan-guard at next boot kills the new daemon by mistake. This is exactly the rc.50 incident's failure shape.

**Test that would have caught it**: a unit test on `shutdown()` invoking it under a stubbed `process.on('SIGINT')` listener. There is none — `tests/` has no `shutdown.test.js`.

**Why v3 missed it**: v3 reviewed the waiters DELETE in isolation (commit 30) which moved waiters logic into createApprovals. v3 didn't grep polygram.js for stale callers of the old name, only checked `lib/approvals/`.

**Fix (3 LOC)**: createApprovals already returns `dropWaiter` and `_approvalWaiters` (test-only). Add a public `cancelAllWaiters(reason)` to the factory's return object, then call it from polygram.js shutdown:

```js
// in lib/handlers/approvals.js return
cancelAllWaiters: (reason) => {
  for (const list of approvalWaiters.values()) {
    for (const fn of list) { try { fn('cancelled', reason); } catch {} }
  }
  approvalWaiters.clear();
},
```

```js
// in polygram.js — replace L2041–2044
cancelAllApprovalWaiters?.('polygram shutting down');
```

(declare `let cancelAllApprovalWaiters = null` near the other approvals placeholders L527–530, destructure it in the createApprovals call at L1884.)

**Severity**: CRITICAL. Production-blocking. Don't merge until fixed AND a `shutdown()` test pins it. Repro is one node invocation:
```
node -e "require('./polygram.js'); /* trigger main */; process.kill(process.pid, 'SIGTERM');"
```

### 2. HIGH — `let X = null` count grew from 9 to 17; pattern is now load-bearing scaffolding, not a smell

Question 1 from your prompt asked whether this could collapse to one `const handlers = wireHandlers(deps)`. **Answer: no — and the growth is a feature, not a regression.** Per-handler reasoning:

```
102: let DB_PATH = null;                    // arg-driven, set in main() L1781
103: let PID_PATH = null;                   // same
122: let approvalSweepTimer = null;         // setInterval handle, cleared on shutdown
123: let ipcCloser = null;                  // async resource, awaited in shutdown
127: let BOT_NAME = null;                   // arg-driven
128: let bot = null;                        // grammy Bot, after createBot()
247: let recordInbound = null;              // factory output
261: let transcribeVoiceAttachments = null; // factory output
265: let downloadAttachments = null;        // factory output
334: let pm = null;                         // SDK ProcessManager, after factories
372: let buildSdkOptions = null;            // factory output
450-454: let dispatchHandleMessage / attemptAutoResume / errorReplyText / queueWarnThreshold / inFlightHandlers
                                             // 5-tuple from createDispatcher
502: let handleSendOverIpc = null;          // factory output
520: let formatConfigInfoText = null;       // factory output
527-530: let makeCanUseTool / handleApprovalCallback / resolveApprovalWaiter / startApprovalSweeper
                                             // 4-tuple from createApprovals
1750-1751: let pollBot / startPollWatchdog  // 2-tuple from createPollLoop
```

Why a `wireHandlers(deps)` object **doesn't** simplify this:

1. Top-level functions like `handleMessage` (L553), `dispatchRegularMessage` (inside createBot, L1527), `formatPrompt` (L282), and `getOrSpawnForChat` (L388) close over these names *by identifier*. Replacing `dispatchHandleMessage` with `handlers.dispatchHandleMessage` means rewriting every call site. There are ~30 such sites across handleMessage alone.
2. The factories are intentionally late-bound for a reason commit 29 documents (L1866–1881): `pm` needs `buildSdkOptions` which needs `makeCanUseTool` which needs `bot`. The `let X = null` declarations *encode the dependency graph as data* and main() walks it in topological order. A `wireHandlers` helper would just hide the topology behind a builder method — same complexity, less explicit.
3. The bug from finding #1 is exactly the kind of bug a `handlers` namespace would have prevented (`handlers.cancelAllWaiters?.()` is a typo-resistant shape). But the bug is one missing line, not 17 — fixing it doesn't justify a rewrite of all 17.

**Recommendation**: stay the course. The placeholders are honest. v3's verdict ("signal accepted; the temporal coupling is acceptable") still holds. **Do NOT** introduce a `wireHandlers` object — it would fight the existing call sites for marginal cleanup.

**Optional polish (~10 min, do if touching that block)**: collapse the 4 destructure-tuples (dispatcher 5-tuple at 450–454, approvals 4-tuple at 527–530, poll 2-tuple at 1750–1751, voice/download/etc. singletons) into a single `// Module-scope handlers — see main() L1882–1959 for wiring order` comment block at the top of the file, instead of one apologetic comment per declaration. Net: ~10 LOC saved, zero behavior change.

### 3. HIGH — Logger optional-chains are still dead code (~30 sites)

v3 audit confirmed: every factory defaults `logger = console`, then guards every call with `?.`. Since `console.error` and `console.log` are non-null, the optional chain can never short-circuit. v3 said "mechanical sed-replace, 2 min." Still not done. Re-confirmed in tree: **35 `logger.error?.(` sites + 4 `logger.log?.(` sites + 2 `this.logger.error?.(` sites in process-manager.js** = 41 dead optional chains.

```
$ grep -rn "logger\.\(error\|log\)?\." lib/handlers/*.js lib/sdk/*.js | wc -l
67   (counting both factory definitions and call sites)
```

Mechanical fix:
```bash
# In lib/handlers/*.js + lib/sdk/*.js:
sed -i '' 's/logger\.error?\.(/logger.error(/g; s/logger\.log?\.(/logger.log(/g; s/logger\.warn?\.(/logger.warn(/g'
```

**Why this matters more than v3 implied**: the `?.` is anti-documentation. It tells the next reader "the logger might be missing those methods" — which is false. Anyone touching these handlers will preserve the pattern out of caution, propagating the lie. It's also a ~3-byte-per-call drag on cache locality in hot paths (`download.js` runs once per turn × per attachment).

**Recommendation**: do the sed-replace pre-merge. Two minutes. Zero risk because the default is provably non-null.

**Alternative (rejected)**: drop the `logger = console` default and require explicit injection. This is *theoretically* purer but doubles every factory's setup line and would force a much larger diff. Skip.

### 5. MEDIUM — handleMessage at 1100 LOC stays as-is; createBot at 330 LOC stays as-is

Question 4 + 5. Re-evaluated after the 13 surrounding handlers extracted:

**handleMessage (L553–1417, ~864 LOC)** is still the right boundary. It's not 1100 LOC of business logic — it's 1100 LOC of *integration glue* calling 30+ extracted helpers in arrival order:

```
extractAttachments → filterAttachments → downloadAttachments → transcribeVoiceAttachments
  → formatPrompt → startTyping → createStreamer → createReactionManager
  → autosteer.tryAutosteer → sendToProcess → result-handling → markReplied
```

Each step is a single concern that's been extracted. handleMessage is the **call graph** through them. Splitting it would create a `runTurn(deps, msg)` factory that takes 25+ injected helpers and returns nothing useful — pure ceremony, no testability gain (the integration points are already unit-tested via the extracted modules). v3's verdict holds: "stop extracting once the test boundary is clean, which it now is."

**createBot (L1418–1747, 330 LOC)** is the borderline case. Question 5 asks whether `onboardPairedChat` (~80 LOC), `dispatchRegularMessage` (~37 LOC), media-group buffering, and the 5 grammy event handlers could be 3 modules. Cost-benefit:

- `onboardPairedChat`: **viable extraction**. Self-contained, takes config/pairings/logEvent/tg/bot/BOT_NAME. ~80 LOC out + 30 LOC of factory ceremony in. Net: ~50 LOC win. But it's already cleanly nested inside createBot and only called from one place (L1633).
- `dispatchRegularMessage`: **NOT viable**. Closes over `bot`, `botUsername`, `mentionRe`, `dispatchHandleMessage`, `handleAbortIfRequested`, `getSessionKey`, `shouldHandle`, `config.chats` — at least 9 deps. Extraction would be a factory that takes 9 args and is called from 2 sites (the bot.on('message') handler + the media-group flush). Pure ceremony.
- The grammy event handlers (`bot.on('message')`, `bot.on('callback_query:data')`, `bot.on('edited_message')`, `bot.on('message:migrate_to_chat_id')`, `bot.catch`): each is a 5–40 LOC adapter. Extracting them would require passing the same 9–12 deps to each factory. Same ceremony cost as dispatchRegularMessage.

**Recommendation**: leave createBot intact. If you must trim, extract `onboardPairedChat` to `lib/handlers/onboard-paired-chat.js` — it's the only piece that's both self-contained and >50 LOC. Net: ~50 LOC out of polygram.js. **But** — this is the kind of marginal extraction that v3 warned against. Defer to 0.9.1 unless reviewer is itching for symmetry.
