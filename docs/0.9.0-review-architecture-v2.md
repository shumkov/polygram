# Polygram 0.9.0 Cleanup — Architecture Review v2

> Branch: `0.9.0-cleanup` @ HEAD ab0aee5
> Base: `0.8.0-spike` (rc.68 tree)
> Scope of v2: Phase A nested-lib reorg (commits 14-17) + Phase B
> partial extraction 5 of 10 (commits 18-23). Net since v1 baseline
> 5d9f88e: 36 files touched, +1183 / −1015, polygram.js −1008 lines.
> Reviewer: architecture-strategist (focus: layering, factory+DI
> consistency, residual orchestrator shape, test coverage gap).

## TL;DR

Phase A landed cleanly. The lib/<dir>/ split is directional (no cross-
subdir cycles), the rename moved files where the code already
gravitated, and cross-subdir imports flow `sdk/ → telegram/, error/,
agents/, lib root primitives` and `handlers/ → telegram/, error/, lib
root` without back-edges. The factory+DI pattern is consistent across
all six extracted modules — same `createX(deps) → fn` shape, same
upfront `TypeError` validation, same closure-over-runtime-context
strategy. The boot sequence at `main()` lines 3207-3252 wires
everything in a clear declarative block.

The risks introduced or surfaced by v2 fall into three buckets:

1. **Phase-A reorg created NEW stale-path documentation debt** that
   v1's LOW-4 didn't anticipate. Files moved (`lib/process-manager-
   sdk.js → lib/sdk/process-manager.js`, `lib/pm-router.js →
   lib/sdk/router.js`, etc.) but ~12 source-comment references still
   point to the old flat paths. Same class as v1 LOW-4 but expanded
   surface area.
2. **`pm-interface.js` is now mis-located.** It's the canonical
   contract for `lib/sdk/process-manager.js`, but it sits at lib/
   root while every other "sdk-coupled" file moved into lib/sdk/.
   Either it should move, or the rationale for keeping it at root
   needs a header note (it's plausibly a "future-pms-implement-this"
   contract that transcends sdk/, but the prose doesn't say so).
3. **The Phase B extractions left polygram.js with two import
   leaks** — `appendDisplayHint` (line 53), `MAX_FILE_BYTES` and
   `redactBotToken` (lines 27, 68) are no longer referenced in
   polygram.js after build-options.js / download.js absorbed their
   call sites. Three dead `require`s. Trivial to drop, but
   indicative — extraction commits should sweep the imports they
   orphan.

The remaining `polygram.js` (3592 lines) is **not** hollowed out —
the extraction has been disciplined about taking factory-shaped
slices, and the orchestrator core (`handleMessage` 1194 lines,
`createBot` 333, `dispatchHandleMessage` 162, `handleApprovalCallback`
150, `makeCanUseTool` 119) remains coherently mountable. But the
"700 lines of misc helpers" framing in the task brief understates
where the mass actually sits — see HIGH-1.

The **router** (`lib/sdk/router.js`, 30 LOC of identity + null-check)
v1 already flagged as ceremony. Phase A's move to `lib/sdk/` made it
worse: the router is now in the same subdir as the only thing it
"routes to" — defeating its own forward-compat justification (which
needs the seam to be ABOVE the impl, not next to it). See MEDIUM-2.

Tests: 1391/1391 pass. New unit tests for build-options (25) and
sdk-callbacks (22) — both well-targeted. The other four extracted
modules (voice/download/config-callback/abort) ride on integration
coverage; this is a real gap given they have non-trivial branching.

## HIGH (v2 NEW)

### HIGH-1 — `handleMessage` (1194 lines) is the architectural elephant; current extraction strategy doesn't reach it

**File**: `polygram.js:1441-2634`

Phase B has extracted six small-to-medium factories so far, totaling
**933 LOC** across lib/sdk/ + lib/handlers/. Of those, the
**meaningful orchestrator surface area moved** is closer to ~400 LOC
(the rest is JSDoc, factory wrapper, dependency validation). Not
nothing — but the polygram.js delta is −386 lines on a starting
file of 3978, ~10%.

Meanwhile a single function — `handleMessage` — is still **1194
lines (33% of post-extraction polygram.js)**. Its body holds:

- All slash commands (/model, /effort, /config, /context, /compact,
  /new, /reset, /reload, /agent, /stop) inlined as `if (text === ...)`
  branches.
- Streamer + reactor wiring per message.
- Autosteer detection + `pm.injectUserMessage` priority routing.
- The actual `pm.send` orchestration around assistant reply
  delivery.
- `entry.inputController.push` direct-leak sites (LOW-1 carry-forward,
  lines 1592 + 3526 — the second one is in attemptAutoResume, the
  first is in /compact handling inside handleMessage).
- The 30+ `sendReply` exit paths that all need `markReplied()`
  bookkeeping (the rc.59 hoist that introduced this lives at
  line 1491-1493).

The brief frames the remaining work as "autosteer detection,
slash-commands, approvals, handle-message orchestrator core, ~700
lines of misc helpers." That ordering is right; but the cumulative
weight of those four planned extractions is **~2400 lines** of the
current 3592. The polygram.js diet so far is the easy ~10%, not
the bulk.

**Why this matters now (not after Phase B finishes)**: the factory+DI
pattern works beautifully for the modules already extracted because
each one is a leaf — `voice` only writes to db + tg, `abort` only
reads pm + writes tg, etc. `handleMessage` is a tree: it dispatches
to ~12 sub-handlers, each with their own slice of state, and several
of those sub-handlers have non-trivial mutual recursion (e.g.
/compact triggers an inputController push, which queues a turn that
flows through `handleMessage` again on the next inbound).

If `handleMessage` gets extracted as ONE factory `createHandleMessage(deps)`
the deps list will be 30+ entries — the test failure mode becomes
"this factory needs every closure in polygram.js, what was the point."

**Recommendation**:

1. Do NOT defer slash-command extraction until after handleMessage.
   The slash commands are the cleanest sub-orchestrators (each is
   ~30-150 lines and a clear boundary: parse → mutate → reply →
   markReplied). Extract them FIRST as `lib/commands/<name>.js` —
   each as a factory `createCommand<Name>(deps)`. After that lands,
   handleMessage shrinks to ~600-700 lines and the residual
   structure (inbound-classification → command-route → fall-through-
   to-LLM-turn) becomes legible.
2. Pre-write a lightweight router for slash commands: a Map<string,
   handler> populated at boot, dispatched from a single ~10-line
   function in handleMessage. Avoids the 1:1 if-chain and gives a
   natural seam for `/help` to enumerate available commands.
3. Reconsider whether the "handleMessage orchestrator core" should
   be a factory at all. After slash + autosteer + approvals leave,
   what remains is the assistant-turn pipeline — that's a class-
   shaped concern (per-turn state: streamer, reactor, sourceMsgId,
   abortGrace mark). A `Turn` object whose constructor takes
   per-turn context and whose method `run()` does the work might
   model the domain better than a 600-line factory closure.

**Severity rationale**: HIGH because the architectural decision of
"how do we extract handleMessage" is the load-bearing call for the
rest of Phase B. Get it wrong and the next 2400 lines of extraction
either compound the current factory pattern beyond its reach or
require re-architecting after the fact.

**Files**: `polygram.js:27, 53, 68`

```js
        ^^^^^^^^^^^^^^^^^^                  // unused (build-options.js owns it)

        ^^^^^^^^^^^^^^^                     // unused (download.js owns it)
```

`filterAttachments` is still used (line 1832, 1840, 1880); only

fully dead.

**Why HIGH not LOW**: this is a pattern bug, not a typo. The

of truth ambiguous to a future reader: "is download.js authoritative
for redactBotToken or is polygram.js still using it for something?"
Multiplied across the four remaining Phase B extractions, this
becomes 6-15 additional dead imports in the post-Phase-B tree.

**Recommendation**: amend each Phase B commit (or follow-up before
0.9.0) with the import-cleanup. Add a checklist item to the Phase B
template: "did you grep for every symbol you migrated and remove

### MEDIUM-2 — Router moved to lib/sdk/, defeating its own forward-compat justification

**File**: `lib/sdk/router.js`

v1 LOW-2 flagged the router as 30 lines of `(x) => x` ceremony.
The team's response (and the router's own docstring) defended this
as a forward-compat seam: "future alternate pm impl (a pi-agent-
core adapter, a synthetic test pm) can slot in cleanly behind the
same interface."

Phase A then moved the router INTO `lib/sdk/`. This is geometrically
incoherent with the forward-compat claim:

- A "router" that picks between sdk-pm and pi-agent-core-pm
  cannot live INSIDE the sdk/ subdir. It needs to be ABOVE it,
  alongside `lib/pm-interface.js` (the cross-impl contract).
- A future contributor adding `lib/pi-agent/process-manager.js`
  would have to cross-import from lib/pi-agent/ → lib/sdk/router.js,
  which reads as "the pi-agent pm depends on the sdk router" — a
  coupling that violates the sibling-impl story.
- The router currently `require`s nothing except its own factory
  closure; it has zero dependency on anything in lib/sdk/. The
  rename was filing-cabinet logic ("router-of-pm-things lives with
  pm-things") not architecture.

**Combined with v1 LOW-2**, this puts the router in an awkward
position: it's still 30 lines of identity, AND it's now mis-
located for the future-state it's supposed to enable.

**Recommendation**: pick one:

(a) **Accept the router is theatre and delete it.** polygram.js
imports `ProcessManagerSdk` directly, `pm = new
ProcessManagerSdk(...)`, no factory, no router file. Saves 30 lines
+ one require + cognitive overhead. When the second pm arrives
(IF it arrives), introduce the seam THEN — likely as a different
shape (e.g. per-chat dispatch in `lib/pm-dispatcher.js` at lib/
root, with a Map<chatId, pmName> instead of a wrapper).

(b) **Keep the router but move it back to lib/ root** as
`lib/pm-router.js` (its v0.8.x location) so it sits alongside
`lib/pm-interface.js` — the "above all impls" position the
forward-compat narrative requires. lib/sdk/ is for "things that
depend on the SDK"; the router does not.

Strong preference for (a). The forward-compat scenario is uncertain
and the cost of re-introducing the router LATER is one PR. The cost
of the wrong-place ceremony NOW is paid every time a contributor
asks "wait, why is the router inside the impl it's allegedly
abstracting over."

### MEDIUM-3 — `lib/pm-interface.js` location is unargued

**File**: `lib/pm-interface.js`

After Phase A, the layout is:

```
lib/sdk/process-manager.js   ← only impl of Pm
lib/sdk/router.js            ← also touches Pm
lib/pm-interface.js          ← contract (still at lib/ root)
```

If the interface is genuinely cross-impl (the "future pi-agent
adapter implements this too" frame), then it correctly lives
above sdk/. But the prose at lib/pm-interface.js:1-16 doesn't
make that case explicit — it reads as the same canonical-contract
tone that lived alongside two impls in 0.8.x, just edited down.

The candidate decisions:

1. **Keep at lib/ root + add a one-paragraph header**: "This
   contract is intentionally above lib/sdk/ because it documents
   the seam alternate pm implementations will conform to." Pairs
   with MEDIUM-2(b) — both files at root.
2. **Move into lib/sdk/** as `lib/sdk/interface.js`. Defensible
   if the team accepts the forward-compat scenario is theatre
   (MEDIUM-2(a) collapse). But: this conflates contract with
   impl in a way that the JSDoc-only file resists; and if a
   second pm arrives, the contract has to migrate back.

Right now it's neither — the file is at lib/ root by accident of
not being moved, with prose that doesn't justify the position.

**Recommendation**: pair with MEDIUM-2 decision. If (a), move
pm-interface.js into lib/sdk/ and rename to `interface.js`. If
(b), keep both interface + router at lib/ root and add the
header note.

### MEDIUM-4 — Test coverage gap for 4 of 6 extracted modules

**Files**:

- `lib/handlers/voice.js` — 115 LOC, no unit test (tests/voice.test.js
  covers `lib/telegram/voice.js`, the lower-level transcribe API)
- `lib/handlers/download.js` — 187 LOC, no unit test
- `lib/handlers/config-callback.js` — 126 LOC, no unit test
- `lib/handlers/abort.js` — 97 LOC, no unit test

The two with tests (build-options.js + 25 tests; sdk-callbacks.js +
22 tests) were the LEAST orchestration-heavy of the six. The four
without tests are exactly the ones with branching:

- voice.js has provider-config flow + ackEmitted boolean + per-
  attachment success-or-failure + combined-text persistence.
- download.js has the reuse-path branch (att already on disk),
  3-layer size enforcement, EEXIST race, atomic-rename + cleanup,
  redactBotToken on failure.
- config-callback.js has the model-vs-effort branching, 4 distinct
  early-exit paths, the existingRows card-shape detection, the
  `applied`/`anyActive` ACK text wording.
- abort.js has the `hadActive` race-with-close-event ordering, the
  ru/en language detection, the markBeforeKill ordering invariant.

Integration coverage for these flows lives in tests like
`tests/replay.test.js`, `tests/process-manager-sdk.test.js`, etc. —
but those exercise happy paths. The bug-shaped behaviors above
(EEXIST race, abort-before-close ordering, ackEmitted suppressing
QUEUED reaction) need targeted tests.

**Recommendation**: each of the four extracted handler modules
should have a unit-test file before 0.9.0 cuts. Estimated 60-80
tests total, ~3-4 hours of work. Not a blocker if the team accepts
the integration coverage; but the factory+DI pattern was chosen
PRECISELY to enable cheap unit testing (deps mockable at
construction time) — leaving that affordance unused weakens the
extraction's justification.

### LOW-2 — Factory dependency lists growing past readable

**Files**: `lib/sdk/callbacks.js:23-39`, `polygram.js:3207-3212`

`createSdkCallbacks` takes 13 deps (db, dbWrite, config, bot,
botName, tg, logEvent, classifyToolName, announce, shouldAnnounce,
contextHintShown, extractAssistantText, getChatIdFromKey,
getThreadIdFromKey, logger). It validates each with a `TypeError`
guard.

That's fine for ONE module. But the same six deps (db, config, tg,
logEvent, dbWrite, botName) reappear in voice.js, download.js,
config-callback.js, abort.js. Plus pm appears in two of them. Plus
each module adds its own 3-5 specific deps.

If the remaining four extractions (slash commands, autosteer,
approvals, handleMessage core) add at the same rate, each new
factory will be opening with 8-15 dep validations. The `main()`
wiring block becomes a catalog of 10+ `createX({ ... })` calls
each with 8-15 properties.

**Why LOW not MEDIUM**: this is forecasting, not an existing bug.
But the 13-dep `createSdkCallbacks` is already at the edge of what
a `{ a, b, c, ... } = {}` destructure reads cleanly.

**Recommendation** (forward-looking): consider an explicit
`PolygramRuntime` object built once in main() — `{ db, dbWrite,
config, bot, botName, tg, logEvent, logger }` — passed as
`{ runtime, ...moduleSpecific }` to each factory. Each factory
destructures `runtime` for the common deps. Reduces wiring noise,
makes "what's the runtime context" a named thing.

If Phase B sticks with the current pattern, that's defensible —
just flag this as a watch-the-wiring-noise concern.

### LOW-4 — Boot-time wiring order has an undocumented invariant

**File**: `polygram.js:3225-3252`

```js
buildSdkOptions = createBuildSdkOptions({ config, ..., makeCanUseTool, ... });
// transcribeVoiceAttachments, downloadAttachments, handleConfigCallback, handleAbortIfRequested wired here
const sdkPm = new ProcessManagerSdk({ ...pmOpts, spawnFn: buildSdkOptions });
pm = createPmRouter({ pm: sdkPm });  // ← pm bound HERE
```

But `handleConfigCallback` and `handleAbortIfRequested` (lines 3241,
3246) take `pm` as a dep, and they're wired BEFORE `pm` is assigned
on line 3252. This works only because:

1. `pm` is captured as a closure-binding at top-level (line 518:
   `let pm = null`), and
2. The handlers don't actually CALL `pm` until later (when a
   callback fires on a real chat message), by which time `pm` has
   been reassigned.

This is fine in practice — the let-rebind pattern hides the
ordering — but it's an undocumented invariant. If a future
extraction adds a factory that calls `pm` synchronously during
its own construction (e.g. to read `pm.keys()` for replay), the
wiring breaks subtly.

**Recommendation**: either
- Move pm assignment ABOVE the four handler factories that depend
  on it (move line 3251-3252 up to before 3241), so the dep chain
  is left-to-right; OR
- Add a one-line comment at the wiring block: "Order matters: pm
  is captured via closure, so handler factories that call pm
  during construction must wire AFTER `pm = createPmRouter(...)`."

5-line move, no behavior change.

### LOW-5 — handlers/config-callback.js leaks SDK-specific knowledge

**File**: `lib/handlers/config-callback.js:90-94`

```js
if (setting === 'effort') {
  applied = await pm.applyFlagSettings(callbackSessionKey, { effortLevel: value });
} else if (setting === 'model') {
  applied = await pm.setModel(callbackSessionKey, value);
}
```

These two pm methods are documented in `lib/pm-interface.js` as
**optional**. Pre-0.9.0, the contract said callers should
feature-detect — `typeof pm.applyFlagSettings === 'function'`.
v1 LOW-1 noted the contract claim was being relaxed because SDK
pm exposes everything.

The extracted handler now bakes "these methods exist" as a hard
assumption (if they were absent, the call rejects with TypeError).
Acceptable today (single SDK pm). Coupled to MEDIUM-2/MEDIUM-3
forward-compat claim — if a future pm doesn't implement either
method, this handler breaks.

**Recommendation**: either drop the "optional" language from
pm-interface.js for these two methods (acknowledge SDK-only world)
or restore the feature-detect in config-callback.js. Don't leave
the contract fork.

## Pass-through (verified, no concerns)

- **Phase A directional flow**: confirmed no cross-subdir cycles.
  Imports flow `sdk → telegram, error, agents, lib root`,
  `handlers → telegram, error, lib root`, `telegram → error`,
  `approvals → lib root`. No back-edges.
- **Factory shape consistency**: all six extracted modules use
  the same `createX({ deps }) → fn-or-object` pattern, all do
  upfront `TypeError` validation, all close over runtime context.
  Pattern is appropriate for these slices (leaf handlers, no
  per-call state).
- **Boot wiring at main()**: declarative block at 3207-3252 is
  legible. Six `createX({ ... })` calls in sequence, then
  `new ProcessManagerSdk(...)`, then `createPmRouter`. Ordering
  caveat at LOW-4 but no boot bug in practice.
- **Test discipline for build-options + sdk-callbacks**: 47 tests
  total, well-targeted, exercise both happy path and error
  branches. Run in <100ms. Demonstrates the factory pattern's
  testability when followed through.
- **No new circular imports**: `grep -rn 'require.*\.\./'` across
  all subdirs returns 9 cross-subdir imports, all directional.
- **handlers/* import discipline**: handlers/ never imports from
  sdk/, never imports from polygram.js. Correct layering — handlers
  are LEAF orchestrators called by polygram.js, not peers of pm.
- **`build-options.js` env scrub correctness**: `filterEnv` +
  CHILD_ENV_ALLOWLIST + CHILD_ENV_PREFIXES preserved verbatim
  from polygram.js pre-extraction. The extraction is faithful to
  the v4 plan §6.5.7 SHADOW semantics.
- **`sdk-callbacks.js` event delegation**: each callback delegates
  to head pending's per-turn streamer/reactor, with `?.context?.`
  null-chaining. Heartbeat plumbing for stall/freeze timer
  preserved.
- **`abort.js` mark-before-kill ordering**: explicit comment at
  line 56-58 captures the race-with-close-event invariant.
  Preserved from pre-extraction.
- **`download.js` 3-layer size cap + atomic write**: all three
  size enforcement points preserved (content-length, streaming
  accumulator, post-buffer); EEXIST race comment preserved.
