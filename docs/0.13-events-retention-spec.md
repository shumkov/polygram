# 0.13 — events-table retention (#3)

> **Status: spec v2 (post multi-persona review) — awaiting sign-off, then build (TDD).**
> **Severity:** operational — `events` grows unbounded fleet-wide. It is the table that
> ballooned `shumabit.db` to 4.4GB in the May-3 EIO storm (23.7M dead rows). Root cause is
> fixed (c153c0d) but there is still **no cap** on growth. Deletes from PRODUCTION
> partner-facing DBs ⇒ irreversible; the safety layer below is load-bearing, not optional.

## Problem
`events` (`migrations/001-initial.sql:85`: `id, ts, chat_id, kind, detail_json`; indexed
`idx_events_recent(ts DESC)`, `idx_events_kind(kind, ts DESC)`) is append-only, never pruned.

### Grounded data (shumorobot 0.12.x + VPS shumabit.db, 2026-06-15)
- ~850 events/day on the busy bot, unbounded ⇒ ~300MB/yr/bot (DB already 19MB).
- Active high-volume diagnostics: `reactor-state`, `hook-lag-sample`, `tool-result` (and the
  now-dormant `hook-event`/`turn-phase-change`, silent since 2026-05-25 — kept in the diagnostic
  tier defensively in case they're re-enabled).
- Rare high-value: `polygram-start/stop`, `handler-error`, `shutdown-drain`, `resume-fail`.
- Distinct kinds in practice: ~82 (≫ the handful we can name) ⇒ **the tier lists cannot be the
  only growth boundary** (a kind's volume changes release-to-release — hook-event proved it).

## Consumers — audited (corrected after review)
- **Only in-process reader: `db.js findOrphanedCompactCommands`.** Its *scan* is bounded
  (`compact-command` within `resolveReplayWindowMs`, **capped at 2h** — `lib/db/replay-window.js`).
  BUT its rc.66 dedup sub-query (`db.js:403`) matches handled markers by `original_ts` with **NO
  time bound**. Safe under our windows (all `compact-*` sit in the 90d default ≫ 2h), but a future
  config shortening their retention below ~2h could **re-surface an already-handled /compact to a
  partner**. ⇒ guard at policy-load (below), don't rely on luck.
- **Out-of-process (checked, all safe):** `scripts/doctor.js` (24h failure window), `scripts/split-db.js`
  (one-time copy), polygram-deploy skill forensics (reactor-state/autosteer/handler-error, all ≤30d).

## Design — tiered time prune + universal per-kind row cap
Time tiers target the known noise; a **universal per-kind row cap** is the real safety net that
makes list-completeness *not* load-bearing and makes keep-forever incident-proof.

| tier | kinds | retain by time |
|---|---|---|
| diagnostic | reactor-state, hook-lag-sample, tool-result, cli-ups-seen, hook-event, turn-phase-change | **14d** |
| default | everything else (incl. autosteer, turn-timeout*, compact-*) | **90d** |
| keep-forever | polygram-start/stop, shutdown-drain, handler-error, auth-expired, resume-fail | never (by time) |

**Universal cap (NEW, the incident-proofing):** after time-pruning, for **every** kind — including
keep-forever — keep at most `MAX_PER_KIND` (default **50,000**) most-recent rows; delete older.
This bounds (a) any runaway/unknown new kind before someone updates a list, and (b) a `handler-error`
storm of the exact May-3 shape (12k/sec) — keep-forever can never exceed 50k rows. Subsumes the two
review findings about hardcoded lists + uncapped keep-forever.

Defaults in code; overridable via `config.json` `events_retention` (windows, tier membership, caps,
`enabled`, `dryRun`).

## Mechanism — `pruneEvents(db, now, policy)` in `lib/db.js` (pure, testable)
- **Single `now` snapshot** passed in; every cutoff = `now - windowDays*86400_000`; comparator is
  **`ts < cutoff` (exclusive)** everywhere (pinned in design, not just tests).
- **Explicit placeholders** for IN-lists: build `?,?,?` sized to the set (better-sqlite3 does NOT
  expand a JS array from one param; `NOT IN (…, NULL)` is a 3-valued-logic trap → wrong/zero deletes).
  Validate no NULL/empty member.
- **Steady-state prune in ONE `rawDb.transaction(()=>…).immediate()`** (BEGIN IMMEDIATE — the
  `approvals/store.js:188` / `pairings.js:193` pattern): all tier DELETEs + cap DELETEs atomic, so a
  mid-prune crash can't half-prune and the `events-pruned` audit reflects exactly what committed.
- **First catch-up is batched, NOT one big DELETE.** `DELETE ... LIMIT N` **is supported** in our
  better-sqlite3 build (verified: compiled with `SQLITE_ENABLE_UPDATE_DELETE_LIMIT` — my v1 claim it
  wasn't was wrong). Loop `DELETE … LIMIT 5000` committing per batch, yielding to the event loop
  between batches, so a large first prune can't stall the synchronous daemon (measured: 2M-row single
  DELETE blocks ~1.3s — unacceptable; batched it doesn't). After a large catch-up, one
  `PRAGMA wal_checkpoint(TRUNCATE)` to reclaim WAL slack.
- **Indexes:** per-kind `WHERE kind=? AND ts<?` → `idx_events_kind`; default `WHERE ts<? AND kind NOT
  IN(…)` → range-scan `idx_events_recent` then filter (bounded by time — confirm via EXPLAIN in tests).

## Safety layer (load-bearing — the review's core asks)
1. **Clock-sanity guard:** compute `MAX(ts)`; if `now < MAX(ts)` (clock went backward) or
   `now - MAX(ts)` is implausibly large (forward jump), **skip the prune** + emit a loud
   `events-prune-skipped` event. Never delete on a clock you can't trust (NTP jump on a cloud host
   could otherwise mass-delete recent data).
2. **Per-run mass-delete cap:** before deleting a bucket, `COUNT(*)` it; if it would remove
   > `MAX_DELETE_FRACTION` (default 50%) of the table OR a configurable absolute, **refuse + log
   loud** instead of deleting. At steady state a prune removes ~850 rows; anything removing half the
   table is anomalous by definition. (This is the check that would have made May-3 a deliberate op.)
3. **`enabled` kill switch** (default true) — disables BOTH boot-prune and interval via config, no
   redeploy needed.
4. **`dryRun` mode** — runs every COUNT, deletes nothing, emits `events-prune-preview` with per-bucket
   counts. Used for the first VPS run before arming.
5. **Backup before first real prune per DB:** `VACUUM INTO 'shumabit.db.pre-prune-<ts>.bak'` (online,
   read-snapshot) on the first armed run; keep until size plateau is confirmed.
6. **Audit survives the prune:** `events-pruned` / `events-prune-preview` / `events-prune-skipped` are
   in keep-forever (and thus under the universal cap, so still bounded). Detail carries per-bucket
   cutoff ts + table count before/after + rows deleted. Also `console.log` the prune line so the
   deploy log has it even if the table is later compromised.

## Cadence
Boot prune is the **primary** path (≈7 deploys/day ⇒ a daemon rarely lives to a 24h tick). Run it
once via `setImmediate` **after** `runMigrations` + after the bot is marked ready (non-blocking). A
24h `setInterval` is genuine insurance for long-uptime daemons (e.g. a settled VPS) — and **must be
`.unref()`'d** (like `polygram.js:2319`) so it can't hold the event loop against the SIGHUP shutdown
drain (the EIO-storm path is delicate — see [[polygram-deploy-eio-storm-known]]). An in-flight bool
prevents a tick overlapping a long first-run.

## Policy-load validation (fail loud at startup)
- The three tier sets are **pairwise disjoint** (a kind in both diagnostic + keep-forever would be
  deleted at 14d — the per-kind DELETE doesn't honor keep-forever). Throw if not.
- All `compact-*` kinds resolve to retention **≥ replay-window cap (2h) + margin** (else the rc.66
  re-surface bug re-arms). Throw if a config edit violates it.
- No NULL/empty kind in any list.

## Test plan (TDD — write first, watch fail, then implement)
`tests/events-retention.test.js`, temp DB:
1. diagnostic pruned at 14d (13d survives, 15d deleted).
2. default pruned at 90d (89d survives, 91d deleted).
3. keep-forever survives at 400d **but** universal cap trims it past MAX_PER_KIND (seed 50,001 →
   50,000 kept).
4. universal cap on an unlisted/new high-volume kind (seed 60k of `foo-sample` → capped to 50k).
5. recent (1d) all-kinds survive.
6. boundary: `ts == cutoff` survives (pins `<`).
7. **consumer regression:** `compact-command` + its handled marker at 20d both survive → no
   re-surface; AND policy-load **rejects** a config putting compact-* below the 2h replay cap.
8. disjoint-set validation throws on overlapping tiers.
9. clock-skew guard: `now` < MAX(ts) ⇒ skip, nothing deleted, skip-event emitted.
10. mass-delete cap: a bucket that would delete >50% ⇒ refuse + log, nothing deleted.
11. dryRun: counts emitted, zero rows deleted.
12. IN-list binding: keep-forever kind just past default cutoff survives AND non-protected rows at
    same age are deleted (proves the placeholder list actually bound, not a NULL no-op).
13. return value: per-bucket deleted counts feed `events-pruned` correctly.

## Rollout (staged — do NOT couple first prod delete to a normal release)
1. Ship code with `dryRun` honored. Deploy to **shumorobot** first.
2. Dry-run on shumorobot → inspect `events-prune-preview` counts → arm (enabled, dryRun off) → soak ~1 day.
3. Dry-run on the **VPS** (`shumabit.db` + `umi-assistant.db`) → inspect → `VACUUM INTO` backup → arm.
4. Watch one `events-pruned` per bot; confirm DB size plateaus over the following week.

## Changelog (v1 → v2, from the multi-persona review)
- **Fixed factual error:** `DELETE...LIMIT` IS supported (drove the batching design).
- **Added** universal per-kind row cap (incident-proofs keep-forever + unknown new kinds).
- **Added** safety layer: clock-sanity, mass-delete cap, dryRun, enabled kill switch, backup-first,
  audit-survives-prune.
- **Corrected** consumer audit (the unbounded `original_ts` dedup; doctor.js/split-db.js noted).
- **Pinned** boundary `<` + single `now`; explicit IN-list placeholders; single BEGIN IMMEDIATE txn;
  batched first catch-up + WAL checkpoint; `.unref()` interval; boot-prune-primary framing.
- **Added** policy-load validation (disjoint tiers, compact-* ≥ replay window, no NULL kinds).
- **Staged** rollout (shumorobot → VPS, dry-run-then-arm) instead of fleet-wide-on-deploy.

## Open decisions (sign-off)
1. **Windows:** 14d diagnostic / 90d default / keep-forever-by-time — good? (90d default keeps
   quarterly forensics; the universal cap, not the window, is what bounds growth.)
2. **Universal cap `MAX_PER_KIND` = 50,000** — reasonable? (At ~850/day mixed, 50k of any single kind
   is months of that kind; an incident storm gets bounded hard.)
3. **`MAX_DELETE_FRACTION` = 50%** refuse-threshold — good, or stricter?
4. **Config surface** `events_retention` (windows/tiers/caps/enabled/dryRun) — wanted, or code-only?
