# 0.10.0 — tmux backend: the patience-model problem

> **Status: OPEN.** Problem statement for a multi-agent structural
> investigation. Every investigating agent must read this in full
> before touching code or proposing a fix.

## Why this matters

The 0.10.0 tmux concurrency rewrite (`0.10.0-tmux-concurrency-problem.md`
/ `solution.md`) shipped a correct turn-ledger and closed the
content-matching class of bugs. Since then we have shipped **eight
release candidates** (rc.20 → rc.28) — each closing a real bug, each
making the Music topic work for one more case, each followed by a new
production failure in an *adjacent* spot:

| rc | Fix | Music topic broke again because… |
|---|---|---|
| rc.20-22 | turn ledger, R7/8 timeout, B1/B2/B3 | …spawn-lifecycle (S1) and config drift (S2) |
| rc.21 | S1 orphan kill + S2 config drift | …large-paste-not-submitted (B5) |
| rc.23 | B5 submit-confirm via capture-pane | …slow-MCP startup gates fooled (B6) |
| rc.24 | B6 readiness on pane quiescence | …banner-stays-forever for slow-MCP (B6 v2) |
| rc.25 | B7 submit-confirm via JSONL token | …user-level config bloat dragged in serena (`isolateUserConfig`) |
| rc.26 | `isolateUserConfig` removes global MCP | …`_waitForReady` still fooled when MCP loaded inside an isolated topic (B8) |
| rc.27 | B8 readiness on debug-log quiescence | …subagent (Agent tool) turns failed §6 (B10) |
| rc.28 | B10 outstanding-Agent keeps turn alive | **today: §6 fired at 2 s anyway; B7 fails loud on a paste the TUI legitimately queued** |

The pattern is unambiguous. The fundamental turn machinery is not the
problem any more. What keeps breaking is **polygram's "is this turn
making progress" model** — a constellation of independent patience
windows, each tuned to a different assumed workload. The
music-curation workload (slow MCP, subagents, multi-minute downloads,
batched parallel messages) lives further out on the timeline than any
single window expects, and every window we extend just makes the next
one the cliff edge.

## The current patience constellation (audit, may be incomplete)

`lib/process/tmux-process.js`, `lib/tmux/*`, `lib/process-manager.js`,
`polygram.js`:

| # | Window | Mechanism | Patience | Motivating incident |
|---|---|---|---|---|

| 2 | `_pasteAndEnter` atomicity | per-session async-lock + 50 ms drain | 50 ms | L3 |
| 3 | `pasteConfirmMs` next-paste gate | gates the *next* paste on JSONL `user-message` for the previous | ~250 ms | Phase 3 §5 |
| 4 | `_confirmSubmitViaJsonl` | waits for tokened `user-message`; re-sends Enter `N` times | `submitConfirmMs` × 5 retries | B7 |
| 5 | §6 fail-loud "no JSONL reply text" | capture-pane wins, JSONL has no main-text → grace → throw | `lateGraceMs` | R10, B7 §6 |
| 6 | B10 outstanding-Agent | suppresses §6 while an unreturned `Agent` tool_use exists | unbounded (until tool_result) | B10 |
| 7 | `_awaitTurnComplete` quiescence | capture-pane sees TUI quiescent → declares complete | `quiesceMs` | C-original |
| 8 | `turnTimeoutMs` (chat `timeout`) | absolute deadline on a single turn | now 1800 s (30 min) | the music-download timeouts |
| 9 | Reactor STALL → TIMEOUT → ERROR | visual emoji cascade on no-text-activity | 45 s STALL, longer for the rest | L6, the visible "stuck" feedback |
| 10 | `_sweepStaleTurns` | ledger sweep for `pasted` with no JSONL correlation | `turnTimeoutMs` | Phase 4 |

Several of these windows are **already mutually inconsistent.** B7
gives up at ~5 × `submitConfirmMs` and throws `TMUX_SUBMIT_FAILED`
even when the TUI has legitimately *queued* the paste (#11) and would
process it later. §6 fires loud at `lateGraceMs` even when the agent
is just about to spawn a subagent (B10 patches one variant of this,
but only if the Agent emission lands inside the grace). The reactor
visual escalates to 🤯 while the agent is genuinely working (#9 vs
#8 vs the actual turn liveness).

Each window assumes a different workload distribution; none of them
sees the same "turn is making progress" signal.

## The empirical pressure

The music-curation workload, from real JSONL and debug-log evidence
across the Music-topic incidents:

- **MCP cold-start:** serena 27.5 s, context7 26 s, peekaboo 9 s,
  playwright 24 s (cold). `_waitForReady` (B8) handles this — but
  only if the debug-log quiesces and the pane stabilises.
- **Subagent (`Agent` tool) duration:** 9–12 minutes is normal for a
  download task. The main pane is quiescent the whole time; only the
  sidechain JSONL has activity.
- **Single-tool wall time:** `dl` (audio download), `dl-batch` —
  multi-minute. One Bash invocation, then nothing in JSONL for
  minutes.
- **Batched messages:** users send multiple followups while the agent
  works. The TUI parks them (`Press up to edit queued messages`)
  visibly, but polygram has no token-bound notion of "this paste is
  legitimately parked, not lost."
- **Polygram-wrapped prompt size:** 1–3 KB → claude TUI collapses to
  `[Pasted text #N]` bracketed paste blocks. Submit is sometimes a
  second Enter (B5 / B7 retry).
- **Combined turn duration:** a "download 3 releases" turn legitimately
  runs 10–15 minutes, with 30+ tool uses, possibly across subagents.

Every window in the constellation above was calibrated against a
chat-style workload (seconds, occasional minute). None of them are
calibrated against this empirical distribution.

## The structural question

Replace a constellation of independent timers with **one unified
progress predicate.** Some candidate signals — the investigation must
characterise which are reliable:

- **TUI bottom bar / status line:** the live TUI shows `esc to
  interrupt` while a turn is streaming, `⏵⏵ accept edits on` /
  `bypass permissions on` while idle, `Press up to edit queued
  messages` while pastes are queued, `◯ <name> <task> Nm Ns` while a
  subagent runs, `Running…` next to a Bash, `Crafting… Nm Ns` /
  `Forging…` while thinking.
- **JSONL activity:** the rate of new lines (main + sidechain), the
  presence of outstanding `tool_use` without matching `tool_result`,
  the presence of an unreturned `Agent` tool_use.
- **Debug-log activity:** MCP connections, slow-render logs, tool
  invocations.

The deep question is whether **the union of these signals** can
support a single boolean — "the turn is making progress" — that
every patience window in §"current constellation" should gate on,
instead of its own timer. Possibly with one absolute floor (the chat
`timeout`) as the only hard limit.

If yes: the design collapses 11 windows to ~2 (the progress predicate
+ the absolute deadline), and the music-curation workload sails
through because *every* one of its slow phases registers as
progress.

If no — if the signals aren't reliable enough to unify on — the
investigation should produce a smaller, principled set of windows
that are at least *coherent with each other* (e.g. B7's `5 × short`
retry must understand TUI-queued pastes; §6 must understand subagent
activity; the reactor must reflect actual progress, not just text).

## What the investigation must do

The five-agent pattern that worked for the original tmux concurrency
rewrite (independent audits converging on the same fix) is the right
shape. Each agent reads this doc in full, then takes one facet:

1. **Patience-window audit.** Walk the code; produce a complete,
   accurate version of the table above; tie each window to the
   production incident that motivated it; identify the windows that
   conflict with each other under the music-curation workload.
2. **Workload characterisation.** From real JSONL
   (`~/.claude/projects/-Users-ivanshumkov-Music-rekordbox/*.jsonl`),
   the debug logs (`~/.polygram/shumorobot/logs/`), and the
   `events` DB (`~/.polygram/shumorobot.db`), produce the empirical
   distribution polygram's patience must accommodate — durations,
   gap lengths, message-burst patterns, subagent counts.
3. **TUI progress signals.** Catalog *every* TUI bottom-bar /
   status-line indicator across the states that matter (streaming,
   idle, queued, subagent-running, tool-running, thinking,
   approval-pending, error). Verify against real `tmux capture-pane`
   output from live sessions. Output: a mapping from indicator to
   progress state.
4. **JSONL + debug-log progress signals.** Same, for the structured
   sources. Specifically: how does an outstanding `Agent` tool_use
   appear; how do sidechain lines appear; what does an MCP startup
   write; what does a hung tool look like vs an idle TUI; what
   distinguishes "agent just emitted a tool_use and is waiting on
   tool_result" from "agent is done and the turn is over."
5. **Unified progress predicate + implementation feasibility.**
   Given the catalogs from (3) and (4), draft a single predicate
   *"the turn is making progress"* that the windows in (1) can all
   gate on. Identify which current windows can be retired entirely
   (replaced by the predicate + the absolute deadline), and which
   must remain (e.g. a hard timeout). Sketch the impl.

All five agents work in parallel, read-only. They return findings.
I synthesise into the solution design.

## Constraints

- The claude CLI is pinned to 2.1.142 and unmodifiable. Whatever
  signals we use must be observable from the outside (capture-pane,
  JSONL, debug-log).
- All chats are migrating to the tmux backend.
- The fix must not regress the existing 2026+ passing tests, the
  closed B1–B10 / S1 / S2 / R-iso findings, or the spike scenarios.
- The fix must work for both ends of the workload:
  short chat turns (seconds), and music-curation (15+ minutes,
  subagents, batched messages).

## Goal

Stop tuning windows one bug at a time. Produce a coherent progress
model so the music-curation workload — and any future workload
heavier than chat — works without a new patch each time.
