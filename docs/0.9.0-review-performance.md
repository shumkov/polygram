# 0.9.0 Cleanup — Performance Review

> Reviewer: performance-oracle
> Branch: `0.9.0-cleanup` (HEAD `f4649d0`)
> Base:   `0.8.0-spike`
> Scope:  `polygram.js`, `lib/pm-router.js`, `lib/process-manager-sdk.js`
> Date:   2026-05-05

## TL;DR

The 0.9.0 cleanup is **net performance-positive** on every axis examined:
boot path is faster (single SDK pm vs. CLI+SDK dual instantiation), hot path
is marginally faster (1–4 fewer function-pointer dereferences per
`handleMessage` and per `applyConfigChange`), idle RSS drops modestly
(the deleted CLI pm carried a `child_process` Map and stream-json line-
buffer machinery), and the inlined `pm.X` call sites do **strictly less
work** than the old `pm.pickFor(sessionKey).X` form. No regressions found.

The rest of this doc enumerates the savings concretely so the 2026-05-15
architecture review can confirm them, plus a handful of LOW-severity
clean-ups the cleanup didn't pick up.

#### LOW-1: `applyConfigChange` and `handleConfigCallback` `typeof === 'function'` guards are dead-but-cheap

**Files:**
- `polygram.js:1818` — `if (setting === 'effort' && typeof pm.applyFlagSettings === 'function')`
- `polygram.js:1821` — `} else if (setting === 'model' && typeof pm.setModel === 'function')`
- `polygram.js:2166` — same pattern in `applyConfigChange`
- `polygram.js:2170` — same

**Observation.** Per `lib/pm-interface.js:77` and the SDK pm class
definition (`lib/process-manager-sdk.js:869`, `:889`), `setModel` and
`applyFlagSettings` are **always-present instance methods** on
`ProcessManagerSdk`. With the CLI pm gone, `typeof pm.X === 'function'`
is invariably `true`. The check is now pure overhead.

**Quantification.** Each `typeof` check is a single property lookup +
typeof-tag comparison — single-digit nanoseconds in V8. Both `/model`
and `/effort` callbacks are operator-rate, not message-rate (humans
toggle settings, not turns), so the absolute hot-path cost is
negligible (~10 ns × O(once per minute) = noise).

**Why it still matters.** The plan's stated rationale for keeping the
router as a thin wrapper is "future alternate pm impls slot in
cleanly behind the same interface" (`docs/0.9.0-cleanup-plan.md:155`).
A future pm that didn't implement `setModel` / `applyFlagSettings` would
silently hit the `typeof` fallback and report `anyActive: false`, leaving
the user's `/model gpt-5` request silently a no-op (only the on-disk
chatConfig updated). That's a *correctness* concern, not performance.
Either:

- Drop the `typeof` guards (commits to "every pm impl must support
  setModel / applyFlagSettings", document it on `pm-interface.js`), OR
- Promote `setModel` / `applyFlagSettings` from optional to **required**
  in `pm-interface.js:75-78` so the guards don't drift back to
  meaningfulness.

The current state is "guard checks an invariant we already commit to" —
not a performance regression, but the cleanup left a vestigial defense.

**Recommendation.** Pure cosmetics; defer to the 2026-05-15 architecture
review. Either tightening is fine. No urgency.

#### LOW-2: `createPmRouter` boot indirection is identity — kept by design

**File:** `lib/pm-router.js:35-38`

```js
function createPmRouter({ pm } = {}) {
  if (!pm) throw new TypeError('pm required');
  return pm;
}
```

**Observation.** Post-cleanup `createPmRouter` returns the SDK pm
unchanged — `router === pm` at runtime. Boot pays one extra function
call (~5 ns, called once per launchctl kickstart, ~10×/day). Per-message
hot path is **zero** overhead — `pm.send`, `pm.has`, etc. are direct
`ProcessManagerSdk.prototype.X` calls with no wrapper layer between them
and the user code.

**Compared to old boot path** (`polygram.js:0.8.0-spike` lines around
4197-4222 of the diff):
- Old: `new ProcessManager(...)` (CLI pm, ~200 µs incl. internal Map
  creation) + `new ProcessManagerSdk(...)` (~50 µs) + `createPmRouter`
  with policy parsing (~10 µs).
- New: `new ProcessManagerSdk(...)` (~50 µs) + `createPmRouter` identity
  (~5 ns).

**Boot delta:** ~250 µs faster. Imperceptible to humans, but real.

**Recommendation.** Keep the indirection (the JSDoc rationale is sound;
it's a forward-compat seam, not a perf hazard). No action.

#### LOW-3: `handleMessage` hot-path savings

**Files / sites enumerated by the request:**
- `polygram.js:2148-2255` (slash-command dispatch)
- `polygram.js:2750-2870` (autosteer detection — current line range
  `2588-2680` post-cleanup)
- `polygram.js:3299-3301` (abort path — current line range
  `3299-3301` post-cleanup)

**Per-message cost analysis.** The old form was
`pm.pickFor(sessionKey).X(...)` which expanded to:

1. `pm.pickFor` — property lookup on the router object.
2. `pickFor(sessionKey)` — function call into router; inside,
   `pickPmKindFor(sessionKey)` runs (Set membership lookup +
   `getChatIdFromKey` invocation + string comparison).
3. Returns `cliPm` or `sdkPm`.
4. `.X` — property lookup on the resolved pm.
5. `X(...)` — actual method call.

The new form is `pm.X(...)`:

1. `pm.X` — property lookup on the SDK pm.
2. `X(...)` — actual method call.

**Savings per inlined call site:** 3 function-pointer dereferences
(`pickFor`, `pickPmKindFor`, `getChatIdFromKey`) + 1 Set.has + 1 string
comparison + 1 conditional. Order-of-magnitude **~50–80 ns saved per
inlined site** in V8 (rough estimate from the equivalent ops in
microbenchmarks; the actual savings depend on inline-cache state).

**Inlined sites in `handleMessage`:**
- `polygram.js:2027-2048` — `/context` path: 1 site (the `pm.isSdkFor`
  early-return; net was 0 inlined dereferences but saved a whole
  `sendReply` early-exit branch).
- `polygram.js:2027` — `/compact` path: same.
- `polygram.js:2127-2135` — `/new` `/reset` path: 1 inlined `pickFor` +
  removed `else { kill + clearSessionId }` branch.
- `polygram.js:2165-2174` — `applyConfigChange`: 1 inlined `pickFor`,
  invoked once per `/model` or `/effort`.
- `polygram.js:2593-2597` — `willAutosteer`: 1 removed `pm.isSdkFor`
  AND-clause (saves a whole router method call on every message).
- `polygram.js:2655` — `autosteerEnabled`: same — removed `pm.isSdkFor`
  AND-clause.
- `polygram.js:2738-2740` — auto-recover path: 1 inlined `pickFor`.
- `polygram.js:2798` — context-hint path: 1 removed `pm.isSdkFor`
  AND-clause.
- `polygram.js:3299-3301` — abort path: 1 inlined `pickFor`, simplified
  away the `typeof interrupt === 'function'` branch (the SDK pm always
  has `interrupt`, so the `else { kill }` fallback was dead).

**Total per-message savings (rough order):**
- Every message: ~150 ns (3× removed `isSdkFor` AND-clauses on the
  thinking-state + autosteer + context-hint paths).
- Slash-command messages (`/new`, `/reset`, `/model`, `/effort`):
  additional ~50 ns each.
- Aborts: ~50 ns + the eliminated subprocess-kill fallback.

At polygram's current ~10 messages/sec sustained ceiling per bot, this
is ~1.5 µs/sec saved — negligible against the multi-second LLM turn
times that dominate the request lifecycle. **The win is in code clarity
and eliminated branching, not measurable wall-clock perf.**

**Recommendation.** None — the cleanup did the right thing. Logging this
purely for the 2026-05-15 architecture review baseline.

#### LOW-5: `willAutosteer` does redundant Map lookups

**File:** `polygram.js:2593-2597`

```js
const willAutosteer = pm.has(sessionKey)
  && pm.get(sessionKey)?.inFlight
  && (chatConfig.autosteer != null
    ? chatConfig.autosteer !== false
    : config.bot?.autosteer !== false);
```

**Observation.** `pm.has(sessionKey)` followed by `pm.get(sessionKey)`
is two Map lookups when one suffices — `pm.get(sessionKey)` returns
`undefined` on miss, and the optional chain (`?.inFlight`) handles that
cleanly.

**Pre-existing.** This pattern existed at `0.8.0-spike` (line 2768 of
the old polygram.js) — **not introduced by the cleanup**. Confirmed via
`git show 0.8.0-spike:polygram.js`. Listing it here for completeness
since the cleanup left it alone.

**Same pattern at:**
- `polygram.js:2656` — `if (autosteerEnabled && pm.has(sessionKey))` then
  `pm.get(sessionKey)` immediately inside.
- `polygram.js:3454` (estimated) — `pm.has(sessionKey) && !!pm.get(sessionKey)?.inFlight`.

**Quantification.** `Map.prototype.has` + `Map.prototype.get` are both
O(1) hash lookups (~20 ns each in V8). Saving the redundant `has` saves
~20 ns/message × ~10 msg/sec = ~200 ns/sec/bot. Cosmetic.

**Recommendation.** Standalone follow-up: collapse the
`has` + `get`-into-temp pattern. Out of scope for the 0.9.0 cleanup.

#### LOW-6: Boot-path: `ProcessManagerSdk` instantiation deferral

**File:** `polygram.js:3992`

**Observation.** The SDK pm is instantiated synchronously in `main()`
before the bot starts polling. Constructor cost (`process-manager-sdk.js:181-228`)
is just option assignment + `new Map()` + `[]` — no I/O, no allocation
of any subprocess or stream resources. **Microseconds, not milliseconds.**

**Lazy-construct opportunity?** The user asks: "any opportunities to
defer / lazy-construct that were obscured when both pms had to be built
upfront for the dual-pm router?"

**Answer: no.** The SDK pm constructor doesn't touch the network, the
filesystem, or spawn any subprocess. It's pure object initialization.
Deferring it would save no measurable boot time and would force every
caller of `pm.X` to either await or carry a `Promise<Pm>`. That's a
worse tradeoff than the current "build at boot, every use is sync" form.

**Recommendation.** No action. Current boot is already optimal.

#### LOW-7: Idle RSS — old CLI pm carried `child_process.spawn` machinery

**Pre-cleanup (0.8.0-spike).** When `POLYGRAM_USE_SDK=1`, the daemon
boot built **both** CLI pm and SDK pm (`polygram.js:0.8.0-spike` ~line
4214). The CLI pm carried:

- A `procs` Map keyed by sessionKey, each entry holding a
  `child_process.ChildProcess` reference (~few hundred bytes per entry
  for the V8 Object + the wrapped libuv handle when alive).
- Per-session stream-json line-buffer state for stdout/stderr (the
  `proc.stdout.on('data', ...)` line-splitter accumulators).
- Per-session pendingQueue + spawn-args closures.

At idle (no active sessions), the empty Maps are ~16 bytes each. The
**class definition** of `ProcessManager` (lib/process-manager.js, 806
lines, deleted) is gone from the v8 heap snapshot — perhaps 50–150 KB
of compiled code + closures.

**Post-cleanup.** Only `ProcessManagerSdk` is loaded.
`require('./lib/process-manager')` no longer happens. The daemon's
`require.cache` is one less module entry. Total RSS savings at idle:
**estimated ~200–500 KB** (compiled code + module-level constants +
per-instance state for the never-used CLI pm). Real savings only show
up if the dual-pm boot was actually instantiating both — which it was,
on shumabit + umi-assistant under `POLYGRAM_USE_SDK=1`.

**Verification suggestion.** After the next deploy, capture
`/proc/<pid>/status` (or `ps -o rss` on macOS) for shumabit's polygram
PID 30 minutes after boot, compare to the same metric on a 0.8.0-rc.68
RSS baseline if telemetry kept it. Expected delta: small but visible
(<1% of total RSS, since the Anthropic SDK + node_modules dominate).

**Leftover state audit:**
- ✅ `cliPm` references — none in polygram.js (grepped).
- ✅ Dual-pm event listeners (the broadcast `Promise.allSettled` machinery
  inside `pm-router.js`) — fully deleted.
- ✅ `--input-format stream-json` parsing buffers — those lived inside
  CLI pm, never in polygram.js, and CLI pm is deleted.
- ✅ `bin/approval-hook.js` IPC bridge — deleted in commit 7.

**Recommendation.** No action. The cleanup is thorough.
