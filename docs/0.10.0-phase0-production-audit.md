## Design implications for the spike

1. **Spike chat selection**: ALL spike testing uses fake/throwaway chat IDs. No real production chats are touched.
2. **Latency baseline**: SDK pm averages 65s/turn on shumabit. tmux pm overhead budget: target ≤80s avg (≤23% overhead). G6 verification must measure this.
3. **Autosteer is load-bearing**: G8 must PASS for at least scenarios S1 + S2 + S5 (the common cases) before tmux backend ships to any chat that uses autosteer (5 of 6 active shumabit chats).
4. **Approval flow can defer**: G13 is FUTURE-protection, not current-traffic protection. Could mark G13 as DEFER if Phase 0 budget runs tight.
5. **Soak rollout order**:
   - Phase 4a: spike findings + Phase 1+2 land. Local shumorobot trials on Ivan's DM (clean baseline, error-tolerant).
   - Phase 4b: shumabit Ivan DM (68861949) once shumorobot is clean for 7d.
   - Phase 4c: one shumabit partner chat ONLY after Ivan DM clean for additional 3d, AND only with explicit `tmuxAttachConsent: true` per R2-F2.
   - **Umi-assistant: never by default.** Too little traffic to validate; partner-facing risk too high.
