## TL;DR

ChannelsProcess is implemented, contract-compliant, isolated-tested end-to-end via a fake bridge that speaks the real socket protocol. The Channels protocol shapes themselves were validated against pinned claude 2.1.142 in Phase 0 (interactive tmux run, three round-trips + clean compact). The remaining work to put a real polygram chat onto `driver=channels` is **daemon-side wiring** — the last-mile glue from polygram's existing message handler into ChannelsProcess. That's deploy-timing-sensitive and is deliberately deferred.

### Production code
- **`lib/process/channels-bridge.mjs`** (~246 LoC) — stdio MCP bridge. Claude spawns it as a child via inline `--mcp-config`. Capability declaration, `reply` tool, permission relay, socket handshake auth, tool_ack roundtrip, ping/pong watchdog, stdin-EOF exit, XML-escape on inbound content (prompt-injection defense).
- **`lib/process/channels-process.js`** (~600 LoC) — `Process` subclass. `start` creates a per-session unix socket (opaque random token, mode 0600, per-socket secret), spawns claude via `tmuxRunner.spawn` with the Phase-0-correct argv (`--strict-mcp-config --dangerously-load-development-channels server:polygram-bridge --session-id <uuid> --mcp-config <inline>`), polls past the trust + dev-channel confirmation dialogs, waits for bridge handshake. `send` tracks turns with quiet-window heuristic. `interrupt` sends tmux SIGINT. `kill` graceful teardown + socket cleanup. `respondToPermission` writes verdicts back to the bridge. chat_id mismatch on tool calls drops + logs + nacks.
- **`lib/process/factory.js`** — `'channels'` backend recognized via existing `pickBackend` precedence. Falls back to SDK with loud warning if required wiring (`tmuxRunner`, `botName`, `toolDispatcher`, `channelsClaudeBin`) is missing.
- **`lib/telegram/heartbeat-reactor.js`** (~220 LoC) — time-driven liveness reactor. ChannelsProcess-only by deployment (other drivers keep per-tool reactions). Subscribes to `Process` events (`thinking` → start ticking, `idle` → clear, `close` → permanent stop). STALL detector preserves rc.32 signal — 45s of no liveness → sticky `🥱`. Decoupled from bot client via `setReaction` callback.

## What's wired (post-2026-05-24 follow-up)

### ✅ 1. `polygram.js` factory wiring — DONE

Added two new options at `polygram.js:2219`:
- `toolDispatcher` — instance created via `createChannelsToolDispatcher({bot, send: tg, chunkText, deliverReplies, logger})`
- `channelsClaudeBin` — extracted from the existing `binCheck` (now hoisted to `pinnedClaudeBin` in outer scope so it can be reused)

Both fall back gracefully when not present: factory.js logs a loud warning and falls back to SDK if a chat configures `pm:'channels'` without wiring complete.

### ✅ 2. `toolDispatcher` implementation — DONE

`lib/process/channels-tool-dispatcher.js` (~115 LoC + 8 unit tests).
- Maps `{sessionKey, chatId, threadId, toolName, text, files}` → `chunkText` → `deliverReplies` → TG.
- Files: `.png/.jpg/etc` → `sendPhoto`, everything else → `sendDocument`. Partial-file-attach failures log but don't poison the overall result.
- Returns `{ok, error?}` per the ChannelsProcess contract.
- Refuses any tool name other than `reply` until the follow-on phase (Plan §Decision #10) decides on `react`/`edit_message`. *(Review F#21 — earlier drafts called this "Phase 1b"; the plan defines it as a "follow-on phase" with no shorthand. Standardizing on "follow-on phase".)*

### ✅ 3. Permission UI — DONE (zero new code in polygram.js)

`ChannelsProcess.emit('approval-required', ...)` now uses the **canonical TmuxProcess signature** (`{id, toolName, toolInput, sessionId, backend, respond}`). polygram.js's existing `sdkCallbacks.onApprovalRequired` handler at `polygram.js:2229` consumes channels emissions unchanged — same `canUseTool` flow, same admin-card UI, same sender-allowlist enforcement (via `lib/approvals/store.js`).

### ✅ 4. HeartbeatReactor wiring — DONE (`cf3448a`)

`polygram.js` `handleMessage` now instantiates `new HeartbeatReactor(...)` alongside the existing symbolic `reactor` (`polygram.js:1003`), gated on `pickBackend(...) === 'channels'`. `setReaction` is an inline closure over `tg(bot, 'setMessageReaction', ...)`. Stop in `finally` + autosteer-success path; idempotent so double-stop is safe.

Process binding uses `getOrSpawnForChat(sessionKey)` — idempotent with the inner call from `sendToProcess`, no double-spawn. The reactor binds to `thinking`/`idle`/`close` (process-agnostic) plus `bridge-disconnected` (channels-only, closes the visible gap between bridge crash and the kill-then-close pm-manager triggers).

Prerequisite landed in `47aa1c1`: `ChannelsProcess` now emits `idle` on `turn-timeout`, `resetSession`, and `interrupt`-grace-resolve paths. Without this, the reactor would have kept cycling forever on those rejection/synthetic-resolve flows because they don't take the `_resolveTurn` path.

### ✅ 5. Config schema — DONE

`config.example.json` `_comment_pm` entry documents the three valid values (`sdk`/`tmux`/`channels`), explains the precedence (topic > chat > bot), and notes channels research-preview status.

### ✅ 6. tmuxRunner generalization — DONE (`ee5238f`)

`ChannelsProcess._handleStartupDialogs` extracted to `lib/tmux/startup-gate.js` (`runStartupGate({runner, tmuxName, triggers, readySignal, deadlineMs, ...})`). Channels-specific triggers (dev-channels WARNING, trust prompt) and ready signal (`Listening for channel messages from: server:polygram-bridge`) are declared inline at the call site. 11 unit tests cover the gate independently.

## Known caveats

- **Pre-existing flaky tests.** Full `npm test` shows 7–8 tmux-process-related failures that pre-date this branch. All channels tests pass in isolation. The flakiness is concurrent-test-runner timing on TmuxProcess JSONL — orthogonal to channels work.
- **Misleading "no MCP server configured" banner.** Claude prints `server:polygram-bridge · no MCP server configured with that name` in the TUI even when the bridge is working perfectly. Documented in the plan's risk register.
- **`--dangerously-load-development-channels` permanent in spawn args.** Phase 3 rollout criterion is contingent on Anthropic allowlisting or providing a stable replacement. Kill-switch documented in the risk register.
- **`-p` mode incompatible with channel notifications.** Headless `claude -p` does not auto-trigger turns from channel events. Not a production concern (polygram always uses tmux) but documented to prevent future "let's run it headless for tests" surprises.
