# Upstream report (ready to file) — claude `--resume` startup death via MCP connect-timeout

> Draft for `anthropics/claude-code`. Content-free (timestamps + sessionIds
> only; no message content). Phase 2a of the 0.12.0 stable-release plan.

## Title
`--resume` startup intermittently killed at exactly +30s by the MCP connect-timeout, even after the connection succeeded (dev-channels)

## Summary
When launching `claude` with `--resume <id>` plus a dev-channels MCP server
(`--dangerously-load-development-channels server:<name>`), the session
intermittently dies at **exactly connect-start + 30s** — the declared MCP
connect timeout (`Starting connection with timeout of 30000ms`) — **even though
the MCP connection already completed in well under a second and the channel
registered healthy.** A fresh (non-`--resume`) spawn of the same config never
exhibits this.

## Environment
- claude Code CLI **2.1.158** and **2.1.173** (both affected).
- macOS (arm64), tmux-hosted TUI, `--permission-mode bypassPermissions`,
  `--strict-mcp-config`, a stdio MCP server declaring
  `experimental: { "claude/channel": {} }`.

## Evidence (from claude's own MCP debug logs)
`~/Library/Caches/claude-cli-nodejs/<cwd>/mcp-logs-<server>/*.jsonl` for every
observed death shows the same shape:

```
12:31:51.468  <bootSessionId>  Starting connection with timeout of 30000ms
12:31:52.161  <resumedSessionId>  Successfully connected (transport: stdio) in 695ms
12:31:52.180  <resumedSessionId>  Channel notifications registered
   … (healthy; channel delivers) …
12:32:21       <-- transport torn down here, connect-start + ~30.0s
```

Key observations:
1. The connection **succeeds in 300–700ms** and the channel **registers**.
2. The `sessionId` logged on "Starting connection" differs from the one on
   "Successfully connected" — `--resume` swaps the session id mid-connect.
3. The transport dies at **connect-start + 30s** regardless — i.e. the 30s
   connect-timeout timer fires against an already-established connection.
4. A 5th sample (2.1.173) shows a single sessionId throughout and still dies at
   +30s, so the visible id-swap isn't the discriminator — the resume flow
   races the connect timer internally regardless of how the log renders.

## Reproduction (intermittent; ~3–7 / 24h / session under normal use)
1. Complete at least one turn so a resumable session JSONL exists.
2. Relaunch with `--resume <id>` + the dev-channels MCP server, in a cwd whose
   session is non-trivial (the race widens as resume load time grows).
3. Observe: occasional exit at connect-start + 30s with a healthy connection in
   the MCP debug log. Fresh (`--session-id`) spawns of the same config: no death.

## Impact
The conversation is lost to a fresh-session fallback on each death (a daemon
wrapping claude must re-preload context). Frequency rises with how often
`--resume` is invoked.

## Suspected cause
The MCP connect-timeout timer is not cancelled (or is re-keyed incorrectly to
the pre-resume session) when `--resume` swaps the session id during connection
init, so it fires against a connection that already completed and tears down
the transport.

## Requested fix
Cancel/re-key the MCP connect-timeout when the connection completes (or when
`--resume` swaps the session id), so an already-established transport is never
torn down by a stale connect timer.

## Samples on file
5 deaths across 2.1.158 + 2.1.173 (2026-06-10 → 2026-06-12), all `--resume`,
all at +30s. Paired dead-vs-survivor MCP debug logs preserved locally
(e.g. `2026-06-10T12-31-50-…` dead vs `2026-06-10T12-32-23-…` survivor).
