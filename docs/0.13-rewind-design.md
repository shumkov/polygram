# 0.13 — Telegram `/rewind` — implementation design

**Status:** design, P0 spike PASSED (2026-06-09). Approach A (drive claude's native
Esc-Esc rewind via tmux + capture-pane) is validated end-to-end. One channels-specific
check (P0.5) remains before P2. Parent: `docs/0.13-rewind-spec.md`.

---

## P0 spike result (2026-06-09) — PASS

Drove the **real** claude rewind menu (Opus 4.8, pinned CLI) in a tmux pane via
`send-keys` + `capture-pane`, with 3 codeword checkpoints (APPLE/BANANA/CHERRY).
Rewound to "before BANANA", then asked what codewords claude remembered → **"APPLE"**
only. BANANA + CHERRY were genuinely dropped from context. Every step was readable and
verifiable from capture-pane. Findings that drive the design:

- **Menu lists each checkpoint by its full prompt text** — match the target by text, not
  by counting. e.g. `❯ Remember the codeword BANANA…`.
- **`❯` cursor position is readable every step** → close the loop (verify before Enter).
- **Confirm screen** shows the exact target + a relative timestamp (`(2m ago)`) + "The
  conversation will be **forked**. The code will be unchanged." → final verification gate.
- **Restore is non-destructive (fork)** and **pre-fills the rewound prompt** into the input.
- **Gotchas:** (1) the prompt must be EMPTY before `Esc Esc` (a non-empty prompt → the
  first `Esc Esc` just clears the text). (2) A typed submit (`Enter`) sometimes does **not
  register on the first try** — observed twice; must capture-verify the submit and re-send
  `Enter` if the text is still in the input box.

## The drive sequence (validated)

```
1. Ensure idle + empty prompt:   send C-u (clear), then capture → prompt line empty
2. Open menu:                    send Escape Escape ; capture → "Rewind / Restore … before…"
3. Read menu:                    capture-pane → list of rows (each = a checkpoint's prompt text)
4. Match target row:             find the row whose text == M's text (operator replied to M,
                                 so we have its exact text); compute Up-count from "(current)"
5. Navigate (verified):          for each Up: send Up ; capture ; assert ❯ moved one row
                                 → stop when ❯ is on M's row
6. Select:                       send Enter ; capture → confirm screen shows M + "forked"
7. Verify + confirm:             assert the confirm screen's quoted message == M ;
                                 ensure ❯ on "1. Restore conversation" ; send Enter
8. Settle:                       capture → transcript now ends before M ; clear the
                                 pre-filled prompt (C-u)
   ABORT path at any mismatch:   send Escape (Never mind) and alert the operator.
```

## polygram integration

| Concern | Design |
|---|---|
| Trigger | `dispatchRegularMessage`: inbound reply-to `M` with text `/rewind`, **admin/paired-operator only**. Record `{sessionKey, target: {msg_id, text, ts}}`. Distinct from the question free-text path. |
| Defer to turn-end | enqueue; fire on the session's next `stop-hook`/turn-resolved (the signal the question keep-alive already consumes). Never drive the menu mid-turn. A per-session lock prevents a racing new turn. |
| Find the pane | the channel session runs claude in a known tmux target (the cli-process owns it). Reuse the existing pane-control path (the rc.45 esc-to-interrupt already send-keys to this pane). |
| Drive | the validated sequence above, **capture-verified at every step**, with the two gotchas handled (clear-first, Enter-retry). |
| Confirm to operator | "⏪ Rewound to: «first line of M» — N messages dropped." If the menu couldn't be matched/driven, "couldn't rewind — <reason>" (never a silent or wrong rewind). |
| TG cleanup (default) | delete the bot's messages after `M` by default (operator decision); the operator's own only if the bot is group admin, else they remain. |
| Session bookkeeping | claude forks internally; if it issues a new session id, capture it (Stop hook / pane) and update polygram's `sessionKey → claude_session_id` mapping so the next `--resume` targets the fork. **(P0.5 confirms whether/where the new id surfaces.)** |

## P0.5 result (2026-06-09) — **FAILED. Approach A is dead on channels.**

Ran the rewind drive in a **real ChannelsBridgeServer + claude session**
(`scripts/spikes/rewind-channels-spike.js`): delivered 3 codeword messages *through the
bridge* (replies `OK1/OK2/OK3` confirm they processed), then opened the rewind menu on the
session pane. Result:

```
  Rewind
  Nothing to rewind to yet.
```

**Bridge/MCP-delivered messages do not create rewind checkpoints.** claude's checkpoints
are tied to *typed prompt submissions* in the TUI; the channels backend never types — it
delivers user turns as MCP `<channel>` notifications — so no checkpoints exist and the
native rewind has nothing to act on. The P0 standalone spike passed only because it typed.
**Approach A is not viable on the channels backend.**

## Revised approach: B (transcript fork) — **safe variant** (post-P0.5)

A's death forces B (cut the conversation transcript) — but the earlier "corruption" veto
assumed *in-place* editing of the original. Do it **backup-first / copy-only** and the
irrecoverable case disappears:

1. **Never touch the live transcript.** Copy the session JSONL aside (original preserved,
   auditable).
2. Build the rewound conversation as a **new session file**: the prefix up to the clean turn
   boundary before `M` (located deterministically via the `<channel msg_id="M">` wrapper the
   transcript already carries — verified present when reading the real channels transcripts).
3. **Format-sanity check** the prefix (valid JSON lines, no dangling `tool_use`, recognised
   entry shapes). If anything is unrecognised → **fail safe**: no-op, keep the original,
   alert the operator. A CLI-format change degrades to "rewind unavailable", never corruption.
4. `pm.kill(sessionKey)` → resume the **new** session id; update `sessionKey → claude_session_id`.
5. Worst case (a bad fork that won't resume): the original is intact → restore it → the
   rewind simply "didn't happen". Recoverable by construction.

So the net of both spikes: native rewind is the *safe* mechanism but **doesn't exist for
channels**; transcript-fork is the *only* mechanism for channels and is made acceptably safe
by copy-only + sanity-check + fail-safe. This is a genuine risk increase over A — flagged for
the operator + the reviewers. (SDK backend remains out of scope: no on-disk JSONL.)

**Still to validate (P0.6, before P2):** that resuming a hand-built prefix JSONL actually
yields a clean rewound conversation on the pinned CLI (the spike proved the *menu* path, not
the *fork-file* path). If P0.6 also fails, `/rewind` is not feasible on channels without
upstream support — shelve and revisit.

## Limitations (carry from the spec — state to the operator)

- **`/rewind` reverts the conversation, NOT real-world actions.** Forked-away Drive files,
  Sheets, sent emails, external API calls persist. Offer (P4) an end-of-rewind "want me to
  reverse anything I did since then?" prompt; don't imply undo.
- **Granularity = claude prompt.** Autosteer can fold several TG messages into one prompt →
  one checkpoint; a rewind lands at that prompt boundary. Confirm the landing point back.
- **TG deletion asymmetry** — bot's own messages always; the operator's only if admin.
- **Backend** — channels/cli only (needs the TUI). SDK out of scope.

## Phases (revised post-P0.5 → Approach B-safe)

- **P0** ✅ — native Esc-Esc rewind is drivable + actually rewinds (standalone *typed* TUI).
- **P0.5** ✅ (negative) — bridge-delivered messages are NOT checkpointed → **A dead on
  channels.** Pivot to B-safe.
- **P0.6 — GATES the feature.** Prove that a copy-only, hand-built prefix JSONL (cut at the
  `<channel msg_id>` boundary) **resumes as a clean rewound conversation** on the pinned CLI
  (codeword test: claude remembers only pre-target turns). **No feature code until P0.6 passes.**
  If it fails, `/rewind` on channels is shelved pending upstream support.
- **P1** — `/rewind` detection + admin gate + turn-end deferral + operator confirmation msg.
- **P2** — the B-safe core: copy transcript → locate cut via `msg_id` → sanity-check → write
  new session file → fail-safe on any anomaly → kill+resume the fork → update the id mapping.
- **P3** — TG message cleanup (bot's own by default; operator's if admin).
- **P4** — UX: target preview, landing-point confirmation, optional side-effect-reversal prompt.

## Test plan

- Unit: transcript parser (JSONL → turns), `msg_id`→cut-point locator, prefix builder + the
  **format-sanity / fail-safe** gate (must reject malformed/unrecognised input and no-op).
- Unit: `/rewind` trigger detection + admin gate + turn-end deferral queue.
- Integration (gated, real claude like the existing E2Es): build a forked prefix from a real
  channels transcript with N codeword turns, resume it, assert claude's memory == only the
  pre-target turns (P0.6, automated). Plus a corruption-injection test → asserts fail-safe
  (original restored, no rewind, operator alerted), never a broken session.
