# 0.13 — Telegram `/rewind` — implementation design

**Status:** design. P0 spike PASSED for a TYPED CLI (2026-06-09); **P0.5 spike FAILED**
(2026-06-09) — channels messages aren't checkpointed, so native rewind (Approach A) is dead
on the channels backend. Pivoted to Approach **B-safe** (transcript fork), **gated on a P0.6
spike** before any feature code. Parent: `docs/0.13-rewind-spec.md`.

---

## P0 spike result (2026-06-09) — PASS

Drove the **real** claude rewind menu (Opus 4.8, pinned CLI) in a tmux pane via
`send-keys` + `capture-pane`, with 3 codeword checkpoints (APPLE/BANANA/CHERRY).
Rewound to "before BANANA", then asked what codewords claude remembered → **"APPLE"**
only. BANANA + CHERRY were genuinely dropped from context. Every step was readable and
verifiable from capture-pane. Findings that drive the design:

- **Menu lists each checkpoint by its full prompt text** — match the target by text, not
  by counting. e.g. `❯ Remember the codeword BANANA…`.
- **`❯` cursor position is readable every step** → close the loop (verify before Enter).
- **Confirm screen** shows the exact target + a relative timestamp (`(2m ago)`) + "The
  conversation will be **forked**. The code will be unchanged." → final verification gate.
- **Restore is non-destructive (fork)** and **pre-fills the rewound prompt** into the input.
- **Gotchas:** (1) the prompt must be EMPTY before `Esc Esc` (a non-empty prompt → the
  first `Esc Esc` just clears the text). (2) A typed submit (`Enter`) sometimes does **not
  register on the first try** — observed twice; must capture-verify the submit and re-send
  `Enter` if the text is still in the input box.

## The drive sequence (validated)

> **⚠️ SUPERSEDED — Approach A only (typed TUI). NOT applicable to channels** (P0.5: bridge
> messages aren't checkpointed). Retained as spike evidence. The live design is **B-safe**
> (see "Revised approach" above), not this menu drive.

```
1. Ensure idle + empty prompt:   send C-u (clear), then capture → prompt line empty
2. Open menu:                    send Escape Escape ; capture → "Rewind / Restore … before…"
3. Read menu:                    capture-pane → list of rows (each = a checkpoint's prompt text)
4. Match target row:             find the row whose text == M's text (operator replied to M,
                                 so we have its exact text); compute Up-count from "(current)"
5. Navigate (verified):          for each Up: send Up ; capture ; assert ❯ moved one row
                                 → stop when ❯ is on M's row
6. Select:                       send Enter ; capture → confirm screen shows M + "forked"
7. Verify + confirm:             assert the confirm screen's quoted message == M ;
                                 ensure ❯ on "1. Restore conversation" ; send Enter
8. Settle:                       capture → transcript now ends before M ; clear the
                                 pre-filled prompt (C-u)
   ABORT path at any mismatch:   send Escape (Never mind) and alert the operator.
```

> **Security model (P1 — security review; resolve before P1 build).** `/rewind` is a
> destructive op (forks+kills a session, deletes messages), so the gate must be hardened:
> - **Operator = a concrete, nameable identity** — NOT just "paired". `pairings.hasLivePairing`
>   is true for ANY paired user, so a second paired group member could rewind/kill the
>   operator's session. Pin operator to `config.bot.adminChatId` (or an explicit
>   `operatorUserId`) and hard-check it.
> - **Ownership of `M`** — verify `msg.reply_to_message.from.id` is the operator (or a bot
>   bubble from the operator's own prior request). Without this, any allowed user can rewind
>   to *any* message in the chat (incl. another user's).
> - **Transcript copy hygiene** — the JSONL holds full business conversation content. Write the
>   copy + the fork file in `~/.claude/projects/<cwd-mangled>/` (same dir as the original), mode
>   **`0o600`**, and **unlink in all exit paths** (success and failure). No `/tmp` world-readable
>   staging.
> - **Deletion snapshot + bound** — snapshot the message-id set to delete **at enqueue time**
>   (not at turn-end), log it before deleting, and consider an age/recency bound on `M` so a
>   stale target can't wipe the whole chat history.

| Concern | Design |
|---|---|
| Trigger | `dispatchRegularMessage`: inbound reply-to `M` with text `/rewind`, gated to the **operator identity** (see Security model) AND the replied-to `M` owned by the operator. Record `{sessionKey, target: {msg_id, text, ts}, deleteIds: [...snapshot...]}`. Distinct from the question free-text path. |
| Defer to turn-end | enqueue; fire on the session's next `stop-hook`/turn-resolved. Never mid-turn. The per-session lock must span the **entire** kill → write-fork → spawn → id-update sequence (not just the deferral check), and queue inbound messages until the new id is registered — else a message arriving in the kill window spawns a third session on the stale id. |
| Confirm to operator | "⏪ Rewound to: «first line of M» — N messages dropped. **Note: any files/emails/Sheets I already created still exist** — say the word to reverse them." (the side-effect caveat is inline by default, not a P4 optional — product review). If the rewind couldn't be done safely, "couldn't rewind — <reason>" (never a silent or wrong rewind). |
| TG cleanup (default) | delete the bot's messages after `M` by default (operator decision); the operator's own only if the bot is group admin, else they remain. |
| Session bookkeeping | claude forks internally; if it issues a new session id, capture it (Stop hook / pane) and update polygram's `sessionKey → claude_session_id` mapping so the next `--resume` targets the fork. **(P0.5 confirms whether/where the new id surfaces.)** |

## P0.5 result (2026-06-09) — **FAILED. Approach A is dead on channels.**

Ran the rewind drive in a **real ChannelsBridgeServer + claude session**
(`scripts/spikes/rewind-channels-spike.js`): delivered 3 codeword messages *through the
bridge* (replies `OK1/OK2/OK3` confirm they processed), then opened the rewind menu on the
session pane. Result:

```
  Rewind
  Nothing to rewind to yet.
```

**Bridge/MCP-delivered messages do not create rewind checkpoints.** claude's checkpoints
are tied to *typed prompt submissions* in the TUI; the channels backend never types — it
delivers user turns as MCP `<channel>` notifications — so no checkpoints exist and the
native rewind has nothing to act on. The P0 standalone spike passed only because it typed.
**Approach A is not viable on the channels backend.**

## Revised approach: B (transcript fork) — **safe variant** (post-P0.5)

A's death forces B (cut the conversation transcript) — but the earlier "corruption" veto
assumed *in-place* editing of the original. Do it **backup-first / copy-only** and the
irrecoverable case disappears:

1. **Never touch the live transcript.** Copy the session JSONL aside (original preserved).
2. Build the rewound conversation as a **new session file** — and this is more than a prefix
   cut (feasibility + adversarial review, code-verified):
   - **Locate** the cut at the `<channel msg_id="M">` wrapper (present in real channels
     transcripts), at a clean **turn boundary** — never mid-`message.id` (one assistant turn
     spans multiple JSONL lines sharing `message.id`).
   - **Rewrite the internal `sessionId` on EVERY line** to the new fork id, and write the file
     to the exact resume path `~/.claude/projects/<cwd '/'→'-'>/<newId>.jsonl`. If the file
     isn't at that path with a matching internal id, the ghost-session guard **silently drops
     the id and starts fresh** → the "rewind" becomes a *total context wipe*. This is the core
     write-contract and was unstated.
   - **Reconcile the `parentUuid` linked-list chain** + any surviving `leafUuid` / `toolUseID`
     references so the prefix's head is coherent and nothing references a removed `uuid`.
3. **Format-sanity check** the prefix — not just "valid JSON / no dangling tool_use", but the
   full observed entry-type set (`user`/`assistant`/`system`/`mode`/`permission-mode`/
   `queue-operation`/`attachment`/`last-prompt`), `parentUuid` chain continuity to the cut,
   and **no surviving ref to a removed uuid**. Unrecognised → **fail safe**: no-op, keep the
   original, alert the operator.
4. `pm.kill(sessionKey)` → resume the **new** session id; update `sessionKey → claude_session_id`.
5. **The safety story, corrected (adversarial review).** Copy-only protects the *original*
   file — but the dangerous failure is NOT "won't resume" (loud, recoverable). It is a fork
   that **resumes with subtly-wrong context** (severed chain, baked-in summary, orphaned
   tool_use) — silent, and the operator believes it worked. So "recoverable by construction"
   only holds for loud failures. To cover the silent case, P2 must **verify the rewound state
   is coherent after resume** (not just that it resumed) and treat anything off as a fail-safe
   restore. This is a genuine residual risk, not a fully-closed one.

**Auto-compaction (adversarial, code-verified — `PreCompact`/`PostCompact` are handled in the
codebase).** claude auto-compacts long sessions: turns before the boundary collapse into a
summary entry. A target `M` older than the last compaction is then **un-locatable** (the
`<channel msg_id>` is gone) or yields a prefix whose summary baked in turns meant to be
dropped. The cut MUST detect a compacted transcript and either refuse (fail-safe) or handle
the summary explicitly — the naive turn-cut is unsafe across a compaction boundary.

So the net: native rewind is the *safe* mechanism but **doesn't exist for channels**;
transcript-fork is the *only* channels mechanism and is **materially riskier and more
specified-dependent than first framed** — copy-only bounds the original-file loss but not the
silent-wrong-fork case. SDK backend out of scope (no on-disk JSONL).

**P0.6 — GATES the feature, hardened scope (adversarial).** Prove a hand-built prefix resumes
as a *correct* rewound conversation on the pinned CLI across the real failure surface, not the
happy path: a transcript containing **tool_use/tool_result pairs, an `isSidechain` subagent
run, autosteer-folded follow-ups, AND a post-auto-compact prefix** — and assert the resumed
session can **complete a fresh tool-using turn** (not just recall a codeword). Also evaluate
the documented **`--fork-session`** flag as a first leg (can claude mint the fork file so we
trim a CLI-produced base instead of hand-writing the whole format?). If P0.6 fails, `/rewind`
on channels is shelved pending upstream support.

## Limitations (carry from the spec — state to the operator)

- **`/rewind` reverts the conversation, NOT real-world actions.** Forked-away Drive files,
  Sheets, sent emails, external API calls persist. Offer (P4) an end-of-rewind "want me to
  reverse anything I did since then?" prompt; don't imply undo.
- **Granularity = claude prompt.** Autosteer can fold several TG messages into one prompt →
  one checkpoint; a rewind lands at that prompt boundary. Confirm the landing point back.
- **TG deletion asymmetry** — bot's own messages always; the operator's only if admin.
- **Backend** — channels/cli only (needs the TUI). SDK out of scope.

## Phases (revised post-P0.5 → Approach B-safe)

- **P0** ✅ — native Esc-Esc rewind is drivable + actually rewinds (standalone *typed* TUI).
- **P0.5** ✅ (negative) — bridge-delivered messages are NOT checkpointed → **A dead on
  channels.** Pivot to B-safe.
- **P0.6 ✅ PASS** (2026-06-09, `scripts/spikes/rewind-p06-spike.js`). Real channels session →
  copy-only fork → resume → verified: remembers the kept turns INCLUDING a kept tool_use
  output, does NOT know the dropped turns, AND completes a fresh Bash turn. Confirmed: the
  transcript has 8 entry types and `sessionId` on every line (45/45); **rewriting `sessionId`
  per line + writing to the projects dir is necessary and sufficient**; a
  clean prefix cut needs **no explicit `parentUuid` reconciliation** (prefix is self-consistent).
  ⚠️ The spike used a *realpath'd* cwd everywhere so its fork-path and resume-path agreed by
  construction; in production the resume check (`cli-process.js`) mangles the **raw** cwd, so the
  executor must do the same or they silently diverge — see Finding A in the post-review below.
  **Residual (handle in P2): auto-compaction** — not triggered in the spike (short session);
  a cut whose target predates a summary entry must be detected and refused (fail-safe), not
  attempted. `--fork-session` not needed — the hand-write works. B-safe is feasible; proceed.

**P1–P4 are CONTINGENT on P0.6 passing** (scope review — don't pre-invest the whole pipeline

- **P1** — `/rewind` detection + the **operator-identity gate + M-ownership check** (Security

- **P4** — UX: target preview, landing-point confirmation, "N messages removed". (Side-effect

## Open Questions (ce-doc-review, 2026-06-09 — judgment-level, for the build/skip decision)

These need an operator/product call before committing to the B-safe build; the fixes above
already folded in the mechanical/security findings.

1. **Does conversation-only rewind even solve the motivating problem?** (product-lens, P1) The
   origin was a misdirected "Yes" that already created Drive artifacts. `/rewind` leaves those
   artifacts and makes claude *forget* it made them — arguably worse for cleanup than doing
   nothing (claude can no longer "delete that folder you just made"). Is `/rewind` the right
   tool for that incident class, or should the real feature be **side-effect reversal**? If we
   build `/rewind` anyway, state explicitly that it's for the no-side-effect case.
2. **Cheaper alternative not evaluated** (product-lens, P2). A "re-decide from here" flow —
   claude keeps history but is instructed to treat M onward as retracted and offers to reverse
   its actions — needs **no transcript surgery and no internals risk**, and addresses the
   side-effect harm conversation-rewind can't. Justify full context-eviction over this 80%/20% path.
3. **Maintenance liability** (product-lens + feasibility, P2). B-safe is a standing commitment
   to reverse-engineer claude's *undocumented, version-moving* transcript format (already moved
   2.1.142→2.1.158). Pin the format to the validated CLI version and **re-run P0.6 + the
   corruption test on every claude bump** before re-enabling `/rewind`. Weigh this compounding
   cost in the build/skip decision.
4. **`--fork-session` vs hand-write** (feasibility, P2). The documented `--fork-session` flag
   may let claude mint the fork file so we only trim a CLI-produced base instead of hand-writing
   the whole format. First leg of P0.6.
5. **Granularity under autosteer** (adversarial, P1). Folded follow-ups are delivered as
   separate `injectUserMessage` user_msgs — do they land as distinct `msg_id` entries (clean
   cut) or merge into one logical turn (mid-turn split risk)? Resolve in P0.6; it determines
   whether targeting an individual message is even well-defined.

## Post-implementation review (2026-06-09) — code-reviewer + silent-failure-hunter

Two reviewers ran on the committed P1–P4 (`65d0fe4` + `c2fe8ca`). The copy-only invariant on
the *original* transcript held, and the gate / cut-location / dangling-tool detection /
id-swap-spread / lazy-resume model were confirmed correct. Six findings were fixed (TDD
red→green, +9 tests); each violated the load-bearing invariant *"never a silent or wrong
rewind."* All verified against real channels transcripts on disk, not just synthetic fixtures.

- **A — realpath divergence = silent context wipe** (`execute.js`). `transcriptPathFor`
  realpath'd the cwd; `cli-process.js` resume-check mangles the **raw** cwd. On any symlinked
  cwd the fork is written where claude keeps it but resume looks elsewhere → fresh empty
  session. Fix: mangle the raw cwd (lockstep with the resume check); a symlinked cwd now fails
  clean at the read step. *Test: `transcriptPathFor` uses the raw symlink path, not its target.*
- **B — `<reply_to msg_id="X">` false-match = silent WRONG cut** (`fork.js`). The cut locator
  matched a bare `msg_id="X"` substring, which also appears in a `<reply_to msg_id="X">` block
  echoed inside a *later* turn's body (confirmed present in real transcripts). When the genuine
  target was compacted away, the locator false-matched the reply turn and cut at the wrong
  point, reporting success. Fix: anchor to the channel envelope (`<channel[^>]*\bmsg_id="X"`) —
  the only unescaped `<channel` in the parsed content. *Test: compacted-away target whose id is
  echoed in a later reply → not-found fail-safe.*
- **C — non-atomic write = truncated fork** (`fork.js`). A direct write to the live resume path
  could leave a half-written `<id>.jsonl` that resumes partial/empty context. Fix: write a
  temp dotfile sibling then `rename` into place. *Test: write targets a temp path then renames;
  an interrupted write leaves nothing at the resume path.*
- **D — deferred rewind silently lost on proc death** (`rewind.js`). The defer parked on
  `proc.once('idle')`, but a killed/evicted/disconnected proc emits `'close'`/`'session-reset'`,
  never `'idle'` — so a queued rewind never ran and the operator (already told "queued") never
  heard back. Fix: settle on idle (run) OR close/session-reset (tell the operator to retry),
  with a deadline backstop, single-fire. *Tests: close + session-reset surface a failure; idle
  still runs exactly once even if close follows.*
- **E — `pm.kill` failure reported as clean success** (`execute.js`). A kill throw left the DB
  pointing at the fork while the old proc may survive on the old id (two-transcript split), yet
  returned `ok:true`. Fix: surface a `warning` (logged + shown in the confirmation). *Test:
  throwing kill → `ok:true` with a warning.*
- **I — dispatch fall-through on throw** (`polygram.js`). A recognized `/rewind` that threw in
  `tryConsume` fell through to normal dispatch → sent `/rewind` to claude as a prompt. Fix:
  `return` after logging (the command is already recognized, so consume it).

**Considered, not changed (with reasoning):**
- *Delete-id snapshot at enqueue* (design §P3) — deleting the bot's own outbound messages after
  M *during* the defer window is correct, not over-deletion: those messages are post-M and are
  exactly what the rewind discards. The fork (cut at M) and the cleanup (delete after M) stay
  self-consistent. Scope is already `direction='out' AND status='sent' AND` thread.
- *Stale proc at enqueue* — `schedule()` attaches its lifecycle listeners synchronously to the
  proc read from `pm.get` (no await between), and `executeRewind` re-reads the session from the
  DB at run time, so the proc reference can't go stale across an await. The D fix covers the
  death case.

**Gate policy — RESOLVED (operator decision, 2026-06-09).** The earlier gate degraded to *any
paired user* when `operatorUserId` was unset (configured nowhere), so on a multi-paired group bot
a second paired member could rewind the operator's session. New three-part gate (`gateRewindRequest`,
caller computes the inputs in `polygram.js`):

1. **Rewind-safe chat only.** `/rewind` is refused in any chat that is neither a DM nor an
   `isolateTopics` group. A shared (non-isolated) group runs ONE session across all topics, so a
   rewind there would blast every topic/user — disallowed outright.
2. **Operator/admin by default.** The operator is `config.bot.operatorUserId` if set, else the
   admin user derived from `config.bot.adminChatId` (a private adminChatId equals that user's
   Telegram id; a group adminChatId can't match a sender id → default-deny). No more "any paired
   user" as the implicit default.
3. **Opt-in widening.** A single per-chat setting `rewindAccess: 'operator' (default) | 'paired'`.
   `'paired'` additionally lets any *paired* member of that chat rewind; the operator/admin is
   always allowed regardless. Ownership (own message or bot bubble, never another user's) still applies.

Tests: `gateRewindRequest` covers the isolation refusal, operator-only default (rejects a paired
non-operator), paired-mode widening, paired-mode still rejecting the unpaired, and operator-always-allowed.
