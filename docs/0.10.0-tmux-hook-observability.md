# 0.10.0 — tmux backend: hook-based turn observability

> **Status: DESIGN PROPOSAL.** Supersedes the "progress-aware W1"
> timeout-tuning thread. Reframes the problem from *"how long do we
> wait before giving up"* to *"know exactly what the agent is doing,
> and show it."*
>
> Companion to `0.10.0-tmux-patience-model.md` /
> `-solution.md` (the predicate) and `0.10.0-tmux-status.md`
> (shipped state).

## The real problem (Ivan, 2026-05-21)

> "we need to monitor everything what is happening inside (agents
> running, etc). we also can use hook to figure out if step is
> actually completed. … now in SDK we see proper reacting for agents,
> coding, etc. here we see only scary emotions where it takes too
> long. I think we need to design system with proper understanding
> what is happening and properly show it to user instead of scaring
> him."

The tmux backend is **blind to in-turn activity**. It scrapes
capture-pane and tails the main JSONL. During a subagent (`Task`/
`Agent` tool) the main session emits the `Agent` tool_use **once**,
then is silent for minutes while the subagent works in its own
sidechain. So:

- The **reactor** gets one `setState('TOOL')` → 🔥, then nothing →
  auto-escalates 🥱 (STALL, 45 s) → 😨 (TIMEOUT) → 🤯. The only
  feedback the user gets on a long, healthy turn is *escalating
  fear*.
- The **turn deadline** (W1) can't tell "progressing" from "wedged",
  so it killed a legitimate 49-minute SoundCloud-re-likes subagent at
  the 30-minute wall-clock (2026-05-21 12:16, msg 884) — the subagent
  was demonstrably alive (sidechain + debug-log writing until 12:35).

The SDK backend doesn't have this problem: the SDK streams typed
events (tool use, thinking, subagent activity) from *inside* the run,
so polygram's reactor stays meaningful. **The tmux backend needs the
same fidelity from the outside.**

## The keystone: Claude Code hooks

claude 2.1.142 fires **hooks** — a reliable push channel claude emits
itself. Verified against the 2.1.143 binary (hook surface identical;
field names confirmed by direct binary scan + official docs):

- **`PreToolUse` / `PostToolUse` / `PostToolUseFailure`** fire for
  every tool — **including tools executed inside a subagent.** Payload
  carries `tool_name`, `tool_input`, `tool_use_id`, `tool_response`/
  `error`, plus `session_id`, `transcript_path`, `cwd`. Subagent-
  context events additionally carry **`agent_id`**, **`agent_type`**,
  and **`parent_tool_use_id`** (the Task call that spawned them).
- **`SubagentStart` / `SubagentStop`** bracket each subagent (carry
  `agent_type`).
- **`Stop`** fires when the main agent finishes responding
  (`stop_hook_active` guards loops) — an **authoritative** turn-done
  signal, stronger than capture-pane quiescence.
- **`Notification`** fires on permission prompts / idle.
- **`UserPromptSubmit`** fires when a prompt is submitted (an
  authoritative submit-confirm — stronger than the JSONL
  `user-message` token round-trip B7 relies on).
- Hooks fire on the **full event set in interactive TUI** (print mode
  `-p` is the restricted one — we use the TUI, the favorable case).

### Injection without touching user config

`claude --settings <file-or-json>` layers a settings object on top of
whatever `--setting-sources` loaded, **independent of**
`--strict-mcp-config` (MCP-only) and `--setting-sources project,local`
— both of which polygram already passes for `isolateUserConfig`. So
polygram ships its own `polygram-hooks.json` and adds
`--settings <path>` to the spawn args. Zero user-config pollution.

### Transport: append-to-ndjson, tail it

Each hook is an `async` command that appends its stdin JSON (one
compacted line) to a per-session ndjson file. polygram tails that file
with the existing `LogTail` (same machinery as the JSONL/debug-log
tails). **`async: true` + `timeout: 5`** means a hook can NEVER slow
or stall the agent (the single most important safety property; the
short timeout is the backstop in case `async` is silently ignored on
2.1.142).

```
spawn:  claude … --settings ~/.polygram/<bot>/hooks/<sid>.settings.json
hook:   <event JSON on stdin> → append one line → ~/.polygram/<bot>/hooks/<sid>.ndjson
tail:   LogTail(<sid>.ndjson) → _handleHookEvent(ev)
```

(Hook command portability: `jq -c` if present, else a node/python
one-liner — decided in impl. The host already runs node.)

## What the hook stream gives us — three signals, one channel

### 1. Progress (retires the W1 guessing game)

Every `PreToolUse`/`PostToolUse` — **including inside subagents** — is
an unambiguous "the turn is doing work" heartbeat. This is exactly the
signal the patience-model predicate wanted but had to *infer* from
capture-pane + debug-log + sidechain scraping (which the 2026-05-21
data showed gapping up to 233 s on a throttled turn).

With hooks, "is the turn progressing?" is no longer inferred:
- Heartbeat `turn.lastActivityAt` on every hook event.
- The turn is **wedged** only if NO hook event arrives for
  `idleCeilingMs` (a genuinely silent agent — no tool starting, none
  finishing, no subagent activity). A modest ceiling (e.g. 5 min) is
  safe because a working agent fires hooks continuously; a
  rate-limited SoundCloud re-like still fires PostToolUse per mutation.
- The W1 absolute wall-clock killer is **removed for progressing
  turns**. A large hard backstop (hours) remains only against a
  pathological infinite tool loop.

### 2. Status (replaces fear with understanding)

The hook stream names exactly what's happening, so the reactor — and
optionally a richer Telegram status line — can reflect it:

| Hook | Reactor / status |
|---|---|
| `PreToolUse {tool_name:'Bash'}` | CODING 👨‍💻 (or a labelled "Running Bash…") |
| `PreToolUse {tool_name:'WebFetch'}` | WEB ⚡ |
| `SubagentStart {agent_type:'music-curator'}` | a subagent state — e.g. 🤖 "music-curator running" |
| `PreToolUse {agent_id:…, tool_name:'Bash'}` | "music-curator → Bash" (subagent's inner tool) |
| `SubagentStop` | subagent done; back to main-agent state |
| `Stop` | DONE 👍 |

The reactor's `classifyToolName` already maps tool names to states;
hooks just feed it **continuously and from inside subagents**, so it
never goes silent → never auto-escalates to 🥱/😨 on a healthy turn.
The scary states become what they should be: reserved for genuine
silence.

(Stretch: a real status *message* — not just a reaction emoji —
mirroring the SDK's richer feedback. Out of scope for the first cut;
the reaction upgrade is the high-leverage win.)

### 3. Completion (an authoritative turn-done)

`Stop` is claude saying "I'm done responding" — far stronger than
capture-pane quiescence + the §6/lateGrace dance. With a reliable
`Stop`:
- The `quiesced` settle outcome (capture-pane idle) can be
  **demoted to a fallback** behind the `Stop` hook.
- §6 (`TMUX_NO_JSONL_TEXT`) and the lateGrace window shrink toward
  vestigial — `Stop` + the JSONL `result` are the real terminal
  signals.
- `UserPromptSubmit` is an authoritative submit-confirm — a candidate
  to simplify B7 (`_scheduleSubmitRetries`) further.

## How this lands on the existing predicate

The hook stream doesn't replace the `TurnPhase` predicate — it
becomes its **best input**, displacing the inferred ones:

| Predicate need | Today (inferred) | With hooks (authoritative) |
|---|---|---|
| submit confirmed | JSONL `user-message` token round-trip | `UserPromptSubmit` |
| tool running | JSONL `tool-use` (main only) | `PreToolUse` (main + subagent) |
| tool done | JSONL `tool-result` | `PostToolUse` |
| subagent running | `Agent` tool_use w/o result | `SubagentStart`/`Stop` + inner Pre/Post |
| progressing | capture `esc to interrupt` + debug-log growth | any hook event |
| turn done | JSONL `result` / capture quiesce / §6 | `Stop` |

`outstandingTools` / `outstandingSubagents` (already on the turn)
populate from `PreToolUse`/`SubagentStart` and drain on
`PostToolUse`/`SubagentStop`, keyed by `tool_use_id`/`agent_id` — more
reliable than the JSONL-derived sets.

## Phased plan (proposed)

Each phase independently shippable + soakable, lowest-risk first.

- **H1 — emit + observe (no behaviour change).** Inject
  `--settings <hooks>.json` at spawn; write the per-session ndjson;
  tail it; parse into typed hook events; emit a `hook-event` for
  observability and persist to the events DB. Verify on a real Music
  subagent turn that we see `SubagentStart` → inner `PreToolUse`/
  `PostToolUse` ×N → `SubagentStop` → `Stop`. **Nothing consumes the
  events yet.** (Mirrors the predicate's "observer-only" Commit 1.)
- **H2 — feed the reactor.** Route hook events to the reactor
  `setState` (incl. subagent context). The 🥱/😨 escalation now only
  fires on genuine hook silence. User sees meaningful status on long
  turns.
- **H3 — feed the predicate's progress + deadline.** Heartbeat on
  every hook event; make the idle ceiling key on hook silence; remove
  the W1 wall-clock killer for progressing turns (large hard backstop
  remains). This is the structural fix for the 49-min-turn kill.
- **H4 — authoritative completion.** Adopt `Stop` as the primary
  terminal signal; demote capture-pane quiescence + §6 to fallback;
  consider `UserPromptSubmit` for submit-confirm.

H1+H2 deliver the user-visible win (no more fear on healthy turns).
H3 retires the timeout problem. H4 simplifies the settle path.

## Open questions / risks

1. **`async` on 2.1.142.** Unconfirmed the `async` keyword is honored
   on the pinned version; `timeout: 5` is the backstop. **Must verify
   in an H1 spike** that hooks don't add latency to tool calls.
2. **ndjson location + writability.** Per-session path under
   `~/.polygram/<bot>/hooks/`. Confirm `$CLAUDE_PROJECT_DIR` / cwd is
   writable from the hook process for every topic (the Music topic cwd
   is `~/Music/rekordbox`). A fixed `~/.polygram` path sidesteps cwd
   variance.
3. **Hook-command portability.** `jq` may be absent; pick a dependency
   we control (node one-liner). Keep the command tiny + robust.
4. **Event volume.** A heavy turn fires many hooks; the ndjson +
   events-DB rows grow. Same order as `turn-phase-change`; acceptable,
   but H1 measures it.
5. **CLI version pin.** Hooks are CLI-internal like everything else
   the tmux backend reads — a version bump can change the event shape.
   Same pin discipline as the JSONL parser.
6. **Cleanup.** The per-session ndjson + settings file need a
   lifecycle (delete on kill / orphan-sweep). Small, but real.
7. **Does `SubagentStart` exist on exactly 2.1.142?** Confirmed in
   2.1.143 binary; H1 spike confirms on the pinned version (fall back
   to `Agent` tool_use + `SubagentStop` if `SubagentStart` is absent).

## Goal restated

Stop showing the user fear when the agent is working. Give the tmux
backend the same *understanding* of a turn's internal state that the
SDK backend has — which subagent, which tool, which step, done or
not — sourced from claude's own hook stream, and reflect it. The
timeout problem dissolves as a side effect: a turn that fires hooks is
visibly progressing and is never falsely killed.
