# 0.9.0 Cleanup — Simplicity Review

> Reviewer angle: bias toward "delete more." The cleanup achieved a
> net −2919 lines but introduced one new abstraction (the thin pm
> wrapper) and left several vestigial structures from the deleted
> requestRespawn machinery. None of these are critical; collectively
> they're ~150 more lines and a layer that could go.

## Severity ranking

- **HIGH**: speculative abstraction with a documented "in case" justification, or dead code with a control path.
- **MEDIUM**: dead state / dead callbacks the runtime never touches.
- **LOW**: stale or noisy comments that mislead future readers but don't change behaviour.

---

## HIGH-1 — `lib/pm-router.js` is pure ceremony. Delete the file.

**File**: `/Users/ivanshumkov/Projects/shumkov/polygram/lib/pm-router.js` (40 lines)

The entire surviving module is:

```js
function createPmRouter({ pm } = {}) {
  if (!pm) throw new TypeError('pm required');
  return pm;
}
```

That's a guard clause and an identity return. It does not wrap, transform,
forward, or own anything. The header comment justifies it explicitly as a
"forward-compatible seam" for "a future alternate pm impl (a pi-agent-core
adapter, a synthetic test pm)" — a textbook YAGNI violation. There is no
alternate pm. There is no committed plan to ship one. The only consumer
(`polygram.js:3993`) does:

```js
const sdkPm = new ProcessManagerSdk({ ...pmOpts, spawnFn: buildSdkOptions });
pm = createPmRouter({ pm: sdkPm });
```

If/when a second pm impl arrives, re-introducing a router is a 30-minute
edit at one site. Keeping it now buys nothing and obligates the reader to
chase an indirection that does not indirect.

What you'd lose by deleting `lib/pm-router.js`:

- 40 lines of code.
- 50 lines of `tests/pm-router.test.js` that prove the identity function is the identity function.
- 2 lines in `polygram.js` (the require + the wrapper call → direct assignment).
- The comment in `lib/pm-interface.js` that points at `pm-router.js`.

What you'd lose functionally: nothing. The error case
(`!pm → throw`) is a defensive guard against a constructor mistake one
file over. If you fear the `new ProcessManagerSdk(...)` could yield a
falsy value, that fear is misplaced; if you don't, the throw is dead.

**Recommendation**: delete `lib/pm-router.js`, delete
`tests/pm-router.test.js`, and inline `polygram.js:3993` to
`pm = sdkPm;` (or just rename `sdkPm` → `pm` at construction).
Net delta: ~−95 LOC.

If the team really wants to preserve "the seam", a one-line comment in
`polygram.js` ("If we ever add a second pm impl, route here") is
strictly better than a file that exists only to be the seam.

## HIGH-2 — `lib/pm-interface.js` is JSDoc looking for an interface.

**File**: `/Users/ivanshumkov/Projects/shumkov/polygram/lib/pm-interface.js` (97 lines)

This file has:

- 95 lines of JSDoc `@typedef`.
- 2 lines of code: `module.exports = {};`.
- A single implementer post-cleanup: `lib/process-manager-sdk.js`.

Interface contracts earn their keep by **forcing** multiple implementers
to agree. With one implementer, the JSDoc on `process-manager-sdk.js`'s
class itself is the canonical contract — adding a separate "interface"
file is documentation-of-documentation.

The header comment still describes a multi-pm world ("Both
`lib/process-manager.js` (CLI pm) and `lib/process-manager-sdk.js`
(SDK pm) implement this. `lib/pm-router.js`'s `createPmRouter()`
forwards calls to one or the other based on per-chat policy.") — a
factually wrong description of post-cleanup reality. The CLI pm is
deleted. The router doesn't forward.

Even the `tests/pm-interface-contract.test.js` file admits this isn't
testing real implementers — it tests a `_helpers/fake-pm` against the
canonical surface, i.e., it tests that the fake matches the JSDoc. This
is a contract test for documentation.

**Recommendation**: delete `lib/pm-interface.js`. Move any genuinely
useful `@typedef` (e.g., `PmEntry`, `PmSendResult`) inline into
`lib/process-manager-sdk.js` next to the class. Delete or sharply
rewrite `tests/pm-interface-contract.test.js` — if the SDK pm itself
asserts the shape of `send()`'s return value, that's the right place.
Net delta: ~−95 LOC + ~−100 LOC of contract test churn.

**File**: `/Users/ivanshumkov/Projects/shumkov/polygram/lib/process-manager-sdk.js`

**Recommendation**: delete the field on line 333 and the `if` block on
640–642. Net delta: −5 LOC and one less dead branch in the hot path.

## HIGH-4 — `onRespawn` callback wired in `polygram.js` is never invoked.

**File**: `/Users/ivanshumkov/Projects/shumkov/polygram/polygram.js`, lines 3964–3987.

`pmOpts.onRespawn` is a 24-line callback (with 7 lines of comment
defending its purpose) registered against the SDK pm constructor. Grep
for `onRespawn` in `lib/process-manager-sdk.js` returns zero hits — the
SDK pm never reads or calls this option. It's dead from the moment of
construction.

The matching variable name `respawn` in `handleConfigCallback` (lines
1817–1827) and the `applyConfigChange.return.queued` field
(lines 2168, 2172, 2174) are the same archaeology: the call sites that
fed into the deleted `requestRespawn` graceful-drain machinery. The CLI
pm called `onRespawn` after the graceful-drain swap completed; SDK pm
applies changes synchronously via `setModel` / `applyFlagSettings` and
has nothing to fire.

**Recommendation**: delete the `onRespawn` callback (lines 3964–3987,
24 lines). If the team genuinely wants a "✓ Using sonnet now"
confirmation message after a config swap, post it inline at the
`applyConfigChange` site where the swap happens — the current
indirection survives only because nothing consumes it. Net delta:
−24 LOC plus closure of an obsolete contract surface.

## MEDIUM-1 — `applyConfigChange` returns vestigial `{ queued }`.

**File**: `polygram.js:2165–2175`

```js
const applyConfigChange = async (setting, value) => {
  if (setting === 'effort' && typeof pm.applyFlagSettings === 'function') {
    const ok = await pm.applyFlagSettings(sessionKey, { effortLevel: value });
    return { queued: 0, anyActive: !ok };
  }
  if (setting === 'model' && typeof pm.setModel === 'function') {
    const ok = await pm.setModel(sessionKey, value);
    return { queued: 0, anyActive: !ok };
  }
  return { queued: 0, anyActive: false };
};
```

`queued` is always 0. Both call sites (`polygram.js:2188, 2208`)
destructure only `{ anyActive }`. Drop `queued` from the return. While
you're there: the function returns `{anyActive}` rather than just
`anyActive` — that compound shape is the last fingerprint of a richer
return that no longer exists.

The two-branch sentinel-fallback shape also reads odd: the third path
(`return { queued: 0, anyActive: false };`) only fires if the SDK pm
loses `applyFlagSettings` or `setModel` — i.e., never, since those are
hard-coded methods on the only pm impl. The `typeof === 'function'`
feature-detect was meaningful in the dual-pm world (CLI pm didn't have
these methods); single-pm, it's defensive code for a future regression
in SDK pm itself. Drop it.

**Recommendation**:

```js
const applyConfigChange = async (setting, value) => {
  if (setting === 'effort') return !(await pm.applyFlagSettings(sessionKey, { effortLevel: value }));
  if (setting === 'model')  return !(await pm.setModel(sessionKey, value));
  return false; // unknown setting; chatConfig still updated above
};
// Call sites:
const anyActive = await applyConfigChange('model', newModel);
```

Net delta: −7 LOC, less ceremony, same behaviour.

The same simplification applies to `handleConfigCallback` lines
1817–1827 — the `respawn = { killed: ok }` / `anyActive = !respawn.killed`
indirection is the CLI-pm shape preserved verbatim. Collapse to a
direct boolean.

## MEDIUM-2 — `tests/pm-interface-contract.test.js` opt-in fake matches a deleted contract.

**File**: `/Users/ivanshumkov/Projects/shumkov/polygram/tests/pm-interface-contract.test.js`

The test asserts that "optional methods are off by default" and require
explicit opt-in: `steer`, `setModel`, `applyFlagSettings`,
`setPermissionMode`, `drainQueue`, `interrupt`, `resetSession`. The
"optional" framing was meaningful when CLI pm was missing these methods.
Single-pm, every one of these IS implemented by SDK pm, so the
"optional" axis tests a property of the fake pm helper, not of any real
pm. The test can only fail if someone changes the fake.

**Recommendation**: when you delete `lib/pm-interface.js` per HIGH-2,
delete this file too. If you keep the interface file, retitle the test
to "fake-pm helper" and remove the "optional" framing. ~−100 LOC.

## LOW-2 — rc.X / Pre-rc.Y archaeological comments.

**File**: `polygram.js` — 162 lines containing `rc.`/`Pre-rc.`/`0.X.Y` references.

Sample audited around `pm.has()` / `pm.send()` / `streamer.onChunk`:

- **Lines 993–998** ("0.4.8: per-session concurrent dispatch. No FIFO
  polygram-level queue any more …"): describes a 0.4.8 design choice
  that's still current. Keep — it explains *why* the pm.send call is
  inside `stdinLock.acquire()`.
- **Lines 3279–3298** ("0.8.0 Phase 2 step 2: under SDK pm, prefer
  interrupt() + drainQueue() … Falls back to pm.kill() under CLI pm,
  which is the original behaviour. … Pre-0.6.5 this was
  pm.killChat(chatId) which fanned out across all topics under
  isolateTopics=true …"): the "Falls back to pm.kill() under CLI pm"
  sentence is now FALSE — there's no CLI pm to fall back to. The
  Pre-0.6.5 archaeology is interesting but doesn't help a reader
  understand current behaviour. Trim to: "Why interrupt + drainQueue
  instead of kill: keep the Query alive (cheap to reuse), no respawn
  cost. Kill ONLY the user's own session (pm.killChat would fan out
  across topics)."
- **Lines 3785–3792** ("0.8.0-rc.16: heartbeat the reactor so long
  text generation doesn't trip the 10s STALL → 🥱 / 30s TIMEOUT → 😨
  promotion. Pre-rc.16 the reactor only got setState calls at turn
  start (THINKING) and per-tool (CODING/TOOL/...); pure text turns hit
  STALL within 10s of streaming. heartbeat() re-arms the stall timers
  without changing the visible emoji."): the **why** (heartbeat exists
  to prevent stall promotion during pure text) is load-bearing. The
  rc.16 attribution is noise. Trim to "heartbeat the reactor so long
  text generation doesn't trip the 10s STALL → 🥱 promotion".

**Pattern**: rc.X comments fall into two buckets.

1. **Load-bearing**: comments where the *behaviour* explained survives, and the rc-tag is just provenance. Strip the rc-tag, keep the reasoning.
2. **Migration noise**: comments that justify why the code differs from a *deleted* prior version. These tell a reader "trust me, the old way was bad" without showing the old code. Delete entirely.

A future reader of this 4333-line file is not going to git-blame each
rc-tag back to the commit. They want to know what the code does *now*.

**Recommendation**: not a mechanical sweep — needs taste per comment.
Estimate ~80 of the 162 hits are migration noise that can be deleted
with no information loss; ~40 are load-bearing where the rc-tag should
be stripped but the reasoning kept; ~40 are genuinely about decisions
that still inform behaviour and should stay verbatim. Could be a
follow-up pass; not blocking 0.9.0.

## Final assessment

The cleanup branch achieved its primary goal (CLI pm and dual-pm
router gone, code halved). What remains is **cosmetic over-engineering**
in two flavours:

1. **Speculative abstraction**: `pm-router.js` and `pm-interface.js`
   were both justified to me explicitly as "in case we ship a second
   pm impl." This is exactly the YAGNI wedge — ~190 LOC of pure layer
   defending a future that may never arrive. Delete now; re-add (as a
   30-line file) the day a second impl actually lands.
2. **Vestigial state**: `needsRespawn`, `onRespawn`, `{queued: 0,
   anyActive}`, `respawn = { killed: ok }` — all are fingerprints of
   the deleted `requestRespawn` mechanism. The CLI pm shaped these
   structures; the SDK pm doesn't need them. Each one looks like
   "real code" to a future reader and will resist removal further if
   left to soak.

**Recommended action**: ship 0.9.0 as-is (the cleanup is sound),
land HIGH-1, HIGH-2, HIGH-3, HIGH-4, MEDIUM-1, MEDIUM-2 as a
follow-up `0.9.1-cleanup` in the same window. LOW items can ride
alongside or be deferred.

**Complexity score**: LOW for the deleted scope, MEDIUM-LOW for
what remains. The router/interface pair is the one place the cleanup
overshot on caution.
