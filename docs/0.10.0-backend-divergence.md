# SDK vs Tmux backend — known divergence

The Process abstraction (`lib/process/process.js`) guarantees behavioural
parity for everything in the contract suite (`tests/process-contract.test.js`,
26 scenarios × 2 backends = 52 tests). This doc enumerates what's
DELIBERATELY different — structural backend traits that aren't fixable
with more tests, and that polygram operators should know before
switching a chat from `pm: 'sdk'` to `pm: 'tmux'`.

If you find a divergence not listed here, either (a) it's a bug and
should be fixed, or (b) the contract suite is missing the scenario —
add it.

---

## 1. Live typing granularity

| Backend | Behaviour |
|---|---|
| sdk | Telegram bubble updates per-token. Each SDK stream event delivers a delta; polygram edits the message progressively (word-by-word typing animation). |
| tmux | Telegram bubble updates per assistant-message segment. The session JSON log writes whole messages, not per-token deltas. Updates "pop in" by paragraph. |

**Why it's structural:** the JSON log is the only structured event
channel claude TUI emits, and it only writes after each message
completes. The alternative — polling `tmux capture-pane` every 50ms
for diff — is brittle (TUI rendering ornaments, terminal width
artifacts) and was tried in earlier iterations.

**User impact:** noticeable on long replies. Short replies (1-2
sentences) feel similar. Tool-heavy turns OK because the segments are
naturally chunky on both backends.

## 2. Tool-approval flow (different mechanics, same UX)

| Backend | Mechanism |
|---|---|
| sdk | SDK calls polygram's `canUseTool` callback synchronously inside the Query iteration. Polygram posts an approval card to `adminChatId`, races user click vs timeout, returns `{behavior: 'allow' \| 'deny'}`. |
| tmux | TUI shows in-pane prompt "Do you want to do this?". TmuxProcess detects via `APPROVAL_PROMPT_RE` in the capture-pane poll, parses tool + input, emits `approval-required` event with `respond()` closure. Polygram's `onApprovalRequired` handler calls the SAME `makeCanUseTool(sessionKey)(tool, input)` plumbing as SDK, then routes the verdict back: `1`/`2`/`3` + Enter into the TUI. |

**Same UX:** approval card looks identical, `chat_tool_decisions`
persistence works for both, 4-button keyboard works for both, timeout
race works for both. Operator can't tell the chat is on tmux from the
approval flow.

**Differences that ARE real:**

- **Opt-in flag:** SDK auto-uses `canUseTool` when `apprCfg.adminChatId`
  is configured. Tmux opts in by setting `permissionMode: 'default'`
  in chatConfig — otherwise it stays on `acceptEdits` (auto-approve)
  as before for back-compat.
- **Tool-input shape:** SDK gets the typed input object directly from
  Claude. Tmux parses the parenthesised string from the TUI line via
  `lib/tmux/tui-tool-input.js` — common tools (`Bash`/`Read`/`Write`/
  `Glob`/`WebFetch`/`WebSearch`) get their canonical field; unknown
  tools land as `{ _raw: <str> }`. The approval card still renders
  readably either way; `chat_tool_decisions` dedup may differ for
  unknown tools (less aggressive matching).
- **Format drift risk:** the TUI's prompt format could shift across
  claude versions. SDK's typed callback is stable. The
  `APPROVAL_PROMPT_RE` regex is intentionally permissive but isn't a
  contract.
- **Tools below the threshold:** TUI's `--permission-mode default`
  also handles tools the SDK would just allow (low-risk Read on cwd).
  Both surface to the user as "do you want to" prompts on tmux.
  Polygram's `gatedTools` config filters which actually request
  approval — but tmux will see EVERY prompt and pass them through, so
  if `gatedTools` is narrow, most tmux prompts auto-approve via the
  same plumbing.

## 3. Latency tax on short replies

| Backend | Behaviour |
|---|---|
| sdk | Turn resolves the moment the SDK fires its result event. |
| tmux | Turn resolves on JSON-log result event OR (fallback) capture-pane quiescence + late-grace window. For replies where the TUI shows "ready" before the JSON log has fully flushed, we wait `lateGraceMs` (default 1500 ms) for the JSON event to catch up so we use its structured text instead of the brittle pane diff. |

**Why it's structural:** the two signals race; whichever wins
determines the path. JSON log usually wins, but for very short replies
the TUI signals ready first.

**User impact:** ~1-2 second perceptible delay on short replies on
tmux. Long replies (5+ seconds) — invisible.

**Workaround:** lower `lateGraceMs` per chat. Faster turns at the cost
of more capture-pane-diff fallback (slightly less reliable text
extraction). Default 1500 is the conservative midpoint.

## 4. RSS footprint

| Backend | Per chat |
|---|---|
| sdk | ~50 MB |
| tmux | ~545 MB (10× heavier) |

**Why it's structural:** tmux backend hosts a full `claude` TUI
process per chat (Node + claude-agent-sdk + electron-ish memory).
SDK backend shares a single `claude-agent-sdk` instance across chats.

**User impact:** LRU eviction kicks in more aggressively for tmux
chats. With default `budget=10` and weighted costs (sdk=1, tmux=3),
you can keep ~10 SDK chats hot OR ~3 tmux chats — exceed that and
older entries get evicted (cold-spawn delay on the next message).
This is exactly what `Process.cost` weighting handles automatically.

## 5. `resetSession.closed` semantic

| Backend | After `resetSession()` |
|---|---|
| sdk | Returns `{ closed: true, drainedPendings: N }`. The SDK Query is closed; next `pm.send` spawns a fresh Query (small spawn delay). |
| tmux | Returns `{ closed: false, drainedPendings: N }`. Same TUI process stays alive; `/new` is pasted to clear context. Next `pm.send` reuses the same PTY (no spawn delay). |

**Why it's structural:** SDK Queries are bound to a session_id and
must be torn down to start fresh. TUIs support `/new` to clear context
within the same process.

**User impact:** invisible. Both produce a fresh-context conversation
on the next user message. Tmux is marginally faster for the
immediately-next turn.

## Contract suite coverage

For every behavior NOT listed above, the contract suite asserts parity.
Run `node --test tests/process-contract.test.js` — it executes 26
scenarios twice (once per backend) and BOTH must pass for the
abstraction to be considered intact.
