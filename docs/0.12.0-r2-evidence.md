# R2 risk assessment — Anthropic `--dangerously-load-development-channels` flag removal

Phase 0.5 deliverable. Date: 2026-05-27. Researched via `ce-web-researcher`.

## Verdict

**LOW probability of removal within 6 months.**

Phase 4 deletion gate: **PROCEED with TmuxProcess deletion as planned.**

## Evidence summary

The `--dangerously-load-development-channels` flag is explicitly documented in Anthropic's official channels reference as the intended mechanism for custom channel development during the research preview. The research preview itself shows no signs of ending — active bug reports are still being filed and tracked (April 2026), GA language is absent from release notes through May 2026, and Anthropic has published a full enterprise allowlist architecture (`allowedChannelPlugins`) that extends the flag's role rather than replacing it.

## Key signals (with citations)

- **Flag is load-bearing in official docs, not incidental.** The channels reference page explicitly states: *"During the research preview, custom channels aren't on the approved allowlist. Use `--dangerously-load-development-channels` to test locally."* Anthropic wrote the bypass into the developer workflow, not around it.
  Source: https://code.claude.com/docs/en/channels-reference (last confirmed live May 2026)

- **Research preview explicitly ongoing, no GA timeline stated.** The channels page states: *"Channels are a research preview feature. Availability is rolling out gradually, and the `--channels` flag syntax and protocol contract may change based on feedback."* No removal date, no GA milestone, no deprecation warning anywhere in the docs.
  Source: https://code.claude.com/docs/en/channels

- **Enterprise path preserves dev-flag as escape hatch.** The new `allowedChannelPlugins` org setting explicitly documents: *"An empty array blocks all channel plugins from the allowlist, but `--dangerously-load-development-channels` can still bypass it for local testing."* Anthropic architectured around the flag, not over it.
  Source: https://code.claude.com/docs/en/channels#restrict-which-channel-plugins-can-run

- **Active bug reports filed in April 2026 — Anthropic treating it as a supported surface.** GitHub issue #46125 (Windows notification failure with the flag) filed April 10, 2026 — no "won't fix / flag is being removed" response.
  Source: https://github.com/anthropics/claude-code/issues/46125

- **Release notes (v2.1.x, May 2026) show channels expansion, not contraction.** Recent releases added `--channels` permission relay and expanded channel tooling. No deprecation notices present.
  Source: https://releasebot.io/updates/anthropic/claude-code

## Counterfactuals (what would reduce confidence in LOW)

- Anthropic announces a plugin submission/approval path that removes the need for local bypass — this would make the dev flag redundant and a cleanup target.
- Channels exit research preview and Anthropic moves to a strict allowlist-only model (making the dev flag a security liability they want to remove).
- A high-severity prompt injection incident traced to the dev flag triggers an emergency removal.

**None of these signals are present today.**

## Recommendation for polygram 0.12

1. **Proceed with TmuxProcess deletion in Phase 4 as planned.** R2 risk does not justify keeping ~3300 LoC around as a kill-switch backend.

2. **Low-cost defensive hedge:** add a `claude --version` check in the CliProcess boot path that detects whether `--dangerously-load-development-channels` is still accepted. Emit a clear error message if a future binary drops the flag, rather than silently failing on first turn. ~5 LoC. Tracked under the [Phase 0.6 binary-bump preflight script](./0.12.0-cli-driver-plan.md#phase-0--spike--validation-1d) — the preflight is invoked before binary bumps; this is the per-spawn runtime guard.

3. **Close Q3** (TmuxProcess as no-subscription kill-switch backend) as resolved: default no, delete as planned. Already reflected in the plan's [Open questions resolved here](./0.12.0-cli-driver-plan.md#open-questions-resolved-here) section.
